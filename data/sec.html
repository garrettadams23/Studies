🎟️ Kerberos Authentication Flow 4-STEP PROTOCOL ▶
Protocol — Source: CEH (Certified Ethical Hacker) + CISSP (Certified Information Systems Security Professional) Cheat Sheets
Kerberos — Ticket-Based Authentication (port 88)
Kerberos uses symmetric + asymmetric encryption. Default in Active Directory environments. Attacks: Kerberoasting (offline crack service ticket), Pass-the-Ticket (reuse TGT/TGS), Golden Ticket (forged TGT using KRBTGT hash).
KDC (Key Distribution Center)
Key Distribution Centre — central trust authority (runs AS + TGS)
AS
Authentication Service — validates identity; issues TGT (Ticket Granting Ticket)
TGS
Ticket Granting Service — issues service tickets upon valid TGT
TGT
Ticket Granting Ticket — proof of identity; valid for session
1
Client → KDC (AS)
Client sends AS-REQ with username in cleartext. No password sent yet.
2
KDC (AS) → Client
AS responds with TGT encrypted with KRBTGT (Kerberos Ticket Granting Ticket account) hash. Client decrypts AS-REP using their password-derived key. If incorrect password → cannot decrypt → fail.
3
Client → KDC (TGS)
Client presents TGT to TGS, requests service ticket for specific service (TGS-REQ).
4
KDC (TGS) → Client → Service
TGS issues service ticket encrypted with service account's hash. Client presents ticket to target service. Access granted without re-entering password.

🔒 TLS (Transport Layer Security) — Handshake, Cipher Suites & Certificate Chain SEC+ · SECX ▶
Transport Layer Security
How HTTPS (HyperText Transfer Protocol Secure) Actually Works — Step by Step
TLS (formerly SSL) provides confidentiality (encryption), integrity (MAC), and authentication (certificates) over any transport. Used by HTTPS (443), SMTPS (Simple Mail Transfer Protocol Secure) (465), IMAPS (993), and most modern protocols. Current standard: TLS 1.3 (2018).
▸ TLS 1.2 HANDSHAKE (4 ROUND TRIPS)
1
ClientHello
Client → Server. Sends: TLS version, random number (client_random), list of supported cipher suites, compression methods, extensions (SNI, ALPN, supported curves).
2
ServerHello + Certificate
Server → Client. Selects cipher suite and TLS version. Sends server_random. Sends its X.509 certificate chain. Optionally sends ServerKeyExchange (for DHE/ECDHE).
3
Client Key Exchange
Client validates the certificate chain. Generates pre-master secret. If RSA (Rivest-Shamir-Adleman): encrypts with server's public key. If DHE/ECDHE: sends client DH (Diffie-Hellman) public value. Both sides derive the master secret and session keys independently.
4
Finished (both sides)
Both send a Finished message: HMAC (Hash-based Message Authentication Code) of the entire handshake transcript, encrypted with the new session keys. If both verify correctly — encrypted data transfer begins.

🧒Security Basics in Plain EnglishSec+ • Start Here▶
BIG IDEA
The CIA Triad (No Spies Involved)
Security protects three things. Confidentiality = only the right people can see it (a sealed letter). Integrity = nobody changed it secretly (a tamper seal). Availability = it's there when you need it (the door is unlocked for you). Almost every security idea protects one of these three.
ANALOGY
Authentication vs. Authorization
Authentication proves who you are (showing your ID at the door). Authorization decides what you're allowed to do once inside (your key only opens certain rooms). You authenticate first, then you're authorized.
ANALOGY
Encryption = a Locked Box
Encryption scrambles data so only someone with the key can read it. Picture putting a note in a locked box: anyone can carry the box, but only the key-holder can open it. That's why 'https' sites are safer.
HABIT
Passwords → Passphrases + MFA
Long beats complicated: 'correct-horse-battery-staple' is stronger and easier than 'P@ss1'. Multi-factor authentication (MFA) adds a second proof (a code on your phone) so a stolen password alone isn't enough.
MINDSET
Least Privilege
Give people (and programs) only the access they truly need — nothing extra. The new intern doesn't get the master key. Less access means less damage if an account is ever stolen.
STREET-SMART
Spotting Phishing
Phishing is a fake message that tricks you into clicking or typing a password. Red flags: urgency ('act now!'), odd sender addresses, surprise links, and requests for credentials. When unsure, don't click — verify through a channel you trust.

🔑 Passwords & Hashing — How Logins Are Stored Safely SEC • Start Here ▶
NEVER STORE PLAINTEXT
The Golden Rule of Password Storage
Databases get breached. If passwords are stored as-is, every user's password is exposed instantly. Instead, store a hash — a one-way transformation that cannot be reversed. When a user logs in, hash what they typed and compare hashes.
WHAT IS A HASH
One-Way Fingerprint
A hash function takes any input and produces a fixed-length output. Same input ALWAYS produces same output. Even one character change completely changes the hash (avalanche effect). You cannot go from hash → original (one-way).
import hashlib text = "hunter2" h = hashlib.sha256(text.encode()).hexdigest() # f52fbd32b2b3b86ff88ef6c490628285f482af15ddcb29541f94bcf526a3f6c7 text2 = "hunter3" # one char different h2 = hashlib.sha256(text2.encode()).hexdigest() # 7a20f6f8c04b1a590a39c74b4f6b3c4a8e6a7f1c2d3e4f5a6b7c8d9e0f1a2b3 # Completely different — avalanche effect
SALTING
Why Two Users With Same Password Need Different Hashes
Without salts, two users with "password123" produce the same hash — attackers can pre-compute tables (rainbow tables) and look up hashes instantly. A salt is a random value added to the password before hashing. Every user gets a unique salt. Rainbow tables become useless.
RIGHT TOOLS FOR PASSWORDS
Use bcrypt, scrypt, or Argon2
SHA-256 is fast — that's GOOD for verifying file integrity, BAD for passwords (attackers can try billions/sec). bcrypt, scrypt, and Argon2 are deliberately slow and memory-hard. They automatically handle salting. Never hand-roll password hashing.
# pip install bcrypt import bcrypt # Hash when user registers password = "my_secure_pass" hashed = bcrypt.hashpw(password.encode(), bcrypt.gensalt()) # Verify on login entered = "my_secure_pass" if bcrypt.checkpw(entered.encode(), hashed): print("Login OK")
STRONG PASSWORDS
Length Beats Complexity
A 20-character random passphrase is stronger than "P@$$w0rd!" — and much easier to remember. Use a password manager (Bitwarden, 1Password, KeePass). Generate unique passwords for every site. Enable MFA (Multi-Factor Authentication) everywhere possible.
📲 Multi-Factor Authentication — Layers of Proof SEC • Foundation ▶
THREE FACTORS
Something You Know, Have, or Are
Knowledge factor — something you know: password, PIN, security questions (weakest).
Possession factor — something you have: phone (SMS code, authenticator app), hardware token (YubiKey), smart card.
Inherence factor — something you are: fingerprint, face, iris, voice.
MFA (Multi-Factor Authentication) requires 2 or more different factor types. Two passwords is NOT MFA.

HOW TOTP WORKS
Time-Based One-Time Passwords
During setup, the server shares a secret key with your phone (usually via QR code). Every 30 seconds, both your phone AND the server compute HMAC-SHA1(secret + current_time_window). They should match. An attacker needs the secret AND the current window — that's why TOTP codes expire so fast.
🎣 Phishing — Anatomy of a Social Engineering Attack SEC • Threat Awareness ▶
WHAT IS PHISHING
Deception, Not Hacking
Phishing attacks trick people into giving up credentials, installing malware, or sending money. They exploit psychology, not software vulnerabilities. No patch exists for human instinct. The name comes from "fishing" — casting bait and waiting for a bite.
ATTACK VARIETIES
Phishing, Spear, Whaling, Vishing, Smishing
Phishing — mass emails, generic "Dear Customer" bait.
Spear phishing — targeted at a specific person using research (LinkedIn, social media). High success rate.
Whaling — targets C-suite executives. Higher payoff.
Vishing — voice phishing by phone. "This is Microsoft Support…"
Smishing — SMS phishing. "Your package is stuck, click here."
Business Email Compromise (BEC) — impersonates a CEO to trick finance into a wire transfer.
RED FLAGS
How to Spot a Phishing Attempt
• Urgency or fear: "Your account will be suspended in 24 hours!"
• Mismatched URLs (Uniform Resource Locator): display text says google.com, actual link is g00gle.evil.com
• Unexpected attachment — especially .exe, .docm, .zip files
• Slightly wrong sender address: support@amaz0n.com vs amazon.com
• Grammar errors (though AI-generated phishing now has perfect grammar)
• Requests for credentials, wire transfers, or gift cards via email
• Too-good-to-be-true offers
DEFENSE
What Actually Stops Phishing
Technical: email filtering (spam/malware), DMARC/SPF/DKIM to prevent spoofing, URL rewriting, MFA (Multi-Factor Authentication) (even if credentials are stolen, attacker can't log in).
Human: regular security awareness training with simulated phishing campaigns. People need to fail safely in training, not in real attacks.
Process: out-of-band verification (call the CEO on a known number before wiring $500k).
🔒 TLS (Transport Layer Security) & HTTPS (HyperText Transfer Protocol Secure) — How Secure Connections Work SEC • Foundation ▶
THE PROBLEM
HTTP (HyperText Transfer Protocol) Is Plaintext — Anyone Can Read It
When you send a form over HTTP, the data travels through multiple hops (your router, ISP, CDN, etc.) as readable text. Anyone on those hops can see your password, credit card, messages. TLS (Transport Layer Security) encrypts the connection so even if someone intercepts the traffic, all they see is gibberish.
TLS HANDSHAKE
Establish Trust + Exchange Keys
1. Client → Server: "Hello. I support these cipher suites and TLS versions."
2. Server → Client: "Hello. Here's my certificate. We'll use cipher X."
3. Client: Verify certificate against trusted CA (Certificate Authority) list.
4. Key exchange (ECDHE): Both sides derive the same symmetric session key without ever transmitting it (Diffie-Hellman magic).
5. All further communication encrypted with that session key.
The asymmetric crypto (certificates) is only used during handshake. The bulk encryption uses faster symmetric crypto.
CERTIFICATES
Digital Identity Documents
A TLS certificate binds a domain name to a public key, signed by a Certificate Authority (CA) the browser trusts. The chain of trust:
Root CA → (built into OS/browser)
Intermediate CA → (issued by root)
End-entity cert → (your server's cert)
If you trust the root, and the root signed the intermediate, and the intermediate signed your cert, you trust your cert.
CERT VALIDATION LEVELS
DV vs OV vs EV
Domain Validated (DV) — CA just verifies you control the domain. Free (Let's Encrypt). Shows padlock in browser. Good for most sites.
Organization Validated (OV) — CA verifies organization identity. More trust signal for businesses.
Extended Validation (EV) — rigorous identity check. Historically showed green bar with company name (most browsers dropped this UI).

🔐 Encryption Fundamentals — Symmetric vs Asymmetric SEC • Foundation ▶
SYMMETRIC ENCRYPTION
Same Key to Lock and Unlock
One key encrypts AND decrypts. Fast, efficient for large data. Problem: key distribution — how do you securely share the key with the other party? Best algorithms: AES-256 (gold standard), ChaCha20. Used for: encrypting data at rest, bulk data transfer after handshake.
ASYMMETRIC ENCRYPTION
Public Key + Private Key
Two mathematically linked keys. Public key encrypts (share freely — give to everyone). Private key decrypts (keep secret). Solves key distribution: encrypt with their public key → only they can decrypt with their private key. Slower than symmetric. Best algorithms: RSA-2048+, ECC (Elliptic Curve Cryptography) (smaller keys, same strength). Used for: TLS (Transport Layer Security) handshake, SSH (Secure Shell) auth, digital signatures.

Keys1 shared keyKey pair (public + private)

DIGITAL SIGNATURES
Prove It Came From You and Wasn't Changed
Signing: hash the document, encrypt the hash with your PRIVATE key → signature.
Verifying: decrypt signature with sender's PUBLIC key → get hash. Hash the document yourself. If hashes match → not tampered, signed by private key holder.
Used in: software distribution (code signing), email (S/MIME, PGP), TLS certificates, git commits, JWT (JSON Web Token) tokens.
🪪 Identity & Access Management — Who Can Do What SEC • Foundation ▶
THE CORE PROBLEM
Authentication vs Authorization
Authentication (AuthN) — proving who you are. "I am Alice." Verified by password, biometric, token, or certificate.
Authorization (AuthZ) — what you're allowed to do. "Alice can read reports but not delete records." Enforced by permissions, roles, policies.
These are separate concerns. Getting them confused causes security holes (assuming that anyone logged in can do anything).
PRINCIPLE OF LEAST PRIVILEGE
Give Only What's Needed
Every user, service, and process should have the minimum permissions needed to do its job — and nothing more. An analytics service that reads data shouldn't have write permissions. A developer account shouldn't have production database access by default. When something is compromised, least privilege contains the blast radius.
RBAC vs ABAC
Role-Based vs Attribute-Based Access Control
RBAC (Role-Based) — assign roles to users; permissions attached to roles. Simple to manage at scale. "Alice is an Admin; Admins can do X, Y, Z." Standard in most systems.
ABAC (Attribute-Based) — permissions based on attributes of user, resource, environment. "Allow if user.department = finance AND resource.sensitivity = confidential AND time = business_hours." More flexible, harder to audit.
SSO & FEDERATION
One Login, Many Systems
SSO (Single Sign-On) — log in once, access many applications. Used with SAML (Security Assertion Markup Language) 2.0 or OIDC (OpenID Connect) (OAuth 2.0 extension). Benefits: one password to manage, one place to revoke access when someone leaves.
OIDC/OAuth 2.0 — modern standard for federated identity. "Login with Google" is OIDC. Google proves your identity to the app without giving the app your password.
SAML 2.0 — XML-based, enterprise standard. Used for enterprise SSO (Okta, Entra ID, Ping).
ZERO TRUST
Never Trust, Always Verify
Traditional security assumed: inside the network = trusted; outside = untrusted. Zero trust assumes breach and verifies every request regardless of source — even from inside the corporate network.
Principles:
• Verify explicitly — authenticate and authorize every request, every time
• Least privilege — minimal access, time-limited
• Assume breach — design as if attackers are already inside
⛓️ Supply Chain Security — Trust What You Build With SEC • Advanced Awareness ▶
WHAT IS SUPPLY CHAIN SECURITY
Attackers Go for the Builder, Not the Building
Modern apps depend on thousands of open-source packages. Attackers compromise upstream — a popular library, build tool, or CI/CD (Continuous Integration / Continuous Delivery) pipeline — and then automatically infect everything downstream that uses it. The SolarWinds breach (2020) infected 18,000 organizations via a compromised software update. The XZ Utils backdoor (2024) nearly compromised SSH (Secure Shell) servers worldwide.
SBOM
Software Bill of Materials
An SBOM is an inventory of every component in your software — all dependencies, their versions, and their licenses. Like an ingredients list for your app. When a critical vulnerability (Log4Shell, Heartbleed) drops, you can instantly check if you're affected by scanning your SBOM. Now required for software sold to US federal agencies.
DEPENDENCY HYGIENE
Practical Steps to Reduce Risk
• Pin versions: use requests==2.31.0 not requests>=2. Unpinned deps silently update and break.
• Verify hashes: pip install --require-hashes validates that downloaded packages match expected hashes.
• Use Dependabot or Renovate: automated PRs when dependencies have security updates.
• Audit regularly: pip audit, npm audit, cargo audit scan for known vulnerabilities.
• Don't install unknown packages: "typosquatting" packages (requestts, colors2) exist to compromise you.

KEY EXCHANGE
Diffie-Hellman — Sharing a Secret in Public
How do two parties agree on a secret key over a network an eavesdropper is watching? Diffie-Hellman key exchange lets them derive a shared secret without ever transmitting it — using math (modular exponentiation / elliptic curves) that's easy to compute forward but practically impossible to reverse. The eavesdropper sees the public exchanges but cannot compute the shared secret. This is the magic that makes HTTPS (HyperText Transfer Protocol Secure) possible.

Public-key crypto has a chicken-and-egg problem: how do you know a public key really belongs to who it claims? PKI solves this with certificates — a public key plus identity, vouched for (signed) by a trusted Certificate Authority (CA). Your browser/OS trusts a set of root CAs, forming a "chain of trust."

The Cardinal Rule of Crypto
Never invent your own cryptographic algorithm or implementation. Decades of expert scrutiny go into vetted libraries; homemade crypto is almost always broken in subtle ways. Your job is to use crypto correctly, not to build it.

Core Concept
What Is a SIEM?
A SIEM (Security Information and Event Management) system collects logs from every device in your environment, stores them in one place, and helps you search for threats. Think of it as the security camera DVR for your entire network.

Common SIEMs: Splunk, IBM QRadar, Microsoft Sentinel, Elastic SIEM (ELK), Wazuh (open-source).

What gets sent to a SIEM:
• Windows Event Logs (logins, process creation, PowerShell activity).
• Linux syslog / auditd events.
• Firewall and router logs (connections, blocks).
• DNS (Domain Name System) query logs (what domains hosts looked up).
• Web proxy / email gateway logs.
• Cloud trail logs (AWS CloudTrail, Azure Activity Log).

Logs are useless if you never look at them — the SIEM turns the firehose of logs into searchable, alertable data.

1. Understand the alert — what behaviour triggered it?
2. Check context — who is the user/host? Is this behaviour normal for them? (User Entity Behaviour Analytics).
3. Look before & after — what happened in the 10 minutes before and after the alert?
4. Corroborate — does another log source confirm it?
5. Classify — True Positive (real threat) / False Positive (benign) / Tuning Required (alert needs refinement).

You can't make someone make the right choice, yet you can pick up the pieces afterwards — if a developer opens port 22 to the world, the SIEM will catch the resulting attack. Document it, remediate, and use it to educate.
Beginner Malware Analysis – Static & Dynamic Analysis Fundamentals
Core Concept
What Is Malware Analysis?
Malware analysis is the process of understanding what a malicious file does. There are two approaches:

Static analysis — examine the file without running it. Look at strings, headers, imports, code structure.
Safe but limited — obfuscated malware hides its behaviour.

Dynamic analysis — run the file in an isolated sandbox and observe its behaviour (network calls, file writes, registry changes, process spawning).
Reveals behaviour but requires a safe environment.

The golden rule: never run malware on a production or host machine. Always use a dedicated, isolated VM (Virtual Machine) (snapshots enabled, no network or host-only network).

"Not my circus, not my monkey" — reverse engineering packed malware is a specialist skill. For most incidents, initial triage with static analysis + a sandbox is enough to classify the threat.

Dynamic Analysis
Sandbox Analysis & Behavioural Indicators
Free online sandboxes: Any.Run, Hybrid Analysis, Joe Sandbox. Upload the file; get a full behavioural report in minutes without running anything locally.

When reading a sandbox report, look for Indicators of Compromise (IoCs):

• Network: C2 (Command and Control) server IPs/domains, beaconing intervals, unusual ports.
• Files: dropped executables, modified startup folders, scheduled tasks created.
• Registry: HKCU\Software\Microsoft\Windows\CurrentVersion\Run — persistence mechanism.
• Processes: PowerShell spawned by Word/Excel (macro malware), cmd.exe spawned by browser.
• MITRE ATT&CK (Adversarial Tactics, Techniques and Common Knowledge): sandbox reports map behaviours to ATT&CK tactics and techniques.
Response
After Malware Is Confirmed — What To Do
You can't make someone make the right choice, yet you can pick up the pieces afterwards. When a user opens a phishing attachment:

1. Isolate the machine (pull the network cable or disable NIC via remote management).
2. Preserve a memory image if possible (winpmem on Windows).
3. Collect IoCs (hashes, IPs, domains, registry keys) from the malware analysis.
4. Hunt across the fleet — was the same file opened on other machines? (EDR/SIEM query by hash).
5. Block IoCs at firewall, DNS (Domain Name System), and email gateway.
6. Eradicate & restore — reimage from known good backup; patch the vulnerability that was exploited.
7. Document & improve — update playbooks, add detection rules, conduct phishing awareness training.
Beginner Container Security 101 – Why an Image Is Not a Sandbox
Core Concept
The Container Threat Model
Containers share the host's kernel — they are not as isolated as virtual machines. A misconfigured container can:

• Access the host filesystem (if volumes are mis-mounted).
• Escape to the host (kernel exploits, privileged mode).
• Run as root inside the container — and root in a container can sometimes mean root on the host.
• Pull a malicious base image from a public registry.

Defence-in-depth layers for containers:
1. Secure the image (what you build).
2. Secure the registry (where images are stored).
3. Secure the runtime (how containers run).
4. Secure the orchestrator (Kubernetes RBAC, network policies).

"Assume" makes an ass out of you and me — never assume a public Docker Hub image is safe just because it has many downloads. Scan it first.

Technical Controls
Email Authentication: SPF, DKIM (DomainKeys Identified Mail), DMARC (Domain-based Message Authentication, Reporting and Conformance)
These three DNS-based protocols work together to stop attackers from spoofing your domain in phishing emails:

• SPF (Sender Policy Framework) — a DNS (Domain Name System) TXT (Text Record) record listing which mail servers are allowed to send for your domain.
• DKIM (DomainKeys Identified Mail) — cryptographically signs outgoing emails so receivers can verify they weren't altered in transit.
• DMARC (Domain-based Message Authentication) — tells receiving servers what to do when SPF/DKIM checks fail (quarantine, reject) and where to send reports.

Defence Mindset
"Never Trust User Input" — The Golden Rule
"Assume" makes an ass out of you and me — and nowhere is this truer than in web development. Every single piece of data that comes from outside your application — form fields, URL (Uniform Resource Locator) parameters, HTTP (HyperText Transfer Protocol) headers, cookies, file uploads, even data from "trusted" third-party APIs (Application Programming Interface) — must be treated as potentially hostile until validated.

Defence in depth for web apps:
• Validate input on the server (client-side validation is a UX nicety, not a security control — it's trivially bypassed).
• Use parameterised queries / ORMs (Object-Relational Mapping) — never string-concatenate SQL.
• Encode output based on context (HTML, JS, URL, SQL each need different encoding).
• Apply the principle of least privilege to database accounts — your web app's DB user shouldn't be able to DROP TABLE.
• Keep dependencies updated — run npm audit, pip-audit, or Dependabot regularly.
• Practice on intentionally vulnerable apps: OWASP Juice Shop, DVWA, PortSwigger Web Security Academy (all free, all legal).
Beginner API (Application Programming Interface) Security – OAuth2, JWT (JSON Web Token) & Token-Based Authentication
Core Concept
Why Modern APIs Don't Use Passwords Directly
Imagine giving your house key (password) to every app that needs to check your mailbox. If one app is compromised, your whole house is at risk. Token-based authentication solves this: you get a limited, revocable, expiring "guest pass" instead of handing out your master key.

The vocabulary you'll see everywhere:
• Authentication — "Who are you?" (proving identity).
• Authorization — "What are you allowed to do?" (granting permissions).
• Token — a piece of data that proves you've already authenticated, so you don't have to send your password every single request.

"Assume" makes an ass out of you and me — never assume "the user is logged in" means "the user is allowed to do this specific action." Authentication and authorization are different checks — confusing them is the root of A01 (Broken Access Control).
OAuth2
OAuth2 – The "Sign in With Google" Flow
OAuth2 is the protocol behind every "Sign in with Google/GitHub/Microsoft" button. It lets an app access your data on another service without ever seeing your password for that service.

Key roles in OAuth2:
• Resource Owner — you, the user.
• Client — the app requesting access (e.g. a scheduling tool that wants to read your Google Calendar).
• Authorization Server — issues tokens (e.g. Google's login servers).
• Resource Server — holds your data and checks tokens (e.g. the Google Calendar API).
─── The Authorization Code Flow (most common, most secure) ──── 1. You click "Sign in with Google" on ScheduleApp 2. ScheduleApp redirects you to Google's login page GET https://accounts.google.com/o/oauth2/auth ?client_id=schedule_app_123 &redirect_uri=https://scheduleapp.com/callback &scope=calendar.readonly &response_type=code 3. You log in to GOOGLE directly (ScheduleApp never sees your password) 4. Google asks: "ScheduleApp wants to read your calendar. Allow?" 5. You click Allow → Google redirects back with a temporary CODE https://scheduleapp.com/callback?code=4/0AX4XfWh... 6. ScheduleApp's SERVER (not your browser) exchanges the code for tokens POST https://oauth2.googleapis.com/token { client_id, client_secret, code, grant_type: "authorization_code" } 7. Google returns: { "access_token": "ya29.a0AfH6...", ← used for API calls, short-lived "refresh_token": "1//0gLGn...", ← used to get new access tokens "expires_in": 3600 } 8. ScheduleApp now calls the Calendar API with the access token — never touching your Google password at any point in this process
JWT
JWT – JSON (JavaScript Object Notation) Web Tokens Decoded
A JWT (JSON Web Token) is a self-contained, signed token — three Base64-encoded parts separated by dots: header.payload.signature. The server can verify it's legitimate without a database lookup, because the signature proves it hasn't been tampered with.
# A JWT looks like this (one long string with two dots): eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJhbGljZSIsInJvbGUiOiJhZG1pbiJ9.SflKxwRJSMeKKF2QT4f... # Decoded HEADER (algorithm + token type): { "alg": "HS256", "typ": "JWT" } # Decoded PAYLOAD (claims — the actual data): { "sub": "alice", # subject = who this token is about "role": "admin", "iat": 1717689600, # issued-at timestamp "exp": 1717693200 # expiration timestamp — ALWAYS set this! } # SIGNATURE — proves the token wasn't modified # HMACSHA256(base64(header) + "." + base64(payload), SECRET_KEY) # Generate and verify with Python (PyJWT) import jwt, datetime token = jwt.encode( {"sub": "alice", "role": "admin", "exp": datetime.datetime.utcnow() + datetime.timedelta(hours=1)}, "your-secret-key", algorithm="HS256" ) try: payload = jwt.decode(token, "your-secret-key", algorithms=["HS256"]) print("Valid token for:", payload["sub"]) except jwt.ExpiredSignatureError: print("Token expired — request a new one") except jwt.InvalidTokenError: print("Invalid token — reject the request")
Common Mistakes
JWT & Token Pitfalls That Cause Breaches
"Not my circus, not my monkey" — but if you're reviewing someone else's API design, these are the red flags worth raising immediately:

• "alg: none" attack — some JWT libraries will accept tokens with no signature if you ask nicely. Always explicitly specify allowed algorithms when verifying.
• Storing JWTs in localStorage — accessible to any JavaScript on the page (XSS risk). HttpOnly cookies are safer for session tokens.
• No expiration — a stolen token that never expires is a permanent backdoor. Always set exp, and keep access tokens short-lived (minutes to hours).
• Sensitive data in the payload — JWT payloads are Base64-encoded, NOT encrypted. Anyone can decode and read them. Never put passwords or secrets in a JWT.
• No revocation strategy — once issued, a JWT is valid until it expires. Plan for "I need to log this user out everywhere right now" (e.g. short expiry + refresh token blocklist).

Beginner Encryption Basics – At Rest, In Transit, and Why "It's Encrypted" Isn't Enough
Concept

Encryption answers one question: "who can read this?"

Encryption transforms readable data ("plaintext") into scrambled data ("ciphertext") using a mathematical algorithm and a key — so that only someone holding the right key can reverse the process and read it. Everything interesting about encryption comes down to two follow-up questions: where is the data when it's protected, and who controls the key?

Concept

"At rest" vs "in transit" — two different problems

StateWhat it protects againstCommon technology
In transitSomeone intercepting data as it travels across a networkTLS/HTTPS, SSH (Secure Shell), VPN (Virtual Private Network) tunnels
At restSomeone gaining access to the storage itself — a stolen laptop, a compromised database, a discarded hard driveFull-disk encryption (BitLocker, LUKS, FileVault), database-level encryption, encrypted backups

A system can be excellent at one and weak at the other — HTTPS (HyperText Transfer Protocol Secure) protects your password on the way to the server, but if that server stores passwords in plaintext, the encryption in transit did nothing to protect you from a database breach. Both layers matter, and they solve different threats.

Concept

Symmetric vs asymmetric, in one paragraph each

Symmetric encryption (AES is the modern standard) uses the same key to lock and unlock — fast and efficient, but both parties need a way to share that key securely first. Asymmetric encryption (RSA, elliptic-curve) uses a pair of mathematically linked keys: anything encrypted with the public key can only be decrypted with the matching private key. This solves the "how do we share a key safely" problem — you can publish your public key everywhere, and only you can decrypt what people send you with it. In practice, most real systems (like HTTPS) use asymmetric encryption briefly to safely exchange a symmetric key, then switch to fast symmetric encryption for the actual data — getting the security benefits of both.

Hands-on

Seeing encryption in action

# Inspect the TLS certificate a website is presenting (in transit)
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null | openssl x509 -noout -subject -issuer -dates

# Encrypt and decrypt a file symmetrically with a passphrase (at rest, simple demo)
openssl enc -aes-256-cbc -salt -in report.txt -out report.txt.enc
openssl enc -aes-256-cbc -d -in report.txt.enc -out report_decrypted.txt

# Generate an asymmetric keypair and use it (the basis of SSH, GPG, and HTTPS certs)
ssh-keygen -t ed25519 -f my_key -C "demo key"
# my_key       = private key — never share this, ever
# my_key.pub   = public key — safe to hand out freely
Mindset

"It's encrypted" is the start of a sentence, not the end of one

Assume makes an ass out of you and me: hearing "the data is encrypted" should prompt follow-up questions, not relief — encrypted with what algorithm, who holds the keys, is it encrypted in transit, at rest, or both, and what happens if the key itself is compromised? A vendor that can answer all four clearly has actually thought it through. A vendor that just repeats "it's encrypted, don't worry" usually hasn't — and that's worth noting before you trust them with something sensitive.

Beginner Zero Trust – "Never Trust, Always Verify" Explained Simply
Concept

The old model: a castle with a moat

Traditional network security worked like a medieval castle — build strong walls (firewalls) around the perimeter, and trust everything inside them. Once you were "inside the network," you were generally treated as trustworthy by default. This worked reasonably well when "inside the network" meant "physically in the building, on a company-owned computer." It works far less well in a world of remote work, cloud services, personal devices, and contractors — where the very idea of a single, defensible "inside" has mostly dissolved.

Concept

Zero Trust flips the assumption

Zero Trust starts from a different premise: don't automatically trust anything, whether it's inside or outside the network — verify every request, every time, based on who's asking, what they're asking for, and the context they're asking from. The name sounds extreme, but the underlying idea is closer to "trust, but continuously re-verify" than "trust no one ever." A useful mental model: instead of one big castle wall, imagine every single room has its own locked door and its own ID check — including rooms you're already inside.

Castle-and-moat thinkingZero Trust thinking
"You're on the VPN (Virtual Private Network), so you must be legitimate""You're on the VPN — now let's also verify your device is patched, your identity via MFA (Multi-Factor Authentication), and that this specific request makes sense for your role"
One login grants broad access to "the network"Each request to each resource is evaluated on its own merits, continuously
Internal traffic is implicitly trustedInternal traffic is monitored and verified just like external traffic

Assume makes an ass out of you and me — the philosophy in one phrase

If you remember nothing else about Zero Trust, remember this: it is, in essence, "assume makes an ass out of you and me," turned into an architecture. Every assumption that something is safe because of *where* it's coming from — "it's an internal IP (Internet Protocol)," "it's a company laptop," "they logged in successfully an hour ago" — is exactly the kind of assumption attackers count on defenders making. Zero Trust simply builds systems that verify instead of assume, by design, every single time.

Beginner Security Headers – The HTTP (HyperText Transfer Protocol) Response Fields That Quietly Protect You
Concept

A web server can tell your browser how to defend you

When your browser loads a webpage, the server sends back more than just the page content — it also sends HTTP response headers, a set of instructions about how the browser should treat that content. A handful of these headers exist purely for security: they tell the browser "don't allow this page to be embedded elsewhere," "only ever load this site over HTTPS (HyperText Transfer Protocol Secure)," or "don't run scripts from sources I haven't explicitly approved." Most users never see them — but their presence (or absence) says a lot about how seriously a site takes security.

Concept

The headers worth knowing

Strict-Transport-SecurityTells the browser "always use HTTPS for this site, never plain HTTP, even if a link points to http://"Downgrade attacks that try to trick a browser into an unencrypted connection

Hands-on

Checking what headers a site actually sends

# Filter for just the security-relevant ones
curl -sI https://example.com | grep -iE "strict-transport|content-security|x-frame|x-content-type|referrer-policy"

#
#   strict-transport-security: max-age=63072000; includeSubDomains
#   content-security-policy: default-src 'self'; script-src 'self' cdn.example.com
#   x-frame-options: DENY
#   x-content-type-options: nosniff

# Or use a free online scanner that grades a site's headers and

Running this against a few of your own frequently-used sites is a genuinely eye-opening exercise — you'll often find that well-known, security-conscious organizations send a rich set of these headers, while smaller or older sites send almost none.

Mindset

Not my circus, not my monkey — except your users' browsers are always your circus

It's tempting for a small team to think "security headers are for big companies with dedicated security staff" — but a single missing Content-Security-Policy header can be the difference between an XSS bug being a minor annoyance and it being a full account-takeover vector. These headers cost nothing to add, take minutes to configure on most modern web frameworks, and quietly protect every single visitor without requiring them to do anything at all. Few security investments offer that kind of return for that little effort.

🎫 OAuth (Open Authorization) 2.0, OIDC (OpenID Connect) & SAML (Security Assertion Markup Language) — Federated Identity Identity ▶

Delegated Access vs Proving Who You Are

SAML does the same job as OIDC but with XML (eXtensible Markup Language), and still dominates enterprise SSO (Single Sign-On).

🔑 Passkeys & WebAuthn (Web Authentication) — Killing the Password Auth ▶
Concept
Why Passkeys Are Phishing-Resistant
A passkey is a public/private key pair bound to a specific website. Your device keeps the private key (in a secure enclave / TPM, unlocked by biometrics or a PIN) and only ever sends a signature — never a shared secret. Because the key is tied to the site's real origin, a look-alike phishing domain simply cannot trigger it. There is nothing to type, reuse, leak in a breach, or hand to an attacker. This is the FIDO2 (Fast Identity Online 2) standard: WebAuthn (the browser API) + CTAP (Client to Authenticator Protocol) (the authenticator protocol).
How It Works
Registration & Authentication

1. Site sends a random challenge + its origin
2. Device generates a NEW key pair for this site only
3. Private key stays on device; PUBLIC key is sent to the site
4. Site stores the public key against your account

# ── AUTHENTICATION (every login) ──────────────────────────
1. Site sends a fresh random challenge
2. You unlock the device (Face ID / fingerprint / PIN)
3. Device SIGNS the challenge with the private key
4. Site verifies the signature with the stored public key

# The server only ever stores a PUBLIC key — useless if breached.

🍪 Sessions, Cookies & JWT (JSON Web Token) — Managing Web Auth State Auth ▶
Concept
HTTP (HyperText Transfer Protocol) Is Stateless — So How Do You Stay Logged In?
Every HTTP request is independent; the server doesn't inherently remember you between clicks. After you log in, the app needs a way to prove "this request is still Alice" on every subsequent call. There are two dominant strategies: server-side sessions (the server remembers) and stateless tokens / JWT (the proof travels with the request). Both usually ride in a cookie.

Anatomy of a JWT
A JWT is three Base64url parts joined by dots: header.payload.signature. The signature is what makes it trustworthy — the server verifies it to know the payload wasn't tampered with. The payload is only encoded, not encrypted — anyone can read it, so never put secrets in it.

.eyJzdWIiOiIxMjMiLCJ  # payload → {"sub":"123","exp":1730000000}
.SflKxwRJSMeKKF2QT4f  # signature → HMAC/RSA over header.payload

# Server verifies: recompute the signature with its secret/key.

🛡️ Web Application Firewalls (WAF) AppSec ▶
Concept
A Filter That Understands HTTP (HyperText Transfer Protocol)
A network firewall decides which ports and IPs (Internet Protocol) may connect — it can't see inside a web request. A Web Application Firewall operates at layer 7: it inspects the actual HTTP request — URL (Uniform Resource Locator), headers, body, parameters — and blocks ones that look like attacks (SQL injection, XSS, path traversal) before they reach your app. It's a shield in front of the application, not a replacement for writing secure code.

💉 The Injection Family — One Bug Class, Six Costumes AppSec • Defence ▶
The shape
Every Injection Is Data Being Read as Instructions
SQL (Structured Query Language), shell, LDAP (Lightweight Directory Access Protocol), template and NoSQL injection look like five vulnerabilities and are one. In each, untrusted input is concatenated into something an interpreter parses, and the interpreter cannot tell which characters came from you and which came from the attacker. Recognising the shape means recognising the fix, which is the same every time.
FlavourInterpreterThe fix that actually works
SQLThe database query parserParameterised queries — never string formatting
CommandThe shellPass an argument array; do not invoke a shell at all
LDAPThe directory filter parserEscape per RFC (Request for Comments) 4515, or use a filter builder
TemplateThe template engineNever let user input be the template
NoSQLThe document query parserReject non-scalar input where a scalar is expected
PromptAn LLM (Large Language Model)No complete fix exists — see the AI (Artificial Intelligence) domain
The verdict: the answer is always separate the code from the data, never clean the data. Parameterisation moves user input to a channel the parser already knows is data. A blocklist tries to guess every dangerous string, and loses to an encoding you did not think of.
Failure mode
Parameterising the Values and Formatting the Table Name
Placeholders bind values. They cannot bind identifiers — table names, column names, sort direction — because those change what the query is, not what it operates on. So dynamic sorting and dynamic table selection get built by string formatting, in code that otherwise looks parameterised and safe. 
# Safe — the value is bound
cur.execute("SELECT * FROM users WHERE email = %s", (email,))

# Injectable — the identifier cannot be bound, so it was formatted
cur.execute(f"SELECT * FROM users ORDER BY {sort_col} {direction}")

# The only safe pattern for identifiers: an allow-list you control
COLS = {"name", "created_at", "email"}
if sort_col not in COLS: raise ValueError(sort_col)
direction = "DESC" if direction.upper() == "DESC" else "ASC"
Same rule for shell commands: arguments can be passed as a list, but the program name and any flags cannot come from user input. If the shape of the command is dynamic, the allow-list is the control.
Detection
Second-Order Injection Passes Every Test
The payload is stored safely — parameterised on the way in, so nothing fires — and injected later, when some other code path reads it back out of the database and concatenates it into a query. A profile name saved today; a nightly report built with string formatting tomorrow.
This is why "input is validated at the boundary" is not a complete defence, and why scanners miss it: the request that stores the payload looks harmless and the request that triggers it contains nothing suspicious. Parameterise every query, including the ones reading data you believe you already trust.
🚪 Broken Access Control — IDOR (Insecure Direct Object Reference), Traversal & the Checks Nobody Ran AppSec • Defence ▶
Orientation
The Models Are Covered; This Is Where Applications Break Them
Access Control Models covers the models themselves. This card is the implementation failure — consistently the highest-ranked category in the OWASP (Open Worldwide Application Security Project) Top 10, and the one least caught by tools, because nothing in the code looks wrong. The vulnerability is an absent check, and absence has no signature.
FailureLooks like
Insecure direct object reference/invoice/1042 returns someone else's invoice when you change the number
Path traversal?file=../../etc/passwd escapes the intended directory
Function-level gapThe admin button is hidden, but POST /admin/delete still works
Mass assignmentA profile update accepts "role": "admin" because the model was bound wholesale
Forced browsingGuessable URLs (Uniform Resource Locator) reachable without ever passing the menu that gates them
Hiding the control is not access control. A removed button, a client-side role check and an unlinked URL are all presentation. The server must re-answer "may this specific user do this specific thing to this specific object?" on every request, because the client's answer is attacker-controlled.
The fix
Deny by Default, and Check Ownership Where the Object Is Loaded
The durable pattern is to make the check impossible to forget: scope the query to the caller rather than fetching by identifier and testing afterwards. If the object is loaded through a filter that already includes ownership, a missing check cannot return someone else's data — it returns nothing. 
# Fragile: fetch, then remember to check. The second line is optional
# in the sense that nothing breaks visibly if it is deleted.
inv = Invoice.get(id)
if inv.owner_id != user.id: raise Forbidden

# Durable: ownership is part of the lookup. Forgetting it is a 404.
inv = Invoice.filter(id=id, owner_id=user.id).one_or_none()
if inv is None: raise NotFound
Returning 404 rather than 403 for an object the caller may not see is deliberate: 403 confirms the record exists, which is itself a disclosure when the identifier is sequential.
Testing
Automated Scanners Cannot Find This — People Can
A scanner does not know that invoice 1042 belongs to a different tenant. It sees a 200 response and moves on. That is why access control needs a test approach the tooling cannot supply: two accounts, and every object identifier tried across both.
Make it a test suite rather than a pen-test finding. A fixture with two users and a loop over every object-scoped endpoint catches the whole class on every commit — and it is the one security test that repays writing before the feature.
🛰️ SSRF (Server-Side Request Forgery), XXE (XML External Entity) & Deserialization — The Server-Side Heavy Hitters AppSec • Defence ▶
SSRF
Making the Server Fetch Something on the Attacker's Behalf
Any feature that takes a URL (Uniform Resource Locator) and fetches it — webhook testing, image import, PDF (Portable Document Format) rendering, link previews — can be pointed inward. The server is inside the network, so it reaches things the attacker cannot: internal admin panels, databases, and cloud instance metadata.
Metadata is the prize. On a cloud instance, one unauthenticated HTTP (HyperText Transfer Protocol) request to a link-local address returns credentials for the instance's role. That is the step that turns "our thumbnail service has a bug" into a breach, and it is the mechanism behind several very large ones.
DefenceWorth
Block-list of internal rangesWeak — DNS (Domain Name System) rebinding, redirects, IPv6 (Internet Protocol version 6) and decimal-encoded addresses all bypass it
Allow-list of destination hostsStrong — the only reliable answer when the set is knowable
Fetch from an egress proxy with no network accessStrong — architectural, and survives a bypass
Require metadata service v2 (session tokens)Removes the highest-value target
Validate after resolution, not before. Checking the hostname then letting the HTTP client resolve it again invites DNS rebinding — the name passes the check and resolves to an internal address a moment later. Resolve once, check the resulting address, connect to that address.
XXE
An XML (eXtensible Markup Language) Parser Will Fetch Files If You Let It
XML supports external entities: a document can declare an entity whose value is loaded from a URI (Uniform Resource Identifier), including file:///etc/passwd. Parsers historically enabled this by default, so an application accepting XML would read local files and make outbound requests on request. 
# Python: defusedxml, or disable entity resolution explicitly
from defusedxml.ElementTree import parse   # drop-in, safe defaults

# Java: the two features that matter
factory.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);
factory.setXIncludeAware(false);
Modern parsers mostly default to safe now, which makes this a legacy-and-dependency problem rather than a new-code one. The exposure is an old service, or a library that parses XML somewhere you did not know it did — SOAP, SVG (Scalable Vector Graphics) upload, XLSX, SAML (Security Assertion Markup Language). SAML in particular is XML you accept from outside and use for authentication.
Deserialization
Rebuilding an Object Runs Code, by Design
Native deserialization — Python pickle, Java's ObjectInputStream, PHP (PHP: Hypertext Preprocessor) unserialize — reconstructs arbitrary objects, which means invoking constructors and magic methods that exist in the application's own dependency tree. An attacker who controls the byte stream chains those into remote code execution without needing any vulnerability in your code.
Never deserialize untrusted data with a native format. There is no hardening that makes it safe, because the capability is the feature. Use JSON (JavaScript Object Notation) and build the object yourself, and where a native format is unavoidable, sign the payload and verify the signature before parsing a single byte — see Secrets Management — Stop Hardcoding Passwords for where that key lives.
⚛️ Post-Quantum Cryptography — Harvest Now, Decrypt Later SEC • Cryptography ▶
The threat
Only Public-Key Crypto Breaks, and the Deadline Is Already Past
A sufficiently large quantum computer running Shor's algorithm breaks RSA (Rivest-Shamir-Adleman) and elliptic curve — the maths those rest on becomes tractable. Symmetric encryption and hashing are far less affected: Grover's algorithm roughly halves the effective key length, so AES-256 stays comfortable and SHA-256 remains sound.
PrimitiveQuantum impactAction
RSA, ECDSA (Elliptic Curve Digital Signature Algorithm), ECDH (Elliptic Curve Diffie-Hellman), Diffie-HellmanBroken by ShorMigrate
AES-128Effective 64-bit against GroverMove to AES-256
AES-256, SHA-256, SHA-3AdequateNothing
"Harvest now, decrypt later" is why this is not a future problem. An adversary can record encrypted traffic today and decrypt it once the hardware exists. Any secret that must stay confidential for a decade — health records, state secrets, source code, long-lived keys — is already exposed if it crosses the wire under classical key exchange.
The standards
ML-KEM (Module-Lattice Key Encapsulation Mechanism) and ML-DSA (Module-Lattice Digital Signature Algorithm), and Why Deployments Are Hybrid
NIST (National Institute of Standards and Technology) standardised the first post-quantum algorithms in 2024: ML-KEM (formerly Kyber) for key encapsulation and ML-DSA (formerly Dilithium) for signatures, with SLH-DSA (Stateless Hash-Based Digital Signature Algorithm) as a conservative hash-based signature alternative.
Real deployments run hybrid: a classical key exchange and a post-quantum one together, combining both shared secrets. That way a break in either — including an undiscovered flaw in the new, far less battle-tested maths — still leaves the connection secure. Browsers and major TLS (Transport Layer Security) terminators already do this by default for key exchange.
Signatures are the slower half and it matters less: a signature must resist forgery at the moment it is verified, so there is no harvest-now equivalent. Key exchange first, signatures later is the correct migration order, not a compromise.
What to do now
Inventory Beats Migration
The blocker for most organisations is not choosing an algorithm — it is not knowing where cryptography lives. Hard-coded curve names, pinned certificates, an appliance that only speaks RSA, a device fleet that cannot be updated.
Build the cryptographic inventory, and make new systems crypto-agile — algorithm as configuration rather than a compile-time constant. That work pays off regardless of quantum timelines, because it is the same capability needed to retire any broken primitive, and every primitive eventually breaks. See Cryptography Fundamentals — The Building Blocks of Security.
🚧 Data Loss Prevention — Classification, Egress & the False-Positive Problem SEC • Data Protection ▶
The premise
You Cannot Protect What You Have Not Classified
DLP (Data Loss Prevention) inspects data in three states — at rest, in motion, in use — and blocks or alerts when something sensitive moves somewhere it should not. Every deployment lives or dies on the step before that: deciding what counts as sensitive, in a way a machine can evaluate.
DetectionCatchesCosts
Pattern / regexCard numbers, national insurance numbersNoisy without a checksum test
Exact data matchRecords from a known databaseNeeds a hashed copy of the real data
Document fingerprintDerivatives of a known fileMisses retyped or summarised content
Classification labelWhatever the author markedDepends on people labelling honestly
Labels beat patterns where you can get them. A regex cannot tell a real card number in an export from an example in documentation; a label carries the author's intent. The catch is that labelling has to be nearly free at the point of writing, or it will not happen.
Failure mode
Blocking Mode on Day One Teaches People to Route Around You
A DLP policy that blocks from the start will, within a week, stop something legitimate and urgent. What follows is predictable: an exception, then a habit of using personal email or a USB (Universal Serial Bus) stick for anything time-sensitive — which is precisely the behaviour the control existed to prevent, now with no visibility at all.
Run in monitor mode long enough to see real traffic, tune until the alert volume is one a human can read, and only then block the narrow set you are confident about. A control people work around is worse than none, because it also produces a false sense that the risk is handled.
Scope
Most Data Loss Is Not Malicious, and DLP Is Not Anti-Exfiltration
The common cases are an attachment to the wrong recipient, a file synced to a personal cloud account, a screenshot in a support ticket. DLP is well suited to those — mistakes made in the clear.
It is much weaker against a determined insider, who can photograph a screen, retype figures, or encrypt before sending. Buying DLP as an anti-exfiltration control is buying the wrong thing: for that threat the useful controls are access minimisation, egress monitoring and joiner-mover-leaver discipline. Position DLP as a mistake-catcher and it earns its cost.
🧱 Network Security Architecture — Segmentation, DMZ (Demilitarized Zone) & Egress Filtering SEC • Architecture ▶
The purpose
Segmentation Is About the Second Machine, Not the First
Segmentation does not stop an intrusion. It decides what an intrusion is worth — whether a compromised laptop can reach the finance database and the domain controllers, or only a print server and a proxy. Assume the first machine falls, then ask what it can touch.
LevelSeparatesEffort
Perimeter / DMZInternet-facing from internalLow — nearly everyone has this
VLAN (Virtual Local Area Network) segmentationBroad zones: users, servers, OT, guestsModerate; the usual practical target
Micro-segmentationWorkload from workloadHigh — needs an accurate service map
Egress filteringOutbound from everythingLow effort, high value, usually skipped
Egress filtering is the underrated row. Most organisations control inbound carefully and let anything leave. Command-and-control, data theft and tool download are all outbound — restricting a server segment to the handful of destinations it genuinely needs breaks a large share of intrusion tooling for very little work.
Failure mode
The Any-Any Rule Added at 2 a.m.
Segmentation degrades one exception at a time. An outage is traced to a firewall, a permissive rule is added to restore service, and the ticket to tighten it later is never done. After a few years the topology diagram shows zones the rule base does not enforce.
The defences are unglamorous and effective: an expiry date on every temporary rule, periodic rule review with hit counters to find rules nothing matches, and an actual test — try to reach the database segment from a user VLAN and see what happens. A segmentation diagram is a claim; only a packet is evidence.
Modern shape
Identity Is the New Segment, But the Network Still Matters
Zero Trust shifts the decision from where a request came from to who and what is making it — see Zero Trust — Never Trust, Always Verify. That does not retire network segmentation; it layers on top of it. Legacy systems that cannot participate in identity-aware access still need a network boundary, and that is most operational technology, most medical devices, and every appliance with a web console from 2014.
Treat them as complementary. Identity controls what a healthy, known device may reach; segmentation contains everything that cannot be made healthy or known.
🗝️ Privileged Access Management — Vaulting, Just-in-Time & Session Recording SEC • Identity ▶
The problem
Standing Privilege Is a Credential Waiting to Be Stolen
The traditional model gives administrators permanent elevated accounts. Every one is a target that is valuable every hour of every day, whether or not anyone is using it — and a phished session at 3 a.m. is worth exactly as much as one during a change window.
ControlRemoves
VaultingHumans knowing the password at all; it is checked out and rotated after use
Just-in-time elevationStanding privilege — rights are granted for a window, with a reason
Session brokeringDirect connections; the credential never reaches the workstation
Session recordingThe dispute about what was actually run
Approval workflowUnilateral access to the most sensitive systems
Just-in-time is the one that changes the risk most. It converts "this account is always dangerous" into "this account is dangerous for the twenty minutes somebody justified" — and it produces a natural audit trail, because every elevation has a requester, a reason and a clock.
Failure mode
The Break-Glass Account Nobody Tested
Every PAM (Privileged Access Management) deployment needs an emergency path for when the vault itself is unavailable — and that account is the one most likely to be forgotten, unmonitored, and still holding the credentials from installation day.
Break-glass credentials should be sealed, alerted on every use, rotated after use, and tested on a schedule. Untested emergency access is the same class of claim as an untested backup: believed until the day it matters. The failure is rarely that the account is missing — it is that it no longer works, and nobody looked.
Sequencing
Do the Free Things Before Buying the Platform
PAM products are expensive and slow to deploy, and much of the benefit is available first from discipline: separate administrative accounts, no email or browsing from them, an inventory of who holds what, and removing the standing rights nobody has used in ninety days.
Buying a vault while administrators still browse the web from privileged workstations is buying a lock for a door that is not in a wall. Sequence it: tiering and hygiene first, then vaulting and just-in-time for what remains. 🏭 OT vs IT & the Purdue Model — When the Generic Answer Is the Wrong Answer SecurityX • OT ▶
Core Concept
Operational Technology Inverts the Priorities You Trust
IT security ranks confidentiality first; operational technology — the systems that run turbines, pumps, assembly lines and power grids — ranks availability and safety first, because the failure mode is not a data breach, it is a flooded town or a dead worker. That single inversion breaks most IT instincts. You cannot reboot a blast furnace controller to apply a patch, you cannot take a leaked credential offline if it is authenticating a safety system, and "just update it" can void the certification that makes the machine legal to run.

Reference
The Purdue Model — a Map of Where the Boundaries Go
The Purdue model layers an industrial environment from the physical process up to the business network, and its enduring value is telling you where the segmentation belongs. The most important line is between OT and IT, historically enforced by a DMZ (Demilitarized Zone) at Level 3.5 — the boundary a well-run plant defends hardest.
LevelWhat lives there
0 — ProcessSensors and actuators — the physical world
1 — ControlPLCs (Programmable Logic Controller) and controllers reading sensors, driving actuators
2 — SupervisoryHMIs and SCADA (Supervisory Control and Data Acquisition) — operators watching and steering

The model describes intent, not most real plants. Convergence, remote access and cloud historians have punched holes through the layers everywhere. The value of the map is spotting which holes exist in your plant — the vendor laptop that dials straight into Level 1 is the finding, and the model is what lets you see it.
🔌 ICS (Industrial Control System) Protocols — Modbus, DNP3, OPC UA and Their Security Assumptions SecurityX • OT ▶
Core Concept
Most of Them Were Designed With No Security at All
Industrial protocols were built for isolated, trusted serial networks decades before anyone imagined them on a routable IP (Internet Protocol) network. The design assumption was physical isolation, so most have no authentication and no encryption — a command on the wire is obeyed because it arrived, not because it was proven legitimate. That is not a bug to patch; it is the protocol working as designed, and it is why segmentation, not protocol hardening, is the primary OT control.
ProtocolUsed forSecurity reality
ModbusThe ubiquitous PLC (Programmable Logic Controller) protocolNone native — no auth, no encryption; a read is a write away
DNP3Utilities, electric & water SCADA (Supervisory Control and Data Acquisition)Plain by default; Secure Authentication exists but is often unused
OPC UAThe modern interoperability standardDesigned with security — auth, encryption, signing — when configured on
EtherNet/IP, PROFINETFactory automationLargely trust-the-network
Defence
You Watch These Protocols; You Rarely Touch Them
Because you cannot bolt authentication onto Modbus and you cannot risk an active scan knocking a controller offline, OT defence is overwhelmingly passive. A span/tap port feeds traffic to a monitor that learns the normal command patterns and alerts on the abnormal — an engineering-workstation command from an address that has never issued one, a firmware write outside a maintenance window. This is the mirror image of IT's active-scanning instinct, and using an IT vulnerability scanner on a live OT segment is a classic way to cause the very outage you were trying to prevent.

🦺 Securing OT Without Breaking It — Segmentation, Access & Safety-First IR (Incident Response) SecurityX • OT ▶
Controls
Segmentation Is the Whole Game
When you cannot patch the endpoints and cannot authenticate the protocols, the control that carries the load is keeping the attacker away from them. Every serious OT security programme is, at its core, a segmentation and access-control programme — the standards bodies just formalize it (IEC 62443's zones and conduits; NERC CIP for the North American power grid).
ControlIn practice
Zones & conduitsGroup assets by risk; every crossing is a controlled, monitored conduit
The IT/OT DMZ (Demilitarized Zone)No direct path enterprise→control; brokered data exchange only
Remote access done rightBrokered, MFA (Multi-Factor Authentication), session-recorded, time-boxed — the vendor VPN (Virtual Private Network) is the top OT breach vector
Removable-media controlSanctioned scanning kiosks — USB (Universal Serial Bus) is how air-gapped plants still get hit
Unidirectional gatewaysData diodes let telemetry out while making inbound physically impossible
Incident Response
Safety First, and Why You May Not Pull the Plug
The IT reflex — isolate and power off the compromised system — can be the most dangerous possible move in OT. That "system" may be holding a valve in a safe position or keeping a process within limits; killing it can cause the physical incident the attacker wanted. OT incident response is led by the people who understand the physical process, with security advising, and the first question is never "how do we contain the malware" but "what happens to the process if we do."
This is where the site's IR playbooks need an asterisk. Ransomware — The Defining Threat of the Era and the standard containment steps assume you can isolate freely. In OT you cannot; safety and the process come first, containment second, and the plant engineer, not the SOC (Security Operations Center), has the final call on touching a live controller.

🔀 Doing the PQC (Post-Quantum Cryptography) Migration — Inventory, Crypto-Agility & the Roadmap SecurityX • Crypto ▶
Core Concept
The Hard Part Is Not the Algorithm — It Is Finding Where Crypto Lives
Post-Quantum Cryptography — Harvest Now, Decrypt Later covers why the migration is urgent and which standards replace what. This card is the operational half: actually swapping the algorithms across a real estate. And the first, humbling discovery is that you do not know where all your cryptography is — it is embedded in TLS (Transport Layer Security) configs, in code libraries, in hardware modules, in firmware, in protocols you inherited and forgot. You cannot migrate what you have not found, so the migration begins as an inventory project, not a cryptography project.
StepWhat it involves
1 Cryptographic inventoryDiscover every use — libraries, certs, protocols, hardware, embedded; automated scanning plus code review
2 Prioritise by data lifetimeLong-lived secrets exposed to harvest-now-decrypt-later go first
3 Build in crypto-agilityAbstract the algorithm behind config so the next swap is not another multi-year project

Reference
Crypto-Agility and the CBOM
Two ideas make the difference between a one-time scramble and a repeatable capability. Crypto-agility is designing systems so the algorithm is a configuration choice, not a hard-coded assumption — because there will be a next migration, and the organizations that hard-coded RSA (Rivest-Shamir-Adleman) are learning that lesson now. A CBOM (cryptographic bill of materials) is the durable output of the inventory: a machine-readable record of what crypto each system uses, the same idea as an SBOM (Software Bill of Materials) but for algorithms, keys and certificates.
ArtifactAnswers
Cryptographic inventoryWhere do we use crypto, and which algorithms?
CBOMThe inventory as living, machine-readable data — feeds the next audit automatically
Data-lifetime mapWhich secrets must stay confidential for years, not days
Agility layerCan we swap an algorithm by config, or is it a code change?
Sequence by two axes at once: data lifetime (what an attacker gains by harvesting it today) and replaceability (how hard the system is to touch). Long-lived data on an easy-to-update system is the first, cheapest win; long-lived data on an unpatchable embedded device is the problem you start planning around now, because it has the longest lead time.
🧮 Adjacent Cryptography — ZKPs, Homomorphic Encryption, MPC & Confidential Computing SecurityX • Crypto ▶
Core Concept
Cryptography That Does More Than Hide Data
Classical crypto keeps a secret secret. A newer family lets you compute on secrets without exposing them — prove a fact without revealing it, run a calculation on encrypted data, or split trust so no single party holds the whole key. These are moving from research into real products, unevenly, and the practitioner's job is knowing which are ready and which are still expensive science projects, so you neither dismiss a real tool nor build on one that will not perform.
TechniqueLets youMaturity
Zero-knowledge proof (ZKP)Prove a statement true without revealing whyReal in identity & blockchain; niche in enterprise IT
Homomorphic encryptionCompute on ciphertext, get an encrypted resultWorks, but still slow and costly for general use
Secure multi-party computationJointly compute over private inputs no party sharesDeployed in specific analytics/finance cases
Threshold signaturesSplit a signing key so k of n must cooperateMature; used in key custody and wallets
Confidential computing (TEE)Process data in a hardware enclave shielded from the hostAvailable on major clouds today
Reference
Confidential Computing — the One You Can Use Now
Of the family, confidential computing is the most immediately practical. A trusted execution environment — a hardware enclave — decrypts and processes data inside a region the operating system, hypervisor and cloud operator cannot read, then re-encrypts the result. It closes the last gap in the classic trio: you already encrypt data at rest and in transit, and this protects it in use. The catch is the trust you still extend: you are trusting the chip vendor's enclave and its attestation — the proof that your code really is running in a genuine, unmodified enclave. Verify the attestation; an enclave you did not attest is just a black box you decided to trust.
The reason these matter for privacy work: they enable computation on data that regulation or contract forbids you from seeing in the clear — running analytics for a partner without either side exposing raw records. That is the same goal the anonymization and differential-privacy techniques in `grc` pursue, reached by a different route: not de-identifying the data, but never decrypting it where it could leak.
🗺️ Mapping Your Own Attack Surface — Domains, Certificates, Cloud, Code & People External Exposure ▶
Concept
An Attacker's First Step Is an Inventory You Do Not Have
Reconnaissance against your organisation is cheap, legal and mostly automated, and it routinely produces a more complete picture of your internet-facing estate than your own asset register. The gap is structural: your inventory records what was provisioned deliberately, and the exposure includes everything anyone ever stood up and forgot. Running the same collection against yourself, on a schedule, closes it.
SourceReveals

The job-advert row is consistently underestimated. A posting listing your exact stack, versions and tooling is a free technology inventory published by your own recruiting team, and it needs no scanning at all.
Concept
Dangling DNS Is the Finding That Turns Into a Real Compromise
A DNS record pointing at a cloud resource that no longer exists is not merely untidy. If anyone can claim that resource name — a storage bucket, an app-service hostname, a third-party service subdomain — they inherit your subdomain, with the trust and often the cookies that come with it. This is the most reliably exploitable class of finding an external review produces, and it is created by ordinary decommissioning that skipped one step.
PatternRisk

A record to a released IP addressWhoever gets that address next inherits your traffic

Make DNS cleanup an explicit step in decommissioning, and scan for dangling records monthly. The scan is cheap; the incident is not.
Technique
Do It on a Schedule, and Diff It
A one-off external review produces a report that is out of date within weeks, because the estate changes continuously and mostly without the security team's knowledge. The value is in the difference between this month and last: a new hostname, a newly opened port, a certificate for a name nobody recognises.
SignalAsk
A new subdomain appearedWho created it, and does it belong in the estate?
A new open portDeliberate, or a firewall change with an unintended effect?
A certificate for an unknown nameShadow IT, a supplier, or an impersonation attempt
A host disappearedDecommissioned properly, or is its DNS now dangling?
The tooling for this is the same tooling in Reconnaissance (OSINT) — the difference is only the target and the intent, which is why running it against yourself is both easy and rarely done.

Corporate email addresses appear in breaches of unrelated consumer services constantly, because people sign up for things with their work address. Monitoring for your domains in breach corpora is a genuine control, and it comes with obligations.

Breach corpora are other people's personal data, frequently obtained illegally, and holding them creates obligations and hazards of its own. The defensible position is narrow and worth stating explicitly before anyone downloads anything.

🎫 Access Credentials & Cloning — Why 125 kHz Prox Is Not a Control Physical Security ▶
Concept
Old Proximity Cards Broadcast a Number and Nothing Else
Legacy 125 kHz proximity cards transmit a fixed identifier with no authentication and no encryption. Anything that reads the number can reproduce it, and readers and writers are inexpensive and widely available. A badge of this type is an identifier, not a credential — it establishes who a card claims to be and offers no evidence that it is genuine. Many organisations still run entirely on them, frequently without knowing which technology they have.
TechnologySecurity
125 kHz proximityStatic number, no authentication — clone by reading it once
13.56 MHz, legacy modesBetter, but several older schemes are thoroughly broken
Modern smart cards with mutual authenticationCryptographic; cloning is not practical from a read
Phone-based credentialsStrong, tied to the device, and revocable instantly
A read can be taken from a normal distance in a corridor or a lift with concealed equipment. The threat is not theoretical, and the card need never leave the holder's pocket.
Technique
What to Do About It, Realistically
Replacing every reader and card in an estate is expensive and slow, so the practical answer is layered: know what you have, prioritise the doors that matter, and add controls that do not depend on the card being unforgeable.
StepDetail
Find out which technology you actually runMany estates are mixed, and nobody has checked in a decade
Upgrade the doors that matter firstServer rooms, comms rooms, records storage — not every door
Add a second factor where it countsPIN at the reader, or a phone credential
Monitor for impossible journeysThe same badge in two places is the cloning signal

🛡️ Hardware Root of Trust — What a Verified Boot Chain Actually Proves Device Security ▶
Concept
Every Verification Chain Ends Somewhere You Must Simply Trust
Boot verification works by each stage checking the next before handing control to it. That regress has to stop, and it stops at something immutable — code in mask ROM (Read-Only Memory), and a key fused into the silicon at manufacture. That anchor is the root of trust: it cannot be updated, which is what makes it trustworthy, and also what makes a flaw in it permanent.
StageVerified by
ROM bootloaderNothing — it is the anchor, immutable in silicon
First-stage bootloaderThe ROM, against a fused key
Main bootloaderThe first stage
KernelThe bootloader
Root filesystemThe kernel, if integrity verification is enabled
ApplicationsUsually nothing — the chain commonly stops here
Note where the chain typically ends. A device with impeccable secure boot and no runtime integrity checking is verified up to the moment it starts running, and unprotected thereafter — which is exactly the window an exploited service occupies.
Comparison
Secure Boot Refuses; Measured Boot Records
These are constantly conflated and do different jobs. Secure boot enforces locally: it checks signatures and stops if they fail. Measured boot enforces nothing — it hashes each component into tamper-resistant registers so that a remote party can later ask what actually ran. The second is what makes remote attestation possible, and it is why a compromised device cannot simply claim to be healthy.

NeedsSignatures and a trusted keyA TPM (Trusted Platform Module) or equivalent to hold the measurements

Sealing is the practically important consequence: a key released by the TPM only when the measurements match means a disk encrypted on a healthy machine will not unlock after the boot chain is modified. The Linux implementation of all this is in Secure Boot, LUKS & Integrity — Measured Boot, dm-verity & IMA.
Concept
What It Does Not Prove
Verified boot is frequently cited as though it settled a device's trustworthiness. It establishes something narrower and worth stating precisely, because the gap is where real compromises live.
ClaimReality

🔌 The OWASP (Open Worldwide Application Security Project) API (Application Programming Interface) Security Top 10 — Where the Web List Stops Being Enough API Security ▶
Concept
A Separate List Exists Because the Bugs Are Genuinely Different
The web Top 10 was written for applications that render pages. An API renders nothing: it accepts a request, checks something, and returns objects. That difference moves the whole centre of gravity. Injection and cross-site scripting drop down the list because there is no HTML (HyperText Markup Language) being assembled and the parsing is usually a library's job. What rises is authorization — because in an API, every single object the caller asks for is a decision the server has to make on its own, with no page flow to hide behind and no UI (User Interface) to constrain what gets asked for.
The practical consequence: a scanner tuned for web applications finds very little in an API, and finding nothing is routinely misread as the API being sound. Most real API findings require knowing what the caller is supposed to be able to see, which is business context a scanner does not have. The web list is in OWASP Top 10 (2021) and remains correct for what it covers.
Reference

Read the list as three clusters rather than ten separate items: authorization failures, resource-consumption failures, and inventory failures. Nearly everything falls into one.

Mass Assignment — The One That Surprises Developers
Object-property-level authorization is the modern name for two older bugs, and the write half is the one that bites. A framework that binds a request body straight onto a model object will happily accept fields the client was never meant to send. The endpoint that updates a display name also updates role, because nobody wrote down which fields were in scope — the form only had one box, so the developer reasoned the request only had one field. 
POST /api/v2/users/me
{ "displayName": "Sam" }          // what the UI sends

POST /api/v2/users/me
{ "displayName": "Sam",
  "role": "admin",
  "emailVerified": true,
  "accountId": 41 }               // what the API accepts
The fix is an explicit allow-list of bindable fields per endpoint — never a deny-list, which fails the moment somebody adds a column. The read half is the same failure in reverse: returning the whole object and letting the client decide what to display, which means the data is in the response whether or not it reaches the screen.
🔓 Broken Object-Level Authorization — The Bug in Almost Every API (Application Programming Interface) API Security ▶
Concept
Authenticated Is Not Authorized, Per Object, Every Time
BOLA is one missing line of code repeated across an application: the endpoint verifies the token, loads the record by the ID in the request, and returns it — without ever asking whether this caller owns that record. It is the most-reported real API vulnerability by a wide margin, and it survives code review because the missing check is invisible. Nothing in the diff looks wrong. There is simply no line where the wrongness would have been. 
# Vulnerable: the token proved who you are, and nothing else
invoice = Invoice.objects.get(id=request_id)
return serialize(invoice)

# Correct: ownership is part of the lookup, not a later check
invoice = Invoice.objects.get(id=request_id, tenant=current_user.tenant)
Scoping the query beats checking after the fetch. A separate if can be forgotten on the next endpoint; a repository layer that will not return cross-tenant rows cannot be.
Reference
Where the Identifier Hides
Testing for BOLA means finding every place a request names an object. The URL (Uniform Resource Locator) path is the obvious one and usually the one that got fixed; the rest are where it survives.

Nested object/projects/7/tasks/93Project ownership checked; task parentage not
Batch or bulk endpoint{"ids":[1,2,3,…]}Written after the single-item endpoint, by someone else

Export, report and webhook payloadsA scheduled job's outputRuns as a service account with everything
Troubleshooting
Unguessable IDs Are Not a Control
Replacing sequential integers with UUIDs (Universally Unique Identifier) is worth doing — it stops trivial enumeration and removes a business-intelligence leak, since order 8841 tells a competitor roughly how many orders you have. It does not fix BOLA. Identifiers leak constantly through legitimate channels: shared links, exports, webhook bodies, support tickets, a former employee's screenshots. Once an attacker holds one valid identifier they should not have, an unguessable format has bought nothing.
Testing needs two accounts, not one. Authenticate as user A, capture the requests, replay them with user B's token and A's identifiers, and record the status codes. That two-account diff is the whole test, it is cheap to automate, and it belongs in the pipeline rather than in an annual assessment — see Web Application Pentesting — Hacking the Web Safely for the wider methodology this sits inside. One warning on results: a 403 that took measurably longer than a 404 still tells the attacker the object exists.

🎫 Federation Attack Surface — Golden SAML (Security Assertion Markup Language), Token Forgery & Reply-URL Abuse Identity ▶
Concept
Federation Moves the Crown Jewels to the Signing Key
Single sign-on replaces many password checks with one assertion that many services agree to believe. That is a real security gain and it concentrates risk in a specific, physical place: the private key the identity provider signs with. An attacker holding that key does not need to authenticate as anyone. They mint an assertion stating whatever they like — any user, any group membership, multi-factor already satisfied — and every federated service accepts it, because accepting it is exactly what they were configured to do.
This is the golden SAML technique, and its defining property is that it is invisible at the service provider. There is no failed login, no impossible travel, no multi-factor prompt. The sign-in logs at the relying party show a normal successful federated authentication, because from its point of view that is precisely what happened. Detection has to live at the identity provider, or in the gap between the two logs.

🪝 OAuth (Open Authorization) Consent Phishing — The Attack That Needs No Password Identity ▶
Concept
Nothing About It Is Fake
Credential phishing puts up a counterfeit login page and hopes you do not look at the address bar. Consent phishing does the opposite: it sends you to the real identity provider, on the real domain, with a valid certificate, where you authenticate genuinely and satisfy multi-factor genuinely. The only thing the attacker supplies is the application asking for access — and the button you press grants it a token, not your password.
Every control aimed at fake pages therefore misses. Multi-factor authentication is satisfied, not bypassed. The domain is correct, so link-checking passes. A password reset afterwards changes nothing, because no password was involved — the refresh token keeps working across the reset, and it will keep working until the grant itself is revoked. That last point is the operational difference that catches responders out.
Reference

Consent screens are written to be reassuring and are read by users who want to get on with their work. A small number of scope patterns account for most of the damage, and they are recognisable once you have seen them named.

🤖 Non-Human Identity — Service Accounts, Workloads and the Sprawl Nobody Owns Identity ▶
Concept
They Outnumber Staff, and None of the Identity Lifecycle Applies
Machine identities — service accounts, service principals, workload identities, CI runners, API (Application Programming Interface) keys, bot accounts — typically outnumber human accounts in an estate by a large multiple. Every mechanism built for human identity fails on them by construction. There is no joiner process, because one gets created whenever a developer needs one. There is no leaver process, because nothing resigns. Multi-factor authentication is not applicable. Access reviews stall immediately, because the reviewer cannot tell what the account is for and the person who created it left two years ago.
The result is a population that is larger than the human one, more privileged on average, and unmanaged. Attackers know this: a service account is the ideal foothold precisely because its credential does not expire, its behaviour is unmonitored, and its permissions were set generously to make something work on a deadline.

🔑 OAuth (Open Authorization) 2.1 & PKCE (Proof Key for Code Exchange) — The Flows That Remain, and the Ones That Were Removed Identity ▶
Concept
OAuth 2.1 Is a Tidy-Up, Not a New Protocol
OAuth 2.0 accumulated a decade of extensions, security advisories and best-current-practice documents, and the result was a specification where several documented flows were known to be unsafe. OAuth 2.1 consolidates that guidance into one document: it removes the flows that had become indefensible and makes the mitigations mandatory rather than recommended. If you already follow current best practice you are broadly compliant with it; if you are running something written in 2015 against a copied tutorial, you probably are not.
ChangeReason
Implicit flow removedReturned tokens in the URL (Uniform Resource Locator) fragment — logged, cached, leaked via referrer and history
Resource owner password credentials removedThe application handles the user's password, defeating the point of OAuth
PKCE required for all authorization-code flowsNot just public clients — confidential clients benefit too
Redirect URIs (Uniform Resource Identifier) matched exactlyWildcard and prefix matching is how tokens end up at attacker-controlled URLs
Bearer tokens not permitted in query stringsSame leakage path as the implicit flow
Refresh tokens must be sender-constrained or rotatedA stolen non-rotating refresh token is indefinite access
What remains is a short list: authorization code with PKCE for anything with a user, client credentials for machine-to-machine, device authorization grant for input-limited devices, and refresh tokens under the rules above. If a design calls for something else, that is worth a second look.
Concept
PKCE — What It Actually Prevents
PKCE — Proof Key for Code Exchange — closes the authorization-code interception attack. The code comes back to the client through a redirect, which on a mobile device or in a browser can be observed or hijacked by another application registered for the same URI scheme. Without PKCE, whoever holds that code can exchange it for a token. With it, the code is useless to anyone who does not also hold the secret that generated it. 
# 1. Client invents a random secret and sends only its hash
code_verifier  = random(64)                     # kept in memory
code_challenge = base64url(sha256(code_verifier))

# 2. Authorization request carries the hash
GET /authorize?response_type=code&client_id=…
    &code_challenge=<hash>&code_challenge_method=S256

# 3. Token exchange carries the original — the server re-hashes and compares
POST /token   grant_type=authorization_code
              code=<code>&code_verifier=<original>
Two details decide whether it works. Use S256, never the plain method, which sends the verifier itself and protects nothing. And the authorization server must reject a token request with no verifier when a challenge was presented — an implementation that treats the verifier as optional can be downgraded by simply omitting it.
Troubleshooting
The Device Code Flow, and Why It Keeps Appearing in Incidents
The device authorization grant exists for things with no browser and no keyboard — a television, a command-line tool, a meeting-room display. The user is shown a short code and told to enter it on another device. It is a legitimate flow and it is also the mechanism behind a persistent phishing technique, because the attacker never needs to control any part of the sign-in.
Step in the attackWhat the victim sees
Attacker initiates a device-code request for a real applicationNothing
Attacker sends the user the genuine code and the genuine URLA real Microsoft or Google page, correct domain, valid certificate
User signs in and approvesAn ordinary, successful sign-in with MFA (Multi-Factor Authentication)
Attacker's pending request receives the tokenNothing at all
Every anti-phishing control misses this for the same reason OAuth Consent Phishing — The Attack That Needs No Password is missed: nothing is fake. The practical answer is to restrict the device-code flow by policy to the small number of scenarios that genuinely need it — meeting-room devices and specific command-line tooling — and to alert on its use everywhere else, where it is almost always someone being phished.
⏳ Token Lifetime & Revocation — The Logout That Does Not, and How to Fix It Identity ▶
Concept
A Self-Contained Token Cannot Be Withdrawn, Only Outlived
The property that makes signed tokens efficient is the same one that makes them impossible to revoke: the resource server validates the signature locally and never asks the issuer anything. That is why an API (Application Programming Interface) can scale without a shared session store — and it is why disabling an account, changing a password, or clicking "sign out everywhere" has no effect on a token already issued. It remains valid until it expires, and every control you thought you had over that session is really a control over the next one.
Nearly every design decision in this area follows from that single constraint. The question is never "how do we revoke this token" — it is "how short can the window be, and what do we check during it".
ApproachRevocation latencyCost
Long-lived self-contained tokenIts full lifetime — hoursNone; also no control
Short access token plus refreshMinutes — the access-token lifetimeFrequent refresh round trips; the standard answer
Reference token, introspected per requestImmediateA call to the issuer on every request
Self-contained plus a revocation list checkNear immediateA shared list every resource server must consult
Continuous access evaluationNear immediate for supported eventsRequires issuer and resource server to both implement it
Most estates should land on row two with a deliberately short access-token lifetime, and should know what that number is. "Fifteen minutes" and "eight hours" are both defensible answers to different risk questions; not knowing which one is configured is not.
Reference
Refresh Token Rotation, and Detecting a Stolen One
The refresh token is the valuable one: it is long-lived by design and exchanging it produces fresh access tokens indefinitely. Rotation makes theft detectable rather than merely limited — each use issues a new refresh token and invalidates the old, so a token used twice means two parties hold it.
BehaviourInterpretation
Refresh token used once, as expectedNormal; issue the replacement
A previously-rotated token presented againReplay — either the attacker or the legitimate client is using a stale copy

Refresh from a new address or deviceWorth a signal; refresh tokens are supposed to stay put
Refresh continuing after the account was disabledA configuration defect — the refresh path must re-check account state
The family-revocation rule is the part people soften and should not. It occasionally logs out a legitimate user whose client raced itself or restored from a backup — mildly annoying, and enormously better than the alternative, which is silently allowing the attacker to continue because you could not prove it was them.
Troubleshooting

Users, help desks and incident responders all believe that disabling an account ends access immediately. Making that belief true takes deliberate work at several layers, and the gap between the belief and the reality is where post-compromise access persists.

🚧 ZTNA (Zero Trust Network Access) — Replacing the VPN (Virtual Private Network), and What Breaks When You Do SEC • Architecture ▶
Concept
Access to an Application, Not to a Network
A VPN answers one question — "are you allowed on?" — and then puts you on a network where everything is reachable. Zero trust network access answers a different question for every connection: may this identity, on this device, in this state, reach this application, right now? The user never gets an IP (Internet Protocol) address on your network at all. The practical consequence is that a stolen credential reaches whatever that one person was authorised for, instead of everything the network could route to.

The fourth row is underrated. 🔗 Certificate & PKI (Public Key Infrastructure) Migration — Chains, HSMs (Hardware Security Module) & the Devices That Will Never Update SEC • Cryptography ▶
Concept
A Certificate Is a Chain, and a Chain Migrates From the Wrong End
Changing the algorithm on a certificate sounds like a certificate problem. It is a chain problem: a leaf is only usable if everything above it — the issuing authority, any intermediates, the root in the trust store — can be validated by whatever is checking it. That gives the migration a fixed order, and the order runs opposite to the instinct. You do not start by issuing new leaf certificates. You start by asking whether anything in your estate can validate the new chain at all, because a leaf nobody trusts is worse than the old one that worked.
LayerMigration questionTypical lifetime
Root CA (Certificate Authority)Can it be created, protected and *distributed* to every trust store?Decades — this is the slow one

The shrinking leaf lifetime is quietly the most helpful trend here. As public certificate validity drops toward weeks, the automation to reissue constantly becomes mandatory — and an estate that reissues every leaf automatically every few weeks is an estate that can change algorithm as a configuration change rather than as a project. Short lifetimes are crypto-agility arriving by another route.

Every estate contains devices that cannot be updated: they are out of support, the vendor is gone, the firmware is signed with a key nobody has, or updating them requires a site visit to a location that is now a car park. Pretending otherwise is how migrations stall at 94%.
SituationRealistic option
Building controls, meters, industrial equipmentIsolate and put a gateway in front that speaks the new algorithm outward
Medical or safety-certified equipmentRecertification cost usually decides; compensating controls and network separation
Embedded devices in the fieldReplacement on the normal refresh cycle — start counting cycles now
An appliance whose vendor has goneTerminate the connection in front of it; treat it as untrusted
Firmware signed with an old keyThe device's trust anchor cannot be changed. It is a replacement, not a migration
Something nobody can identifyThe inventory problem again — and it is always bigger than the crypto problem
The pattern in the first and fourth rows is the general answer for this whole category: terminate the modern cryptography at a proxy you control and let the legacy device speak whatever it can, on a segment where that is acceptable. It is not elegant and it is how large estates will actually get through this decade. Concept
Naming an Algorithm Answers Almost Nothing
"AES-256 encryption" is the most common security claim in the industry and one of the least informative. It says which cipher is used and nothing about the questions that determine whether anything is actually protected: encrypted at rest, in transit, or both; who holds the key; whether the vendor can decrypt it; whether the ciphertext is authenticated; how the key was derived. Every serious failure in deployed cryptography over the last two decades has been in one of those answers rather than in the cipher — which is exactly why the cipher is the part that gets printed on the slide.
The claimWhat it leaves open
"AES-256"Which mode? Is it authenticated? Where does the key come from?
"Encrypted at rest"Usually full-disk, which protects a stolen drive and nothing else
"End-to-end encrypted"Which two ends? If the vendor can reset your access, they are an end
"Zero knowledge"A precise term with a precise meaning, and usually not the one intended
"Military-grade"Nothing. There is no such standard
"Bank-level security"Also nothing, and banks are not a cryptographic benchmark
"Quantum-safe"Which algorithm, for which operation? Signatures and key exchange are different problems
"Proprietary encryption"The strongest available warning sign
The last row deserves its reputation. A cipher that has not been published and attacked by people trying to break it has not been shown to be strong — it has only been shown to resist its designers, who are the group least able to find its flaws. "We invented our own" is, on its own, sufficient reason to look elsewhere.
Reference
The Questions That Actually Separate Products
Six questions, answerable by any vendor with a real design, and revealing in proportion to how uncomfortable they make the conversation.
AskWhat a good answer sounds like
Who holds the key, and can you decrypt my data?A specific "no, and here is why we cannot" — or an honest yes
What happens when a user forgets their password?If the vendor can restore the data, the encryption is not what you thought
Is the ciphertext authenticated?An AEAD mode by name. Encryption without integrity is a known family of attacks
Where do keys come from and how are they rotated?A named derivation function, a rotation story, and no key in a config file
Has it been independently reviewed?A published report with findings — not a certification logo
What is the threat model?A vendor that can name what it does *not* protect against is telling the truth
The password-reset question is the fastest tell available and takes ten seconds. If a service can give you your data back after you forget everything, then it holds a key — which may be entirely acceptable, and is simply not the same product as one where it cannot. The failure is not the design; it is the marketing that describes both the same way.

Certifications, Compliance and What They Do and Do Not Say
Logos are evidence of something narrower than they appear, and knowing which is which prevents both misplaced trust and unfair dismissal.
SignalActually means
Validated cryptographic moduleA specific module, at a specific version, implements specific algorithms correctly. Not that the product uses it well
Compliance certificationControls were assessed against a framework at a point in time. Says little about the cryptography
"Uses industry-standard algorithms"The minimum bar, stated as an achievement
A published protocol specificationGenuinely meaningful — it can be reviewed by people with no incentive to be kind
An independent audit with findingsThe strongest ordinary signal, especially when the findings are unflattering
A bug bounty with real payoutsEvidence that outside scrutiny is welcome rather than tolerated
The first row is the one most often over-read: a validated module inside a product does not make the product's cryptography sound, because the interesting mistakes are almost always in how the module is *used* — key management, mode selection, protocol design. The general principle behind all of this is the one on Cryptography Fundamentals — The Building Blocks of Security: do not build your own, and be equally suspicious of anyone who did.
