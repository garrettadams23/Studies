🔤 Regular Expressions (Regex) PATTERN MATCHING ▶
Reference
Regex Syntax — Anchors · Classes · Quantifiers · Groups
Regex is used across all platforms — grep/sed/awk on Linux, PowerShell, JavaScript, Python, SQL. Uses PCRE (Perl Compatible) or POSIX syntax depending on engine.
▸ ANCHORS & ASSERTIONS
Token Meaning Example
^ Start of string/line ^Hello matches "Hello world" but not "Say Hello"
$ End of string/line world$ matches "Hello world" but not "world class"
\b Word boundary \bcat\b matches "cat" not "catch"
\B Non-word boundary \Bcat\B matches "scatter" not "cat"
▸ CHARACTER CLASSES
Token Meaning Equivalent
. Any character except newline c.t → "cat","cot","cut"
\d Digit [0-9] \d{3} → "123","456"
\D Non-digit [^0-9]
\w Word char [a-zA-Z0-9_] \w+ → "hello_world"
\W Non-word character [^a-zA-Z0-9_]
\s Whitespace (space, tab, newline) [ \t\n\r]
\S Non-whitespace [^\t\n\r]
[abc] Character class (a, b, or c) [aeiou] matches vowels
[^abc] Negated class (not a, b, or c) [^0-9] matches non-digits
[a-z] Range (lowercase a to z) [A-Za-z] matches any letter
▸ QUANTIFIERS
Token Meaning Greedy vs Lazy
* 0 or more a* greedy; a*? lazy
+ 1 or more a+ greedy; a+? lazy
? 0 or 1 (optional) colou?r → "color" or "colour"
{n} Exactly n times \d{4} → 4-digit number
{n,} n or more times \w{3,} → 3+ word chars
{n,m} Between n and m times \d{2,4} → 2–4 digits
▸ GROUPS & ALTERNATION
Token Meaning Example
(abc) Capture group (\d{3})-(\d{4}) captures area code & number
(?:abc) Non-capture group (?:https?|ftp):// (group without capture)
(?<name>...) Named capture group (?<year>\d{4}) — reference with \k<year>
| Alternation (OR) cat|dog → "cat" or "dog"
(?=...) Positive lookahead \d+(?= dollars) matches "100" in "100 dollars"
(?!...) Negative lookahead \d+(?! dollars) skips dollar amounts
(?<=...) Positive lookbehind (?<=\$)\d+ matches digits after $
▸ FLAGS / MODIFIERS
Flag Meaning Usage
i Case-insensitive /hello/i matches "Hello","HELLO"
g Global (find all matches) /\d+/g finds all numbers
m Multiline (^ $ per line) /^start/m matches each line start
s Dotall (. matches newline) /a.b/s matches "a b"
x Verbose (allow comments) Extended mode for readable patterns
▸ COMMON PATTERNS
# Email address ^[\w.+\-]+@[\w\-]+\.[\w.\-]+$ # IPv4 address ^((?:25[0-5]|2[0-4]\d|[01]?\d\d?)\.){3}(?:25[0-5]|2[0-4]\d|[01]?\d\d?)$ # Strong password: 8+ chars, upper, lower, digit, special ^(?=.*[A-Z])(?=.*[a-z])(?=.*\d)(?=.*[\W_]).{8,}$ # MAC address (colon-separated) ^([0-9A-Fa-f]{2}:){5}[0-9A-Fa-f]{2}$

🔗 URL Encoding — Percent Encoding Reference ENCODING REFERENCE ▶
Reference — W3Schools · MDN · Google · Sigma
URL / Percent Encoding — Rules, Characters & Interactive Decoder
URLs can only contain a safe subset of ASCII characters. Any character outside that set must be percent-encoded: replaced with %XX where XX is the two-digit uppercase hex value of the UTF-8 byte. Also called percent-encoding (RFC 3986).
▸ ENCODING RULES
Safe Characters
Never encoded: A–Z a–z 0–9 - _ . ~
Also safe in specific URL parts: ! * ' ( )
Reserved Characters
Have special URL meaning — encode when used as data:
: / ? # [ ] @ ! $ & ' ( ) * + , ; =
Always Encode
Spaces, Unicode, control chars, and anything outside ASCII printable range must always be percent-encoded. Space → %20 (or + in query strings only)
Query String Rule
In application/x-www-form-urlencoded (HTML forms), space becomes +. In all other contexts use %20.

🧱 Object-Oriented Programming — Classes, Objects & the 4 Pillars OOP ▶
Paradigm
OOP — Modelling the World as Objects
OOP organises code around objects — bundles of related data (fields / properties) and behaviour (methods / functions). A class is the blueprint; an object (instance) is a copy built from that blueprint. Used in Python, Java, C#, C++, JavaScript, Go, Ruby, and most modern languages.
▸ CLASS vs OBJECT — THE KEY DISTINCTION
# CLASS = blueprint. Defined once. Lives in your source file. # OBJECT = instance. Created at runtime. Can have thousands. # Blueprint (Class) class Dog: # __init__ is the CONSTRUCTOR — runs when object is created def __init__(self, name, breed): self.name = name # PROPERTY (instance data) self.breed = breed def speak(self): # METHOD (behaviour) return f"{self.name} says Woof!" # Objects (Instances) dog1 = Dog("Rex", "Husky") # new Dog object in memory dog2 = Dog("Bella","Poodle") # different object, same class print(dog1.speak()) # → Rex says Woof! print(dog2.name) # → Bella (dot notation accesses properties) # dog1 and dog2 share the CLASS but have INDEPENDENT DATA. # Changing dog1.name does NOT affect dog2.name.
▸ THE FOUR PILLARS OF OOP
1. Encapsulation
Bundle data + methods together. Hide internal state — only expose a controlled interface (public vs private). Why: protects data from accidental corruption. The object is a black box; you call methods, not raw variables.
2. Inheritance
A child class inherits properties & methods from a parent class. Child can extend or override them. Why: reuse code without copy-pasting. Cat extends Animal → Cat automatically has all Animal behaviour.
3. Polymorphism
"Many forms." The same method name behaves differently depending on the object it's called on. animal.speak() returns "Woof" for Dog, "Meow" for Cat. Why: write one piece of code that works with any subtype.
4. Abstraction
Hide complex implementation; expose only what the user needs. You call car.start() without knowing about fuel injectors. Why: reduces cognitive load and prevents misuse of internals.

BIG IDEA
What Is Code?
Code is a set of precise instructions you give a computer — like a recipe. The computer follows it exactly and literally, top to bottom, with zero common sense. Most 'bugs' are just the computer doing exactly what you said instead of what you meant.
PLAIN
Program vs. Script
A program is any software built from code. A script is a smaller program, usually run line-by-line to automate a task (rename 1,000 files, back up a folder). The line is blurry — don't worry about it as a beginner.

Computers only understand 1s and 0s (machine code). Compiled languages (C, Go) translate your whole file to machine code once, then run fast. Interpreted languages (Python, JavaScript, Bash) translate line-by-line as they run — easier to start with, a little slower.
DON'T PANIC
You Don't Memorize It
Nobody remembers every command. Real developers look things up constantly, read documentation, and copy-adapt examples. The skill isn't memory — it's breaking a problem into small steps and knowing what to search for.

🐞Errors & Debugging — When Things BreakBeginner • Survival▶
REFRAME
Bugs Are Normal
Every programmer writes bugs every day — the term comes from a real moth found in a 1947 computer. Errors aren't failure; they're the computer telling you precisely where it got confused. Read the message; don't fear it.
SKILL
Read the Error Message
Error messages usually name the file, the line number, and the problem. Start at the top, read the actual words, and look up anything unfamiliar. 90% of beginner debugging is simply slowing down to read what it says.
TECHNIQUE
Print & Rubber-Duck
Two timeless tricks: (1) print values along the way to see what the code actually has, not what you assume. (2) Explain the code out loud, line by line, to a rubber duck — you'll often hear your own mistake.
METHOD
Change One Thing at a Time
Debug like a scientist: form one guess, change one thing, test, repeat. Changing five things at once means you won't know which fixed (or broke) it. Small steps, frequent saves.

RULE #1

🧩Thinking in AlgorithmsBeginner • Problem-Solving▶
PLAIN
An Algorithm Is Just a Plan
An algorithm is a clear, finite list of steps to get a result — a recipe, directions to a friend’s house, the steps to make tea. Coding is mostly writing the plan precisely enough that a literal machine can follow it.
WORKED EXAMPLE
Find the Biggest Number
Watch how a vague goal becomes steps: assume the first item is the biggest, look at each remaining item, and whenever you see a bigger one, remember it instead. At the end, you’re holding the biggest. That’s an algorithm.
# pseudocode
biggest = first item
for each item in list:
    if item > biggest:
        biggest = item
return biggest
WHY IT MATTERS
Some Plans Are Faster
Finding a name in a shuffled pile means checking every card; in a sorted phone book you can flip to the middle and halve the search each time. Same goal, wildly different speed — that idea (Big-O) is why algorithm choice matters as data grows.

🧪Testing Your CodeBeginner • Quality▶
WHY
Tests Catch Tomorrow’s Bug
A test is code that checks your code still works. It feels like extra effort until the day a ‘small fix’ silently breaks something across the project — and a test catches it in one second instead of a customer catching it later.
THE SHAPE
Arrange, Act, Assert
Most tests follow three beats: set up the inputs (arrange), run the thing (act), and check the result is what you expected (assert). If the assertion fails, you found a bug — on purpose, in private.

Happy Path vs. Sad Path

🔢Numbers, Math & Rounding GotchasBeginner • Core▶
TWO KINDS
Integers vs. Decimals
Whole numbers (integers) and decimals (floats) behave differently. In some languages 7 / 2 with two integers throws away the decimal and gives 3, not 3.5 — a surprise that bites beginners. When precision matters, make sure you’re using floats.
FAMOUS BUG
Why 0.1 + 0.2 ≠ 0.3
Computers store decimals in binary, which can’t represent some fractions exactly — just like 1/3 is messy in decimal. So tiny rounding errors appear. It’s not a bug in your code; it’s how floating point works everywhere.
// JavaScript
0.1 + 0.2   // 0.30000000000000004
// round when displaying money, etc.
(0.1 + 0.2).toFixed(2)  // "0.30"
CONVERT
Turning Text into Numbers

📋Looping Over Data — Iteration PatternsBeginner • Core▶
FOR-EACH
Do Something to Every Item
The most common loop visits each item in a list in turn. You rarely need the index — you just want ‘for each thing, do this.’ Cleaner and harder to get wrong than counting positions by hand.

  console.log(`Hi ${n}`);
}
ACCUMULATOR
Build Up a Result
A huge share of real code is: start with an empty total/list, loop, and add to it. Summing numbers, counting matches, filtering a list — all the same shape. Recognize the pattern and most tasks look familiar.

  total=$((total + n))
done < numbers.txt

STEERING
break & continue
Inside a loop, break exits early (‘found it — stop looking’) and continue skips to the next item (‘not interested in this one’). They keep loops from doing needless work.
NESTING
Loops Inside Loops
A loop inside a loop handles grids and combinations — every row, and within each row every column. Powerful, but remember it multiplies the work: 1,000 × 1,000 is a million steps. Use with care on big data.

🧯Handling Errors GracefullyBeginner • Quality▶
CHOICE
Crash or Catch?
When something can fail — a missing file, bad input, a dropped network — you either let it crash (loud, sometimes fine) or catch it and respond calmly. User-facing programs should catch and show a friendly message, not a wall of red.
THE SHAPE
try / catch (try / except)
Wrap the risky bit in ‘try’; if it fails, the ‘catch’ block runs instead of crashing. A ‘finally’ block always runs, perfect for cleanup like closing a file.

    data = open("config.txt").read()
except FileNotFoundError:
    print("No config — using defaults")
BETTER
Validate Before You Leap
Many errors are avoidable: check that a number is in range or a field isn’t empty before using it. Use exceptions for the genuinely unexpected, not as a substitute for basic checks.

🗓️Dates, Times & Time ZonesBeginner • Real-World▶
UNDER THE HOOD
Time Is a Big Number
Computers often store a moment as the number of seconds (or milliseconds) since Jan 1, 1970 — the ‘Unix epoch.’ It looks meaningless (1700000000) but it’s easy to compare and do math on, then format for humans at the end.
THE HEADACHE
Always Store UTC
Time zones and daylight saving cause endless bugs. The pro habit: store and calculate in UTC (one global clock), and convert to the user’s local time only when displaying. Never assume everyone is in your zone.
FORMAT
ISO 8601 — the Sane Format
Write dates as YYYY-MM-DD (2026-06-01) and timestamps as 2026-06-01T13:45:00Z. It sorts correctly as text, removes the is-it-month-or-day confusion, and every language understands it.
🧵A First Look at AsyncBeginner • Web▶

Don’t Stand at the Counter
Some tasks take time — fetching data, reading a big file. ‘Synchronous’ code waits in line, frozen, until it’s done. ‘Asynchronous’ code is like ordering food, taking a buzzer, and sitting down — you get on with other things and react when it’s ready.
WHY IT MATTERS
Keeps Apps Responsive
If a web page waited synchronously for every download, it would freeze on every click. Async lets the page stay alive while data loads in the background — essential for anything that talks to the network.
MODERN SHAPE
async / await

}

🌐 APIs & HTTP — How Programs Talk to Each Other SCRIPT • Start Here ▶
WHAT IS AN API

An API is a menu at a restaurant. You don't walk into the kitchen — you order from a menu (the API), the kitchen (server) makes it, and the waiter (HTTP) brings it back. You get what you need without knowing how it's made.

PUT — replace existing data entirely
DELETE — remove data

Every response has a 3-digit status code.
2xx = Success (200 OK, 201 Created)
3xx = Redirect (301 Moved, 304 Not Modified)
4xx = Your fault (400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found)
5xx = Server's fault (500 Internal Server Error, 503 Service Unavailable)

GraphQL — you ask for exactly what you need in one request; returns only what you specified. Reduces over-fetching.

WHAT IS JSON
JavaScript Object Notation
JSON is text that represents structured data. It's language-neutral — Python, JavaScript, Java, Go all read it. You'll use JSON constantly: API responses, config files, log data, database records.

Six Data Types in JSON

THE BIG IDEA
Bundle Data + Behavior Together
OOP groups related data (attributes) and actions (methods) into one unit called a class. A class is a blueprint; an object (or instance) is the real thing built from that blueprint. One blueprint → many objects.
CLASS ANATOMY
Your First Class
class Dog: # __init__ runs when you create a new Dog def __init__(self, name, breed): self.name = name # instance attribute self.breed = breed self.tricks = [] # every dog starts with no tricks def learn(self, trick): self.tricks.append(trick) def show_off(self): if self.tricks: print(f"{self.name} knows: {', '.join(self.tricks)}") else: print(f"{self.name} knows nothing yet.") # Create two Dog objects from one blueprint rex = Dog("Rex", "Lab") buddy = Dog("Buddy", "Poodle") rex.learn("sit") rex.learn("shake") rex.show_off() # Rex knows: sit, shake buddy.show_off() # Buddy knows nothing yet.
FOUR PILLARS
Encapsulation · Inheritance · Polymorphism · Abstraction
Encapsulation — hide internal details; expose only what's needed (private _name convention in Python).
Inheritance — child class gets parent's methods; add or override as needed.
Polymorphism — same method name, different behavior per class (speak() on Dog vs Cat).
Abstraction — focus on WHAT, not HOW (you call .sort() without knowing the algorithm).
INHERITANCE EXAMPLE
Extend Without Duplicating
class Animal: def __init__(self, name): self.name = name def speak(self): raise NotImplementedError class Dog(Animal): # Dog inherits from Animal def speak(self): return f"{self.name} says Woof!" class Cat(Animal): def speak(self): return f"{self.name} says Meow." animals = [Dog("Rex"), Cat("Whiskers"), Dog("Buddy")] for a in animals: print(a.speak()) # polymorphism — same call, different result
WHEN TO USE OOP
Not Everything Needs a Class
OOP shines when you have multiple instances of the same kind of thing (users, transactions, network packets). Overkill for a 30-line script that reads a file and prints output. Rule of thumb: if you're writing the same data structure twice, make it a class.

LIST COMPREHENSION
Build a List in One Readable Line
A list comprehension is a concise way to create a list by applying an expression to each item in an iterable, with an optional filter. It replaces 4-6 lines of loop code with 1.

A list comprehension builds the entire list in memory at once. A generator expression (() instead of []) produces values one at a time on demand. Essential for large datasets (files with millions of lines, streaming data).

🗄️ SQL & Databases — Where Data Actually Lives SCRIPT • Foundation ▶
WHAT IS A DATABASE
Structured, Persistent, Queryable Storage
A database stores data so it can be retrieved, filtered, sorted, and updated efficiently. A file full of JSON works for small things; a real database handles millions of rows, concurrent users, transactions, and relationships between tables without losing data.
RELATIONAL DATABASES
Tables, Rows, and Relationships
A relational database stores data in tables (like spreadsheets). Each table has rows (records) and columns (fields). Tables relate to each other through foreign keys. SQL (Structured Query Language) is the language for interacting with them. Popular: PostgreSQL, MySQL, SQLite, Microsoft SQL Server, Oracle.
BASIC SQL
CRUD in SQL — Create, Read, Update, Delete
-- Create a table CREATE TABLE users ( id INTEGER PRIMARY KEY AUTOINCREMENT, name TEXT NOT NULL, email TEXT UNIQUE NOT NULL, age INTEGER, created DATETIME DEFAULT CURRENT_TIMESTAMP ); -- Insert rows INSERT INTO users (name, email, age) VALUES ('Alice', 'alice@example.com', 30); -- Read / query SELECT * FROM users; SELECT name, email FROM users WHERE age > 25; SELECT * FROM users ORDER BY name ASC LIMIT 10; -- Update UPDATE users SET age = 31 WHERE email = 'alice@example.com'; -- Delete DELETE FROM users WHERE id = 5;
JOINS
Combine Data From Multiple Tables
-- Users and their orders (one user, many orders) CREATE TABLE orders ( id INTEGER PRIMARY KEY, user_id INTEGER REFERENCES users(id), amount REAL, status TEXT ); -- INNER JOIN: only rows that match in BOTH tables SELECT users.name, orders.amount, orders.status FROM orders INNER JOIN users ON orders.user_id = users.id; -- LEFT JOIN: all users, even those with no orders SELECT users.name, orders.amount FROM users LEFT JOIN orders ON users.id = orders.user_id; -- Aggregate: total spent per user SELECT users.name, SUM(orders.amount) AS total FROM users LEFT JOIN orders ON users.id = orders.user_id GROUP BY users.id ORDER BY total DESC;
PYTHON + SQLITE
Embedded Database, No Server Required
import sqlite3 # Connect (creates file if not exists) conn = sqlite3.connect("mydb.sqlite") conn.row_factory = sqlite3.Row # access columns by name cursor = conn.cursor() # Create table cursor.execute(""" CREATE TABLE IF NOT EXISTS notes ( id INTEGER PRIMARY KEY AUTOINCREMENT, title TEXT NOT NULL, body TEXT ) """) # Parameterized insert (ALWAYS use ? placeholders, never f-strings in SQL!) cursor.execute("INSERT INTO notes (title, body) VALUES (?, ?)", ("First note", "Content here")) conn.commit() # Query rows = cursor.execute("SELECT * FROM notes ORDER BY id DESC").fetchall() for row in rows: print(row["title"], row["body"]) conn.close()
The ? placeholder is critical. Never build SQL with string formatting — that's how SQL injection happens: f"WHERE name = '{user_input}'" lets attackers inject arbitrary SQL.
SQL vs NoSQL
Relational vs Document/Key-Value/Graph
SQL databases (PostgreSQL, MySQL, SQLite) — structured schema, ACID transactions, complex queries, relationships. Best for: financial data, user records, anything needing data integrity.
NoSQL databases — flexible schemas, horizontal scaling, specialized access patterns:
• Document (MongoDB) — JSON-like docs; good for varying schemas
• Key-Value (Redis) — extremely fast lookups; caching, sessions
• Column-family (Cassandra) — time-series, logs, analytics
• Graph (Neo4j) — relationships between entities (social network, fraud detection)

⏳ Async Programming — Do More Without Waiting SCRIPT • Intermediate ▶
THE PROBLEM
I/O-Bound vs CPU-Bound Work
CPU-bound: computation is the bottleneck (image processing, cryptography, simulations). More CPU cores help. Use multiprocessing.
I/O-bound: waiting for external things (network responses, disk reads, database queries). CPU is mostly idle waiting. One thread can handle hundreds of concurrent I/O operations by switching between them while each waits. Use asyncio.
ASYNC / AWAIT
Coroutines in Python
An async def function is a coroutine — it can pause itself at await points while other coroutines run. The event loop switches between them, never blocking the thread.
import asyncio import aiohttp # pip install aiohttp async def fetch_url(session, url): async with session.get(url) as response: text = await response.text() print(f"{url}: {len(text)} chars") return text async def main(): urls = [ "https://httpbin.org/delay/1", "https://httpbin.org/delay/1", "https://httpbin.org/delay/1", ] async with aiohttp.ClientSession() as session: # Fetch all three CONCURRENTLY — takes ~1s total, not 3s tasks = [fetch_url(session, url) for url in urls] results = await asyncio.gather(*tasks) asyncio.run(main())

🔀 Concurrency — Doing More Than One Thing at Once SCRIPT • Advanced ▶
CONCURRENCY VS PARALLELISM
Two Words People Confuse
Concurrency is dealing with many things at once (structure) — like a chef juggling several dishes, switching between them. Parallelism is doing many things at literally the same instant (execution) — like several chefs each cooking one dish. Concurrency is about structure; parallelism is about simultaneous execution. You can have concurrency on a single core (task switching); you need multiple cores for true parallelism.
THE GIL
Why Python Threads Don't Speed Up CPU Work
CPython has a Global Interpreter Lock (GIL) — only one thread executes Python bytecode at a time. This means threads don't give you parallel CPU work in Python. But they're still great for I/O-bound work (waiting on network/disk), because the GIL is released during I/O waits. The key question for choosing a tool: is your task I/O-bound or CPU-bound?

FROM SNIPPET TO TOOL
What Separates a Script from a Tool
A throwaway script has hardcoded values and prints with print(). A real tool that others can use has: command-line arguments, configuration, proper logging, error handling, and a clear exit code. Here's a complete example that ties together everything — argparse, logging, config, and exit codes — into a tool you'd actually deploy.
#!/usr/bin/env python3 """logcheck — scan a log file for error patterns and report.""" import argparse, logging, sys, re from pathlib import Path # ── Logging setup ───────────────────────────────────────── log = logging.getLogger("logcheck") def setup_logging(verbose: bool): level = logging.DEBUG if verbose else logging.INFO logging.basicConfig( level=level, format="%(asctime)s %(levelname)s %(message)s", ) # ── Core logic ──────────────────────────────────────────── def scan(path: Path, pattern: str) -> int: regex = re.compile(pattern) matches = 0 with path.open() as f: for num, line in enumerate(f, 1): if regex.search(line): matches += 1 log.debug("match line %d: %s", num, line.strip()) return matches # ── Argument parsing ────────────────────────────────────── def main(argv=None): p = argparse.ArgumentParser(description="Scan a log for a pattern.") p.add_argument("logfile", type=Path, help="log file to scan") p.add_argument("-p", "--pattern", default="ERROR", help="regex pattern") p.add_argument("-t", "--threshold", type=int, default=0, help="exit non-zero if matches exceed this") p.add_argument("-v", "--verbose", action="store_true") args = p.parse_args(argv) setup_logging(args.verbose) if not args.logfile.exists(): log.error("File not found: %s", args.logfile) return 2 # exit code 2 = usage/file error count = scan(args.logfile, args.pattern) log.info("Found %d matches for %r", count, args.pattern) # Exit code drives monitoring/automation if count > args.threshold: log.warning("Threshold exceeded!") return 1 return 0 if __name__ == "__main__": sys.exit(main())
USING IT
Why This Design Pays Off

The key lessons: accept input via arguments (not hardcoding), use logging (not print) so output levels are controllable, return meaningful exit codes (0 = success, non-zero = problem) so the tool plays well with shell scripts and monitoring, and guard main() with if __name__ == "__main__" so it's also importable. This is the anatomy of every good CLI tool.

🔤 Encoding — Bytes, Text, and Why "It Works on My Machine" SCRIPT • Foundation ▶
BYTES VS TEXT
The Distinction That Trips Up Everyone
Computers store everything as bytes (numbers 0-255). Text is bytes interpreted through an encoding. str is human-readable text; bytes is raw binary. You encode text → bytes (to send/store) and decode bytes → text (to read). Confusing the two causes the classic UnicodeDecodeError and garbled "mojibake" text.
# Text (str) ↔ raw bytes text = "café" data = text.encode("utf-8") # str → bytes: b'caf\xc3\xa9' back = data.decode("utf-8") # bytes → str: 'café' # The golden rule: decode at input, encode at output. # Work with str internally; only deal in bytes at the edges # (files, network, subprocess). # Always specify encoding explicitly — don't rely on defaults with open("f.txt", encoding="utf-8") as f: ...
UTF-8 & UNICODE
One Encoding to Rule Them All
Unicode assigns every character a number ("code point") — covering every language, emoji, and symbol. UTF-8 is the dominant way to encode those code points as bytes: it's variable-width (1 byte for ASCII, up to 4 for others) and backward-compatible with ASCII. Rule of thumb: use UTF-8 everywhere. Legacy encodings (Latin-1, Windows-1252) cause the most "weird character" bugs.
ENCODING SCHEMES
Base64, Hex, URL — Different Jobs
These are not encryption — they're reversible representations, no secrecy. They exist to safely move binary data through text-only channels.
SchemePurposeExample
Base64Binary → ASCII text (email attachments, JWTs, data URIs)SGVsbG8= = "Hello"

HASHING (NOT ENCODING)
One-Way by Design
Don't confuse hashing with encoding/encryption. Encoding is reversible (anyone can decode). Encryption is reversible with a key. Hashing is one-way — you cannot get the input back from the hash. Hashing is for integrity checks and password storage, never for "hiding" data you need to recover.

🧪 Testing Strategy — Why and How to Test SCRIPT • Professional ▶
WHY TEST
Tests Are Your Safety Net for Change
Tests aren't about proving code works once — they're about being able to change code confidently later. Without tests, every change risks silently breaking something elsewhere, so people become afraid to touch the code (it "ossifies"). With a good test suite, you refactor fearlessly: if you break something, a test tells you instantly. Tests are also living documentation of how the code is meant to behave.
THE TEST PYRAMID
Many Fast Tests, Few Slow Ones

Unit (base)One function/class in isolationMillisecondsMany (the bulk)

The shape is a pyramid for a reason: lots of fast, reliable unit tests at the base; fewer slow, brittle E2E tests at the top. The "ice cream cone" anti-pattern (mostly slow E2E tests) makes a suite slow and flaky — painful to run, so people stop running it.
TDD

TDD flips the usual order: write the test first, watch it fail, then write just enough code to pass. It forces you to clarify what the code should do before writing it, and guarantees test coverage. Not everyone does strict TDD, but the cycle is a valuable tool to know.

Core Concept
Why IoT Is a Security Problem
IoT (Internet of Things) devices — cameras, smart TVs, routers, industrial sensors, medical devices — are computers with network access. Unlike PCs, they often:

• Ship with default credentials that users never change.
• Run outdated Linux kernels with no automatic updates.
• Expose unnecessary services (Telnet, FTP, unencrypted HTTP) on open ports.

Intermediate Python Async/Await – Concurrent I/O Without Threads
Core Concept
Why Async? The Waiting Problem
A normal Python function blocks while waiting for I/O (network call, file read, database query). If you have 1,000 API calls to make, sequential blocking takes 1,000 × wait time.

Async lets Python do something else while waiting. When an I/O call is in-flight, the event loop switches to another coroutine — so 1,000 API calls can be in-flight simultaneously.

Rule of thumb:
• Use async/await for I/O-bound work (HTTP calls, DB queries, file I/O).
• Use multiprocessing for CPU-bound work (image processing, ML training) — Python's GIL still blocks CPU work in a single process.

"Not my circus, not my monkey" — don't force async on everything. A simple script with two HTTP calls doesn't need it. Use it when you have many concurrent I/O operations.
Syntax
async def, await, and asyncio.run
An async def function is a coroutine. Calling it returns a coroutine object — it doesn't run until you await it or pass it to the event loop.
import asyncio, time async def fetch_data(url: str) -> str: print(f"Starting {url}") await asyncio.sleep(1) # simulate network wait print(f"Done {url}") return f"data from {url}" async def main_sequential(): t = time.perf_counter() r1 = await fetch_data("http://api-1") r2 = await fetch_data("http://api-2") print(f"Sequential: {time.perf_counter()-t:.1f}s") # ~2 s async def main_concurrent(): t = time.perf_counter() r1, r2 = await asyncio.gather( fetch_data("http://api-1"), fetch_data("http://api-2"), ) print(f"Concurrent: {time.perf_counter()-t:.1f}s") # ~1 s asyncio.run(main_sequential()) asyncio.run(main_concurrent())

The requests library is synchronous — it blocks. Use aiohttp for async HTTP. This example fetches 100 URLs concurrently instead of one at a time.
# pip install aiohttp import asyncio, aiohttp URLS = [ "https://httpbin.org/delay/1", "https://httpbin.org/delay/1", "https://httpbin.org/delay/1", ] # extend to 100+ in real use async def fetch(session: aiohttp.ClientSession, url: str) -> dict: async with session.get(url) as resp: data = await resp.json() return {"url": url, "status": resp.status} async def main(): async with aiohttp.ClientSession() as session: tasks = [fetch(session, u) for u in URLS] results = await asyncio.gather(*tasks, return_exceptions=True) for r in results: if isinstance(r, Exception): print("Error:", r) else: print(r) asyncio.run(main()) # 3 × 1-second requests complete in ~1 second total
Rate Limiting

Launching 10,000 coroutines at once can overwhelm an API or exhaust file descriptors. Use a Semaphore to cap concurrent tasks.

Investigation
git bisect — Finding the Commit That Broke Things
When a bug appears and you don't know which of the last 200 commits introduced it, git bisect performs an automated binary search through history.
# Start a bisect session git bisect start # Tell git the current commit is broken (bad) git bisect bad # Tell git a known-good commit (e.g. last release tag) git bisect good v2.3.0 # Git checks out a commit halfway between good and bad. # Test it, then tell git the result: git bisect good # if this commit works # or git bisect bad # if this commit is broken # Repeat — git narrows the range each time (log2(N) steps total) # When done, git identifies the exact commit that introduced the bug: # "a1b2c3d is the first bad commit" # Clean up when finished git bisect reset # Automate it entirely with a test script (no manual testing!) git bisect start HEAD v2.3.0 git bisect run pytest tests/test_regression.py # git runs the test at each step and decides good/bad automatically

# Interactively edit the last 5 commits git rebase -i HEAD~5 # This opens an editor with lines like: pick a1b2c3d Add login form pick d4e5f6a Fix typo in login form pick 7890abc WIP debugging pick bcdef12 Actually fix the bug pick 3456789 Remove debug prints # Change "pick" to control what happens to each commit: # pick = keep commit as-is # reword = keep changes, edit the commit message # squash = combine with the commit above (keep both messages) # fixup = combine with commit above (discard this message) # drop = remove the commit entirely # Cleaned-up result might look like: pick a1b2c3d Add login form fixup d4e5f6a Fix typo in login form drop 7890abc WIP debugging fixup bcdef12 Actually fix the bug drop 3456789 Remove debug prints # Result: one clean commit "Add login form" instead of five messy ones
Recovery
git reflog — Your Undo Button for Almost Anything
You can't make someone make the right choice, yet you can pick up the pieces afterwards — someone on your team will run git reset --hard on the wrong branch eventually. git reflog is how you save them.

Git keeps a log of every place HEAD has pointed — commits, resets, rebases, checkouts — for about 90 days, even ones that seem to have "vanished."
# Show every recent HEAD movement (even "lost" commits) git reflog # Output looks like: # a1b2c3d HEAD@{0}: reset: moving to HEAD~3 # d4e5f6a HEAD@{1}: commit: Add payment validation # 7890abc HEAD@{2}: commit: Fix currency rounding bug # ... # Recover "lost" commits by checking out the reflog entry git checkout HEAD@{1} # Or restore your branch to before the bad reset git reset --hard HEAD@{1} # Recover a deleted branch entirely git reflog | grep "checkout: moving from feature-x" git branch feature-x <commit-hash-from-reflog> # Find "dangling" commits not referenced by any branch git fsck --lost-found

These commands solve the "I need to switch context without losing my work" problem in different ways.
# STASH — temporarily shelve uncommitted changes git stash push -m "WIP: refactoring auth module" git checkout main # switch branches with a clean working tree # ... fix the urgent bug ... git checkout feature-branch git stash pop # bring your work back git stash list # see all stashed changes # CHERRY-PICK — apply a specific commit from another branch git log other-branch --oneline # find the commit hash you need git cherry-pick a1b2c3d # apply just that one commit here # Common use: backporting a critical bugfix to a release branch # WORKTREES — check out multiple branches simultaneously in # separate directories (no stashing needed) git worktree add ../hotfix-dir hotfix/critical-bug # Now you have two working directories on two branches at once — # build/test the hotfix while your main feature work stays untouched git worktree list git worktree remove ../hotfix-dir

    print("No tags on this resource")

# Also always check the status code BEFORE trusting the body —
# a 404 page might still return something that *looks* like JSON
if response.status_code == 200:
    process(response.json())
else:
    print(f"Request failed: {response.status_code} — {response.text[:200]}")

Regular Expressions – A Survival Guide for IT Tasks

Concept

Regex is "find by pattern" instead of "find by exact text"

A regular expression is a mini-language for describing patterns in text — instead of searching for the literal string "192.168.1.1", you can search for "anything that looks like an IPv4 address." That shift — from matching exact text to matching shapes of text — is what makes regex so powerful for log analysis, data validation, and bulk text processing. It has a reputation for looking like line noise, but a relatively small set of building blocks covers the vast majority of real IT use cases.

Hands-on

A real log-parsing example, built up piece by piece

import re

log_line = '2026-06-06 03:14:07 ERROR [auth-service] Failed login from 203.0.113.42 for user jdoe'

# Build the pattern in labeled pieces — far more readable than one giant blob
pattern = (
    r"(?P<date>\d{4}-\d{2}-\d{2}) "          # 2026-06-06
    r"(?P<time>\d{2}:\d{2}:\d{2}) "          # 03:14:07
    r"(?P<level>\w+) "                       # ERROR
    r"\[(?P<service>[\w-]+)\] "            # [auth-service]
    r".*from (?P<ip>\d+\.\d+\.\d+\.\d+) "  # 203.0.113.42
    r"for user (?P<user>\w+)"                # jdoe
)

match = re.search(pattern, log_line)
if match:
    print(f"{match['level']} from {match['ip']} targeting account '{match['user']}'")
    print(f"Service: {match['service']}  at {match['date']} {match['time']}")
# Output:
# ERROR from 203.0.113.42 targeting account 'jdoe'
# Service: auth-service  at 2026-06-06 03:14:07

Named groups ((?P<name>...)) are the difference between a regex you can read again in six months and one you'll have to rebuild from scratch. They turn "what does group 4 mean again?" into "oh, that's obviously the IP address."

Mindset

Assume makes an ass out of you and me — test against real, messy data

A pattern that works perfectly on the three sample lines you wrote it against can fall apart the moment it meets real-world data — an extra space, a different timestamp format, a username with a hyphen you didn't anticipate. Before trusting a regex in a script that runs unattended, run it against a large, genuinely messy sample of real data and actually look at what it *fails* to match — that's usually far more informative than looking at what it successfully matches.

Scheduling Scripts the Right Way – Cron, Timers, and Idempotency

Concept

Automation that runs on its own schedule — and why that's harder than it sounds

Plenty of useful scripts are designed to run on a schedule rather than on demand — nightly backups, hourly report generation, weekly cleanup jobs. Getting a script to "just run at 2 AM" is the easy part. The harder, more important part is making sure that when something goes wrong — the script crashes halfway, runs twice by accident, or runs while a previous run is still going — the result is "annoying log entry" rather than "corrupted data" or "duplicate emails sent to every customer."

Hands-on

The classic: cron syntax, decoded

# Cron's five fields, in order:
#   minute  hour  day-of-month  month  day-of-week

# Run every day at 2:30 AM
30 2 * * *  /opt/scripts/nightly_backup.sh

# Run every 15 minutes
*/15 * * * *  /opt/scripts/check_health.sh

# Run at 9 AM, Monday through Friday only
0 9 * * 1-5  /opt/scripts/send_daily_digest.sh

# Run on the 1st of every month at midnight
0 0 1 * *   /opt/scripts/monthly_report.sh

# View your current scheduled jobs
crontab -l

# Edit them (opens your default editor)
crontab -e

Many modern Linux systems also offer systemd timers as an alternative — they integrate with journalctl for logging, can express dependencies on other services, and handle "what if the system was off when this should have run?" more gracefully. Cron remains common and perfectly fine for simple jobs; timers shine once your scheduling needs get more sophisticated.

Concept

Idempotency: the property that turns "uh oh" into "no big deal"

A script is idempotent if running it multiple times produces the same end result as running it once. This single property is what determines whether "the job accidentally ran twice" is a non-event or an incident.

# NOT idempotent — running this twice creates two records,
# sends two emails, charges a customer twice...
def process_daily_signups():
    new_users = get_signups_since_last_run()
    for user in new_users:
        send_welcome_email(user)
        create_billing_record(user)

# IDEMPOTENT — checks what's already been done before doing it again
def process_daily_signups():
    new_users = get_signups_since_last_run()
    for user in new_users:
        if not already_sent_welcome_email(user):
            send_welcome_email(user)
            mark_welcome_email_sent(user)
        if not has_billing_record(user):
            create_billing_record(user)

Notice the pattern: instead of just "do the thing," idempotent code asks "has this already been done?" first. That one habit — checking before acting, every time — is what separates scheduled automation you can trust from scheduled automation that occasionally needs a 3 AM apology email to customers.

Mindset

Assume makes an ass out of you and me — assume it WILL run twice someday

"It only runs once a day, what are the odds it overlaps with itself?" is exactly the kind of assumption that holds up fine for months — until a slow database connection causes one run to take 25 hours, and suddenly two copies are running at once, both modifying the same data. Writing scheduled scripts as though they will eventually run concurrently or get interrupted mid-task — using locks, idempotency checks, and transactional updates — costs a little extra effort upfront and saves an enormous amount of cleanup later.
