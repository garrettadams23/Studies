🏢 Microsoft Endpoint Configuration Manager (MECM) On-Prem ▶
Reference
ConfigMgr / SCCM (System Center Configuration Manager) — What It Is & Where It Fits
MECM (formerly SCCM, universally called ConfigMgr) is Microsoft's on-premises platform for managing Windows (and some Linux/macOS/servers) at scale: application deployment, patching, OS (Operating System) imaging, hardware/software inventory, and compliance. It ships in the Current Branch model — a new feature release roughly three times a year (e.g. 2403 = 2024, March), applied in-console.
StrengthWhy it still matters
Deep OS deploymentFull bare-metal imaging & task sequences Intune can't match
Bandwidth controlOn-prem DPs, peer caching for large/branch fleets
Granular software dist.Complex app models, supersedence, dependencies
Mature reportingSQL (Structured Query Language) Reporting Services, rich inventory
The direction of travel is cloud: most orgs now run co-management (ConfigMgr + Intune on the same device) and move workloads to Intune over time. ConfigMgr isn't dead — it's the on-prem anchor of a hybrid estate (see the Co-management card).
Architecture
Sites, the Database & Site System Roles
A ConfigMgr deployment is a hierarchy of sites, each identified by a 3-character site code (e.g. P01). Most orgs need only a single standalone primary site; very large or multi-geo estates add a CAS and/or secondary sites.

Most organisations need one primary site, and the ones that built a hierarchy usually regret it. A central administration site adds replication, upgrade complexity and a class of fault that only exists because the hierarchy does — and it earns its place only at genuinely large scale. Of the roles below, the cloud management gateway is the one that changes how the estate works: it manages internet- based clients without a VPN (Virtual Private Network), which is what makes ConfigMgr survive remote working.
The Client

The ConfigMgr client (ccmsetup.exe → CcmExec service) runs policy, inventory, and deployments. It can be installed several ways; client behavior is governed by Client Settings (default + prioritized custom sets assigned to collections).

Content & Targeting
Boundaries, Boundary Groups & Distribution
Clients find their nearest servers via boundaries (IP subnet, AD site, IPv6 prefix, or IP range) grouped into boundary groups, which map to the MPs/DPs/SUPs a client should use — with fallback relationships and time delays.

Deploying Things
Applications, Updates & OS Deployment
Everything targets a collection (device or user; direct or query/WQL membership). The three big deployment workloads:

ApplicationsDeployment types + detection method + requirement rules + supersedence; purpose Available (Software Center) or Required (enforced by deadline)

Detection method is the make-or-break of app deployment: it's how ConfigMgr decides "already installed?" (file version, registry, MSI product code, or script). Wrong detection = endless reinstall or false failure. Maintenance windows on a collection limit when Required installs/reboots may run — critical for servers.

🪪 Azure AD (Active Directory) / Microsoft Entra ID — Endpoint Identity Identity ▶
Concept
The Identity Layer Everything Sits On
Microsoft Entra ID (formerly Azure AD) is the cloud directory behind Microsoft 365 and Intune. Every managed device gets a device object in Entra; how it obtains that identity (its join type) determines which management, SSO (Single Sign-On), and Conditional Access experiences are possible.
Join typeHow & when
Entra JoinedCloud-only. Set during OOBE/Autopilot or Settings. The modern default for corporate Windows
Entra Hybrid JoinedDomain-joined and synced to Entra (needs Entra Connect + SCP). For orgs still reliant on on-prem AD/GPO/apps
Entra RegisteredBYOD/personal — a work identity is added but the org doesn't own the device (Workplace Join)
Hybrid is heavier & more fragile (sync timing, SCP, network line-of-sight to a DC for the join). Microsoft's clear guidance: go cloud-native (Entra Joined) unless a hard dependency forces hybrid.
Internals
dsregcmd, the PRT (Primary Refresh Token) & Windows Hello for Business
The device's join/registration state is the first thing to check when SSO or enrollment misbehaves. dsregcmd /status is the definitive local tool. 
# Show device join & SSO state (run as the signed-in user)
dsregcmd /status
# Key fields:
#   AzureAdJoined : YES        -> Entra Joined
#   DomainJoined  : YES        -> (also) on-prem = Hybrid
#   AzureAdPrt    : YES        -> Primary Refresh Token present (SSO works)
#   MdmUrl / MdmEnrollmentUrl  -> auto-enrollment configured
TermMeaning
Primary Refresh Token (PRT)Issued at sign-in; grants seamless SSO to M365 apps & browsers
Windows Hello for BusinessPasswordless (PIN/biometric) bound to the device via asymmetric keys
Device objectThe Entra record CA & Intune reason about (compliant? managed? join type?)
Run the status command first, and read the join state before anything else. Single sign-on failures, Conditional Access surprises and enrolment loops nearly all reduce to a device that is not in the state you assumed — and one command settles it in seconds. If the refresh token is absent, everything downstream will misbehave in ways that look like separate faults.

✈️ Windows Autopilot — Zero-Touch Provisioning Provisioning ▶
Concept
Ship a Sealed OEM Laptop Straight to the User
Windows Autopilot customizes the out-of-box experience (OOBE) so a factory device configures itself for your org — no imaging, no touching it in IT. The device's hardware identity is pre-registered to your tenant; at first boot it recognizes itself, Entra-joins, enrolls in Intune, and applies your apps/policies through the ESP (Enrollment Status Page).
Deployment modeUse case & behavior
User-drivenUser signs in during OOBE → device joins Entra as theirs. The standard mode
Pre-provisioning (White Glove)IT/OEM/partner runs the device phase first (apps, policies), reseals; user gets a short finish
Self-deployingNo user creds — kiosks, digital signage, shared/lab (requires TPM 2.0)
Existing devicesRe-provision an in-place PC via a ConfigMgr task sequence into Autopilot
Autopilot ResetWipe user data/apps but keep Entra join & enrollment — hand-off/refresh
Pre-provisioning is the mode that makes the promise deliverable on a real network. User- driven is the demonstration everybody sees and it puts the entire application install in front of somebody waiting at a kitchen table on domestic broadband — which is where the good impression is lost. Do the device phase in advance where you can, and keep the reset row in mind: it is the cheapest way to hand a machine to the next person.

🚀 Autopilot Device Preparation — The Newer Flow That Deletes the Hardware Hash Intune • Provisioning ▶
The Inversion
The Hardware Hash Was the Bottleneck. Device Preparation Removes It Entirely.
Classic Autopilot's whole model rests on pre-registering each device's ~4 KB hardware hash to the tenant before it can provision — and that registration is the fragile, slow part: it depends on the OEM or reseller doing it, or on you harvesting hashes, and an unregistered device simply falls through to a plain out-of-box experience. Autopilot device preparation — the newer flow — removes the pre-registration altogether. The device is no longer identified by a hash uploaded in advance; instead the user signs in, the device is placed into a security group you nominate, and a device-preparation policy targeted at that group provisions it. The single most brittle dependency in classic Autopilot — get the hash in first — is gone.
AspectClassic AutopilotDevice Preparation
Device identityPre-uploaded hardware hashUser sign-in + a nominated security group — no hash
Registration stepOEM / reseller / manual harvest — fragile at scaleNone required
What provisions itDeployment profile via a dynamic group on a group tagA device-preparation policy assigned directly to a user group
Unregistered deviceDrops to a normal OOBE (Out-of-Box Experience) with no brandingNot a failure mode — there is nothing to pre-register
The unit that actually changed is device identity: hash-first becomes user-and-group-first, which deletes the dependency that generated most “Autopilot didn't trigger” tickets in the first place.
The Fingerprint
Simpler, But Not a Drop-In Replacement — It Is a Narrower Model
Device preparation is not classic Autopilot with the hash removed; it is a different, deliberately narrower model. It is Entra join only — no hybrid Entra join — it provisions a defined set of apps and scripts from the policy rather than gating on the full Enrollment Status Page app catalogue, and it targets a security group directly. So the way to tell which tool a scenario needs is to ask what it requires: hybrid join, white-glove pre-provisioning or self-deploying kiosks still belong to classic Autopilot; cloud-native user-driven provisioning where the hash was the pain belongs to device preparation.
What the scenario needsWhich flow answers it
Cloud-native, Entra-joined, user-driven setupDevice preparation
Hybrid Entra join to on-prem AD (Active Directory)Classic Autopilot — device preparation cannot
Pre-provisioning / white gloveClassic Autopilot
Self-deploying kiosks with no userClassic Autopilot self-deploying
Kill the hardware-hash registration dependencyDevice preparation
Same intent — zero-touch to the user — inside a different envelope: device preparation trades some of classic Autopilot's flexibility for the removal of its most fragile dependency.
The Decision
New Cloud-Native Fleets Start Here; Hybrid and Edge Cases Keep Classic
The mistake in both directions is treating this as a like-for-like upgrade. It is not: for a greenfield or cloud-native estate handing Entra-joined Windows devices to users, device preparation is the lower-friction default going forward — no hash wrangling, fewer moving parts. But a working classic Autopilot pipeline with OEM registration is not broken, and where you still need hybrid join, white-glove or self-deploying kiosks, classic Autopilot remains the only tool.
So the decision is scenario-led, not version-led: reach for device preparation on new cloud-native provisioning to be rid of the hardware hash, and keep Windows Autopilot — Zero-Touch Provisioning for hybrid and the pre-provisioning modes it still owns. Either way the desktop is still gated by the same finish-line logic that Enrollment Status Page (ESP) describes — do not migrate a pipeline that already works simply because a newer flow exists.
⏳ Enrollment Status Page (ESP) Provisioning ▶
Concept
The Gate That Makes a Device Ready on Day One
The Enrollment Status Page is the full-screen progress screen during Autopilot/enrollment. Its purpose is to withhold the desktop until the device is genuinely ready — required apps installed, policies applied, certs delivered — so nobody lands on a half-configured machine and starts working before security settings arrive.
PhaseRunsTracks
Device preparationPre-sign-inTPM (Trusted Platform Module) attestation (self-deploy), Entra join, Intune enrollment
Device setupPre-sign-inDevice-targeted apps, policies, certificates, security
Account setupAfter user signs inUser-targeted apps & policies
Configured under Intune → Devices → Enrollment → Enrollment Status Page: a Default profile plus higher-priority profiles assigned to groups.
Settings
Every Knob and What It Does
SettingEffect
Show app/profile install progressMaster switch — turns the ESP on for the group
Block device use until all apps & profiles installHard gate — no desktop until success
Selected blocking appsExplicit list that must succeed before release
Show error when time exceeds (timeout)Default 60 min — raise for big app sets/slow links
Allow reset on failureUser can wipe & retry
Allow use of device on failureContinue to desktop if non-blocking items fail

Allow log collection on failureUser can export diagnostics

Keep the blocking list short, and raise the timeout before you first deploy rather than after. Every application on the blocking list is a chance for a user's first ten minutes with a new laptop to end in an error screen — block on the two or three things that genuinely make the machine unusable without them, and let the rest arrive afterwards. Log collection on failure costs nothing and is the difference between a diagnosable and an undiagnosable report from a remote user.
Reference
What Counts, Timeouts & Troubleshooting
ESP tracks only Required-assigned apps/policies that target the device/user in scope — Available apps are ignored. In the device phase it can only track device-targeted items (user isn't known yet), which is why heavy user-targeted apps belong in the account phase or pre-provisioning.
PitfallFix
Too many/large blocking apps → timeoutKeep blocking set minimal; raise timeout; use pre-provisioning
Wrong detection rule → waits foreverFix the app's detection method (it already installed)
User-targeted app tracked in device phaseAssign to devices, or move to account phase
Win32 app depends on another → orderModel dependencies so prerequisites finish first
Best practice: block only what a user truly needs on day one (security agent, VPN, core LOB app); set a realistic timeout; and front-load device-targeted apps via pre-provisioning so the end-user wait is minutes, not an hour. Logs: Event Viewer → DeviceManagement-Enterprise-Diagnostics-Provider and the Autopilot diagnostics page.

Common combos: on slow branch links, raise SMSTSDownloadRetryCount/Delay, set SMSTSLocalDataDrive=C early, and enable SMSTSPeerDownload so peers share content. Use SMSTSPreserveContent when a later phase (or a re-image retry) reuses the same packages. Verify all of it in smsts.log.
🏛️ MECM (Microsoft Endpoint Configuration Manager) at Scale — Site Design, Boundary Groups & Collections That Don't Melt the Server MECM • Architecture ▶
The Inversion
The CAS Is the Mistake. One Primary Site Goes Further Than You Think.
The instinct when the estate is large is to build a hierarchy — a Central Administration Site on top, primary sites beneath it, a secondary site at every branch. It is almost always wrong. A single standalone primary site supports on the order of 150,000 clients; the CAS exists only to roll several primaries into one console above that ceiling, and it buys you a whole new failure domain — SQL (Structured Query Language) replication between sites — that you now have to keep healthy and debug when it drifts. The shops that stood up a CAS “to be safe” mostly spend their time nursing replication they never needed.
Site typeWhat it is forWhen it is actually justified
Central Administration SiteRoll-up console and configuration across multiple primary sitesOnly above a single primary's ceiling (~150k), or a genuine multi-primary need — not for tidiness
Primary siteThe workhorse: clients attach here, it owns a SQL databaseAlmost every organisation needs exactly one, and only one
Secondary siteThrottles and controls content sent upstream to a remote locationOnly when a location can't reach a distribution point and needs local, bandwidth-managed content — otherwise a plain DP is the answer
The unit you are really choosing is how many SQL databases you must keep in sync. Build one primary; add a secondary only to manage a starved WAN (Wide Area Network) link, and reach for a distribution point — not a site — everywhere else.
The Fingerprint
When Content Comes From the Wrong Place, It Is Almost Always Boundary Groups
Boundaries — an IP (Internet Protocol) subnet, an AD (Active Directory) site, an IP range — map a client to a boundary group, and the boundary group names the site systems (management point, distribution point, software update point) that client should use. The classic failure is a client pulling content from the wrong distribution point: an install that crawls over the WAN when a healthy DP sits on the same subnet, or “no content available” when the local DP plainly has it. That symptom has one usual cause — a boundary the client falls outside of, a fallback that lands on a distant DP or the site server itself, or a fallback timer so short the client reaches across the link before its preferred DP even answers.
SymptomThe boundary-group cause behind it
Client pulls content over the WAN though a local DP existsThe client's subnet isn't in a boundary group that references the local DP
“No content available” despite a healthy DPClient is in no boundary group and no fallback source is configured
Site server itself hammered for contentFallback lands on the default site boundary group, with the site server acting as a DP
Content arrives, but slowly and from far awayFallback time is too short — the client gives up on the near DP and reaches out
A boundary group is a two-layer map — boundaries into the group, group onto site systems — and both the relationships (which neighbouring group to fall back to) and the fallback timers decide routing. Wrong here means wrong for everyone in that boundary, which is why content problems are a boundary-group check first, a DP check second.
The Decision
Collections Are Queries — and a Careless Query Is a Site-Wide Tax
A collection is the unit of targeting: deployments, maintenance windows and client settings all point at collections, so membership is who gets what. Query-based collections re-evaluate their membership — on a schedule, or continuously if incremental updates are on. The trap is turning incremental updates on across dozens of collections, or writing a query that scans every resource on the estate: the site server then re-evaluates without pause, evaluation load climbs, the console lags and deployments are slow to land. Incremental updates are a finite budget — Microsoft's own guidance caps how many collections should use them — not a default to switch on everywhere.
Collection choiceWhat it costs the site server
Incremental updates on many collectionsNear-constant re-evaluation; load climbs; runs past the documented cap
Scheduled full evaluation, off-hoursCheap and predictable — the right default for most targeting
Query limited to All Systems that scans everythingEvery evaluation touches the whole estate
Query limited to a tight parent collectionEvaluation only ever touches the parent's members
So the three architecture decisions compound into one rule: one primary site unless you have truly outgrown it, boundary groups whose fallback and timers you have actually reasoned about, and collections on scheduled evaluation with incremental reserved for the few that need near-real-time membership. Get them right and the site server stays responsive under load; get them wrong and every deployment inherits the tax — which is what the log map in MECM Site Health & Server Log Map is really diagnosing. And when the hierarchy's whole reason for being — imaging, deep app packaging, on-prem content — has moved to the cloud, the honest exit is the workload-by-workload path Co-management & Cloud Attach lays out, not a big-bang cutover.

🥊 Policy Conflicts — Proving Which One Won Intune • Policy ▶
Concept
Nobody Wins a Conflict
The instinct from Group Policy is that the last writer, or the most restrictive value, wins. That is not how Intune configuration profiles behave. When two profiles set the same setting to different values, the usual outcome is a Conflict state and the setting is not applied at all — the device keeps whatever it had. A few CSP (Configuration Service Provider) areas do resolve to the more restrictive value, but relying on any tie-break is how you end up with a fleet that is neither configuration.
SituationWhat actually happens
Two Intune profiles, same setting, different valuesConflict — the setting is not applied
Two Intune profiles, same setting, same valueApplies cleanly; no conflict
Intune profile vs security baselineStill a conflict — a baseline is just another profile
Intune vs GPO (Group Policy Object) on a co-managed deviceDepends on the workload slider; whichever authority owns it wins
User-targeted vs device-targetedBoth apply to their own scope; a conflict only if the CSP is the same node
The fix is always the same: find the duplicate and delete one. There is no correct way to have two profiles arguing about one setting.

🎯 Assignment Strategy — Users, Devices, Filters & Exclusions Intune • Policy ▶
Concept
Targeting Is Where Policy Goes Wrong
Most "the policy is assigned but not applying" tickets are not policy problems at all — they are targeting problems. Three rules cover nearly all of them.
RuleConsequence
Exclusion always beats inclusion A user in both an included and an excluded group is excluded. Nested groups count. This is the single most common cause.
Scope has to match the setting A device-scoped CSP (Configuration Service Provider) assigned to a user group applies to that user's devices; a user-scoped setting assigned to a device group may never apply at all.
A device with no primary user is invisible to user targeting Kiosks, shared and Autopilot pre-provisioned devices need device-group assignment.
The first rule is the one that explains most mysteries, and it is invisible from the policy's own page. A user in both an included and an excluded group gets nothing, and the exclusion is usually in a group somebody set up for an unrelated reason months earlier. When a policy "is assigned and not applying", enumerate the person's group memberships before reading a single setting.
Choosing

ToolReach for it whenCost

Corporate-owned models change the answer: a COPE (Corporate-Owned, Personally Enabled) device has a real primary user and user targeting works; a COBO (Corporate-Owned, Business Only) or kiosk device does not, and every policy for it must be device-assigned. Four Rings, and the Setting Everyone Forgets
Update rings are a deferral policy, not a deployment. Windows fetches updates itself; the ring decides how long it waits, when it stops waiting, and how much warning the user gets before a reboot happens anyway.

The grace period is the whole user experience. A deadline with no grace period reboots someone mid-meeting, and you will hear about it for a year. The deadline says "you can no longer defer"; the grace period says "and you have this long to pick your moment". Set both, always.

Silently wrong

Silently wrong

There is a fourth actor in the servicing decision besides your deferral, your deadline and the user: Microsoft applies safeguard holds to devices whose hardware, driver or application telemetry matches a known-bad combination for a specific feature update. The device simply is not offered the update. 🔩 Driver Management — Driver Packs, DISM (Deployment Image Servicing and Management) & the Autopilot Dilemma Endpoint • Provisioning ▶
Concept
Imaging Solved Drivers by Owning Them; Modern Provisioning Solved It by Giving Them Away
In a task-sequence world the driver problem is a supply problem you control. You download the vendor's driver pack for a model, import it, and apply it by WMI (Windows Management Instrumentation) query so a Latitude gets Latitude drivers. The build is deterministic because you decided, per model, exactly which versions ship. The cost is a catalogue: every new model is a new pack, every pack needs testing, and the boot image needs its own storage and network drivers or WinPE (Windows Preinstallation Environment) never gets far enough to ask.
Autopilot inverts that. There is no image and no task sequence, so there is nowhere to inject anything — the device arrives with the OEM's factory drivers and takes everything after that from Windows Update. That is genuinely less work, and it is also a control you have handed to someone else: you no longer choose the version, and "we tested that build" stops meaning what it meant. The honest framing is not which is better but which failure you would rather own: a stale pack you forgot to refresh, or a vendor publishing a regression to your fleet on their schedule. 
# What is actually installed — the store, not Device Manager's rendering
Get-WindowsDriver -Online | Where-Object { $_.ProviderName -ne 'Microsoft' } |
  Select-Object OriginalFileName, ProviderName, Date, Version

# Offline servicing: add drivers to a mounted image (or a boot image)
DISM /Image:C:\mount /Add-Driver /Driver:D:\DriverPack\Latitude5450 /Recurse

# Remove a known-bad OEM driver by its published name (oemNN.inf)
pnputil /delete-driver oem42.inf /uninstall /force

Pitfall
Three Driver Failures and the Log Line That Names Each One
PE boots, then nothing. The task sequence never appears, or it appears and cannot reach content. Almost always a boot image missing the model's storage or network driver, and it is architecture-specific — an x64 pack does nothing for the ARM (Advanced RISC Machines) device someone just bought. The fingerprint is in smsts.log: content download failing immediately with no IP (Internet Protocol), or a disk that never enumerates. Fix the boot image, then remember it needs redistributing to every distribution point before it means anything.
The driver applied, and Windows chose a different one anyway. Windows ranks drivers, and a signed generic driver with a newer date can outrank the vendor pack you injected. The fingerprint is Get-WindowsDriver showing your driver present in the store while pnputil /enum-devices shows something else bound to the device. Injection stages a driver, it does not force it — pinning a specific one means blocking the alternative, not adding yours harder.
A driver shipped to the fleet on a Tuesday and took the docks with it. The rollback path for drivers is not the update rollback path: you block the specific update and roll back per device in Device Manager, which is a per-machine action at fleet scale. This is the argument for putting drivers in rings even when you have delegated the versions — a pilot ring that includes one of each model catches the regression while it is still a support ticket rather than a bridge call. The wider mechanics of rings and deadlines are in Windows Update for Business — Rings, Deferrals & Deadlines.
Decide it once, per estate, and write it down: either you own driver versions and accept the catalogue, or you delegate them and accept the drift — with rings and a named exception list for the hardware that genuinely cannot be delegated. The expensive position is the accidental third one, where nobody refreshed the packs and nobody configured the policies, so the fleet is running whatever the last engineer's image happened to contain. That is the same drift the servicing split describes in Feature vs Quality vs Driver Updates.

🔐 BitLocker at Scale — Silent Enablement, Key Escrow & Recovery Endpoint • Security ▶
Concept
The Only Question That Matters Is "Can You Get the Key Back"
Encrypting the fleet is easy; a policy does it in an afternoon. The part that ends careers is a device that has gone into recovery and a recovery key that was never escrowed anywhere. At scale, BitLocker is a key-management problem wearing an encryption costume — design the escrow first, then turn on encryption, never the other way round.
PieceWhat it is
TPM (Trusted Platform Module)The chip that seals the key to a known-good boot state; unlocks transparently at boot
Recovery keyThe 48-digit fallback when the TPM refuses — the thing you must have escrowed
Escrow locationEntra ID for cloud-joined devices, AD (Active Directory) for hybrid; MECM (Microsoft Endpoint Configuration Manager) keeps its own recovery store too
Encryption methodXTS-AES 128 or 256; used space only vs full disk on first encryption
Test the escrow before you encrypt anything, on a real device you are willing to lock out. A policy that encrypts the fleet and silently fails to store keys looks identical to one that works, right up until somebody is standing at a recovery screen — and by then the number of affected machines is the whole estate. Prove you can retrieve a key by identifier, from the console, by somebody on the service desk, before the rollout.
Flow
Silent Enablement, and the Order It Must Happen In
Silent enablement means the user never sees a prompt — the disk encrypts and the key escrows without interaction. It only works if the prerequisites are already true when the policy lands, and the classic failure is a device that reports "encrypted" with a key that reached nowhere.
StepMust be true
1 PrerequisitesTPM present and ready, UEFI (Unified Extensible Firmware Interface), Secure Boot on, no third-party encryption already resident
2 Policy appliesDisk-encryption profile assigned; "allow standard users to enable" set for non-admin devices
3 EncryptKicks off silently; used-space-only is faster on a fresh device
4 EscrowThe one to verify — confirm the key is visible in Entra/AD before you call it done
A device can be encrypted and unrecoverable at the same time. Report on escrowed keys, not on encryption status. The two diverge exactly on the devices you will most need to recover.
Troubleshooting
Why a Device Drops Into Recovery
Recovery is the TPM doing its job — something in the measured boot path changed, so it refused to release the key. Most are benign and self-inflicted, which is why users should never see the recovery screen as a crisis.
TriggerUsually
Firmware/BIOS updateChanged PCRs; expected — suspend BitLocker before flashing firmware

Repeated recovery on one modelA driver or firmware bug — a real fleet issue, not a user one
The last row is the only one that is your problem; the rest are the chip working correctly. One-off recoveries after a firmware update or a boot-order change are expected, and the fix is process — suspend before the update, tell the service desk what to say. Repeated recovery on one hardware model is a fleet defect and needs a driver or firmware investigation, not another key lookup.

ASR Rules — Audit Before You Block, Always
Attack Surface Reduction rules block whole classes of behaviour malware relies on — Office spawning child processes, credential theft from LSASS (Local Security Authority Subsystem Service), script-launched executables. Every ASR rule has an audit mode that logs what it would have blocked; run there first and read the reports, or you will block a line-of-business app on day one.

WarnUser can bypass — a middle ground for rules with legitimate edge cases
Per-rule exclusionsScalpel, not the off switch — exclude the one path, keep the rule
Tamper protection stops malware — and local admins, and your own scripts — from disabling Defender. Leave it on; when it blocks a legitimate change, make that change through policy, which is the supported path through it.
🧑‍💼 Local Admin Rights — Removing Them, and Endpoint Privilege Management Endpoint • Security ▶
Concept
Standing Local Admin Is the Single Biggest Endpoint Risk You Control
A user who is a local administrator turns every phishing click and every malicious installer into a full device compromise, and defeats most of the controls on the rest of this page. Removing standing admin is the highest-leverage endpoint hardening there is — and the reason it survives everywhere is that removing it naively generates a wall of "I can't do my job" tickets. The work is not deleting the right; it is replacing what people legitimately used it for.
Choosing

EPM lets a standard user run a specific, approved action with admin rights while staying a standard user for everything else. The unit of trust moves from the person to the task, which is the whole point.

📉 Reporting on Drift — Finding Devices That Quietly Stopped Complying Endpoint • Compliance ▶
Concept

A non-compliant device is a known problem the system is already acting on. The device that should worry you is the one that stopped checking in — it is not evaluated, so it is neither compliant nor blocked, just invisible. A fleet report that only counts compliant vs non-compliant hides its own blind spot. Report on the third bucket explicitly.

Technique
Trend the Rate, Alert on the Slope
A single day's compliance percentage is noise. What tells you something broke is the change: a five-point drop overnight is almost always a policy edit or a bad update ring, not a hundred users independently misbehaving. Tie a sudden compliance drop to what you changed. The first question on a drift spike is "what deployed in the last 24 hours" — a new baseline, a tightened setting, or an update. Correlating drift with your own change log finds the cause faster than inspecting devices.

🖥️ Shared, Kiosk & Frontline Devices ENDPOINT • Device Classes ▶
The Inversion
Every Assumption in Endpoint Management Is About One Device, One User
Compliance is evaluated per user-device pair, licences are assigned per user, and the wipe path assumes one owner whose data leaves with them. A shared device breaks all four at once — identity, compliance, licensing and the wipe path each assume a one-to-one relationship that a frontline tablet passed between three shifts does not have. Managing shared devices is not a harder version of managing laptops; it is a different configuration where the defaults are actively wrong.
AssumptionHow a shared device breaks it
One user's identity on the deviceMany users, or a generic kiosk identity with no person behind it
Compliance = this user's this deviceWhose compliance? The device has no single owner
Per-user app licensingA device app used by fifty people needs device licensing

Each device pattern needs its own answer: a true kiosk locks to one app and a generic identity, a shared frontline device uses fast sign-in and per-session data clearing, and a hot-desk PC leans on roaming profiles. Picking the pattern first, then configuring to it, is the whole job — the failure is applying the standard laptop baseline and watching it misbehave.
The Decision
Name the Pattern Before You Enrol the First One
The expensive mistake is enrolling a batch of shared tablets as if they were personal devices and discovering the mismatch in production — sign-in friction on a factory floor, licences consumed by a shared identity, one user's session bleeding into the next. The device-management platforms have specific enrolment modes for these, and choosing the right one is a design decision made once, up front.

Device trust still has to hold — Device Trust End to End — Enrolment → Compliance → CA → Access — but it has to hold for a device with no single human behind it, which is the part the standard flow was never built for.
📱 BYOD (Bring Your Own Device) in Practice — What You Can Actually Require ENDPOINT • Device Classes ▶
The Inversion

Security teams reach for full device management by reflex and then hit a wall on personal devices: you cannot enforce disk encryption, wipe the whole phone, or inventory personal apps on hardware the employee owns — legally in many places, and practically everywhere, because people refuse. The honest control surface on a personal device is the corporate application and its data, not the device, and pretending otherwise produces a BYOD policy that legal will not sign and staff will not accept.

☁️ Virtual Desktops — When the Endpoint Is a Session ENDPOINT • Device Classes ▶

When the endpoint is a session on a server rather than a device in a hand, the whole model turns inside out. A non-persistent desktop is rebuilt from a golden image every logon, which means nothing installed at runtime survives — including the very agents that usually do the managing. The pattern is universal: a Windows feature update, a browser migration or a hardware refresh is held hostage by a single business-critical application that only runs on the old thing — an ancient line-of-business tool, a vendor app abandoned by its maker, a macro-laden spreadsheet someone built in 2009. 🔎 Lost, Stolen & Returning Devices ENDPOINT • Operations ▶
The Decision

When a laptop is reported missing, the panic question is “what was on it?” — and if the answer depends on encryption and remote wipe that were configured after the loss, it is too late. A lost encrypted device with a strong pre-boot secret is a hardware loss; a lost unencrypted one is a data breach, and which of the two you are holding was decided at enrolment. The lost-device runbook is short only because the hard work was done in advance.

The Fingerprint
The Device That Comes Back Six Months Later, Still Enrolled
The forgotten half of the lifecycle is return. A device written off as lost reappears — found in a drawer, returned by a leaver, recovered by police — and it is still enrolled, still trusted, and possibly still holding cached credentials for accounts that were never rotated. A returning device is not automatically safe just because it is back in the building.
Treat a returned device as untrusted until wiped and re-enrolled, and make “lost” a state with a proper close-out — licence released, object cleaned up, credentials rotated — not an open ticket that lingers. The device found in a drawer a year later is the one nobody remembered still had a valid certificate on it.

The action arm is Proactive Remediations — a pair of PowerShell scripts deployed to a device group on a schedule. A detection script checks for a known-bad state and signals with its exit code; the remediation script runs only when detection says something is wrong, and fixes it. It is cron-for-the-fleet with a condition: look for the stopped service, the stale certificate, the drifted setting — and self-heal it, reporting how many devices were found and how many were fixed. The hazard is scale: a remediation with a bug does not break one device, it breaks every device it targets, so it is a change like any other and belongs on a pilot ring first.

The Decision
Analytics Says Where It Hurts; Remediations Stop the Recurring Ache — Neither Is Root Cause
The trap is treating remediations as a dumping ground for band-aids — a growing pile of scripts papering over problems that a policy or an image should solve properly. If every device from one build has the same failing service, that is an image or baseline bug, and scripting round it forever only hides it. Use analytics to find the systemic issue, fix it at the source, and reserve remediations for genuine per-device drift that has no upstream fix.
So before you script a fix, ask whether the thing you are fixing should exist at all: if every device needs the same repair, it is a policy or image defect, not a remediation. Analytics ranks the pain, remediations handle the residue, and the cause is handled upstream — in the image from Windows Autopilot — Zero-Touch Provisioning and the configuration and compliance policies of Microsoft Intune — Cloud MDM & MAM.

The Inversion
Two Ways to Put the Desktop in Azure: Fixed-Price Simplicity vs Pooled-Density Control
When the endpoint becomes a session in Azure there are two Microsoft answers, and they are not interchangeable. Windows 365 gives each user a dedicated Cloud PC — a persistent, single-user Windows machine, billed a fixed monthly price per user, provisioned and managed like any other Intune device. Azure Virtual Desktop (AVD) is the platform underneath: a pooled, multi-session host farm you size and run yourself, billed on Azure consumption, capable of packing many users onto each host. One is a product you assign; the other is infrastructure you operate.

The Fingerprint
It Is Still an Endpoint You Manage — the Estate Does Not Shrink, It Moves
The seductive error is thinking a cloud desktop is one less thing to manage. It is not: a Cloud PC is a full Windows device that still needs Intune policy, compliance, patching, Defender, Conditional Access and identity, exactly like a physical one. What changes is where it runs and how it is provisioned; what stays is the entire management burden — and AVD adds to it (host pools, gold images, FSLogix profile containers, session-host autoscale), it does not subtract. Both live or die on identity and the network path: a Cloud PC behind a broken Conditional Access grant, or a slow route to on-prem resources, is a user with no working computer at all.

The Decision
Choose by Who Operates It, and How Predictable the Need Is
The choice is organisational as much as technical. Want per-user desktops with the least effort and a predictable bill — knowledge workers, contractors, turning BYOD (Bring Your Own Device) into managed — and Windows 365 is the answer: assign a licence, manage it like any Intune device. Need to squeeze cost through multi-session density, run specialist or GPU (Graphics Processing Unit) images, or absorb spiky seasonal scale, and you have the platform skills to operate a host farm — and AVD is the answer. Plenty of estates run both: Windows 365 for the steady per-user population, AVD for the pooled call-centre or the GPU workload.
Ask two things: do these users need a dedicated machine or will pooled sessions do, and do we want to operate a desktop platform or consume one? Pooled and willing-to-operate points to AVD's density and control; dedicated and wanting-simplicity points to Windows 365's fixed price.
