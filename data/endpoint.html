🏢 Microsoft Endpoint Configuration Manager (MECM) On-Prem ▶
Reference
ConfigMgr / SCCM (System Center Configuration Manager) — What It Is & Where It Fits
MECM (formerly SCCM, universally called ConfigMgr) is Microsoft's on-premises platform for managing Windows (and some Linux/macOS/servers) at scale: application deployment, patching, OS (Operating System) imaging, hardware/software inventory, and compliance. It ships in the Current Branch model — a new feature release roughly three times a year (e.g. 2403 = 2024, March), applied in-console.
StrengthWhy it still matters
Deep OS deploymentFull bare-metal imaging & task sequences Intune can't match
Bandwidth controlOn-prem DPs, peer caching for large/branch fleets
Granular software dist.Complex app models, supersedence, dependencies
Mature reportingSQL (Structured Query Language) Reporting Services, rich inventory
The direction of travel is cloud: most orgs now run co-management (ConfigMgr + Intune on the same device) and move workloads to Intune over time. ConfigMgr isn't dead — it's the on-prem anchor of a hybrid estate (see the Co-management card).
Architecture
Sites, the Database & Site System Roles
A ConfigMgr deployment is a hierarchy of sites, each identified by a 3-character site code (e.g. P01). Most orgs need only a single standalone primary site; very large or multi-geo estates add a CAS and/or secondary sites.
Site typePurpose
CAS (Central Admin Site)Top of a multi-primary hierarchy — reporting/admin only, no clients
Primary siteManages clients; holds the site database
Secondary siteControls content/upstream traffic for a remote location
Site system roleJob
Site database (SQL)Everything — config, inventory, status
SMS (Systems Management Server) ProviderWMI (Windows Management Instrumentation) layer the console talks through
Management Point (MP)Primary client ↔ site channel (policy, inventory)
Distribution Point (DP)Hosts & serves content
Software Update Point (SUP)Sits on WSUS (Windows Server Update Services); drives patching
Cloud Management Gateway (CMG)Manage internet-based clients via Azure (no VPN)
Reporting Services PointSSRS reports
Fallback Status Point (FSP)Collects client install/health state
The Client
Agent Install, Settings & Health
The ConfigMgr client (ccmsetup.exe → CcmExec service) runs policy, inventory, and deployments. It can be installed several ways; client behavior is governed by Client Settings (default + prioritized custom sets assigned to collections).
Install methodNotes
Client pushSite pushes to discovered devices (needs push account + firewall)
GPO (Group Policy Object) / logon scriptClassic mass deployment
Software update-basedClient delivered as an "update" via WSUS
Intune / co-mgmt (ccmsetup)Push the client as a Win32 app during Autopilot
Control Panel → Configuration Manager exposes actions like Machine Policy Retrieval, Hardware Inventory Cycle, and Software Updates Scan — the buttons you press when "it's not showing up yet." Client health is monitored by the built-in ccmeval scheduled task, which auto-remediates a broken client.
Content & Targeting
Boundaries, Boundary Groups & Distribution
Clients find their nearest servers via boundaries (IP subnet, AD site, IPv6 prefix, or IP range) grouped into boundary groups, which map to the MPs/DPs/SUPs a client should use — with fallback relationships and time delays.
ConceptDetail
Content librarySingle-instance store of all distributed content on a DP
Pull DPA DP that pulls content from another DP (scale-out)
Peer CacheClients serve content to peers on the same subnet
BranchCache / Delivery OptimizationPeer-to-peer to cut WAN (Wide Area Network) usage
Prestaged contentShip content on disk to a slow-link DP
#1 support ticket: "content won't download." Almost always a missing/overlapping boundary, content not distributed to the client's DP, or a boundary group with no fallback. Check LocationServices.log and ContentTransferManager.log.
Deploying Things
Applications, Updates & OS Deployment
Everything targets a collection (device or user; direct or query/WQL membership). The three big deployment workloads:
WorkloadKey pieces
ApplicationsDeployment types + detection method + requirement rules + supersedence; purpose Available (Software Center) or Required (enforced by deadline)
Software UpdatesSUP scan → deploy manually or via ADR (Automatic Deployment Rule) that grabs each Patch Tuesday into a deployment package
OS Deployment (OSD)Task sequence: boot image (WinPE) → partition → apply WIM (Windows Imaging Format) → drivers → join (AD/Entra) → apps
Detection method is the make-or-break of app deployment: it's how ConfigMgr decides "already installed?" (file version, registry, MSI product code, or script). Wrong detection = endless reinstall or false failure. Maintenance windows on a collection limit when Required installs/reboots may run — critical for servers.

🪪 Azure AD (Active Directory) / Microsoft Entra ID — Endpoint Identity Identity ▶
Concept
The Identity Layer Everything Sits On
Microsoft Entra ID (formerly Azure AD) is the cloud directory behind Microsoft 365 and Intune. Every managed device gets a device object in Entra; how it obtains that identity (its join type) determines which management, SSO (Single Sign-On), and Conditional Access experiences are possible.
Join typeHow & when
Entra JoinedCloud-only. Set during OOBE/Autopilot or Settings. The modern default for corporate Windows
Entra Hybrid JoinedDomain-joined and synced to Entra (needs Entra Connect + SCP). For orgs still reliant on on-prem AD/GPO/apps
Entra RegisteredBYOD/personal — a work identity is added but the org doesn't own the device (Workplace Join)
Hybrid is heavier & more fragile (sync timing, SCP, network line-of-sight to a DC for the join). Microsoft's clear guidance: go cloud-native (Entra Joined) unless a hard dependency forces hybrid.
Internals
dsregcmd, the PRT (Primary Refresh Token) & Windows Hello for Business
The device's join/registration state is the first thing to check when SSO or enrollment misbehaves. dsregcmd /status is the definitive local tool. 
# Show device join & SSO state (run as the signed-in user)
dsregcmd /status
# Key fields:
#   AzureAdJoined : YES        -> Entra Joined
#   DomainJoined  : YES        -> (also) on-prem = Hybrid
#   AzureAdPrt    : YES        -> Primary Refresh Token present (SSO works)
#   MdmUrl / MdmEnrollmentUrl  -> auto-enrollment configured
TermMeaning

Windows Hello for BusinessPasswordless (PIN/biometric) bound to the device via asymmetric keys
Device objectThe Entra record CA & Intune reason about (compliant? managed? join type?)
Reference
MDM (Mobile Device Management) Authority & Automatic Enrollment
Entra is where devices are told to enroll. Under Entra → Mobility (MDM and MAM) → Microsoft Intune you set the MDM user scope (which users' devices auto-enroll on Entra join) and the MAM (Mobile Application Management) scope.
SettingEffect

MAM user scopeApp-level (MAM) enrollment for BYOD (Bring Your Own Device) without full MDM
Dynamic device groupsMembership by rule (OS, ownership, enrollment profile) → drives targeting everywhere
Device categoriesAuto-place devices into groups at enrollment
Licensing gotcha: auto-enrollment and many CA features require the right licenses (Intune + Entra ID P1/P2, usually via M365 E3/E5). No license = "your device can't be enrolled" errors.

✈️ Windows Autopilot — Zero-Touch Provisioning Provisioning ▶
Concept
Ship a Sealed OEM Laptop Straight to the User
Windows Autopilot customizes the out-of-box experience (OOBE) so a factory device configures itself for your org — no imaging, no touching it in IT. The device's hardware identity is pre-registered to your tenant; at first boot it recognizes itself, Entra-joins, enrolls in Intune, and applies your apps/policies through the ESP (Enrollment Status Page).
Deployment modeUse case & behavior
User-drivenUser signs in during OOBE → device joins Entra as theirs. The standard mode
Pre-provisioning (White Glove)IT/OEM/partner runs the device phase first (apps, policies), reseals; user gets a short finish
Self-deployingNo user creds — kiosks, digital signage, shared/lab (requires TPM 2.0)
Existing devicesRe-provision an in-place PC via a ConfigMgr task sequence into Autopilot
Autopilot ResetWipe user data/apps but keep Entra join & enrollment — hand-off/refresh
Registration
Hardware Hash, Group Tags & Who Uploads It
A device becomes "an Autopilot device" when its hardware hash (a ~4KB device fingerprint) is uploaded to your tenant. Registration source matters for scale. 
# Capture the hash locally and register the device online
Install-Script Get-WindowsAutopilotInfo -Force
Get-WindowsAutopilotInfo -Online -GroupTag "Kiosk"
# -Online prompts Entra sign-in and uploads; -GroupTag stamps a
# tag used by dynamic groups to auto-assign a deployment profile.
Registration pathWhen
OEM / reseller (CSP)Best — vendor registers at purchase; you never touch it
Manual PowerShellExisting stock / pilots
ConfigMgr / Intune diagnosticsHarvest hashes from managed devices
Group Tag (a.k.a. OrderID) is the trick for targeting: a dynamic group with rule device.devicePhysicalIds -any (_ -eq "[OrderID]:Kiosk") auto-collects tagged devices and assigns the right profile.
Flow
Deployment Profile & the OOBE Sequence
A deployment profile (assigned to the device's group) defines the join type and OOBE behavior; the ESP then gates the desktop.
Profile settingControls

OOBE togglesHide EULA/privacy, hide account-change, user account type (Std/Admin)

Sequence: power on → network → OOBE fetches the Autopilot profile → branded Entra sign-in → Entra join → auto MDM (Mobile Device Management) enroll → ESP installs device- & user-targeted content → desktop. Requires internet + a supported Windows edition (Pro/Enterprise/Edu).

⏳ Enrollment Status Page (ESP) Provisioning ▶
Concept
The Gate That Makes a Device Ready on Day One
The Enrollment Status Page is the full-screen progress screen during Autopilot/enrollment. Its purpose is to withhold the desktop until the device is genuinely ready — required apps installed, policies applied, certs delivered — so nobody lands on a half-configured machine and starts working before security settings arrive.
PhaseRunsTracks
Device preparationPre-sign-inTPM (Trusted Platform Module) attestation (self-deploy), Entra join, Intune enrollment
Device setupPre-sign-inDevice-targeted apps, policies, certificates, security
Account setupAfter user signs inUser-targeted apps & policies
Configured under Intune → Devices → Enrollment → Enrollment Status Page: a Default profile plus higher-priority profiles assigned to groups.
Settings
Every Knob and What It Does
SettingEffect
Show app/profile install progressMaster switch — turns the ESP on for the group
Block device use until all apps & profiles installHard gate — no desktop until success
Selected blocking appsExplicit list that must succeed before release
Show error when time exceeds (timeout)Default 60 min — raise for big app sets/slow links
Allow reset on failureUser can wipe & retry
Allow use of device on failureContinue to desktop if non-blocking items fail
Block until required apps installed if assignedChoose "all" vs a chosen subset
Allow log collection on failureUser can export diagnostics
Custom messagesBranded text at each phase
Reference
What Counts, Timeouts & Troubleshooting
ESP tracks only Required-assigned apps/policies that target the device/user in scope — Available apps are ignored. In the device phase it can only track device-targeted items (user isn't known yet), which is why heavy user-targeted apps belong in the account phase or pre-provisioning.
PitfallFix
Too many/large blocking apps → timeoutKeep blocking set minimal; raise timeout; use pre-provisioning
Wrong detection rule → waits foreverFix the app's detection method (it already installed)
User-targeted app tracked in device phaseAssign to devices, or move to account phase
Win32 app depends on another → orderModel dependencies so prerequisites finish first
Best practice: block only what a user truly needs on day one (security agent, VPN, core LOB app); set a realistic timeout; and front-load device-targeted apps via pre-provisioning so the end-user wait is minutes, not an hour. Logs: Event Viewer → DeviceManagement-Enterprise-Diagnostics-Provider and the Autopilot diagnostics page.

🛂 Conditional Access & Device Compliance Zero Trust ▶
Concept
Tie Access to Device Health — the Zero-Trust Loop
The payoff of managing endpoints is being able to say "only healthy, managed devices reach corporate data." Conditional Access (Entra) is the policy engine; Intune compliance is the health signal it consumes. 
# The loop, end to end
Intune compliance policy  ──▶  device evaluated (encryption? Defender? min OS?)
        │                              │ writes result to…
        ▼                              ▼
Entra device object (compliant: true/false)
        │
        ▼
Conditional Access reads it  ──▶  Grant (compliant OR Entra-joined) / Block / require MFA
Reference
Building a CA Policy
A CA policy is if [assignments] then [controls]. Assignments = who + what they're accessing + conditions; controls = grant/block requirements.
PartExamples
Users/groupsAll users, exclude break-glass admins
Target resourcesOffice 365, a specific app, all cloud apps
ConditionsDevice platform, location, client app, sign-in risk (P2)
Grant controlsRequire MFA (Multi-Factor Authentication), require compliant device, require Entra hybrid join, require app protection policy
Session controlsApp-enforced restrictions, sign-in frequency
Always keep a break-glass account excluded from CA (a CA misconfig can lock everyone — including you — out). Use report-only mode to preview impact before enforcing. Filters for devices let you scope by attributes (e.g. exclude kiosks). This is the concrete implementation of Zero Trust for endpoints.

📖 Glossary — Acronyms, Logs & Task-Sequence Variables Reference ▶
Reference
Acronyms & Components You'll Keep Meeting
The alphabet soup of Microsoft endpoint management, decoded — the pieces that show up constantly in ConfigMgr/Intune/Autopilot work.
TermMeaning
WMIWindows Management Instrumentation — the local management data layer. ConfigMgr's console talks to the site through the SMS (Systems Management Server) Provider over WMI; the client stores state & inventory in the root\ccm and root\cimv2 namespaces (query with wbemtest / Get-CimInstance)

Reference
Key Log Files (open with CMTrace)
ConfigMgr troubleshooting is log reading. Client logs live in C:\Windows\CCM\Logs; during OSD they start in X:\Windows\Temp\SMSTSLog (WinPE) and move to C:\_SMSTaskSequence\Logs then C:\Windows\CCM\Logs.
LogTells you
smsts.logThe task sequence engine — every OSD step, variable, and failure. The single most important OSD log
CAS.logContent Access Service — how the client locates content and whether it's already in the cache (cache hits/misses, requesting a DP list)
ContentTransferManager.logSchedules and tracks the actual content download jobs (via BITS or SMB) from a distribution point
DataTransferService.logThe BITS (Background Intelligent Transfer Service) transfer layer used for policy and content downloads — TLS/proxy/BITS errors surface here
Content-download triage order: CAS.log (is it cached / which DPs?) → ContentTransferManager.log (did a job start?) → DataTransferService.log (did BITS actually move the bytes?). During OSD, cross-reference all of it against smsts.log.
Reference
OSD Task-Sequence Variables Worth Knowing
Task-sequence variables tune how OSD downloads, caches, and stores content. Set them on a collection, in the deployment, or with a Set Task Sequence Variable step. TRUE/FALSE values are strings.
VariableWhat it does
SMSTSPreserveContentKeeps the TS's downloaded content in the ConfigMgr client cache (ccmcache) after the sequence finishes, instead of purging it — handy when the same content is needed again soon (TRUE)
SMSTSPersistContentPersists content in the task-sequence working cache (_SMSTaskSequence) for the duration of the sequence, so it survives reboots between steps
SMSTSDownloadRetryCountHow many times the client retries a failed content download (default 2) — raise it on flaky/slow links
SMSTSDownloadRetryDelaySeconds to wait between download retries (default 15) — pair with the count above for unreliable networks
SMSTSLocalDataDriveChooses the drive where the TS stores its temp working files & logs (the _SMSTaskSequence folder) — set it before content downloads to avoid X:\ (RAM) space issues in WinPE (Windows Preinstallation Environment)
SMSTSPeerDownloadEnables/allows the TS to pull content from peers (Windows PE Peer Cache / peer sources) rather than a DP — TRUE/FALSE
SMSTSDownloadProgramSpecifies an Alternate Content Provider (ACP) — a custom download program (e.g. third-party peer-to-peer like Nomad/Adaptiva) used instead of the built-in downloader
Common combos: on slow branch links, raise SMSTSDownloadRetryCount/Delay, set SMSTSLocalDataDrive=C early, and enable SMSTSPeerDownload so peers share content. Use SMSTSPreserveContent when a later phase (or a re-image retry) reuses the same packages. Verify all of it in smsts.log.

📦 MECM (Microsoft Endpoint Configuration Manager) Deployment & Content Troubleshooting MECM • Troubleshooting ▶
Flow
Follow the Package Server-Side, Then Client-Side
An application reaches a device through a fixed chain: it is distributed to a distribution point, advertised in policy, located by the client, downloaded, then enforced. Find the first link that failed and stop reading logs from the wrong end.
StageWhereLog
Content sent to the DPSite serverdistmgr.log then PkgXferMgr.log
Content verified on the DPDistribution pointsmsdpmon.log, smsdpprov.log
Policy reaches the clientClientPolicyAgent.log, AppIntentEval.log
Client finds a sourceClientCAS.log — cached? which DP?
Bytes actually moveClientContentTransferManager.log, DataTransferService.log
Install runsClientAppEnforce.log (apps), execmgr.log (packages)
Result detectedClientAppDiscovery.log — the detection method's verdict
The single most common false failure: the installer ran fine, but the detection method looks for the wrong file, version or registry key — so MECM reports failure and retries forever. AppEnforce.log shows exit code 0 while AppDiscovery.log says "not detected". That combination always means the detection rule, never the installer.

Software Updates
When Patching Stops, Suspect WSUS (Windows Server Update Services) First
Software updates run on the software update point, which is WSUS wearing a MECM hat. Scan failures are almost always the WSUS side: a bloated database, an exhausted app pool, or a proxy in the way.

0x80244010 — "exceeded max server round trips" — is the classic sign of an unmaintained WSUS: decline superseded updates and run the cleanup so the client can finish enumerating. 0x80072ee2 is a timeout, usually a proxy or firewall. And if the WSUS app pool keeps recycling, raise its private memory limit (0 = unlimited) before touching anything else.

Method
Find smsts.log, Then Read Backwards
Every task sequence failure is in smsts.log. The hard part is knowing where it lives at the moment it failed — the file moves as the sequence progresses. Open it in CMTrace, jump to the end, and scroll up to the first red line: the error you see reported is usually the consequence, not the cause.
Phasesmsts.log lives at
In WinPE (Windows Preinstallation Environment), before the disk is formattedX:\Windows\Temp\SMSTSLog\smsts.log
In WinPE, after formattingX:\SMSTSLog\smsts.log then C:\_SMSTaskSequence\Logs
In the full OS (Operating System), before the client is installedC:\_SMSTaskSequence\Logs\SMSTSLog
In the full OS, client installedC:\Windows\CCM\Logs\SMSTSLog
After the sequence endsC:\Windows\CCM\Logs\smsts.log

Real Time
CMPivot (Configuration Manager Pivot) — Ask the Fleet Instead of Waiting for Inventory
Hardware inventory is a scheduled snapshot; CMPivot queries live clients now, in a KQL-like syntax. It is the fastest way to answer "how many machines actually have this" during an incident — and it doubles as a hunting tool alongside the Blue Team domain. 
// Which machines still have the vulnerable version installed?
InstalledSoftware
| where ProductName contains 'Contoso Agent'
| summarize count() by ProductVersion

// Is the file present, and when was it last written?
File('C:\\Program Files\\Contoso\\agent.exe')
| project Device, Version, LastWriteTime

// Disk pressure across the fleet, worst first
LogicalDisk
| where DeviceID == 'C:'
| project Device, FreeGB = FreeSpace / 1024
| order by FreeGB asc
Two limits to keep in mind: CMPivot only reaches clients that are online and healthy — the broken ones you most want to see are exactly the ones that will not answer — and results are capped, so scope the query to a collection rather than the whole estate.
