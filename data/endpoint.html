🏢 Microsoft Endpoint Configuration Manager (MECM) On-Prem ▶
Reference
ConfigMgr / SCCM — The On-Prem Management Workhorse
MECM (formerly SCCM, still called ConfigMgr) is Microsoft's on-premises platform for managing Windows at scale — software deployment, patching, OS imaging, inventory, and compliance across thousands of devices. It's the traditional half of the modern co-management story (the cloud half is Intune).
ComponentRole
Site server & site codeThe brain of a site (3-letter code, e.g. P01); stores config & runs the SMS Provider
HierarchyCAS (Central Admin Site) → Primary → Secondary sites for scale/geography
ConfigMgr clientAgent on each device that runs policy, inventory & deployments
Management Point (MP)Client ↔ site communication endpoint
Distribution Point (DP)Hosts content (apps, updates, images) close to clients
SUP (WSUS)Software Update Point — drives patching
Boundaries & boundary groups: define client locations (IP subnet, AD site, IP range) and map them to the DPs/MPs they should use — misconfigured boundaries are the #1 cause of "content not downloading."
How It Works
Collections, Deployments & Task Sequences
Everything in ConfigMgr targets a collection — a grouping of devices or users. Collections can be direct (hand-picked) or query-based (dynamic membership via WQL, e.g. "all Windows 11 laptops").
CapabilityDetail
ApplicationsDetection method + install/uninstall; Available (Software Center) or Required (forced)
Software UpdatesADRs (Automatic Deployment Rules) auto-approve & deploy Patch Tuesday updates
OSD / Task SequencesOS deployment: partition → apply image (WIM) → drivers → apps → domain/Entra join
Compliance settingsConfiguration baselines & items — audit/remediate settings
InventoryHardware & software inventory, Asset Intelligence
Software CenterThe end-user portal for optional installs
Co-management lets ConfigMgr and Intune manage the same device at once — you move workloads (compliance, updates, apps, endpoint protection) from ConfigMgr to Intune slider-by-slider. This is the bridge from on-prem to cloud and the modern migration path.
🪪 Azure AD / Microsoft Entra ID — Endpoint Identity Identity ▶
Concept
The Identity Foundation Everything Else Sits On
Microsoft Entra ID (formerly Azure AD) is the cloud identity/directory behind Microsoft 365 and Intune. Every modern-managed device has a device identity in Entra, and how it gets that identity (join type) determines what management and sign-in experiences are possible.
Join typeWhat it means
Entra JoinedCloud-only join — sign in with Entra account; the modern default (Autopilot uses this)
Entra Hybrid JoinedJoined to both on-prem AD and Entra (needs Entra Connect sync) — for orgs still tied to on-prem AD/GPO
Entra RegisteredPersonal/BYOD device with a work identity added (not fully "owned" by the org)
Rule of thumb: greenfield/cloud-first → Entra Joined; still dependent on Group Policy or on-prem apps → Hybrid Joined (but it's more fragile — sync timing, SCP config). Microsoft's guidance is to go cloud-native (Entra Joined) wherever possible.
Reference
MDM Authority, Conditional Access & the PRT
Entra is where you set the MDM authority (Intune), configure automatic enrollment, and enforce access with Conditional Access.
FeatureDetail
MDM auto-enrollmentEntra setting: devices auto-enroll into Intune on join (scoped by group)
Conditional Access (CA)"Only compliant / Entra-joined devices can reach email" — ties device state to access
Primary Refresh Token (PRT)The token that gives Windows SSO to M365 apps after sign-in
Device compliance signalIntune tells Entra a device is compliant → CA allows access
Groups (dynamic)Membership by rule (e.g. device OS, department) — drive targeting everywhere
The loop that matters: Intune evaluates compliance → writes the result to the device's Entra identity → Conditional Access reads it → grants or blocks access to corporate resources. Identity + compliance + CA is the heart of Zero Trust for endpoints.
☁️ Microsoft Intune — Cloud MDM & MAM Cloud MDM ▶
Reference
Manage Devices & Apps From the Cloud
Microsoft Intune (part of Microsoft Intune Suite / the Intune admin center, intune.microsoft.com) is the cloud service that manages devices (MDM) and apps (MAM) across Windows, macOS, iOS/iPadOS, Android, and Linux — no on-prem infrastructure required.
Policy typeDoes
Compliance policiesDefine "healthy" (encryption on, min OS, defender on) → feeds Conditional Access
Configuration profilesSettings Catalog, ADMX-backed (GPO-equivalent), templates, custom OMA-URI
AppsWin32 (.intunewin), MSI/LOB, Microsoft Store, web links, iOS/Android store apps
App Protection Policies (APP/MAM)Protect corporate data inside apps on unmanaged/BYOD devices (no full enrollment)
Endpoint securityDefender AV, ASR rules, disk encryption (BitLocker/FileVault), firewall
Update ringsWindows Update for Business — phased deferrals & deadlines
How It Works
Enrollment, Targeting & Win32 Packaging
Policies and apps are assigned to Entra groups (user- or device-based), with optional filters (e.g. only Windows 11) and scope tags for delegated (RBAC) administration.

✈️ Windows Autopilot — Zero-Touch Provisioning Provisioning ▶
Concept
Ship a Sealed Laptop Straight to the User
Windows Autopilot turns the out-of-box experience (OOBE) into a self-configuring, corporate setup — no imaging. The device's hardware identity is pre-registered to your tenant, so when the user signs in, it automatically Entra-joins and enrolls in Intune, then applies your apps and policies.
Deployment modeUse case
User-drivenStandard — user signs in, device joins Entra & sets up as theirs
Pre-provisioning (White Glove)IT/partner runs the device phase first; user gets a fast finish
Self-deployingNo user credentials — kiosks, digital signage, shared/lab PCs
Autopilot for existing devicesWipe & re-provision an existing PC via a ConfigMgr task sequence
Autopilot ResetReturn a device to a business-ready state, keeping enrollment
How It Works
Hardware Hash, Profiles & the OOBE Flow
Registration is by hardware hash (a unique device fingerprint). OEMs/CSPs can register at purchase, or you capture it yourself. 
# Capture the hardware hash on a device and upload to Autopilot
Install-Script -Name Get-WindowsAutopilotInfo -Force
Get-WindowsAutopilotInfo -Online   # prompts Entra sign-in, registers the device
StepWhat happens
1. RegisterHardware hash uploaded → device appears under Autopilot devices
2. Assign profileDeployment profile (join type, OOBE settings) assigned via group
3. OOBEDevice boots, hits network, recognizes itself, shows branded sign-in
4. Entra join + enrollJoins Entra, enrolls in Intune automatically
5. ESPEnrollment Status Page tracks apps/policies before desktop (next card)
Profile settings control the experience: skip privacy/EULA, hide account-change options, set the join type, and give the device a naming template. Pre-provisioning front-loads the heavy device-targeted apps so the end user's wait is short.
⏳ Enrollment Status Page (ESP) Provisioning ▶
Concept
The Gate That Makes a Device Ready Before First Use
The Enrollment Status Page is the full-screen progress screen shown during Autopilot/enrollment. Its job is to block access to the desktop until the device is genuinely ready — required apps installed, policies applied, certs delivered — so users don't land on a half-configured machine.
PhaseTracks
Device preparationEntra join, Intune enrollment (before any user signs in)
Device setupDevice-targeted apps, policies, certificates, security
Account setupUser-targeted apps & policies after sign-in
ESP is configured under Enrollment → Enrollment Status Page in Intune, assigned to groups (default profile + targeted profiles).
Reference
Key Settings & Troubleshooting
SettingEffect
Show app/profile install progressTurns the ESP on for that group
Block device use until all apps installedHard gate — desktop is withheld until success
Blocking appsExplicit list that must succeed (choose critical ones only)
Timeout (default 60 min)How long before it fails/allows — tune for large app sets
Allow reset on failureLet the user retry/reset instead of being stuck
Allow use on failureLet the user continue to the desktop if non-blocking items fail
Collect logsLet users export diagnostics on error
Common pitfalls: too many blocking apps or a large Win32 app makes ESP hit the timeout and fail; a wrong app detection rule makes ESP wait forever on an install that already succeeded. Best practice: keep the blocking set minimal (only what a user truly needs on day one), raise the timeout for heavy images, and use pre-provisioning so device-phase apps finish before the user ever sees the account phase.
