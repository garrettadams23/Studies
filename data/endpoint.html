🏢 Microsoft Endpoint Configuration Manager (MECM) On-Prem ▶
Reference
ConfigMgr / SCCM (System Center Configuration Manager) — What It Is & Where It Fits
MECM (formerly SCCM, universally called ConfigMgr) is Microsoft's on-premises platform for managing Windows (and some Linux/macOS/servers) at scale: application deployment, patching, OS (Operating System) imaging, hardware/software inventory, and compliance. It ships in the Current Branch model — a new feature release roughly three times a year (e.g. 2403 = 2024, March), applied in-console.

The direction of travel is cloud: most orgs now run co-management (ConfigMgr + Intune on the same device) and move workloads to Intune over time. ConfigMgr isn't dead — it's the on-prem anchor of a hybrid estate (see the Co-management card).

🪪 Azure AD (Active Directory) / Microsoft Entra ID — Endpoint Identity Identity ▶
Concept
The Identity Layer Everything Sits On
Microsoft Entra ID (formerly Azure AD) is the cloud directory behind Microsoft 365 and Intune. Every managed device gets a device object in Entra; how it obtains that identity (its join type) determines which management, SSO (Single Sign-On), and Conditional Access experiences are possible.
Join typeHow & when
Entra JoinedCloud-only. Set during OOBE/Autopilot or Settings. The modern default for corporate Windows

✈️ Windows Autopilot — Zero-Touch Provisioning Provisioning ▶
Concept
Ship a Sealed OEM Laptop Straight to the User
Windows Autopilot customizes the out-of-box experience (OOBE) so a factory device configures itself for your org — no imaging, no touching it in IT. The device's hardware identity is pre-registered to your tenant; at first boot it recognizes itself, Entra-joins, enrolls in Intune, and applies your apps/policies through the ESP (Enrollment Status Page).

The ticket this answers is setting up a new laptop, and the point of Autopilot is that nobody sets one up. The work moves off the bench and into a profile written once, so the marginal cost of the hundredth device is the same as the second — which is also the honest warning: a profile that is wrong is wrong on every machine at once, and there is no technician in the loop to notice.
Deployment modeUse case & behavior
User-drivenUser signs in during OOBE → device joins Entra as theirs. The standard mode
Pre-provisioning (White Glove)IT/OEM/partner runs the device phase first (apps, policies), reseals; user gets a short finish
Self-deployingNo user creds — kiosks, digital signage, shared/lab (requires TPM 2.0)
Existing devicesRe-provision an in-place PC via a ConfigMgr task sequence into Autopilot
Autopilot ResetWipe user data/apps but keep Entra join & enrollment — hand-off/refresh
Pre-provisioning is the mode that makes the promise deliverable on a real network. User- driven is the demonstration everybody sees and it puts the entire application install in front of somebody waiting at a kitchen table on domestic broadband — which is where the good impression is lost. Do the device phase in advance where you can, and keep the reset row in mind: it is the cheapest way to hand a machine to the next person.

🚀 Autopilot Device Preparation — The Newer Flow That Deletes the Hardware Hash Intune • Provisioning ▶
The Inversion
The Hardware Hash Was the Bottleneck. Device Preparation Removes It Entirely.
Classic Autopilot's whole model rests on pre-registering each device's ~4 KB hardware hash to the tenant before it can provision — and that registration is the fragile, slow part: it depends on the OEM or reseller doing it, or on you harvesting hashes, and an unregistered device simply falls through to a plain out-of-box experience. Autopilot device preparation — the newer flow — removes the pre-registration altogether. The device is no longer identified by a hash uploaded in advance; instead the user signs in, the device is placed into a security group you nominate, and a device-preparation policy targeted at that group provisions it. The single most brittle dependency in classic Autopilot — get the hash in first — is gone.
AspectClassic AutopilotDevice Preparation
Device identityPre-uploaded hardware hashUser sign-in + a nominated security group — no hash
Registration stepOEM / reseller / manual harvest — fragile at scaleNone required
What provisions itDeployment profile via a dynamic group on a group tagA device-preparation policy assigned directly to a user group
Unregistered deviceDrops to a normal OOBE (Out-of-Box Experience) with no brandingNot a failure mode — there is nothing to pre-register
The unit that actually changed is device identity: hash-first becomes user-and-group-first, which deletes the dependency that generated most “Autopilot didn't trigger” tickets in the first place.
The Fingerprint
Simpler, But Not a Drop-In Replacement — It Is a Narrower Model
Device preparation is not classic Autopilot with the hash removed; it is a different, deliberately narrower model. It is Entra join only — no hybrid Entra join — it provisions a defined set of apps and scripts from the policy rather than gating on the full Enrollment Status Page app catalog, and it targets a security group directly. So the way to tell which tool a scenario needs is to ask what it requires: hybrid join, white-glove pre-provisioning or self-deploying kiosks still belong to classic Autopilot; cloud-native user-driven provisioning where the hash was the pain belongs to device preparation.
What the scenario needsWhich flow answers it
Cloud-native, Entra-joined, user-driven setupDevice preparation
Hybrid Entra join to on-prem AD (Active Directory)Classic Autopilot — device preparation cannot
Pre-provisioning / white gloveClassic Autopilot
Self-deploying kiosks with no userClassic Autopilot self-deploying
Kill the hardware-hash registration dependencyDevice preparation
Same intent — zero-touch to the user — inside a different envelope: device preparation trades some of classic Autopilot's flexibility for the removal of its most fragile dependency.
The Decision
New Cloud-Native Fleets Start Here; Hybrid and Edge Cases Keep Classic
The mistake in both directions is treating this as a like-for-like upgrade. It is not: for a greenfield or cloud-native estate handing Entra-joined Windows devices to users, device preparation is the lower-friction default going forward — no hash wrangling, fewer moving parts. But a working classic Autopilot pipeline with OEM registration is not broken, and where you still need hybrid join, white-glove or self-deploying kiosks, classic Autopilot remains the only tool.
So the decision is scenario-led, not version-led: reach for device preparation on new cloud-native provisioning to be rid of the hardware hash, and keep Windows Autopilot — Zero-Touch Provisioning for hybrid and the pre-provisioning modes it still owns. Either way the desktop is still gated by the same finish-line logic that Enrollment Status Page (ESP) describes — do not migrate a pipeline that already works simply because a newer flow exists.

The Gate That Makes a Device Ready on Day One
The Enrollment Status Page is the full-screen progress screen during Autopilot/enrollment. Its purpose is to withhold the desktop until the device is genuinely ready — required apps installed, policies applied, certs delivered — so nobody lands on a half-configured machine and starts working before security settings arrive.

Keep the blocking list short, and raise the timeout before you first deploy rather than after. Log collection on failure costs nothing and is the difference between a diagnosable and an undiagnosable report from a remote user.
Reference
What Counts, Timeouts & Troubleshooting
ESP tracks only Required-assigned apps/policies that target the device/user in scope — Available apps are ignored. In the device phase it can only track device-targeted items (user isn't known yet), which is why heavy user-targeted apps belong in the account phase or pre-provisioning.
PitfallFix
Too many/large blocking apps → timeoutKeep blocking set minimal; raise timeout; use pre-provisioning
Wrong detection rule → waits foreverFix the app's detection method (it already installed)
User-targeted app tracked in device phaseAssign to devices, or move to account phase
Win32 app depends on another → orderModel dependencies so prerequisites finish first
Best practice: block only what a user truly needs on day one (security agent, VPN, core LOB app); set a realistic timeout; and front-load device-targeted apps via pre-provisioning so the end-user wait is minutes, not an hour. Logs: Event Viewer → DeviceManagement-Enterprise-Diagnostics-Provider and the Autopilot diagnostics page.
🧳 Windows Backup for Organizations — Settings Restore on a New PC, and What It Leaves Behind Intune • Provisioning ▶
What it carries
It Brings Back Settings and the Store App List, Under a New Name
Windows Backup for Organizations, which Microsoft is renaming Windows settings backup and restore, saves a user's Windows settings and preferences and the list of their Microsoft Store apps to their Entra account, and offers them back on a new or reset device. Once a policy turns backup on, a scheduled task runs it every eight days, and users can run it themselves from the Windows Backup app. It needs an Entra joined or hybrid joined device on a recent build of Windows 10 22H2 or Windows 11. From Windows 11 version 26H2, backup is on by default, in most regions, wherever its policy is left not configured, and since July 2026 the same feature manages Enterprise State Roaming.
On the new deviceComes back from
Windows settings and preferencesThis backup
Microsoft Store appsThis backup's list of them
Files in Desktop, Documents and PicturesNot this backup: OneDrive, if Known Folder Move was on
Win32 and line-of-business appsNot this backup: the Intune assignments, or whatever installed them the first time
Pair it with Known Folder Move, or the user gets their wallpaper back and not their documents. Microsoft describes what the backup holds as settings, preferences and the Store app list, so a device swap that relies on it alone restores how Windows looked and loses what the user was working on. Moving the known folders into OneDrive is OneDrive — Known Folder Move, Files On-Demand & Sync Triage.
Restore
Restore Is Off Until You Turn It On, and the Tenant Switch Reaches Only New Enrollments
Backup and restore are separate policies, and restore is off by default. It is offered at two points. During setup, the out-of-box experience, it needs an Entra joined device, and an Autopilot profile in user-driven mode rather than self-deploying. At the user's first sign-in after enrollment, on Windows 11 24H2 or 25H2 with March 2026's builds, it also works on hybrid joined devices. Either way the user signs in with the same work account that made the backup, picks a backup profile from a previous device or chooses to start fresh, and a restore summary appears about an hour later, visible for seven days.
Turned on byReachesWhen
The tenant-wide enrollment setting, Devices > Enrollment > Windows Backup and RestoreEvery device that enrolls from then onAt enrollment, ahead of other policy, in time for setup. Devices already enrolled never see a change to it

A self-deploying device never shows the restore page. Restore during setup needs a person signing in, so kiosks and shared devices provisioned in self-deploying mode skip it by design, and the ticket that says the restore page never appeared on one is answered by the profile, not by the backup. The profile types are in Windows Autopilot — Zero-Touch Provisioning.
When it does not work
A Policy That Turns Off the Activity Feed Turns Off Backup Too
Microsoft lists five policies that must not be set to Disabled, or backup does not apply: the three activity history settings, EnableActivityFeed, PublishUserActivities and UploadUserActivities, plus EnableCDP for the Connected Devices Platform and AllowConnectedDevices. Each looks like a privacy setting with nothing to do with backup. Configure the feature through Group Policy or through MDM (Mobile Device Management), never both. And Conditional Access can stop the restore itself: a user who sees You can't get there from here during setup is being refused a token, which a policy allowing the restore service's app ID fixes.

Read the baseline before blaming the feature. Activity history and the Connected Devices Platform are the kind of thing a privacy-minded hardening baseline switches off, and nothing in either setting's name says backup depends on it. Find which baseline sets them, and decide which matters more, as Security Baselines Without Breaking the Fleet describes.

🏛️ MECM (Microsoft Endpoint Configuration Manager) at Scale — Site Design, Boundary Groups & Collections That Don't Melt the Server MECM • Architecture ▶
The Inversion
The CAS Is the Mistake. One Primary Site Goes Further Than You Think.
The instinct when the estate is large is to build a hierarchy — a Central Administration Site on top, primary sites beneath it, a secondary site at every branch. It is almost always wrong. A single standalone primary site supports on the order of 150,000 clients; the CAS exists only to roll several primaries into one console above that ceiling, and it buys you a whole new failure domain — SQL (Structured Query Language) replication between sites — that you now have to keep healthy and debug when it drifts. The shops that stood up a CAS “to be safe” mostly spend their time nursing replication they never needed.
Site typeWhat it is forWhen it is actually justified
Central Administration SiteRoll-up console and configuration across multiple primary sitesOnly above a single primary's ceiling (~150k), or a genuine multi-primary need — not for tidiness
Primary siteThe workhorse: clients attach here, it owns a SQL databaseAlmost every organization needs exactly one, and only one
Secondary siteThrottles and controls content sent upstream to a remote locationOnly when a location can't reach a distribution point and needs local, bandwidth-managed content — otherwise a plain DP is the answer
The unit you are really choosing is how many SQL databases you must keep in sync. Build one primary; add a secondary only to manage a starved WAN (Wide Area Network) link, and reach for a distribution point — not a site — everywhere else.
The Fingerprint
When Content Comes From the Wrong Place, It Is Almost Always Boundary Groups
Boundaries — an IP (Internet Protocol) subnet, an AD (Active Directory) site, an IP range — map a client to a boundary group, and the boundary group names the site systems (management point, distribution point, software update point) that client should use. The classic failure is a client pulling content from the wrong distribution point: an install that crawls over the WAN when a healthy DP sits on the same subnet, or “no content available” when the local DP plainly has it. That symptom has one usual cause — a boundary the client falls outside of, a fallback that lands on a distant DP or the site server itself, or a fallback timer so short the client reaches across the link before its preferred DP even answers.
SymptomThe boundary-group cause behind it
Client pulls content over the WAN though a local DP existsThe client's subnet isn't in a boundary group that references the local DP
“No content available” despite a healthy DPClient is in no boundary group and no fallback source is configured
Site server itself hammered for contentFallback lands on the default site boundary group, with the site server acting as a DP
Content arrives, but slowly and from far awayFallback time is too short — the client gives up on the near DP and reaches out
A boundary group is a two-layer map — boundaries into the group, group onto site systems — and both the relationships (which neighboring group to fall back to) and the fallback timers decide routing. Wrong here means wrong for everyone in that boundary, which is why content problems are a boundary-group check first, a DP check second.
The Decision
Collections Are Queries — and a Careless Query Is a Site-Wide Tax
A collection is the unit of targeting: deployments, maintenance windows and client settings all point at collections, so membership is who gets what. Query-based collections re-evaluate their membership — on a schedule, or continuously if incremental updates are on. The trap is turning incremental updates on across dozens of collections, or writing a query that scans every resource on the estate: the site server then re-evaluates without pause, evaluation load climbs, the console lags and deployments are slow to land. Incremental updates are a finite budget — Microsoft's own guidance caps how many collections should use them — not a default to switch on everywhere.
Collection choiceWhat it costs the site server
Incremental updates on many collectionsNear-constant re-evaluation; load climbs; runs past the documented cap
Scheduled full evaluation, off-hoursCheap and predictable — the right default for most targeting
Query limited to All Systems that scans everythingEvery evaluation touches the whole estate
Query limited to a tight parent collectionEvaluation only ever touches the parent's members
So the three architecture decisions compound into one rule: one primary site unless you have truly outgrown it, boundary groups whose fallback and timers you have actually reasoned about, and collections on scheduled evaluation with incremental reserved for the few that need near-real-time membership. Get them right and the site server stays responsive under load; get them wrong and every deployment inherits the tax — which is what the log map in MECM Site Health & Server Log Map is really diagnosing. And when the hierarchy's whole reason for being — imaging, deep app packaging, on-prem content — has moved to the cloud, the honest exit is the workload-by-workload path Co-management & Cloud Attach lays out, not a big-bang cutover.

🥊 Policy Conflicts — Proving Which One Won Intune • Policy ▶
Concept
Nobody Wins a Conflict
The instinct from Group Policy is that the last writer, or the most restrictive value, wins. That is not how Intune configuration profiles behave. When two profiles set the same setting to different values, the usual outcome is a Conflict state and the setting is not applied at all — the device keeps whatever it had. A few CSP (Configuration Service Provider) areas do resolve to the more restrictive value, but relying on any tie-break is how you end up with a fleet that is neither configuration.
SituationWhat actually happens
Two Intune profiles, same setting, different valuesConflict — the setting is not applied
Two Intune profiles, same setting, same valueApplies cleanly; no conflict
Intune profile vs security baselineStill a conflict — a baseline is just another profile
Intune vs GPO (Group Policy Object) on a co-managed deviceDepends on the workload slider; whichever authority owns it wins
User-targeted vs device-targetedBoth apply to their own scope; a conflict only if the CSP is the same node
The fix is always the same: find the duplicate and delete one. There is no correct way to have two profiles arguing about one setting.

🎯 Assignment Strategy — Users, Devices, Filters & Exclusions Intune • Policy ▶
Concept
Targeting Is Where Policy Goes Wrong
Most "the policy is assigned but not applying" tickets are not policy problems at all — they are targeting problems. Three rules cover nearly all of them.
RuleConsequence

The first rule is the one that explains most mysteries, and it is invisible from the policy's own page. 📡 Delivery Optimization — Download Modes, Peer Groups & Where Windows Gets Its Updates Intune • Servicing ▶
What it is
Delivery Optimization Is Windows' Downloader, and Peers Are Only One of Its Sources
Delivery Optimization is the downloader Windows uses for its updates, Store apps, Defender definitions, Intune Win32 apps, Microsoft 365 Apps, Edge and Teams. Download mode
The Download Mode Decides Who Counts as a Peer, and the Default Is the Same Public IP (Internet Protocol)
One setting, the download mode, decides where peers may come from. The default, LAN (Local Area Network), offers as peers the devices that reach the internet through the same public IP address, which then connect to each other over their private addresses. Group mode draws the line by group instead, across subnets and out to remote offices: by default the device's Active Directory site, then its domain, then the Entra tenant, unless a Group ID you set overrides it. HTTP (HyperText Transfer Protocol) only turns peering off and keeps everything else. In Intune the settings live in a configuration profile, in the settings catalog's format since April 2025, beside the cache's limits: by default, files kept three days in up to 20% of the drive's free space.

🔩 Driver Management — Driver Packs, DISM (Deployment Image Servicing and Management) & the Autopilot Dilemma Endpoint • Provisioning ▶
Concept
Imaging Solved Drivers by Owning Them; Modern Provisioning Solved It by Giving Them Away
In a task-sequence world the driver problem is a supply problem you control. You download the vendor's driver pack for a model, import it, and apply it by WMI (Windows Management Instrumentation) query so a Latitude gets Latitude drivers. The build is deterministic because you decided, per model, exactly which versions ship. The cost is a catalog: every new model is a new pack, every pack needs testing, and the boot image needs its own storage and network drivers or WinPE (Windows Preinstallation Environment) never gets far enough to ask.
Autopilot inverts that. There is no image and no task sequence, so there is nowhere to inject anything — the device arrives with the OEM's factory drivers and takes everything after that from Windows Update. That is genuinely less work, and it is also a control you have handed to someone else: you no longer choose the version, and "we tested that build" stops meaning what it meant. The honest framing is not which is better but which failure you would rather own: a stale pack you forgot to refresh, or a vendor publishing a regression to your fleet on their schedule. 
# What is actually installed — the store, not Device Manager's rendering
Get-WindowsDriver -Online | Where-Object { $_.ProviderName -ne 'Microsoft' } |
  Select-Object OriginalFileName, ProviderName, Date, Version

# Offline servicing: add drivers to a mounted image (or a boot image)
DISM /Image:C:\mount /Add-Driver /Driver:D:\DriverPack\Latitude5450 /Recurse

# Remove a known-bad OEM driver by its published name (oemNN.inf)

Pitfall
Three Driver Failures and the Log Line That Names Each One
PE boots, then nothing. The task sequence never appears, or it appears and cannot reach content. Almost always a boot image missing the model's storage or network driver, and it is architecture-specific — an x64 pack does nothing for the ARM (Advanced RISC Machines) device someone just bought. The fingerprint is in smsts.log: content download failing immediately with no IP (Internet Protocol), or a disk that never enumerates. Fix the boot image, then remember it needs redistributing to every distribution point before it means anything.
The driver applied, and Windows chose a different one anyway. Windows ranks drivers, and a signed generic driver with a newer date can outrank the vendor pack you injected. The fingerprint is Get-WindowsDriver showing your driver present in the store while pnputil /enum-devices shows something else bound to the device. Injection stages a driver, it does not force it — pinning a specific one means blocking the alternative, not adding yours harder.
A driver shipped to the fleet on a Tuesday and took the docks with it. The rollback path for drivers is not the update rollback path: you block the specific update and roll back per device in Device Manager, which is a per-machine action at fleet scale. This is the argument for putting drivers in rings even when you have delegated the versions — a pilot ring that includes one of each model catches the regression while it is still a support ticket rather than a bridge call. The wider mechanics of rings and deadlines are in Windows Update for Business — Rings, Deferrals & Deadlines.
Decide it once, per estate, and write it down: either you own driver versions and accept the catalog, or you delegate them and accept the drift — with rings and a named exception list for the hardware that genuinely cannot be delegated. The expensive position is the accidental third one, where nobody refreshed the packs and nobody configured the policies, so the fleet is running whatever the last engineer's image happened to contain. That is the same drift the servicing split describes in Feature vs Quality vs Driver Updates.

Group Policy
Group Policy Objects (GPOs) Explained
A GPO is a collection of settings pushed from the domain controller to computers and users automatically. Examples of what GPOs control:

• Password complexity requirements.
• Screen lock after N minutes of inactivity.
• Mapped drives (e.g. H: = home folder on file server).
• Software deployment (install apps on logon).
• Firewall rules, browser settings, USB (Universal Serial Bus) restrictions.

GPOs apply in order: Local → Site → Domain → OU (LSDOU). Later policies win unless "Enforced" is set. Use gpresult /r on a PC to see which GPOs actually applied.

You can't make someone make the right choice, yet you can pick up the pieces afterwards — GPOs don't stop a determined user completely, but they raise the barrier and give you an audit trail when something goes wrong.

🔐 BitLocker at Scale — Silent Enablement, Key Escrow & Recovery Endpoint • Security ▶
Concept
The Only Question That Matters Is "Can You Get the Key Back"
Encrypting the fleet is easy; a policy does it in an afternoon. The part that ends careers is a device that has gone into recovery and a recovery key that was never escrowed anywhere. At scale, BitLocker is a key-management problem wearing an encryption costume — design the escrow first, then turn on encryption, never the other way round.
PieceWhat it is
TPM (Trusted Platform Module)The chip that seals the key to a known-good boot state; unlocks transparently at boot
BitLocker recovery keyThe 48-digit fallback when the TPM refuses — the thing you must have escrowed
Escrow locationEntra ID for cloud-joined devices, AD (Active Directory) for hybrid; MECM (Microsoft Endpoint Configuration Manager) keeps its own recovery store too
Encryption methodXTS-AES 128 or 256; used space only vs full disk on first encryption
Test the escrow before you encrypt anything, on a real device you are willing to lock out. A policy that encrypts the fleet and silently fails to store keys looks identical to one that works, right up until somebody is standing at a recovery screen — and by then the number of affected machines is the whole estate. Prove you can retrieve a key by identifier, from the console, by somebody on the service desk, before the rollout.
Flow
Silent Enablement, and the Order It Must Happen In
Silent enablement means the user never sees a prompt — the disk encrypts and the key escrows without interaction. It only works if the prerequisites are already true when the policy lands, and the classic failure is a device that reports "encrypted" with a key that reached nowhere.
StepMust be true
1 PrerequisitesTPM present and ready, UEFI (Unified Extensible Firmware Interface), Secure Boot on, no third-party encryption already resident
2 Policy appliesDisk-encryption profile assigned; "allow standard users to enable" set for non-admin devices
3 EncryptKicks off silently; used-space-only is faster on a fresh device
4 EscrowThe one to verify — confirm the key is visible in Entra/AD before you call it done
A device can be encrypted and unrecoverable at the same time. Report on escrowed keys, not on encryption status. The two diverge exactly on the devices you will most need to recover.
Troubleshooting
Why a Device Drops Into Recovery
Recovery is the TPM doing its job — something in the measured boot path changed, so it refused to release the key. Most are benign and self-inflicted, which is why users should never see the recovery screen as a crisis.
TriggerUsually
Firmware/BIOS updateChanged PCRs; expected — suspend BitLocker before flashing firmware
Secure Boot / boot-order changeSomeone changed a UEFI setting
Docking / hardware changeSome configs measure it; re-seal or adjust the PCR profile
Repeated recovery on one modelA driver or firmware bug — a real fleet issue, not a user one
The last row is the only one that is your problem; the rest are the chip working correctly. One-off recoveries after a firmware update or a boot-order change are expected, and the fix is process — suspend before the update, tell the service desk what to say. Repeated recovery on one hardware model is a fleet defect and needs a driver or firmware investigation, not another key lookup.

🧯 Defender Vulnerability Management — Exposure Score, Recommendations & Handing the Fix to Intune Endpoint • Security ▶

An Exception Hides a Risk for a Fixed Time, and Cannot Be Extended
When a recommendation cannot be acted on, because there is no fix, a compensating control covers it, or the update breaks an application, an exception takes it out of the work. 🧑‍💼 Local Admin Rights — Removing Them, and Endpoint Privilege Management Endpoint • Security ▶
Concept
Standing Local Admin Is the Single Biggest Endpoint Risk You Control
A user who is a local administrator turns every phishing click and every malicious installer into a full device compromise, and defeats most of the controls on the rest of this page. Removing standing admin is the highest-leverage endpoint hardening there is — and the reason it survives everywhere is that removing it naively generates a wall of "I can't do my job" tickets. The work is not deleting the right; it is replacing what people legitimately used it for.

🛂 App Control for Business — Managed Installers, Audit Mode & the AppLocker Policy That Can Stop Sign-In Endpoint • Security ▶
What it is
App Control Runs Only What a Policy Trusts; AppLocker Is the Older Tool Beside It
App Control for Business, which Microsoft called Windows Defender Application Control until its rename, turns Windows from a place where anything runs unless antivirus objects into one where code runs only if a policy trusts it. That covers executables and DLLs (Dynamic Link Library), drivers, scripts and MSI installers, and interactive PowerShell, which drops into Constrained Language Mode. A rule can trust a signing certificate, a file's attributes or hash, Microsoft's reputation service, the installer that put the app there, or a path. AppLocker, from Windows 7, does a narrower version of the same job; it still gets security fixes and no new features. Neither replaces antivirus.

Managed installer

Intune can make its management extension a managed installer: every app it installs from then on is tagged as coming from a known source, and an App Control policy that trusts managed installers lets those apps run without a rule each. Turning the policy off, or excluding a group, stops new tagging but removes nothing from devices that already have it. Marking a device non-compliant the instant it drifts, and blocking it the same second, locks people out over a signature that is four hours stale. 📉 Reporting on Drift — Finding Devices That Quietly Stopped Complying Endpoint • Compliance ▶
Concept

A non-compliant device is a known problem the system is already acting on. The device that should worry you is the one that stopped checking in — it is not evaluated, so it is neither compliant nor blocked, just invisible. A fleet report that only counts compliant vs non-compliant hides its own blind spot. Report on the third bucket explicitly.

Technique
Trend the Rate, Alert on the Slope
A single day's compliance percentage is noise. What tells you something broke is the change: a five-point drop overnight is almost always a policy edit or a bad update ring, not a hundred users independently misbehaving. Watch the trend and the last-check-in distribution, and treat a spike in "not evaluated" as an operational incident — it usually means an agent, an enrollment, or a network path stopped working for a whole segment at once.
Tie a sudden compliance drop to what you changed. The first question on a drift spike is "what deployed in the last 24 hours" — a new baseline, a tightened setting, or an update. Correlating drift with your own change log finds the cause faster than inspecting devices.

🖥️ Shared, Kiosk & Frontline Devices ENDPOINT • Device Classes ▶
The Inversion

Compliance is evaluated per user-device pair, licenses are assigned per user, and the wipe path assumes one owner whose data leaves with them. A shared device breaks all four at once — identity, compliance, licensing and the wipe path each assume a one-to-one relationship that a frontline tablet passed between three shifts does not have. Managing shared devices is not a harder version of managing laptops; it is a different configuration where the defaults are actively wrong.
AssumptionHow a shared device breaks it

Name the Pattern Before You Enrol the First One
The expensive mistake is enrolling a batch of shared tablets as if they were personal devices and discovering the mismatch in production — sign-in friction on a factory floor, licenses consumed by a shared identity, one user's session bleeding into the next. The device-management platforms have specific enrollment modes for these, and choosing the right one is a design decision made once, up front.

The Inversion

When the endpoint is a session on a server rather than a device in a hand, the whole model turns inside out. A non-persistent desktop is rebuilt from a golden image every logon, which means nothing installed at runtime survives — including the very agents that usually do the managing. Profiles, licensing, patching and troubleshooting all move location, and a team that treats a virtual desktop like a thin laptop gets each one subtly wrong.

Virtual desktops are sometimes deployed as a default modernization move, which is how organizations end up paying per-user compute and storage every month for users who needed a laptop. The browsers support central policy — extension allow-lists, forced updates, controlled sync, a separated work profile — through the same MDM (Mobile Device Management) channel as everything else. Assign the browser an owner and a policy baseline: allow-list extensions, force updates, and draw the work/personal profile boundary deliberately. It is the highest-traffic application in the estate and deserves at least the attention given to the ones nobody uses.
🧩 Application Compatibility & the Legacy App ENDPOINT • Applications ▶
The Fingerprint

The pattern is universal: a Windows feature update, a browser migration or a hardware refresh is held hostage by a single business-critical application that only runs on the old thing — an ancient line-of-business tool, a vendor app abandoned by its maker, a macro-laden spreadsheet someone built in 2009. The app cannot be changed and the platform cannot stand still, and the whole estate's modernization stalls on it. 🔎 Lost, Stolen & Returning Devices Endpoint • Operations ▶
The Decision
The Data Question Is Answered Before the Device Is Lost, or Not at All
When a laptop is reported missing, the panic question is “what was on it?” — and if the answer depends on encryption and remote wipe that were configured after the loss, it is too late. A lost encrypted device with a strong pre-boot secret is a hardware loss; a lost unencrypted one is a data breach, and which of the two you are holding was decided at enrollment. The lost-device runbook is short only because the hard work was done in advance.

The Fingerprint
The Device That Comes Back Six Months Later, Still Enrolled
The forgotten half of the lifecycle is return. A device written off as lost reappears — found in a drawer, returned by a leaver, recovered by police — and it is still enrolled, still trusted, and possibly still holding cached credentials for accounts that were never rotated. A returning device is not automatically safe just because it is back in the building.
Treat a returned device as untrusted until wiped and re-enrolled, and make “lost” a state with a proper close-out — license released, object cleaned up, credentials rotated — not an open ticket that lingers. The device found in a drawer a year later is the one nobody remembered still had a valid certificate on it.

📦 MSI (Microsoft Installer), EXE & .intunewin — What Each Package Is, and How It Installs Packaging • Formats ▶
Three different things
MSI vs EXE: a Database Windows Runs, a Program That Runs Itself — and a Box That Carries Either
The three file types an endpoint engineer packages are not three versions of one idea. An MSI is a Windows Installer database: tables that describe the files, registry entries and shortcuts to put in place, which the Windows Installer service applies through msiexec. An EXE is a program, and what it does when run is up to whoever built it: it may be an installer made with Inno Setup, NSIS, InstallShield or WiX, or a bootstrapper that unpacks an MSI and runs that. A .intunewin file is not an installer at all. Prefer the vendor's MSI, and when there is only an EXE, find out what built it. Many EXEs are a known installer framework, with known switches, or a wrapper around an MSI that can be deployed on its own. An EXE nobody can identify is the one that needs a wrapper script around it, so that the deployment tool gets a silent command, a predictable exit code and something to detect.
Testing
Test It the Way the Client Runs It: as SYSTEM, With No One to Click
MECM's Install for system and Intune's System install behavior both run the command as the local SYSTEM account, with no user to answer a prompt. A dialog box that appears there waits, unseen, until the tool gives up: by default after 120 minutes in MECM, its maximum allowed run time, and 60 minutes in Intune, which allows up to 1,440. Microsoft's own advice is to test the exact command in the system context first. 
# A command prompt running as SYSTEM, from an administrator prompt, with Sysinternals PsExec
psexec -accepteula -s -i cmd
whoami                     # nt authority\system
# Run the exact command the deployment will run, with a verbose log, then read the exit code
msiexec /i "app.msi" /qn /norestart /l*v "%TEMP%\app-install.log"
echo %ERRORLEVEL%

A command tested only as yourself has not been tested. Your session has a desktop, your profile, mapped drives and a 64-bit shell, and the client has none of those. When the install works and the tool still reports failure, the fault is usually the detection rule, which is the subject of App Deployment Error Codes — Intune and MECM Side by Side, by What Raised Them.

Read the layer first
Three Layers Raise Codes, and the Form of the Number Says Which
Comparing Intune with MECM is the wrong place to start for most codes, because most of them belong to neither. A deployment has three layers that can fail, and each reports in its own form. The installer returns a small decimal exit code, and both tools pass it on unchanged. The management agent, MECM's client or Intune's management extension, raises codes that start 0x87D. Windows itself raises codes that start 0x8007 or 0x8000. Both consoles may also show the same code as a negative decimal: 0x87D00324 is -2016410844.

📜 Certificate Delivery — SCEP (Simple Certificate Enrollment Protocol), PKCS (Public Key Cryptography Standards) & Why Wi-Fi Fails Silently Intune • Certificates ▶
The Inversion
The Profile That Fails Is Never the One That Reports the Error
Wi-Fi and VPN (Virtual Private Network) profiles that authenticate with a certificate have a dependency the console does not draw: the certificate profile must land first, and it must land on the same device, for the same user, from a template the issuing authority will actually sign. When any of that fails, the certificate profile is what errors — but nobody is looking at it, because the symptom the user reports is “wi-fi does not connect” and the Wi-Fi profile says it deployed successfully.
What the reader seesWhat is actually true
Wi-Fi profile: SucceededThe profile arrived. It was never claimed the certificate did
Device is compliantCompliance does not evaluate whether a certificate was issued
It works for the admin who tested itThe admin was in the group that had already received a certificate
It worked last yearCertificates expire. Renewal is a separate flow with its own failures
Debug in dependency order, not in complaint order. Check that the certificate exists on the device before touching the Wi-Fi profile at all — on Windows the personal certificate store, on iOS the profile's payload. Every hour spent re-reading a Wi-Fi profile that deployed correctly is an hour spent on the wrong object.
Choosing
SCEP, PKCS and Cloud PKI (Public Key Infrastructure) — Three Ways to Get a Key onto a Device
The difference that matters is where the private key is generated. That single property decides what infrastructure you must run, what happens when a device is lost, and whether the credential can be exported.
MethodKey generatedInfrastructureSuits
SCEPOn the device — the key never movesCertificate authority plus a connector endpoint the device can reachDevice and user authentication at scale; the default choice
PKCSOn the certificate authority, then deliveredCertificate authority plus a connector serviceCases where the key must be escrowed or reused, such as S/MIME
Imported PKCSElsewhere entirely, uploaded in advanceA store of pre-generated certificatesEmail encryption where old keys must be recoverable

Prefer SCEP unless something specific forbids it. A private key that never leaves the device is the stronger posture, and a lost device becomes a revocation rather than a key-compromise investigation. PKCS exists for the genuine exception — chiefly encrypted mail, where a key that cannot be recovered means mail that cannot be read — and that exception should be a decision somebody wrote down, not the option that happened to be picked first.

Habit
Renewal Is the Deployment You Are Not Watching
A certificate rollout gets attention because somebody is running it. The renewal a year later gets none, and it runs against a fleet that has drifted: devices retired without revocation, users who moved between groups, a connector nobody patched. The failure arrives as a slow trickle of authentication problems rather than an incident, which is why it is usually diagnosed late.
PracticeWhy it earns its place

The last row is the one worth putting in a calendar today. Every certificate this system issues is bounded by the life of the authority above it, that life is measured in years, and nothing in the endpoint tooling will warn you. It is the single highest-impact, lowest-frequency failure in the estate — and the only defense is somebody having written the date down.
🔑 Intune RBAC (Role-Based Access Control) & Scope Tags — Delegating Without Handing Over the Fleet Intune • Delegation ▶
The Inversion
Two Permission Systems, and the One People Reach for Is the Wrong One
Intune permissions come from two places that look interchangeable and are not. Directory roles are tenant-wide and coarse; Intune's own roles are scoped and fine-grained. The common failure is granting a directory role because it is the one visible from the identity console, which hands somebody the entire fleet in order to let them wipe one laptop.
MechanismGranularityUse it for
Directory role — Intune AdministratorEverything in the service, every device, every policyThe two or three people who own the service. Not a helpdesk tier
Intune role — built-inA named set of actions: Help Desk Operator, Policy and Profile Manager, Read OnlyAlmost every delegation. Start from these before writing one
Intune role — customIndividual permissions, chosen action by actionThe genuine exception the built-ins do not fit
Scope tag on a role assignmentWhich objects the assignment can seeRegional or business-unit separation inside one tenant
Reach for a built-in Intune role first, and treat the directory role as the break-glass tier. A custom role written on day one usually encodes a misunderstanding of what the built-ins already do — and every custom role is a thing somebody must re-review the next time the product adds a permission.
Concept
A Role Assignment Is Three Answers, Not One
This is where the model stops resembling ordinary permissions. An assignment names who holds the role, which admins' objects they may act on, and which users or devices they may act against. Those last two are separate lists, and conflating them is the reason a delegation either does nothing or does far too much.
Part of the assignmentAnswersGetting it wrong looks like
MembersWho is being given the roleNothing subtle — it simply does not apply
Scope (groups)Which users and devices they may act onThe operator sees a device and cannot wipe it, with no useful error
Scope (tags)Which objects — policies, apps, profiles — they may even seeAn empty console for an admin who has permissions, because nothing carries their tag
The empty console is the signature of this model, and it is not a bug. An administrator with a correct role and no matching scope tag sees a working portal with nothing in it. Anybody debugging a delegation should check tags before checking permissions — the permission is usually right and the object simply is not visible.
Reference
What Scope Tags Do Not Do
Scope tags are a visibility filter over objects. They are widely assumed to be a security boundary, and treating them as one produces a delegation that is weaker than the diagram suggests.
AssumptionReality
“Regional admins cannot affect other regions”True for tagged objects. A policy with the default tag is visible to everybody
“Untagged means private”The opposite — the default tag is the broadest one, and it is what new objects get
“It limits which devices they can see”Devices are limited by the scope groups, not by tags
“It stops them creating things”Creation is a permission. A tag decides what the new object inherits, not whether it may exist
“It is an audit boundary”Audit logs are tenant-wide; the tag does not partition them
Row two is the one that quietly undoes a design. Every object created before the tagging scheme existed carries the default tag, and so does every object created by somebody who forgot to set one. A tagging model is only as good as the audit that finds untagged objects — and that audit has to run more than once, because the population grows every time somebody clicks Create.
Habit
Design the Delegation From the Tickets, Not the Org Chart
Delegation models drawn from the organization chart produce a role per team and a permission set nobody can justify. Drawn from the work, they produce two or three roles that cover most tickets and an escalation path for the rest.
TierCan doCannot
Service deskRead devices, sync, restart, retrieve a recovery key, assign a userChange policy, wipe, alter compliance

Service ownerEverything, including role assignmentsNothing — which is why it is two or three people with privileged access management around it
Put the recovery-key read in tier one deliberately, and audit it. It is the single most-requested action, so withholding it guarantees the escalation path becomes a standing exception — and standing exceptions are how a service desk ends up holding an administrator role. Grant it, log it, and review the log; that is a smaller risk than the workaround it prevents.
