🏢 Microsoft Endpoint Configuration Manager (MECM) On-Prem ▶
Reference
ConfigMgr / SCCM (System Center Configuration Manager) — What It Is & Where It Fits
MECM (formerly SCCM, universally called ConfigMgr) is Microsoft's on-premises platform for managing Windows (and some Linux/macOS/servers) at scale: application deployment, patching, OS (Operating System) imaging, hardware/software inventory, and compliance. It ships in the Current Branch model — a new feature release roughly three times a year (e.g. 2403 = 2024, March), applied in-console.
StrengthWhy it still matters
Deep OS deploymentFull bare-metal imaging & task sequences Intune can't match
Bandwidth controlOn-prem DPs, peer caching for large/branch fleets
Granular software dist.Complex app models, supersedence, dependencies
Mature reportingSQL (Structured Query Language) Reporting Services, rich inventory
The direction of travel is cloud: most orgs now run co-management (ConfigMgr + Intune on the same device) and move workloads to Intune over time. ConfigMgr isn't dead — it's the on-prem anchor of a hybrid estate (see the Co-management card).
Architecture

A ConfigMgr deployment is a hierarchy of sites, each identified by a 3-character site code (e.g. P01). Most orgs need only a single standalone primary site; very large or multi-geo estates add a CAS and/or secondary sites.

The Client
Agent Install, Settings & Health
The ConfigMgr client (ccmsetup.exe → CcmExec service) runs policy, inventory, and deployments. It can be installed several ways; client behavior is governed by Client Settings (default + prioritized custom sets assigned to collections).

Control Panel → Configuration Manager exposes actions like Machine Policy Retrieval, Hardware Inventory Cycle, and Software Updates Scan — the buttons you press when "it's not showing up yet." Client health is monitored by the built-in ccmeval scheduled task, which auto-remediates a broken client.
Content & Targeting
Boundaries, Boundary Groups & Distribution
Clients find their nearest servers via boundaries (IP subnet, AD site, IPv6 prefix, or IP range) grouped into boundary groups, which map to the MPs/DPs/SUPs a client should use — with fallback relationships and time delays.

#1 support ticket: "content won't download." Almost always a missing/overlapping boundary, content not distributed to the client's DP, or a boundary group with no fallback. Check LocationServices.log and ContentTransferManager.log.
Deploying Things
Applications, Updates & OS Deployment
Everything targets a collection (device or user; direct or query/WQL membership). The three big deployment workloads:
WorkloadKey pieces
ApplicationsDeployment types + detection method + requirement rules + supersedence; purpose Available (Software Center) or Required (enforced by deadline)
Software UpdatesSUP scan → deploy manually or via ADR (Automatic Deployment Rule) that grabs each Patch Tuesday into a deployment package
OS Deployment (OSD)Task sequence: boot image (WinPE) → partition → apply WIM (Windows Imaging Format) → drivers → join (AD/Entra) → apps
Detection method is the make-or-break of app deployment: it's how ConfigMgr decides "already installed?" (file version, registry, MSI product code, or script). Wrong detection = endless reinstall or false failure. Maintenance windows on a collection limit when Required installs/reboots may run — critical for servers.

🪪 Azure AD (Active Directory) / Microsoft Entra ID — Endpoint Identity Identity ▶
Concept
The Identity Layer Everything Sits On
Microsoft Entra ID (formerly Azure AD) is the cloud directory behind Microsoft 365 and Intune. Every managed device gets a device object in Entra; how it obtains that identity (its join type) determines which management, SSO (Single Sign-On), and Conditional Access experiences are possible.
Join typeHow & when
Entra JoinedCloud-only. Set during OOBE/Autopilot or Settings. The modern default for corporate Windows
Entra Hybrid JoinedDomain-joined and synced to Entra (needs Entra Connect + SCP). For orgs still reliant on on-prem AD/GPO/apps
Entra RegisteredBYOD/personal — a work identity is added but the org doesn't own the device (Workplace Join)
Hybrid is heavier & more fragile (sync timing, SCP, network line-of-sight to a DC for the join). Microsoft's clear guidance: go cloud-native (Entra Joined) unless a hard dependency forces hybrid.

✈️ Windows Autopilot — Zero-Touch Provisioning Provisioning ▶
Concept
Ship a Sealed OEM Laptop Straight to the User
Windows Autopilot customizes the out-of-box experience (OOBE) so a factory device configures itself for your org — no imaging, no touching it in IT. The device's hardware identity is pre-registered to your tenant; at first boot it recognizes itself, Entra-joins, enrolls in Intune, and applies your apps/policies through the ESP (Enrollment Status Page).

Reference
What Counts, Timeouts & Troubleshooting
ESP tracks only Required-assigned apps/policies that target the device/user in scope — Available apps are ignored. In the device phase it can only track device-targeted items (user isn't known yet), which is why heavy user-targeted apps belong in the account phase or pre-provisioning.
PitfallFix
Too many/large blocking apps → timeoutKeep blocking set minimal; raise timeout; use pre-provisioning
Wrong detection rule → waits foreverFix the app's detection method (it already installed)
User-targeted app tracked in device phaseAssign to devices, or move to account phase
Win32 app depends on another → orderModel dependencies so prerequisites finish first
Best practice: block only what a user truly needs on day one (security agent, VPN, core LOB app); set a realistic timeout; and front-load device-targeted apps via pre-provisioning so the end-user wait is minutes, not an hour. Logs: Event Viewer → DeviceManagement-Enterprise-Diagnostics-Provider and the Autopilot diagnostics page.

Building a CA Policy
A CA policy is if [assignments] then [controls]. Assignments = who + what they're accessing + conditions; controls = grant/block requirements.
PartExamples

Target resourcesThe Office 365 app group, a specific app, all cloud apps

Reference
OSD Task-Sequence Variables Worth Knowing
Task-sequence variables tune how OSD downloads, caches, and stores content. Set them on a collection, in the deployment, or with a Set Task Sequence Variable step. TRUE/FALSE values are strings.
VariableWhat it does
SMSTSPreserveContentKeeps the TS's downloaded content in the ConfigMgr client cache (ccmcache) after the sequence finishes, instead of purging it — handy when the same content is needed again soon (TRUE)
SMSTSPersistContentPersists content in the task-sequence working cache (_SMSTaskSequence) for the duration of the sequence, so it survives reboots between steps
SMSTSDownloadRetryCountHow many times the client retries a failed content download (default 2) — raise it on flaky/slow links
SMSTSDownloadRetryDelaySeconds to wait between download retries (default 15) — pair with the count above for unreliable networks
SMSTSLocalDataDriveChooses the drive where the TS stores its temp working files & logs (the _SMSTaskSequence folder) — set it before content downloads to avoid X:\ (RAM) space issues in WinPE (Windows Preinstallation Environment)
SMSTSPeerDownloadEnables/allows the TS to pull content from peers (Windows PE Peer Cache / peer sources) rather than a DP — TRUE/FALSE
SMSTSDownloadProgramSpecifies an Alternate Content Provider (ACP) — a custom download program (e.g. third-party peer-to-peer like Nomad/Adaptiva) used instead of the built-in downloader
Common combos: on slow branch links, raise SMSTSDownloadRetryCount/Delay, set SMSTSLocalDataDrive=C early, and enable SMSTSPeerDownload so peers share content. Use SMSTSPreserveContent when a later phase (or a re-image retry) reuses the same packages. Verify all of it in smsts.log.

📦 MECM (Microsoft Endpoint Configuration Manager) Deployment & Content Troubleshooting MECM • Troubleshooting ▶

Follow the Package Server-Side, Then Client-Side
An application reaches a device through a fixed chain: it is distributed to a distribution point, advertised in policy, located by the client, downloaded, then enforced. Find the first link that failed and stop reading logs from the wrong end.

The single most common false failure: the installer ran fine, but the detection method looks for the wrong file, version or registry key — so MECM reports failure and retries forever. AppEnforce.log shows exit code 0 while AppDiscovery.log says "not detected". That combination always means the detection rule, never the installer.

🥊 Policy Conflicts — Proving Which One Won Intune • Policy ▶
Concept
Nobody Wins a Conflict
The instinct from Group Policy is that the last writer, or the most restrictive value, wins. That is not how Intune configuration profiles behave. When two profiles set the same setting to different values, the usual outcome is a Conflict state and the setting is not applied at all — the device keeps whatever it had. A few CSP (Configuration Service Provider) areas do resolve to the more restrictive value, but relying on any tie-break is how you end up with a fleet that is neither configuration.
SituationWhat actually happens
Two Intune profiles, same setting, different valuesConflict — the setting is not applied
Two Intune profiles, same setting, same valueApplies cleanly; no conflict
Intune profile vs security baselineStill a conflict — a baseline is just another profile
Intune vs GPO (Group Policy Object) on a co-managed deviceDepends on the workload slider; whichever authority owns it wins
User-targeted vs device-targetedBoth apply to their own scope; a conflict only if the CSP is the same node
The fix is always the same: find the duplicate and delete one. There is no correct way to have two profiles arguing about one setting.

🎯 Assignment Strategy — Users, Devices, Filters & Exclusions Intune • Policy ▶
Concept
Targeting Is Where Policy Goes Wrong
Most "the policy is assigned but not applying" tickets are not policy problems at all — they are targeting problems. Three rules cover nearly all of them.
RuleConsequence
Exclusion always beats inclusion A user in both an included and an excluded group is excluded. Nested groups count. This is the single most common cause.
Scope has to match the setting A device-scoped CSP (Configuration Service Provider) assigned to a user group applies to that user's devices; a user-scoped setting assigned to a device group may never apply at all.
A device with no primary user is invisible to user targeting Kiosks, shared and Autopilot pre-provisioned devices need device-group assignment.
Choosing
Groups, Filters, or Both
ToolReach for it whenCost

🧴 App Protection Policies — MAM (Mobile Application Management) Without Enrolment Intune • Apps ▶
Reference
Protecting the Data on a Device You Do Not Own
App protection policies apply controls to the app and its data rather than to the device. That is what makes BYOD (Bring Your Own Device) workable: the user keeps their phone unmanaged, and company data inside supported apps still obeys your rules.
ControlWhat it does

🔄 Windows Update for Business — Rings, Deferrals & Deadlines Intune • Servicing ▶
Flow
Four Rings, and the Setting Everyone Forgets
Update rings are a deferral policy, not a deployment. Windows fetches updates itself; the ring decides how long it waits, when it stops waiting, and how much warning the user gets before a reboot happens anyway.
RingWhoQuality deferralDeadlineGrace
0 — CanaryIT, a handful of devices0 days2 days1 day
1 — EarlyVolunteers, ~5%2 days3 days2 days
2 — BroadMost of the fleet5 days5 days2 days
3 — CriticalExecutives, clinical, production floor9 days7 days3 days
The grace period is the whole user experience. A deadline with no grace period reboots someone mid-meeting, and you will hear about it for a year. The deadline says "you can no longer defer"; the grace period says "and you have this long to pick your moment". Set both, always.
Deferral and deadline are measured from different points: deferral counts from the day the update was published, deadline counts from the day it became applicable to that device. A machine that was off for a fortnight starts its deadline clock when it comes back, not retroactively — which is why "everyone is patched by day 7" is a claim about machines that were switched on.

Group Policy
Group Policy Objects (GPOs) Explained
A GPO is a collection of settings pushed from the domain controller to computers and users automatically. Examples of what GPOs control:

• Password complexity requirements.
• Screen lock after N minutes of inactivity.
• Mapped drives (e.g. H: = home folder on file server).
• Software deployment (install apps on logon).
• Firewall rules, browser settings, USB (Universal Serial Bus) restrictions.

GPOs apply in order: Local → Site → Domain → OU (LSDOU). Later policies win unless "Enforced" is set. Use gpresult /r on a PC to see which GPOs actually applied.

You can't make someone make the right choice, yet you can pick up the pieces afterwards — GPOs don't stop a determined user completely, but they raise the barrier and give you an audit trail when something goes wrong.

🔐 BitLocker at Scale — Silent Enablement, Key Escrow & Recovery Endpoint • Security ▶
Concept
The Only Question That Matters Is "Can You Get the Key Back"
Encrypting the fleet is easy; a policy does it in an afternoon. The part that ends careers is a device that has gone into recovery and a recovery key that was never escrowed anywhere. At scale, BitLocker is a key-management problem wearing an encryption costume — design the escrow first, then turn on encryption, never the other way round.
PieceWhat it is
TPM (Trusted Platform Module)The chip that seals the key to a known-good boot state; unlocks transparently at boot
Recovery keyThe 48-digit fallback when the TPM refuses — the thing you must have escrowed
Escrow locationEntra ID for cloud-joined devices, AD (Active Directory) for hybrid; MECM (Microsoft Endpoint Configuration Manager) keeps its own recovery store too
Encryption methodXTS-AES 128 or 256; used space only vs full disk on first encryption
Flow
Silent Enablement, and the Order It Must Happen In
Silent enablement means the user never sees a prompt — the disk encrypts and the key escrows without interaction. It only works if the prerequisites are already true when the policy lands, and the classic failure is a device that reports "encrypted" with a key that reached nowhere.
StepMust be true
1 PrerequisitesTPM present and ready, UEFI (Unified Extensible Firmware Interface), Secure Boot on, no third-party encryption already resident
2 Policy appliesDisk-encryption profile assigned; "allow standard users to enable" set for non-admin devices
3 EncryptKicks off silently; used-space-only is faster on a fresh device
4 EscrowThe one to verify — confirm the key is visible in Entra/AD before you call it done
A device can be encrypted and unrecoverable at the same time. Report on escrowed keys, not on encryption status. The two diverge exactly on the devices you will most need to recover.
Troubleshooting
Why a Device Drops Into Recovery
Recovery is the TPM doing its job — something in the measured boot path changed, so it refused to release the key. Most are benign and self-inflicted, which is why users should never see the recovery screen as a crisis.
TriggerUsually
Firmware/BIOS updateChanged PCRs; expected — suspend BitLocker before flashing firmware
Secure Boot / boot-order changeSomeone changed a UEFI setting
Docking / hardware changeSome configs measure it; re-seal or adjust the PCR profile
Repeated recovery on one modelA driver or firmware bug — a real fleet issue, not a user one
🛡️ Defender for Endpoint & Intune — Onboarding, ASR (Attack Surface Reduction) Rules & Tamper Protection Endpoint • Security ▶
Concept
Two Products, One Connector
Defender for Endpoint is the EDR (Endpoint Detection and Response) platform; Intune is how you configure it on managed devices. The seam between them is the service-to-service connector — turn it on once, and Intune can onboard devices, ship Defender policy, and consume the device risk score for Conditional Access. Half of "Defender isn't working" tickets are that connector being off or the onboarding blob never landing.
Flow

StepDetail

2 OnboardEDR policy pushes the onboarding package; device registers with the service

Reference
ASR Rules — Audit Before You Block, Always
Attack Surface Reduction rules block whole classes of behaviour malware relies on — Office spawning child processes, credential theft from LSASS (Local Security Authority Subsystem Service), script-launched executables. They are high value and high blast radius, because legitimate software does some of these things too. Every ASR rule has an audit mode that logs what it would have blocked; run there first and read the reports, or you will block a line-of-business app on day one.
ModeUse
AuditLog only — the mandatory first phase; mine it for false positives
BlockEnforce, once audit is clean for that rule
WarnUser can bypass — a middle ground for rules with legitimate edge cases
Per-rule exclusionsScalpel, not the off switch — exclude the one path, keep the rule
Tamper protection stops malware — and local admins, and your own scripts — from disabling Defender. Leave it on; when it blocks a legitimate change, make that change through policy, which is the supported path through it.
🧑‍💼 Local Admin Rights — Removing Them, and Endpoint Privilege Management Endpoint • Security ▶
Concept
Standing Local Admin Is the Single Biggest Endpoint Risk You Control
A user who is a local administrator turns every phishing click and every malicious installer into a full device compromise, and defeats most of the controls on the rest of this page. Removing standing admin is the highest-leverage endpoint hardening there is — and the reason it survives everywhere is that removing it naively generates a wall of "I can't do my job" tickets. The work is not deleting the right; it is replacing what people legitimately used it for.
Choosing
What Replaces the Right
They used admin to…Replace with
Install approved softwareCompany Portal self-service; deploy as system-context apps
Run one app that demands elevationEndpoint Privilege Management — elevate the app, not the user
Change a setting IT lockedA settings-catalog policy exposing exactly that control
Genuine developer / IT needA time-boxed, audited elevation, or a separate admin account — never their daily login
Reference
Endpoint Privilege Management — Elevate the Task, Not the Person
EPM lets a standard user run a specific, approved action with admin rights while staying a standard user for everything else. The unit of trust moves from the person to the task, which is the whole point.
ModelHow it works
Automatic ruleA named, hash-verified app always elevates, silently — for known-good tools
User-confirmedUser clicks through a justification prompt; logged
Support-approvedRequest routes to IT for one-time approval — for the long tail
Full audit trailEvery elevation recorded — the evidence that makes admin removal defensible
Rule on the file's hash or signature, not its name. A rule that elevates anything called setup.exe is a privilege-escalation primitive you built and handed to an attacker.
🗝️ Windows LAPS (Local Administrator Password Solution) — Local Admin Password Rotation in Entra and AD (Active Directory) Endpoint • Security ▶
Concept
The Built-In Admin Account Is Still There — LAPS Makes It Safe
Even after you remove user admin rights, every Windows device has a built-in local administrator account, and the historic sin was giving it one shared password across the whole fleet. One machine compromised, that password dumped, and it unlocks every other machine — the textbook lateral-movement path. LAPS sets a unique, random password per device, rotates it on a schedule, and escrows it centrally so support can still get in.
Reference
Windows LAPS vs the Legacy One, and Where the Password Lives
"Windows LAPS" is the modern built-in feature, distinct from the old downloadable Microsoft LAPS. It stores the password in the directory the device is joined to, and retrieval is a permission you grant deliberately and audit.
AspectDetail
Backup targetEntra ID for cloud-joined, on-prem AD for hybrid — chosen by policy
ConfigurationAn Intune policy or GPO (Group Policy Object); no agent to deploy on current Windows
RetrievalScoped directory permission; every read is logged
RotationOn a schedule, and automatically right after a password is used
Password encryptionEncrypted in the directory (AD path); readable only by the accounts you authorize
LAPS and admin-rights removal are a pair. Removing standing user admin closes the front door; LAPS makes sure the emergency key under the mat is different for every house. Deploy them together, not years apart.

✅ Compliance Policies Deep — Settings, Grace Periods & What Non-Compliant Costs Endpoint • Compliance ▶
Concept
A Compliance Policy Only Bites Through Conditional Access
A compliance policy on its own does nothing but set a flag: compliant or not. It has no teeth until Conditional Access is configured to require compliance for a resource — then a non-compliant device is blocked from mail, files and apps. People routinely deploy compliance policies, see devices marked non-compliant, and wonder why nothing happened. Nothing happened because the enforcement lives in CA, not in the policy.
Common settingWhat it checks
OS (Operating System) version floorMinimum build — the lever for forcing an update deadline
Disk encryptionBitLocker/FileVault on
Secure boot / firmwareHealth-attestation signals on supported hardware
Defender / antivirusReal-time protection on, signatures current
Password / PINComplexity and lock timeout

Reference
The Grace Period — Warn Before You Block
Marking a device non-compliant the instant it drifts, and blocking it the same second, locks people out over a signature that is four hours stale. The grace period is the humane and operationally sane setting: the device is flagged non-compliant but keeps access for a defined window, during which the user is nudged to fix it before the block lands.
StageWhat the user sees
CompliantNothing — access as normal
Non-compliant, in graceA warning and a remediation step; access continues
Grace expiredCA blocks the protected resources until fixed
RemediatedNext check-in flips it back; access restores automatically
Set the grace period to the remediation you actually offer. One day is cruel if the fix is a feature update that takes a maintenance window; a week is negligent for a disabled-antivirus flag. Match the clock to how fast the specific issue can honestly be resolved.
🔗 Device Trust End to End — Enrolment → Compliance → CA → Access Endpoint • Compliance ▶
Flow
Four Links, and a Break in Any One Denies Access
"Only healthy, managed devices reach company data" sounds like one control. It is a chain of four, each owned by a different config surface, and a user locked out is almost always a broken link somewhere upstream of where they are complaining. Learning the chain in order is how you triage it in minutes instead of guessing.

1 Identity joinThe device has an identity (Entra join / registration)Never joined, or registration was cleaned up

Troubleshooting
Read the Chain Backwards From the Denial
The CA sign-in log is the single best triage tool: it names the policy that blocked, and the device state it saw. From there you walk upstream.
Symptom in the sign-in logLook upstream at
"device not compliant"Compliance policy — which setting failed, and is it in grace

📉 Reporting on Drift — Finding Devices That Quietly Stopped Complying Endpoint • Compliance ▶
Concept
The Dangerous State Is "Not Evaluated," Not "Non-Compliant"
A non-compliant device is a known problem the system is already acting on. The device that should worry you is the one that stopped checking in — it is not evaluated, so it is neither compliant nor blocked, just invisible. A fleet report that only counts compliant vs non-compliant hides its own blind spot. Report on the third bucket explicitly.
StateMeansAction
CompliantEvaluated, passingNone
Non-compliantEvaluated, failing a settingRemediate the named setting
Not evaluated / no graceHasn't reported — stale or fallen off management, so neither compliant nor blockedChase check-in; may need re-enrolment
In grace periodFailing but still inside its windowNudge before the window closes
Technique
Trend the Rate, Alert on the Slope
A single day's compliance percentage is noise. What tells you something broke is the change: a five-point drop overnight is almost always a policy edit or a bad update ring, not a hundred users independently misbehaving. Watch the trend and the last-check-in distribution, and treat a spike in "not evaluated" as an operational incident — it usually means an agent, an enrolment, or a network path stopped working for a whole segment at once.
Tie a sudden compliance drop to what you changed. The first question on a drift spike is "what deployed in the last 24 hours" — a new baseline, a tightened setting, or an update. Correlating drift with your own change log finds the cause faster than inspecting devices.
🪢 The Identity/Endpoint Seam — The Failure That Lands Both Teams on the Bridge Endpoint • Operations ▶
Concept

Modern access control is a joint venture the org charter rarely acknowledges: the identity team owns Conditional Access and the user/group targeting; the endpoint team owns enrolment and compliance. The device-trust chain runs straight across that seam, so an outage caused by one team's change surfaces as a symptom the other team gets paged for. "Users can't get mail" pulls in endpoint; the cause is an identity-side CA edit — or the reverse. The fix is rarely technical; it is knowing the seam exists and getting both teams on the bridge fast.

FileVault & Key Escrow — the Same Rule as BitLocker
FileVault is Apple's full-disk encryption, and the rule from BitLocker at Scale — Silent Enablement, Key Escrow & Recovery applies unchanged: enabling encryption is easy, and the only thing that matters is whether the recovery key escrowed. Supervision and the Work Profile — the Two Levers
Supervision on iOS unlocks the powerful restrictions — the ones that only exist for company-owned, ADE-enrolled devices; you cannot supervise a user's personal phone, by design. For the contractor or the employee who will not enrol a personal phone, you do not manage the device at all — you manage the app. App Protection Policies wrap the corporate apps so data cannot be copied out to personal apps, require a PIN to open them, and can wipe only the corporate data, all without the device ever being enrolled.
