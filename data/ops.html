Recovery Time Objective — Maximum acceptable time to restore a system after a disaster. "How fast must we recover?"

🔬 Digital Forensics Process 6-PHASE PROCESS ▶
Process — Source: CISSP + Net+ Cheat Sheets
Identification → Preservation → Collection → Examination → Analysis → Presentation
Digital forensics produces court-admissible evidence. Evidence must be relevant, complete, sufficient, and reliable. Chain of custody documents every person who handled evidence, when, and what they did.
1
Identification
Identify potential evidence sources: devices, logs, network captures, cloud data. First responder secures and documents the scene before anything is touched.
2
Preservation
Protect evidence from alteration (write blockers). Follow Order of Volatility: CPU registers/cache → RAM → swap → disk → remote logs → paper. Issue Legal Hold.
3
Collection
Create forensic image (bit-for-bit copy) using tools like dd, FTK Imager, EnCase. Hash the image (MD5/SHA-256) immediately for integrity verification. Never work on originals.
4
Examination
Extract relevant data from the forensic image: files, metadata, deleted files (unallocated space), slack space, registry hives, logs, browser history, memory dumps.
5
Analysis
Interpret extracted data to reconstruct events: timeline analysis, correlation with other evidence, identification of IOCs, attribution of actions to users/systems.
6
Presentation / Court
Produce forensics report documenting methodology, findings, and conclusions. Expert witness testimony must be clear to non-technical judges/jury. E-discovery for legal proceedings.

What a SOC Does
A Security Operations Center (SOC) is the team that watches the screens — like a building's security guards reviewing cameras 24/7. They notice odd activity, investigate, and respond before small problems become big ones.
ANALOGY
Logs = a Diary
Every device keeps logs: a timestamped diary of what happened (who logged in, what failed, what changed). When something goes wrong, the logs are the story you read back to find out how and when.

Monitoring tools raise alerts the way a smoke detector beeps. Some are real fires; many are burnt toast (false positives). A big part of the job is tuning the detector so it cries wolf less.

Mature teams assume an attacker will get in eventually, so they limit damage and keep tested backups. A backup you've never restored is just a hope — practice the recovery before you need it.

🔧Troubleshooting Like a ProA+ • Start Here▶
MINDSET
Calm, Curious, Methodical
Good troubleshooting isn’t magic or luck — it’s a repeatable method. Panic and random clicking make things worse; a calm, one-step-at-a-time approach fixes problems and teaches you something each time.
THE METHOD
CompTIA’s 7 Steps
The industry-standard loop: identify the problem, form a theory of the cause, test that theory, make a plan, fix it, verify it’s really solved (and prevention), then document what happened. Skipping ‘document’ is how the same fire gets fought twice.
FIRST QUESTIONS
Narrow It Down Fast
Start by shrinking the search: What changed recently? Does it affect one person or everyone? Can you reproduce it? ‘It worked yesterday’ plus ‘what changed’ solves a surprising share of problems.
CLASSIC WISDOM
Check the Simple Stuff First
Is it plugged in? Is it on the right network? Did you restart it? Seasoned techs aren’t being condescending — the boring, simple cause really is the answer most of the time. Rule it out before chasing the exotic.
StepIn Plain English
1. IdentifyGather symptoms; what exactly is wrong?
2. TheoryBest guess at the cause (simple first)
3. Test theoryProve or disprove the guess
4. PlanDecide the fix and any risk
5. ImplementApply the fix (one change at a time)
6. VerifyConfirm it’s solved + prevent recurrence
7. DocumentWrite it down for next time

FALSE POSITIVES
Alert Fatigue Is a Real Threat
When a SIEM generates 10,000 alerts per day, analysts tune out. Alert fatigue causes real attacks to be dismissed as noise. Good SOC work involves constantly tuning detection rules — raising thresholds for noisy rules, adding context (business hours, user role, geography), and building baselines for normal behavior.

CONTAINMENT STRATEGIES
Short-Term vs Long-Term
Short-term: immediate isolation — unplug network cable, disable account, null-route IP. Buy time without losing evidence.
Long-term: rebuild system from a known-good image, re-image endpoints, force password resets, revoke compromised certificates.
Key decision: preserve evidence vs stop the bleeding. If active data exfiltration is happening, containment wins. If already contained, preserve first.
CHAIN OF CUSTODY
Evidence Must Be Unimpeachable
If the incident leads to legal action or law enforcement, digital evidence must be collected and handled correctly. Document: who collected it, when, what state it was in, and how it was stored. Use write blockers for disk imaging. Hash every piece of evidence (MD5 + SHA-256) and verify hashes later. Mishandled evidence gets thrown out.
💾 Backup & Disaster Recovery — Surviving the Worst Case OPS • Critical ▶
THE 3-2-1 RULE
Three Copies, Two Media, One Off-Site
3 copies of your data (original + 2 backups)
2 different storage types (SSD + external drive, local + cloud)
1 copy off-site (cloud, different building, different region)
Why: ransomware encrypts local + network shares. Fire/flood destroys same-room copies. Off-site survives both. Modern extension: 3-2-1-1-0 (add 1 offline/air-gapped copy and 0 errors verified by testing).
BACKUP TYPES
Full vs Incremental vs Differential
TypeWhat It Backs UpBackup SpeedRestore Speed
FullEverythingSlowFast (one file)
IncrementalChanges since last backup of any typeFastSlow (full + all incrementals)
DifferentialChanges since last FULL backupMediumMedium (full + last differential)
RTO & RPO
Recovery Time and Data Loss Objectives
RTO (Recovery Time Objective) — how long can the business tolerate being down? An e-commerce site might have an RTO of 1 hour. A hospital might have an RTO of minutes.
RPO (Recovery Point Objective) — how much data can we afford to lose? If RPO is 4 hours, backups must run at least every 4 hours.
These drive backup strategy: low RTO/RPO requires continuous replication and hot standby; high RTO/RPO can use daily backups to tape.
TEST YOUR BACKUPS
An Untested Backup Is Not a Backup
Backups regularly fail silently (disk full, permission error, partial write). The only way to know a backup is good is to restore from it in a test environment. Restore tests should be:
• Scheduled (quarterly at minimum)
• Documented (how long did restore take? any errors?)
• Realistic (restore to isolated environment, not production)
Many organizations discover their backups are corrupted during an actual disaster — the worst time to find out.
RANSOMWARE RESPONSE
When Encryption Happens to You
If ransomware strikes:
1. Isolate affected systems immediately — disconnect from network
2. Don't pay if you have clean backups — payment doesn't guarantee decryption
3. Preserve evidence — image affected systems before wiping
4. Restore from known-good backup made before infection
5. Find the initial access before coming back online — if you restore without finding the entry point, you'll be re-infected
📡 Monitoring & Observability — Know Before Users Complain OPS • Foundation ▶
THREE PILLARS
Metrics · Logs · Traces
Metrics — numerical measurements over time: CPU %, request rate, error rate, latency percentiles (p50, p95, p99). Great for dashboards and alerting thresholds.
Logs — event records: what happened, when, and on which system. Needed to understand the WHY behind a metric spike.
Traces — record the journey of a single request through multiple services. Essential for distributed systems to find which service is causing latency.
KEY METRICS
The Four Golden Signals (Google SRE)
Latency — how long does a request take? Track P95/P99 not just average (average hides slow outliers).
Traffic — how many requests per second? Understand normal baseline so anomalies are visible.
Errors — what percentage of requests fail? Even 0.1% on 1M req/s is 1000 errors/sec.
Saturation — how full is your system? CPU, memory, disk, connections — approaching limits causes cascading failures.
ALERTING PHILOSOPHY
Alert on Symptoms, Not Causes
Alert when USERS are affected, not when internal metrics are interesting. "Error rate > 1% for 5 minutes" is a user-facing symptom. "CPU > 80%" is a cause that may or may not matter. Too many non-actionable alerts → alert fatigue → real alerts ignored. Every alert should have a runbook: what to check, what to do, who to escalate to.

DEVSECOPS
Security Shifted Left
DevSecOps integrates security checks into every stage of the CI/CD pipeline — not as a gate at the end ("is this ready to ship?") but as automated checks throughout:
• SAST (Static Application Security Testing) — analyze code for vulnerabilities
• DAST (Dynamic Application Security Testing) — attack the running app

"Shift left" = catch vulnerabilities when they're cheap to fix (in development), not expensive (in production).
☸️ Kubernetes — Container Orchestration at Scale OPS • Cloud Native ▶
WHAT IS KUBERNETES
Run, Scale, and Heal Containers Automatically
Kubernetes (k8s) is a container orchestration platform. You tell it "I want 5 replicas of my web container running at all times." k8s does the scheduling (which node to run it on), restarts failed containers, scales up/down based on load, and manages networking between services. Originally from Google; now the de-facto cloud standard.
CORE OBJECTS
Pod → Deployment → Service → Ingress
Pod — smallest deployable unit; one or more containers sharing a network namespace and storage. Ephemeral — can die and be replaced.
Deployment — manages N replicas of a Pod; handles rolling updates and rollbacks.
Service — stable network endpoint that load-balances traffic to pods (pods have dynamic IPs; Services don't change).
Ingress — HTTP/HTTPS routing: example.com/api → api-service, example.com/ → frontend-service.
ConfigMap / Secret — inject config and secrets into pods as env vars or files.
KUBECTL BASICS
The k8s CLI

WHEN TO USE K8S
It's Powerful But Complex
Kubernetes adds significant operational complexity. For a small startup with one app: Docker Compose or a single managed service (Heroku, Railway, Fly.io) is simpler and faster to operate. k8s shines when you have: many services, need to scale services independently, have a team to manage it, or require advanced deployment strategies (canary, blue/green). "Kubernetes because it's cool" is not a good reason.
🏗️ Infrastructure as Code — Servers You Define in Text Files OPS • Modern ▶
THE BIG IDEA
Stop Clicking, Start Declaring
The old way: log into a server, click through setup wizards, run commands manually, hope you remember what you did. The problem? It's not repeatable, not documented, and "works on my server" becomes a nightmare. Infrastructure as Code (IaC) means defining your servers, networks, and configs in version-controlled text files. Run the file → get identical infrastructure every time. This is the foundation of modern operations.

DECLARATIVE VS IMPERATIVE
Describe the Destination, Not the Route
Imperative: list every step ("install nginx, then edit config, then start service"). Declarative: describe the desired end state ("nginx should be installed and running"), and the tool figures out how to get there. Declarative is idempotent — running it 100 times produces the same result as running it once. Most modern IaC is declarative.

🎫 ITIL & Service Management — How IT Runs as a Business OPS • Process ▶
WHAT IS ITIL
A Framework for Delivering IT Services
ITIL (Information Technology Infrastructure Library) is the most widely adopted framework for IT Service Management (ITSM). It's a set of best practices for delivering IT as a service to a business — covering how you handle outages, changes, requests, and continuous improvement. You'll encounter ITIL terminology constantly in enterprise IT, especially on help desks and ops teams. Even if your company doesn't "do ITIL," they probably use its vocabulary.
INCIDENT VS PROBLEM VS CHANGE VS REQUEST
The Four Terms People Mix Up
TypeDefinitionGoalExample
IncidentUnplanned interruption or degradation of a serviceRestore service ASAP (even with a workaround)"Email is down"
ProblemThe underlying root cause of one or more incidentsFind & fix root cause permanently"Why does email keep going down? Bad disk."
ChangeAdding/modifying/removing anything that could affect servicesImplement safely with minimal risk"Upgrade the mail server"
Service RequestA user asking for something standard/pre-approvedFulfill efficiently"I need access to the shared drive"
Key distinction: an incident is "it's broken, fix it now." A problem is "why does it keep breaking?" You restore the incident fast (workaround), then investigate the problem to prevent recurrence.
INCIDENT PRIORITY
Priority = Impact × Urgency
Not every incident is equal. Priority determines what gets worked first. It's calculated from impact (how many people / how critical) and urgency (how fast it needs fixing).
PriorityTypical MeaningExample
P1 — CriticalMajor outage, business stoppedEntire company can't access core system

P3 — MediumLimited impact or workaround existsOne team's printer is broken

CHANGE MANAGEMENT
Why You Can't Just Push to Production
Most outages are self-inflicted — caused by changes. Change management adds guardrails so changes are reviewed, approved, scheduled, and reversible. The CAB (Change Advisory Board) reviews risky changes.

🎚️ SRE — Engineering Reliability with Data, Not Heroics OPS • Modern ▶
WHAT IS SRE
"What Happens When a Software Engineer Runs Operations"
Site Reliability Engineering (SRE), pioneered at Google, applies software-engineering thinking to operations. Instead of manually firefighting, SREs use code, automation, and data to make systems reliable at scale. The core insight: reliability is a feature you can measure and budget for — not an absolute. 100% reliability is the wrong target (it's impossibly expensive and users can't even tell).
ERROR BUDGETS
Reliability You Can Spend
If your SLO is 99.9% availability, then 0.1% unreliability is your error budget — about 43 minutes/month you're "allowed" to be down. This brilliantly resolves the eternal dev-vs-ops conflict: as long as you're within budget, ship features fast. Blow the budget? Freeze features and focus on reliability. It turns reliability into a shared, data-driven decision instead of an argument.

TOIL
The Enemy of Engineering
Toil is manual, repetitive, automatable work that scales linearly with growth and produces no lasting value — resetting passwords by hand, manually restarting services, copy-pasting between dashboards. SRE culture caps toil (often at ~50% of time) and invests the rest in automation and engineering that eliminates toil. Chaos engineering deliberately injects failures (kill a server, add latency, drop a dependency) into systems — ideally in production, carefully — to discover weaknesses before they cause real outages. Beginner PostgreSQL Administration – Database Ops 101
Core Concept
What Is a Database Server?
A database server stores data in structured tables and answers queries from applications. PostgreSQL (Postgres) is the most popular open-source relational database. As an ops person you are responsible for keeping it running, backed up, and fast.

Quick orientation:
• Cluster – one running Postgres instance (port 5432).
• Database – a namespace inside the cluster.
• Schema – a namespace inside a database (default: public).
• Table – rows & columns, like a spreadsheet.
• Role – a user or group (Postgres uses one object for both).
Daily Commands
psql – The Postgres CLI
psql is the interactive terminal for Postgres. Master these and you can do 80 % of admin tasks.
# Connect as the postgres superuser sudo -u postgres psql -- Inside psql (lines starting with -- are SQL comments) -- List all databases \l -- Connect to a specific database \c myapp_db -- List tables in current schema \dt -- Show table structure \d users -- Run a query SELECT id, email FROM users LIMIT 5; -- Show currently running queries SELECT pid, now() - query_start AS duration, query FROM pg_stat_activity WHERE state = 'active' ORDER BY duration DESC; -- Kill a stuck query (use pid from above) SELECT pg_terminate_backend(12345); -- Quit psql \q
Backup & Restore
pg_dump and pg_restore
You can't make someone make the right choice, yet you can pick up the pieces afterwards — a developer may drop a table by accident. Your job is to have a backup ready so you can restore it.
# Backup a single database to a compressed file pg_dump -U postgres -Fc myapp_db > myapp_db_$(date +%F).dump # Backup all databases (SQL text format) pg_dumpall -U postgres > all_databases_$(date +%F).sql # Restore from a compressed dump pg_restore -U postgres -d myapp_db --clean myapp_db_2026-06-01.dump # Restore from SQL text dump psql -U postgres < all_databases_2026-06-01.sql # Automate nightly backup via cron (runs at 2 AM daily) # Add to crontab with: crontab -e 0 2 * * * pg_dump -U postgres -Fc myapp_db > /backups/myapp_$(date +\%F).dump
Performance
VACUUM, ANALYZE, and Indexes
Postgres uses Multi-Version Concurrency Control (MVCC) — deleted rows are not immediately removed, they become "dead tuples." VACUUM reclaims that space. ANALYZE updates statistics so the query planner makes good choices.

Autovacuum handles this automatically in normal operation — never disable it.

Indexes speed up queries on large tables (like a book's index). Add one when a column appears frequently in WHERE clauses, but don't over-index — every index slows down INSERT/UPDATE.
-- Manual vacuum + analyze (safe to run any time) VACUUM ANALYZE users; -- Check table bloat (dead tuple ratio) SELECT relname, n_dead_tup, n_live_tup, round(n_dead_tup::numeric / nullif(n_live_tup,0) * 100, 2) AS dead_pct FROM pg_stat_user_tables ORDER BY dead_pct DESC NULLS LAST; -- Add an index on the email column CREATE INDEX CONCURRENTLY idx_users_email ON users(email); -- CONCURRENTLY = no table lock, safe on production -- Explain a query (show execution plan) EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'alice@example.com';
Beginner Kubernetes – Container Orchestration Fundamentals
Core Concept
Why Kubernetes Exists
Docker runs one container on one machine. When you need to run hundreds of containers across dozens of machines, you need an orchestrator. Kubernetes (K8s) handles:

• Scheduling — decides which machine runs which container.
• Self-healing — restarts crashed containers automatically.
• Scaling — adds/removes container replicas based on load.
• Rolling updates — deploys new versions with zero downtime.
• Service discovery — containers find each other by name, not IP.

"Not my circus, not my monkey" — the control plane (API server, etcd, scheduler) is managed for you on EKS/GKE/AKS. Your job is to manage your workloads, not the cluster control plane.
Key Objects
The K8s Object Hierarchy
Everything in Kubernetes is a YAML-defined object:

Pod — the smallest unit; one or more containers that share a network namespace. Pods are ephemeral — don't store state in them.

Deployment — manages a set of identical Pod replicas; handles rolling updates and rollbacks.

Service — a stable network endpoint (IP + DNS name) that load-balances across matching Pods.

ConfigMap / Secret — inject configuration or credentials into Pods without baking them into the image.

Namespace — a virtual cluster inside a cluster; used to separate teams or environments.

Beginner CI/CD Pipelines – From Commit to Production Automatically
Core Concept
What CI/CD Actually Means
Continuous Integration (CI) — every code change is automatically built and tested the moment it's pushed. Catches bugs within minutes instead of weeks.

Continuous Delivery (CD) — every change that passes CI is automatically packaged and ready to deploy (a human clicks "go").

Continuous Deployment — every change that passes CI is automatically deployed to production with no human in the loop.

The pipeline stages (typical order):
1. Checkout code → 2. Install dependencies → 3. Lint/static analysis → 4. Unit tests → 5. Build artifact (binary, container image) → 6. Integration tests → 7. Security scan → 8. Deploy to staging → 9. Smoke tests → 10. Deploy to production.

"Not my circus, not my monkey" — if your pipeline is red, do not merge more changes on top of it. Fix the pipeline first; a broken main branch blocks everyone.
GitHub Actions
A Real CI/CD Pipeline in YAML
GitHub Actions is one of the most common CI/CD tools — config lives in .github/workflows/*.yml right alongside your code.
# .github/workflows/ci.yml name: CI Pipeline on: push: branches: [main] pull_request: branches: [main] jobs: test: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - name: Set up Python uses: actions/setup-python@v5 with: python-version: "3.12" - name: Install dependencies run: pip install -r requirements.txt -r requirements-dev.txt - name: Lint run: ruff check . - name: Run tests with coverage run: pytest --cov=src --cov-report=xml --cov-fail-under=80 - name: Security scan run: | pip install bandit bandit -r src/ -ll build-and-push: needs: test # only runs if 'test' job passes runs-on: ubuntu-latest if: github.ref == 'refs/heads/main' steps: - uses: actions/checkout@v4 - name: Build container image run: docker build -t myapp:${{ github.sha }} . - name: Scan image run: trivy image --exit-code 1 --severity CRITICAL myapp:${{ github.sha }} - name: Push to registry run: | echo ${{ secrets.REGISTRY_TOKEN }} | docker login -u user --password-stdin docker push myapp:${{ github.sha }}
Deployment Strategies
How to Ship Without Breaking Things
How you roll out a new version matters as much as the code itself:

• Rolling update — replace instances one at a time; if health checks fail, stop and roll back. Default in Kubernetes.
• Blue-green deployment — run two identical environments ("blue" = current, "green" = new); switch traffic instantly; instant rollback by switching back.
• Canary release — send 5% of traffic to the new version, watch metrics, gradually increase to 100% (or roll back if errors spike).
• Feature flags — deploy code "dark" (disabled), then turn it on for specific users without a new deployment.

"Assume" makes an ass out of you and me — never assume a deploy "should be fine" because it worked in staging. Staging never perfectly mirrors production load, data, and integrations.
Failure Recovery
When the Pipeline Ships a Bad Release
You can't make someone make the right choice, yet you can pick up the pieces afterwards — a teammate's bad commit will reach production eventually. Your safety net matters more than prevention alone.

Build these into every pipeline:
• Automated rollback — if health checks fail post-deploy, automatically revert to the last known-good version.
• Deployment markers — send an event to your monitoring system on every deploy, so spikes can be correlated instantly: "errors started 90 seconds after deploy #4521."
• Fast rollback path — rolling back should take seconds, not the same time as a forward deploy.
• Post-incident review — every bad release gets a blameless writeup: what broke, why CI didn't catch it, what test or gate would have.
Beginner Web Server Hardening – nginx, Apache & TLS Done Right
Core Concept
The Default Config Is Not the Secure Config
Out of the box, web servers prioritise compatibility over security — they'll happily serve old TLS versions, leak version information, and allow risky HTTP methods. Hardening means deliberately tightening these defaults.

The five hardening layers:
1. TLS configuration — which protocol versions and ciphers are allowed.
2. HTTP security headers — instructions to the browser about how to treat your site.
3. Information disclosure — hide server version and technology stack from attackers.
4. Rate limiting — slow down brute-force and scraping attempts.
5. Certificate management — automated renewal so sites never go down from an expired cert (a surprisingly common self-inflicted outage).
nginx Hardening
A Hardened nginx Server Block
This configuration covers the essentials most security scanners and compliance checks look for.
# /etc/nginx/sites-available/example.com server { listen 443 ssl http2; server_name example.com; # ── TLS: only modern protocols and strong ciphers ── ssl_certificate /etc/letsencrypt/live/example.com/fullchain.pem; ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem; ssl_protocols TLSv1.2 TLSv1.3; # no SSLv3, TLSv1.0, TLSv1.1 ssl_ciphers HIGH:!aNULL:!MD5:!3DES; ssl_prefer_server_ciphers on; ssl_session_cache shared:SSL:10m; # ── Hide version info (reduces fingerprinting) ── server_tokens off; # ── Security headers ── add_header Strict-Transport-Security "max-age=63072000; includeSubDomains" always; add_header X-Frame-Options "SAMEORIGIN" always; add_header X-Content-Type-Options "nosniff" always; add_header Referrer-Policy "strict-origin-when-cross-origin" always; add_header Content-Security-Policy "default-src 'self'" always; # ── Rate limiting (defined in http{} block, applied here) ── limit_req zone=login_limit burst=5 nodelay; location / { proxy_pass http://127.0.0.1:8080; proxy_set_header Host $host; proxy_set_header X-Real-IP $remote_addr; } } # Redirect all plain HTTP to HTTPS server { listen 80; server_name example.com; return 301 https://$host$request_uri; } # In the http{} block — define the rate limit zone: # limit_req_zone $binary_remote_addr zone=login_limit:10m rate=5r/m;

A runbook is a step-by-step procedure for handling a specific operational situation — restarting a stuck service, failing over a database, rotating an expired certificate. The test of a good runbook isn't whether the author understands it; it's whether a half-asleep on-call engineer who has never touched this system can follow it correctly under pressure, at 3 AM, without calling anyone for help.

Hands-on

A short runbook excerpt, written the right way

# RUNBOOK: API gateway returning 503s

# TRIGGER: PagerDuty alert "gateway-503-rate-high" fires when error
# rate > 5% for 5 minutes straight.

# IMPACT: All customer-facing API traffic degraded. Treat as SEV-2.

# STEP 1 — confirm the alert is real, not a monitoring blip
curl -s -o /dev/null -w "%{http_code}\n" https://api.internal.example.com/healthz
# Expect: 200. If you see 503 here too, this is real — continue.

# STEP 2 — check whether it's one node or all of them
kubectl get pods -n gateway -o wide
# Look for pods stuck in CrashLoopBackOff or 0/1 Ready

# STEP 3 — restart only the unhealthy pods (NOT the whole deployment)
kubectl delete pod <pod-name> -n gateway
# Kubernetes will reschedule it automatically — this is non-destructive

# VERIFY — error rate back under 1% for 5 consecutive minutes
watch -n 10 'curl -s https://api.internal.example.com/metrics | grep error_rate'

# IF STILL FAILING after step 3 — STOP. Escalate to #platform-oncall.
# Do not attempt a full deployment restart without a second engineer present.

You can't make someone make the right choice...

The best operational teams plan for both the happy path and the moment a tired human deviates from it.

Capacity Planning – Answering "Will We Run Out of Room?" Before You Do

Concept

Capacity planning is forecasting, not firefighting

Capacity planning is the practice of looking at how a resource — disk space, bandwidth, server load, license seats — is being consumed over time, and projecting forward to answer "when will this become a problem, and what should we do about it before it does?" The opposite approach — waiting for an alert that says "disk 98% full" — turns a planning exercise into a 2 AM emergency. Good capacity planning quietly prevents most of the outages that bad capacity planning causes people to brag about firefighting.

Concept

The basic forecasting loop

StepWhat you're doingExample question it answers
1. Measure current usageEstablish a baseline — what does "normal" look like today?"We're using 620 GB of our 1 TB volume"
2. Track the trend over timeIs usage flat, growing steadily, or growing faster than before?"We've added about 15 GB per week for the last two months"
3. Project forwardAt the current rate, when do you cross the danger threshold?"At 15 GB/week, we hit 900 GB (our alert threshold) in about 19 weeks"
4. Plan the interventionWhat needs to happen before that date — and how long does it take to do it?"Provisioning additional storage takes 6 weeks of lead time, so we need to start the request now, not in week 18"

    (date(2026, 5, 4), 590),
    (date(2026, 5, 11), 605),
    (date(2026, 5, 18), 622),
    (date(2026, 5, 25), 636),
]

# Average weekly growth across the sampled period
days_elapsed = (history[-1][0] - history[0][0]).days
total_growth = history[-1][1] - history[0][1]
weekly_growth = total_growth / (days_elapsed / 7)

threshold_gb = 900
current_gb = history[-1][1]
weeks_remaining = (threshold_gb - current_gb) / weekly_growth
projected_date = history[-1][0] + timedelta(weeks=weeks_remaining)

print(f"Growing ~{weekly_growth:.1f} GB/week")
print(f"Projected to hit {threshold_gb} GB around {projected_date}")
print(f"That's roughly {weeks_remaining:.0f} weeks from the last measurement")

This is deliberately simple — straight-line ("linear") projection. Real-world usage often grows in bursts (a new product launch, a seasonal spike), so mature capacity planning layers in seasonality and known upcoming events on top of the trend line. But even this basic version turns a vague worry into a concrete date you can act on.

Mindset

Not my circus, not my monkey — until the monkey runs out of room

"That's the database team's disk, not mine" works fine right up until their volume fills up and takes down a service your team depends on. Capacity problems rarely stay neatly inside team boundaries — a full log partition can crash an application server, a maxed-out license pool can block an entire department's work. Part of good capacity planning is simply knowing which shared resources you depend on, even ones you don't directly own, so "not my circus" doesn't quietly become "my outage."

Beginner

Writing a Postmortem People Actually Learn From

Concept

A postmortem is a story about a system, not a trial of a person

A postmortem (or "post-incident review") is a written analysis of what happened during an outage or incident, why it happened, and what will change as a result. The single most important design decision in any postmortem process is whether it's blameless — focused on "what conditions made this mistake possible and likely?" rather than "who do we blame for this?" Get that one decision right, and people will tell you the truth about what happened. Get it wrong, and every future postmortem will quietly omit the details that actually mattered.

Concept

The shape of a postmortem that actually gets read

SectionWhat it answersCommon mistake to avoid
SummaryWhat happened, in 3-4 sentences a busy executive could read in 20 secondsBurying the headline under technical preamble nobody reads first
ImpactWho was affected, for how long, and how badly — with real numbersVague language like "some users experienced issues" instead of "approximately 4,200 users over 38 minutes"
TimelineWhat happened, in order, with timestamps — including detection and responseStarting the timeline at "the fix" instead of at the first sign something was wrong
Root cause(s)Why it happened — usually more than one contributing factor, not a single villainStopping at "a bad config was deployed" instead of asking "why was it possible to deploy that config unreviewed?"
Action itemsSpecific, owned, dated changes that reduce the chance of recurrenceVague commitments like "we'll be more careful" — that's not an action item, it's a hope
Hands-on

The "five whys" — finding the real root cause

# A simple technique for digging past the surface-level explanation.
# Keep asking "why" until you reach something you can actually fix.

Problem: The payment service was down for 40 minutes.

Why #1: Why was it down?
   -> The service crashed when it ran out of memory.

Why #2: Why did it run out of memory?
   -> A new code path loaded an entire customer table into memory at once.

Why #3: Why did that code path do that?
   -> The developer tested only against a small sample database in staging.

Why #4: Why didn't testing catch this before production?
   -> Staging databases aren't seeded with production-scale data volumes.

Why #5: Why isn't that part of the standard testing process?
   -> There's no documented requirement for load-realistic staging data.

# Notice where this ended up: not "the developer made a mistake"
# (Why #1-3), but "our process doesn't ensure realistic testing
# conditions" (Why #5) — a SYSTEM problem with a fixable solution,
# not a PERSON problem with only blame to offer.
Mindset

Not my circus, not my monkey — except blameless culture is everyone's circus

It's easy to think "writing good postmortems is the SRE team's job" — but a blameless culture is built or destroyed by everyone in the room, in the moment someone says "well, obviously they should have known better." One unkind comment in a review meeting can undo months of careful culture-building, and it teaches everyone present — not just the person being criticized — that honesty here has a cost. Protecting that culture, even in a meeting that isn't "yours," is part of keeping the whole system honest enough to actually improve.

📬 Message Queues & Event-Driven Architecture Architecture ▶
Concept
Decouple With a Buffer in the Middle
When service A calls service B directly, A waits for B and breaks if B is down. A message queue puts a durable buffer between them: A drops a message and moves on; B picks it up when ready. This decouples producers from consumers — they can scale, fail, and deploy independently. It's the backbone of event-driven systems, where components react to things that happened rather than calling each other in lockstep.
Reference
Queue vs Pub/Sub & Key Terms
▸ TWO MESSAGING SHAPES
PatternDeliveryExample
Queue (point-to-point)Each message goes to one consumer in a pool — spreads workTask/job processing (RabbitMQ, SQS)
Pub/Sub (topic)Each message goes to every subscriber — fan-outEvent broadcasting (Kafka, SNS, Redis)
▸ VOCABULARY
TermMeaning
ProducerPublishes messages
ConsumerReads and processes them
BrokerThe queue/log system in the middle (Kafka, RabbitMQ)
AckConsumer confirms "done" so the broker can drop the message
Dead-letter queueWhere messages go after repeated processing failures
BackpressureThe queue absorbs bursts so a slow consumer isn't overwhelmed
Delivery
Guarantees & Idempotence
Distributed messaging can't cheaply promise "exactly once," so you pick a guarantee and design around it:
GuaranteeMeaning
At-most-onceFast, but a message can be lost. Fine for disposable telemetry.
At-least-onceNever lost, but may be redelivered. The common default.
Exactly-onceIdeal but expensive/limited — usually emulated via dedup.
Because at-least-once means duplicates happen, make consumers idempotent — processing the same message twice has the same effect as once (e.g. key writes on a unique message ID). This is the single most important habit in event-driven systems.
Trade-offs
What You Gain and Pay
Detail
Gain: resilienceA consumer can crash or deploy; messages wait in the queue.
Gain: elastic scaleAdd consumers to drain a backlog faster; smooth out traffic spikes.
Gain: decouplingProducers don't know or care who consumes — add new consumers freely.
Cost: complexityAnother system to run/monitor; harder to trace a request end-to-end.
Cost: eventual consistencyWork happens asynchronously — the result isn't ready the instant you publish.
⚡ Caching Strategies — From App to CDN Performance ▶
Concept
Store the Answer, Skip the Work
A cache keeps a copy of expensive-to-compute or slow-to-fetch data somewhere fast, so repeated requests don't redo the work. Done right, it's the single biggest performance lever you have. The catch is the famous one: "There are only two hard things in computer science — cache invalidation and naming things." A stale cache serves wrong data; the art is knowing when to trust the copy and when to refresh it.
Reference
Where Caches Live (the Layers)
LayerExampleCaches
BrowserHTTP cacheStatic assets on the user's device
CDN / edgeCloudflare, CloudFrontContent served near the user, globally
App / in-memoryRedis, MemcachedQuery results, sessions, computed values
DatabaseQuery & buffer cacheHot pages & plans in RAM
The closer to the user a cache sits, the faster and cheaper the hit — but the harder it is to invalidate. Each layer is a trade of speed vs freshness.
Patterns
Read & Write Strategies
PatternHow It Works
Cache-aside (lazy)App checks cache; on a miss, reads the DB and populates the cache. Most common.
Read-throughThe cache itself loads from the DB on a miss — app only talks to the cache.
Write-throughWrites go to cache and DB together — always fresh, slightly slower writes.
Write-backWrite to cache now, flush to DB later — fast, but risks loss on crash.
▸ CACHE-ASIDE IN CODE
function getUser(id) {
  let u = cache.get(`user:${id}`);
  if (u) return u;                 // hit
  u = db.query("SELECT ...", id);  // miss → load
  cache.set(`user:${id}`, u, { ttl: 300 }); // store 5 min
  return u;
}
Invalidation
Keeping Copies Honest
TechniqueWhat It Does
TTL (expiry)Data auto-expires after N seconds. Simple; tolerates brief staleness.
Explicit purgeDelete the key when the source changes. Precise; needs write-path hooks.
Versioned keysBake a version/hash into the key (user:42:v3); old keys just age out.
Cache-Control headersFor HTTP/CDN: max-age, no-store, ETag for revalidation.
Watch for the thundering herd / stampede: when a hot key expires, thousands of requests miss at once and hammer the DB. Mitigate with a short lock, request coalescing, or staggered TTLs.
🐒 Chaos Engineering — Breaking Things on Purpose Reliability ▶
Concept
Find the Weakness Before It Finds You
Chaos engineering is the discipline of deliberately injecting failure into a system — killing servers, adding network latency, exhausting disk — to discover how it actually behaves under stress, rather than how you hope it does. The insight: distributed systems fail in ways no one predicted, so you'd rather trigger those failures in a controlled experiment (business hours, watching closely) than at 3 a.m. during a real outage. Netflix pioneered it with Chaos Monkey, which randomly kills production instances to force teams to build resilience in.
Method
Running an Experiment
StepWhat You Do
1. Steady stateDefine a measurable "healthy" metric (e.g. checkout success rate > 99%).
2. Hypothesis"If we kill one payment node, checkout success stays above 99%."
3. Blast radiusStart tiny — one instance, small % of traffic — to limit harm.
4. Inject & observeIntroduce the failure; watch the metric and your alerts.
5. Learn & fixIf the hypothesis breaks, you found a real weakness — fix it, then re-run.
Always have an abort switch to stop the experiment instantly, and never run one you're confident will cause a major outage — the goal is learning, not self-inflicted downtime.
Reference
Common Failures to Inject
FailureTests Whether…
Kill an instanceLoad balancing & auto-healing actually replace it
Add network latencyTimeouts & retries are tuned; slow ≠ down
Drop a dependencyCircuit breakers & fallbacks kick in (graceful degradation)
Fill the disk / CPUResource limits & alerts fire before a crash
Zone/region outageFailover to another region works end-to-end
Tooling: Chaos Monkey / Simian Army, Gremlin, LitmusChaos and Chaos Mesh (Kubernetes).
Prerequisites
Don't Start Here
Chaos engineering pays off only once you already have solid monitoring and alerting (or you won't see what breaks) and the basics of resilience — retries, timeouts, health checks, redundancy. Injecting failure into a system you can't observe just causes an outage with no lesson. It's an advanced reliability practice that builds on observability and SRE fundamentals, not a starting point.

🎚️ Deployment Strategies — Blue-Green, Canary & Rolling Reliability ▶

🔺 CAP Theorem & Consistency Models Architecture ▶
Concept
Pick Two — the Fundamental Trade-off
The CAP theorem says a distributed data store can guarantee at most two of three properties: Consistency (every read sees the latest write), Availability (every request gets a response), and Partition tolerance (it keeps working when the network splits). Since networks will partition, partition tolerance isn't optional in practice — so the real choice, during a partition, is consistency vs availability.
Reference
The Three Letters
LetterGuarantee
ConsistencyAll nodes return the same, most-recent data. A read never sees stale values.
AvailabilityEvery request gets a (non-error) response, even if some nodes are down.
Partition toleranceThe system keeps operating even when nodes can't talk to each other.
Note: CAP's "Consistency" is stricter than ACID's — it means linearizability (one up-to-date copy), not "constraints hold." Different word, different guarantee.
In Practice
CP vs AP — What You Choose During a Split
CP (consistency)AP (availability)
During a partitionRefuse/blocks writes to stay correctKeep serving, reconcile later
Read might beAlways currentStale for a moment
Good forBanking, inventory, bookingsFeeds, carts, social, DNS
Examplesetcd, ZooKeeper, HBaseCassandra, DynamoDB, Riak
Most real systems aren't purely one or the other — they tune per-operation (a shopping cart is AP; the final checkout is CP).
Beyond CAP
Consistency Is a Spectrum
ModelPromise
Strong / linearizableReads always see the latest write — as if one copy existed.
EventualGiven no new writes, all replicas eventually converge. Cheap & available.
Read-your-writesYou always see your own updates (even if others lag).
CausalRelated events are seen in order; unrelated ones may not be.
A related lens, PACELC, extends CAP: even when there's no partition (Else), you still trade Latency vs Consistency — stronger guarantees cost round-trips. There's no free lunch in distributed data.
🕸️ Service Mesh — Istio, Linkerd & the Sidecar Pattern Cloud Native ▶
Concept

When one app becomes 50 microservices, every service needs retries, timeouts, TLS, load balancing, and metrics for its calls to the others. 🧵 Distributed Tracing & OpenTelemetry Observability ▶
Concept
Following One Request Across Many Services
In a microservice system, a single user click might touch a gateway, an auth service, three back-ends, and a database. When it's slow, which hop is to blame? Logs from each service in isolation can't tell you. Distributed tracing stitches the whole journey together: it tags the request with an ID that travels with it, so you can see the end-to-end path and exactly where the time went.
Reference

You instrument your code once with the OTel SDK (much of it automatic for popular frameworks), and it exports to whatever backend you choose — Jaeger, Tempo, Zipkin, or a commercial tool — with no code change to switch. 🔃 GitOps — Git as the Source of Truth for Operations DevOps ▶
Concept
If It's Not in Git, It Doesn't Exist
GitOps applies the software workflow you already know — pull requests, review, merge, history — to infrastructure and deployments. The desired state of your whole system lives in a Git repo as declarative config; an automated agent continuously makes the real cluster match it. You never kubectl apply by hand — you change a file, open a PR, and merging is the deploy.
How It Works
Push vs Pull Deployment
Traditional CI pushes changes into the cluster (the pipeline has cluster credentials and runs apply). GitOps flips it: an agent inside the cluster pulls the desired state from Git and reconciles continuously.
StepWhat Happens
1. DeclareDesired state (Kubernetes manifests, Helm, Terraform) is committed to Git.
2. ObserveAn in-cluster agent (Argo CD, Flux) watches the repo.
3. DiffIt compares Git (desired) against the live cluster (actual).
4. ReconcileIt applies changes to close the gap — automatically and continuously.
Reference

BenefitDetail

A Phishing Playbook
# Trigger: a user reports a suspicious email
1. Extract URLs, attachments, sender from the email
2. Enrich → check URL/hash against threat intel (VirusTotal, etc.)
3. IF malicious:
     - Search mail server for other copies → quarantine them
     - Check who else clicked (proxy/EDR logs)
     - Reset creds / isolate any host that visited the link
4. Open a case, attach all evidence, notify the analyst
5. ELSE: close as false positive with a note
Steps 1–2 and 5 run fully automatically; the risky containment in step 3 can require a human approval gate — a common "automate enrichment, gate the destructive action" pattern.

Detail
SIEM findsCollects & correlates logs to detect and alert.
SOAR actsTakes those alerts and responds via playbooks. They're complementary — SIEM feeds SOAR.
PayoffLower MTTR (mean time to respond), consistent handling, less analyst burnout.

📈 Load & Performance Testing Reliability ▶
Concept
Find the Breaking Point Before Your Users Do
A system that's fast for one user can collapse for ten thousand. Performance testing simulates realistic (and unrealistic) traffic to answer questions you can't answer by clicking around: How many users can we handle? Where's the bottleneck — CPU, database, a single service? What happens at 2× expected peak? You'd much rather learn this in a test than during a product launch or a viral moment.
Reference
Types of Test
TestQuestion It Answers
LoadHow does it behave at expected peak traffic?
StressWhere does it break, and how? (Push past capacity.)
SpikeCan it survive a sudden traffic surge (a launch, a link going viral)?
Soak / enduranceDoes it degrade over hours/days? (Catches memory leaks, resource exhaustion.)
ScalabilityDoes adding servers actually increase throughput linearly?
Metrics
Measure Percentiles, Not Averages
The classic mistake is reporting average latency. Averages hide pain: if 99% of requests are 50 ms but 1% take 5 seconds, the average looks fine while your worst-affected users suffer. Report percentiles.
MetricMeaning
ThroughputRequests/sec the system handles (RPS).
Latency p50 / p95 / p99The value below which 50/95/99% of requests fall. p99 = your unluckiest 1%.
Error rate% of failed requests — watch it climb as load rises.
SaturationHow full the resources are (CPU, memory, connections) — the leading indicator of trouble.
Practice
Doing It Well
GuidelineWhy
Test like productionRealistic data volumes and traffic mix — a test on an empty DB lies.
Ramp up graduallyIncrease load in steps to see where metrics bend, not just where they snap.
Watch the whole stackCorrelate the test with server metrics/traces to find which component is the bottleneck.
Mind the environmentA scaled-down staging env gives relative, not absolute, numbers. Note the difference.
Toolsk6, JMeter, Gatling, Locust generate the traffic; pair with your observability stack.
♾️ What DevOps Actually Is — Culture Over Tools DevOps ▶
Concept
Breaking the Wall Between Dev and Ops
DevOps isn't a job title or a toolchain — it's a culture that removes the traditional wall between developers (who want to ship change) and operations (who want stability). The mantra is "you build it, you run it": the team that writes the code also operates it, so quality and reliability become everyone's job, not a handoff. Tools (CI/CD, IaC, containers) enable it, but adopting them without the culture just automates the old dysfunction faster.

🔁 The Three Ways — Flow, Feedback, Learning DevOps ▶
Concept
The Principles Behind DevOps (The DevOps Handbook)
The Three Ways are the underlying principles all DevOps practices derive from — a useful lens for judging why a practice helps.
WayPrinciplePractices
1. FlowSpeed work left→right (dev→prod)Small batches, CI/CD, limit WIP, remove bottlenecks
2. FeedbackFast signal right→leftMonitoring, automated tests, alerting, stop-the-line on failure
3. LearningContinual experimentationBlameless postmortems, chaos drills, psychological safety
Flow gets change out fast; feedback catches problems fast; learning makes the system better over time. Skip feedback and you ship bugs faster; skip learning and you repeat incidents.

The DORA (DevOps Research & Assessment) research found four metrics that correlate with high-performing organizations. Crucially, speed and stability rise together — elite teams deploy more often and break less. If you measure one thing about delivery, measure these.

🗺️ Value Stream Mapping — Find the Bottleneck DevOps ▶
Concept
Where Does the Time Actually Go?
A value stream map traces every step from idea to production, recording for each: process time (actual work) vs wait time (queued, waiting for approval/review/ environment). The revelation is almost always that waiting dwarfs working — a code change might take 2 hours to write and 2 weeks to ship, stuck in queues. You improve flow by attacking the biggest wait, not by making developers type faster.
%C/A (percent complete & accurate) at each step reveals rework loops — if QA sends 40% back, that handoff is your real problem. Map it, find the fattest wait/rework, fix that, remap. It's the Lean tool DevOps borrowed to make "optimize flow" concrete.
🛝 Platform Engineering & the Internal Developer Platform DevOps ▶
Concept
Paving a Golden Path So Every Team Doesn't Reinvent It
"You build it, you run it" can overload product teams with infra complexity — Kubernetes, pipelines, secrets, observability, all per team. Platform engineering answers this by building an Internal Developer Platform (IDP): a self-service layer that packages the infra into golden paths, so a developer can provision a service, database, and pipeline with a form or a CLI command — without becoming a cloud expert.
PrincipleDetail
Self-serviceDevelopers get what they need without filing tickets
Golden pathsPaved, opinionated defaults that are easy to follow and secure by default
Product mindsetThe platform team treats developers as customers (adoption, not mandate)
Not a rename of opsIt's a product, not a gatekeeper — paved roads, not roadblocks
Tools in the space: Backstage (developer portal), Crossplane/Terraform (provisioning), Port/Humanitec (IDP orchestration).
🏭 CI/CD Pipeline Design — Stages, Gates & Artifacts DevOps ▶
Concept
The Assembly Line From Commit to Production
A pipeline runs a series of stages on every change, each a quality gate that must pass before the next. Build once, produce an immutable artifact, and promote that same artifact through environments — never rebuild per stage, or you're testing something different than you ship.
StageGate
BuildCompiles; produces the artifact (jar, image)
TestUnit + integration pass; coverage threshold
ScanSAST/SCA/secrets clean (fail on high sev)
Deploy → stagingSmoke/e2e tests green
Deploy → prodManual approval or automated canary
CI = integrate + test every change automatically. CD = that artifact is always deployable (Continuous Delivery) or actually auto-deployed (Continuous Deployment). Keep pipelines fast — a 40-minute pipeline kills the feedback loop.
🎬 GitHub Actions — Workflows, Jobs & Secrets DevOps ▶
How-To
CI/CD Built Into Your Repo
GitHub Actions runs YAML workflows in .github/workflows/ triggered by events (push, PR, schedule). A workflow has jobs (run in parallel by default) made of steps (shell commands or reusable actions). 
name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix: { node: [18, 20] }   # test on multiple versions
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '${{ matrix.node }}' }
      - run: npm ci && npm test
      - run: deploy.sh
        env: { TOKEN: '${{ secrets.DEPLOY_TOKEN }}' }
ConceptDetail
MatrixRun the job across a combination of versions/OSes
Secrets${{ secrets.X }} — never hard-code creds
Reusable/compositeFactor shared steps into called workflows/actions
OIDCAssume a cloud role with no stored keys (ties to IAM)

🚦 Progressive Delivery — Flags + Canary in the Pipeline DevOps ▶
Concept
Release ≠ Deploy
Progressive delivery separates deploy (code is on the servers) from release (users see it), and ramps exposure gradually so a bad change hits few people. It stitches together patterns you already know into the pipeline.
TechniqueRole
Feature flagsShip code dark; toggle on for cohorts at runtime
CanaryRoute 1% → 10% → 100% while watching metrics
Blue-greenInstant switch + instant rollback
Automated rollbackBad canary metrics → pipeline reverts automatically
Tools: LaunchDarkly/Unleash/Flagsmith (flags), Argo Rollouts/Flagger (automated canary on Kubernetes). This is how elite teams deploy dozens of times a day with a low change-failure rate — the two DORA goals reconciled.
