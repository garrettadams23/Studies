🤝 TCP vs UDP — Transport Layer NETWORK+ ▶
Reference — RFC 793 (TCP) · RFC 768 (UDP)
Connection Types · 3-Way Handshake · Flags · Use Cases
TCP — connection-oriented, reliable, ordered, error-checked. UDP — connectionless, low-overhead, best-effort. Choose based on need for reliability vs speed.
▸ COMPARISON
Feature TCP UDP
Connection 3-way handshake (SYN→SYN-ACK→ACK) None — send and forget
Reliability ACK, retransmission, ordering No guarantees
Speed Slower (overhead) Faster (low overhead)
Header size 20–60 bytes 8 bytes
Flow control Yes (sliding window) No
Use cases HTTP, HTTPS, FTP, SSH, SMTP, databases DNS, VoIP, video streaming, DHCP, gaming

NMAP — Scan Flags, Responses & Common Options
Nmap is the de-facto tool for network discovery and port scanning. Use nmap <SCAN> <TARGET> syntax. Requires root/administrator for raw socket scans (SYN, FIN, XMAS, etc.).
▸ SCAN TYPES
Flag Scan Type Open Response Closed Response Notes
-sT TCP Connect SYN/ACK RST/ACK Full 3-way handshake; logged by target
-sS SYN (Stealth) SYN/ACK RST/ACK Half-open; doesn't complete handshake; less logged
-sF FIN No response RST Works on Linux/Unix; bypasses some firewalls
-sX XMAS Tree No response RST Sets FIN+URG+PSH flags; binary 00101001
-sN NULL No response Varies by OS No flags set; designed for Linux/Unix
-sA ACK RST No response Maps firewall rules; determines filtered/unfiltered
-sI IDLE (Zombie) SYN/ACK RST/ACK Uses spoofed IP; maximum stealth scan
-sU UDP UDP response ICMP unreachable Slower; needed for DNS/DHCP/SNMP discovery
-sn Ping Sweep — — Host discovery only; no port scan
▸ USEFUL NMAP OPTIONS
# Speed / Timing: -T0 (paranoid) → -T5 (insane) nmap -T4 -A 10.5.23.0/24 # Aggressive: OS detect + version + scripts nmap -sS -p 22,80,443 10.5.23.1 # SYN scan specific ports nmap -sV --top-ports 100 target # Version detection on top 100 ports nmap -sC -sV target # Default scripts + version detection nmap -n -Pn -p- target # All 65535 ports, skip DNS/ping nmap --script vuln target # Run vulnerability scripts nmap --script "vuln and safe" target # Safe vuln scripts only nmap -oX scan.xml target # XML output for import to tools nmap -oN scan.txt target # Normal text output nmap -6 target # IPv6 scan

BIG IDEA
What Is a Network?
A network is just two or more computers that can talk to each other. Your home Wi-Fi is a small network; the Internet is the giant network that connects all the small ones together. If computers are houses, the network is the system of roads between them.
ANALOGY
IP Address = Mailing Address
Every device on a network has an IP address (e.g., 192.168.1.10) so data knows where to go — exactly like a street address tells the mail carrier which house. No address, no delivery.
ANALOGY
Packets = Envelopes
Big files are chopped into small chunks called packets. Each packet is an envelope with a from-address, a to-address, and a piece of the message. They travel separately and get reassembled at the other end.
ANALOGY
Ports = Apartment Numbers
One device (one IP) runs many programs at once. A port number says which program the data is for — like an apartment number after the street address. Web pages use port 80/443, email and other services use their own.
ROLES
Client vs. Server
The client asks (your phone opening a website); the server answers (the computer that stores that website). Most of what you do online is a polite back-and-forth of requests and responses.
HARDWARE
Router vs. Switch
A switch connects devices inside one network (like hallways in a building). A router connects different networks together and finds the path between them (like roads between cities). Your home box is usually both in one.
ANALOGY
DNS = The Phonebook
Humans remember names (google.com); computers need numbers (an IP). DNS is the phonebook that looks up the name and returns the number, automatically, every time you click a link.

📖 DNS — The Internet's Phone Book NET • Start Here ›
THE PROBLEM DNS SOLVES
Humans Hate Numbers
Computers talk to each other using IP addresses like 142.250.80.46. Humans want to type google.com. DNS (Domain Name System) translates names into numbers — like a phone book that covers the whole internet.
THE DNS LOOKUP JOURNEY
8 Steps From Name to IP
1. You type google.com in your browser.
2. Browser checks its own cache. If found → done.
3. OS checks its cache. If found → done.
4. OS asks your recursive resolver (your ISP or 8.8.8.8).
5. Resolver asks a root nameserver (13 clusters worldwide) — "who handles .com?"
6. Root points to the .com TLD nameserver (Verisign).
7. TLD server points to Google's authoritative nameserver.
8. Authoritative server returns the IP. Resolver caches it and gives it to you.

TTL
Time to Live — DNS Caching Timer
Every DNS record has a TTL (Time To Live) in seconds. After TTL expires, resolvers re-query for fresh results. Low TTL = fast changes but more queries. High TTL = slow propagation but less load. When migrating a website, lower the TTL 24 hours before the switch.
🔢 DHCP — How Devices Get Their IP Address NET • Foundation ›
DORA PROCESS
Discover → Offer → Request → Acknowledge
Discover — new device broadcasts "I need an IP!" to 255.255.255.255.
Offer — DHCP server says "How about 192.168.1.25? Here's a lease offer."
Request — client says "Yes, I'll take 192.168.1.25" (broadcast, so other servers know).
Acknowledge — server confirms: "192.168.1.25 is yours for 24 hours. Here's gateway and DNS too."
WHAT DHCP HANDS OUT
More Than Just an IP
A DHCP lease typically includes:
• IP address — unique on the local network
• Subnet mask — defines network boundary (e.g., 255.255.255.0)
• Default gateway — the router's IP (traffic leaving the network goes here)
• DNS server(s) — where to resolve names
• Lease duration — how long before re-requesting
STATIC vs DYNAMIC
Manual vs Automatic Assignment
Dynamic — DHCP assigns from a pool; good for laptops and phones. IP may change on reconnect.
Static — manually set; never changes. Required for servers, printers, network gear (you don't want DNS records breaking because the server got a new IP).
DHCP Reservation — best of both worlds: DHCP assigns based on MAC address, so the device always gets the same IP automatically.
TROUBLESHOOTING
When DHCP Fails — APIPA
If a device can't reach a DHCP server, Windows auto-assigns an APIPA address: 169.254.x.x. This is a red flag — the device only has link-local connectivity and cannot reach the internet. Check: cable unplugged? DHCP server down? VLAN misconfigured?

🔀 Switching & VLANs — Dividing Your Network Logically NET • Foundation ›
SWITCH vs HUB vs ROUTER
Three Different Devices, Three Layers
Hub — Layer 1; dumb repeater. Sends every frame to every port. Creates collisions. Legacy/obsolete.
Switch — Layer 2; intelligent. Learns which MAC addresses are on which ports using a MAC address table. Sends frames only to the correct port. Creates collision domains per port.
Router — Layer 3; connects different networks. Uses IP addresses and routing tables to forward packets between subnets and out to the internet.
HOW A SWITCH WORKS
MAC Address Table Learning
1. Frame arrives with source MAC AA:BB on port 1 → switch records AA:BB → Port 1 in table.
2. Destination MAC CC:DD — not in table yet → switch floods to all ports except source.
3. Device CC:DD responds → its MAC gets recorded.
4. Next frame to CC:DD → switch delivers it only to the correct port.
This is why switches are efficient — after learning, minimal unnecessary traffic.
VLANS
Virtual LANs — Logical Network Segmentation
A VLAN divides one physical switch into multiple logical networks. Devices in different VLANs cannot communicate directly even if they're plugged into the same switch — they need a router (Layer 3) to cross VLAN boundaries. Benefits:
• Security: production servers on VLAN 10, guest WiFi on VLAN 99 — guests can't see servers
• Performance: reduce broadcast domain size
• Organization: group devices by function, not location
TRUNK vs ACCESS PORTS
Single VLAN vs Multiple VLANs
Access port — carries traffic for exactly ONE VLAN. Used for end devices (PCs, printers). Device doesn't know it's on a VLAN.
Trunk port — carries traffic for MULTIPLE VLANs simultaneously. Used between switches, or switch-to-router. Uses 802.1Q tags to label which VLAN each frame belongs to.

STATIC vs DYNAMIC ROUTING
Manual Routes vs Self-Learning
Static routes — an admin manually configures each route. Simple, predictable, no overhead. Works for small networks. Fails when the network changes (adding a link, a failure) because you have to manually update every router.
Dynamic routing protocols — routers talk to each other and automatically discover routes. Self-healing when links fail. Required for large networks.

BGP
The Protocol That Runs the Internet
BGP (Border Gateway Protocol) is used between ISPs and large organizations to exchange routing information across the internet. Every major network has an ASN (Autonomous System Number). BGP is policy-driven — companies can influence which paths their traffic takes. A BGP misconfiguration can accidentally route the internet's traffic through your network (BGP hijacking).
DEFAULT ROUTE
The Fallback Route (0.0.0.0/0)
The default route (0.0.0.0/0 or ::/0) matches ANY destination. It's the "if nothing else matches, send it here" rule — usually pointing to the upstream router or internet gateway. Every end device has a default gateway for this reason.
🧱 Firewalls — The Network's Bouncer NET • Foundation ›
WHAT A FIREWALL DOES
Permit or Deny Based on Rules
A firewall inspects network traffic and decides whether to allow or block it based on rules. Think of it as a bouncer with a list: traffic that matches an allow rule gets in; everything else is dropped or rejected. The implicit deny rule: if nothing matches, deny.
FIREWALL TYPES
Packet Filter → Stateful → NGFW
Packet filter (L3/L4) — examines individual packets: source/dest IP, port, protocol. No context (doesn't know if it's a new connection or response). Fast but dumb.
Stateful inspection — tracks connection state. Knows if a packet is part of an established session. Much smarter — allows response traffic automatically.
NGFW (Next-Gen Firewall) — adds application awareness (block YouTube regardless of port), IPS, deep packet inspection, user identity, SSL inspection. Most enterprise firewalls today.

DMZ
De-Militarized Zone — Public-Facing Servers
A DMZ is a network segment between the internet and your internal network. Public-facing servers (web servers, mail servers) go in the DMZ. If they're compromised, the attacker is in the DMZ — not directly on your internal network. Two firewalls: one between internet and DMZ, another between DMZ and internal. Defense in depth.
⚖️ Load Balancers & High Availability — Never Go Down NET • Intermediate ›
THE PROBLEM
One Server = Single Point of Failure
If your entire service runs on one server and it crashes, everyone is down. High availability (HA) architectures spread load across multiple servers so that if one fails, others continue serving traffic seamlessly. HA goal: no single component failure takes down the service.
LOAD BALANCER
Distributes Traffic Across Backend Servers
A load balancer sits in front of your servers and routes each incoming request to one of the backends. Algorithms:
Round-robin — server 1, server 2, server 3, server 1… Even distribution.
Least connections — sends to whichever server has the fewest active connections.
IP hash — same client IP always goes to the same server (sticky sessions).
Weighted — big server gets more traffic than small server.
HEALTH CHECKS
Automatically Remove Failing Servers
A load balancer periodically pings each backend (HTTP GET /health, TCP connect, etc.). If a backend fails N consecutive checks, it's removed from the pool. No human intervention needed — traffic automatically shifts to healthy servers. When it recovers, it re-enters the pool.

🌐 IPv6 — The Internet's Upgrade NET • Essential ›
WHY IPv6
IPv4 Ran Out of Addresses
IPv4 has 4.3 billion addresses. That sounds like a lot — until you realize there are 8 billion people, each with multiple devices, plus billions of IoT gadgets. IPv4 officially ran out in 2011. IPv6 solves this with 340 undecillion addresses (3.4 × 10³⁸) — roughly one address per atom on Earth's surface. You'll encounter IPv6 constantly in modern networks.
ADDRESS FORMAT
Reading and Writing IPv6 Addresses
IPv6 addresses are 128 bits written as 8 groups of 4 hex digits separated by colons. Two simplification rules reduce the ugliness.

🧮 Subnetting — The Math That Scares Beginners (It Shouldn't) NET • Foundation ›
WHAT IS SUBNETTING
Dividing a Network Into Smaller Networks
An IP address has two parts: a network portion (which network you're on) and a host portion (which specific device). Subnetting is the art of deciding where to draw that line — splitting a big address block into smaller, organized chunks. Why? Security (isolate departments), efficiency (reduce broadcast traffic), and organization. It intimidates beginners, but it's just binary math you can learn in an afternoon.
CIDR NOTATION
The /24 Explained
An IPv4 address is 32 bits. CIDR (Classless Inter-Domain Routing) notation like 192.168.1.0/24 means "the first 24 bits are the network portion." The remaining bits (32 − 24 = 8) are for hosts. More network bits = smaller subnet = fewer hosts.
# 192.168.1.0/24 in binary 192.168.1.0 11000000.10101000.00000001.00000000 └──────── 24 network bits ────────┘└8 host┘ # The /24 tells you the subnet mask /24 = 255.255.255.0 # (24 ones, then 8 zeros) 11111111.11111111.11111111.00000000
THE KEY FORMULAS
Hosts and Subnets — Memorize These
# Number of usable hosts per subnet usable hosts = 2^(host bits) − 2 # (subtract 2: network address + broadcast address) # Example: /24 has 8 host bits 2^8 − 2 = 256 − 2 = 254 usable hosts # Example: /26 has 6 host bits 2^6 − 2 = 64 − 2 = 62 usable hosts # Number of subnets when you "borrow" bits subnets = 2^(borrowed bits)

🔀 NAT & Port Forwarding — How Private Networks Reach the Internet NET • Essential ›
WHY NAT EXISTS
Many Private Devices, One Public IP
There aren't enough IPv4 addresses for every device. NAT (Network Address Translation) lets a whole network of devices with private IPs (192.168.x.x) share a single public IP. Your home router does this: it translates internal addresses to its one public address on the way out, and remembers which internal device each connection belongs to so replies come back correctly.
TYPES OF NAT
Static, Dynamic, and PAT
TypeHow It WorksUse
Static NATOne private IP ↔ one public IP (fixed)Exposing a specific internal server
Dynamic NATPrivate IPs map to a pool of public IPsLess common; needs many public IPs
PAT / NAT overloadMany private IPs → one public IP, distinguished by portThe home router model — by far the most common
PAT (Port Address Translation) is what "NAT" almost always means in practice. The router tracks connections by (internal IP:port ↔ public IP:port) so dozens of devices share one address.
PORT FORWARDING
Letting the Outside Reach In
By default, NAT blocks unsolicited inbound connections (a nice side-effect: a basic firewall). But sometimes you WANT external access to an internal service — a game server, a web server, SSH to your home lab. Port forwarding tells the router: "traffic arriving on public port X → send to internal host:port Y."
# Example port-forward rules on a router Public :443 → 192.168.1.10:443 # web server Public :2222 → 192.168.1.20:22 # SSH to lab box # ⚠️ Security: every forwarded port is exposed to the internet. # Forward only what you must; prefer a VPN for remote access. # Linux iptables DNAT (what routers do under the hood) iptables -t nat -A PREROUTING -p tcp --dport 443 \ -j DNAT --to-destination 192.168.1.10:443

🚪 802.1X & NAC — Who Gets On the Network? NET • Enterprise ›
THE PROBLEM
An Open Network Port Is an Open Door
In a basic network, anyone who plugs into a wall jack or knows the Wi-Fi password is on the network. In an enterprise, that's a serious risk — an attacker in the lobby, a rogue device, a compromised laptop. 802.1X and NAC enforce authentication before access: prove who/what you are before the network lets you communicate.
802.1X
Port-Based Authentication
802.1X authenticates a device at the port level before granting network access. It involves three roles working together via the EAP protocol.
RoleWhoJob
SupplicantThe device wanting access (laptop)Provides credentials/certificate
AuthenticatorThe switch or wireless APGatekeeper — blocks traffic until authorized
Authentication ServerRADIUS serverVerifies credentials, says yes/no
Until authentication succeeds, the port only passes authentication traffic — everything else is blocked. Enterprise Wi-Fi (WPA2/3-Enterprise) uses exactly this model, which is why you log in with your own username/password instead of a shared Wi-Fi key.
NAC
Network Access Control — Beyond Just Identity
NAC extends the idea: it doesn't just check who you are, but whether your device is healthy and compliant before allowing full access — and what it's allowed to reach.
NAC CapabilityExample
Posture assessmentIs AV running? OS patched? Disk encrypted?
Quarantine / remediationNon-compliant device → restricted VLAN to fix itself
Role-based accessGuest → internet only; employee → full; IoT → isolated
Dynamic VLAN assignmentPut devices on the right segment automatically
Guest onboardingCaptive portal, sponsored access
RADIUS
The AAA Workhorse
RADIUS (Remote Authentication Dial-In User Service) is the protocol behind most network authentication. It provides AAA: Authentication (who are you?), Authorization (what may you do?), and Accounting (what did you do? — logging/billing). It centralizes credentials so every switch and AP checks against one source (often tied to Active Directory). TACACS+ is a Cisco-oriented alternative more focused on device administration.

Beginner Active Directory & LDAP – Enterprise Identity 101
Core Concept
What Is Active Directory?
Active Directory (AD) is Microsoft's directory service — the central phonebook of every Windows enterprise. It stores users, computers, groups, and policies in a tree of Organizational Units (OUs). When you log in at work, your laptop asks a Domain Controller (DC) to verify your password.

Key vocabulary:
• Domain – a boundary of administration (e.g. corp.example.com).
• Forest – one or more domains that trust each other.
• OU – a folder inside AD used to organise objects.
• GPO – Group Policy Object; rules pushed to computers/users.
• DC – Domain Controller; the server that runs AD.

"Not my circus, not my monkey" — if you are not the AD admin, do not make changes in AD. Escalate to the team that owns it.
Protocol
LDAP – How Applications Talk to AD
LDAP (Lightweight Directory Access Protocol) is the language software uses to query AD. Every object has a Distinguished Name (DN) — a path like a file system path:
CN=Alice Smith,OU=Finance,DC=corp,DC=example,DC=com

Common LDAP operations:
• Bind – authenticate (log in) to the directory.
• Search – find objects matching a filter.
• Add / Modify / Delete – manage objects (admin only).

Port 389 = plain LDAP  |  Port 636 = LDAPS (TLS encrypted — always prefer this).
# Query AD with Python ldap3 (read-only example) from ldap3 import Server, Connection, ALL, SUBTREE server = Server('ldaps://dc01.corp.example.com', get_info=ALL) conn = Connection(server, user='corp\svc_readonly', password='S3cur3P@ss!', auto_bind=True) # Find all users in the Finance OU conn.search( search_base='OU=Finance,DC=corp,DC=example,DC=com', search_filter='(&(objectClass=user)(!(userAccountControl:1.2.840.113556.1.4.803:=2)))', search_scope=SUBTREE, attributes=['cn', 'mail', 'department'] ) for entry in conn.entries: print(entry.cn, entry.mail) conn.unbind() # The filter above: objectClass=user AND NOT disabled (bit 2 of UAC)
Authentication
Kerberos in Plain English
Kerberos is the default authentication protocol for AD domains. Think of it as a theme-park wristband system:

1. You show your password once to the Key Distribution Center (KDC) on the DC.
2. The KDC gives you a Ticket-Granting Ticket (TGT) — your all-day wristband.
3. When you access a resource (file share, web app), you show the TGT to get a Service Ticket — a ride ticket for that specific attraction.
4. The resource trusts the service ticket without ever seeing your password again.

Why this matters for beginners: you never type your password again during the work day — Single Sign-On (SSO). Kerberos tickets expire (default 10 hours), so you may be prompted again next day.
Best Practice
Principle of Least Privilege in AD
"Assume" makes an ass out of you and me — never assume a user needs more permissions than their job requires. In AD:

• Give users standard accounts for daily work.
• Admins use a separate admin account (e.g. a-alice) only when elevated tasks are needed.
• Service accounts get only the groups they need.
• Review group memberships quarterly — "account creep" is real.

The Domain Admins group is the most powerful group in the domain. Its membership list should be tiny and audited constantly.
Beginner Cloud Networking – VPC, Subnets & Security Groups
Core Concept
What Is a VPC?
A Virtual Private Cloud (VPC) is your own private network inside a cloud provider (AWS, Azure, GCP). Think of it as renting a section of a data centre and installing your own private network switches — except it's all software.

Key building blocks:
• VPC – the outer boundary; you choose the IP range (e.g. 10.0.0.0/16 = ~65 000 addresses).
• Subnet – a slice of the VPC in one availability zone. Public subnets reach the internet; private subnets do not.
• Internet Gateway (IGW) – the door between your VPC and the public internet.
• NAT Gateway – lets private-subnet resources make outbound internet calls without being reachable from outside.
• Route Table – rules that decide where packets go (like a router's routing table).
• Security Group – a stateful firewall attached to an individual resource (VM, load balancer).

"Assume" makes an ass out of you and me — never assume a cloud resource is private just because it's in a VPC. Check security groups AND network ACLs; both must permit the traffic.
AWS Example
Building a VPC with AWS CLI
AWS CLI lets you build the entire network from the command line. This is the same thing the console does behind the scenes.
# Create a VPC aws ec2 create-vpc --cidr-block 10.0.0.0/16 --query Vpc.VpcId --output text # Output: vpc-0abc1234def567890 # Create a public subnet (AZ us-east-1a) aws ec2 create-subnet --vpc-id vpc-0abc1234def567890 --cidr-block 10.0.1.0/24 --availability-zone us-east-1a # Create a private subnet aws ec2 create-subnet --vpc-id vpc-0abc1234def567890 --cidr-block 10.0.2.0/24 --availability-zone us-east-1a # Attach an internet gateway aws ec2 create-internet-gateway --query InternetGateway.InternetGatewayId aws ec2 attach-internet-gateway --internet-gateway-id igw-0xyz --vpc-id vpc-0abc1234def567890 # Security group: allow SSH from your IP only aws ec2 create-security-group --group-name web-sg --description "Web server SG" --vpc-id vpc-0abc1234def567890 aws ec2 authorize-security-group-ingress --group-id sg-0xyz --protocol tcp --port 22 --cidr 203.0.113.5/32 # your IP only!
Best Practice
The Shared Responsibility Model
Cloud providers operate a Shared Responsibility Model: the provider secures the infrastructure of the cloud; you secure everything in the cloud.

AWS/Azure/GCP handles: Physical data centres, hypervisor security, global network, managed service patches.

You handle: VM OS patches, security group rules, S3 bucket permissions, IAM roles, encryption of your data, application code security.

"Not my circus, not my monkey" only applies to the provider's layer. Misconfigured S3 buckets, open security groups, and leaked IAM keys are 100 % your responsibility. Most cloud breaches are misconfiguration, not a failure by the provider.
Beginner DNS Deep-Dive – How Domain Names Actually Work
Core Concept
The DNS Resolution Walk
When you type www.example.com in a browser, this is what happens before the first byte of the page arrives:

1. Browser checks its local cache — did we look this up recently?
2. OS checks /etc/hosts (or Windows Hosts file) — manual overrides.
3. OS asks the Recursive Resolver (usually your router or ISP, or 8.8.8.8/1.1.1.1).
4. Resolver asks a Root Name Server (.): "Who handles .com?"
5. Root refers to the .com TLD server: "Ask ns1.example.com."
6. Resolver asks ns1.example.com: "What's the IP for www?"
7. Authoritative answer returned: 93.184.216.34.
8. Resolver caches the result for the TTL; returns it to your browser.

Total time: usually 10–100 ms. Cached lookups: <1 ms.

Security
DNS Security – DNSSEC, DoH, DNS Attacks
DNS was designed in the 1980s with no security. Several attacks exploit this:

DNS Cache Poisoning — attacker injects a false record into a resolver's cache so users get sent to the wrong IP.
Fix: DNSSEC — cryptographic signatures on DNS records.

DNS Hijacking — malware or rogue ISP changes the resolver you use.
Fix: DNS-over-HTTPS (DoH) or DNS-over-TLS (DoT) — encrypts queries so no one can tamper in transit.

DNS Tunnelling — attacker encodes data inside DNS queries to exfiltrate data or establish C2 (bypasses firewalls).
Fix: Monitor for unusually long query names, high query volume per host, rare TLDs.

"Assume" makes an ass out of you and me — never assume DNS responses are authentic unless DNSSEC is validated end-to-end.

Operations
Managing DNS Zones
Whether you use Route 53, Cloudflare, or BIND on-prem, the concepts are the same. Best practices:

• Set low TTLs (e.g. 300 s) before planned changes; restore high TTLs (3600+) after.
• Always have at least two NS servers in different locations for redundancy.
• Use split-horizon DNS — internal names resolve to private IPs; external names resolve to public IPs.
• Add SPF, DKIM, DMARC TXT records for every domain that sends email to prevent spoofing.
• You can't make someone make the right choice, yet you can pick up the pieces afterwards — when a TTL-expired stale record sends users to a dead IP, reduce TTL proactively next time.

• No shared secret to leak — each user has unique creds.

Attacks

Wi-Fi Network Design Best Practices
• Use WPA3 where supported; WPA2-Enterprise for corporate devices.
• Separate SSIDs for different trust levels: Corp, Guest, IoT — each on its own VLAN.

Beginner Packet Analysis – Reading the Network's Mind with Wireshark
Core Concept
Why Capture Packets?
Every problem on a network eventually shows up in the packets — slow apps, failed connections, intrusions, misconfigurations. A packet capture (pcap) is ground truth: it shows exactly what was sent and received, byte for byte.

Tools:
• tcpdump — command-line capture; runs anywhere, even on headless servers.
• Wireshark — GUI analysis; the gold standard for deep inspection.
• tshark — Wireshark's CLI sibling; great for scripting and automation.

"Not my circus, not my monkey" — capturing traffic on a network you don't own or have authorization for is illegal in most jurisdictions (wiretapping laws). Always get written authorization.
Capture
Capturing Traffic with tcpdump
tcpdump uses Berkeley Packet Filter (BPF) syntax to select exactly the traffic you care about — capturing everything creates huge files and noise.
# Capture all traffic on eth0, write to a file (analyse later in Wireshark) sudo tcpdump -i eth0 -w capture.pcap # Capture only HTTP traffic (port 80) with full packet content sudo tcpdump -i eth0 -s 0 -w http.pcap port 80 # Capture traffic to/from a specific host sudo tcpdump -i eth0 host 192.168.1.50 # Capture traffic between two hosts on a specific port sudo tcpdump -i eth0 'host 192.168.1.50 and host 192.168.1.10 and port 443' # Show packets live, with readable ASCII (good for HTTP debugging) sudo tcpdump -i eth0 -A port 80 # Capture only SYN packets (new connection attempts — good for scan detection) sudo tcpdump -i eth0 'tcp[tcpflags] == tcp-syn' # Rotate captures every 100MB, keep last 10 files (long-running capture) sudo tcpdump -i eth0 -w /data/cap.pcap -C 100 -W 10
Analysis
Reading a Capture in Wireshark
Wireshark's display filter bar (top of the window) is the most powerful tool — it narrows thousands of packets down to the handful you care about.

tshark
Scripting Analysis with tshark
For repeatable analysis or processing huge captures, script it with tshark instead of clicking through the GUI.
# Extract all unique source/destination IP pairs tshark -r capture.pcap -T fields -e ip.src -e ip.dst | sort -u # Count HTTP requests by destination host tshark -r capture.pcap -Y "http.request" -T fields -e http.host | sort | uniq -c | sort -rn # Extract all DNS queries (great for spotting C2 domains) tshark -r capture.pcap -Y "dns.flags.response == 0" -T fields -e frame.time -e ip.src -e dns.qry.name # Find the top talkers by byte volume tshark -r capture.pcap -q -z conv,ip | head -20 # Extract files transferred over HTTP (incident response) tshark -r capture.pcap --export-objects http,/tmp/extracted_files/

DNS Deep Dive – How Name Resolution Really Works

Mindset

Assume makes an ass out of you and me

When a website "won't load," don't assume it's the web server. DNS failures look identical to outages from the user's perspective. Walking the resolution chain step by step — instead of guessing — is what separates a five-minute fix from an hour of chasing the wrong problem.

Concept

The resolution chain, in order

When you type example.com into a browser, your computer doesn't magically know where to send the request. It walks a chain of lookups:

StepWhat happensWhere it's checked
1. Browser cache"Have I looked this up in the last few minutes?"Browser memory
2. OS cache"Does the operating system already know this?"systemd-resolved / dnsmasq / Windows DNS Client
3. Hosts file"Is there a manual override?"/etc/hosts or C:\Windows\System32\drivers\etc\hosts
4. Recursive resolver"Ask my configured DNS server (ISP, 1.1.1.1, 8.8.8.8) to find it"/etc/resolv.conf
5. Root → TLD → authoritativeThe resolver walks the DNS hierarchy until it finds the authoritative answerGlobal DNS infrastructure

Most "the website is down" tickets are solved at step 2 or 3 — a stale cache entry or a leftover hosts file edit from testing months ago.

Hands-on

Tracing resolution yourself

# See which resolver your system is configured to use
cat /etc/resolv.conf

# Look up a name and show the full trip — timing included
dig example.com

# Trace the entire chain from the root servers down (educational, slower)
dig +trace example.com

# Ask a *specific* DNS server directly, bypassing your default resolver
dig @1.1.1.1 example.com

# Check what record types exist — A (IPv4), AAAA (IPv6), MX (mail), TXT, CNAME
dig example.com MX
dig example.com TXT

# Reverse lookup: what name does this IP resolve back to?
dig -x 93.184.216.34

The +trace flag is especially good for learning — it shows the actual hierarchy: your resolver asks a root server "who handles .com?", then asks that TLD server "who handles example.com?", then finally asks the authoritative server for the actual IP.

Common pitfall

"It works on my machine" — DNS cache edition

A classic scenario: a developer changes a DNS record, tells you "it's updated," and your browser still shows the old site. Both of you are right — the record changed at the authoritative server, but your resolver cached the old answer for its full TTL (time-to-live). Common fixes, in order of how invasive they are:

# Flush just your local OS resolver cache (Linux with systemd-resolved)
sudo resolvectl flush-caches

# macOS
sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder

# Windows (run as administrator)
ipconfig /flushdns

# Or simply query a different resolver to sanity-check the *real* current value
dig @8.8.8.8 example.com +short

If a record was just changed, remember that TTL still applies globally — other people's resolvers around the world will keep serving the cached answer until their TTL expires too. This is why planned DNS cutovers lower the TTL days in advance.

VPNs Explained – Tunnels, Encryption, and What They Don't Do

Concept

A VPN is a private tunnel through a public road

Imagine the internet as a public highway system — anyone running the right equipment at the right point could, in theory, see which trucks are going where. A VPN (Virtual Private Network) builds an encrypted tunnel through that highway: your traffic still travels over the same public infrastructure, but it's wrapped in a layer that hides its contents from anyone watching the road, and makes it appear to originate from the tunnel's far end rather than your actual location.

Concept

Two very different reasons people use VPNs

Use caseWhat it actually doesCommon protocols
Corporate / remote-access VPNLets an employee's laptop join the company's internal network from anywhere, as if it were plugged in at the officeWireGuard, OpenVPN, IPsec/IKEv2, Cisco AnyConnect
Consumer / privacy VPNRoutes your traffic through a third-party provider's server so your ISP and local network can't see *what* you're accessing — though the VPN provider now canWireGuard, OpenVPN (commercial offerings)

These solve different problems for different threat models. A corporate VPN exists so IT can extend a trusted network boundary to remote workers; a consumer VPN exists to shift *who* has visibility into your traffic — from your ISP to the VPN provider — which is a meaningfully different guarantee than "no one can see what I do online."

Hands-on

Setting up a minimal WireGuard tunnel (lab environment)

# Install WireGuard (Debian/Ubuntu)
sudo apt install wireguard

# Generate a public/private keypair for this peer
wg genkey | tee privatekey | wg pubkey > publickey

# Minimal config: /etc/wireguard/wg0.conf
# (replace placeholders with real keys and addresses)
#
# [Interface]
# PrivateKey = <this peer's private key>
# Address = 10.10.0.2/24
#
# [Peer]
# PublicKey = <remote peer's public key>
# Endpoint = vpn.example.com:51820
# AllowedIPs = 0.0.0.0/0
# PersistentKeepalive = 25

# Bring the tunnel up and check its status
sudo wg-quick up wg0
sudo wg show

# Confirm your traffic is actually routing through the tunnel
curl https://ifconfig.me

The AllowedIPs = 0.0.0.0/0 line is the one to read carefully — it tells the system to route all traffic through the tunnel ("full tunnel"), versus a narrower range that only sends specific destinations through it ("split tunnel"). Getting this wrong is one of the most common VPN misconfigurations: too broad and you may break local network access; too narrow and traffic you meant to protect goes out in the clear.

Common pitfall

"I'm on a VPN, so I'm anonymous" — assume makes an ass out of you and me

A VPN hides your traffic's path and contents from your local network and ISP — it does not make you anonymous to the websites you visit. You can still be tracked through cookies, browser fingerprinting, account logins, and the VPN provider itself can see (and in some jurisdictions, may be compelled to log and disclose) your activity. Treat "I'm using a VPN" as one layer of a privacy strategy, not a magic cloak — and always read a provider's actual logging policy rather than assuming "no logs" means what it sounds like.

Subnetting Without the Headache – CIDR Notation Made Practical

Concept

A subnet is just "how big is this neighborhood?"

An IP address tells you a device's location; a subnet mask tells you how many of its neighbors share the same local "neighborhood" — the group of addresses that can talk to each other directly, without going through a router. CIDR notation (/24, /26, etc.) is just a compact way of writing that mask: the number after the slash tells you how many bits are reserved for identifying the network itself, leaving the rest for individual hosts.

Concept

The CIDR cheat sheet beginners actually reach for

CIDRSubnet maskUsable hostsCommon use
/24255.255.255.0254Typical small office or home network
/25255.255.255.128126Splitting a /24 in half — two departments, one building
/26255.255.255.19262A single floor or smaller team
/27255.255.255.22430A small lab, a rack of servers, a point-to-point link group
/30255.255.255.2522A direct link between two routers — exactly enough for both ends

Notice the pattern: every step from /24 toward /32 cuts the available addresses roughly in half. "Usable hosts" is two less than the raw count — one address is reserved to identify the network itself, and one is reserved as the broadcast address that reaches every device in that subnet at once.

Hands-on

Let the tools do the arithmetic — verify, don't memorize

# pip install — actually it's built into Python's standard library!
import ipaddress

network = ipaddress.ip_network("192.168.10.0/26")
print(f"Network address:   {network.network_address}")
print(f"Broadcast address: {network.broadcast_address}")
print(f"Usable hosts:      {network.num_addresses - 2}")
print(f"First usable host: {list(network.hosts())[0]}")
print(f"Last usable host:  {list(network.hosts())[-1]}")

# Quick check: is this address inside that subnet?
ip = ipaddress.ip_address("192.168.10.40")
print(f"{ip} in {network}? {ip in network}")

# Splitting a network into smaller subnets — handy for planning
# departmental allocations from a single block you've been given
for sub in network.subnets(new_prefix=28):
    print(f"  Sub-block: {sub}")

This is the honest secret of subnetting: nobody who works with networks daily does the binary math by hand every time. They've internalized the cheat-sheet patterns for common cases, and they reach for a calculator (or ipaddress, or ipcalc on the command line) to double-check anything unusual. Knowing how it works conceptually — and knowing how to verify it — beats memorizing tables you'll forget under pressure.

Mindset

Assume makes an ass out of you and me

"That device should be able to reach the server, they're both on the 192.168.x.x range" is a classic trap — two addresses can look similar and still be in completely different subnets, unable to communicate without a router between them. Before troubleshooting further up the stack, verify the actual subnet boundaries with a tool like the one above rather than eyeballing the addresses and assuming they're neighbors.

Load Balancers Explained – Spreading the Work Around

Concept

A load balancer is a traffic cop for your servers

A load balancer sits in front of a group of servers and decides which one should handle each incoming request — spreading the work around so no single server gets overwhelmed, and so the service keeps running even if one server fails. From the outside, users see a single address; behind that address, the load balancer quietly routes them to whichever healthy server makes the most sense at that moment.

Concept

Common balancing strategies, and when each shines

StrategyHow it decidesGood fit when...
Round robinCycles through servers in order: 1, 2, 3, 1, 2, 3...All servers are roughly equal in capacity and requests are roughly equal in cost
Least connectionsSends the next request to whichever server currently has the fewest active connectionsRequests vary significantly in how long they take to process
IP hashRoutes based on a hash of the client's IP — the same client tends to land on the same serverYou need "session stickiness" without a shared session store
WeightedSome servers get proportionally more traffic than others, based on assigned weightsYour servers have meaningfully different capacities (a newer, beefier box vs. an older one)
Concept

The unsung hero: health checks

A load balancer is only as good as its ability to know which servers are actually healthy. It periodically polls each server — often hitting a dedicated /healthz endpoint — and silently stops sending traffic to any server that fails to respond correctly. This is the mechanism that turns "one server crashed" from a customer-facing outage into a non-event nobody outside the on-call team ever notices.

# A minimal health endpoint, the kind a load balancer polls every few seconds
from flask import Flask, jsonify
app = Flask(__name__)

@app.route("/healthz")
def health_check():
    checks = {
        "database": database_is_reachable(),
        "cache": cache_is_reachable(),
        "disk_space_ok": get_free_disk_percent() > 10,
    }
    healthy = all(checks.values())
    status_code = 200 if healthy else 503
    return jsonify(checks), status_code

# A load balancer that sees repeated 503s here will quietly stop
# routing traffic to this instance — without a single human noticing,
# until someone reviews the dashboards and finds the graceful save
Mindset

Assume makes an ass out of you and me

A health check that only verifies "is the web server process running?" can report "healthy" while the actual database connection behind it is completely down — leaving users staring at error pages from a server the load balancer confidently considers fine. A good health check verifies the things that actually matter to the user's experience, not just the easiest thing to check. "The process is running" and "the service actually works" are two different claims — don't let your monitoring assume they're the same.
