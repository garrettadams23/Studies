🤝 TCP (Transmission Control Protocol) vs UDP (User Datagram Protocol) — Transport Layer NETWORK+ ▶
Reference — RFC (Request for Comments) 793 (TCP) · RFC 768 (UDP)
Connection Types · 3-Way Handshake · Flags · Use Cases
TCP — connection-oriented, reliable, ordered, error-checked. UDP — connectionless, low-overhead, best-effort. Choose based on need for reliability vs speed.
▸ COMPARISON
Feature TCP UDP
Connection 3-way handshake (SYN→SYN-ACK→ACK) None — send and forget
Reliability ACK, retransmission, ordering No guarantees
Speed Slower (overhead) Faster (low overhead)
Header size 20–60 bytes 8 bytes
Flow control Yes (sliding window) No
Use cases HTTP (HyperText Transfer Protocol), HTTPS (HyperText Transfer Protocol Secure), FTP (File Transfer Protocol), SSH (Secure Shell), SMTP (Simple Mail Transfer Protocol), databases DNS (Domain Name System), VoIP (Voice over Internet Protocol), video streaming, DHCP (Dynamic Host Configuration Protocol), gaming

NMAP — Scan Flags, Responses & Common Options
Nmap is the de-facto tool for network discovery and port scanning. Use nmap <SCAN> <TARGET> syntax. Requires root/administrator for raw socket scans (SYN, FIN, XMAS, etc.).
▸ SCAN TYPES
Flag Scan Type Open Response Closed Response Notes
-sT TCP (Transmission Control Protocol) Connect SYN/ACK RST/ACK Full 3-way handshake; logged by target
-sS SYN (Synchronize) stealth scan SYN/ACK RST/ACK Half-open; doesn't complete handshake; less logged
-sF FIN No response RST Works on Linux/Unix; bypasses some firewalls
-sX XMAS Tree No response RST Sets FIN+URG+PSH flags; binary 00101001
-sN NULL No response Varies by OS (Operating System) No flags set; designed for Linux/Unix
-sA ACK RST No response Maps firewall rules; determines filtered/unfiltered
-sI IDLE (Zombie) SYN/ACK RST/ACK Uses spoofed IP (Internet Protocol); maximum stealth scan
-sU UDP (User Datagram Protocol) UDP response ICMP (Internet Control Message Protocol) unreachable Slower; needed for DNS/DHCP/SNMP discovery
-sn Ping Sweep — — Host discovery only; no port scan
▸ USEFUL NMAP OPTIONS

🧒Networking for Absolute BeginnersNet+ • Start Here▶
BIG IDEA
What Is a Network?
A network is just two or more computers that can talk to each other. Your home Wi-Fi is a small network; the Internet is the giant network that connects all the small ones together. If computers are houses, the network is the system of roads between them.
ANALOGY
IP (Internet Protocol) Address = Mailing Address
Every device on a network has an IP address (e.g., 192.168.1.10) so data knows where to go — exactly like a street address tells the mail carrier which house. No address, no delivery.
ANALOGY
Packets = Envelopes
Big files are chopped into small chunks called packets. Each packet is an envelope with a from-address, a to-address, and a piece of the message. They travel separately and get reassembled at the other end.
ANALOGY
Ports = Apartment Numbers
One device (one IP) runs many programs at once. A port number says which program the data is for — like an apartment number after the street address. Web pages use port 80/443, email and other services use their own.
ROLES
Client vs. Server
The client asks (your phone opening a website); the server answers (the computer that stores that website). Most of what you do online is a polite back-and-forth of requests and responses.
HARDWARE
Router vs. Switch
A switch connects devices inside one network (like hallways in a building). A router connects different networks together and finds the path between them (like roads between cities). Your home box is usually both in one.
ANALOGY
DNS (Domain Name System) = The Phonebook
Humans remember names (google.com); computers need numbers (an IP). DNS is the phonebook that looks up the name and returns the number, automatically, every time you click a link.

📖 DNS (Domain Name System) — The Internet's Phone Book NET • Start Here ▶
THE PROBLEM DNS SOLVES
Humans Hate Numbers
Computers talk to each other using IP (Internet Protocol) addresses like 142.250.80.46. Humans want to type google.com. DNS (Domain Name System) translates names into numbers — like a phone book that covers the whole internet.
THE DNS LOOKUP JOURNEY
8 Steps From Name to IP
1. You type google.com in your browser.
2. Browser checks its own cache. If found → done.
3. OS (Operating System) checks its cache. If found → done.
4. OS asks your recursive resolver (your ISP or 8.8.8.8).
5. Resolver asks a root nameserver (13 clusters worldwide) — "who handles .com?"
6. Root points to the .com TLD nameserver (Verisign).
7. TLD server points to Google's authoritative nameserver.
8. Authoritative server returns the IP. Resolver caches it and gives it to you.

TTL
Time to Live — DNS Caching Timer
Every DNS record has a TTL (Time To Live) in seconds. After TTL expires, resolvers re-query for fresh results. Low TTL = fast changes but more queries. High TTL = slow propagation but less load. When migrating a website, lower the TTL 24 hours before the switch.
🔢 DHCP (Dynamic Host Configuration Protocol) — How Devices Get Their IP (Internet Protocol) Address NET • Foundation ▶
DORA PROCESS
Discover → Offer → Request → Acknowledge
Discover — new device broadcasts "I need an IP!" to 255.255.255.255.
Offer — DHCP server says "How about 192.168.1.25? Here's a lease offer."
Request — client says "Yes, I'll take 192.168.1.25" (broadcast, so other servers know).
Acknowledge — server confirms: "192.168.1.25 is yours for 24 hours. Here's gateway and DNS (Domain Name System) too."
WHAT DHCP HANDS OUT
More Than Just an IP
A DHCP lease typically includes:
• IP address — unique on the local network
• Subnet mask — defines network boundary (e.g., 255.255.255.0)
• Default gateway — the router's IP (traffic leaving the network goes here)
• DNS server(s) — where to resolve names
• Lease duration — how long before re-requesting
STATIC vs DYNAMIC
Manual vs Automatic Assignment
Dynamic — DHCP assigns from a pool; good for laptops and phones. IP may change on reconnect.
Static — manually set; never changes. Required for servers, printers, network gear (you don't want DNS records breaking because the server got a new IP).
DHCP Reservation — best of both worlds: DHCP assigns based on MAC (Media Access Control) address, so the device always gets the same IP automatically.
TROUBLESHOOTING
When DHCP Fails — APIPA (Automatic Private IP Addressing)
If a device can't reach a DHCP server, Windows auto-assigns an APIPA address: 169.254.x.x. This is a red flag — the device only has link-local connectivity and cannot reach the internet. Check: cable unplugged? DHCP server down? VLAN (Virtual Local Area Network) misconfigured?

🔀 Switching & VLANs (Virtual Local Area Network) — Dividing Your Network Logically NET • Foundation ▶
SWITCH vs HUB vs ROUTER
Three Different Devices, Three Layers
Hub — Layer 1; dumb repeater. Sends every frame to every port. Creates collisions. Legacy/obsolete.
Switch — Layer 2; intelligent. Learns which MAC (Media Access Control) addresses are on which ports using a MAC address table. Sends frames only to the correct port. Creates collision domains per port.
Router — Layer 3; connects different networks. Uses IP (Internet Protocol) addresses and routing tables to forward packets between subnets and out to the internet.
HOW A SWITCH WORKS
MAC Address Table Learning
1. Frame arrives with source MAC AA:BB on port 1 → switch records AA:BB → Port 1 in table.
2. Destination MAC CC:DD — not in table yet → switch floods to all ports except source.
3. Device CC:DD responds → its MAC gets recorded.
4. Next frame to CC:DD → switch delivers it only to the correct port.
This is why switches are efficient — after learning, minimal unnecessary traffic.
VLANS
Virtual LANs (Local Area Network) — Logical Network Segmentation
A VLAN divides one physical switch into multiple logical networks. Devices in different VLANs cannot communicate directly even if they're plugged into the same switch — they need a router (Layer 3) to cross VLAN boundaries. Benefits:
• Security: production servers on VLAN 10, guest WiFi on VLAN 99 — guests can't see servers
• Performance: reduce broadcast domain size
• Organization: group devices by function, not location
TRUNK vs ACCESS PORTS
Single VLAN vs Multiple VLANs
Access port — carries traffic for exactly ONE VLAN. Used for end devices (PCs, printers). Device doesn't know it's on a VLAN.
Trunk port — carries traffic for MULTIPLE VLANs simultaneously. Used between switches, or switch-to-router. Uses 802.1Q tags to label which VLAN each frame belongs to.

STATIC vs DYNAMIC ROUTING
Manual Routes vs Self-Learning
Static routes — an admin manually configures each route. Simple, predictable, no overhead. Works for small networks. Fails when the network changes (adding a link, a failure) because you have to manually update every router.
Dynamic routing protocols — routers talk to each other and automatically discover routes. Self-healing when links fail. Required for large networks.

BGP
The Protocol That Runs the Internet
BGP (Border Gateway Protocol) is used between ISPs and large organizations to exchange routing information across the internet. Every major network has an ASN (Autonomous System Number). BGP is policy-driven — companies can influence which paths their traffic takes. A BGP misconfiguration can accidentally route the internet's traffic through your network (BGP hijacking).
DEFAULT ROUTE
The Fallback Route (0.0.0.0/0)
The default route (0.0.0.0/0 or ::/0) matches ANY destination. It's the "if nothing else matches, send it here" rule — usually pointing to the upstream router or internet gateway. Every end device has a default gateway for this reason.
🧱 Firewalls — The Network's Bouncer NET • Foundation ▶
WHAT A FIREWALL DOES
Permit or Deny Based on Rules
A firewall inspects network traffic and decides whether to allow or block it based on rules. Think of it as a bouncer with a list: traffic that matches an allow rule gets in; everything else is dropped or rejected. The implicit deny rule: if nothing matches, deny.
FIREWALL TYPES
Packet Filter → Stateful → NGFW (Next-Generation Firewall)
Packet filter (L3/L4) — examines individual packets: source/dest IP (Internet Protocol), port, protocol. No context (doesn't know if it's a new connection or response). Fast but dumb.
Stateful inspection — tracks connection state. Knows if a packet is part of an established session. Much smarter — allows response traffic automatically.
NGFW (Next-Gen Firewall) — adds application awareness (block YouTube regardless of port), IPS (Intrusion Prevention System), deep packet inspection, user identity, SSL (Secure Sockets Layer) inspection. Most enterprise firewalls today.

⚖️ Load Balancers & High Availability — Never Go Down NET • Intermediate ▶
THE PROBLEM
One Server = Single Point of Failure
If your entire service runs on one server and it crashes, everyone is down. High availability (HA) architectures spread load across multiple servers so that if one fails, others continue serving traffic seamlessly. HA goal: no single component failure takes down the service.
LOAD BALANCER
Distributes Traffic Across Backend Servers
A load balancer sits in front of your servers and routes each incoming request to one of the backends. Algorithms:
Round-robin — server 1, server 2, server 3, server 1… Even distribution.
Least connections — sends to whichever server has the fewest active connections.
IP (Internet Protocol) hash — same client IP always goes to the same server (sticky sessions).
Weighted — big server gets more traffic than small server.
HEALTH CHECKS
Automatically Remove Failing Servers
A load balancer periodically pings each backend (HTTP GET /health, TCP connect, etc.). If a backend fails N consecutive checks, it's removed from the pool. No human intervention needed — traffic automatically shifts to healthy servers. When it recovers, it re-enters the pool.

🌐 IPv6 (Internet Protocol version 6) — The Internet's Upgrade NET • Essential ▶
WHY IPv6
IPv4 (Internet Protocol version 4) Ran Out of Addresses
IPv4 has 4.3 billion addresses. That sounds like a lot — until you realize there are 8 billion people, each with multiple devices, plus billions of IoT (Internet of Things) gadgets. IPv4 officially ran out in 2011. IPv6 solves this with 340 undecillion addresses (3.4 × 10³⁸) — roughly one address per atom on Earth's surface. You'll encounter IPv6 constantly in modern networks.
ADDRESS FORMAT

🔐 VPNs (Virtual Private Network) & Tunneling — Secure Connections Over Untrusted Networks NET • Essential ▶
WHAT A VPN ACTUALLY DOES
An Encrypted Tunnel Through a Hostile Network
A VPN (Virtual Private Network) creates an encrypted tunnel between your device and a VPN server. Everything inside the tunnel is encrypted, so even on untrusted networks (coffee shop Wi-Fi), nobody can read your traffic. There are two distinct use cases that people confuse:
TypePurposeExample
Remote Access VPNConnect a remote user to a private corporate networkWorking from home, accessing internal apps
Site-to-Site VPNConnect two networks (offices) over the internetBranch office ↔ HQ network
Commercial VPNPrivacy/geo-unblocking for consumersNordVPN, hiding traffic from ISP (Internet Service Provider)

PROXIES VS VPNs
Related But Different
FeatureProxyVPN
ScopePer-application (e.g., just the browser)Entire device (all traffic)
EncryptionOften none (just relays)Always encrypted

A forward proxy sits between users and the internet (corporate web filtering). A reverse proxy sits in front of servers (load balancing, TLS termination, hiding backend — e.g., nginx, Cloudflare).
SSH (Secure Shell) TUNNELING
The Poor Man's VPN
SSH can forward ports through its encrypted connection — a quick way to securely reach services without a full VPN. Essential for accessing internal services through a jump host.
# Local port forward — reach a remote DB through SSH # "Make my localhost:5432 → db.internal:5432 via jumphost" ssh -L 5432:db.internal:5432 user@jumphost # Now connect to localhost:5432 → actually hits db.internal # Remote port forward — expose YOUR local service to remote ssh -R 8080:localhost:3000 user@remote # remote's :8080 → your local :3000 # Dynamic forward — SOCKS proxy (route browser through SSH) ssh -D 1080 user@jumphost # Set browser SOCKS proxy to localhost:1080 # Jump through a bastion to reach an internal host ssh -J bastion.example.com user@internal-host
ZERO TRUST NETWORK ACCESS
The VPN Replacement
Traditional VPNs give you access to the whole network once connected (overly trusting). Zero Trust Network Access (ZTNA) flips this: "never trust, always verify." Every request is authenticated and authorized individually, granting access only to specific applications — not the whole network. Tools like Cloudflare Access, Tailscale, and Zscaler implement this. Increasingly replacing legacy VPNs.
🧮 Subnetting — The Math That Scares Beginners (It Shouldn't) NET • Foundation ▶
WHAT IS SUBNETTING
Dividing a Network Into Smaller Networks
An IP (Internet Protocol) address has two parts: a network portion (which network you're on) and a host portion (which specific device). Subnetting is the art of deciding where to draw that line — splitting a big address block into smaller, organized chunks. Why? Security (isolate departments), efficiency (reduce broadcast traffic), and organization. It intimidates beginners, but it's just binary math you can learn in an afternoon.
CIDR NOTATION
The /24 Explained
An IPv4 (Internet Protocol version 4) address is 32 bits. CIDR (Classless Inter-Domain Routing) notation like 192.168.1.0/24 means "the first 24 bits are the network portion." The remaining bits (32 − 24 = 8) are for hosts. More network bits = smaller subnet = fewer hosts.
# 192.168.1.0/24 in binary 192.168.1.0 11000000.10101000.00000001.00000000 └──────── 24 network bits ────────┘└8 host┘ # The /24 tells you the subnet mask /24 = 255.255.255.0 # (24 ones, then 8 zeros) 11111111.11111111.11111111.00000000
THE KEY FORMULAS
Hosts and Subnets — Memorize These
# Number of usable hosts per subnet usable hosts = 2^(host bits) − 2 # (subtract 2: network address + broadcast address) # Example: /24 has 8 host bits 2^8 − 2 = 256 − 2 = 254 usable hosts # Example: /26 has 6 host bits 2^6 − 2 = 64 − 2 = 62 usable hosts # Number of subnets when you "borrow" bits subnets = 2^(borrowed bits)

WORKED EXAMPLE
Finding Network, Broadcast, and Range
Given an IP and CIDR, here's how to find the key addresses. This is the most common subnetting question on exams and the job.
# Given: 192.168.1.100/26 — what subnet is it in? # Step 1: /26 → block size. Host bits = 32-26 = 6. Block = 2^6 = 64 # Step 2: subnets start at multiples of the block size (64): # 192.168.1.0, .64, .128, .192 # Step 3: .100 falls between .64 and .128 → subnet is .64 Network address: 192.168.1.64 # first address (not usable) First usable host: 192.168.1.65 Last usable host: 192.168.1.126 Broadcast address: 192.168.1.127 # last address (not usable) Next subnet: 192.168.1.128 # Shortcut: "block size" trick — count by 64s. Done.

🔀 NAT (Network Address Translation) & Port Forwarding — How Private Networks Reach the Internet NET • Essential ▶
WHY NAT EXISTS
Many Private Devices, One Public IP (Internet Protocol)
There aren't enough IPv4 (Internet Protocol version 4) addresses for every device. NAT (Network Address Translation) lets a whole network of devices with private IPs (192.168.x.x) share a single public IP. Your home router does this: it translates internal addresses to its one public address on the way out, and remembers which internal device each connection belongs to so replies come back correctly.
TYPES OF NAT
Static, Dynamic, and PAT (Port Address Translation)
TypeHow It WorksUse
Static NATOne private IP ↔ one public IP (fixed)Exposing a specific internal server
Dynamic NATPrivate IPs map to a pool of public IPsLess common; needs many public IPs
PAT / NAT overloadMany private IPs → one public IP, distinguished by portThe home router model — by far the most common
PAT (Port Address Translation) is what "NAT" almost always means in practice. The router tracks connections by (internal IP:port ↔ public IP:port) so dozens of devices share one address.
PORT FORWARDING
Letting the Outside Reach In
By default, NAT blocks unsolicited inbound connections (a nice side-effect: a basic firewall). But sometimes you WANT external access to an internal service — a game server, a web server, SSH (Secure Shell) to your home lab. Port forwarding tells the router: "traffic arriving on public port X → send to internal host:port Y."
# Example port-forward rules on a router Public :443 → 192.168.1.10:443 # web server Public :2222 → 192.168.1.20:22 # SSH to lab box # ⚠️ Security: every forwarded port is exposed to the internet. # Forward only what you must; prefer a VPN for remote access. # Linux iptables DNAT (what routers do under the hood) iptables -t nat -A PREROUTING -p tcp --dport 443 \ -j DNAT --to-destination 192.168.1.10:443

🚪 802.1X & NAC (Network Access Control) — Who Gets On the Network? NET • Enterprise ▶
THE PROBLEM
An Open Network Port Is an Open Door
In a basic network, anyone who plugs into a wall jack or knows the Wi-Fi password is on the network. In an enterprise, that's a serious risk — an attacker in the lobby, a rogue device, a compromised laptop. 802.1X and NAC enforce authentication before access: prove who/what you are before the network lets you communicate.
802.1X
Port-Based Authentication
802.1X authenticates a device at the port level before granting network access. It involves three roles working together via the EAP (Extensible Authentication Protocol) protocol.
RoleWhoJob
SupplicantThe device wanting access (laptop)Provides credentials/certificate
AuthenticatorThe switch or wireless APGatekeeper — blocks traffic until authorized
Authentication ServerRADIUS (Remote Authentication Dial-In User Service) serverVerifies credentials, says yes/no
Until authentication succeeds, the port only passes authentication traffic — everything else is blocked. Enterprise Wi-Fi (WPA2/3-Enterprise) uses exactly this model, which is why you log in with your own username/password instead of a shared Wi-Fi key.
NAC
Network Access Control — Beyond Just Identity
NAC extends the idea: it doesn't just check who you are, but whether your device is healthy and compliant before allowing full access — and what it's allowed to reach.
NAC CapabilityExample
Posture assessmentIs AV running? OS (Operating System) patched? Disk encrypted?
Quarantine / remediationNon-compliant device → restricted VLAN (Virtual Local Area Network) to fix itself
Role-based accessGuest → internet only; employee → full; IoT (Internet of Things) → isolated
Dynamic VLAN assignmentPut devices on the right segment automatically
Guest onboardingCaptive portal, sponsored access
RADIUS
The AAA (Authentication, Authorization, and Accounting) Workhorse
RADIUS (Remote Authentication Dial-In User Service) is the protocol behind most network authentication. It provides AAA: Authentication (who are you?), Authorization (what may you do?), and Accounting (what did you do? — logging/billing). It centralizes credentials so every switch and AP checks against one source (often tied to Active Directory). TACACS+ (Terminal Access Controller Access-Control System Plus) is a Cisco-oriented alternative more focused on device administration.

📡 Network Monitoring — Seeing What Flows Through NET • Operations ▶
WHY MONITOR
You Can't Manage What You Can't See
Network monitoring tells you device health, bandwidth use, errors, and unusual traffic — essential for both operations (is the link saturated? is a switch down?) and security (is data being exfiltrated? is there C2 traffic?). Different techniques answer different questions, from device health to per-flow detail.
SNMP
Polling Device Health
SNMP (Simple Network Management Protocol) lets a monitoring system query devices (switches, routers, servers, printers) for metrics — interface status, CPU (Central Processing Unit), temperature, traffic counters. Devices expose values in a hierarchical database (MIB) addressed by OIDs. Tools like Zabbix, LibreNMS, and PRTG poll via SNMP and graph/alert on the results.

FLOW DATA
NetFlow / IPFIX / sFlow — Who Talked to Whom
Flow data records metadata about conversations (source/dest IP, ports, protocol, bytes) without capturing full packet contents. It answers "who is talking to whom, how much?" — invaluable for capacity planning, billing, and security (spotting exfiltration, scanning, or C2 beaconing) at scale, far more cheaply than full packet capture.

Beginner Active Directory & LDAP (Lightweight Directory Access Protocol) – Enterprise Identity 101
Core Concept
What Is Active Directory?
Active Directory (AD) is Microsoft's directory service — the central phonebook of every Windows enterprise. It stores users, computers, groups, and policies in a tree of Organizational Units (OUs). When you log in at work, your laptop asks a Domain Controller (DC) to verify your password.

Key vocabulary:
• Domain – a boundary of administration (e.g. corp.example.com).
• Forest – one or more domains that trust each other.
• OU – a folder inside AD used to organise objects.
• GPO – Group Policy Object; rules pushed to computers/users.
• DC – Domain Controller; the server that runs AD.

"Not my circus, not my monkey" — if you are not the AD admin, do not make changes in AD. Escalate to the team that owns it.
Protocol
LDAP – How Applications Talk to AD
LDAP (Lightweight Directory Access Protocol) is the language software uses to query AD. Every object has a Distinguished Name (DN) — a path like a file system path:
CN=Alice Smith,OU=Finance,DC=corp,DC=example,DC=com

Common LDAP operations:
• Bind – authenticate (log in) to the directory.
• Search – find objects matching a filter.
• Add / Modify / Delete – manage objects (admin only).

Port 389 = plain LDAP  |  Port 636 = LDAPS (Lightweight Directory Access Protocol over SSL) (TLS encrypted — always prefer this).
# Query AD with Python ldap3 (read-only example) from ldap3 import Server, Connection, ALL, SUBTREE server = Server('ldaps://dc01.corp.example.com', get_info=ALL) conn = Connection(server, user='corp\svc_readonly', password='S3cur3P@ss!', auto_bind=True) # Find all users in the Finance OU conn.search( search_base='OU=Finance,DC=corp,DC=example,DC=com', search_filter='(&(objectClass=user)(!(userAccountControl:1.2.840.113556.1.4.803:=2)))', search_scope=SUBTREE, attributes=['cn', 'mail', 'department'] ) for entry in conn.entries: print(entry.cn, entry.mail) conn.unbind() # The filter above: objectClass=user AND NOT disabled (bit 2 of UAC)
Authentication
Kerberos in Plain English
Kerberos is the default authentication protocol for AD domains. Think of it as a theme-park wristband system:

1. You show your password once to the Key Distribution Center (KDC) on the DC.
2. The KDC gives you a Ticket-Granting Ticket (TGT) — your all-day wristband.
3. When you access a resource (file share, web app), you show the TGT to get a Service Ticket — a ride ticket for that specific attraction.
4. The resource trusts the service ticket without ever seeing your password again.

Why this matters for beginners: you never type your password again during the work day — Single Sign-On (SSO). Kerberos tickets expire (default 10 hours), so you may be prompted again next day.
Best Practice
Principle of Least Privilege in AD
"Assume" makes an ass out of you and me — never assume a user needs more permissions than their job requires. In AD:

• Give users standard accounts for daily work.
• Admins use a separate admin account (e.g. a-alice) only when elevated tasks are needed.
• Service accounts get only the groups they need.
• Review group memberships quarterly — "account creep" is real.

The Domain Admins group is the most powerful group in the domain. Its membership list should be tiny and audited constantly.
Beginner Cloud Networking – VPC (Virtual Private Cloud), Subnets & Security Groups
Core Concept
What Is a VPC?
A Virtual Private Cloud (VPC) is your own private network inside a cloud provider (AWS, Azure, GCP). Think of it as renting a section of a data centre and installing your own private network switches — except it's all software.

Key building blocks:
• VPC – the outer boundary; you choose the IP (Internet Protocol) range (e.g. 10.0.0.0/16 = ~65 000 addresses).
• Subnet – a slice of the VPC in one availability zone. Public subnets reach the internet; private subnets do not.
• Internet Gateway (IGW) – the door between your VPC and the public internet.
• NAT (Network Address Translation) Gateway – lets private-subnet resources make outbound internet calls without being reachable from outside.
• Route Table – rules that decide where packets go (like a router's routing table).
• Security Group – a stateful firewall attached to an individual resource (VM, load balancer).

"Assume" makes an ass out of you and me — never assume a cloud resource is private just because it's in a VPC. Check security groups AND network ACLs (Access Control List); both must permit the traffic.
AWS (Amazon Web Services) Example
Building a VPC with AWS CLI (Command Line Interface)
AWS CLI lets you build the entire network from the command line. This is the same thing the console does behind the scenes.
# Create a VPC aws ec2 create-vpc --cidr-block 10.0.0.0/16 --query Vpc.VpcId --output text # Output: vpc-0abc1234def567890 # Create a public subnet (AZ us-east-1a) aws ec2 create-subnet --vpc-id vpc-0abc1234def567890 --cidr-block 10.0.1.0/24 --availability-zone us-east-1a # Create a private subnet aws ec2 create-subnet --vpc-id vpc-0abc1234def567890 --cidr-block 10.0.2.0/24 --availability-zone us-east-1a # Attach an internet gateway aws ec2 create-internet-gateway --query InternetGateway.InternetGatewayId aws ec2 attach-internet-gateway --internet-gateway-id igw-0xyz --vpc-id vpc-0abc1234def567890 # Security group: allow SSH from your IP only aws ec2 create-security-group --group-name web-sg --description "Web server SG" --vpc-id vpc-0abc1234def567890 aws ec2 authorize-security-group-ingress --group-id sg-0xyz --protocol tcp --port 22 --cidr 203.0.113.5/32 # your IP only!
Best Practice
The Shared Responsibility Model
Cloud providers operate a Shared Responsibility Model: the provider secures the infrastructure of the cloud; you secure everything in the cloud.

AWS/Azure/GCP handles: Physical data centres, hypervisor security, global network, managed service patches.

You handle: VM (Virtual Machine) OS (Operating System) patches, security group rules, S3 (Simple Storage Service) bucket permissions, IAM (Identity and Access Management) roles, encryption of your data, application code security.

"Not my circus, not my monkey" only applies to the provider's layer. Misconfigured S3 buckets, open security groups, and leaked IAM keys are 100 % your responsibility. Most cloud breaches are misconfiguration, not a failure by the provider.
Beginner DNS (Domain Name System) Deep-Dive – How Domain Names Actually Work
Core Concept
The DNS Resolution Walk
When you type www.example.com in a browser, this is what happens before the first byte of the page arrives:

1. Browser checks its local cache — did we look this up recently?
2. OS (Operating System) checks /etc/hosts (or Windows Hosts file) — manual overrides.
3. OS asks the Recursive Resolver (usually your router or ISP, or 8.8.8.8/1.1.1.1).
4. Resolver asks a Root Name Server (.): "Who handles .com?"
5. Root refers to the .com TLD server: "Ask ns1.example.com."
6. Resolver asks ns1.example.com: "What's the IP (Internet Protocol) for www?"
7. Authoritative answer returned: 93.184.216.34.
8. Resolver caches the result for the TTL (Time To Live); returns it to your browser.

Total time: usually 10–100 ms. Cached lookups: <1 ms.

DNS was designed in the 1980s with no security. Several attacks exploit this:

• Always have at least two NS servers in different locations for redundancy.
• Use split-horizon DNS — internal names resolve to private IPs; external names resolve to public IPs.

Beginner Packet Analysis – Reading the Network's Mind with Wireshark
Core Concept
Why Capture Packets?
Every problem on a network eventually shows up in the packets — slow apps, failed connections, intrusions, misconfigurations. A packet capture (pcap) is ground truth: it shows exactly what was sent and received, byte for byte.

Tools:
• tcpdump — command-line capture; runs anywhere, even on headless servers.
• Wireshark — GUI (Graphical User Interface) analysis; the gold standard for deep inspection.
• tshark — Wireshark's CLI (Command Line Interface) sibling; great for scripting and automation.

"Not my circus, not my monkey" — capturing traffic on a network you don't own or have authorization for is illegal in most jurisdictions (wiretapping laws). Always get written authorization.
Capture
Capturing Traffic with tcpdump
tcpdump uses Berkeley Packet Filter (BPF) syntax to select exactly the traffic you care about — capturing everything creates huge files and noise.
# Capture all traffic on eth0, write to a file (analyse later in Wireshark) sudo tcpdump -i eth0 -w capture.pcap # Capture only HTTP traffic (port 80) with full packet content sudo tcpdump -i eth0 -s 0 -w http.pcap port 80 # Capture traffic to/from a specific host sudo tcpdump -i eth0 host 192.168.1.50 # Capture traffic between two hosts on a specific port sudo tcpdump -i eth0 'host 192.168.1.50 and host 192.168.1.10 and port 443' # Show packets live, with readable ASCII (good for HTTP debugging) sudo tcpdump -i eth0 -A port 80 # Capture only SYN packets (new connection attempts — good for scan detection) sudo tcpdump -i eth0 'tcp[tcpflags] == tcp-syn' # Rotate captures every 100MB, keep last 10 files (long-running capture) sudo tcpdump -i eth0 -w /data/cap.pcap -C 100 -W 10

Beginner DNS (Domain Name System) Deep Dive – How Name Resolution Really Works
Mindset

Assume makes an ass out of you and me

When a website "won't load," don't assume it's the web server. DNS failures look identical to outages from the user's perspective. Walking the resolution chain step by step — instead of guessing — is what separates a five-minute fix from an hour of chasing the wrong problem.

Concept

The resolution chain, in order

When you type example.com into a browser, your computer doesn't magically know where to send the request. It walks a chain of lookups:

StepWhat happensWhere it's checked
1. Browser cache"Have I looked this up in the last few minutes?"Browser memory
2. OS cache"Does the operating system already know this?"systemd-resolved / dnsmasq / Windows DNS Client
3. Hosts file"Is there a manual override?"/etc/hosts or C:\Windows\System32\drivers\etc\hosts
4. Recursive resolver"Ask my configured DNS server (ISP, 1.1.1.1, 8.8.8.8) to find it"/etc/resolv.conf
5. Root → TLD → authoritativeThe resolver walks the DNS hierarchy until it finds the authoritative answerGlobal DNS infrastructure

Most "the website is down" tickets are solved at step 2 or 3 — a stale cache entry or a leftover hosts file edit from testing months ago.

Hands-on

Tracing resolution yourself

# See which resolver your system is configured to use
cat /etc/resolv.conf

# Look up a name and show the full trip — timing included
dig example.com

# Trace the entire chain from the root servers down (educational, slower)
dig +trace example.com

# Ask a *specific* DNS server directly, bypassing your default resolver
dig @1.1.1.1 example.com

# Check what record types exist — A (IPv4), AAAA (IPv6), MX (mail), TXT, CNAME
dig example.com MX
dig example.com TXT

# Reverse lookup: what name does this IP resolve back to?
dig -x 93.184.216.34

The +trace flag is especially good for learning — it shows the actual hierarchy: your resolver asks a root server "who handles .com?", then asks that TLD server "who handles example.com?", then finally asks the authoritative server for the actual IP (Internet Protocol).

Common pitfall

"It works on my machine" — DNS cache edition

A classic scenario: a developer changes a DNS record, tells you "it's updated," and your browser still shows the old site. Both of you are right — the record changed at the authoritative server, but your resolver cached the old answer for its full TTL (time-to-live). Common fixes, in order of how invasive they are:

# Flush just your local OS resolver cache (Linux with systemd-resolved)
sudo resolvectl flush-caches

# macOS
sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder

# Windows (run as administrator)
ipconfig /flushdns

# Or simply query a different resolver to sanity-check the *real* current value
dig @8.8.8.8 example.com +short

If a record was just changed, remember that TTL still applies globally — other people's resolvers around the world will keep serving the cached answer until their TTL expires too. This is why planned DNS cutovers lower the TTL days in advance.

Beginner VPNs (Virtual Private Network) Explained – Tunnels, Encryption, and What They Don't Do
Concept

A VPN is a private tunnel through a public road

Imagine the internet as a public highway system — anyone running the right equipment at the right point could, in theory, see which trucks are going where. A VPN (Virtual Private Network) builds an encrypted tunnel through that highway: your traffic still travels over the same public infrastructure, but it's wrapped in a layer that hides its contents from anyone watching the road, and makes it appear to originate from the tunnel's far end rather than your actual location.

Concept

Two very different reasons people use VPNs

Use caseWhat it actually doesCommon protocols
Corporate / remote-access VPNLets an employee's laptop join the company's internal network from anywhere, as if it were plugged in at the officeWireGuard, OpenVPN, IPsec/IKEv2, Cisco AnyConnect
Consumer / privacy VPNRoutes your traffic through a third-party provider's server so your ISP (Internet Service Provider) and local network can't see *what* you're accessing — though the VPN provider now canWireGuard, OpenVPN (commercial offerings)

These solve different problems for different threat models. A corporate VPN exists so IT can extend a trusted network boundary to remote workers; a consumer VPN exists to shift *who* has visibility into your traffic — from your ISP to the VPN provider — which is a meaningfully different guarantee than "no one can see what I do online."

Hands-on

Setting up a minimal WireGuard tunnel (lab environment)

# Install WireGuard (Debian/Ubuntu)
sudo apt install wireguard

# Generate a public/private keypair for this peer
wg genkey | tee privatekey | wg pubkey > publickey

# Minimal config: /etc/wireguard/wg0.conf
# (replace placeholders with real keys and addresses)
#
# [Interface]
# PrivateKey = <this peer's private key>
# Address = 10.10.0.2/24
#
# [Peer]
# PublicKey = <remote peer's public key>
# Endpoint = vpn.example.com:51820
# AllowedIPs = 0.0.0.0/0

The AllowedIPs = 0.0.0.0/0 line is the one to read carefully — it tells the system to route all traffic through the tunnel ("full tunnel"), versus a narrower range that only sends specific destinations through it ("split tunnel"). Getting this wrong is one of the most common VPN misconfigurations: too broad and you may break local network access; too narrow and traffic you meant to protect goes out in the clear.

Common pitfall

"I'm on a VPN, so I'm anonymous" — assume makes an ass out of you and me

A VPN hides your traffic's path and contents from your local network and ISP — it does not make you anonymous to the websites you visit. You can still be tracked through cookies, browser fingerprinting, account logins, and the VPN provider itself can see (and in some jurisdictions, may be compelled to log and disclose) your activity. Treat "I'm using a VPN" as one layer of a privacy strategy, not a magic cloak — and always read a provider's actual logging policy rather than assuming "no logs" means what it sounds like.

Beginner Subnetting Without the Headache – CIDR (Classless Inter-Domain Routing) Notation Made Practical
Concept

A subnet is just "how big is this neighborhood?"

An IP (Internet Protocol) address tells you a device's location; a subnet mask tells you how many of its neighbors share the same local "neighborhood" — the group of addresses that can talk to each other directly, without going through a router. CIDR notation (/24, /26, etc.) is just a compact way of writing that mask: the number after the slash tells you how many bits are reserved for identifying the network itself, leaving the rest for individual hosts.

Concept

The CIDR cheat sheet beginners actually reach for

CIDRSubnet maskUsable hostsCommon use
/24255.255.255.0254Typical small office or home network
/25255.255.255.128126Splitting a /24 in half — two departments, one building
/26255.255.255.19262A single floor or smaller team
/27255.255.255.22430A small lab, a rack of servers, a point-to-point link group
/30255.255.255.2522A direct link between two routers — exactly enough for both ends

Notice the pattern: every step from /24 toward /32 cuts the available addresses roughly in half. "Usable hosts" is two less than the raw count — one address is reserved to identify the network itself, and one is reserved as the broadcast address that reaches every device in that subnet at once.

Hands-on

Let the tools do the arithmetic — verify, don't memorize

# pip install — actually it's built into Python's standard library!
import ipaddress

network = ipaddress.ip_network("192.168.10.0/26")
print(f"Network address:   {network.network_address}")
print(f"Broadcast address: {network.broadcast_address}")
print(f"Usable hosts:      {network.num_addresses - 2}")
print(f"First usable host: {list(network.hosts())[0]}")
print(f"Last usable host:  {list(network.hosts())[-1]}")

# Quick check: is this address inside that subnet?
ip = ipaddress.ip_address("192.168.10.40")
print(f"{ip} in {network}? {ip in network}")

# Splitting a network into smaller subnets — handy for planning
# departmental allocations from a single block you've been given
for sub in network.subnets(new_prefix=28):
    print(f"  Sub-block: {sub}")

This is the honest secret of subnetting: nobody who works with networks daily does the binary math by hand every time. They've internalized the cheat-sheet patterns for common cases, and they reach for a calculator (or ipaddress, or ipcalc on the command line) to double-check anything unusual. Knowing how it works conceptually — and knowing how to verify it — beats memorizing tables you'll forget under pressure.

Mindset

Assume makes an ass out of you and me

"That device should be able to reach the server, they're both on the 192.168.x.x range" is a classic trap — two addresses can look similar and still be in completely different subnets, unable to communicate without a router between them. Before troubleshooting further up the stack, verify the actual subnet boundaries with a tool like the one above rather than eyeballing the addresses and assuming they're neighbors.

Beginner Load Balancers Explained – Spreading the Work Around
Concept

A load balancer is a traffic cop for your servers

A load balancer sits in front of a group of servers and decides which one should handle each incoming request — spreading the work around so no single server gets overwhelmed, and so the service keeps running even if one server fails. From the outside, users see a single address; behind that address, the load balancer quietly routes them to whichever healthy server makes the most sense at that moment.

Concept

Common balancing strategies, and when each shines

StrategyHow it decidesGood fit when...
Round robinCycles through servers in order: 1, 2, 3, 1, 2, 3...All servers are roughly equal in capacity and requests are roughly equal in cost

Concept

The unsung hero: health checks

A load balancer is only as good as its ability to know which servers are actually healthy. It periodically polls each server — often hitting a dedicated /healthz endpoint — and silently stops sending traffic to any server that fails to respond correctly. This is the mechanism that turns "one server crashed" from a customer-facing outage into a non-event nobody outside the on-call team ever notices.

# A minimal health endpoint, the kind a load balancer polls every few seconds
from flask import Flask, jsonify
app = Flask(__name__)

@app.route("/healthz")
def health_check():
    checks = {
        "database": database_is_reachable(),
        "cache": cache_is_reachable(),
        "disk_space_ok": get_free_disk_percent() > 10,
    }
    healthy = all(checks.values())
    status_code = 200 if healthy else 503
    return jsonify(checks), status_code

# A load balancer that sees repeated 503s here will quietly stop
# routing traffic to this instance — without a single human noticing,
# until someone reviews the dashboards and finds the graceful save
Mindset

Assume makes an ass out of you and me

A health check that only verifies "is the web server process running?" can report "healthy" while the actual database connection behind it is completely down — leaving users staring at error pages from a server the load balancer confidently considers fine. A good health check verifies the things that actually matter to the user's experience, not just the easiest thing to check. "The process is running" and "the service actually works" are two different claims — don't let your monitoring assume they're the same.

Beginner The TLS (Transport Layer Security) Handshake – What Actually Happens Before "https://" Feels Safe
Concept

The padlock icon represents a surprisingly elegant negotiation

Every time you load an HTTPS (HyperText Transfer Protocol Secure) site, your browser and the server perform a rapid multi-step negotiation called the TLS handshake — establishing trust and agreeing on encryption, all before a single byte of your actual page content is transmitted. It happens in well under a second, which is part of why it's so easy to never think about. Understanding the broad strokes demystifies a huge portion of "how the secure web works."

Concept

The handshake in (roughly) five steps

StepWhat happens
1. Client HelloYour browser says hello and lists the encryption methods ("cipher suites") it supports, plus a random number used later in key generation.
2. Server Hello + CertificateThe server picks a cipher suite both sides support and sends back its digital certificate — proof of identity issued by a trusted Certificate Authority (CA).
3. Certificate verificationYour browser checks that the certificate is valid, unexpired, matches the domain you're visiting, and was signed by a CA it trusts. This is the step that turns a green padlock into something meaningful rather than decorative.
4. Key exchangeBoth sides use cryptographic math (often Diffie-Hellman) to agree on a shared session key — without ever transmitting that key in a form an eavesdropper could use.
5. Secure session beginsFrom here on, all traffic is encrypted with the session key using fast symmetric encryption — the certificate-based "slow" cryptography has done its job and steps aside.
Concept

Inspecting a real certificate from the command line

You don't need special tools to see this in action — openssl can show you exactly what your browser is silently checking on every visit:

# Connect and dump the certificate chain for a domain:
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null | openssl x509 -noout -text

# Useful fields to look for in the output:
#   Issuer:        which Certificate Authority vouched for this site
#   Subject:       the domain(s) the certificate is valid for
#   Validity:      the "Not Before" / "Not After" window -- expired
#                  certificates are a surprisingly common outage cause
#   Signature Algorithm:  the cryptographic method used to sign it
Concept

Why "the padlock is green" isn't the same as "this site is trustworthy"

This is a critical distinction that "assume makes an ass out of you and me" captures perfectly. TLS guarantees two specific things: that your connection to the server is encrypted in transit, and that the certificate matches the domain you typed. It guarantees nothing whatsoever about whether the organization running that domain is honest, competent, or safe to hand your data to. Attackers can — and routinely do — obtain valid certificates for convincingly-misspelled lookalike domains. The padlock confirms "this connection isn't being eavesdropped on right now." It does not confirm "you should trust what's on the other end of it." Those are two different questions, and conflating them is one of the most common (and most exploited) assumptions on the web.

🗺️ BGP (Border Gateway Protocol) — How the Internet Routes Between Networks Routing ▶
Concept
The Protocol That Glues the Internet Together
Protocols like OSPF (Open Shortest Path First) route inside one organization. But the internet is ~75,000 independent networks (ISPs, clouds, universities) that must agree on how to reach each other. BGP — the Border Gateway Protocol — is how they do it. Each network is an Autonomous System (AS) with a number, and BGP is how ASes advertise which IP ranges they can reach and learn routes to everywhere else. It's the internet's routing table, assembled by agreement rather than central control.
Reference

How It Chooses
Path Selection & Why It's Different
BGP is a path-vector protocol: it doesn't pick the route with the least latency or fewest hops the way an interior protocol might — it picks based on policy. Operators tune attributes to prefer cheaper or contractually-preferred paths.
Attribute (in order)Effect

Fragility
When BGP Goes Wrong
BGP largely runs on trust, which is also its weakness. A route hijack — an AS advertising prefixes it doesn't own — can silently reroute or black-hole traffic (it has taken down large chunks of the internet, sometimes by accident via a route leak, a misconfigured advertisement). Defenses: RPKI (Resource Public Key Infrastructure) (cryptographically validates who may originate a prefix) and prefix filtering between peers. This fragility is why a single fat-fingered BGP change at a big provider can make headlines.
🚦 QoS — Quality of Service & Traffic Shaping Networking ▶
Concept
Not All Packets Are Equal
When a link gets congested, something has to give. Without Quality of Service, the network drops packets indiscriminately — and a big file download can wreck a video call sharing the same pipe. QoS lets you classify traffic and give the time-sensitive kinds (voice, video, gaming) priority over the ones that don't care about a little delay (backups, email, updates). It manages a scarce resource — bandwidth — by policy instead of first-come-first-served.

Where You Meet QoS
QoS only helps on links you control — your router, your WAN (Wide Area Network), an enterprise LAN (Local Area Network) — because markings are honored within an administrative domain and often reset at the public internet boundary (the internet is best-effort; your DSCP tags mean nothing to your ISP unless you buy an SLA). Classic uses: prioritizing VoIP (Voice over Internet Protocol) on an office network, keeping a video call smooth on a home router, and guaranteeing latency-sensitive traffic across an MPLS (Multiprotocol Label Switching) or SD-WAN (Software Defined Wide Area Network) link.
🚀 HTTP/2 (HyperText Transfer Protocol version 2), HTTP/3 (HyperText Transfer Protocol version 3) & QUIC (Quick UDP Internet Connections) — Modern Web Transport Networking ▶
Concept
Making the Web Fast, One Protocol at a Time
HTTP/1.1 (1997) sends one request at a time per connection and in plain text — browsers opened 6+ connections per site just to keep up. HTTP/2 and HTTP/3 keep the same familiar HTTP (HyperText Transfer Protocol) semantics (methods, headers, status codes) but completely rework how bytes move on the wire to kill latency. Same API (Application Programming Interface), radically faster transport.

Key Ideas
Multiplexing & Head-of-Line Blocking
HTTP/2's big win is multiplexing: many requests share one connection as independent "streams," so a slow response doesn't block the others at the HTTP layer. But they still ride one TCP connection — and if a single TCP packet is lost, TCP stalls all streams until it's retransmitted. That's head-of-line blocking at the transport layer, HTTP/2's remaining weakness.

Because QUIC lives in user space (not the OS kernel like TCP), it evolves faster. The trade-off: some middleboxes/firewalls throttle or block UDP, so clients fall back to HTTP/2 over TCP when needed.
🕰️ NTP (Network Time Protocol) & Time Synchronization — Why Clocks Matter Networking ▶
Concept
A Few Seconds of Drift Breaks Surprising Things
Every computer has a cheap quartz clock that drifts — seconds per day. On one laptop that's harmless; across a fleet it's a disaster. The Network Time Protocol keeps machines synchronized to within milliseconds of a reference time by measuring the round-trip delay to time servers and correcting for it. It's invisible infrastructure — until a clock is wrong and logins fail, logs won't correlate, and TLS (Transport Layer Security) certificates appear "not yet valid."
Why It Matters
What Breaks When Clocks Disagree
SystemFailure With Bad Time
TLS / certificatesCerts have valid-from/valid-to windows; a skewed clock rejects good certs (or trusts expired ones).
Kerberos / AD (Active Directory) authTickets are time-stamped; default tolerance is ~5 minutes — beyond that, logins fail.
MFA (Multi-Factor Authentication) / TOTP codesTime-based one-time codes rotate every 30s; a wrong clock rejects valid codes.
Log correlationInvestigating an incident across servers is impossible if their timestamps don't line up.
Databases / distributed systemsOrdering, leases, and conflict resolution can misbehave with clock skew.

Most machines sync from public pools (pool.ntp.org) or an internal server. Best practice: point your fleet at a couple of internal NTP servers that themselves sync upstream — consistent time, less external dependence.

🔐 DNSSEC (Domain Name System Security Extensions) & Encrypted DNS (Domain Name System) — DoH (DNS over HTTPS) / DoT (DNS over TLS) DNS Security ▶

🗄️ Config Management on Network Devices — Archives, Upgrades & Not Locking Yourself Out Network Ops ▶
Concept
The Device You Are Configuring Is the Device You Are Connected Through
Network gear has a hazard servers do not: the management path runs over the thing being changed. One wrong ACL (Access Control List) line, one interface shut, one VLAN (Virtual Local Area Network) removed from the trunk, and the session dies mid-change with the device in a half-configured state — often in a building several hours away. Every safe network-change practice exists to survive that moment. 
# The safety net: reload with a timer, cancel it only once you can still get in
   reload in 10            # device reboots to the saved config in 10 minutes
   # ... make the risky change ...
   # still connected? then:
   reload cancel
   write memory            # only NOW commit it to startup

# Commit-confirm on platforms that have it does the same thing natively:
   commit confirmed 10     # auto-rollback unless confirmed
The discipline is simple and near-absolute: never save a risky change until you have proved you can still reach the device afterwards. The timed reload turns an outage that needs a site visit into a ten-minute wait.
Technique

Every organisation believes it backs up network configs, and a surprising number discover during an incident that the archive is stale, incomplete, or unreadable without the device that produced it.
PracticeWhy

Firmware upgrades are the change most likely to end in a device that does not come back, and they are frequently done in bulk to save a maintenance window. The order below costs more windows and far fewer incidents.

🔌 Switch Port Configuration — Access, Trunk, Port Security & Edge Protection Network Ops ▶
Reference
Access or Trunk — and the Mismatch That Causes Most VLAN (Virtual Local Area Network) Tickets
An access port carries one VLAN untagged; a trunk carries several, tagged, with one untagged native VLAN. Nearly every "the device gets no address" or "these two sites cannot see each other" ticket is a mismatch between the two ends of a link — one side trunking, the other not, or a VLAN missing from the allowed list. 
# Access port — one VLAN, for an end device
   interface Gi1/0/10
    switchport mode access
    switchport access vlan 20
    switchport voice vlan 110      # phone + PC on one cable
    spanning-tree portfast
    spanning-tree bpduguard enable

# Trunk — several VLANs, to another switch
   interface Gi1/0/48
    switchport mode trunk
    switchport trunk allowed vlan 10,20,30,110
    switchport trunk native vlan 999   # unused VLAN, deliberately
Always state the allowed list explicitly. A trunk left to allow everything carries every VLAN on the switch to wherever that link goes, which is both a broadcast problem and a segmentation failure nobody notices until an audit.
Concept
PortFast and BPDU (Bridge Protocol Data Unit) Guard Are a Pair — Never One Without the Other
PortFast skips the spanning-tree listening and learning states so an end device gets a link immediately instead of waiting half a minute. That is a real usability win and it also means the port will happily join a loop instantly if someone plugs in a switch. BPDU guard is the other half: if a spanning-tree frame ever arrives on that port, it shuts down. Enabling PortFast alone converts a slow-boot complaint into an outage risk.
ProtectionStops
BPDU guardA rogue or accidental switch on an access port taking over the topology
Root guardA downstream switch becoming root and inverting your traffic flows
Loop guardA unidirectional link turning a blocked port into a forwarding loop
Storm controlBroadcast or multicast floods saturating the segment
DHCP (Dynamic Host Configuration Protocol) snoopingA rogue DHCP server handing out addresses and a default gateway
DHCP snooping deserves emphasis: an accidental home router plugged in backwards is one of the most common causes of a floor-wide outage, and it presents as "the internet is down" for some users and not others.
Troubleshooting
Port Security — Useful, and the Thing That Fills Your Ticket Queue
Port security limits which MAC (Media Access Control) addresses may use a port. It genuinely stops casual switch sprawl, and configured carelessly it disables ports whenever someone docks a different laptop. The violation mode is the setting that decides which of those you get.
Violation modeBehaviourUse when
ProtectDrops offending traffic silentlyAlmost never — silent failures are unhelpful
RestrictDrops it and logs/countsSensible default for most access ports
ShutdownErr-disables the port entirelyHigh-security areas, with recovery configured
If shutdown is used, set err-disable recovery with a timer, or every violation becomes a truck roll. And for real access control the answer is 802.1X & NAC — Who Gets On the Network? — port security is a MAC filter, and MAC addresses are trivially changed.
🧱 Firewall Policy Design — Zones, Rule Order & What the Implicit Deny Really Does Network Ops ▶
Concept
First Match Wins, and That Is the Whole Design Problem
Firewall rule bases are evaluated top to bottom and stop at the first match. Every misconfiguration follows from that: a broad permit near the top silently disables everything specific below it, and a deny added at the bottom of a base that already permits the traffic does nothing at all. The rule base is a program with one control-flow construct, and reading it in order is how you understand it.
OrderRulesWhy here
1Explicit denies for known-badNothing below can accidentally permit them
2Narrow, high-volume permitsMatched early; keeps the common path fast
3General business permitsThe bulk of the base
4Explicit deny-all, with loggingThe implicit deny does not log; this one does
Row 4 is the single highest-value line in most rule bases. The implicit deny at the end of every firewall drops traffic silently, so without an explicit logged deny-all you have no record of what was blocked — and troubleshooting becomes guesswork.
Technique
Zones Turn N² Rules Into Something Maintainable
Writing rules between individual addresses produces a base that grows quadratically and that nobody dares clean up. Grouping interfaces into zones — and objects into groups — means policy is expressed as intent between areas, which is both readable and auditable.
PracticeEffect
Zones for trust levels, not for physical topologyPolicy survives a hardware change
Named object groups for servers and servicesAdding a server is one group edit, not six rules
A comment on every rule: who, why, ticket, dateThe only thing that makes cleanup possible later
Expiry dates on temporary rulesOtherwise "temporary" is permanent — check any old firewall
Review hit counts periodicallyZero-hit rules are candidates for removal, with care
A zero-hit rule is not automatically safe to delete — it may cover a disaster-recovery path or an annual process. Check before removing, and record the check, or the next person repeats the analysis.
Concept
Application-Aware Policy Changes What a Rule Means
Modern firewalls can match on the identified application and the authenticated user rather than on port and address. That is genuinely stronger — permitting a specific application rather than "TCP (Transmission Control Protocol) 443, which is everything" — and it introduces a behaviour that surprises people: identification requires seeing some traffic first, so the first packets of a session are evaluated before the application is known, and a policy can change decision mid-flow. Rules still need a sensible port-based fallback, and "any application on 443" is not a migration to application-aware policy.

Troubleshooting
Hairpinning — Why It Works From Outside and Not From Inside
The classic report: the new web server is reachable from home and not from the office. The cause is nearly always hairpin NAT. An internal client resolves the public address, sends traffic to the firewall, which translates the destination inward — but the server replies directly to the internal client, whose stack drops the reply because it came from an address it never sent to. 
# The broken path
   client 10.0.1.50  ->  public 203.0.113.10  ->  firewall DNAT  ->  server 10.0.2.20
   server 10.0.2.20  ->  replies DIRECTLY to 10.0.1.50
   client            ->  drops it: "I was talking to 203.0.113.10, who are you?"

# Three fixes, in order of preference
   1. Split-horizon DNS — internal clients resolve the INTERNAL address.
      Simplest, no NAT involved, and it is what most estates should do.
   2. Hairpin NAT — also source-NAT the internal client so the reply
      returns via the firewall.
   3. Put the service where both can reach it directly.
Split-horizon DNS (Domain Name System) is the right answer far more often than the NAT fix. Internal clients reaching internal servers by their internal address is simpler, faster, and removes the firewall from a path it does not need to be in.
Concept
Order of Operations Decides Which Address Your Rule Should Match
Whether a security policy sees the pre-translation or post-translation address depends on the platform, and getting it wrong produces a rule that never matches while looking entirely correct. Some platforms evaluate policy against the original destination but route using the translated one; others translate first. There is no universal answer — check the vendor's documented order once, write it down, and stop guessing.

🩺 Firewall Troubleshooting — Policy Lookup, the Session Table & Capture Network Ops ▶
Flow
Four Questions, In This Order
"The firewall is blocking it" is a hypothesis, and it is wrong about half the time. These four questions establish whether the firewall is even involved, and they take a couple of minutes.
#QuestionAnswered by
1Did the traffic arrive at all?Capture on the ingress interface — if nothing, it is a routing or client problem
2Which policy matched?The policy-lookup or packet-tracer tool, which names the rule
3Was a session created?The session table — an entry means it was permitted
4Did the reply come back?Capture on egress; asymmetric routing shows up here
Most firewalls have a built-in path simulator that answers question 2 without sending any traffic. It is the single most underused tool on the box and it turns a debate into a rule name in seconds.
Reference
What the Session Table Tells You
Stateful firewalls permit return traffic because a session exists, so the session table is the record of what the firewall believes is happening. Reading it answers questions that logs alone cannot.
ObservationMeans
No session at allBlocked before creation, or never arrived — go back to question 1
Session exists, no return trafficThe far end is not answering, or the reply took another path
Session in a half-open stateA handshake never completed — often a filtered path further along
Session count climbing steadilySomething is not closing sessions; exhaustion is coming
Sessions timing out mid-conversationIdle timeout shorter than the application's keepalive
The last row causes some of the most frustrating intermittent faults in enterprise networks: a database connection pool idle for longer than the firewall's timeout, dropped silently, and discovered by the application only when it next tries to use the connection.
Concept
Asymmetric Routing Breaks Stateful Inspection, Silently
A stateful firewall must see both directions of a flow. If traffic leaves through one path and returns through another — a common outcome of adding a second link, a route change, or a misconfigured redundancy pair — the firewall sees replies for sessions it has no record of and drops them. The application reports timeouts, the firewall logs look ordinary, and the cause is elsewhere in the topology entirely.
📡 RF (Radio Frequency) Fundamentals & Site Surveys — Channels, Width & Co-Channel Interference Network Ops ▶
Concept
Wi-Fi Is a Shared Medium, and More Access Points Is Not More Capacity
Radios on the same channel take turns. Two access points on the same channel within earshot of each other do not double capacity — they halve each other's, because every transmission makes the other wait. This is co-channel interference, and it is why the most common enterprise wireless problem is too many access points at too much power rather than too few.
InstinctReality
"Coverage is bad — add access points"Often makes it worse; the clients were fine, the channel was busy
"Turn the power up"Extends the interference domain and clients still cannot shout back
"Use the widest channels available"Fewer non-overlapping channels; more contention in dense areas
"5 GHz everywhere solves it"Better, but shorter range and more walls in the way
Wider channels are a straight trade: more throughput per client where the air is quiet, fewer distinct channels to reuse where it is not. In a dense office, narrower channels and lower power usually outperform the aggressive settings that look better on paper.
Reference

"We need a site survey" is ambiguous. Which one depends on whether the network exists yet and whether the complaint is coverage or performance.

PassiveWhat does the RF environment look like?Validating coverage and finding interference

A predictive survey is a model, and models are only as good as their assumptions about walls. Validate one on site before ordering hardware — a plasterboard assumption that turns out to be concrete changes the design entirely.

Heat maps are usually drawn as signal strength, which is the least useful of the available views. Strong signal with poor performance is the normal failure in dense environments, and a signal-strength map is green precisely where the problem is.

Rack and Power Realities
Rack planning fails on three constraints, and only the first is obvious from a diagram.
ConstraintDetail
SpaceUnits, and the depth — deep servers do not fit shallow racks
PowerDual feeds from separate sources; a device with one supply defeats the design

The dual-feed detail is the one most often undermined in practice: two PDUs (Protocol Data Unit) from two sources are pointless if a single-supply device is plugged into one of them, and that is exactly what happens with switches, appliances and the KVM (Kernel-based Virtual Machine).

🌙 Cutover Nights — Go/No-Go, Comms & Rollback Triggers Network Ops ▶
Flow
Decide the Rollback Trigger Before You Start, Not at 3 a.m.
Every cutover reaches a moment where something is not working and the team has been awake for six hours. That is the worst possible moment to decide whether to persevere or roll back, because sunk cost and exhaustion both push the same way. Agreeing the trigger and the deadline in advance — in writing, with the decision-maker named — is what makes the decision survivable.
Agree beforehandExample
The point of no return"After the DNS (Domain Name System) change, rollback takes 4 hours"
The rollback deadline"If not validated by 04:00, we roll back regardless"
Who decidesOne named person, present, with authority
What counts as successA written checklist, tested, not "it looks fine"
What is acceptable to deferCosmetic issues do not stop a cutover; agree which are cosmetic
Technique
The Night Itself
The technical work is usually the part that goes to plan. What goes wrong is coordination, validation and the discovery of a dependency nobody listed.
PracticePrevents
A written runbook with per-step verification"I think that worked" as a completion criterion
One person driving, one verifyingBoth people typing on different devices
A bridge open, with a scribeLosing the timeline, which matters if it goes wrong

Comms before, during and afterUsers discovering the change by failing to work
Out-of-band access confirmed before startingLosing the device with no way back in
Test the out-of-band path at the start of the window, not when you need it. Console servers and cellular management links fail quietly for months, and the night of the cutover is when everyone finds out. The organisational half of this is Change Management – The Process That Prevents Self-Inflicted Outages in the Governance domain.
Concept
The Morning After Is Part of the Change
A cutover is not finished when the traffic flows. The first business morning is when the edge cases appear — the scanner nobody knew about, the scheduled job with a hard-coded address, the partner whose firewall allows only the old range. Plan the hypercare: who is watching, who takes the calls, and how long before the old path is decommissioned. Leaving the previous configuration in place for a week costs nothing and turns a crisis into a fallback.
🗺️ Network Documentation That Stays Current Network Ops ▶
Concept
Documentation Decays Unless Producing It Is Part of Changing Things
Every network has a diagram that was accurate on the day it was drawn. Documentation maintained as a separate activity always loses to the pressure of the work, so the only approaches that survive are the ones where the document is generated from reality or updated as part of the change itself.
ArtifactKeep current by
Logical topologyHand-drawn, reviewed quarterly — it encodes intent, so it cannot be generated
Physical/port mapGenerated from the devices; never hand-maintained
IP (Internet Protocol) address planA single authoritative source, updated at allocation time
ConfigsThe archive in version control — the config is the documentation
Cable scheduleUpdated as part of the physical change, or it is fiction within a month
The distinction in row one matters: a generated diagram shows what exists, and a hand-drawn one shows what was intended. Both are useful and they answer different questions — discrepancies between them are frequently the most interesting thing in the network.
Technique
Diagram for the Reader, Not for Completeness
A single diagram containing everything is unreadable and therefore unread. Several diagrams at different altitudes, each answering one question, get used — and being used is the only thing that keeps a document alive.
DiagramAnswers
Site overviewHow do the buildings connect, and what are the links?
Layer 3 / routingWhere do the subnets live and how does traffic get between them?
Layer 2 / VLANs (Virtual Local Area Network) per siteWhat is trunked where, and where does spanning tree root?
Security zones and pathsWhat crosses which boundary, through which device?
One-page "who to call"Circuit IDs, providers, support contracts, escalation numbers
That last row is the page most used during an outage and the one least often written. Circuit references and provider escalation numbers are exactly what nobody can find at 2 a.m., and they belong somewhere reachable when the network is down — which means not only on the network.
🏭 Vendor Firewall Concepts — The Ideas Behind the Different Consoles Network Ops ▶
Concept
Learn the Concepts; the Menus Are the Easy Part
Every enterprise firewall platform solves the same problems and names them differently, which makes moving between them feel harder than it is. The concepts below transfer; the console layouts do not, and both change between major releases. Anyone learning a second platform should map the vocabulary first and expect the underlying model to be familiar.
ConceptRoughly
ZoneA named group of interfaces at one trust level; policy is written between zones
Application identificationClassifying the traffic by what it actually is, not by its port
User identificationMapping addresses to directory users so policy can name people
Security profilesInspection bolted onto an allow rule — antivirus, IPS (Intrusion Prevention System), URL (Uniform Resource Locator) filtering

Concept
The Commit Model Is the Biggest Practical Difference
Some platforms apply each edit immediately; others build a candidate configuration that is committed as a unit. The difference changes how you work more than any feature. With a commit model you can make ten related changes and apply them atomically — but a commit is also a single point of failure, it can take minutes on a busy device, and one person's uncommitted edit ships with the next person's commit.
Immediate applyCandidate + commit
Each change live at onceChanges staged, then applied together
Half-finished states are reachableRelated changes land atomically
Rollback is another editRollback to a previous committed version
No shared-edit hazardCheck for others' pending edits before committing
On a commit-model platform, always review the pending diff before committing. Shipping a colleague's half-finished work because you committed the shared candidate is a classic and entirely avoidable outage.
Concept
Inspection Costs Throughput, and the Datasheet Knows It
Vendor throughput figures are quoted for several scenarios, and the gap between them is large. Raw firewall throughput with no inspection is the headline; the same device with application identification, IPS and TLS (Transport Layer Security) decryption enabled is a fraction of it. Sizing from the headline number is one of the most common and expensive procurement mistakes, and TLS decryption in particular is the heaviest feature on most platforms — check the decrypted throughput figure specifically, because that is the number your estate will actually run at.
