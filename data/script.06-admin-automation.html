🪢 The Object Pipeline — Why PowerShell Is Not Bash With Different Verbs Automation • PowerShell ▶
Concept
Unix Pipes Text and Re-Parses It; PowerShell Never Serialises in the First Place
awk, cut and sed exist because a Unix pipe throws the structure away: every program prints a formatted string and every downstream tool has to reconstruct the fields by counting columns. PowerShell inverts that. Get-Process does not emit text that looks like a table — it emits System.Diagnostics.Process instances, and the table you see is the formatter rendering them at the very end, for you, after the pipeline is over. Everything in between filters and sorts on typed properties.
Which means the habit that transfers from Bash is the bug. Grepping PowerShell output is not just unidiomatic, it is fragile in a way that passes review: a findstr Running over service output matches any service whose display name happens to contain the word, and column-position parsing breaks the day a machine name gets longer and the formatter widens the column. Neither failure shows up in the lab. 
# The transplanted Bash habit — matches DisplayName too, and column widths move
Get-Service | findstr Running

# The same intent, against the property that actually means it
Get-Service | Where-Object Status -eq 'Running'

# Objects survive the whole way: filter, sort, take, and only then render
Get-Process |
  Where-Object { $_.WorkingSet64 -gt 500MB } |
  Sort-Object WorkingSet64 -Descending |
  Select-Object Name, Id, @{n='WS_MB';e={[int]($_.WorkingSet64/1MB)}} -First 10
Reference
The Verbs That Do the Work, and What Each One Returns

Read the third column, not the second. Half of the confusing PowerShell bugs are someone treating the output type as unchanged when a cmdlet quietly replaced it — Select-Object handing back a property bag, Measure-Object handing back a report rather than a total.
Pitfall
Four Places the Object Model Leaks, and How Each One Looks When It Bites
Format-* in the middle of a pipeline. The formatters emit internal layout records, so anything downstream operates on those instead of your data. The fingerprint is unmistakable once you have seen it: a CSV (Comma-Separated Values) whose columns are ClassId2e4f51ef21dd47e99d3c952918aff9cd and whose rows read Microsoft.PowerShell.Commands.Internal.Format.FormatStartData. Nothing errored; the export simply captured the renderer. Format-* is the last thing on a line, always — if you want a file, go straight from objects to Export-Csv.
Objects that crossed a remoting boundary. Invoke-Command and PSSessions serialise on the wire and rehydrate as Deserialized.System.* property bags. Properties survive; methods do not. The fingerprint is a script that works locally and fails only against remote hosts, with "method invocation failed because … does not contain a method named 'Stop'". The fix is to do the acting inside the script block and return only the facts you need out of it.
Comparison operators against a collection. -eq on an array does not answer true or false, it filters and returns the matches. So if ($list -eq 'x') is true whenever any element matches, and a single $null element makes an emptiness check lie. Use -contains, or .Count, and put the literal on the left when comparing against something that might be $null.
Collecting when you meant to stream. Wrapping a pipeline in $(…) or assigning it to a variable materialises every object in memory; so does Sort-Object, which cannot emit anything until it has seen everything. That is fine for a thousand mailboxes and fatal for a hundred thousand log rows. ForEach-Object and Where-Object stream one object at a time — keep the pipeline unbroken and let it.
The decision is one question at every stage: does the next thing in this line need data, or is the next thing a person? Data means the objects stay objects and serialisation waits until the end. A person means you are finished — render, and stop. Automation that ignores that boundary is the source of the export nobody can read and the script that only fails in production; the wider discipline around that is in Automation Risk & Discipline — Blast Radius, Approval Gates & the Kill Switch.
📇 Microsoft Graph From PowerShell — The Modern Admin API (Application Programming Interface) Automation • Admin ▶
Concept
One API Behind Nearly Every Microsoft 365 Admin Task
The older service-specific modules (MSOnline, AzureAD) are retired or retiring, and the single forward path for automating users, groups, devices, Intune and more is Microsoft Graph. The Microsoft.Graph PowerShell module is a generated wrapper over the Graph REST (Representational State Transfer) API, so learning it teaches you the API underneath — and anything the cmdlets do not expose, you can still call as a raw request. 
# Connect with least privilege — name only the scopes you need
Connect-MgGraph -Scopes "User.Read.All","Group.Read.All"

# Cmdlets for the common paths…
Get-MgUser -Filter "accountEnabled eq false" -All

# …and the escape hatch to raw Graph for anything not wrapped
Invoke-MgGraphRequest -Method GET `
  -Uri "https://graph.microsoft.com/v1.0/auditLogs/signIns?`$top=50"
Reference
The Four Things That Trip Up Every Graph Script
IssueWhat to know
PagingGraph returns pages, not everything — -All follows @odata.nextLink; without it you silently get the first page only
ThrottlingHeavy loops hit HTTP (HyperText Transfer Protocol) 429 — honour the Retry-After header, add backoff; do not hammer
Permissions & consentDelegated (as you) vs application (unattended); the scope must be consented, not just requested
v1.0 vs betabeta endpoints change without notice — never build a scheduled job on beta
For anything scheduled and unattended, authenticate as an app registration with a certificate or a managed identity — never an interactive login or a stored password. That path, and its secret handling, is in Environment Variables & Configuration — Keep Secrets Out of Code.
Craft
Read-Only First, Then a Dry Run
Graph will happily disable a thousand accounts as fast as it will read them. Develop every change script against GET until the target set is provably right, then gate the write behind -WhatIf or an explicit confirmation and a hard cap on how many objects one run may touch. A filter that was one character off is a very different event when the next line is a bulk delete — see Automation Risk & Discipline — Blast Radius, Approval Gates & the Kill Switch.
🛂 JEA — Just Enough Administration & Constrained Remoting Automation • Security ▶
Concept
Let Someone Run Three Commands Without Making Them an Admin
The everyday problem: the help desk needs to restart one service and read a couple of logs on a server, and the lazy answer is to make them a local admin, which hands them everything. Just Enough Administration inverts it — a constrained PowerShell endpoint exposes only the specific cmdlets and parameters a role needs, running under a managed identity, so the operator can do their three tasks and nothing else. It is least privilege made concrete for operations.
Reference
How the Constraint Is Built
PieceRole
Role Capability fileDeclares exactly which cmdlets, functions and parameters a role may use
Session Configuration fileMaps users/groups to role capabilities and sets the run-as identity
Virtual / managed run-as accountCommands execute as a privileged identity the user never actually holds
TranscriptionEvery session is logged — who ran what, verbatim
The result: a delegated operator connects to a constrained endpoint, sees only the handful of commands their role defines, and every keystroke is transcribed. The privileged credential never lands on their machine or in their token.
Where It Fits
The On-Prem Counterpart to Cloud PIM
JEA does for a Windows server what privileged-identity management does for the cloud control plane: it removes standing privilege and replaces it with scoped, audited, task-specific access. It pairs naturally with removing local admin rights on endpoints — same principle, server side — and with the credential hygiene in Service Accounts — gMSA and Retiring the Shared Password. Reach for it wherever "they only needed to do one thing" currently means "so we gave them admin."
📜 Configuration as Code On-Prem — Ansible, DSC (Desired State Configuration) & the Drift You Cannot See Automation ▶
Concept
A Script Says How; a Configuration Says What
The distinction between a build script and configuration management is not tooling, it is the shape of the statement. A script describes a sequence of actions — install this, edit that, restart the other — and running it twice does something different from running it once. A configuration describes a desired end state, and the tool works out what to change to reach it. Running it twice is the same as running it once, and running it on a machine that has drifted brings that machine back.
That property is the whole value, and it is why configuration management earns its keep on estates that scripts cannot hold: the answer to "is this server configured correctly?" stops being a matter of memory and becomes a command you can run. Drift is what you are actually buying protection from — the setting somebody changed at 2am during an incident and never mentioned, which works fine until the server is rebuilt.
Reference
Ansible and DSC — Where Each One Fits
The two dominant on-premises options make opposite architectural choices, and the choice matters more than the syntax.
AnsiblePowerShell DSC
ModelPush — a control node connects out and appliesPull or push — the node holds and reapplies its own configuration
Agent requiredNo — SSH (Secure Shell) or WinRM, plus Python on Linux targetsBuilt into Windows; the Local Configuration Manager
TargetsLinux, Windows, network devices, appliancesWindows, essentially
Drift correctionWhen you run itContinuously, on the node's own schedule, if configured to
LanguageYAML (YAML Ain't Markup Language) playbooks, Jinja templatingPowerShell configurations compiled to MOF
Best atOrchestrating a sequence across many mixed hostsHolding one Windows role to a standard, unattended
Current positionWidely used and actively developedStill shipped and useful; increasingly replaced by cloud-managed configuration
The honest summary for a Windows estate: DSC is excellent at the narrow job of keeping a machine's role configuration true, and it has largely lost the broader ground to cloud-managed alternatives and to Ansible. Do not start a large new DSC investment without checking what your management platform already offers; do not rip out a working one either.
Troubleshooting
Idempotency Is a Property You Have to Write, Not One You Get
Both tools are described as idempotent, and both make it trivially easy to write something that is not. The moment a playbook shells out to a raw command, the guarantee is gone and the tool cannot tell. 
# Not idempotent: appends every run, reports "changed" every run
          - shell: echo "10.0.0.5 db01" >> /etc/hosts

          # Idempotent: the module knows the desired state and checks first
          - lineinfile:
              path: /etc/hosts
              line: "10.0.0.5 db01"
              state: present
PracticeEffect
Prefer a module over a shell command, alwaysModules check state; commands do not
Where a command is unavoidable, guard it with a conditionRestores the "only if needed" behaviour by hand
Run in check mode and read what it would changeThe dry run that makes a change reviewable before it lands
A second run should report zero changesThe simplest possible idempotency test, and it catches most failures
Treat unexpected "changed" as a defectConstant noise trains everyone to ignore the one that matters
Version the configuration in Git, review it like codeIt is code, and it has production authority
The zero-changes rule is worth adopting as a hard standard. A playbook that reports changes on every run has stopped being a description of desired state and become a script with extra syntax — and nobody will be able to tell, six months later, whether a reported change was real. The blast-radius discipline that belongs around all of this is in Automation Risk & Discipline — Blast Radius, Approval Gates & the Kill Switch.
🏅 Golden Images as Code — Packer, and Versioning What You Deploy Automation ▶
Concept
The Image Built by Hand Is a Machine Nobody Can Rebuild
Nearly every estate has one: a template built years ago by an administrator who installed the agents, applied the settings, ran sysprep and saved it. It works. Nobody knows exactly what is in it, nobody can reproduce it, and it has been patched by cloning, booting, updating and re-sealing — which means it also carries whatever else was on it the last time somebody did that. It is a build artifact with no source.
Building images from a definition file fixes this by giving the artifact a source. The definition says which base to start from, which provisioning steps to apply, and what to produce; the pipeline runs it on a schedule; the output is versioned and immutable. What changed between last month's image and this one becomes a diff rather than a memory.
Reference
The Structure of an Image Pipeline
Packer is the common tool and the pattern generalises to whatever you use — the stages are the same and the discipline is in the stages, not the syntax.
StageWhat it doesDetail that matters
SourceNames the base image or ISO (International Organization for Standardization)Pin it by version or digest, not by "latest"
BuildBoots a temporary machineRuns somewhere isolated — this machine is unpatched for a while
ProvisionApplies configuration — usually the same Ansible or DSC (Desired State Configuration) you already haveReuse the configuration; do not maintain a second definition of "configured"
Harden and cleanBaseline, remove logs, remove build credentialsBuild-time secrets left in an image are a classic finding
Generalisesysprep, cloud-init prep, machine-ID resetMissing this is how a fleet ends up sharing one identity
TestBoot it and assert it is what you asked forThe stage most often skipped; see the testing card
PublishVersioned artifact, immutable, datedNever overwrite an existing version — that breaks reproducibility
Pinning the source by digest is what makes the whole pipeline reproducible. A base image referenced by a moving tag means two builds a week apart produce different machines with no record of why, which defeats the reason for building images at all. And the hardening row is a genuine security boundary: a build- time secret left in a layer is readable by anybody who can pull the image.
Troubleshooting
Rebuild, Never Patch the Image
The rule that keeps this honest: images are rebuilt from the definition, never updated in place. Boot-patch-reseal reintroduces exactly the untraceability the pipeline removed, and it does it invisibly, one convenient shortcut at a time.
PracticeReason
Rebuild on a schedule — monthly at minimumAn image is a patch level frozen in time; a stale golden image ships a known vulnerability everywhere
Rebuild on base-image or critical-patch release tooThe schedule handles routine; events handle urgency
Keep the previous version deployableRollback for images, and you will need it
Record the base version and patch level in image metadataAnswers "what is running out there?" without logging in
Keep the image thin; configure at deploy timeEvery application baked in is another reason to rebuild for someone else's change

Expire old images deliberatelyOtherwise something is still deploying the one from two years ago
The thin-image rule is the one that decides how much of a burden this becomes. A golden image containing the operating system, the agents and the baseline is rebuilt when those change. One that also contains three applications is rebuilt whenever any of five teams ships anything — and the pipeline that was supposed to reduce work becomes the thing everybody is waiting on.
🔐 Secrets in Automation — Vaults, Managed Identities & Never a Plaintext Credential Automation ▶
Concept
The Best Secret Is the One That Does Not Exist
Every discussion of credentials in scripts starts with where to store them, and that is the second question. The first is whether a stored credential is needed at all. A script running on a cloud virtual machine, in a managed automation account, in a pipeline that federates to the cloud, or as a Windows group-managed service account has an identity supplied by the platform and rotated without anyone's involvement. There is no secret to store, leak, rotate or find in a repository three years later.
SituationUse
Script on a cloud VM (Virtual Machine) or containerThe platform's managed identity
CI/CD (Continuous Integration / Continuous Delivery) pipeline calling cloud APIs (Application Programming Interface)OIDC (OpenID Connect) federation from the pipeline, scoped to repo and branch
Windows service or scheduled task on a domainGroup-managed service account — password rotation is automatic
Scheduled automation in a managed platformThe platform's own credential store and identity
Script on a workstation, run interactivelyThe operator's own credentials, prompted; never a service account
Anything left overA vault, with the retrieval patterns below
Work down that table before designing anything. Most credential-handling problems in an estate are solved by moving the work to somewhere with an identity rather than by managing the credential better.
Reference
When a Stored Secret Is Unavoidable
Legacy systems, third-party APIs with static keys and appliances with local accounts all produce secrets that must live somewhere. The vault is the answer, and how the script uses it decides whether the vault helps.
RuleReason
Retrieve at run time; never write it to diskA cached credential file is the thing you were avoiding
Hold it in memory only as long as neededLimits what a crash dump or a debugger exposes
Authenticate to the vault with an identity, not another secretOtherwise you have moved the problem, not solved it
Scope each secret to one consumerRotation stops being a coordinated estate-wide event
Prefer short-lived, dynamically issued credentialsA leaked credential with a one-hour life is a much smaller incident
Make the vault's audit log a monitored sourceUnusual retrieval is one of the cleanest compromise signals available
Rotate on a schedule, and test the rotationAn untested rotation path means nobody dares revoke during an incident
Retrieval at run time is the rule the other three depend on. A credential written to disk outlives the process, gets backed up, and appears in an image or a snapshot nobody thought about — which is the failure this whole card exists to prevent. The identity row is the one people miss: authenticating to the vault with another stored secret has moved the problem, not solved it.
Troubleshooting
Where Credentials Actually Leak From Scripts
Hardcoding is the obvious one and it is not the common one any more, because it is the one everybody checks for. These are the routes that survive review.
LeakPrevention
Passed as a command-line argumentVisible in the process list to every user on the box — use stdin or the environment
Written to a log by verbose or debug outputWrap secrets in a type that refuses to print; scan logs for patterns
Captured by shell history or a transcriptNever type one interactively into a logged session
Included in an error message or stack traceSanitise exceptions before they reach a ticket or a chat channel
Committed in an earlier revision, then removedStill in history — rotate it, do not merely delete it
Left in a build artifact or a golden imageClean build-time credentials as an explicit pipeline stage
Sitting in a scheduled task's stored passwordThe classic on-premises finding; replace with a managed account
Shared between environmentsA test-environment leak becomes a production incident
The git-history row is the one people get wrong under pressure. Removing a secret in a later commit changes nothing — the old revision still contains it, and rewriting history on a shared branch is disruptive and usually incomplete. Treat any secret that ever reached a repository as compromised and rotate it; that is the only step that actually ends the exposure.
🧪 Testing Automation — Pester, Dry Runs & a Lab That Mirrors Production Automation ▶
Concept
Admin Scripts Are Held to a Lower Standard Than the Code They Outrank
A web application gets unit tests, code review, a staging environment and a canary rollout. The script that disables accounts across the directory gets run. Both are code, and the second one has considerably more authority over the estate than the first — it acts as an administrator, on everything, with no user watching the result. The double standard is historical rather than reasoned: scripts started as one-off conveniences and quietly became infrastructure.
The proportionate response is not full test coverage for every one-liner. It is a rising bar: the more machines it touches and the less reversible its action, the more it has to prove before it runs.
ScriptMinimum bar
Read-only report, one systemRun it and read the output
Changes one object, reversiblyDry run first; confirm the target
Bulk change across many objectsDry run, a reviewed diff, a capped first batch
Destructive or irreversibleAll of the above, plus tests, plus a second pair of eyes
Scheduled and unattendedAll of the above, plus alerting on failure and on suspicious success
Match the bar to the blast radius, and treat the dry run as the minimum for anything that writes. The failure this table addresses is real — administrative scripts change production with less review than the applications they manage — and the fix is proportionate rather than uniform. A capped first batch is the underrated control: it turns a wrong filter into twenty mistakes instead of twenty thousand.
Reference
What to Test, and How
Testing automation feels impossible because the interesting behaviour involves systems you cannot spin up. The resolution is the same as in application testing: separate the logic from the calls, test the logic properly, and mock the calls. 
# Hard to test: decision and action tangled together
          Get-ADUser -Filter * | Where-Object { $_.LastLogon -lt (Get-Date).AddDays(-90) } |
            Disable-ADAccount

          # Testable: the decision is a function that takes data and returns data
          function Get-StaleAccounts {
            param($Accounts, $Days = 90)
            $cutoff = (Get-Date).AddDays(-$Days)
            $Accounts | Where-Object { $_.LastLogon -lt $cutoff -and -not $_.ServiceAccount }
          }

          Describe 'Get-StaleAccounts' {
            It 'excludes service accounts regardless of age' {
              $result = Get-StaleAccounts -Accounts @(
                @{ Name='svc-backup'; LastLogon=(Get-Date).AddYears(-2); ServiceAccount=$true })
              $result | Should -BeNullOrEmpty
            }
          }
The rewrite costs ten minutes and changes what is possible: the selection rule — the part that decides who gets disabled — can now be tested against every awkward case somebody thinks of, without a directory and without disabling anybody. The general testing craft is in Testing Strategy — Why and How to Test and Mocking — Testing Code That Talks to the Outside World; this card is the argument for applying it to operations code.
Troubleshooting
Dry Runs, and the Lab That Is Worth Having
A dry run is the highest-value safety feature an admin script can have, and it has to be built in rather than remembered — a mode the script supports, not a habit the operator has.
PracticeEffect
Support -WhatIf or an equivalent, and default to it where you canThe safe path becomes the one you get by forgetting
Have the dry run output the actual list of targets"Would change 4,812 objects" is the moment to stop and look
Cap the batch size, and require a flag to exceed itTurns a runaway into a small mistake
Log every action taken, with the object and the outcomeThe only way to answer "what did it actually do?"
Write the undo before running the doIf you cannot describe the reversal, you are not ready
On labs: the useful one is not a copy of production, which nobody maintains. It is a small environment with the awkward shapes production has — a nested group, a disabled account with a mailbox, an object with an apostrophe in its name, a machine that has been offline for a year. Those shapes are what break bulk scripts, and a lab of ten deliberately strange objects finds more defects than a lab of a thousand ordinary ones.
🧷 Power Automate & Logic Apps — The Low-Code Option, and Its Real Limits Automation ▶
Concept
The Connectors Are the Product
Low-code automation platforms are sold on the visual designer, and the designer is not why they win. The value is the connector library: authenticated, maintained integrations with hundreds of services that would each be a small project to build and a permanent commitment to maintain. A flow that watches a mailbox, files an attachment, updates a list and posts to a channel is genuinely an afternoon — and the equivalent script is four API (Application Programming Interface) integrations, four credential lifecycles and four sets of breaking changes to track.
Where they lose is equally consistent, and it is not capability. It is the engineering practices that come free with code and are awkward or absent here: version control, meaningful diffs, code review, testing, and a clear story for how a change reaches production.
Reference
Choosing Between a Flow and a Script
The decision is usually made by who is available rather than by fit, which is how estates end up with critical processes in a flow owned by someone who left. These are the honest criteria.
Choose low-code whenChoose code when
The work is gluing together services that have connectorsThe logic is the hard part, not the integration
The trigger is an event in one of those servicesYou need real branching, loops or data structures
The business owner should be able to read itIt must be tested before it runs
Volume is modest and latency is not criticalVolume is high — per-action pricing becomes the constraint
It is genuinely departmental, and its failure is an inconvenienceIts failure is an incident
Time to first version matters more than anythingIt will be maintained for years by people not yet hired
Note the pattern in the right-hand column: it is about the second year, not the first. Low-code wins the build and code wins the maintenance, so the question worth asking is how long this thing will live and how bad its failure would be — not how quickly it can exist.
Troubleshooting
Governing Flows Before They Become Shadow IT
Low-code platforms distribute automation to people who are not administrators, which is the point and the risk. The predictable end state is hundreds of flows, most abandoned, several load-bearing, running under personal accounts with connections to production data.
RiskControl
Flows owned by an individual accountRequire service or shared ownership for anything business-critical
The owner leaves and the flow stopsInclude flow ownership in the offboarding checklist — it rarely is
Connectors bridging internal and external servicesData-loss-prevention policies that separate connector groups
Credentials embedded in a connectionManaged identity or a service principal where the platform supports it
No environments — everything built in productionSeparate development and production environments, and use them
Silent failuresAlert on run failures; a flow that stopped last month is the usual discovery
Nobody knows what existsInventory regularly; sort by last-run and by connector sensitivity
Per-action licensing surprisesWatch run volume; a loop over a large list gets expensive quickly
The offboarding row is the one that produces incidents. A departing employee's account is disabled correctly, and three weeks later an invoice process nobody knew was automated has silently not run. Flow ownership belongs in the same checklist as mailboxes and file shares — the discipline is in Offboarding as a Security Control — The Checklist and Its Failure Modes.
