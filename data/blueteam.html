🦈 Wireshark — Packet Analysis NSM ▶
Reference
See Exactly What's on the Wire
Wireshark is the standard GUI (Graphical User Interface) protocol analyzer — capture live traffic or open a .pcap and inspect every packet, field by field. It's how you confirm what actually happened: a failed handshake, plaintext credentials, C2 (Command and Control) beaconing, or a malformed exploit. The skill is display filters — cutting millions of packets down to the ten that matter.
▸ DISPLAY FILTERS (not capture filters)
FilterShows
ip.addr == 10.0.0.5Traffic to/from a host
tcp.port == 443A specific port
http.request.method == "POST"HTTP (HyperText Transfer Protocol) POSTs
tcp.flags.syn == 1 && tcp.flags.ack == 0Bare SYNs (Synchronize) (scans)
dns.qry.name contains "evil"Suspicious DNS (Domain Name System) lookups
tcp.analysis.retransmissionNetwork trouble
Workflow: Statistics → Conversations to find the top talkers, then right-click → Follow → TCP (Transmission Control Protocol) Stream to reassemble a full session into readable text. tshark is the CLI (Command Line Interface) version for scripting/large captures.
Blind spot
You Cannot Analyse a Capture Nobody Took
Wireshark is the best tool on this page for a question you can still reproduce, and no help at all for last Tuesday. The blind spot is retroactivity: by the time an incident is declared the packets are gone, and the only network evidence that survives is whatever something was already writing down.
QuestionCan Wireshark answer it?
What is this application doing right now?Yes — this is its home ground
What did this host do at 02:00 last Tuesday?Only if a rolling capture was already running
What was inside that TLS (Transport Layer Security) 1.3 session?Not from the server key — forward secrecy removed that. Needs SSLKEYLOGFILE from the client
Which hosts beaconed all month?Wrong tool — that is a Zeek conn.log query
The pairing is a rolling full-capture ring buffer at the choke points that matter (Arkime, or tcpdump -C -W), sized to whatever retention you can afford — even 48 hours changes what a Tuesday-morning investigation can reach. Wireshark then becomes the reader of that archive rather than a tool you can only point at the present.
📡 tcpdump — Capture from the Command Line NSM ▶
Reference
The Capture Tool That's Already Installed
When there's no GUI (Graphical User Interface) — a server, a firewall, a container — tcpdump captures packets from the terminal using BPF (Berkeley Packet Filter) syntax. Grab a capture on the box, then move the .pcap to Wireshark for analysis. Every defender needs this in muscle memory. 
tcpdump -i eth0 -n                 # capture, don't resolve names (-n)
tcpdump -i eth0 -w capture.pcap     # write to file for Wireshark
tcpdump -i eth0 host 10.0.0.5      # one host
tcpdump -i eth0 port 53            # DNS only
tcpdump -i eth0 -A 'tcp port 80'  # print payload as ASCII
tcpdump -i eth0 'tcp[tcpflags] & tcp-syn != 0'  # SYNs
Tip: always add -n (skip DNS lookups — faster and quieter) and cap size with -c / -C so a capture doesn't fill the disk.
Blind spot
The Capture That Looks Complete and Is Missing the Evidence
A capture file is trusted the way a photograph is, and it should not be. Four things routinely make one incomplete without saying so, and every one of them produces a file that opens cleanly in Wireshark and simply does not contain what you were looking for.
What went wrongHow it looksHow to know
The kernel dropped packets under loadGaps, missing halves of conversations, retransmits that make no sensetcpdump prints N packets dropped by kernel on exit — read it, every time
Truncated by snaplenHeaders present, payload cut mid-recordForce -s 0; check frame.cap_len against frame.len
Wrong capture pointOnly one direction, or NAT-rewritten addressesA SPAN port that mirrors one direction, or capturing after the firewall translated
Offload hid the real packetsImpossibly large frames, checksums flagged badGRO/TSO reassembles before the capture point — ethtool -K to disable while capturing
And the biggest one is not a bug at all: TLS (Transport Layer Security). On a modern network the capture proves who talked to whom, how much, for how long and with what fingerprint — not what they said. That is usually enough, because volume and timing answer most questions, but it has to be said out loud before someone spends a day grepping ciphertext for a password. Write the capture's limits into the ticket next to the file, or the next analyst will read absence as evidence.
🧬 Zeek — Network Metadata & Logging NSM ▶
Reference
Not Packets — Structured Facts About Connections
Full packet capture is huge and hard to search. Zeek (formerly Bro) instead watches traffic and writes rich, structured logs — one per protocol: conn.log, dns.log, http.log, ssl.log, files.log, notice.log. It turns raw traffic into queryable evidence and is the backbone of many SOCs (Security Operations Center) and Corelight sensors.
LogAnswers
conn.logWho talked to whom, how long, how many bytes
dns.logEvery query & response (catch DGA / tunneling)
ssl.log / x509.logTLS (Transport Layer Security) certs & JA3 fingerprints
files.logFiles seen crossing the wire (with hashes)
notice.logZeek's own alerts from its scripts
Zeek's scripting language lets you write custom detections — e.g. flag a host that makes 10,000 DNS (Domain Name System) queries an hour (tunneling) or long-lived beacons with fixed intervals (C2).
Blind spot
A Sensor Sees What Crosses It, and Less Crosses It Every Year
Zeek's logs are only as complete as the traffic reaching the tap. The gap is not a setting you forgot — it is where the sensor sits, and the amount of traffic that never passes a central chokepoint has grown every year for a decade: laptops that split-tunnel, workloads that talk east-west inside one subnet, and anything running in a cloud VPC (Virtual Private Cloud) with no on-premise path at all.
Traffic Zeek missesWhat covers it
East-west inside one VLAN (Virtual Local Area Network) or subnetHost telemetry — Sysmon 3, auditd, EDR (Endpoint Detection and Response) process and network events
Remote users on split-tunnel VPN (Virtual Private Network)The endpoint agent, or full-tunnel for the sessions that matter
Cloud workload to cloud serviceVPC flow logs, plus the provider's own service logs
Payload inside TLSssl.log gives SNI (Server Name Indication), JA3 and cert chain — treat the metadata as the detection surface
Before trusting a Zeek deployment, answer one question with a number: what percentage of your hosts' traffic physically traverses this sensor? If nobody knows, that is the finding. A sensor covering 40% of traffic is useful; a sensor believed to cover 100% while covering 40% is worse than none, because it retires the question.
🚨 Suricata & Snort — Signature IDS/IPS NSM ▶
Reference
Rules That Fire on Known-Bad Traffic
Snort (the original) and Suricata (modern, multi-threaded) inspect traffic against signature rules and alert (IDS) or block (IPS) on matches. They ship with community/ET rulesets covering exploits, malware C2 (Command and Control), and policy violations. Suricata adds protocol logging and file extraction, overlapping with Zeek.
▸ ANATOMY OF A RULE
alert tcp any any -> $HOME_NET 445 ( \
  msg:"ET EXPLOIT Possible SMB exploit attempt"; \
  flow:to_server,established; \
  content:"|ff|SMB"; \
  sid:2024001; rev:1; )
PartMeaning
actionalert / drop (IPS) / reject
headerproto, src/dst IPs (Internet Protocol) & ports, direction
msg / sidhuman label & unique rule ID
content / flowwhat to match & connection state
Limit: signatures catch known attacks. Novel or encrypted threats slip past — pair with anomaly detection (Zeek) and endpoint telemetry.
Blind spot
A Signature Is a Description of Something Already Named
Signature IDS (Intrusion Detection System) detects what somebody has already written down. That makes it excellent against commodity tooling and structurally blind to anything first-of-its-kind — not because the rules are bad, but because the rule has to exist before the traffic does.
Blind toWhat covers it
Novel or bespoke toolingAnomaly and frequency analysis over Zeek logs — beacon intervals, new-domain rates
Payload inside TLS (Transport Layer Security)JA3/JA4 fingerprints and certificate anomalies; interception only where policy allows it
Lateral movementPlacement again — a perimeter sensor never sees it. Internal taps or host telemetry
Your own environment's normalNothing ships this. It only comes from tuning against your traffic
The measurable version: track how many distinct rule IDs have fired in the last 30 days. A healthy deployment fires a long tail; a deployment where the same dozen rules produce 95% of events has been tuned into a very expensive way of detecting twelve things. That number is also the honest answer to “is the IDS working?”
🗄️ Arkime & ntopng — Full-Capture & Traffic Analytics NSM ▶
Reference
Searchable History of Everything on the Network
Arkime (formerly Moloch) captures and indexes full packets at scale, giving analysts a searchable web UI (User Interface) to pull the exact session behind an alert — critical for incident response ("show me everything that host did last Tuesday"). ntopng focuses on live traffic analytics — top talkers, flows, bandwidth, and application breakdown in real time.
ToolStrength
ArkimeRetrospective PCAP (Packet Capture) search & session pivoting at scale
ntopngReal-time flow/bandwidth dashboards & alerting
Together with Zeek (metadata) and Suricata (signatures), full capture completes the classic NSM (Network Security Monitoring) triad: alerts tell you something happened, metadata gives context, and full packets prove exactly what.
Blind spot
Full Capture Means Full Until the Disk Wraps
"Show me everything that host did last Tuesday" works exactly as long as last Tuesday is still on disk. Full packet capture is a ring buffer sized by budget: a gigabit link running at a modest average fills roughly ten terabytes a day, so most deployments hold days to weeks, not months. Meanwhile the industry's dwell-time numbers are measured in weeks to months. The overlap between what you retained and when the intrusion began is the whole value of the deployment, and it is a number you can calculate before the incident rather than discover during one.
That is also the argument for the triad rather than for more disk. Zeek metadata costs a fraction of a percent of full packets for the same connection record, so the sensible design keeps weeks of packets and years of metadata — you lose the payload for old events and keep the ability to answer who talked to whom, which is the question most investigations actually ask. Arkime's own session index behaves the same way: it can outlive the PCAP it points at, and a session row whose packets have aged out still tells you the flow existed.
Know your retention in days, and put it where the responders can see it. A team that believes it has full capture and has four days of it will plan an investigation it cannot finish. And decide the exclusions deliberately too — backup traffic and video streams eat the buffer that an interactive session needed, so dropping them by BPF (Berkeley Packet Filter) at the sensor buys retention where it matters.
🔍 Splunk — SPL (Search Processing Language) & the SIEM (Security Information and Event Management) Standard SIEM ▶
Reference
Ask Questions of All Your Logs at Once
A SIEM (Security Information & Event Management) ingests logs from everywhere — firewalls, endpoints, cloud, apps — and lets you search, correlate, and alert across them. Splunk is the market leader; its power is SPL (Search Processing Language), a pipe-based query language.
▸ SPL — PIPE COMMANDS TOGETHER
# Top source IPs for failed logins in the last 24h
index=auth sourcetype=linux_secure "Failed password"
| stats count by src_ip
| sort -count
| head 10

# Detect brute force: 20+ failures from one IP in 5 min
index=auth "Failed password"
| bucket _time span=5m
| stats count by _time, src_ip
| where count > 20
Mental model: search → transform (stats/ eval) → filter (where) → present. Save a search as an alert to run on a schedule and fire on matches. Splunk ES is the security-specific app with prebuilt correlation rules.
Cadence
Field Extractions Break Silently the Day a Log Format Changes
A SIEM's parsing is a contract with every source that feeds it, and nobody on the other end of that contract knows it exists. An application upgrade reorders a field, a vendor adds a wrapper, a firewall changes its syslog template — and the dashboards keep rendering, the searches keep running, and the results quietly go empty. Nothing errors, because a search that matches nothing is a valid search.
What needs a personHow oftenWhat it becomes without them
Checking each source is still parsingWeekly, automaticallyDetections that cannot fire, on sources everyone believes are covered
Watching event volume per sourceContinuously, with an alertA source that stopped sending three weeks ago and nobody noticed
Reviewing searches with zero resultsMonthlyA rule library where an unknown fraction is decorative
Retention and index sizingQuarterlyEither an unexpected bill or data ageing out before the investigation reaches it
Re-testing rules after upgradesPer platform releaseSilent regressions introduced by your own change window
The single most valuable alert in a SIEM is not about attacks. It is “this log source has sent nothing for an hour”, per source, with an owner — because every detection downstream of a dead source is offline and nothing else will tell you. Pair it with a monthly review of searches returning zero results over 30 days, which is where broken parsing surfaces.
🟡 Elastic / ELK Stack — Open-Source Log Analytics SIEM ▶
Reference
Elasticsearch + Logstash + Kibana + Beats
The ELK stack is the dominant open-source logging/SIEM platform. Each piece has a job, and Elastic Security adds SIEM (Security Information and Event Management) detection rules on top.
ComponentRole
BeatsLightweight shippers on hosts (Filebeat = logs, Winlogbeat = Windows events, Packetbeat = network)
LogstashIngest pipeline — parse, enrich, transform (or use Elastic ingest pipelines)
ElasticsearchThe search/analytics engine that stores & indexes everything

Flow: Beats → Logstash → Elasticsearch → Kibana. The trade vs Splunk: much cheaper (open source) but more ops effort to run and scale the cluster yourself.
Cadence
A Cluster With a Mapping Explosion and No Lifecycle Policy
Elasticsearch is happy to accept whatever you send it, which is the property that makes it easy to adopt and expensive to leave unattended. Dynamic mapping creates a field for every new key it sees, so one application logging a unique identifier as a top-level field can add hundreds of thousands of fields — and the cluster slows, then refuses writes, for reasons that look nothing like their cause.
What needs a personHow oftenWhat it becomes without them
Index templates with explicit mappingsPer new sourceDynamic mapping, then a field explosion nobody can undo without reindexing
Index lifecycle management (ILM)Configured once, reviewed quarterlyIndices from 2024 on hot storage, and a disk that fills on a Friday
Shard sizingPer index patternThousands of tiny shards — the most common cause of a slow cluster
Watching cluster health and heapContinuouslyYellow for months, then red during an incident
Snapshot testingQuarterlyBackups that have never been restored, which are not backups
Two settings prevent most of it and both are decided before the first document arrives: an index template that disables dynamic mapping for new sources, and an ILM policy with a delete phase. Retrofitting either means reindexing, which is the same lesson as the landing-zone and default-deny cards elsewhere on this site — cheap on day one, a project on day four hundred.
🛡️ Wazuh — Open-Source XDR/SIEM SIEM ▶
Reference
Agents + Detection + Compliance, Free
Wazuh is a popular free platform that combines endpoint agents with a SIEM (Security Information and Event Management) backend (built on the Elastic stack). Agents on each host do log collection, file-integrity monitoring (FIM), rootkit detection, and vulnerability detection; the manager correlates with rules and maps findings to MITRE ATT&CK (Adversarial Tactics, Techniques and Common Knowledge) and compliance frameworks (PCI, CIS).
CapabilityDetail
Log analysisDecoders + rules turn raw logs into alerts
FIMAlerts when watched files change (tampering)
Vuln detectionCorrelates installed software vs CVE (Common Vulnerabilities and Exposures) feeds
Active responseAuto-actions (block IP, kill process) on triggers
A common home-lab / SMB (Small and Medium Business) choice: it delivers endpoint + SIEM + compliance in one free package, where Splunk/commercial XDR (Extended Detection and Response) would cost heavily.
Blind spot
Free to Install, and the Cost Arrives as Tuning and Storage
The licence is free; the operation is not, and the two places it bites are predictable. The default ruleset is deliberately broad so that a fresh install demonstrates value, which means the first week produces a volume of low-severity alerts that trains everyone who sees the dashboard to stop reading it. Tuning that down — raising levels, excluding known-good file-integrity paths, suppressing the noisy decoders for your estate — is the work that turns the deployment into a detection capability, and skipping it is how a SIEM becomes a compliance screenshot.
What surprises peopleWhy
Indexer storage growthElastic-based storage of every alert; retention and index lifecycle management are a decision, not a default
File-integrity monitoring noiseWatching a path that changes on every update produces thousands of alerts about your own patching
Agent coverage gapsThe same denominator problem as any agent estate — the host without one is silent, not clean
Active responseAuto-blocking an IP (Internet Protocol) is a self-inflicted outage waiting for a false positive on the wrong source — start it in log-only
Vulnerability detectionMatches installed packages against feeds, so it inherits their false positives and knows nothing about compensating controls
Judge it by what you would act on. A short list of high-confidence rules mapped to the techniques that matter in your estate beats the full default ruleset by a wide margin, and it is the same measurement any detection programme uses — see Measuring Detection Quality — Precision, Recall & the Alert-to-Incident Ratio.
📥 Graylog & Loki — Log Aggregation Alternatives SIEM ▶
Reference
Two More Ways to Centralize Logs
Graylog is a streamlined, security-friendly log management platform (streams, alerts, dashboards) that's simpler to operate than raw ELK. Loki (from Grafana) takes a different tack: it indexes only labels, not full log content, making it very cheap to store — and it pairs with Grafana so logs sit next to your metrics.
ToolBest for
GraylogTurnkey central log mgmt with security features
LokiCheap, high-volume logs alongside Grafana metrics
The theme across all of these: centralize logs off the hosts. An attacker's first move is deleting local logs — if they're already shipped to a central store, the evidence survives.
Blind spot
Loki Indexes Labels; Anything Else Is a Scan You Are Paying For in Time
Loki is cheap because it indexes only labels and stores the log line itself as a compressed blob. That trade is excellent for "show me this service's logs for this hour" and hostile to the question a hunt actually asks: "has this indicator appeared anywhere in the last month." The second query has no index to use, so it decompresses and greps its way through the range — and the failure mode is not an error, it is a query that takes minutes, then hits a limit, and returns partial results that look like an answer.
ChoiceWhat it buysWhat it costs
Label itFast, indexed filteringHigh-cardinality labels — user, IP (Internet Protocol), request id — explode the stream count and degrade the whole cluster
Leave it in the lineCheap storage, no cardinality riskEvery search over it is a brute scan of the time range
Graylog / Elasticsearch insteadFull-text search over contentIndex size and cost roughly the thing you were avoiding
Pick by the question, not by the price. Security telemetry is searched by unpredictable content — an indicator nobody knew about last week — so it belongs where content is indexed. Application and platform logs are searched by known dimensions and belong where storage is cheap. Splitting them is not duplication; it is the same reasoning as tiering a SIEM (Security Information and Event Management) by table, and getting it wrong is discovered during the one hunt that mattered.
📜 Sigma — Write Detections Once, Run Anywhere Detection ▶
Reference
The Vendor-Neutral Detection Format
Every SIEM (Security Information and Event Management) has its own query language — so a detection written for Splunk doesn't work in Elastic. Sigma solves this: you write a detection once in a simple YAML (YAML Ain't Markup Language) format, then a converter compiles it into SPL (Search Processing Language), Elastic KQL (Kusto Query Language), Wazuh rules, etc. It's "the YARA (Yet Another Recursive Acronym) of logs" and how the community shares detections. 
title: Many Failed Logins (Brute Force)
logsource:
  product: linux
  service: auth
detection:
  selection:
    message: 'Failed password'
  condition: selection | count() by src_ip > 20
level: high
Workflow: pull community Sigma rules (or write your own) → convert to your SIEM → deploy. It makes detection engineering portable and reviewable in Git (detection-as-code).
Blind spot
Portable Rule, Non-Portable Field Names
sigmac converting a rule into your backend's query language is the easy half of portability. The rule still names fields — CommandLine, ParentImage, TargetUserName — and those exist only if your pipeline collected and named them that way. A rule that converts cleanly and matches nothing looks identical to a rule that converts cleanly and works.
Assumption inside the ruleWhere it breaks
The field was collected4688 command line was never enabled — the field is absent, not empty
The field has this nameYour pipeline normalised to ECS (Elastic Container Service) or OCSF and renamed it

Every imported rule needs one test before it counts as deployed: fire the behaviour and confirm the rule alerts, with Atomic Red Team or a hand-run command. Untested imported rules are the most convincing form of coverage theatre on this page, because the rule count goes up and the detection does not.

🦉 OSQuery — Your Fleet as a SQL (Structured Query Language) Database EDR ▶
Reference
Query Endpoints Like a Table
OSQuery (Meta, open source) exposes the OS (Operating System) as SQL tables — processes, users, listening ports, installed packages, startup items — so you can ask questions across your whole fleet with a query. It's cross-platform (Windows/macOS/Linux) and great for both incident response and continuous monitoring. 
-- What's listening on the network?
SELECT p.name, l.port, l.address
FROM listening_ports l JOIN processes p ON l.pid = p.pid;

-- Unsigned processes running from temp dirs
SELECT name, path FROM processes
WHERE path LIKE '%\Temp\%';
Run ad-hoc during IR (Incident Response), or schedule "packs" of queries that stream diffs to your SIEM (Security Information and Event Management) (via Fleet/Kolide) for continuous detection — e.g. alert whenever a new persistence entry appears.
Cadence
A Query That Errors Returns Nothing, Which Looks Exactly Like a Clean Fleet
osquery (Operating System Query)'s appeal is that fleet questions become SQL. The maintenance cost is that a query which fails on a platform returns an empty result rather than an error you see — a table that does not exist on that OS version, a permission the agent lost, a path that moved. Empty and clean are indistinguishable in the console.
What needs a personHow oftenWhat it becomes without them
Validating packs per platformPer OS release, and per pack changeQueries that silently cover Linux and not macOS, or the reverse
Watching agent check-in countsDaily, automaticallyA fleet number that drifts down as agents die quietly
Reviewing query performanceMonthlyA scheduled query pinning CPU (Central Processing Unit) on laptops, and users disabling the agent
Pruning packs nobody usesQuarterlyInterval creep — dozens of queries running because somebody once wanted one
Confirming a known-true query returns rowsWeeklyNo way to distinguish 'nothing found' from 'nothing asked'
The last row is the whole discipline, and it costs one scheduled query: ask something you know must be true — a file that exists on every host, a process that always runs — and alert when it returns nothing. That single canary distinguishes a healthy deployment from a silent one, and it is the same idea as the SIEM's dead log source, one layer down.
🦖 Velociraptor — Endpoint DFIR (Digital Forensics and Incident Response) & Hunting at Scale DFIR ▶
Reference
Hunt Across Thousands of Machines
Velociraptor is a powerful open-source DFIR and threat-hunting platform. Using its query language VQL, you can collect artifacts, run hunts, and monitor endpoints across an entire estate from one console — "check every machine for this IOC (Indicator of Compromise)" returns answers in minutes, not days.
UseDetail
HuntsRun an artifact collection across all endpoints at once
ArtifactsReusable collectors (prefetch, browser history, registry, memory)
Client monitoringContinuous event queries (like a lightweight EDR)
VQLSQL-like language to query live endpoint state
It's become a go-to for IR (Incident Response) teams who need broad, fast visibility without a six-figure commercial EDR (Endpoint Detection and Response) — especially during active incidents.
Blind spot
A Hunt Answers for Enrolled, Powered-On Clients — and Says Nothing About the Rest
"Check every machine for this IOC" returns in minutes, and the number it returns is the number of machines that answered. Laptops that are asleep, hosts behind a network the server cannot reach, machines that were never enrolled, and the one an attacker uninstalled the agent from all look identical in the result set: absent. During an incident that distinction is the entire question, because the host you most want to hear from is the one most likely to be missing.
So a hunt is only interpretable next to a denominator. Compare the responding client count against your asset inventory before reading the findings, and treat the gap as a work item rather than as noise — it is simultaneously your coverage metric and, quite often, a list that contains the answer. Velociraptor makes this cheap: client metadata is itself queryable in VQL, so "last seen more than seven days ago" is a hunt of its own.
Report hunts as a fraction, never as a verdict. "Clean across 4,180 of 4,900 known endpoints, 720 unreachable" is an honest result that tells the incident commander what to do next; "no findings" from the same run is a sentence that ends an investigation early. The same discipline applies to coverage claims generally — ATT&CK Coverage Mapping — Honest Heat Maps and the Lie of "100% Coverage".

The Event You Need Is Off, or Already Rolled Over

Forwarding to a collector is what turns these IDs from a list into evidence.
🐧 auditd & Linux Endpoint Logging EDR ▶
Reference
The Same Visibility, on Linux
auditd is the Linux audit framework — it logs syscalls, file access, and command execution against rules you define. Pair it with the Linux kernel's audit subsystem (or a modern eBPF agent like Falco) to get process-level telemetry equivalent to Sysmon on Windows. 
# Watch a sensitive file for any access
auditctl -w /etc/shadow -p rwa -k shadow-access

# Log every execve (process execution)
auditctl -a always,exit -F arch=b64 -S execve -k exec

ausearch -k shadow-access        # query by key
Ship these logs to the SIEM (Security Information and Event Management) alongside Windows/Sysmon so hunts and detections cover the whole estate. For richer, lower-overhead visibility, eBPF-based tools (Falco, Tetragon) are the modern complement — see the eBPF (Extended Berkeley Packet Filter) topic in Linux.
Blind spot
Syscalls Are Not Intent, and Containers Muddy Whose Syscall It Was
auditd records with great fidelity that a syscall happened. What it cannot supply is why, and on a container host it often cannot cleanly supply who either — containers share the host kernel, so events arrive attributed to the host namespace unless something maps them back to a container.
LimitationWhat covers it
No process ancestry in the raw eventauditd plus a session tracker, or eBPF tooling (Falco, Tetragon) that carries lineage
Container events land on the hostA runtime-aware collector that resolves cgroup to container and image
Rule cost is realScope rules to paths that matter — a blanket -a always,exit -S all is a performance incident waiting to happen
Log lives on the compromised hostForward it. Same rule as Windows
Write auditd rules against things that should never change — /etc/passwd, /etc/sudoers, /etc/ssh/, the cron directories — rather than trying to record everything every process does. A small rule set whose every hit deserves a look beats a large one nobody reads, and it costs a fraction of the CPU (Central Processing Unit).
🧾 YARA (Yet Another Recursive Acronym) — Pattern-Matching Rules for Malware Detection ▶
Reference
"The Pattern-Matching Swiss Knife for Malware"
YARA lets analysts describe malware families by textual/binary patterns and match files, memory, or processes against them. It's how threat researchers share detections for a specific implant or campaign — and it runs in scanners, EDRs (Endpoint Detection and Response), and IR (Incident Response) tools alike. 
rule Suspicious_PowerShell_Downloader {
  strings:
    $a = "DownloadString" nocase
    $b = "IEX" nocase
    $c = "FromBase64String" nocase
  condition:
    2 of them          // any 2 of the strings present
}
Use: hunt across a fleet ("scan every host for this rule" via Velociraptor/OSQuery), triage a sample, or scan process memory for an unpacked payload. Pair with yara-x (the modern engine) and community rulesets. Focus rules on behavior/capabilities, not just hashes, so they survive repacking.
Finding nothing
A Rule Is a Hypothesis About Bytes, and No Match Falsifies the Rule
YARA answers one question exactly: does this file contain the patterns I described? When the answer is no, the only sound conclusion is that the description does not fit — not that the file is harmless. Packing, a recompilation, one changed string, or a variant from the same family is enough, and none of those makes the file any less malicious.
Why a good rule missesWhat to do about it
The sample is packed or encryptedScan memory rather than disk — the strings exist at runtime

Treat YARA as a fast filter over a large corpus, never as a verdict on one file. Its strength is retrospective: a good rule sweeps years of stored samples or every endpoint's memory in minutes and tells you where else this thing has been. Its weakness is the single clean result, which is the least informative output the tool can produce.
🎯 MITRE ATT&CK (Adversarial Tactics, Techniques and Common Knowledge) & Navigator — Coverage-Driven Detection Detection ▶
Reference
A Shared Map of How Attackers Operate
ATT&CK is a knowledge base of real adversary tactics (the "why" — e.g. Persistence, Lateral Movement) and techniques (the "how" — e.g. T1053 Scheduled Task). It gives defenders a common language and a way to measure detection coverage rather than collecting disconnected alerts.
ConceptDetail
TacticThe adversary's goal for a step (14 columns)
Technique / Sub-techniqueThe specific method (Txxxx)
NavigatorHeat-map tool to mark what you can detect/prevent
The workflow: map each detection you have to a technique, color the Navigator, and the gaps become your detection backlog. Prioritize techniques your actual threat actors use (tie to threat intel). Every good detection references its ATT&CK ID.
Finding nothing
A Green Coverage Map Means a Rule Exists, Not That It Fires
Coverage matrices are the most persuasive artefact in this domain and the easiest to mislead yourself with. A green cell means somebody wrote a rule tagged with that technique. It does not mean the rule fires on that technique, that the data source it needs is being collected, or that anyone is triaging the alert — and a matrix cannot tell the difference between a working detection and a tag.
What green can meanHow to tell
A tested detection that firesSomeone ran the technique and watched the alert arrive
A rule that references absent fieldsSigma-style field mismatch. It converts, deploys, and never matches
A rule for one procedure of manyT1059 is a technique; the rule may catch one PowerShell variant and nothing else

A technique nobody in your threat model usesGreen here is not worth what green elsewhere is worth

Most teams doing this for the first time find their honest coverage is a third of what the inventory-based map claimed, and that number is far more useful — it is the one that predicts what will happen during an incident.

🎚️ Detection Tuning & the Pyramid of Pain Detection ▶
Concept
Make Detections Hurt the Attacker, Not the Analyst
The Pyramid of Pain ranks indicators by how much it costs an adversary to change them. Detecting a file hash is trivial to evade (recompile); detecting their TTPs (Tactics, Techniques, and Procedures) (behaviors) forces them to relearn how they operate. Aim your detections up the pyramid.
IndicatorAttacker cost to change

ToolsChallenging

Tuning: the other half is fighting false positives — a noisy rule everyone mutes is worse than no rule. Track each detection's true/false-positive rate, add context/allowlists, and require every alert to be actionable. Detection-as-code (Sigma in Git, tested with Atomic) keeps quality high.
Finding nothing
Zero Alerts After Tuning: Did You Remove the Noise or the Detection?
Tuning is the right response to alert fatigue and it is also the easiest way to accidentally switch a control off. The two outcomes are indistinguishable on the dashboard — a well-tuned rule and a broken rule both produce silence — and the difference only surfaces during an incident, which is the worst possible moment to discover which one you have.
Tuning actionWhat it costs, and how to keep it honest
Exclude a noisy process pathAttackers use trusted paths. Scope the exclusion by parent and arguments, not by image name alone
Raise a thresholdSlow-and-low activity now passes underneath. Record the threshold and why
Filter out a service accountThe account most worth compromising is now invisible. Prefer narrowing to the specific expected behaviour
Disable the ruleLegitimate sometimes — but with an owner and a review date, or it is permanent
Every exclusion, alwaysIn version control, with a reason and a date. An undocumented exclusion is indistinguishable from an attacker's
The check that separates the two silences: re-run the behaviour after tuning and confirm the alert still fires. Atomic Red Team makes this a few minutes' work per rule, and it converts “the noise stopped” from an assumption into a test. A tuning change that has not been validated this way is a rule you have decided to trust without evidence.
🧠 Volatility — Memory Forensics DFIR ▶
Reference
RAM (Random Access Memory) Holds What Disk Never Sees
Malware runs in memory — decrypted payloads, injected code, live network connections, and cached credentials that never touch disk. Volatility (v3) analyzes a RAM capture to reconstruct exactly what a machine was doing at the moment of capture. It's the cornerstone of incident response. 
vol -f mem.raw windows.pslist        # running processes
vol -f mem.raw windows.pstree        # parent/child tree (spot odd chains)
vol -f mem.raw windows.netscan       # network connections (C2)
vol -f mem.raw windows.malfind       # injected/hidden code
vol -f mem.raw windows.cmdline       # process command lines
Workflow: pslist/pstree to spot anomalies → malfind for injection → netscan for C2 (Command and Control) → dump the suspect process for deeper analysis. Capture memory before pulling the plug — it's volatile (order-of-volatility rule).
Blind spot
Memory Is Gone the Moment the Machine Is
Every Volatility plugin is downstream of one decision made by whoever touched the machine first. Acquisition is the hard part, it happens once, and “we rebooted it to be safe” ends the memory investigation before it starts — along with every injected process, unbacked page, and key that only ever existed in RAM.
Decision at the sceneWhat it costs you
Reboot or shut downAll of memory. Non-recoverable — there is no later
Pull the network cable, leave it runningPreserves memory; may trip malware that watches for it
Image the disk onlyEncryption keys, in-memory-only payloads, live network state
Snapshot a VM (Virtual Machine)Best case — the .vmem is a memory image, taken with no agent on the guest
The pairing here is not another tool but a playbook step: capture memory before containment, written into the procedure rather than decided at 3am by whoever arrived first. On a virtualised estate it is nearly free, which is a good argument for practising it on VMs until the reflex is automatic.
💽 Autopsy & The Sleuth Kit — Disk Forensics DFIR ▶
Reference
Investigate a Disk Image, File by File
The Sleuth Kit (TSK) is the CLI (Command Line Interface) engine; Autopsy is its GUI (Graphical User Interface). Together they analyze a forensic disk image — recovering deleted files, building timelines, carving artifacts, and hashing everything — without altering the original evidence.
CapabilityDetail
Deleted-file recoveryRecover files still in unallocated space
File carvingRebuild files from raw bytes by signature
TimelineMAC times (modified/accessed/created) across the FS
Keyword & hash searchFind IOCs (Indicator of Compromise); flag known-bad by hash
Always work on a write-blocked copy and verify the image hash matches the original — evidence integrity is everything.
Blind spot
On an SSD (Solid State Drive), "Recovered Nothing" Is Not the Same as "Nothing Was There"
Deleted-file recovery is a spinning-disk assumption that survived into an era where it mostly does not hold. When a file is deleted on a TRIM-enabled SSD, the operating system tells the drive those blocks are free, and the controller's garbage collection erases them on its own schedule — often within minutes, entirely outside the investigator's control, and irreversibly. Carving unallocated space then returns zeros. That is not a failure of the tool and it is not evidence that the file never existed; it is the storage layer having already destroyed it.
Assumption from the disk eraWhat actually holds now
Deleted data survives in unallocated spaceTRIM plus wear-levelling may have erased it before the machine was seized
The image is the whole driveOver-provisioned and remapped blocks are not addressable at all
MAC times tell the storyTimestomping is a two-line operation; $STANDARD_INFORMATION lies where $FILE_NAME often does not
Full-disk encryption is a later problemPowering the machine off can cost you the only copy of the key — capture memory first
Which is why disk is now the second question, not the first. Memory, then volatile system state, then the journal and registry artefacts that record what ran, then carving — because a machine's own logs and MFT (Master File Table) records routinely outlive the file contents on modern storage. Say in the report what the media made impossible, so a null result is read as a null result rather than as an exoneration.
⏱️ KAPE & plaso — Triage & Super-Timelines DFIR ▶
Reference
Fast Collection, Then a Unified Timeline
Full disk imaging is slow; often you need answers now. KAPE rapidly collects just the high-value forensic artifacts (registry, event logs, prefetch, browser history) from a live or imaged system. plaso/log2timeline then merges everything into one chronological super-timeline — the single most useful artifact in an investigation.
ToolRole
KAPETargeted artifact collection + modules to parse them
plaso (log2timeline)Combine all timestamped artifacts into one timeline
Timeline ExplorerFilter/pivot the resulting mega-CSV
The timeline answers the core IR (Incident Response) question: what happened, in what order? — from initial access to persistence to exfil.
Blind spot
The Timeline Contains What the Targets File Asked For, and Its Times Are Not All the Same Kind
Triage collection is a scoping decision disguised as a technical one. A KAPE target list defines what is collected, so an artefact outside the list is not merely unexamined — it does not exist in the evidence, and its absence is indistinguishable from its emptiness. The gap is widest exactly where investigations are hardest: application-specific logs, a third-party agent's telemetry, a browser profile in a non-default path. Record which target list you used in the case notes, because the next question is always whether something was looked for.
The super-timeline then flattens sources whose timestamps mean different things. A file's $STANDARD_INFORMATION modified time is trivially altered by a process; $FILE_NAME usually is not, which is why a row where they disagree is worth more than either alone. Windows event logs are UTC (Coordinated Universal Time), filesystem times may be rendered local, and browser history has its own epoch. Pin -z UTC at ingest and say so in the report — a timeline where two sources are an hour apart because of daylight saving produces a confident, entirely wrong sequence of events.
The value is the pivot, not the file. A raw plaso timeline of a workstation runs to millions of rows, which is unreadable and is not meant to be read — you go to a known time and expand outward, or you filter to a handful of artefact types and follow one thread. Treat a super-timeline as an index you query around a hypothesis, and generate it early so the hypothesis has somewhere to land.

🧫 Malware Sandboxes — VirusTotal, Any.Run & Hybrid Analysis Threat Intel ▶
Reference
Detonate the Sample, Watch What It Does

🛡️ OpenSCAP & DISA (Defense Information Systems Agency) STIGs (Security Technical Implementation Guide) — Compliance-Driven Hardening Compliance ▶
Reference
Machine-Readable Security Policy
SCAP (Security Content Automation Protocol) is a set of standards (OVAL, XCCDF, CCE) for expressing security policy as machine-readable content. OpenSCAP scans and even auto-remediates against that content; DISA STIGs are the U.S. DoD (Department of Defense)'s hardening standards distributed in this format. 
# Scan RHEL against a STIG profile and generate an HTML report
oscap xccdf eval \
  --profile xccdf_org.ssgproject.content_profile_stig \
  --report report.html \
  /usr/share/xml/scap/ssg/content/ssg-rhel9-ds.xml
SSG (SCAP Security Guide) ships ready profiles — STIG, CIS (Center for Internet Security), PCI-DSS, HIPAA (Health Insurance Portability and Accountability Act). This is how regulated environments prove and enforce a baseline continuously rather than via a one-time checklist.
Blind spot
A Benchmark Scores Configuration, Not Exploitability — and Counts Two Non-Answers as Wins
The report ends in a percentage, and the percentage is where the reasoning stops. Two things inflate it silently. Rules that cannot be evaluated on this system return notapplicable or notchecked — a kernel rule on a container, a rule whose OVAL definition needs a package that is absent — and the default rendering rolls those into the pass column. A profile can therefore climb by adding scope it does not actually assess. Read fail against pass and list the non-answers separately; the ratio you want is over rules that were genuinely tested.
The deeper limit is what the model measures. XCCDF asserts a configuration state: a permission, a sysctl, a line in a config file. It says nothing about the application running on top, the credential in a repository, or the network path that makes a hardened host reachable from the internet. A STIG-clean box with a vulnerable web app is a common and entirely consistent outcome — which is why compliance scanning and vulnerability scanning are two tools and not one.
Auto-remediation is where this becomes an outage. --remediate applies fixes in rule order with no knowledge of your application, and the classic result is a hardened SSH (Secure Shell) configuration that locks out the management account, or a mount option that stops a database starting. Generate the remediation as a script, read it, and put it through the same change process as any other configuration change — the value of machine-readable policy is that the diff is reviewable, not that it can be applied unread. Severity is still not priority; see Vulnerability Prioritisation — Severity Is Not Priority.
🩹 Patch & Config Management as a Control Vuln Mgmt ▶
Concept
Finding Vulns Is Easy — Fixing at Scale Is Hard
A scanner produces a list; the real work is closing the loop across thousands of systems reliably. Patch and configuration management turn remediation from a manual scramble into a repeatable, measurable control.
ToolRole
WSUS (Windows Server Update Services) / MECM (Microsoft Endpoint Configuration Manager) / IntuneWindows patch orchestration & compliance
Ansible / SaltCross-platform patching & config enforcement (ties to F4)

Metrics that matter: patch coverage %, mean time to remediate (MTTR) by severity, and drift (systems that fell out of compliance). Config management also prevents drift — the box stays hardened, not just gets hardened once.
The Decision
Coverage % Is a Comfort Metric — the Risk Lives in the Exceptions You Can't Patch
A patch-coverage number climbs comfortably toward 95% while the security reality hides in the last 5%, because the systems that resist patching are systematically the highest-risk ones: the box that can't take downtime, the appliance on end-of-life firmware, the crown-jewel server nobody will touch. High coverage is a comfort metric; the exception list is the actual posture — the standing “can't patch,” and why. The other half: patching is itself a risk — a bad patch is an outage — so fast-for-security fights slow-for-stability, the same tension DORA (DevOps Research and Assessment) names for delivery. The mature programme resolves it not by patching everything at once nor by permanent carve-outs, but by ringing the rollout and managing the exceptions.
The comfort moveWhat it hidesThe real control
Report coverage %The unpatched few are the highest-risk systemsWork the exception list — owner and expiry on each
Permanent “can't patch” carve-outRisk with no compensating controlIsolate, virtual-patch (WAF/IPS), monitor harder

So measure the exceptions, not the coverage: every system that can't be patched needs a named owner, a compensating control, and an expiry date, or it is just risk you stopped looking at. And treat the speed-versus-stability tension as the actual job — ring the rollout so a bad patch hits a canary, not the fleet, and spend the urgency budget on what is being exploited in the wild, not on clearing the long tail of low-severity noise.
🍯 Honeypots & Canarytokens — Deception Tech Deception ▶
Concept
Traps That Only an Intruder Trips
A legitimate user never touches a fake admin account, a decoy database, or a file named passwords.xlsx planted on a share. Deception assets have near-zero false positives — any interaction is, by definition, suspicious.
TypeDetail
HoneypotA fake system that logs everything an attacker does (T-Pot, Cowrie)
Honeytoken / CanarytokenA fake credential, AWS (Amazon Web Services) key, or URL (Uniform Resource Locator) that alerts when used

Best value: place canarytokens inside the network where only a snooping attacker would find them. A tripped token is high-fidelity evidence of a breach in progress — the mirror image of the red-team exfil/pivot cards.
Blind spot

A canary's precision is its whole appeal — nothing legitimate touches it, so a hit is a hit. The cost of that precision is zero coverage guarantee: deception detects curiosity, and an intruder who arrived with a specific target and went straight to it triggers nothing at all. Silence from a honeypot is not evidence of absence, and it is worth saying so before anyone treats it as coverage.

Placed where an intruder must pass rather than where they might browse, it stops being a lottery ticket.
📧 Email Security — SPF, DKIM (DomainKeys Identified Mail) & DMARC (Domain-based Message Authentication, Reporting and Conformance) Email Defense ▶
Reference
Stopping Spoofed Mail at the Door
Email is the #1 initial-access vector, and by default anyone can forge your domain in the "From" field. Three DNS-based standards, layered, let receivers verify that mail really came from you — and tell them what to do when it didn't.
RecordAnswers
SPF"Which servers may send mail for this domain?" (IP allow-list in DNS)
DKIM"Was this message signed by the domain & unmodified?" (crypto signature)
DMARC"If SPF/DKIM fail, what do I do — and where do I report?" (policy + alignment)
# A DMARC record that quarantines fakes and sends reports
_dmarc.example.com  TXT  "v=DMARC1; p=quarantine; rua=mailto:dmarc@example.com; adkim=s; aspf=s"
Progress p=none (monitor) → quarantine → reject as you gain confidence. Add sandboxing, link rewriting, and external-sender banners for the phishing that still gets through.
Blind spot
All Three Pass, and the Message Is Still a Fraud
These records authenticate a domain, and almost no user reads a domain. A message from accounts-payable@examp1e-corp.com — a domain the attacker owns, with its own perfectly valid SPF, DKIM and DMARC — passes every check, because the attacker is not spoofing you. Neither does any of it help when a genuine supplier's mailbox is compromised and the invoice arrives from the real address, correctly signed, in an existing thread. That is business email compromise, it is the highest-loss email attack there is, and email authentication is structurally blind to it.
TrapDetail
The SPF ten-lookup limitChained include: statements exceed it and the record fails permerror — which many receivers treat as no SPF at all. Flatten it, and re-check after adding any SaaS (Software as a Service) sender
Alignment, not just a passDMARC cares that the passing domain matches the visible From. Relaxed alignment lets a subdomain pass for the parent; adkim=s; aspf=s is stricter and breaks more forwarders
Forwarding and mailing listsBreak SPF by changing the sending IP (Internet Protocol), and break DKIM if the list edits the body — which is what ARC exists to repair
Stuck at p=noneMonitoring forever is the commonest outcome; the reports exist to find your senders, not to be admired
Lookalike domainsNot addressed by any of the three — this is registrar monitoring plus an external-sender banner
Get to p=reject, then treat that as the floor rather than the finish. It stops others forging your domain, which protects your customers more than it protects you. What protects you is the layer above: display-name and lookalike detection, banners on external mail, and a payment-change process that requires a callback to a number you already held — see Business Email Compromise — The Attack With No Malware.
🪪 Identity Threat Detection & Response (ITDR) Identity ▶
Concept
"Identity Is the New Perimeter"
Modern attackers don't break in, they log in — with phished, sprayed, or stolen credentials and session tokens. ITDR watches the identity provider (Entra ID, Okta, AD) for the behavioral signals of account takeover.
SignalWhat it suggests
Impossible travelLogins from two distant locations too close in time
MFA (Multi-Factor Authentication) fatigue / bombingRepeated push prompts hoping the user taps "approve"
Token / session theftA valid session used from a new device/IP (AiTM phishing)
Password sprayOne password tried across many accounts
Controls: phishing-resistant MFA (FIDO2/passkeys), Conditional Access (device + risk based), and continuous access evaluation that can kill a session mid-flight. This is the defensive answer to the credential-attack and AD (Active Directory) cards on the red-team side.
Blind spot
A Stolen Token Produces No Sign-In Event, Which Is Why the Signals Above Are the Easy Half
Impossible travel and push fatigue are visible because they are authentications. The technique that defeats phishing-resistant thinking is the one that skips authentication entirely: an adversary-in-the-middle proxy captures the session cookie after a successful, fully MFA'd login, and replaying it produces no sign-in log at all — because no sign-in happened. The account looks quiet in the identity provider while the attacker reads mail. This is the gap ITDR actually has to cover, and it is not covered by watching logins.
Where the evidence livesWhat to look for
Token and refresh events, not sign-insA refresh from an IP (Internet Protocol) or device that never authenticated
Mailbox and workload audit logsThe post-access tells: a new inbox rule, a mass download, an OAuth (Open Authorization) grant to an unknown app
Registered authentication methodsA second factor added quietly — the persistence step that survives a password reset
App registrations and consentsA service principal with mail permissions, which needs no user session at all
And the containment order is different from a password compromise. Resetting the password does not invalidate an existing session — the token remains valid until it expires — so the sequence is revoke sessions, then reset, then audit registered methods, app consents and inbox rules for the persistence the attacker left behind. Continuous access evaluation is what shortens the window; token binding is what closes it. The offensive side is in MFA Bypass in Practice — Adversary-in-the-Middle, Push Fatigue & Stolen Sessions.
🤝 Purple Teaming — Closing the Detection Gap Purple ▶
Concept

🗄️ Log Retention as a Design Decision BLUETEAM • Operations ▶
The Inversion
Retention Is Chosen by Cost and Then Discovered During an Incident
Retention is almost always set as a storage-budget line — keep 30 days because 90 was expensive — and the number is never examined again until an investigator asks “when did this start?” and the answer is “before our logs begin.” Dwell time for a real intrusion is routinely longer than the retention window a budget picked, which means the decision that framed the investigation was made months earlier by someone optimising a bill.
The question retention should answerThe implied window
How far back must we reconstruct an intrusion?Longer than typical dwell time — months, not days
What does the regulation require?A floor, often a year or more, per data type
What can we afford to keep hot & searchable?The expensive tier — keep it short and deliberate
What must merely be recoverable, slowly?The cheap tier — keep it long
The right frame reverses the default: start from how far back you must be able to answer a question, then find the cheapest tier that still answers it — not from a storage number with a retention window backed out of it.
The Decision
Tiering Is What Makes Long Retention Affordable
The false choice is “keep everything searchable” versus “delete it”. Between them sits tiering: a small hot tier for the queries you run daily, and progressively cheaper, slower tiers for the data you will only ever touch during an investigation. The art is putting the right source in the right tier, because the sources you need at incident time are not the ones you query day to day.
TierCost / speedWhat belongs here
Hot (searchable)Expensive, instantRecent, high-query sources — auth, EDR (Endpoint Detection and Response) alerts
WarmCheaper, slowerThe last few months of detail
Cold / frozen (archive)Cheap, restore-to-searchLong-tail forensics & compliance evidence
Decide tiering per source, not per age alone: authentication and DNS (Domain Name System) logs earn a long cheap tail because they answer “how far back”, while verbose debug logs can expire fast. This is the depth axis of the same problem Log Volume & Cost — The Detections a Budget Quietly Kills frames as breadth — and the two budgets trade against each other.
📡 Threat-Feed Reality — Why Most Indicators Are Worthless to You BLUETEAM • Intelligence ▶
The Inversion

A purchased threat feed feels like an asset — a million bad IPs (Internet Protocol), updated hourly. Most of it is worthless to you, for two reasons that compound. Indicators decay: a malicious IP is reassigned, a domain is taken down, a hash is recompiled, and a stale indicator produces false positives, not detections. 📈 User & Entity Behaviour Analytics — What Baselining Can and Cannot Learn BLUETEAM • Detection ▶
The Inversion
A Baseline Built During an Incident Learns the Incident as Normal
UEBA (User and Entity Behavior Analytics) promises to catch what rules miss by learning “normal” and flagging deviation. The catch is in the word learn: the model is only as good as the period it trained on. Train it while an attacker is already resident and it bakes the intrusion into the baseline, after which the malicious behaviour is, by definition, normal and invisible. The tool's core assumption — that the training window was clean — is the one thing it cannot verify.
Where UEBA works wellWhere it fails politely
Genuinely repetitive behaviour (service accounts, batch jobs)Small populations — no statistical baseline to build
Impossible-travel & volume anomaliesHighly variable human roles — everything looks anomalous
Peer-group outliersA compromised account whose “peers” are also compromised
Slow, additive changes flagged over timeAn attacker who moves inside the noise band deliberately
UEBA is a hunting aid, not an alarm: it narrows where to look, and every output needs a human to ask “is this a threat or just unusual?” The failure mode is not a wrong alert — it is a confident, quiet baseline that learned the wrong normal.
The Scope Line
It Finds the Unusual, Which Is Not the Same as the Malicious
The category error that wrecks UEBA deployments is treating “anomalous” as “bad”. Most anomalies are a person doing their job differently this week, and a SOC (Security Operations Center) that pages on every deviation drowns. The value appears only when anomaly scores are enrichment feeding an investigation, not alerts firing on their own.
Deploy UEBA to answer “which accounts should a hunter look at first?”, not “which accounts do we alert on?” It repays a mature team with a hunting practice and punishes an immature one with alert fatigue — the same tool, two outcomes, decided by whether a human sits between the score and the ticket.
🔥 Analyst Burnout as a Detection Problem BLUETEAM • Operations ▶
The Inversion

SOC (Security Operations Center) turnover is usually explained as the nature of the work — shifts, stress, the grind. But the volume of alerts an analyst faces is not weather; it is the direct output of tuning decisions made months earlier by engineers who never worked the queue. Burnout is therefore a measurable consequence of detection design, and the fix lives in the detection pipeline, not in a wellbeing programme bolted on afterwards.
What the analyst experiencesThe design decision behind it

The connection worth making explicit to management is that analyst attrition and detection precision are the same graph. 🔄 Shift Handover in a SOC (Security Operations Center) BLUETEAM • Operations ▶
The Inversion

🏗️ What Detection Engineering Is — And Why It Split Off From SOC (Security Operations Center) Analysis Detection Engineering ▶
Concept
A Software Discipline That Happens to Produce Detections
For years, writing rules was something analysts did between alerts, and the results looked like it: logic nobody else could read, no tests, no version history, and no way to tell whether a rule had ever fired on the thing it was written for. Detection engineering is the response — treating detections as a product with requirements, review, tests, deployment and a retirement plan. The split happened because the two jobs have different clocks. Analysis is interrupt-driven and measured in minutes; engineering is planned and measured in releases, and neither survives being done in the other's rhythm.
SOC analysisDetection engineering
Unit of workAn alertA detection
ClockInterrupt-driven, minutesPlanned, a release cycle
Succeeds whenThe incident is resolved correctlyThe rule fires on the technique and rarely otherwise
FeedbackThe next shiftMetrics over weeks, and purple-team results
Fails asA missed incidentA rule everyone learned to ignore
Concept
The Failure Mode It Exists to Prevent
An unengineered rule set decays in a specific, recognisable way, and every stage of the decay looks locally reasonable. Recognising the pattern is most of the argument for the discipline.
StageWhat happens
1. A rule is written after an incidentSpecific to that incident, no requirement written down
2. It is noisyAnalysts add exclusions, one hostname at a time
3. The exclusions accumulateNobody remembers which were temporary

5. It is never removedBecause nobody can prove it is not the only thing catching something

🔄 The Detection Lifecycle — Idea to Retirement, and the Gates Between Detection Engineering ▶
Flow
Seven Stages, Each With an Exit Condition
The value of naming the stages is not process for its own sake — it is that each one has a condition for leaving it, so "is this rule ready?" stops being a matter of taste.
#StageLeaves when
1IdeaA threat, an incident or an intel report names a behaviour worth catching
2RequirementThe behaviour, the log source and the expected response are written down
3LogicA query exists that matches the behaviour in your data
4TestIt fires on a synthetic or emulated instance, and not on a week of normal traffic

6TunePrecision is acceptable, and every exclusion has a reason recorded

Concept
The Two Stages Almost Everyone Skips
Stage 2 and stage 7. Skipping the requirement means nobody can later say what the rule was supposed to catch, so it can never be judged — only defended. Skipping retirement means the rule set only ever grows, and the ratio of signal to noise falls with every addition. A detection programme that has never deleted a rule is not careful; it is unmaintained.

Concept
Every Rule Is Written Against a Field Name, Not Against an Event
A detection does not match "a process started". It matches a specific field holding a specific value in a specific schema. Change the schema and the rule is worthless even though the underlying behaviour is unchanged. That is why normalisation is a detection-engineering concern rather than a data-plumbing one: the schema you normalise to is the vocabulary every rule you ever write will be phrased in, and changing it later means rewriting all of them.

ECSThe Elastic ecosystemFlat dotted field names; widely adopted beyond Elastic itself

Normalise at Ingest, or Query Through a Parser?
Two strategies, and the choice is a real trade rather than a best practice. Normalising at ingest is faster to query and destroys anything the schema has no room for; parsing at query time keeps the raw event and pays for the translation on every search.

Whichever you pick, keep the raw event somewhere for a defined window. Every schema is a judgement about what matters, and incidents are precisely the times that judgement turns out to have been wrong.
Technique
Writing Portable Logic Anyway
Full portability is a marketing claim, but a large fraction of it is reachable with discipline, and it is what makes a platform migration survivable.

🧪 Testing a Detection — Synthetic Events, Emulation & Regression Detection Engineering ▶
Concept
Three Tests, Answering Three Different Doubts
"Does this rule work" is three questions, and passing one of them says nothing about the others. A rule can match a hand-crafted event perfectly and never fire on the real technique; it can fire on the real technique and also on a backup job every night.
TestQuestionMethod
UnitDoes the logic match what I think it matches?Sample events checked into the repository, matched offline
EmulationDoes it fire on the real technique in our estate?Run the procedure on a test host and watch for the alert
NoiseDoes it fire on anything else?Run the logic across a week of historical data before deploying
The noise test is the cheapest of the three and the one most often skipped — the data is already there, and running the query over last week answers the tuning question before a single analyst is interrupted.
Technique
Regression — The Rule That Silently Stopped Working
This is the failure this whole discipline is built around. An agent upgrade renames a field, a Sysmon config is trimmed for volume, a log pipeline drops an event class — and every rule depending on it goes quiet. Nothing alerts, because the absence of alerts is what success looks like. The only defence is to make firing an expectation that can fail.
GuardHow it works
Scheduled emulationRun a benign procedure on a canary host on a schedule; alert if the detection does not fire
Field-presence monitorsAlert when a field the rules depend on drops below its normal fill rate
Volume anomaly on the sourceAlert on a log source whose volume falls off a cliff
Last-fired trackingReview rules that have not fired in 90 days — some are fine, some are broken
The tooling for the first row already exists in Adversary Emulation — Atomic Red Team & Caldera; what turns it from an exercise into a regression test is running it on a schedule and alerting on silence rather than on success.
📐 Measuring Detection Quality — Precision, Recall & the Alert-to-Incident Ratio Detection Engineering ▶
Reference
The Two Numbers, and Why You Cannot Have Both
Precision is the share of alerts that were real. Recall is the share of real events that alerted. Every threshold, every exclusion and every broadened condition trades one against the other, and pretending otherwise is how rule sets end up simultaneously noisy and blind.
MetricFormulaFalls when
Precisiontrue positives ÷ all alertsThe rule is broad, or the environment is noisier than assumed
Recalltrue positives ÷ all real occurrencesThe rule is narrow, or the telemetry is missing
Alert-to-incident ratioalerts ÷ incidents declaredA practical stand-in for precision when ground truth is unknown
Time-to-detectoccurrence → alertBatch pipelines and hourly schedules quietly dominate this
Recall is the hard one, because it needs a denominator nobody has: the real occurrences you did not see. Purple-team exercises exist largely to create that denominator artificially — a known number of executed techniques, and a count of how many alerted.
Concept
Metrics That Look Useful and Are Not
Detection programmes are frequently reported with numbers that go up when things get worse. Each of these appears on real dashboards, and each rewards the wrong behaviour.
MetricWhat it actually rewards
Number of rules deployedWriting rules, not writing good ones or deleting bad ones
Alerts triaged per analystNoise, and burning out the people absorbing it
ATT&CK (Adversarial Tactics, Techniques and Common Knowledge) techniques "covered"Claiming coverage a rule cannot deliver without the telemetry
Mean time to close an alertClosing quickly, which is not the same as investigating
A defensible dashboard is small: precision per rule, the alert-to-incident ratio, the count of rules that have not fired in 90 days, and the share of the estate reporting each log source. Four numbers, each of which gets worse when the programme gets worse.

Four things break the equivalence, and all four are invisible on the heat map: the log source may not be deployed where the technique would occur, the rule may match one procedure out of a dozen, it may be tuned to near-silence, or it may have stopped firing months ago. ✍️ Writing a Good Rule — Specificity, False-Positive Analysis & the Tuning Fields Detection Engineering ▶
Concept
Specific Enough to Be Actionable, General Enough to Survive a Variant
Every rule sits on a line between two failures. Too specific, and it matches one sample from one report — a hash, a filename, a command line copied verbatim — and the next variant walks past it. Too general, and it fires constantly and gets muted. The craft is picking the part of the behaviour that is expensive for the adversary to change, and matching on that.
Matching on…Attacker changes it by…Verdict
A file hashRecompilingNearly free to evade; use as context, not as the rule
A filename or pathRenamingStill cheap
A command-line stringReordering flags, adding whitespace, obfuscatingCheap, and the most common over-fit
A parent/child process relationshipFinding another launcherCostly — usually worth building on
The sequence of actions the objective requiresChanging the objectiveMost expensive; hardest to write
This is the Pyramid of Pain used as a design tool rather than a poster — the ladder itself is in Detection Tuning & the Pyramid of Pain.
Technique
False-Positive Analysis Before Deployment, Not After
Analysts should never be the mechanism by which a rule's noise is discovered. The historical data needed to find out first is already sitting in the platform, and the query takes minutes.
StepWhat it tells you
Run the logic over 7–30 days of historyThe real hit count, not the guessed one
Group hits by host, user and parent processWhether the noise is three machines or the whole estate
Read ten hits properlyWhether they are benign, and why — which becomes the exclusion
Project the alert rate per analyst per dayWhether the response is affordable at all
If the projected rate is more than the team can actually triage, the rule is not ready — and the fix is more often better enrichment than a tighter threshold, because a threshold that cuts volume usually cuts recall with it.
Reference
Exclusions That Do Not Rot
The exclusion list is where rules go to die: entries accumulate, nobody remembers which were meant to be temporary, and eventually the allowlist is wide enough to drive the attack through. Four rules keep it maintainable.
RuleReason
Every exclusion carries a reason and a dateAn entry nobody can justify can be deleted
Exclude on the narrowest attribute that works"This service account on this host" beats "this process name"

🎭 Behavioural vs Signature Detections — One Technique, Both Ways Detection Engineering ▶
Comparison
Two Answers to the Same Question, With Opposite Failure Modes
A signature detection asserts that a specific artifact is bad. A behavioural detection asserts that a pattern of activity is suspicious regardless of the artifacts involved. Both are legitimate, and a programme with only one kind is predictably weak in a known direction.
SignatureBehavioural
Asserts"This exact thing is bad""This pattern is how the objective is achieved"
PrecisionVery high when it hitsLower; needs context to be actionable
Evasion costNear zeroReal — the adversary must change method
Fails byMissing everything it has not seen beforeFiring on the administrator doing their job
Best forKnown-bad, commodity tooling, intel-driven blockingHands-on-keyboard activity, novel tooling
Concept
Worked Example — Credential Dumping From LSASS (Local Security Authority Subsystem Service)
The same technique, detected three ways. The interest is in how each one fails, because that is the argument for running all three rather than picking a favourite.
ApproachDetectsMissed by
Signature: the well-known tool's name or hashOff-the-shelf use, unmodifiedRenaming the binary; any custom loader
Signature: known malicious command-line patternsCopy-pasted procedures from public write-upsTrivial obfuscation and flag reordering
Behavioural: an unusual process opening a handle to LSASS with read accessAny tool that needs the memory, whatever it is calledTechniques that avoid the handle entirely — a driver, or a snapshot API (Application Programming Interface)
The behavioural rule is the durable one and also the noisy one — several legitimate security products open exactly that handle. That is not an argument against building it; it is the reason it needs an allowlist of your own tooling, dated and reviewed.
Choosing
How the Two Should Be Layered
Signatures are cheap to write, cheap to run and cheap to evade — so use them for breadth and for the commodity end of the threat, where volume matters more than sophistication. Behavioural rules are expensive in every sense — write fewer, aim them at the techniques your threat model actually cares about, and give them the enrichment they need to be triaged.
🧩 Enrichment — The Context That Turns an Alert Into a Decision Detection Engineering ▶
Concept

When a rule is drowning a team, the reflex is to tighten it, which trades away recall. Often the real problem is that the alert does not carry enough context for a decision, so every hit costs a full investigation regardless of how obvious it should have been. The same alert, arriving with the asset's criticality, the user's role and whether the destination is known, may need three seconds instead of twenty minutes — and the rule never had to change.

🔗 Correlation & Sequencing — When One Event Genuinely Is Not Enough Detection Engineering ▶
Concept

Stateful detections hold events over a window and fire on a combination. They are strictly harder than single-event rules: they cost memory, they are harder to test, they break in confusing ways when data arrives late, and their windows are a parameter nobody can derive from first principles. So the bar for using one is that the individual events are genuinely unremarkable and only the combination means anything.

Four Numbers, Each Uncomfortable in a Way the Gameable Ones Are Not
A metric is trustworthy roughly in proportion to how bad it feels to report. These four resist gaming because improving the number requires improving the thing, and each is uncomfortable on first measurement in a way that is itself informative.
MetricWhy it resists gaming
Telemetry coverage — % of assets sending the log sources your detections needCannot be improved by reclassifying anything. Needs an asset inventory, which is the honest denominator
Detection efficacy — % of emulated techniques that produced an alertMeasured by running the technique. See Adversary Emulation — Atomic Red Team & Caldera
Alert-to-incident ratioSays what proportion of the team's day is spent on things that mattered. Painful, and directly actionable
Dwell time on confirmed incidentsMeasured backwards from evidence, not forwards from the ticket. Cannot be improved by narrowing the definition
Analyst-hours per incidentReveals automation and tooling gaps that every quality metric hides
Reporting
What a Board Should Be Shown, and What It Should Not
The metrics that survive contact with an executive audience are the ones expressed as coverage and trend rather than as volume. “We handled 4,000 alerts” sounds like work and answers nothing; “we can see 71% of servers and 94% of endpoints, up from 55% and 90%” is a statement about risk that supports a decision.

The pairing this card is written to complete: a SOC's numbers and the organisation's risk reporting have to be the same story told at two levels of detail. When the security team reports coverage and the board hears alert volume, both are describing activity and neither is describing exposure — and the first genuinely bad quarter is when everyone discovers they were tracking different things.
