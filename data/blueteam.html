🦈 Wireshark — Packet Analysis NSM ▶
Reference
See Exactly What's on the Wire
Wireshark is the standard GUI protocol analyzer — capture live traffic or open a .pcap and inspect every packet, field by field. It's how you confirm what actually happened: a failed handshake, plaintext credentials, C2 beaconing, or a malformed exploit. The skill is display filters — cutting millions of packets down to the ten that matter.
▸ DISPLAY FILTERS (not capture filters)
FilterShows
ip.addr == 10.0.0.5Traffic to/from a host
tcp.port == 443A specific port
http.request.method == "POST"HTTP POSTs
tcp.flags.syn == 1 && tcp.flags.ack == 0Bare SYNs (scans)
dns.qry.name contains "evil"Suspicious DNS lookups
tcp.analysis.retransmissionNetwork trouble
Workflow: Statistics → Conversations to find the top talkers, then right-click → Follow → TCP Stream to reassemble a full session into readable text. tshark is the CLI version for scripting/large captures.
📡 tcpdump — Capture from the Command Line NSM ▶
Reference
The Capture Tool That's Already Installed
When there's no GUI — a server, a firewall, a container — tcpdump captures packets from the terminal using BPF (Berkeley Packet Filter) syntax. Grab a capture on the box, then move the .pcap to Wireshark for analysis. Every defender needs this in muscle memory. 
tcpdump -i eth0 -n                 # capture, don't resolve names (-n)
tcpdump -i eth0 -w capture.pcap     # write to file for Wireshark
tcpdump -i eth0 host 10.0.0.5      # one host
tcpdump -i eth0 port 53            # DNS only
tcpdump -i eth0 -A 'tcp port 80'  # print payload as ASCII
tcpdump -i eth0 'tcp[tcpflags] & tcp-syn != 0'  # SYNs
Tip: always add -n (skip DNS lookups — faster and quieter) and cap size with -c / -C so a capture doesn't fill the disk.
🧬 Zeek — Network Metadata & Logging NSM ▶
Reference
Not Packets — Structured Facts About Connections
Full packet capture is huge and hard to search. Zeek (formerly Bro) instead watches traffic and writes rich, structured logs — one per protocol: conn.log, dns.log, http.log, ssl.log, files.log, notice.log. It turns raw traffic into queryable evidence and is the backbone of many SOCs and Corelight sensors.
LogAnswers
conn.logWho talked to whom, how long, how many bytes
dns.logEvery query & response (catch DGA / tunneling)
ssl.log / x509.logTLS certs & JA3 fingerprints
files.logFiles seen crossing the wire (with hashes)
notice.logZeek's own alerts from its scripts
Zeek's scripting language lets you write custom detections — e.g. flag a host that makes 10,000 DNS queries an hour (tunneling) or long-lived beacons with fixed intervals (C2).
🚨 Suricata & Snort — Signature IDS/IPS NSM ▶
Reference
Rules That Fire on Known-Bad Traffic
Snort (the original) and Suricata (modern, multi-threaded) inspect traffic against signature rules and alert (IDS) or block (IPS) on matches. They ship with community/ET rulesets covering exploits, malware C2, and policy violations. Suricata adds protocol logging and file extraction, overlapping with Zeek.
▸ ANATOMY OF A RULE
alert tcp any any -> $HOME_NET 445 ( \
  msg:"ET EXPLOIT Possible SMB exploit attempt"; \
  flow:to_server,established; \
  content:"|ff|SMB"; \
  sid:2024001; rev:1; )
PartMeaning
actionalert / drop (IPS) / reject
headerproto, src/dst IPs & ports, direction
msg / sidhuman label & unique rule ID
content / flowwhat to match & connection state
Limit: signatures catch known attacks. Novel or encrypted threats slip past — pair with anomaly detection (Zeek) and endpoint telemetry.
🗄️ Arkime & ntopng — Full-Capture & Traffic Analytics NSM ▶
Reference
Searchable History of Everything on the Network
Arkime (formerly Moloch) captures and indexes full packets at scale, giving analysts a searchable web UI to pull the exact session behind an alert — critical for incident response ("show me everything that host did last Tuesday"). ntopng focuses on live traffic analytics — top talkers, flows, bandwidth, and application breakdown in real time.
ToolStrength
ArkimeRetrospective PCAP search & session pivoting at scale
ntopngReal-time flow/bandwidth dashboards & alerting
Together with Zeek (metadata) and Suricata (signatures), full capture completes the classic NSM triad: alerts tell you something happened, metadata gives context, and full packets prove exactly what.
🔍 Splunk — SPL & the SIEM Standard SIEM ▶
Reference
Ask Questions of All Your Logs at Once
A SIEM (Security Information & Event Management) ingests logs from everywhere — firewalls, endpoints, cloud, apps — and lets you search, correlate, and alert across them. Splunk is the market leader; its power is SPL (Search Processing Language), a pipe-based query language.
▸ SPL — PIPE COMMANDS TOGETHER
# Top source IPs for failed logins in the last 24h
index=auth sourcetype=linux_secure "Failed password"
| stats count by src_ip
| sort -count
| head 10

# Detect brute force: 20+ failures from one IP in 5 min
index=auth "Failed password"
| bucket _time span=5m
| stats count by _time, src_ip
| where count > 20
Mental model: search → transform (stats/ eval) → filter (where) → present. Save a search as an alert to run on a schedule and fire on matches. Splunk ES is the security-specific app with prebuilt correlation rules.

The ELK stack is the dominant open-source logging/SIEM platform. Each piece has a job, and Elastic Security adds SIEM detection rules on top.

🛡️ Wazuh — Open-Source XDR/SIEM SIEM ▶

Agents + Detection + Compliance, Free
Wazuh is a popular free platform that combines endpoint agents with a SIEM backend (built on the Elastic stack). Agents on each host do log collection, file-integrity monitoring (FIM), rootkit detection, and vulnerability detection; the manager correlates with rules and maps findings to MITRE ATT&CK and compliance frameworks (PCI, CIS).
CapabilityDetail

📥 Graylog & Loki — Log Aggregation Alternatives SIEM ▶
Reference
Two More Ways to Centralize Logs
Graylog is a streamlined, security-friendly log management platform (streams, alerts, dashboards) that's simpler to operate than raw ELK. Loki (from Grafana) takes a different tack: it indexes only labels, not full log content, making it very cheap to store — and it pairs with Grafana so logs sit next to your metrics.
ToolBest for
GraylogTurnkey central log mgmt with security features
LokiCheap, high-volume logs alongside Grafana metrics
The theme across all of these: centralize logs off the hosts. An attacker's first move is deleting local logs — if they're already shipped to a central store, the evidence survives.
📜 Sigma — Write Detections Once, Run Anywhere Detection ▶
Reference
The Vendor-Neutral Detection Format
Every SIEM has its own query language — so a detection written for Splunk doesn't work in Elastic. Sigma solves this: you write a detection once in a simple YAML format, then a converter compiles it into SPL, Elastic KQL, Wazuh rules, etc. It's "the YARA of logs" and how the community shares detections. 
title: Many Failed Logins (Brute Force)
logsource:
  product: linux
  service: auth
detection:
  selection:
    message: 'Failed password'
  condition: selection | count() by src_ip > 20
level: high
Workflow: pull community Sigma rules (or write your own) → convert to your SIEM → deploy. It makes detection engineering portable and reviewable in Git (detection-as-code).
🔬 Sysmon — The Windows Telemetry Powerhouse EDR ▶
Reference
The Logging Windows Should Have Shipped With
Sysmon (Sysinternals) is a free driver that logs rich, high-fidelity endpoint events far beyond default Windows auditing — process creation with command lines and hashes, network connections, file/registry changes, and DLL loads. It's the single highest-value free telemetry source for detecting the attacks in the Red Team domain, feeding your SIEM.
▸ HIGH-VALUE EVENT IDS
IDEvent
1Process creation (cmd line, hashes, parent) — the workhorse
3Network connection (catch C2 beacons)
7Image/DLL loaded (unsigned DLLs, injection)
8CreateRemoteThread (process injection)
10Process access — LSASS access = Mimikatz signal
11File create (dropped payloads)
22DNS query (DGA / tunneling)
Deploy with a curated config (the SwiftOnSecurity / Olaf templates are the community standard) to cut noise. Parent-child process chains (e.g. winword.exe → powershell.exe) are gold for detection.
🦉 OSQuery — Your Fleet as a SQL Database EDR ▶
Reference
Query Endpoints Like a Table
OSQuery (Meta, open source) exposes the OS as SQL tables — processes, users, listening ports, installed packages, startup items — so you can ask questions across your whole fleet with a query. It's cross-platform (Windows/macOS/Linux) and great for both incident response and continuous monitoring. 
-- What's listening on the network?
SELECT p.name, l.port, l.address
FROM listening_ports l JOIN processes p ON l.pid = p.pid;

-- Unsigned processes running from temp dirs
SELECT name, path FROM processes
WHERE path LIKE '%\Temp\%';
Run ad-hoc during IR, or schedule "packs" of queries that stream diffs to your SIEM (via Fleet/Kolide) for continuous detection — e.g. alert whenever a new persistence entry appears.

🐧 auditd & Linux Endpoint Logging EDR ▶
Reference
The Same Visibility, on Linux
auditd is the Linux audit framework — it logs syscalls, file access, and command execution against rules you define. Pair it with the Linux kernel's audit subsystem (or a modern eBPF agent like Falco) to get process-level telemetry equivalent to Sysmon on Windows. 
# Watch a sensitive file for any access
auditctl -w /etc/shadow -p rwa -k shadow-access

# Log every execve (process execution)
auditctl -a always,exit -F arch=b64 -S execve -k exec

ausearch -k shadow-access        # query by key
Ship these logs to the SIEM alongside Windows/Sysmon so hunts and detections cover the whole estate. For richer, lower-overhead visibility, eBPF-based tools (Falco, Tetragon) are the modern complement — see the eBPF topic in Linux.
🧾 YARA — Pattern-Matching Rules for Malware Detection ▶
Reference
"The Pattern-Matching Swiss Knife for Malware"
YARA lets analysts describe malware families by textual/binary patterns and match files, memory, or processes against them. It's how threat researchers share detections for a specific implant or campaign — and it runs in scanners, EDRs, and IR tools alike. 
rule Suspicious_PowerShell_Downloader {
  strings:
    $a = "DownloadString" nocase
    $b = "IEX" nocase
    $c = "FromBase64String" nocase
  condition:
    2 of them          // any 2 of the strings present
}
Use: hunt across a fleet ("scan every host for this rule" via Velociraptor/OSQuery), triage a sample, or scan process memory for an unpacked payload. Pair with yara-x (the modern engine) and community rulesets. Focus rules on behavior/capabilities, not just hashes, so they survive repacking.
🎯 MITRE ATT&CK & Navigator — Coverage-Driven Detection Detection ▶
Reference
A Shared Map of How Attackers Operate
ATT&CK is a knowledge base of real adversary tactics (the "why" — e.g. Persistence, Lateral Movement) and techniques (the "how" — e.g. T1053 Scheduled Task). It gives defenders a common language and a way to measure detection coverage rather than collecting disconnected alerts.
ConceptDetail
TacticThe adversary's goal for a step (14 columns)
Technique / Sub-techniqueThe specific method (Txxxx)
NavigatorHeat-map tool to mark what you can detect/prevent
The workflow: map each detection you have to a technique, color the Navigator, and the gaps become your detection backlog. Prioritize techniques your actual threat actors use (tie to threat intel). Every good detection references its ATT&CK ID.
⚛️ Adversary Emulation — Atomic Red Team & Caldera Detection ▶
Reference
Test Whether Your Detections Actually Fire
A detection you've never triggered is a hope, not a control. Atomic Red Team is a library of small, precise tests — one per ATT&CK technique — you run to see if your telemetry and alerts catch it. Caldera (MITRE) automates full, chained adversary emulations. This is the safe, authorized way to validate the blue team.
ToolDoes
Atomic Red TeamPer-technique "atomic" tests (run T1053, check the alert fired)
CalderaAutomated, chained emulation of full adversary behavior
Purple teamRed runs the test, blue tunes the detection, together
Run these in a lab or with authorization. The loop — emulate → observe → tune → re-test — is how you turn ATT&CK coverage from theoretical to proven.
🎚️ Detection Tuning & the Pyramid of Pain Detection ▶
Concept
Make Detections Hurt the Attacker, Not the Analyst
The Pyramid of Pain ranks indicators by how much it costs an adversary to change them. Detecting a file hash is trivial to evade (recompile); detecting their TTPs (behaviors) forces them to relearn how they operate. Aim your detections up the pyramid.
IndicatorAttacker cost to change
Hash valuesTrivial
IP addressesEasy
Domain namesSimple
Network/host artifactsAnnoying
ToolsChallenging
TTPs (behaviors)Tough — forces a rethink
Tuning: the other half is fighting false positives — a noisy rule everyone mutes is worse than no rule. Track each detection's true/false-positive rate, add context/allowlists, and require every alert to be actionable. Detection-as-code (Sigma in Git, tested with Atomic) keeps quality high.
🧠 Volatility — Memory Forensics DFIR ▶
Reference
RAM Holds What Disk Never Sees
Malware runs in memory — decrypted payloads, injected code, live network connections, and cached credentials that never touch disk. Volatility (v3) analyzes a RAM capture to reconstruct exactly what a machine was doing at the moment of capture. It's the cornerstone of incident response. 
vol -f mem.raw windows.pslist        # running processes
vol -f mem.raw windows.pstree        # parent/child tree (spot odd chains)
vol -f mem.raw windows.netscan       # network connections (C2)
vol -f mem.raw windows.malfind       # injected/hidden code
vol -f mem.raw windows.cmdline       # process command lines
Workflow: pslist/pstree to spot anomalies → malfind for injection → netscan for C2 → dump the suspect process for deeper analysis. Capture memory before pulling the plug — it's volatile (order-of-volatility rule).

Investigate a Disk Image, File by File
The Sleuth Kit (TSK) is the CLI engine; Autopsy is its GUI. Together they analyze a forensic disk image — recovering deleted files, building timelines, carving artifacts, and hashing everything — without altering the original evidence.
CapabilityDetail

⚖️ Chain of Custody & Evidence Handling DFIR ▶
Procedure
Evidence That Holds Up in Court
If findings might lead to legal action, how you handle evidence matters as much as what you find. Mishandled evidence is inadmissible — the process is as important as the tools.
PrincipleDetail
Order of volatilityCollect most-volatile first: RAM → network state → disk → archives
Write-blockingNever alter the original; image it, work on copies
HashingHash on acquisition & verify — proves the evidence is unchanged
Chain of custody logWho had it, when, why — an unbroken documented trail
DocumentationRecord every action; reproducibility = credibility
