🦈 Wireshark — Packet Analysis NSM ▶
Reference
See Exactly What's on the Wire
Wireshark is the standard GUI (Graphical User Interface) protocol analyzer — capture live traffic or open a .pcap and inspect every packet, field by field. It's how you confirm what actually happened: a failed handshake, plaintext credentials, C2 (Command and Control) beaconing, or a malformed exploit. The skill is display filters — cutting millions of packets down to the ten that matter.
▸ DISPLAY FILTERS (not capture filters)
FilterShows
ip.addr == 10.0.0.5Traffic to/from a host
tcp.port == 443A specific port
http.request.method == "POST"HTTP (HyperText Transfer Protocol) POSTs
tcp.flags.syn == 1 && tcp.flags.ack == 0Bare SYNs (Synchronize) (scans)
dns.qry.name contains "evil"Suspicious DNS (Domain Name System) lookups
tcp.analysis.retransmissionNetwork trouble
Workflow: Statistics → Conversations to find the top talkers, then right-click → Follow → TCP (Transmission Control Protocol) Stream to reassemble a full session into readable text. tshark is the CLI (Command Line Interface) version for scripting/large captures.
Blind spot
You Cannot Analyse a Capture Nobody Took
Wireshark is the best tool on this page for a question you can still reproduce, and no help at all for last Tuesday. The blind spot is retroactivity: by the time an incident is declared the packets are gone, and the only network evidence that survives is whatever something was already writing down.
QuestionCan Wireshark answer it?
What is this application doing right now?Yes — this is its home ground
What did this host do at 02:00 last Tuesday?Only if a rolling capture was already running
What was inside that TLS (Transport Layer Security) 1.3 session?Not from the server key — forward secrecy removed that. Needs SSLKEYLOGFILE from the client
Which hosts beaconed all month?Wrong tool — that is a Zeek conn.log query
The pairing is a rolling full-capture ring buffer at the choke points that matter (Arkime, or tcpdump -C -W), sized to whatever retention you can afford — even 48 hours changes what a Tuesday-morning investigation can reach. Wireshark then becomes the reader of that archive rather than a tool you can only point at the present.
📡 tcpdump — Capture from the Command Line NSM ▶
Reference
The Capture Tool That's Already Installed
When there's no GUI (Graphical User Interface) — a server, a firewall, a container — tcpdump captures packets from the terminal using BPF (Berkeley Packet Filter) syntax. Grab a capture on the box, then move the .pcap to Wireshark for analysis. Every defender needs this in muscle memory. 
tcpdump -i eth0 -n                 # capture, don't resolve names (-n)
tcpdump -i eth0 -w capture.pcap     # write to file for Wireshark
tcpdump -i eth0 host 10.0.0.5      # one host
tcpdump -i eth0 port 53            # DNS only
tcpdump -i eth0 -A 'tcp port 80'  # print payload as ASCII
tcpdump -i eth0 'tcp[tcpflags] & tcp-syn != 0'  # SYNs
Tip: always add -n (skip DNS lookups — faster and quieter) and cap size with -c / -C so a capture doesn't fill the disk.
🧬 Zeek — Network Metadata & Logging NSM ▶
Reference
Not Packets — Structured Facts About Connections
Full packet capture is huge and hard to search. Zeek (formerly Bro) instead watches traffic and writes rich, structured logs — one per protocol: conn.log, dns.log, http.log, ssl.log, files.log, notice.log. It turns raw traffic into queryable evidence and is the backbone of many SOCs (Security Operations Center) and Corelight sensors.
LogAnswers
conn.logWho talked to whom, how long, how many bytes
dns.logEvery query & response (catch DGA / tunneling)
ssl.log / x509.logTLS (Transport Layer Security) certs & JA3 fingerprints
files.logFiles seen crossing the wire (with hashes)
notice.logZeek's own alerts from its scripts
Zeek's scripting language lets you write custom detections — e.g. flag a host that makes 10,000 DNS (Domain Name System) queries an hour (tunneling) or long-lived beacons with fixed intervals (C2).
Blind spot
A Sensor Sees What Crosses It, and Less Crosses It Every Year
Zeek's logs are only as complete as the traffic reaching the tap. The gap is not a setting you forgot — it is where the sensor sits, and the amount of traffic that never passes a central chokepoint has grown every year for a decade: laptops that split-tunnel, workloads that talk east-west inside one subnet, and anything running in a cloud VPC (Virtual Private Cloud) with no on-premise path at all.
Traffic Zeek missesWhat covers it
East-west inside one VLAN (Virtual Local Area Network) or subnetHost telemetry — Sysmon 3, auditd, EDR (Endpoint Detection and Response) process and network events
Remote users on split-tunnel VPN (Virtual Private Network)The endpoint agent, or full-tunnel for the sessions that matter
Cloud workload to cloud serviceVPC flow logs, plus the provider's own service logs
Payload inside TLSssl.log gives SNI (Server Name Indication), JA3 and cert chain — treat the metadata as the detection surface
Before trusting a Zeek deployment, answer one question with a number: what percentage of your hosts' traffic physically traverses this sensor? If nobody knows, that is the finding. A sensor covering 40% of traffic is useful; a sensor believed to cover 100% while covering 40% is worse than none, because it retires the question.
🚨 Suricata & Snort — Signature IDS/IPS NSM ▶
Reference
Rules That Fire on Known-Bad Traffic
Snort (the original) and Suricata (modern, multi-threaded) inspect traffic against signature rules and alert (IDS) or block (IPS) on matches. They ship with community/ET rulesets covering exploits, malware C2 (Command and Control), and policy violations. Suricata adds protocol logging and file extraction, overlapping with Zeek.
▸ ANATOMY OF A RULE
alert tcp any any -> $HOME_NET 445 ( \
  msg:"ET EXPLOIT Possible SMB exploit attempt"; \
  flow:to_server,established; \
  content:"|ff|SMB"; \
  sid:2024001; rev:1; )
PartMeaning
actionalert / drop (IPS) / reject
headerproto, src/dst IPs (Internet Protocol) & ports, direction
msg / sidhuman label & unique rule ID
content / flowwhat to match & connection state
Limit: signatures catch known attacks. Novel or encrypted threats slip past — pair with anomaly detection (Zeek) and endpoint telemetry.
Blind spot
A Signature Is a Description of Something Already Named
Signature IDS (Intrusion Detection System) detects what somebody has already written down. That makes it excellent against commodity tooling and structurally blind to anything first-of-its-kind — not because the rules are bad, but because the rule has to exist before the traffic does.
Blind toWhat covers it
Novel or bespoke toolingAnomaly and frequency analysis over Zeek logs — beacon intervals, new-domain rates
Payload inside TLS (Transport Layer Security)JA3/JA4 fingerprints and certificate anomalies; interception only where policy allows it
Lateral movementPlacement again — a perimeter sensor never sees it. Internal taps or host telemetry
Your own environment's normalNothing ships this. It only comes from tuning against your traffic
The measurable version: track how many distinct rule IDs have fired in the last 30 days. A healthy deployment fires a long tail; a deployment where the same dozen rules produce 95% of events has been tuned into a very expensive way of detecting twelve things. That number is also the honest answer to “is the IDS working?”

🔍 Splunk — SPL (Search Processing Language) & the SIEM (Security Information and Event Management) Standard SIEM ▶
Reference
Ask Questions of All Your Logs at Once
A SIEM (Security Information & Event Management) ingests logs from everywhere — firewalls, endpoints, cloud, apps — and lets you search, correlate, and alert across them. Splunk is the market leader; its power is SPL (Search Processing Language), a pipe-based query language.
▸ SPL — PIPE COMMANDS TOGETHER
# Top source IPs for failed logins in the last 24h
index=auth sourcetype=linux_secure "Failed password"
| stats count by src_ip
| sort -count
| head 10

# Detect brute force: 20+ failures from one IP in 5 min
index=auth "Failed password"
| bucket _time span=5m
| stats count by _time, src_ip
| where count > 20
Mental model: search → transform (stats/ eval) → filter (where) → present. Save a search as an alert to run on a schedule and fire on matches. Splunk ES is the security-specific app with prebuilt correlation rules.
Cadence
Field Extractions Break Silently the Day a Log Format Changes
A SIEM's parsing is a contract with every source that feeds it, and nobody on the other end of that contract knows it exists. An application upgrade reorders a field, a vendor adds a wrapper, a firewall changes its syslog template — and the dashboards keep rendering, the searches keep running, and the results quietly go empty. Nothing errors, because a search that matches nothing is a valid search.
What needs a personHow oftenWhat it becomes without them
Checking each source is still parsingWeekly, automaticallyDetections that cannot fire, on sources everyone believes are covered
Watching event volume per sourceContinuously, with an alertA source that stopped sending three weeks ago and nobody noticed
Reviewing searches with zero resultsMonthlyA rule library where an unknown fraction is decorative
Retention and index sizingQuarterlyEither an unexpected bill or data ageing out before the investigation reaches it
Re-testing rules after upgradesPer platform releaseSilent regressions introduced by your own change window
The single most valuable alert in a SIEM is not about attacks. It is “this log source has sent nothing for an hour”, per source, with an owner — because every detection downstream of a dead source is offline and nothing else will tell you. Pair it with a monthly review of searches returning zero results over 30 days, which is where broken parsing surfaces.
🟡 Elastic / ELK Stack — Open-Source Log Analytics SIEM ▶
Reference
Elasticsearch + Logstash + Kibana + Beats
The ELK stack is the dominant open-source logging/SIEM platform. Each piece has a job, and Elastic Security adds SIEM (Security Information and Event Management) detection rules on top.
ComponentRole
BeatsLightweight shippers on hosts (Filebeat = logs, Winlogbeat = Windows events, Packetbeat = network)
LogstashIngest pipeline — parse, enrich, transform (or use Elastic ingest pipelines)
ElasticsearchThe search/analytics engine that stores & indexes everything

Flow: Beats → Logstash → Elasticsearch → Kibana. The trade vs Splunk: much cheaper (open source) but more ops effort to run and scale the cluster yourself.
Cadence
A Cluster With a Mapping Explosion and No Lifecycle Policy
Elasticsearch is happy to accept whatever you send it, which is the property that makes it easy to adopt and expensive to leave unattended. Dynamic mapping creates a field for every new key it sees, so one application logging a unique identifier as a top-level field can add hundreds of thousands of fields — and the cluster slows, then refuses writes, for reasons that look nothing like their cause.
What needs a personHow oftenWhat it becomes without them
Index templates with explicit mappingsPer new sourceDynamic mapping, then a field explosion nobody can undo without reindexing
Index lifecycle management (ILM)Configured once, reviewed quarterlyIndices from 2024 on hot storage, and a disk that fills on a Friday
Shard sizingPer index patternThousands of tiny shards — the most common cause of a slow cluster
Watching cluster health and heapContinuouslyYellow for months, then red during an incident
Snapshot testingQuarterlyBackups that have never been restored, which are not backups
Two settings prevent most of it and both are decided before the first document arrives: an index template that disables dynamic mapping for new sources, and an ILM policy with a delete phase. Retrofitting either means reindexing, which is the same lesson as the landing-zone and default-deny cards elsewhere on this site — cheap on day one, a project on day four hundred.

📜 Sigma — Write Detections Once, Run Anywhere Detection ▶
Reference
The Vendor-Neutral Detection Format
Every SIEM (Security Information and Event Management) has its own query language — so a detection written for Splunk doesn't work in Elastic. Sigma solves this: you write a detection once in a simple YAML (YAML Ain't Markup Language) format, then a converter compiles it into SPL (Search Processing Language), Elastic KQL (Kusto Query Language), Wazuh rules, etc. It's "the YARA (Yet Another Recursive Acronym) of logs" and how the community shares detections. 
title: Many Failed Logins (Brute Force)
logsource:
  product: linux
  service: auth
detection:
  selection:
    message: 'Failed password'
  condition: selection | count() by src_ip > 20
level: high
Workflow: pull community Sigma rules (or write your own) → convert to your SIEM → deploy. It makes detection engineering portable and reviewable in Git (detection-as-code).
Blind spot
Portable Rule, Non-Portable Field Names
sigmac converting a rule into your backend's query language is the easy half of portability. The rule still names fields — CommandLine, ParentImage, TargetUserName — and those exist only if your pipeline collected and named them that way. A rule that converts cleanly and matches nothing looks identical to a rule that converts cleanly and works.
Assumption inside the ruleWhere it breaks
The field was collected4688 command line was never enabled — the field is absent, not empty
The field has this nameYour pipeline normalised to ECS (Elastic Container Service) or OCSF and renamed it
The log source is what it saysA rule scoped to Sysmon, run against an estate with no Sysmon
Values look like the author'sPaths, drive letters and locale differ — a regex tuned to one estate misses in another
Every imported rule needs one test before it counts as deployed: fire the behaviour and confirm the rule alerts, with Atomic Red Team or a hand-run command. Untested imported rules are the most convincing form of coverage theatre on this page, because the rule count goes up and the detection does not.

🦉 OSQuery — Your Fleet as a SQL (Structured Query Language) Database EDR ▶
Reference
Query Endpoints Like a Table
OSQuery (Meta, open source) exposes the OS (Operating System) as SQL tables — processes, users, listening ports, installed packages, startup items — so you can ask questions across your whole fleet with a query. It's cross-platform (Windows/macOS/Linux) and great for both incident response and continuous monitoring. 
-- What's listening on the network?
SELECT p.name, l.port, l.address
FROM listening_ports l JOIN processes p ON l.pid = p.pid;

-- Unsigned processes running from temp dirs
SELECT name, path FROM processes
WHERE path LIKE '%\Temp\%';
Run ad-hoc during IR (Incident Response), or schedule "packs" of queries that stream diffs to your SIEM (Security Information and Event Management) (via Fleet/Kolide) for continuous detection — e.g. alert whenever a new persistence entry appears.
Cadence
A Query That Errors Returns Nothing, Which Looks Exactly Like a Clean Fleet
osquery (Operating System Query)'s appeal is that fleet questions become SQL. The maintenance cost is that a query which fails on a platform returns an empty result rather than an error you see — a table that does not exist on that OS version, a permission the agent lost, a path that moved. Empty and clean are indistinguishable in the console.
What needs a personHow oftenWhat it becomes without them
Validating packs per platformPer OS release, and per pack changeQueries that silently cover Linux and not macOS, or the reverse
Watching agent check-in countsDaily, automaticallyA fleet number that drifts down as agents die quietly
Reviewing query performanceMonthlyA scheduled query pinning CPU (Central Processing Unit) on laptops, and users disabling the agent
Pruning packs nobody usesQuarterlyInterval creep — dozens of queries running because somebody once wanted one
Confirming a known-true query returns rowsWeeklyNo way to distinguish 'nothing found' from 'nothing asked'
The last row is the whole discipline, and it costs one scheduled query: ask something you know must be true — a file that exists on every host, a process that always runs — and alert when it returns nothing. That single canary distinguishes a healthy deployment from a silent one, and it is the same idea as the SIEM's dead log source, one layer down.

🪟 Windows Event Logs — The IDs That Matter EDR ▶

Before Sysmon, there's the built-in Security log. Knowing the key event IDs lets you reconstruct logons, privilege use, and lateral movement — these show up constantly in SOC (Security Operations Center) interviews and real investigations.

Blind spot
The Event You Need Is Off, or Already Rolled Over
The IDs above are only useful if they were being written and were still there when you went looking. Two separate defaults defeat that, and both are Windows shipping as designed rather than anyone misconfiguring it: the richest events are disabled, and the default log sizes are small.
DefaultConsequence

Then ship the logs off the host: local retention is not retention, because the intruder who cleared 1102 owned the only copy. Forwarding to a collector is what turns these IDs from a list into evidence.
🐧 auditd & Linux Endpoint Logging EDR ▶
Reference
The Same Visibility, on Linux
auditd is the Linux audit framework — it logs syscalls, file access, and command execution against rules you define. Pair it with the Linux kernel's audit subsystem (or a modern eBPF agent like Falco) to get process-level telemetry equivalent to Sysmon on Windows. 
# Watch a sensitive file for any access
auditctl -w /etc/shadow -p rwa -k shadow-access

# Log every execve (process execution)
auditctl -a always,exit -F arch=b64 -S execve -k exec

ausearch -k shadow-access        # query by key
Ship these logs to the SIEM (Security Information and Event Management) alongside Windows/Sysmon so hunts and detections cover the whole estate. For richer, lower-overhead visibility, eBPF-based tools (Falco, Tetragon) are the modern complement — see the eBPF (Extended Berkeley Packet Filter) topic in Linux.
Blind spot
Syscalls Are Not Intent, and Containers Muddy Whose Syscall It Was
auditd records with great fidelity that a syscall happened. What it cannot supply is why, and on a container host it often cannot cleanly supply who either — containers share the host kernel, so events arrive attributed to the host namespace unless something maps them back to a container.
LimitationWhat covers it
No process ancestry in the raw eventauditd plus a session tracker, or eBPF tooling (Falco, Tetragon) that carries lineage
Container events land on the hostA runtime-aware collector that resolves cgroup to container and image
Rule cost is realScope rules to paths that matter — a blanket -a always,exit -S all is a performance incident waiting to happen
Log lives on the compromised hostForward it. Same rule as Windows
Write auditd rules against things that should never change — /etc/passwd, /etc/sudoers, /etc/ssh/, the cron directories — rather than trying to record everything every process does. A small rule set whose every hit deserves a look beats a large one nobody reads, and it costs a fraction of the CPU (Central Processing Unit).
🧾 YARA (Yet Another Recursive Acronym) — Pattern-Matching Rules for Malware Detection ▶
Reference
"The Pattern-Matching Swiss Knife for Malware"
YARA lets analysts describe malware families by textual/binary patterns and match files, memory, or processes against them. It's how threat researchers share detections for a specific implant or campaign — and it runs in scanners, EDRs (Endpoint Detection and Response), and IR (Incident Response) tools alike. 
rule Suspicious_PowerShell_Downloader {
  strings:
    $a = "DownloadString" nocase
    $b = "IEX" nocase
    $c = "FromBase64String" nocase
  condition:
    2 of them          // any 2 of the strings present
}
Use: hunt across a fleet ("scan every host for this rule" via Velociraptor/OSQuery), triage a sample, or scan process memory for an unpacked payload. Pair with yara-x (the modern engine) and community rulesets. Focus rules on behavior/capabilities, not just hashes, so they survive repacking.
Finding nothing
A Rule Is a Hypothesis About Bytes, and No Match Falsifies the Rule
YARA answers one question exactly: does this file contain the patterns I described? When the answer is no, the only sound conclusion is that the description does not fit — not that the file is harmless. Packing, a recompilation, one changed string, or a variant from the same family is enough, and none of those makes the file any less malicious.
Why a good rule missesWhat to do about it
The sample is packed or encryptedScan memory rather than disk — the strings exist at runtime
Strings were compiler-specificPrefer code constructs and structural patterns over incidental strings
A variant changed one literalWide/nocase, wildcards in hex patterns, and a lower of them threshold
The rule targets one campaignFamily and behaviour rules age far better than campaign rules
It was never tested against clean filesEvery rule needs a false-positive corpus, or it ships untested in both directions
Treat YARA as a fast filter over a large corpus, never as a verdict on one file. Its strength is retrospective: a good rule sweeps years of stored samples or every endpoint's memory in minutes and tells you where else this thing has been. Its weakness is the single clean result, which is the least informative output the tool can produce.
🎯 MITRE ATT&CK (Adversarial Tactics, Techniques and Common Knowledge) & Navigator — Coverage-Driven Detection Detection ▶
Reference
A Shared Map of How Attackers Operate
ATT&CK is a knowledge base of real adversary tactics (the "why" — e.g. Persistence, Lateral Movement) and techniques (the "how" — e.g. T1053 Scheduled Task). It gives defenders a common language and a way to measure detection coverage rather than collecting disconnected alerts.
ConceptDetail
TacticThe adversary's goal for a step (14 columns)
Technique / Sub-techniqueThe specific method (Txxxx)
NavigatorHeat-map tool to mark what you can detect/prevent
The workflow: map each detection you have to a technique, color the Navigator, and the gaps become your detection backlog. Prioritize techniques your actual threat actors use (tie to threat intel). Every good detection references its ATT&CK ID.
Finding nothing
A Green Coverage Map Means a Rule Exists, Not That It Fires
Coverage matrices are the most persuasive artefact in this domain and the easiest to mislead yourself with. A green cell means somebody wrote a rule tagged with that technique. It does not mean the rule fires on that technique, that the data source it needs is being collected, or that anyone is triaging the alert — and a matrix cannot tell the difference between a working detection and a tag.
What green can meanHow to tell
A tested detection that firesSomeone ran the technique and watched the alert arrive
A rule that references absent fieldsSigma-style field mismatch. It converts, deploys, and never matches
A rule for one procedure of manyT1059 is a technique; the rule may catch one PowerShell variant and nothing else
A vendor's tag on a generic signatureCommon in marketing matrices — check whether you or the vendor coloured the cell
A technique nobody in your threat model usesGreen here is not worth what green elsewhere is worth
Colour the matrix from test results, not from rule inventory: run the technique with Atomic Red Team or by hand, and only then mark the cell. Most teams doing this for the first time find their honest coverage is a third of what the inventory-based map claimed, and that number is far more useful — it is the one that predicts what will happen during an incident.
⚛️ Adversary Emulation — Atomic Red Team & Caldera Detection ▶
Reference
Test Whether Your Detections Actually Fire
A detection you've never triggered is a hope, not a control. Atomic Red Team is a library of small, precise tests — one per ATT&CK (Adversarial Tactics, Techniques and Common Knowledge) technique — you run to see if your telemetry and alerts catch it. Caldera (MITRE) automates full, chained adversary emulations. This is the safe, authorized way to validate the blue team.
ToolDoes
Atomic Red TeamPer-technique "atomic" tests (run T1053, check the alert fired)
CalderaAutomated, chained emulation of full adversary behavior
Purple teamRed runs the test, blue tunes the detection, together
Run these in a lab or with authorization. The loop — emulate → observe → tune → re-test — is how you turn ATT&CK coverage from theoretical to proven.
Cadence
Run Once, It Is Evidence About One Tuesday in March
An emulation exercise measures detection on the day it runs, against the estate as it was configured that morning. Presented later as coverage, it is a claim about a moment — and everything it measured has since changed: rules tuned, agents upgraded, log sources added and removed, exclusions written during an incident.
What needs a personHow oftenWhat it becomes without them
Running a fixed core setMonthly, automatedA number quoted in a board pack that is a year old
Adding techniques as intel arrivesQuarterlyTesting only what you already detect, which always looks good
Re-running after tuning changesPer change to a ruleNo idea whether a tuning change removed a detection
Recording results over timeEvery runNo trend, so no way to show improvement or catch regression
Keeping the test environment honestContinuouslyEmulation on a host with exclusions that production does not have
The value is entirely in the trend: the same twenty techniques, monthly, scored the same way, so a drop is visible and attributable to a change somebody made. A single run tells you where you stand today and nothing about whether you are getting better — and it is the repeated run, not the sophisticated one, that catches the detection quietly removed three weeks ago.

Tuning: the other half is fighting false positives — a noisy rule everyone mutes is worse than no rule. Track each detection's true/false-positive rate, add context/allowlists, and require every alert to be actionable. Detection-as-code (Sigma in Git, tested with Atomic) keeps quality high.

🧠 Volatility — Memory Forensics DFIR ▶
Reference
RAM (Random Access Memory) Holds What Disk Never Sees
Malware runs in memory — decrypted payloads, injected code, live network connections, and cached credentials that never touch disk. Volatility (v3) analyzes a RAM capture to reconstruct exactly what a machine was doing at the moment of capture. It's the cornerstone of incident response. 
vol -f mem.raw windows.pslist        # running processes
vol -f mem.raw windows.pstree        # parent/child tree (spot odd chains)
vol -f mem.raw windows.netscan       # network connections (C2)
vol -f mem.raw windows.malfind       # injected/hidden code
vol -f mem.raw windows.cmdline       # process command lines
Workflow: pslist/pstree to spot anomalies → malfind for injection → netscan for C2 (Command and Control) → dump the suspect process for deeper analysis. Capture memory before pulling the plug — it's volatile (order-of-volatility rule).
Blind spot
Memory Is Gone the Moment the Machine Is
Every Volatility plugin is downstream of one decision made by whoever touched the machine first. Acquisition is the hard part, it happens once, and “we rebooted it to be safe” ends the memory investigation before it starts — along with every injected process, unbacked page, and key that only ever existed in RAM.
Decision at the sceneWhat it costs you
Reboot or shut downAll of memory. Non-recoverable — there is no later
Pull the network cable, leave it runningPreserves memory; may trip malware that watches for it
Image the disk onlyEncryption keys, in-memory-only payloads, live network state
Snapshot a VM (Virtual Machine)Best case — the .vmem is a memory image, taken with no agent on the guest
The pairing here is not another tool but a playbook step: capture memory before containment, written into the procedure rather than decided at 3am by whoever arrived first. On a virtualised estate it is nearly free, which is a good argument for practising it on VMs until the reflex is automatic.

Absence of an Artefact Is Not Absence of Activity
Every artefact on this page has a lifetime, a default state, and a way of being removed — and analysts routinely report “no evidence of execution” when what they mean is no evidence in the four places they looked. 🧫 Malware Sandboxes — VirusTotal, Any.Run & Hybrid Analysis Threat Intel ▶
Reference
Detonate the Sample, Watch What It Does
When you have a suspicious file, a sandbox runs it in an instrumented VM (Virtual Machine) and reports its behavior — files dropped, registry changes, network callbacks — without risking a real host. VirusTotal aggregates dozens of AV verdicts + community intel; Any.Run gives an interactive live detonation; Hybrid Analysis produces deep behavioral reports.
OPSEC (Operational Security) caution: uploading a sample to a public sandbox makes it (and any secrets in it) public — attackers monitor VT for their own samples. For sensitive incidents, use a private/on-prem sandbox (Cuckoo, CAPE) instead of a public service.
Finding nothing
A Clean Verdict Often Means the Sample Knew It Was Being Watched
Detonation produces a confident-looking report and a benign verdict is the least trustworthy thing in it. Modern samples check whether they are in a sandbox and simply do nothing if they are — and a sample that does nothing looks exactly like a sample that is harmless. Several other causes produce the same clean report for reasons that have nothing to do with the file.
Reason for a benign verdictSignal that this is what happened
Anti-analysis checksVery short run, no network, no persistence — suspicious because nothing happened
Time bomb or long sleepThe sandbox ran for two minutes; the sample waits an hour

GeofencingThe C2 (Command and Control) answers only from one country
The C2 was already taken downNothing to talk to, so nothing to observe. Common with samples over a few weeks old
Read a sandbox report for behaviour, not verdict, and treat a suspiciously empty report as its own finding. Two habits help: submit to more than one sandbox, since evasion checks target specific environments; and never upload a sample you have not thought about — public submission is publication, and uploading a document from an incident can disclose it to the attacker and to everyone else.
🧭 Threat Hunting — Assume Breach, Go Looking Threat Intel ▶
Concept
Proactively Finding What Alerts Missed
Detection waits for a rule to fire; threat hunting proactively searches the environment on a hypothesis that something slipped through. It assumes breach and asks "if an attacker were here, what would I see?" — turning findings into new automated detections.
StepDetail

HuntQuery telemetry (Sysmon/EDR/SIEM) for that behavior
InvestigateTriage anomalies — benign or malicious?
OperationalizeTurn a real finding into a standing detection
Good hunts are driven by ATT&CK (Adversarial Tactics, Techniques and Common Knowledge) (hunt technique by technique) and threat intel (hunt for your actors' TTPs (Tactics, Techniques, and Procedures)). Every hunt either finds evil or finds a detection gap — both are wins.
Finding nothing
A Hunt That Finds Nothing Is Either Good News or No News
Most hunts find nothing, and that is the expected outcome rather than a failure. The problem is that an undocumented hunt cannot tell the two apart. “We looked and there was nothing” and “we looked in the wrong place with the wrong query over the wrong fortnight” produce identical write-ups, and only one of them is worth anything to the person reading it next quarter.
Write it down before you startWhy it matters afterwards
The hypothesis, as a falsifiable sentence“An attacker is using scheduled tasks for persistence” can be ruled out. “Look for weird stuff” cannot
The data source and its coverage“4698 across 82% of Windows endpoints” is a result. “The SIEM (Security Information and Event Management)” is not
The time window, and why that oneA hunt over seven days says nothing about a dwell time of ninety
The query, verbatimSo the next person can re-run it, and so you can tell it was wrong
What you would have seen if it were trueThe step that catches a query that could never have matched anything
The output of a hunt that finds nothing should be a statement of what has been ruled out, and over what coverage — which is a genuinely useful artefact, and compounds. Two other outcomes are worth as much as a finding: a detection written so the hunt never has to be run manually again, and a visibility gap discovered because the data you needed was not being collected. Both should be logged as results, not as reasons the hunt failed.

🏗️ What Detection Engineering Is — And Why It Split Off From SOC (Security Operations Center) Analysis Detection Engineering ▶
Concept
A Software Discipline That Happens to Produce Detections
For years, writing rules was something analysts did between alerts, and the results looked like it: logic nobody else could read, no tests, no version history, and no way to tell whether a rule had ever fired on the thing it was written for. Detection engineering is the response — treating detections as a product with requirements, review, tests, deployment and a retirement plan. The split happened because the two jobs have different clocks. Analysis is interrupt-driven and measured in minutes; engineering is planned and measured in releases, and neither survives being done in the other's rhythm.

An unengineered rule set decays in a specific, recognisable way, and every stage of the decay looks locally reasonable. Recognising the pattern is most of the argument for the discipline.

The value of naming the stages is not process for its own sake — it is that each one has a condition for leaving it, so "is this rule ready?" stops being a matter of taste.
#StageLeaves when
1IdeaA threat, an incident or an intel report names a behaviour worth catching
2RequirementThe behaviour, the log source and the expected response are written down
3LogicA query exists that matches the behaviour in your data
4TestIt fires on a synthetic or emulated instance, and not on a week of normal traffic
5DeployMerged, versioned, and shipped with a responder runbook
6TunePrecision is acceptable, and every exclusion has a reason recorded
7RetireThe behaviour is impossible, better covered, or the rule is measurably useless
Concept
The Two Stages Almost Everyone Skips
Stage 2 and stage 7. Skipping the requirement means nobody can later say what the rule was supposed to catch, so it can never be judged — only defended. Skipping retirement means the rule set only ever grows, and the ratio of signal to noise falls with every addition. A detection programme that has never deleted a rule is not careful; it is unmaintained.
SymptomWhich stage was skipped
"What is this alert telling me to do?"2 — no requirement, so no response was ever defined
"It has always been noisy, we just close them"6 — tuning never had a target to hit
"Nobody knows if it still works"4 — it was never tested, so there is nothing to re-run
"We have 900 rules and 40 fire"7 — nothing has ever been retired
📝 Detection Requirements — Writing One Before Writing the Rule Detection Engineering ▶
Reference
Seven Fields, and the Rule Is Half Written
A detection requirement is short — a paragraph and a table, not a document. Its purpose is to force the questions that are expensive to answer after the logic exists, particularly the third and the sixth.
FieldAnswers

If the "known benign" field is empty, the requirement is not finished — it means nobody has looked at what normal traffic does, and the tuning phase will discover it in production instead.
Concept

Ask what the analyst should do, and a surprising number of proposed detections have no answer. "Investigate" is not an answer; it is the absence of one. A detection whose only possible response is "look at it and decide it was probably fine" is producing work rather than security, and the honest options are to enrich it until a decision is possible, raise its threshold until it is rare enough to justify the look, or not build it.

📚 Log Source Inventory & Telemetry Gaps — Proving a Rule Can Fire at All Detection Engineering ▶
Concept
Coverage Claims Are Claims About Data, Not About Rules
A rule can only detect what the telemetry records. This sounds obvious and is routinely violated: coverage maps are drawn from the rule set, so a technique shows as covered because a rule exists, regardless of whether the log source that rule reads is deployed on the machines where the technique would occur. The gap is invisible in every dashboard and obvious in every incident.
Inventory columnWhy it matters
SourceWhat produces it — the sensor, not the vendor
Estate coverageWhich fraction of hosts actually send it
FidelityFull events, sampled, or summarised — the difference decides what is detectable
LatencySeconds or hours; some detections are pointless at hours
RetentionHow far back an investigation can reach
Fields presentThe specific fields rules depend on, which vendors quietly change
Technique
Prove the Gap, Don't Assert It
The convincing form of a telemetry gap is not "we think we lack process creation on servers". It is a query showing how many distinct hosts reported that event class in the last seven days, held against the asset inventory count. That is a number a budget conversation can proceed from, and it is the same query that catches silent collection failures later.
CheckReveals
Distinct reporting hosts per source, per dayEstate coverage, and the day it dropped

A collection outage is a security incident with no alert of its own unless you write one; on Windows estates, Sysmon — The Windows Telemetry Powerhouse is usually the source most worth monitoring this way, because its config is edited far more often than agents are reinstalled.
🧬 Normalisation Schemas — OCSF, ECS (Elastic Container Service) & ASIM, and Why the Schema Decides the Query Detection Engineering ▶
Concept
Every Rule Is Written Against a Field Name, Not Against an Event
A detection does not match "a process started". It matches a specific field holding a specific value in a specific schema. Change the schema and the rule is worthless even though the underlying behaviour is unchanged. That is why normalisation is a detection-engineering concern rather than a data-plumbing one: the schema you normalise to is the vocabulary every rule you ever write will be phrased in, and changing it later means rewriting all of them.
SchemaComes fromShape
OCSFA vendor-neutral consortium effortEvent classes with typed attributes; aims to be the interchange format
ECSThe Elastic ecosystemFlat dotted field names; widely adopted beyond Elastic itself
ASIMMicrosoft SentinelNormalising parsers over native tables, queried as functions
"Whatever the vendor sent"NobodyThe default, and the reason rule portability is usually zero
Choosing
Normalise at Ingest, or Query Through a Parser?
Two strategies, and the choice is a real trade rather than a best practice. Normalising at ingest is faster to query and destroys anything the schema has no room for; parsing at query time keeps the raw event and pays for the translation on every search.
Normalise at ingestParse at query time
Query speedFast — the work is already doneSlower, sometimes much
Raw fidelityLost unless you keep a copyPreserved
Schema changeReindex or accept a split historyEdit the parser, and history follows
Failure modeA field silently dropped at ingest, discovered months laterA parser that stops matching after a vendor update
Whichever you pick, keep the raw event somewhere for a defined window. Every schema is a judgement about what matters, and incidents are precisely the times that judgement turns out to have been wrong.
Technique
Writing Portable Logic Anyway
Full portability is a marketing claim, but a large fraction of it is reachable with discipline, and it is what makes a platform migration survivable.
PracticeBuys
Express the rule in Sigma, generate the backend queryOne source of truth, several deployments
Keep field mappings in one place, not in each ruleA schema change is one edit
Avoid backend-specific functions in the core logicThe clever regex is where portability dies
Test the generated query, not just the sourceGeneration is a translation, and translations have bugs
The format itself and its backends are covered by Sigma — Write Detections Once, Run Anywhere; this card is about the decision that has to be made before Sigma can help you.

🧪 Testing a Detection — Synthetic Events, Emulation & Regression Detection Engineering ▶
Concept
Three Tests, Answering Three Different Doubts
"Does this rule work" is three questions, and passing one of them says nothing about the others. A rule can match a hand-crafted event perfectly and never fire on the real technique; it can fire on the real technique and also on a backup job every night.
TestQuestionMethod
UnitDoes the logic match what I think it matches?Sample events checked into the repository, matched offline
EmulationDoes it fire on the real technique in our estate?Run the procedure on a test host and watch for the alert
NoiseDoes it fire on anything else?Run the logic across a week of historical data before deploying
The noise test is the cheapest of the three and the one most often skipped — the data is already there, and running the query over last week answers the tuning question before a single analyst is interrupted.
Technique
Regression — The Rule That Silently Stopped Working
This is the failure this whole discipline is built around. An agent upgrade renames a field, a Sysmon config is trimmed for volume, a log pipeline drops an event class — and every rule depending on it goes quiet. Nothing alerts, because the absence of alerts is what success looks like. The only defence is to make firing an expectation that can fail.
GuardHow it works
Scheduled emulationRun a benign procedure on a canary host on a schedule; alert if the detection does not fire
Field-presence monitorsAlert when a field the rules depend on drops below its normal fill rate
Volume anomaly on the sourceAlert on a log source whose volume falls off a cliff
Last-fired trackingReview rules that have not fired in 90 days — some are fine, some are broken
The tooling for the first row already exists in Adversary Emulation — Atomic Red Team & Caldera; what turns it from an exercise into a regression test is running it on a schedule and alerting on silence rather than on success.
📐 Measuring Detection Quality — Precision, Recall & the Alert-to-Incident Ratio Detection Engineering ▶
Reference
The Two Numbers, and Why You Cannot Have Both
Precision is the share of alerts that were real. Recall is the share of real events that alerted. Every threshold, every exclusion and every broadened condition trades one against the other, and pretending otherwise is how rule sets end up simultaneously noisy and blind.
MetricFormulaFalls when
Precisiontrue positives ÷ all alertsThe rule is broad, or the environment is noisier than assumed
Recalltrue positives ÷ all real occurrencesThe rule is narrow, or the telemetry is missing
Alert-to-incident ratioalerts ÷ incidents declaredA practical stand-in for precision when ground truth is unknown
Time-to-detectoccurrence → alertBatch pipelines and hourly schedules quietly dominate this
Recall is the hard one, because it needs a denominator nobody has: the real occurrences you did not see. Purple-team exercises exist largely to create that denominator artificially — a known number of executed techniques, and a count of how many alerted.
Concept
Metrics That Look Useful and Are Not
Detection programmes are frequently reported with numbers that go up when things get worse. Each of these appears on real dashboards, and each rewards the wrong behaviour.
MetricWhat it actually rewards
Number of rules deployedWriting rules, not writing good ones or deleting bad ones
Alerts triaged per analystNoise, and burning out the people absorbing it
ATT&CK (Adversarial Tactics, Techniques and Common Knowledge) techniques "covered"Claiming coverage a rule cannot deliver without the telemetry
Mean time to close an alertClosing quickly, which is not the same as investigating
A defensible dashboard is small: precision per rule, the alert-to-incident ratio, the count of rules that have not fired in 90 days, and the share of the estate reporting each log source. Four numbers, each of which gets worse when the programme gets worse.
🗺️ ATT&CK (Adversarial Tactics, Techniques and Common Knowledge) Coverage Mapping — Honest Heat Maps and the Lie of "100% Coverage" Detection Engineering ▶
Concept
A Green Square Means "A Rule Exists", Not "We Would Catch It"
Coverage maps are built by counting rules against techniques, which makes them a map of the rule set rather than of the defence. Four things break the equivalence, and all four are invisible on the heat map: the log source may not be deployed where the technique would occur, the rule may match one procedure out of a dozen, it may be tuned to near-silence, or it may have stopped firing months ago. Green is a claim about inventory; the interesting question is about capability.
The map saysReality can be
Technique coveredCovered on 40% of the estate, where the agent is deployed
Technique coveredOne procedure of many; the common variant walks past
Technique coveredCovered, but tuned down to nothing after a noisy month
Technique coveredWas covered, until a field rename in March
Technique
Colouring the Map With Something Defensible
The repair is to stop colouring by rule existence and start colouring by evidence. Each level below costs more to establish than the one before it, and each is honest about a different thing — publishing which level a square is at is more useful than any single colour.
LevelEvidence required

Concept
Coverage Is Not the Goal Anyway
Chasing breadth across the whole matrix spreads effort evenly over techniques that are not evenly likely or evenly damaging. A threat-informed programme covers the techniques its actual adversaries use, deeply, and accepts gaps elsewhere on purpose — a documented, deliberate gap is a defensible position in a way that a thin green wash is not.
🗃️ The Detection Backlog & Retiring a Rule Without Losing Why It Existed Detection Engineering ▶
Technique
Threat Model In, Rules Out
Without a queue, detections get written in response to whatever happened most recently — the last incident, the last vendor briefing, the last thing a manager read. That produces deep coverage of the past and none of the likely. A backlog is the mechanism for spending engineering time on the highest-value gap instead of the most recent noise.
InputContributes

Incidents and near-missesProven gaps, with evidence attached

Crown-jewel analysisWhere a detection is worth the most

Score each item on likelihood, impact, and whether the telemetry exists. The third column is the one that reorders the list: a high-value detection you cannot currently write is a logging project, not a detection task, and it should be routed as one.
Concept
Retirement — Deleting a Rule Is a Feature
Nobody wants to be the person who deleted the rule that would have caught it, so nothing is ever deleted, and the rule set silently degrades into a haystack. The fix is to make retirement a normal, recorded decision with criteria agreed in advance — and to note that deletion in a version-controlled repository is reversible, which removes most of the fear.

Record the retirement with its reason and the date in the repository. The next person to propose that detection will find the note, which is the difference between an institution that learns and one that rediscovers.

✍️ Writing a Good Rule — Specificity, False-Positive Analysis & the Tuning Fields Detection Engineering ▶
Concept
Specific Enough to Be Actionable, General Enough to Survive a Variant
Every rule sits on a line between two failures. Too specific, and it matches one sample from one report — a hash, a filename, a command line copied verbatim — and the next variant walks past it. Too general, and it fires constantly and gets muted. The craft is picking the part of the behaviour that is expensive for the adversary to change, and matching on that.
Matching on…Attacker changes it by…Verdict
A file hashRecompilingNearly free to evade; use as context, not as the rule
A filename or pathRenamingStill cheap
A command-line stringReordering flags, adding whitespace, obfuscatingCheap, and the most common over-fit
A parent/child process relationshipFinding another launcherCostly — usually worth building on
The sequence of actions the objective requiresChanging the objectiveMost expensive; hardest to write
This is the Pyramid of Pain used as a design tool rather than a poster — the ladder itself is in Detection Tuning & the Pyramid of Pain.
Technique
False-Positive Analysis Before Deployment, Not After
Analysts should never be the mechanism by which a rule's noise is discovered. The historical data needed to find out first is already sitting in the platform, and the query takes minutes.
StepWhat it tells you
Run the logic over 7–30 days of historyThe real hit count, not the guessed one
Group hits by host, user and parent processWhether the noise is three machines or the whole estate
Read ten hits properlyWhether they are benign, and why — which becomes the exclusion
Project the alert rate per analyst per dayWhether the response is affordable at all
If the projected rate is more than the team can actually triage, the rule is not ready — and the fix is more often better enrichment than a tighter threshold, because a threshold that cuts volume usually cuts recall with it.
Reference
Exclusions That Do Not Rot
The exclusion list is where rules go to die: entries accumulate, nobody remembers which were meant to be temporary, and eventually the allowlist is wide enough to drive the attack through. Four rules keep it maintainable.
RuleReason
Every exclusion carries a reason and a dateAn entry nobody can justify can be deleted
Exclude on the narrowest attribute that works"This service account on this host" beats "this process name"
Never exclude on an attribute the attacker controlsA rule excluding a filename is a rule with published bypass instructions
Review exclusions on a scheduleThe temporary ones outlive the thing they were for
🎭 Behavioural vs Signature Detections — One Technique, Both Ways Detection Engineering ▶
Comparison
Two Answers to the Same Question, With Opposite Failure Modes
A signature detection asserts that a specific artifact is bad. A behavioural detection asserts that a pattern of activity is suspicious regardless of the artifacts involved. Both are legitimate, and a programme with only one kind is predictably weak in a known direction.
SignatureBehavioural
Asserts"This exact thing is bad""This pattern is how the objective is achieved"
PrecisionVery high when it hitsLower; needs context to be actionable
Evasion costNear zeroReal — the adversary must change method
Fails byMissing everything it has not seen beforeFiring on the administrator doing their job
Best forKnown-bad, commodity tooling, intel-driven blockingHands-on-keyboard activity, novel tooling
Concept
Worked Example — Credential Dumping From LSASS (Local Security Authority Subsystem Service)
The same technique, detected three ways. The interest is in how each one fails, because that is the argument for running all three rather than picking a favourite.
ApproachDetectsMissed by
Signature: the well-known tool's name or hashOff-the-shelf use, unmodifiedRenaming the binary; any custom loader
Signature: known malicious command-line patternsCopy-pasted procedures from public write-upsTrivial obfuscation and flag reordering
Behavioural: an unusual process opening a handle to LSASS with read accessAny tool that needs the memory, whatever it is calledTechniques that avoid the handle entirely — a driver, or a snapshot API (Application Programming Interface)
The behavioural rule is the durable one and also the noisy one — several legitimate security products open exactly that handle. That is not an argument against building it; it is the reason it needs an allowlist of your own tooling, dated and reviewed.
Choosing
How the Two Should Be Layered
Signatures are cheap to write, cheap to run and cheap to evade — so use them for breadth and for the commodity end of the threat, where volume matters more than sophistication. Behavioural rules are expensive in every sense — write fewer, aim them at the techniques your threat model actually cares about, and give them the enrichment they need to be triaged.
🧩 Enrichment — The Context That Turns an Alert Into a Decision Detection Engineering ▶
Concept
Most "Noisy" Rules Are Actually Context-Starved
When a rule is drowning a team, the reflex is to tighten it, which trades away recall. Often the real problem is that the alert does not carry enough context for a decision, so every hit costs a full investigation regardless of how obvious it should have been. The same alert, arriving with the asset's criticality, the user's role and whether the destination is known, may need three seconds instead of twenty minutes — and the rule never had to change.
EnrichmentQuestion it answers instantly

Vulnerability and exposure stateCould the attempted thing actually have worked?
The fifth row is the cheapest large win in most environments. "First time this user has run this binary, ever" converts an ambiguous alert into an obvious one, and it needs no external data — only your own history.

Both have a place, and the deciding question is whether the context changes the verdict or merely informs the human.

🔗 Correlation & Sequencing — When One Event Genuinely Is Not Enough Detection Engineering ▶
Concept
Correlation Is Expensive — Spend It Where a Single Event Cannot Work
Stateful detections hold events over a window and fire on a combination. They are strictly harder than single-event rules: they cost memory, they are harder to test, they break in confusing ways when data arrives late, and their windows are a parameter nobody can derive from first principles. So the bar for using one is that the individual events are genuinely unremarkable and only the combination means anything.

Each of these produces silence rather than an error, which is why correlation rules need the regression guards more than any other kind.
