Filesystem Hierarchy Standard — Linux Directory Structure
Everything begins at root /. The FHS defines the purpose of each directory.
/ Root of the entire hierarchy
├─ bin/ Essential user binaries: ls, cp, mv, grep, cat
├─ sbin/ System admin binaries: fdisk, iptables, init, fsck
├─ etc/ System-wide config files: passwd, fstab, hosts, ssh/
├─ home/ User home directories: /home/alice, /home/bob
├─ root/ Root user's home — NOT inside /home
├─ var/ Variable data — logs, spool, mail, databases
└─ var/log/ System logs: auth.log, syslog, kern.log
├─ tmp/ Temporary files; typically cleared on reboot
├─ usr/ Secondary hierarchy — non-essential user programs
├─ usr/bin/ Non-essential user binaries: git, python3, vim
├─ usr/lib/ Shared libraries for /usr/bin and /usr/sbin
└─ usr/share/ Arch-independent data: man pages, icons
├─ lib/ Shared libraries for /bin & /sbin; kernel modules
├─ dev/ Device files: /dev/sda, /dev/null, /dev/random
├─ proc/ Virtual FS: /proc/cpuinfo, /proc/meminfo, /proc/PID/
├─ sys/ Virtual FS (sysfs): hardware & kernel device info
├─ mnt/ Temporary mount point for filesystems
├─ media/ Auto-mounted removable media: USB (Universal Serial Bus), CD/DVD
├─ opt/ Optional / third-party software packages
├─ srv/ Service data: web root, FTP (File Transfer Protocol) content
└─ boot/ Bootloader files: vmlinuz, initrd (Initial RAM Disk).img, grub/

🚀 Linux Boot Process (BIOS/UEFI → systemd) BOOT CHAIN ▶
Sequence Diagram
Full Linux Boot Chain — Firmware to Login
1 — BIOS (Basic Input/Output System) / UEFI (Unified Extensible Firmware Interface) Firmware
Hardware POST (Power-On Self-Test) · Locate bootable device via boot order · UEFI reads EFI (Extensible Firmware Interface) System Partition (ESP)
2 — MBR (Master Boot Record) / GPT Partition Table
Read first sector for MBR (legacy) or GUID (Globally Unique Identifier) Partition Table (UEFI) · Locate boot partition
3 — GRUB2 Bootloader
Presents boot menu · Loads compressed kernel image (vmlinuz) + initramfs (Initial RAM Filesystem) into RAM (Random Access Memory)
4 — Kernel Initialization
Decompresses itself · Probes hardware · Loads drivers · Mounts initramfs as temporary root
5 — initramfs / initrd (Initial RAM Disk)
Temporary root FS in RAM · Provides drivers needed to mount real root filesystem from disk
6 — systemd (PID 1)
First real process · Reads unit files · Manages targets (runlevels) · Starts services in parallel
7 — Login / TTY (Teletypewriter) / Display Manager
getty for console · GDM/LightDM for GUI (Graphical User Interface) · User session starts · PAM (Pluggable Authentication Modules) handles authentication
🔐 SSH (Secure Shell) — Commands, Keys & Tunneling COMPLETE REFERENCE ▶
Reference — Source: SSH Cheat Sheet
SSH · SCP (Secure Copy Protocol) · SFTP (SSH File Transfer Protocol) · ssh-keygen · Tunneling
Secure Shell listens on TCP (Transmission Control Protocol) port 22 by default. Uses asymmetric crypto for key exchange, symmetric for session data. Replaces Telnet/FTP/rsh. Config files: ~/.ssh/config (client) · /etc/ssh/sshd_config (server).
BASIC CONNECTION COMMANDS
# Connect to remote host ssh user@hostname # Default port 22 ssh -p 3344 user@hostname # Custom port ssh -i ~/.ssh/key.pem user@1.2.3.4 # Specific identity file ssh user@host 'ls -la /var/log' # Execute remote command inline ssh user@host bash < script.sh # Run local script remotely # Compress traffic (useful on slow links) ssh -C user@hostname # X11 forwarding (run GUI apps remotely) ssh -X user@hostname # Trusted X11 forwarding ssh -Y user@hostname # Less secure — full display forward
SSH KEY MANAGEMENT (ssh-keygen)
# Generate key pair (RSA 4096-bit, labeled with email) ssh-keygen -t rsa -b 4096 -C "you@email.com" # Generate modern Ed25519 key (preferred — smaller, faster) ssh-keygen -t ed25519 -C "you@email.com" # Other key management commands ssh-keygen -F hostname # Check if host is in known_hosts ssh-keygen -R hostname # Remove host from known_hosts ssh-keygen -y -f private.key # Derive public key from private key ssh-keygen -p -f ~/.ssh/id_rsa # Change key passphrase ssh-copy-id user@server # Install public key to remote host # Key files reference # ~/.ssh/id_rsa — private key (protect with chmod 600) # ~/.ssh/id_rsa.pub — public key (safe to share) # ~/.ssh/known_hosts — trusted hosts (auto-populated) # ~/.ssh/authorized_keys — keys permitted to log in here
SCP — SECURE COPY
scp user@server:/remote/file.txt ./local/ # Remote → local scp ./local/file.txt user@server:/remote/ # Local → remote scp -r user@server:/folder ./local/ # Recursive (directory) scp -P 8022 user@server:/file ./ # Custom port (-P uppercase) scp -C user@server:/big_file ./ # Enable compression scp user1@host1:/file user2@host2:/dest # Server-to-server
SSH TUNNELING — PORT FORWARDING
# LOCAL (-L): Forward local_port → remote_host:remote_port via SSH server # Access internal service on remote network as if it were local ssh -L 8080:internal-db:5432 user@jump-host # → localhost:8080 now reaches internal-db port 5432 # REMOTE (-R): Forward remote_port on SSH server → local machine # Expose a local service through a remote public server ssh -R 9090:localhost:3000 -N -f user@public-server # → public-server:9090 now reaches your local port 3000 # DYNAMIC (-D): Create a SOCKS proxy on local_port # Route browser/app traffic through SSH server ssh -D 8888 -q -C -N -f user@remote-host # → Set browser SOCKS5 proxy to 127.0.0.1:8888 # PROXY JUMP (-J): Multi-hop through bastion host ssh -J user@bastion user@internal-host ssh -J user@hop1:port1,user@hop2:port2 user@target # Multi-hop # Flags used in tunneling # -N No remote commands — dedicated tunnel only # -f Fork to background after authentication # -q Quiet mode — suppress all warnings # -C Compress tunnel data

💾 RAID (Redundant Array of Independent Disks) Levels Reference STORAGE REDUNDANCY ▶
Reference — Source: A+ Cheat Sheet
Redundant Array of Independent Disks — Levels 0, 1, 5, 6, 10
RAID provides fault tolerance and/or performance. Does NOT replace backups. Minimum disk counts and failure tolerance differ by level.
Level Name Min Disks Can Lose Characteristic Use Case
RAID 0 Striping 2 0 Data split across disks; combined read/write speed. No redundancy. Scratch disks, video editing (speed > safety)
RAID 1 Mirroring 2 1 Exact copy on each disk. Half usable capacity. Fast reads, slower writes. OS (Operating System) drives, critical single-point protection
RAID 5 Striping + Parity 3 1 Data + parity distributed. (N-1) usable capacity. Rebuild from parity on failure. File servers, NAS (Network Attached Storage); good balance of speed/redundancy
RAID 6 Double Parity 4 2 Like RAID 5 but two parity blocks. (N-2) usable capacity. Slower writes. Large arrays where double failure is a real risk
RAID 10 Stripe of Mirrors 4 1 per mirror Mirrored pairs then striped. 50% usable capacity. Excellent performance + redundancy. Databases, high-performance high-availability workloads
⚠️ RAID is NOT backup. RAID protects against drive failure only — not against ransomware, accidental deletion, corruption, or site disasters. Follow the 3-2-1 rule: 3 copies · 2 different media types · 1 offsite.

▸ LASER PRINTER IMAGING PROCESS (7 STEPS)
1 — Processing
Page data received; printer RIP (Raster Image Processor) converts to bitmap image in memory
2 — Charging
Primary corona wire/charge roller applies uniform negative charge (~-600V) to photosensitive drum
3 — Exposing
Laser beam neutralizes charge on drum where text/images will appear, creating a latent electrostatic image
4 — Developing
Negatively charged toner is attracted to the uncharged (exposed) areas of the drum; visible image forms
5 — Transferring
Transfer corona belt/roller applies positive charge to paper, attracting toner from drum to paper
6 — Fusing
Fuser assembly (heating element + pressure roller) melts toner permanently into paper fibers (~180°C)
7 — Cleaning
Cleaning blade scrapes residual toner off drum; erase lamp neutralizes drum charge for next cycle

🔐Permissions & OwnershipLinux+ • Security▶
MODEL
rwx for User / Group / Other
Three triads of read(4)/write(2)/execute(1). chmod sets them numerically or symbolically; chown / chgrp set ownership; umask sets defaults.

SUID (4000) runs as the file owner — a classic privesc target. SGID (2000) inherits group. Sticky (1000) on /tmp lets only owners delete their files.

🔑 Linux Permissions — Who Can Do What, In Depth LINUX • Essential ▶
THE PERMISSION MODEL
Reading rwxr-xr-- at a Glance
Every Linux file has an owner, a group, and a set of permissions for three categories: user (owner), group, and others. Permissions are read (r), write (w), and execute (x). When you run ls -l, the first 10 characters tell the whole story.
# ls -l output explained -rwxr-xr-- 1 alice devs 2048 Jan 15 script.sh ^└┬┘└┬┘└┬┘ └─┬─┘ └┬─┘ │ │ │ │ │ └── group name │ │ │ │ └──────── owner name │ │ │ └── others: r-- (read only) │ │ └───── group: r-x (read + execute) │ └──────── owner: rwx (read + write + execute) └────────── type: - file, d dir, l symlink # Numeric (octal) — each digit is a sum: r=4 w=2 x=1 rwx = 4+2+1 = 7 r-x = 4+0+1 = 5 r-- = 4+0+0 = 4 # So rwxr-xr-- = 754
CHMOD & CHOWN
Changing Permissions and Ownership
# Numeric (octal) mode — set absolute permissions chmod 755 script.sh # rwxr-xr-x (common for scripts) chmod 644 file.txt # rw-r--r-- (common for files) chmod 600 ~/.ssh/id_rsa # rw------- (private keys MUST be this) chmod 700 ~/.ssh # rwx------ (private dir) # Symbolic mode — modify relative to current chmod u+x script.sh # add execute for owner chmod g-w file.txt # remove write for group chmod o= secret.txt # remove ALL for others chmod a+r public.txt # add read for all (a = all) chmod -R 755 /var/www # recursive # Change ownership (usually needs sudo) chown alice file.txt # change owner chown alice:devs file.txt # change owner AND group chown -R www-data:www-data /var/www # recursive chgrp devs file.txt # change group only

💾 Storage Management — Disks, Partitions, LVM (Logical Volume Manager) & RAID (Redundant Array of Independent Disks) LINUX • Essential ▶
THE STACK
From Physical Disk to Mounted Directory
Linux storage is layered: a physical disk is divided into partitions, each formatted with a filesystem, then mounted onto a directory in the unified tree. Understanding the layers is key to managing storage and troubleshooting "disk full" emergencies.
# See block devices and their layout lsblk # tree of disks/partitions/mounts lsblk -f # include filesystem + UUID fdisk -l # detailed partition tables # Disk usage df -h # free space per filesystem df -i # inode usage (can fill before space!) du -sh /var/* # what's eating space in /var du -h --max-depth=1 / | sort -h # biggest dirs # The ten largest files anywhere find / -type f -printf '%s %p\n' 2>/dev/null | sort -rn | head -10 # Deleted but still held open — space df counts and du cannot see lsof +L1 | grep deleted
When df and du disagree, the last command is the answer. df reports the disk full, du adds up to far less, and the difference is a deleted file that some process still has open — a log rotated out from under a service that never reopened it. The space returns when that process restarts, not when the file is removed, because it already was. df -i covers the other confusing case: inodes exhausted while space remains, which is a directory full of tiny files.
PARTITION → FORMAT → MOUNT
Adding a New Disk
# 1. Partition the new disk (e.g., /dev/sdb) sudo fdisk /dev/sdb # interactive: n, w (or use parted) # 2. Create a filesystem sudo mkfs.ext4 /dev/sdb1 # or xfs, btrfs # 3. Mount it sudo mkdir /mnt/data sudo mount /dev/sdb1 /mnt/data # 4. Make it permanent — add to /etc/fstab (use UUID!) blkid /dev/sdb1 # get the UUID # /etc/fstab line: # UUID=xxxx-xxxx /mnt/data ext4 defaults 0 2 sudo mount -a # test fstab WITHOUT rebooting
Always use UUIDs (Universally Unique Identifier) in fstab, not /dev/sdb1 — device names can change between boots, and a bad fstab can prevent the system from booting. Test with mount -a before rebooting.
LVM
Logical Volume Manager — Flexible Storage
LVM adds a layer of abstraction so you can resize volumes, span disks, and snapshot — without repartitioning. The hierarchy: Physical Volumes (PV) → grouped into a Volume Group (VG) → carved into Logical Volumes (LV) that you format and mount. The killer feature: grow a volume on the fly when you add a disk.
# PV → VG → LV sudo pvcreate /dev/sdb /dev/sdc # mark disks as PVs sudo vgcreate data_vg /dev/sdb /dev/sdc # pool them into a VG sudo lvcreate -L 50G -n data_lv data_vg # carve a 50G LV sudo mkfs.ext4 /dev/data_vg/data_lv sudo mount /dev/data_vg/data_lv /mnt/data # The magic: extend it later (no downtime) sudo lvextend -L +20G /dev/data_vg/data_lv sudo resize2fs /dev/data_vg/data_lv # grow the filesystem too

🧬 Under the Hood — Namespaces & cgroups LINUX • Advanced ▶
THE SECRET
Containers Are Just Linux Processes
A container isn't a lightweight VM (Virtual Machine) — it's a normal Linux process that's been isolated using two kernel features: namespaces (what a process can SEE) and cgroups (what a process can USE). Docker just orchestrates these kernel primitives nicely. Understanding this demystifies containers — and explains both their efficiency and their security model (shared kernel = the isolation boundary).
NAMESPACES
Isolating What a Process Sees
Namespaces give a process its own private view of a system resource — so a container thinks it has its own hostname, network, process tree, etc., while really sharing one kernel.
NamespaceIsolates
PID (Process Identifier)Process IDs — container sees its own PID 1, not the host's processes

MNTMount points / filesystem view
UTSHostname and domain name
IPCInter-process communication (shared memory)

CGROUPS
Limiting What a Process Can Use
Control groups (cgroups) limit and account for resource usage — CPU (Central Processing Unit), memory, disk I/O (Input/Output), network. This is how docker run --memory 512m works, and how the kernel prevents one container from starving the others. Hit a memory cgroup limit and the OOM killer terminates the process.
# Docker resource limits are cgroups under the hood docker run --memory 512m --cpus 1.5 myapp # systemd uses cgroups too — limit a service systemctl set-property nginx.service MemoryMax=1G CPUQuota=50% # Inspect cgroup hierarchy systemd-cgls # tree of cgroups systemd-cgtop # top-like view of cgroup resource use
THE SECURITY ANGLE
Why "Shared Kernel" Matters
Because all containers share the host kernel, a kernel vulnerability or a misconfiguration can allow a container escape — breaking isolation to reach the host. This is why container hardening matters (no root, drop capabilities, read-only, seccomp profiles that restrict syscalls) and why high-security workloads sometimes use stronger isolation: gVisor (sandboxed kernel), Kata Containers (lightweight VMs per container), or just plain VMs. Defense in depth applies even to containers.

Beginner NFS (Network File System) & Samba – Sharing Files Across the Network
Core Concept
NFS vs Samba – When to Use Which
Two protocols dominate network file sharing on Linux:

NFS (Network File System)
• Linux-to-Linux sharing (Unix permissions, UIDs).
• Fast and simple; no user login required (host-based trust).
• Best for: server-to-server shares, Kubernetes persistent volumes, developer workstations on the same trusted LAN (Local Area Network).

Samba (SMB/CIFS)
• Linux server sharing files to Windows clients (and macOS).
• Supports AD (Active Directory) authentication — Windows users log in with their domain credentials.
• Best for: office file servers, home directories for Windows users.

"Not my circus, not my monkey" — if Windows clients are complaining about a share, check with the Windows team before touching Samba config; their GPOs (Group Policy Object) may be overriding settings.

Beginner LVM (Logical Volume Manager) & Storage – Flexible Disk Management on Linux
Core Concept
Why LVM? The Problem with Fixed Partitions
Traditional partitions are fixed-size — if /var fills up, resizing it usually means backing up data, repartitioning, and restoring. LVM (Logical Volume Manager) adds a flexible layer between physical disks and filesystems.

The LVM stack (bottom to top):
1. Physical Volume (PV) — a disk or partition (e.g. /dev/sdb1).
2. Volume Group (VG) — a pool combining one or more PVs.
3. Logical Volume (LV) — a "virtual partition" carved from the VG; this is what you format and mount.

Benefits: resize volumes live, add disks to a VG without downtime, take instant snapshots, and move data between physical disks transparently.
Building Blocks
Creating an LVM Setup From Scratch
This walks through turning a raw disk into a mounted, growable filesystem.
# 1. Create a physical volume on a new disk sudo pvcreate /dev/sdb # 2. Create a volume group from one or more PVs sudo vgcreate data_vg /dev/sdb # 3. Create a logical volume (50 GB) inside the VG sudo lvcreate -L 50G -n app_data data_vg # 4. Format it with a filesystem sudo mkfs.ext4 /dev/data_vg/app_data # 5. Mount it sudo mkdir -p /data sudo mount /dev/data_vg/app_data /data # 6. Make it persistent — add to /etc/fstab echo '/dev/data_vg/app_data /data ext4 defaults 0 2' | sudo tee -a /etc/fstab # Inspect the stack at any layer sudo pvdisplay # physical volumes sudo vgdisplay # volume groups sudo lvdisplay # logical volumes lsblk # visual block-device tree
Resizing
Growing a Volume Without Downtime
This is LVM's superpower — extending storage on a live system, no reboot required. Always shrink with extreme care (and a backup) — growing is safe, shrinking can destroy data.
# Scenario: /data is filling up. Add a new disk and grow it live. # 1. Add the new disk to the volume group sudo pvcreate /dev/sdc sudo vgextend data_vg /dev/sdc # 2. Grow the logical volume by 20 GB sudo lvextend -L +20G /dev/data_vg/app_data # 3. Resize the filesystem to use the new space (ext4 — does this LIVE) sudo resize2fs /dev/data_vg/app_data # For XFS filesystems, use xfs_growfs instead (also live): sudo xfs_growfs /data # Verify the new size df -h /data ─── SHRINKING (dangerous — backup first!) ─────────────────── # ext4 must be unmounted to shrink; XFS cannot be shrunk at all sudo umount /data sudo e2fsck -f /dev/data_vg/app_data sudo resize2fs /dev/data_vg/app_data 30G sudo lvreduce -L 30G /dev/data_vg/app_data
Snapshots
LVM Snapshots – Instant Point-in-Time Backups
A snapshot freezes the state of a volume at an instant, so you can back it up consistently while the original keeps changing — essential for backing up live databases.

You can't make someone make the right choice, yet you can pick up the pieces afterwards — when someone runs a bad migration against production, an LVM snapshot from five minutes earlier can save the day.
# Create a snapshot before a risky change (10GB reserved for changes) sudo lvcreate -L 10G -s -n app_data_snap /dev/data_vg/app_data # Mount the snapshot read-only to inspect/back it up sudo mkdir /mnt/snapshot sudo mount -o ro /dev/data_vg/app_data_snap /mnt/snapshot # ... run backup tools against /mnt/snapshot ... sudo umount /mnt/snapshot # Roll back to the snapshot if the change went wrong sudo umount /data sudo lvconvert --merge /dev/data_vg/app_data_snap # Volume reverts to the snapshot's state on next activation # Remove a snapshot once you no longer need it (frees space) sudo lvremove /dev/data_vg/app_data_snap # Note: snapshots are NOT a substitute for off-site backups — # they live on the same physical disks as the original data!
Beginner Mail Servers – Postfix, Dovecot & Email Plumbing
Core Concept
How Email Actually Travels
Email involves more moving parts than people realise. Three protocols and two server roles cover almost everything:

• MTA (Mail Transfer Agent) — moves mail between servers using SMTP (Simple Mail Transfer Protocol, port 25/587). Examples: Postfix, Exim, Sendmail.
• MDA (Mail Delivery Agent) / IMAP-POP server — stores mail and lets users retrieve it. Examples: Dovecot.
• IMAP (Internet Message Access Protocol) (port 143/993) — keeps mail on the server, syncs across devices (the modern standard).
• POP3 (Post Office Protocol version 3) (port 110/995) — downloads mail to one device, often deletes it from the server (legacy).

The journey of an email:
Your client → your MTA (SMTP) → recipient's MX server (SMTP) → recipient's mailbox store → recipient's client (IMAP/POP3).

Intermediate Container Internals – What Docker Is Actually Built From
Core Concept
Containers Are Not Magic — They're Linux Features
Here's the secret that demystifies Docker: "containers" aren't a real thing in the Linux kernel. Docker (and Podman, containerd, etc.) is really just a friendly interface around two much older Linux kernel features:

• Namespaces — make a process think it's alone on the system (its own PIDs, network, filesystem, hostname).
• cgroups (control groups) — limit and measure how much CPU (Central Processing Unit), memory, and I/O (Input/Output) a process (or group of processes) can use.

Put these two together — a process that can't see anything outside its bubble (namespaces) and can't consume more than its allotted resources (cgroups) — and you have a "container."

Understanding this helps you debug containers like Linux processes (because that's exactly what they are) and explains why container escapes are possible — they exploit gaps in this kernel-level isolation.
Namespaces
The Six Linux Namespace Types
Each namespace type isolates a different slice of what a process can see:
Namespace What it isolates What this means for a container PID Process IDs Container's PID 1 looks like the only process on the system NET Network interfaces, routes, ports Container has its own IP, can't see the host's network traffic MNT Filesystem mount points Container sees its own root filesystem, not the host's UTS Hostname and domain name Container can have its own hostname (e.g. "web-7d9f8c") IPC Inter-process communication Container can't access host's (shared memory, semaphores) shared memory segments USER User and group IDs "root" inside the container can map to an unprivileged host user # See the namespaces of a running process ls -la /proc/$(pgrep -f myapp | head -1)/ns/ # Output looks like: # lrwxrwxrwx ... net -> 'net:[4026532245]' # lrwxrwxrwx ... pid -> 'pid:[4026532248]' # lrwxrwxrwx ... uts -> 'uts:[4026532246]' # Compare to the host's own namespaces (PID 1) ls -la /proc/1/ns/ # Different numbers = different namespace = isolated # Run your own minimal "container" with unshare (no Docker needed!) sudo unshare --pid --net --mount --uts --fork bash hostname my-fake-container # changes hostname ONLY inside this shell ps aux # shows almost nothing — your own PID namespace

cgroups are how Docker enforces --memory=512m and --cpus=1. They live in a virtual filesystem you can explore directly.

Why It Matters
Using This Knowledge to Debug Real Problems
You can't make someone make the right choice, yet you can pick up the pieces afterwards — when a container mysteriously gets killed or throttled, knowing the internals turns "it's broken, restart it" into "I found exactly why, here's the fix":

• "My container keeps getting OOM-killed" → Check memory.current vs memory.max — the cgroup is enforcing a limit you set too low.
• "My container is randomly slow" → Check cpu.max — CPU throttling from cgroup limits looks exactly like random slowness from the inside.
• "Processes inside my container can see host processes" → The container may be running with --pid=host — a misconfiguration that breaks PID (Process Identifier) namespace isolation (and is a security risk).
• "I need to debug a container that has no shell" → Use nsenter to attach to its namespaces directly from the host: nsenter -t <PID> -n -p -m sh

Beginner File Permissions Demystified – rwx, Octal Notation, and chmod
Concept

Reading the permission string, left to right

Run ls -l and you'll see a string like -rwxr-xr-- at the start of each line. It looks cryptic until you break it into four pieces:

PositionMeansIn -rwxr-xr--
1st characterFile type: - regular file, d directory, l symlink- (a regular file)
Characters 2-4Owner's permissions: read, write, executerwx — owner can do all three
Characters 5-7Group's permissionsr-x — group can read and execute, not write
Characters 8-10Everyone else's permissionsr-- — others can only read

For a directory, the meaning of each letter shifts slightly: r lets you list its contents, w lets you create/delete files inside it, and x lets you actually enter it (via cd) or access files inside by full path. A directory with r-- but no x is a common source of confusing "permission denied" errors — you can see what's there but can't actually get in.

Concept

Octal notation: the same thing, in a faster shorthand

Each rwx triplet can be represented as a single digit by adding up values: read = 4, write = 2, execute = 1. So rwx = 4+2+1 = 7, r-x = 4+0+1 = 5, and r-- = 4+0+0 = 4. That makes -rwxr-xr-- equivalent to the much more typeable 754 — which is exactly the form you'll see in chmod commands and deployment scripts everywhere.

Octal digitPermissions grantedCommon use
7rwx — read, write, executeScripts and programs you own and run
6rw- — read and write, no executeRegular documents and config files
5r-x — read and execute, no writeShared programs others should run but not modify
4r-- — read onlyReference files nobody but the owner should change
Hands-on

Setting permissions deliberately

# View permissions in detail
ls -l deploy.sh

# Make a script executable for the owner only — common for personal scripts
chmod 700 deploy.sh
# Result: rwx------  (owner: full control, everyone else: nothing)

# Make a shared script runnable by the whole team, editable only by the owner
chmod 755 deploy.sh
# Result: rwxr-xr-x  (owner: full, group/others: read+execute)

# Symbolic form — same end result, sometimes clearer to read in scripts
chmod u=rwx,g=rx,o=rx deploy.sh

# Add execute permission without disturbing existing read/write bits
chmod +x deploy.sh

# Recursively fix an entire directory tree (use carefully!)
chmod -R u=rwX,g=rX,o= /opt/myapp
Mindset

"chmod 777 it" is the duct tape of permissions — and just as ugly under the surface

chmod 777 grants read, write, and execute to literally everyone — the owner, the group, and every other user on the system. It "fixes" almost any permission error instantly, which is exactly why it spreads through forums and Stack Overflow answers as a quick solution. Assume makes an ass out of you and me: assuming "wide open" is harmless because "it's just my home lab" is how a small convenience habit becomes a real vulnerability the day that file matters. Take the extra thirty seconds to figure out the narrowest permission that actually solves the problem — your future self (and anyone auditing the system later) will thank you.

Beginner Process Management – Finding and Taming Runaway Processes
Concept

Every running thing is a process — and every process tells a story

A process is a running instance of a program — and at any moment, a Linux system might have hundreds of them, most quietly doing their job. The skill of process management is being able to quickly answer "what's running, what's it doing, is it behaving normally, and how do I deal with it if it isn't?" — questions that come up constantly in troubleshooting, whether the symptom is "the server feels slow" or "this thing won't quit."

Hands-on

Seeing what's running, and how it's behaving

# The classic snapshot view — every process, full detail
ps aux

# Live, auto-refreshing view sorted by resource usage —
# your first stop when something "feels slow"
top
# or, with friendlier output and mouse support:
htop

# Find processes by name — handy when you know what you're
# looking for but not its process ID (PID)
pgrep -fl nginx

# See the full ancestry — what launched what, and in what order
# (extremely useful for understanding "where did this come from?")
ps -ef --forest

# Check what files and network connections a specific process has open —
# great for "why won't this file unmount?" or "what is this PID

Concept

Stopping a process: three signals, three very different outcomes

SignalCommandWhat it actually means
SIGTERM (15)kill 4821"Please shut yourself down gracefully" — gives the process a chance to save state, close connections, and clean up
SIGKILL (9)kill -9 4821"Stop immediately, no negotiation" — the kernel terminates it on the spot; the process gets no chance to clean up anything
SIGHUP (1)kill -1 4821"Reload your configuration" — many daemons treat this as "re-read your config file without fully restarting"

The escalation order matters: try SIGTERM first, wait a few seconds, and reach for SIGKILL only if the process genuinely won't respond. Reaching straight for kill -9 out of habit is how database processes end up with corrupted files and temp directories end up full of orphaned lock files — the very cleanup steps SIGTERM would have given the process a chance to perform.

Mindset

Assume makes an ass out of you and me — verify the PID (Process Identifier) before you kill it

Process IDs get reused constantly as old processes exit and new ones start — the PID you noted five minutes ago in a different terminal might belong to a completely different program by the time you act on it. Before running kill on a number you wrote down earlier, re-run ps or pgrep to confirm that PID still belongs to what you think it does. The few seconds that takes is far cheaper than explaining why you killed the wrong service.

Beginner "The Disk Is Full" – Diagnosing Storage Problems Like a Calm Professional
Concept

The classic 2 AM page: "No space left on device"

Few alerts feel as urgent as a server running out of disk space — services start failing to write logs, databases stop accepting writes, and everything gets weird in ways that don't immediately look storage-related. The good news: diagnosing where the space went is usually a five-minute job once you know the right three commands and the order to run them in.

Concept

Step 1 — confirm it, and find which filesystem is the problem

df ("disk free") shows you space at the filesystem level — this is where you confirm the emergency is real and identify exactly which mount point is the culprit:

# -h = human-readable sizes (GB/MB instead of raw byte counts)
df -h

# Typical output -- the "Use%" column is what you're scanning for:
# Filesystem      Size  Used Avail Use% Mounted on
# /dev/sda1        50G   48G  0.5G  99% /
# /dev/sdb1       200G   80G  110G  43% /var/log
#
# Here, the root filesystem ("/") is the emergency -- 99% full.
# /var/log on its own disk is fine. Now we know WHERE to dig.
Concept

Step 2 — find which directory is actually eating the space

Once you know which filesystem is full, du ("disk usage") helps you walk down the directory tree to find the actual offender — usually a runaway log file, an old backup nobody cleaned up, or a temp directory that grew out of control:

# Summarize top-level directory sizes, sorted largest first:
du -h --max-depth=1 / 2>/dev/null | sort -rh | head -10

# Drill into the biggest offender, one level deeper:
du -h --max-depth=1 /var 2>/dev/null | sort -rh | head -10

# Often the trail leads somewhere very specific, e.g.:
#   23G   /var/log/myapp/debug.log
#   -- a log rotation policy was never configured for this app
Concept

Step 3 — understand the "phantom space" trap before you panic further

Here's a scenario that confuses almost every beginner at least once: you delete a huge file, run df again, and the space still isn't free. This isn't a bug — it's how Unix-like systems handle deletion. If a running process still has the file open, the space isn't released until that process closes it (or restarts). lsof ("list open files") reveals exactly this:

# Find processes holding open file handles to deleted files
# (the "(deleted)" marker is the giveaway):
lsof +L1 2>/dev/null | grep deleted

# Output might show something like:
# myapp     2841  root   12w   REG   8,1  19327352  (deleted) /var/log/myapp/debug.log
#
# The fix isn't deleting it again -- it's already gone from the
# directory listing. Restart (or signal) the process holding it open,
# and the space returns immediately.

This is also a perfect moment to remember "assume makes an ass out of you and me" — assuming a deleted file's space was reclaimed (when it wasn't) has led more than one engineer to delete more files in a panic, sometimes ones that were actually needed. Confirm with lsof before escalating to more drastic measures.

🧱 Linux Firewalls — iptables, nftables & ufw Hardening ▶
Concept
The Kernel Decides What Packets Live or Die
Every Linux host has a packet filter built into the kernel (Netfilter). You program it with rules that ACCEPT, DROP, or REJECT packets based on source, destination, port, and protocol. Three tools front it: iptables (classic), its successor nftables, and ufw (a friendly wrapper). The default posture you want: deny inbound, allow outbound, permit only the ports you actually serve.
Reference
Chains & Policy — The Mental Model
ChainHandles
INPUTPackets destined for this host (protect your services here)
OUTPUTPackets originating from this host
FORWARDPackets routed through this host (routers, NAT, containers)
Rules in a chain are checked top to bottom; the first match wins. If nothing matches, the chain's default policy applies. Set the INPUT policy to DROP and explicitly allow what you need.
Commands

sudo ufw status numbered           # review the ruleset
Commands
iptables & nftables — The Raw Tools

🛂 SELinux (Security-Enhanced Linux) & AppArmor — Mandatory Access Control Hardening ▶
Concept

🐝 eBPF (Extended Berkeley Packet Filter) — Programmable Kernel Observability & Security Advanced ▶
Concept
Run Your Own Code Inside the Kernel — Safely
eBPF (extended Berkeley Packet Filter) lets you load small programs into the running Linux kernel that execute when events fire — a packet arrives, a system call is made, a function is entered. Historically, changing kernel behavior meant patching the kernel or writing a risky module. eBPF gives you that power without the risk: a verifier checks each program can't crash or loop forever before it runs. It's become the foundation of modern Linux observability, networking, and security tooling.
How It Works
Attach → Verify → Run → Report
StepWhat Happens
AttachHook a program to an event: kprobes (kernel fns), tracepoints, network hooks (XDP/tc), or user-space (uprobes).
VerifyThe kernel verifier proves the program is safe — bounded loops, no bad memory access — before loading.
RunIt executes in-kernel at event time, extremely fast (often JIT-compiled to native code).
ReportResults flow to user space via maps (shared key/value structures) or ring buffers.
Why It Matters
What eBPF Replaced
The old way to get deep visibility was strapping together strace, tcpdump, and sampling profilers — each with overhead and blind spots. eBPF sees everything the kernel sees, with minimal overhead, because it runs at the source of the event instead of copying data out to analyze it.
DomainWhat eBPF Enables
ObservabilityTrace syscalls, latency, and function calls live (bpftrace, BCC).
NetworkingFast packet processing & load balancing at the earliest hook (XDP, Cilium).
SecurityRuntime detection — flag suspicious syscalls/process behavior (Falco, Tetragon).
ProfilingContinuous, low-overhead CPU/off-CPU flame graphs across a fleet.

A One-Liner With bpftrace
# Count every process that opens a file, live — no app changes

# Histogram of read() sizes across the whole system

Requires a modern kernel (4.x+, richer on 5.x+) and root/capabilities. The tooling ladder: bpftrace (quick one-liners) → BCC (Python tools) → libbpf (production programs).

🔒 Secure Boot, LUKS (Linux Unified Key Setup) & Integrity — Measured Boot, dm-verity & IMA (Integrity Measurement Architecture) Linux • Hardening ▶
Core Concept
Three Different Trust Questions
"Is this machine trustworthy" is really three questions, each answered by a different mechanism, and conflating them is the usual source of confusion. Secure Boot asks: did only signed code run before the OS (Operating System)? LUKS asks: is the data unreadable when the disk is at rest? Runtime integrity (dm-verity, IMA) asks: has anything been tampered with since? You can have any one without the others, and a real hardened build wants all three.

Secure BootBootkits, unsigned kernels/driversPower-on to kernel handoff
Measured boot (TPM)Silent tampering with the boot chainRecords hashes into PCRs as it goes

dm-verityModification of a read-only rootEvery block read, at runtime

Boot Chain
Secure Boot Verifies; Measured Boot Records
These get mixed up constantly. Secure Boot is a gate: firmware verifies the bootloader's signature against keys in its store, the bootloader verifies the kernel, and an unsigned link is refused. On most hardware the chain trusts a Microsoft-controlled CA (Certificate Authority), which is why Linux distributions ship a small signed shim to bootstrap their own keys. Measured boot does not gate anything — it hashes each component into TPM (Trusted Platform Module) PCRs as it loads, producing evidence you can check afterward.
The two combine in TPM-sealed LUKS: seal the disk key to a set of PCR values so it releases automatically only when the boot chain is unchanged. Tamper with the bootloader and the PCRs differ, the TPM refuses the key, and the disk stays locked. The trade is real — a legitimate kernel update changes the measurements and you must re-seal, which is the single most common way people lock themselves out. Keep the passphrase as a fallback.
Runtime Integrity
dm-verity for Immutable Roots, IMA for Mutable Ones
dm-verity puts a hash tree under a read-only block device: every block is verified against the tree as it is read, and the tree's root hash is signed. Change one byte on disk and the read fails. It is how Android, ChromeOS and image-based Linux guarantee the root filesystem — but it assumes the filesystem never changes. For a normal writable system you want IMA/EVM instead: it measures and appraises files against signed reference values on access, and can extend those measurements into the TPM for remote attestation. 
# LUKS: the at-rest layer, in two commands
cryptsetup luksFormat /dev/sdb1        # create the encrypted volume
cryptsetup open /dev/sdb1 secure       # unlock -> /dev/mapper/secure

# Is Secure Boot actually on right now?
mokutil --sb-state
bootctl status | grep -i secure
The honest caveat: none of this defends a running, unlocked machine against someone who already has root — it defends the boot path and the data at rest. Pair it with the mandatory access control in SELinux & AppArmor — Mandatory Access Control, which is what constrains a process while the system runs.
📀 Package & Image Building — From rpm/deb to Immutable Linux Linux • Ops ▶
Core Concept
The Unit of Deployment Has Been Getting Bigger
Linux deployment has climbed a ladder of ever-larger units. First the package — install software into a shared system. Then the container image — ship the app and its dependencies as one artifact. Now the whole OS (Operating System) as an image, updated atomically. Each rung trades flexibility for reproducibility, and the higher you go the more "it works on my machine" stops being a sentence anyone says.
Packages
Building an rpm or a deb
A package is a compressed archive plus metadata: dependencies, version, and scripts that run at install and removal time. Building one means declaring what goes where and what it needs. The value is the dependency graph and the clean uninstall — which is exactly what you throw away when you curl | sudo bash a project's install script, and why that habit is worth breaking.

Images
Immutable & Image-Based Operating Systems
The newest rung ships the OS the way we ship containers: a read-only root you replace wholesale rather than patch in place. An update swaps to a new image and reboots; if it misbehaves, you roll back to the previous one because it is still there. Fleet machines become byte-identical, which kills configuration drift — the slow divergence that makes every long-lived server its own unique problem.
