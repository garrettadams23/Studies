Filesystem Hierarchy Standard — Linux Directory Structure
Everything begins at root /. The FHS defines the purpose of each directory.
/ Root of the entire hierarchy
├─ bin/ Essential user binaries: ls, cp, mv, grep, cat
├─ sbin/ System admin binaries: fdisk, iptables, init, fsck
├─ etc/ System-wide config files: passwd, fstab, hosts, ssh/
├─ home/ User home directories: /home/alice, /home/bob
├─ root/ Root user's home — NOT inside /home
├─ var/ Variable data — logs, spool, mail, databases
└─ var/log/ System logs: auth.log, syslog, kern.log
├─ tmp/ Temporary files; typically cleared on reboot
├─ usr/ Secondary hierarchy — non-essential user programs
├─ usr/bin/ Non-essential user binaries: git, python3, vim
├─ usr/lib/ Shared libraries for /usr/bin and /usr/sbin
└─ usr/share/ Arch-independent data: man pages, icons
├─ lib/ Shared libraries for /bin & /sbin; kernel modules
├─ dev/ Device files: /dev/sda, /dev/null, /dev/random
├─ proc/ Virtual FS: /proc/cpuinfo, /proc/meminfo, /proc/PID/
├─ sys/ Virtual FS (sysfs): hardware & kernel device info
├─ mnt/ Temporary mount point for filesystems
├─ media/ Auto-mounted removable media: USB, CD/DVD
├─ opt/ Optional / third-party software packages
├─ srv/ Service data: web root, FTP content
└─ boot/ Bootloader files: vmlinuz, initrd.img, grub/

🚀 Linux Boot Process (BIOS/UEFI → systemd) BOOT CHAIN ▶
Sequence Diagram
Full Linux Boot Chain — Firmware to Login
1 — BIOS / UEFI Firmware
Hardware POST · Locate bootable device via boot order · UEFI reads EFI System Partition (ESP)
2 — MBR / GPT Partition Table
Read first sector for MBR (legacy) or GUID Partition Table (UEFI) · Locate boot partition
3 — GRUB2 Bootloader
Presents boot menu · Loads compressed kernel image (vmlinuz) + initramfs into RAM
4 — Kernel Initialization
Decompresses itself · Probes hardware · Loads drivers · Mounts initramfs as temporary root
5 — initramfs / initrd
Temporary root FS in RAM · Provides drivers needed to mount real root filesystem from disk
6 — systemd (PID 1)
First real process · Reads unit files · Manages targets (runlevels) · Starts services in parallel
7 — Login / TTY / Display Manager
getty for console · GDM/LightDM for GUI · User session starts · PAM handles authentication

💾 RAID Levels Reference STORAGE REDUNDANCY ▶
Reference — Source: A+ Cheat Sheet
Redundant Array of Independent Disks — Levels 0, 1, 5, 6, 10
RAID provides fault tolerance and/or performance. Does NOT replace backups. Minimum disk counts and failure tolerance differ by level.
Level Name Min Disks Can Lose Characteristic Use Case
RAID 0 Striping 2 0 Data split across disks; combined read/write speed. No redundancy. Scratch disks, video editing (speed > safety)
RAID 1 Mirroring 2 1 Exact copy on each disk. Half usable capacity. Fast reads, slower writes. OS drives, critical single-point protection
RAID 5 Striping + Parity 3 1 Data + parity distributed. (N-1) usable capacity. Rebuild from parity on failure. File servers, NAS; good balance of speed/redundancy
RAID 6 Double Parity 4 2 Like RAID 5 but two parity blocks. (N-2) usable capacity. Slower writes. Large arrays where double failure is a real risk
RAID 10 Stripe of Mirrors 4 1 per mirror Mirrored pairs then striped. 50% usable capacity. Excellent performance + redundancy. Databases, high-performance high-availability workloads
⚠️ RAID is NOT backup. RAID protects against drive failure only — not against ransomware, accidental deletion, corruption, or site disasters. Follow the 3-2-1 rule: 3 copies · 2 different media types · 1 offsite.

▸ LASER PRINTER IMAGING PROCESS (7 STEPS)
1 — Processing
Page data received; printer RIP (Raster Image Processor) converts to bitmap image in memory
2 — Charging
Primary corona wire/charge roller applies uniform negative charge (~-600V) to photosensitive drum
3 — Exposing
Laser beam neutralizes charge on drum where text/images will appear, creating a latent electrostatic image
4 — Developing
Negatively charged toner is attracted to the uncharged (exposed) areas of the drum; visible image forms
5 — Transferring
Transfer corona belt/roller applies positive charge to paper, attracting toner from drum to paper
6 — Fusing
Fuser assembly (heating element + pressure roller) melts toner permanently into paper fibers (~180°C)
7 — Cleaning
Cleaning blade scrapes residual toner off drum; erase lamp neutralizes drum charge for next cycle

WHAT IS CRON

🔑 Linux Permissions — Who Can Do What, In Depth LINUX • Essential ›
THE PERMISSION MODEL
Reading rwxr-xr-- at a Glance
Every Linux file has an owner, a group, and a set of permissions for three categories: user (owner), group, and others. Permissions are read (r), write (w), and execute (x). When you run ls -l, the first 10 characters tell the whole story.
# ls -l output explained -rwxr-xr-- 1 alice devs 2048 Jan 15 script.sh ^└┬┘└┬┘└┬┘ └─┬─┘ └┬─┘ │ │ │ │ │ └── group name │ │ │ │ └──────── owner name │ │ │ └── others: r-- (read only) │ │ └───── group: r-x (read + execute) │ └──────── owner: rwx (read + write + execute) └────────── type: - file, d dir, l symlink # Numeric (octal) — each digit is a sum: r=4 w=2 x=1 rwx = 4+2+1 = 7 r-x = 4+0+1 = 5 r-- = 4+0+0 = 4 # So rwxr-xr-- = 754
CHMOD & CHOWN
Changing Permissions and Ownership
# Numeric (octal) mode — set absolute permissions chmod 755 script.sh # rwxr-xr-x (common for scripts) chmod 644 file.txt # rw-r--r-- (common for files) chmod 600 ~/.ssh/id_rsa # rw------- (private keys MUST be this) chmod 700 ~/.ssh # rwx------ (private dir) # Symbolic mode — modify relative to current chmod u+x script.sh # add execute for owner chmod g-w file.txt # remove write for group chmod o= secret.txt # remove ALL for others chmod a+r public.txt # add read for all (a = all) chmod -R 755 /var/www # recursive # Change ownership (usually needs sudo) chown alice file.txt # change owner chown alice:devs file.txt # change owner AND group chown -R www-data:www-data /var/www # recursive chgrp devs file.txt # change group only
SPECIAL PERMISSION BITS
SUID, SGID, and the Sticky Bit
Beyond rwx, there are three special bits that change execution and inheritance behavior. These matter for both administration and security (SUID binaries are a classic privilege-escalation target).
BitOctalEffectExample
SUID4000Run file as the FILE's owner, not the runnerpasswd runs as root so users can change their own password
SGID2000On file: run as group. On dir: new files inherit the dir's groupShared project directories
Sticky1000On dir: only the file owner can delete their files/tmp — anyone can write, but can't delete others' files
# Set special bits chmod u+s binary # SUID chmod g+s shared_dir # SGID chmod +t /shared # sticky bit # SECURITY: hunt for SUID binaries (privilege escalation recon) find / -perm -4000 -type f 2>/dev/null
UMASK & ACLs
Default Permissions and Fine-Grained Control
# umask — sets DEFAULT permissions for new files umask # show current (often 022) # New files: 666 - umask. New dirs: 777 - umask # umask 022 → files 644, dirs 755 # ACLs — go beyond owner/group/other for specific users getfacl file.txt # view ACLs setfacl -m u:bob:rw file.txt # give bob read+write setfacl -m g:contractors:r file.txt # give a group read setfacl -x u:bob file.txt # remove bob's ACL # A "+" after permissions in ls -l means ACLs are present
MANDATORY ACCESS CONTROL
SELinux and AppArmor
Standard permissions are Discretionary Access Control (DAC) — owners decide. SELinux (Red Hat) and AppArmor (Ubuntu/SUSE) add Mandatory Access Control (MAC): a system-wide policy enforces what processes can do, regardless of file ownership. Even root is constrained. This contains compromised services — a hacked web server can only touch what its policy allows.
# SELinux (Red Hat family) getenforce # Enforcing / Permissive / Disabled sestatus # detailed status ls -Z file.txt # show SELinux context setenforce 0 # temporarily permissive (testing) # Tip: don't disable SELinux to "fix" an issue — fix the policy # AppArmor (Ubuntu/Debian/SUSE) sudo aa-status # list profiles and their mode sudo aa-complain /path/to/program # log violations, don't block sudo aa-enforce /path/to/program # enforce the profile
🔑 SSH — Secure Remote Access Done Right LINUX • Essential ›
SSH BASICS
The Universal Remote Access Protocol
SSH (Secure Shell) is how you remotely access and manage Linux/Unix servers over an encrypted connection. It's foundational — every sysadmin, DevOps engineer, and security professional lives in SSH. It replaced the old, insecure Telnet (which sent passwords in plaintext).
# Connect to a server ssh alice@server.example.com ssh -p 2222 alice@server.com # custom port # Run a single command remotely ssh alice@server "df -h" # Copy files over SSH scp file.txt alice@server:/tmp/ # local → remote scp alice@server:/var/log/app.log . # remote → local rsync -avz ./data/ alice@server:/backup/ # efficient sync
KEY-BASED AUTH
Stop Using Passwords — Use Keys
SSH key pairs are far more secure than passwords: a private key (kept secret on your machine) and a public key (placed on servers). Authentication happens via cryptography, not a guessable password. This is THE standard for professional server access.
# Generate a modern key pair (ed25519 preferred) ssh-keygen -t ed25519 -C "alice@laptop" # Creates ~/.ssh/id_ed25519 (private) and id_ed25519.pub (public) # Copy your PUBLIC key to a server (enables key login) ssh-copy-id alice@server.example.com # Now you can log in without a password ssh alice@server.example.com # Permissions MUST be strict or SSH refuses the key chmod 700 ~/.ssh chmod 600 ~/.ssh/id_ed25519 # private key chmod 644 ~/.ssh/id_ed25519.pub # public key # Use ssh-agent so you don't retype the passphrase eval $(ssh-agent) ssh-add ~/.ssh/id_ed25519
SSH CONFIG
Save Yourself Typing with ~/.ssh/config
# ~/.ssh/config — define shortcuts and defaults Host web HostName web1.example.com User alice Port 2222 IdentityFile ~/.ssh/id_ed25519 Host bastion HostName jump.example.com User admin # Reach internal host through the bastion automatically Host internal-db HostName 10.0.5.20 User dbadmin ProxyJump bastion # Now just: ssh web (instead of the full command)

Locking Down the SSH Server
SSH is the #1 target of automated internet attacks — bots constantly try to brute-force it. Hardening /etc/ssh/sshd_config dramatically reduces risk.

💾 Storage Management — Disks, Partitions, LVM & RAID LINUX • Essential ›
THE STACK
From Physical Disk to Mounted Directory
Linux storage is layered: a physical disk is divided into partitions, each formatted with a filesystem, then mounted onto a directory in the unified tree. Understanding the layers is key to managing storage and troubleshooting "disk full" emergencies.
# See block devices and their layout lsblk # tree of disks/partitions/mounts lsblk -f # include filesystem + UUID fdisk -l # detailed partition tables # Disk usage df -h # free space per filesystem df -i # inode usage (can fill before space!) du -sh /var/* # what's eating space in /var du -h --max-depth=1 / | sort -h # biggest dirs
PARTITION → FORMAT → MOUNT
Adding a New Disk
# 1. Partition the new disk (e.g., /dev/sdb) sudo fdisk /dev/sdb # interactive: n, w (or use parted) # 2. Create a filesystem sudo mkfs.ext4 /dev/sdb1 # or xfs, btrfs # 3. Mount it sudo mkdir /mnt/data sudo mount /dev/sdb1 /mnt/data # 4. Make it permanent — add to /etc/fstab (use UUID!) blkid /dev/sdb1 # get the UUID # /etc/fstab line: # UUID=xxxx-xxxx /mnt/data ext4 defaults 0 2 sudo mount -a # test fstab WITHOUT rebooting
Always use UUIDs in fstab, not /dev/sdb1 — device names can change between boots, and a bad fstab can prevent the system from booting. Test with mount -a before rebooting.
LVM
Logical Volume Manager — Flexible Storage
LVM adds a layer of abstraction so you can resize volumes, span disks, and snapshot — without repartitioning. The hierarchy: Physical Volumes (PV) → grouped into a Volume Group (VG) → carved into Logical Volumes (LV) that you format and mount. The killer feature: grow a volume on the fly when you add a disk.
# PV → VG → LV sudo pvcreate /dev/sdb /dev/sdc # mark disks as PVs sudo vgcreate data_vg /dev/sdb /dev/sdc # pool them into a VG sudo lvcreate -L 50G -n data_lv data_vg # carve a 50G LV sudo mkfs.ext4 /dev/data_vg/data_lv sudo mount /dev/data_vg/data_lv /mnt/data # The magic: extend it later (no downtime) sudo lvextend -L +20G /dev/data_vg/data_lv sudo resize2fs /dev/data_vg/data_lv # grow the filesystem too
RAID LEVELS
Redundancy and Performance Tradeoffs
RAID combines multiple disks for redundancy, performance, or both. RAID is not a backup — it protects against disk failure, not against deletion, corruption, or ransomware.

RAID 1 (mirror)21 diskFull copy; simple, safe, 50% capacity

🐚 Robust Bash — Scripts That Don't Silently Destroy Things LINUX • Advanced ›
THE UNSAFE DEFAULT
Bash Keeps Going After Errors
By default, a bash script continues after a command fails — which can be catastrophic (imagine cd /backup; rm -rf * where the cd silently failed). The first thing every serious bash script should do is enable strict mode. This one line prevents a huge class of disasters.
#!/usr/bin/env bash set -euo pipefail # -e : exit immediately if any command fails # -u : error on use of undefined variables (catches typos!) # -o pipefail : a pipeline fails if ANY part fails (not just the last) IFS=$'\n\t' # safer word-splitting (avoid spaces breaking loops)

🧬 Under the Hood — Namespaces & cgroups LINUX • Advanced ›
THE SECRET
Containers Are Just Linux Processes
A container isn't a lightweight VM — it's a normal Linux process that's been isolated using two kernel features: namespaces (what a process can SEE) and cgroups (what a process can USE). Docker just orchestrates these kernel primitives nicely. Understanding this demystifies containers — and explains both their efficiency and their security model (shared kernel = the isolation boundary).
NAMESPACES
Isolating What a Process Sees
Namespaces give a process its own private view of a system resource — so a container thinks it has its own hostname, network, process tree, etc., while really sharing one kernel.
NamespaceIsolates
PIDProcess IDs — container sees its own PID 1, not the host's processes
NETNetwork interfaces, IPs, routing, ports
MNTMount points / filesystem view
UTSHostname and domain name
IPCInter-process communication (shared memory)
USERUser/group IDs — can be root inside, unprivileged outside
# See namespaces a process belongs to ls -l /proc/$$/ns # $$ = current shell's PID # Run a process in a new namespace (the raw primitive) sudo unshare --pid --fork --mount-proc bash # Inside: ps aux shows almost nothing — isolated PID namespace
CGROUPS
Limiting What a Process Can Use
Control groups (cgroups) limit and account for resource usage — CPU, memory, disk I/O, network. This is how docker run --memory 512m works, and how the kernel prevents one container from starving the others. Hit a memory cgroup limit and the OOM killer terminates the process.
# Docker resource limits are cgroups under the hood docker run --memory 512m --cpus 1.5 myapp # systemd uses cgroups too — limit a service systemctl set-property nginx.service MemoryMax=1G CPUQuota=50% # Inspect cgroup hierarchy systemd-cgls # tree of cgroups systemd-cgtop # top-like view of cgroup resource use
THE SECURITY ANGLE
Why "Shared Kernel" Matters
Because all containers share the host kernel, a kernel vulnerability or a misconfiguration can allow a container escape — breaking isolation to reach the host. This is why container hardening matters (no root, drop capabilities, read-only, seccomp profiles that restrict syscalls) and why high-security workloads sometimes use stronger isolation: gVisor (sandboxed kernel), Kata Containers (lightweight VMs per container), or just plain VMs. Defense in depth applies even to containers.
🔬 Performance Debugging — When You Need to Go Deeper LINUX • Advanced ›
BEYOND top
Tools for "Why Is This Process Doing That?"
When the basic tools (top, free, df) tell you which process is misbehaving but not why, Linux has powerful introspection tools. These let you see exactly what a running process is doing — which system calls it makes, which files it touches, where it's stuck.
STRACE & LTRACE
Watch a Process Talk to the Kernel
strace traces system calls (a process's requests to the kernel — open files, read, write, network). It's invaluable for "why is this hanging?" or "what file is it failing to find?" ltrace does the same for library calls.
# Trace system calls of a command strace ls /tmp # Attach to a RUNNING process (find why it's stuck) sudo strace -p 12345 # Only file-related calls — "what file can't it find?" strace -e trace=open,openat,stat myprogram # Count syscalls + time spent (find the bottleneck) strace -c myprogram # Classic use: a program fails silently → strace reveals # ENOENT (missing file) or EACCES (permission denied)
LSOF & FUSER
Who Has That File/Port Open?
# What files does a process have open? lsof -p 12345 # Which process is using a port? (the classic "port in use") sudo lsof -i :8080 sudo ss -tlnp | grep 8080 # Why can't I unmount this disk? What's using it? lsof +D /mnt/data fuser -m /mnt/data # Find deleted-but-still-open files eating disk space lsof | grep deleted # common cause of "df full but du not"

Beginner NFS & Samba – Sharing Files Across the Network
Core Concept
NFS vs Samba – When to Use Which
Two protocols dominate network file sharing on Linux:

NFS (Network File System)
• Linux-to-Linux sharing (Unix permissions, UIDs).
• Fast and simple; no user login required (host-based trust).
• Best for: server-to-server shares, Kubernetes persistent volumes, developer workstations on the same trusted LAN.

Samba (SMB/CIFS)
• Linux server sharing files to Windows clients (and macOS).
• Supports AD authentication — Windows users log in with their domain credentials.
• Best for: office file servers, home directories for Windows users.

"Not my circus, not my monkey" — if Windows clients are complaining about a share, check with the Windows team before touching Samba config; their GPOs may be overriding settings.
NFS Server
Setting Up an NFS Export
The NFS server exposes directories via /etc/exports. Each line names the directory and which clients may mount it.
# Install NFS server (Debian/Ubuntu) sudo apt install nfs-kernel-server # Create a shared directory sudo mkdir -p /srv/share sudo chown nobody:nogroup /srv/share sudo chmod 755 /srv/share # Edit /etc/exports # Format: /path client(options) # rw = read-write | sync = safe writes | no_subtree_check = faster /srv/share 192.168.1.0/24(rw,sync,no_subtree_check) # Apply changes and restart sudo exportfs -ra sudo systemctl restart nfs-kernel-server ─────────── NFS CLIENT SIDE ─────────── # Install NFS client tools sudo apt install nfs-common # Mount the share temporarily sudo mount 192.168.1.10:/srv/share /mnt/nfs # Make it persistent (add to /etc/fstab) 192.168.1.10:/srv/share /mnt/nfs nfs defaults,_netdev 0 0
Samba Server
Setting Up a Samba Share
Samba's configuration lives in /etc/samba/smb.conf. The [global] section sets domain-wide options; each [share-name] section defines one share.
# Install Samba sudo apt install samba # /etc/samba/smb.conf snippet [global] workgroup = CORP server string = File Server security = user ; or 'ads' for AD integration map to guest = Bad User ; unauthenticated = read-only guest [documents] path = /srv/samba/documents browseable = yes read only = no valid users = @finance ; only 'finance' Linux group create mask = 0664 directory mask = 0775 # Create a Samba user (must already be a Linux user) sudo smbpasswd -a alice # Check config for errors testparm # Restart Samba sudo systemctl restart smbd nmbd # Mount from Linux client (CIFS) sudo mount -t cifs //fileserver/documents /mnt/docs -o username=alice,password=secret,uid=$(id -u)
Troubleshooting
Common NFS & Samba Gotchas
"Assume" makes an ass out of you and me — don't assume the firewall allows NFS/SMB traffic. Always verify:

NFS troubleshooting:
• sudo showmount -e 192.168.1.10 — list exports from a server.
• NFS needs ports 111 (rpcbind) and 2049 (nfsd) open in the firewall.
• UID mismatch = files owned by wrong user; use idmapd or explicit UID mapping.

Samba troubleshooting:
• smbclient -L //server -U alice — list shares.
• sudo smbstatus — show connected clients and locked files.
• Check /var/log/samba/log.smbd for auth failures.
• SMB needs TCP 445 (and 139 for older clients).
