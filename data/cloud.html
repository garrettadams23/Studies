🌩️ Cloud Fundamentals — Regions, AZs & Shared Responsibility Foundations ▶
Concept
The Mental Model Before the Buttons
Cloud providers rent computing on demand. You should hold three ideas before touching a console: the service models (how much you manage), the global infrastructure (where your stuff physically runs), and the shared responsibility model (who secures what).
▸ SERVICE MODELS
ModelYou ManageExample
IaaSOS + runtime + appEC2, Compute Engine
PaaSJust your appApp Engine, Elastic Beanstalk
SaaSNothing — just use itGmail, Workspace
▸ GLOBAL LAYOUT
TermMeaning
RegionA geographic area (us-east-1, europe-west1). Pick for latency, law, cost.
Availability ZoneIsolated datacenter(s) in a region. Deploy across ≥2 AZs for HA.
Edge / PoPCDN locations near users (CloudFront, Cloud CDN).
Shared responsibility: the provider secures the cloud itself (hardware, hypervisor, physical); you secure what you put in it — IAM, data, patching your VMs, network config. Most breaches are the customer's side (a public bucket, a wildcard IAM policy), not the provider's.
🟧 AWS — Getting Started AWS ▶
How-To
Account, Identity & First Steps
Amazon Web Services is the largest cloud, with 200+ services. The first thing to get right is identity — mistakes here cause most incidents and surprise bills.
▸ DAY-ONE CHECKLIST
DoWhy
Stop using the root accountCreate an admin IAM user/role; lock root with MFA and don't use it daily.

Three ways to drive AWS: the Console (web, learn here), the CLI (scripting/repeatability), and SDKs/IaC (Terraform, CloudFormation) for production. Graduate from console → CLI → IaC as you go.
⌨️ AWS CLI & CloudShell AWS ▶
How-To
Driving AWS From the Terminal
aws configure                     # set key, secret, region, output format
aws configure --profile work       # named profile for a second account
aws sts get-caller-identity        # "who am I?" — confirm creds/role

aws ec2 describe-instances         # list VMs (JSON)
aws s3 ls                          # list buckets
aws s3 cp file.txt s3://my-bucket/  # upload

# JMESPath --query trims the noise; --output table for humans
aws ec2 describe-instances \
  --query 'Reservations[].Instances[].[InstanceId,State.Name]' \

CloudShell is a browser terminal with the CLI pre-authenticated as your console identity — nothing to install. Prefer IAM roles over long-lived access keys; on an EC2 instance the CLI picks up an attached role automatically (no keys on disk).

🔑 AWS IAM — Users, Roles & Policies AWS ▶
How-To
Who Can Do What, to Which Resources
IAM is the heart of AWS security — and the #1 source of breaches when done sloppily. It answers: which principal (user/role) can perform which actions on which resources, under what conditions. Everything is deny-by-default; access must be explicitly granted by a policy.
ConceptWhat
UserA long-lived human/app identity (avoid keys where possible)
RoleAn identity you assume temporarily — the preferred pattern (no stored keys)
GroupA bucket of users sharing policies
PolicyJSON document granting/denying permissions
▸ A POLICY (JSON)
{
  "Effect": "Allow",
  "Action": ["s3:GetObject"],
  "Resource": "arn:aws:s3:::my-bucket/*",
  "Condition": { "IpAddress": { "aws:SourceIp": "10.0.0.0/8" } }
}
Golden rule: grant least privilege — start with nothing, add the specific actions needed. Never attach *:* ("AdministratorAccess") to app roles.
🎫 AWS IAM Deep — AssumeRole, STS & Boundaries AWS ▶
How-To
Temporary Credentials Done Right
Long-lived access keys are the thing that leaks. The modern pattern is roles + STS: you assume a role and get temporary credentials that auto-expire (minutes to hours). Cross-account access, CI/CD, and EC2/Lambda all use this.
MechanismUse
sts:AssumeRoleSwap into a role (incl. cross-account) for short-lived creds
Trust policyOn the role — says who is allowed to assume it
Instance/Task roleEC2/ECS/Lambda auto-receive creds — no keys on disk
Permission boundaryA ceiling on the max perms an identity can ever have
IAM Identity CenterSSO for humans → short-lived console/CLI sessions
OIDC federationLet GitHub Actions assume a role with no stored secret
Policy evaluation: an explicit Deny always wins; otherwise you need an explicit Allow. Effective permission = intersection of identity policy, resource policy, permission boundary, and any SCP (org guardrail).
🔑 GCP IAM — Members, Roles & Hierarchy GCP ▶
How-To
Who (member) Can Do What (role) on Which Resource
GCP IAM binds a member (user, group, or service account) to a role (a bundle of permissions) on a resource. Because of the resource hierarchy, a binding at the project or folder level is inherited by everything beneath it — powerful and easy to over-grant.
Role typeDetail
BasicOwner/Editor/Viewer — broad, legacy, avoid in prod
PredefinedFine-grained, service-specific (e.g. roles/storage.objectViewer)
CustomYour own hand-picked permission set for true least-privilege
gcloud projects add-iam-policy-binding my-proj \
  --member="user:alice@example.com" \
  --role="roles/storage.objectViewer"
Prefer predefined/custom roles over basic ones, and bind as low in the hierarchy as possible (project > folder > org).
🤖 GCP Service Accounts & Workload Identity GCP ▶
How-To
Machine Identity Without Leaking Keys
A service account (SA) is an identity for an app or VM rather than a person. The trap is downloaded SA key files — long-lived JSON secrets that leak and rarely rotate. Workload Identity is the modern answer: it lets workloads (GKE pods, or external systems like GitHub Actions and even AWS) obtain short-lived SA credentials automatically, with no key file at all.
ApproachVerdict
Downloaded SA key (.json)Long-lived secret — avoid; the #1 GCP credential leak
Attached SA (on a VM/pod)Metadata server issues short-lived tokens automatically
Workload Identity FederationExternal identities (GitHub/AWS) assume an SA keylessly
Rule: if you're storing a .json key, ask whether Workload Identity can replace it. Usually it can.
⚠️ Cloud IAM Pitfalls & Privilege Escalation Security ▶
Security
How Over-Permissive IAM Becomes a Breach
Most cloud compromises aren't zero-days — they're IAM misconfigurations an attacker chains into full control. Knowing the traps is how you avoid (and, on a red team, find) them.
PitfallWhy It's Dangerous
Wildcards (*:*)"Just make it work" grants admin — the classic root cause
iam:PassRole / actAsLets a low-priv identity hand a powerful role to a service it controls → escalation
Overbroad AssumeRole trustA role anyone can assume is a role attackers assume
Long-lived access keysLeak in code/logs/laptops; rarely rotated
SSRF → metadata serviceApp-layer SSRF steals the instance's role creds (IMDSv2 mitigates on AWS)
Public resource policiesA bucket/queue open to "Principal": "*"
Defenses: least privilege, no wildcards, IMDSv2, short-lived creds, and continuous scanning with CSPM tools (Prowler, ScoutSuite, Steampipe) that flag these exact patterns.
🌐 AWS VPC — Subnets, Security Groups & NACLs AWS ▶
How-To
Your Private Slice of the AWS Network
A VPC is an isolated virtual network you define with a CIDR block (e.g. 10.0.0.0/16). Inside it you carve subnets, control routing, and layer two firewalls. Getting the public/private split right is the foundation of a secure architecture.
PieceRole
Public subnetRoute to an Internet Gateway (IGW) — for load balancers, bastions
Private subnetNo direct inbound; outbound via a NAT Gateway — for app servers, DBs
Route tableDecides where a subnet's traffic goes (IGW, NAT, peering)
Security GroupStateful firewall on the instance — allow rules only; return traffic auto-allowed
NACLStateless firewall on the subnet — allow + deny; must allow both directions
Remember: Security Groups are stateful (the common case, instance-level); NACLs are stateless (subnet-level, coarse). Put databases in private subnets and never give them a public IP.
🔀 AWS Load Balancing & DNS — ELB, Route 53, CloudFront AWS ▶
How-To
Getting Traffic to the Right Place, Fast
ServiceDoes
ALB (Application LB)Layer 7 — routes HTTP(S) by path/host, WebSockets, target groups
NLB (Network LB)Layer 4 — ultra-fast TCP/UDP, static IPs, extreme throughput
Route 53DNS + health checks + routing policies (latency, weighted, failover, geo)

A typical web path: Route 53 → CloudFront → ALB → targets across multiple AZs. Route 53's failover routing + health checks is how you build multi-region resilience.
🌐 GCP VPC — Global Networks & Firewall Rules GCP ▶
How-To
One Network That Spans the Planet
GCP's big networking difference: a VPC is global, not regional. One VPC can hold subnets in every region, and instances in different regions talk over Google's private backbone without extra peering. Subnets are regional; the VPC that contains them is global.
PieceRole
VPC (global)The whole network; subnets are regional within it
Firewall rulesStateful; applied by network tags or service accounts, not per-instance objects
Cloud NATManaged egress for private instances (no per-VM NAT gateway)
Cloud RouterDynamic (BGP) routing for hybrid/VPN links
Firewall rules being tag-based is the mental shift from AWS: tag an instance web, write a rule "allow 443 to tag:web" — no security-group object to attach.

🔗 Hybrid Connectivity — VPN, Interconnect & Peering Cloud ▶
Reference
Wiring the Cloud to Your Datacenter (and Itself)
Real deployments connect cloud networks to on-prem and to each other. The options trade cost against bandwidth and reliability.
NeedAWSGCP
Encrypted over internetSite-to-Site VPNCloud VPN
Private dedicated lineDirect ConnectCloud Interconnect
Connect two VPCsVPC Peering / Transit GatewayVPC Peering / Network Connectivity Center

VPN is cheap and quick but rides the public internet; Direct Connect / Interconnect is a private circuit — pricier, but consistent low latency and high bandwidth for production hybrid workloads. PrivateLink-style endpoints keep traffic to cloud services off the public internet entirely.

🏃 GCP Serverless & Containers — Cloud Run, Functions, GKE GCP ▶

Cloud Run is GCP's standout: give it a container, get a scalable HTTPS endpoint that scales to zero and bills per request — serverless containers with almost no config. It's often the simplest way to deploy a web service on any cloud.

🧭 Choosing Compute — VM vs Container vs Serverless Reference ▶
Reference
A Decision Guide
Pick…When
Serverless functionsEvent-driven, spiky, short tasks; you want zero ops & scale-to-zero
Serverless containers (Cloud Run / Fargate)Web services/APIs you want managed, but with a real container & no cold-start-only limits
Managed KubernetesMany services, complex networking, portability, an existing K8s investment
Plain VMsLegacy apps, special OS/kernel needs, GPUs, or maximum control
The trend runs left-to-right toward more managed — start as serverless as the workload allows and drop down to VMs only when you need the control. Less to operate = less to break.
💾 AWS Storage — S3 Classes, EBS & EFS AWS ▶
How-To
Three Storage Types for Three Jobs
AWS storage splits into object (S3), block (EBS — a virtual disk for one EC2), and file (EFS — a shared NFS mount for many). Pick by access pattern; mixing them up is a classic mistake. (See the Object Storage topic for S3 fundamentals — here we focus on the AWS-specific pieces.)
ServiceTypeUse
S3ObjectFiles, backups, static sites, data lakes
EBSBlockBoot/data volume for one EC2 (like a disk)
EFSFileShared filesystem mounted by many instances
FSxFileManaged Windows/Lustre file systems
▸ S3 STORAGE CLASSES (cost vs access)
ClassFor
StandardHot, frequent access
Standard-IA / One Zone-IAInfrequent access, cheaper storage
Intelligent-TieringAuto-moves objects by usage
Glacier / Deep ArchiveCold archive — pennies to store, slow/paid retrieval
Use lifecycle rules to age objects into colder classes automatically. EBS volumes are AZ-locked — snapshot to S3 for backup/restore across AZs.
🗃️ AWS Databases — RDS, Aurora & DynamoDB AWS ▶
How-To
Managed SQL & NoSQL
ServiceWhat
RDSManaged relational (Postgres, MySQL, SQL Server, Oracle, MariaDB) — patching, backups, replicas handled

📊 BigQuery — Serverless Data Warehouse GCP ▶
How-To
Query Terabytes With SQL, No Cluster
BigQuery is GCP's flagship analytics warehouse: fully serverless (no infrastructure to size), it runs SQL over terabytes-to- petabytes in seconds by massively parallelizing the scan. It's the OLAP counterpart to the transactional databases above (see the OLTP vs OLAP topic).
TraitDetail
ServerlessNo clusters; it scales compute (slots) automatically
ColumnarReads only the columns your query touches → fast + cheap
Cost modelPriced by bytes scanned (or flat-rate slots) — SELECT * on a huge table is expensive
BQ MLTrain ML models in SQL, in place
Cost tip: select only needed columns and use partitioned/clustered tables — you pay for data scanned, so pruning saves real money. AWS's equivalent is Redshift (and Athena for S3).
