🔑 AWS (Amazon Web Services) IAM (Identity and Access Management) — Users, Roles & Policies AWS ▶
How-To
Who Can Do What, to Which Resources
IAM is the heart of AWS security — and the #1 source of breaches when done sloppily. It answers: which principal (user/role) can perform which actions on which resources, under what conditions. Everything is deny-by-default; access must be explicitly granted by a policy.
ConceptWhat
UserA long-lived human/app identity (avoid keys where possible)
RoleAn identity you assume temporarily — the preferred pattern (no stored keys)
GroupA bucket of users sharing policies
PolicyJSON (JavaScript Object Notation) document granting/denying permissions
▸ A POLICY (JSON)
{
  "Effect": "Allow",
  "Action": ["s3:GetObject"],
  "Resource": "arn:aws:s3:::my-bucket/*",
  "Condition": { "IpAddress": { "aws:SourceIp": "10.0.0.0/8" } }
}
Golden rule: grant least privilege — start with nothing, add the specific actions needed. Never attach *:* ("AdministratorAccess") to app roles.
🎫 AWS (Amazon Web Services) IAM (Identity and Access Management) Deep — AssumeRole, STS (Security Token Service) & Boundaries AWS ▶
How-To
Temporary Credentials Done Right
Long-lived access keys are the thing that leaks. The modern pattern is roles + STS: you assume a role and get temporary credentials that auto-expire (minutes to hours). Cross-account access, CI/CD (Continuous Integration / Continuous Delivery), and EC2/Lambda all use this.
MechanismUse
sts:AssumeRoleSwap into a role (incl. cross-account) for short-lived creds
Trust policyOn the role — says who is allowed to assume it
Instance/Task roleEC2/ECS/Lambda auto-receive creds — no keys on disk
Permission boundaryA ceiling on the max perms an identity can ever have
IAM Identity CenterSSO (Single Sign-On) for humans → short-lived console/CLI sessions
OIDC (OpenID Connect) federationLet GitHub Actions assume a role with no stored secret
Policy evaluation: an explicit Deny always wins; otherwise you need an explicit Allow. Effective permission = intersection of identity policy, resource policy, permission boundary, and any SCP (Service Control Policy) (org guardrail).
🔑 GCP (Google Cloud Platform) IAM (Identity and Access Management) — Members, Roles & Hierarchy GCP ▶
How-To
Who (member) Can Do What (role) on Which Resource
GCP IAM binds a member (user, group, or service account) to a role (a bundle of permissions) on a resource. Because of the resource hierarchy, a binding at the project or folder level is inherited by everything beneath it — powerful and easy to over-grant.
Role typeDetail
BasicOwner/Editor/Viewer — broad, legacy, avoid in prod
PredefinedFine-grained, service-specific (e.g. roles/storage.objectViewer)

  --member="user:alice@example.com" \

Prefer predefined/custom roles over basic ones, and bind as low in the hierarchy as possible (project > folder > org).
🤖 GCP (Google Cloud Platform) Service Accounts & Workload Identity GCP ▶
How-To
Machine Identity Without Leaking Keys
A service account (SA) is an identity for an app or VM (Virtual Machine) rather than a person. The trap is downloaded SA key files — long-lived JSON (JavaScript Object Notation) secrets that leak and rarely rotate. Workload Identity is the modern answer: it lets workloads (GKE pods, or external systems like GitHub Actions and even AWS) obtain short-lived SA credentials automatically, with no key file at all.
ApproachVerdict
Downloaded SA key (.json)Long-lived secret — avoid; the #1 GCP credential leak
Attached SA (on a VM/pod)Metadata server issues short-lived tokens automatically
Workload Identity FederationExternal identities (GitHub/AWS) assume an SA keylessly
Rule: if you're storing a .json key, ask whether Workload Identity can replace it. Usually it can.
⚠️ Cloud IAM (Identity and Access Management) Pitfalls & Privilege Escalation Security ▶
Security
How Over-Permissive IAM Becomes a Breach
Most cloud compromises aren't zero-days — they're IAM misconfigurations an attacker chains into full control. Knowing the traps is how you avoid (and, on a red team, find) them.
PitfallWhy It's Dangerous
Wildcards (*:*)"Just make it work" grants admin — the classic root cause
iam:PassRole / actAsLets a low-priv identity hand a powerful role to a service it controls → escalation
Overbroad AssumeRole trustA role anyone can assume is a role attackers assume
Long-lived access keysLeak in code/logs/laptops; rarely rotated
SSRF (Server-Side Request Forgery) → metadata serviceApp-layer SSRF steals the instance's role creds (IMDSv2 mitigates on AWS)
Public resource policiesA bucket/queue open to "Principal": "*"
Defenses: least privilege, no wildcards, IMDSv2, short-lived creds, and continuous scanning with CSPM (Cloud Security Posture Management) tools (Prowler, ScoutSuite, Steampipe) that flag these exact patterns.
🌐 AWS (Amazon Web Services) VPC (Virtual Private Cloud) — Subnets, Security Groups & NACLs (Network Access Control List) AWS ▶
How-To
Your Private Slice of the AWS Network
A VPC is an isolated virtual network you define with a CIDR (Classless Inter-Domain Routing) block (e.g. 10.0.0.0/16). Inside it you carve subnets, control routing, and layer two firewalls. Getting the public/private split right is the foundation of a secure architecture.
PieceRole
Public subnetRoute to an Internet Gateway (IGW) — for load balancers, bastions
Private subnetNo direct inbound; outbound via a NAT (Network Address Translation) Gateway — for app servers, DBs
Route tableDecides where a subnet's traffic goes (IGW, NAT, peering)
Security GroupStateful firewall on the instance — allow rules only; return traffic auto-allowed
NACLStateless firewall on the subnet — allow + deny; must allow both directions
Remember: Security Groups are stateful (the common case, instance-level); NACLs are stateless (subnet-level, coarse). Put databases in private subnets and never give them a public IP (Internet Protocol).

GCP's big networking difference: a VPC is global, not regional. One VPC can hold subnets in every region, and instances in different regions talk over Google's private backbone without extra peering. Subnets are regional; the VPC that contains them is global.

| where TimeGenerated > ago(1d)
| where OperationNameValue endswith "/DELETE"

☸️ The Kubernetes Threat Model — The Four Cs and What an Attacker Sees Security ▶
Concept
An Attacker Does Not See a Cluster — They See One Pod, and What It Can Reach
Kubernetes diagrams are drawn from the operator's viewpoint: a control plane above, nodes below, workloads inside. An attacker arrives somewhere entirely different — inside one container, usually through an ordinary application vulnerability that has nothing to do with Kubernetes at all. Everything that follows is a question of what that one process can reach: which token is mounted, which network destinations answer, which host resources are shared, and whether the node's cloud identity is borrowable.
This is why cluster hardening that starts at the control plane frequently misses. The control plane is usually managed, patched and unreachable from the internet. The interesting path runs the other way — from a compromised workload outward — and almost every step of it is a default that was never changed.

🔑 Kubernetes RBAC (Role-Based Access Control) Deep — The Escalation Paths People Miss Security ▶
Concept
Several Innocuous Permissions Are Cluster-Admin Wearing a Hat
Kubernetes RBAC is easy to read and hard to reason about, because the permission model describes API (Application Programming Interface) verbs on resources while the actual privilege depends on what those resources do. Nothing in a role definition says "this is equivalent to root". The knowledge lives entirely in knowing what the object is for, which is why RBAC reviews that read like least-privilege frequently are not.
The reframing that makes review possible: stop reading roles as lists of verbs and start asking what can the holder of this role cause to run, and as whom? Anything that creates or controls a workload inherits every identity that workload can use.

Auditing It Without Reading Every Manifest
RBAC review by hand does not scale past a small cluster, and the built-in tooling answers the question backwards — it tells you what a subject can do, when the useful question is who can do a dangerous thing. 
# Backwards, and still the fastest first check for one identity
          kubectl auth can-i --list --as=system:serviceaccount:prod:api

          # The question that actually matters, asked directly
          kubectl auth can-i create pods --as=system:serviceaccount:prod:api -n prod

          # Find every binding to the built-in admin role — expect this list to be short
          kubectl get clusterrolebindings -o json \
            | jq -r '.items[] | select(.roleRef.name=="cluster-admin")
                     | "\(.metadata.name): \([.subjects[]?.name] | join(","))"'
Three habits do most of the work: default every workload to a dedicated service account with no permissions at all, so a grant is always deliberate; prefer namespaced Roles to ClusterRoles, since the blast radius is the difference; and re-run the dangerous-verb query in CI, so a permission added in a Helm chart upgrade surfaces as a diff rather than as an audit finding a year later.
🎟️ Service Account Tokens & Workload Identity — The Credential Every Pod Carries Security ▶
Concept
Every Pod Is Issued an API (Application Programming Interface) Credential Whether It Needs One or Not
Unless it is switched off, Kubernetes mounts a service-account token into every pod at a fixed path. The application never asked for it and in most cases never uses it — but it is on the filesystem, readable by the process, and it authenticates to the API server. Any code execution inside that container therefore starts with a cluster credential in hand. This is the single most useful fact an attacker learns about Kubernetes, and it is a one-line fix.

The original design stored a permanent token in a Secret object. Projected (bound) tokens replaced it, and the differences are exactly the properties that decide how bad a stolen token is.

The practical consequence for defenders: on a modern cluster, a token exfiltrated from a pod stops working. On a cluster still carrying legacy tokens — usually because something old requested one, or because a manifest creates a token Secret by hand — it works forever, from anywhere, and its use is indistinguishable from the real workload. Auditing for long-lived token Secrets is a short, high-value job.
Concept
Federating to Cloud IAM (Identity and Access Management) Without a Long-Lived Key
Workloads need cloud permissions — a bucket, a queue, a database. The two obvious answers are both wrong: a static access key in a Secret is a credential that leaks and never expires, and letting the pod use the node's instance role gives every pod on that node the same access, which is the union of what all of them need.

The federation mechanism is the projected token's audience field doing real work: the cluster's OIDC (OpenID Connect) issuer is trusted by the cloud provider, and the trust policy names the exact namespace and service account. Pair it with blocking pod access to the metadata endpoint — otherwise the node-role path stays open next to the good one, and an attacker will simply take it. 🚪 Container Breakout Paths & Pod Security Standards Security ▶
Concept
Most Escapes Are Not Exploits — They Are Configuration Working Correctly
"Container escape" suggests a kernel vulnerability and an exploit chain. Those exist and are rare. The overwhelming majority of real escapes are a pod that was granted a host resource on purpose, by a manifest somebody wrote to make something work, that then did exactly what it was configured to do. Nothing is exploited. The container was simply never a boundary in that configuration.
Which is good news for defence: these are visible in the manifest, checkable before deployment, and enforceable by admission policy. The vulnerability class you cannot see is the small one; the configuration class you can see is the large one.
Reference

Each of these has a legitimate use, which is why blanket bans fail and admission policy with a documented exception process works. The right question is never "should this be allowed" but "is this workload the one that needs it".

🕸️ Network Policies & Service Mesh — Default-Deny, mTLS (Mutual Transport Layer Security) & the Complexity Cost Security ▶
Concept
A Cluster Is a Flat Network Until Somebody Says Otherwise
By default every pod can open a connection to every other pod, in every namespace. The marketing image of workload isolation describes resource scheduling, not network segmentation. This means one compromised container has unrestricted reachability to the database, the internal admin service, the metadata endpoint and every other team's workloads — the exact lateral movement that segmentation exists to prevent, inside a boundary people describe as isolated.
Two facts make this worse than it sounds. NetworkPolicy resources are enforced by the CNI plugin, so on a plugin that does not implement them the objects apply cleanly and do nothing at all — a policy that appears in kubectl get is not evidence of enforcement. And policies are additive with no deny rules, so a namespace with no policy is fully open, and adding one policy to a namespace flips its pods to deny-by-default for the direction that policy covers.
Reference
Reaching Default-Deny Without an Outage
Default-deny is the single highest-value cluster control and the one most often abandoned halfway, because it is adopted in the wrong order. Writing the deny rule first turns an unknown dependency graph into an incident.
StepAction
1Observe first — use flow logs or the mesh's telemetry to learn who actually talks to whom
2Write allow rules from observed traffic, still with no deny in place
3Confirm the allow set covers a full business cycle — the nightly job is what breaks
4Apply default-deny ingress in one non-critical namespace
5Then egress, which is the half that stops exfiltration and the half people skip
6Namespace-by-namespace, with the DNS (Domain Name System) rule remembered every time
The DNS rule earns its own mention because it causes most first-attempt failures: a default-deny egress policy blocks lookups to the cluster DNS service, so everything fails in a way that looks nothing like a network policy problem. Allow UDP (User Datagram Protocol) and TCP (Transmission Control Protocol) 53 to the DNS namespace in every egress policy, as a template, before you need to debug it.
Troubleshooting
When a Service Mesh Is Worth Its Cost
A mesh gives identity-based authorization and mutual TLS (Transport Layer Security) between workloads — controls that network policy cannot express, because IP (Internet Protocol) addresses in a cluster are ephemeral and reassigned. It also adds a proxy beside every pod, a control plane to run and upgrade, and a new place for latency and failures to originate.
NeedNetwork policyMesh
Stop pod A reaching pod BYes — do this firstOverkill
Encrypt traffic between workloadsNoYes, transparently
Authorize by workload identity rather than addressNoYes — the real reason to adopt one
Prove who called what, for auditNoYes
Regulatory encryption-in-transit requirementNoYes, without changing applications
The honest sequencing: network policy first, always, because it is free with the platform and stops the movement that matters most. Adopt a mesh when you have a specific need in that table's second column, not because the architecture diagram looks more complete with one. A half-operated mesh is a new failure domain in exchange for controls nobody configured. The architectural view is in Service Mesh — Istio, Linkerd & the Sidecar Pattern.
🏘️ Kubernetes Multi-Tenancy — Namespaces Are Not a Security Boundary Security ▶
Concept

Namespaces partition object names and give RBAC (Role-Based Access Control) something to scope to. That is the whole feature. They do not partition the network, the nodes, the kernel, or the control plane — pods in different namespaces share all four by default. The phrase "we isolate tenants with namespaces" is extremely common and describes an isolation that mostly is not there.

📡 Runtime Security & Audit Logs — eBPF (Extended Berkeley Packet Filter) Detection and What the API (Application Programming Interface) Server Records Security ▶
Concept
Two Telemetry Sources, Answering Two Different Questions
Cluster detection has exactly two vantage points and confusing them wastes a lot of effort. The API server audit log records what was asked of Kubernetes — every request, its subject, its object, its outcome. Runtime sensors record what happened inside a container — processes, files, network connections, syscalls. An attacker who abuses RBAC (Role-Based Access Control) is visible only in the first. An attacker who runs a cryptominer in a pod they were entitled to create is visible only in the second.
Most clusters have neither properly. Managed control planes often ship audit logs to the cloud provider's logging service where nobody has written a query against them, and runtime sensors are installed in default mode where they produce a volume of low-value alerts that gets muted within a fortnight.
Reference
Audit Log Queries Worth Saving
The audit stream is enormous and almost entirely uninteresting, so the value is in a small set of specific, low-frequency events. These are the ones that are rare in normal operation and significant when they occur.
EventWhy it matters

RoleBinding or ClusterRoleBinding changesPrivilege grants; every one should map to a change record

Troubleshooting

eBPF-based sensors — Falco, Tetragon and their commercial equivalents — observe kernel events from outside the container, so a compromised workload cannot hide from them. The difficulty is never collection; it is that container workloads are so uniform that the default rule sets fire constantly on legitimate behaviour.

🧯 Incident Response in Kubernetes — Investigating Something That No Longer Exists Security ▶
Concept
The Platform's Best Feature Is Working Against You
Kubernetes exists to replace unhealthy workloads automatically. During an incident that behaviour destroys evidence faster than any anti-forensic technique an attacker would bother with: kill the compromised pod and the controller schedules a fresh one, the original filesystem is gone, its logs may be gone with it, and the replacement is running the same vulnerable image. The instinct that works on a server — isolate it, then investigate — deletes the crime scene here.
The correction is a single change of order: isolate without terminating. A pod can be cut off from the network and detached from its controller while continuing to run, which preserves memory, filesystem and process state for as long as you need it.
Reference
Containing a Compromised Pod, in Order
Each step is deliberately reversible until the last, and the order matters: label first, or the isolation policy will not select it. 
# 1. Relabel so the ReplicaSet stops owning it — the controller
          #    creates a replacement, the original keeps running, untouched
          kubectl label pod api-7d9f quarantine=true app-

          # 2. Cut network reachability with a policy that selects only that label
          kubectl apply -f quarantine-deny-all.yaml

          # 3. Capture, in this order — memory before anything that might restart it
          kubectl cp api-7d9f:/proc/1/environ ./evidence/environ
          kubectl logs api-7d9f --previous > ./evidence/logs.txt
          kubectl get pod api-7d9f -o yaml > ./evidence/spec.yaml

          # 4. Snapshot the node's disk through the cloud provider, not the cluster
Step 1 is the one worth memorising. Removing the label that the controller's selector matches orphans the pod: the workload heals, users see a brief blip, and the evidence stays alive. Without it you are choosing between service availability and knowing what happened, and under pressure availability wins every time.
Troubleshooting
Scoping It — and the Preparation That Has to Exist Beforehand
Once one pod is contained, the question is what else the attacker reached. In a cluster the answer follows the identity and the network far more than the host.
QuestionWhere the answer is
What could that service account do?auth can-i --list as that subject — this is the blast radius
Did the token get used elsewhere?Audit log, filtered by that subject, across the whole window
Did it reach the cloud?Cloud audit trail for the node role and any federated identity
What could it connect to?The absence of a network policy is itself the answer
Is the image compromised or just the running pod?Registry provenance and the image digest actually deployed
Did anything change in the cluster?GitOps (Git Operations) diff against the declared state — drift is a finding
Three things must exist before the incident or none of the above works: audit logs retained somewhere outside the cluster, a quarantine network policy written and tested in advance, and node-snapshot permissions that an on-call responder actually holds at three in the morning. Rehearse the containment sequence on a scratch cluster once — it takes twenty minutes and it is the difference between doing this from a runbook and improvising it. The general process is in Incident Response — What to Do When It Goes Wrong.
⚡ Serverless Threat Model — Event Injection, Over-Permissive Roles & the Function You Cannot Log Into Security ▶
Concept
Removing the Server Removes Some Risks and Concentrates the Rest
Serverless genuinely deletes categories of work: no patching, no SSH (Secure Shell), no long-lived host for an attacker to persist on, and a process that dies in seconds. What it does not delete is the application logic and the identity attached to it — and by removing everywhere else risk could live, it concentrates the entire remaining attack surface into two things: what the function does with its input, and what its execution role is allowed to do.
That concentration cuts both ways. It makes the review tractable, because there are only two questions and both are answerable from the repository. It also means an over-permissive role has nothing standing between it and the attacker: no network boundary, no host hardening, no lateral step to detect. Compromise the function, and you are already the role.
Reference
Event Injection — Untrusted Input From Places That Do Not Look Like Input
Web applications teach developers to distrust the request. Serverless functions are invoked by dozens of event sources, most of which feel like infrastructure rather than user input, and validation is skipped accordingly.
TriggerAttacker-controlled part
HTTP (HyperText Transfer Protocol) gatewayEverything — the one people do validate
Object storage uploadFile name, path, metadata, and the content itself
Queue or stream messageThe payload, if anything upstream can publish
Email or SMS ingestionHeaders, sender, subject, body
Database change streamAny field a user could write, arriving as an event
Third-party webhookThe entire body, unless the signature is verified — and it usually is not
Log or notification eventsAnything an attacker can cause to be logged
The object-storage row produces the classic chain: a user uploads a file whose name contains a shell metacharacter, a function passes that name to a media tool, and the function's role does the rest. Nobody thought of the filename as user input because the event came from storage.
Troubleshooting
The Failures That Are Specific to This Model
These are the findings that a general application review misses because they are properties of the platform rather than of the code.

The reused-state rows surprise people most, because the mental model says each invocation is fresh. The execution environment is reused when it can be — which is what makes warm starts fast, and what makes a credential or a user's data left in a global variable readable by the next caller.
🧾 Managed Service Trust Boundaries — What the Provider Secures, and Precisely What You Do Security ▶
Concept
The Shared Responsibility Diagram Is True and Not Actionable
Every provider publishes a diagram with a diagonal line: they secure the cloud, you secure what you put in it. Correct, and it has never prevented a single breach, because the line moves for every service and the diagram does not say where. 🔍 IaC (Infrastructure as Code) Security Scanning — Catching the Misconfiguration Before It Deploys Security ▶
Concept
The Same Finding, Found Three Days Earlier, Is a Different Finding
A posture-management tool tells you a bucket is public. Nothing about the rule changes; the economics change completely. Cloud misconfiguration is overwhelmingly a deployment-time problem being detected at runtime, and moving the detection is the single highest-return change in this whole area.
Keep both. The scanner sees what the code declares; posture management sees what actually exists, including everything created by hand, by another team, or by a service that provisions its own resources. Each has a blind spot precisely where the other looks.

🛰️ Cloud Detection Engineering — The Control-Plane Log as a Detection Source Security ▶
Concept
In the Cloud, the API (Application Programming Interface) Call Is the Attack
On-premises detection watches processes, files and packets, because that is where an attacker's actions show up. In a cloud account the equivalent actions are API calls: creating a user, attaching a policy, snapshotting a volume, disabling a log, copying a bucket. There is no malware to find and no endpoint to query — the control-plane log is both the primary telemetry and, on a well-run account, very nearly the only telemetry that matters.
This is good for detection engineers: the events are structured, complete, attributed to an identity, and generated by the platform rather than by an agent an attacker can disable. It is bad for anyone hoping to start small — the volume is enormous and almost all of it is automation doing its job, so detections have to be written against identity and sequence rather than against individual actions.

🚨 Cloud Incident Response — Snapshot, Revoke & Contain the Blast Radius Security ▶
Concept
The Compromised Thing Is Almost Never a Machine
Traditional response starts by identifying affected hosts. In a cloud account the answer is usually that no host is affected: a credential was used. An access key from a repository, a role assumed through a misconfigured trust policy, a token stolen from an instance's metadata endpoint. The attacker never ran code anywhere you own. Asking which server is compromised produces the answer "none", which is true and leads the whole investigation nowhere.
Replace the question. Which identity acted, what is that identity permitted to do, and what did it actually do? The first is in the log, the second is computable from policy, and the third is the rest of the investigation. The general process still applies — Incident Response — What to Do When It Goes Wrong — but the artefacts are identities and API (Application Programming Interface) calls rather than hosts and files.
Reference
The First Thirty Minutes, in Order
The ordering is deliberate and it is the opposite of the instinct. Preserve before you contain, because containment in the cloud frequently deletes the thing you needed.
OrderActionWhy here
1Protect the logs — confirm the trail is intact and stored outside this accountEverything else depends on it, and it is the attacker's first target
2Snapshot volumes and capture memory before touching the instanceTerminating or stopping destroys memory, and auto-scaling may do it for you
3Isolate rather than terminate — swap to a deny-all security group, detach from the scaling groupKeeps the evidence running while removing the reach
4Revoke the identity: deactivate keys, and attach an explicit deny to the roleA role cannot be "logged out"; issued session tokens stay valid until denied
5Enumerate what the identity could do — the blast radius is the permission setDefines the scope of everything after this
6Search the trail for that identity across the full window, all regionsAttackers work in regions nobody watches
7Hunt for persistence — new users, keys, trust policies, functions, scheduled tasksRevoking one credential achieves nothing if a second was created
Step 4 is the one that catches teams out. Deleting an access key stops new sessions and does nothing to sessions already issued — temporary credentials remain valid for their full lifetime. The immediate control is an explicit deny policy on the role, applied before you start cleaning up.
