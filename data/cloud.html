🌩️ Cloud Fundamentals — Regions, AZs (Availability Zone) & Shared Responsibility Foundations ▶
Concept
The Mental Model Before the Buttons
Cloud providers rent computing on demand. You should hold three ideas before touching a console: the service models (how much you manage), the global infrastructure (where your stuff physically runs), and the shared responsibility model (who secures what).
▸ SERVICE MODELS
ModelYou ManageExample
IaaS (Infrastructure as a Service)OS (Operating System) + runtime + appEC2 (Elastic Compute Cloud), Compute Engine
PaaS (Platform as a Service)Just your appApp Engine, Elastic Beanstalk
SaaS (Software as a Service)Nothing — just use itGmail, Workspace
▸ GLOBAL LAYOUT
TermMeaning
RegionA geographic area (us-east-1, europe-west1). Pick for latency, law, cost.
Availability ZoneIsolated datacenter(s) in a region. Deploy across ≥2 AZs for HA.
Edge / PoPCDN (Content Delivery Network) locations near users (CloudFront, Cloud CDN).
Shared responsibility: the provider secures the cloud itself (hardware, hypervisor, physical); you secure what you put in it — IAM (Identity and Access Management), data, patching your VMs (Virtual Machine), network config. Most breaches are the customer's side (a public bucket, a wildcard IAM policy), not the provider's.

🔑 AWS (Amazon Web Services) IAM (Identity and Access Management) — Users, Roles & Policies AWS ▶
How-To
Who Can Do What, to Which Resources
IAM is the heart of AWS security — and the #1 source of breaches when done sloppily. It answers: which principal (user/role) can perform which actions on which resources, under what conditions. Everything is deny-by-default; access must be explicitly granted by a policy.
ConceptWhat
UserA long-lived human/app identity (avoid keys where possible)
RoleAn identity you assume temporarily — the preferred pattern (no stored keys)
GroupA bucket of users sharing policies
PolicyJSON (JavaScript Object Notation) document granting/denying permissions
▸ A POLICY (JSON)
{
  "Effect": "Allow",
  "Action": ["s3:GetObject"],
  "Resource": "arn:aws:s3:::my-bucket/*",
  "Condition": { "IpAddress": { "aws:SourceIp": "10.0.0.0/8" } }
}
Golden rule: grant least privilege — start with nothing, add the specific actions needed. Never attach *:* ("AdministratorAccess") to app roles.
🎫 AWS (Amazon Web Services) IAM (Identity and Access Management) Deep — AssumeRole, STS (Security Token Service) & Boundaries AWS ▶
How-To
Temporary Credentials Done Right
Long-lived access keys are the thing that leaks. The modern pattern is roles + STS: you assume a role and get temporary credentials that auto-expire (minutes to hours). Cross-account access, CI/CD (Continuous Integration / Continuous Delivery), and EC2/Lambda all use this.
MechanismUse
sts:AssumeRoleSwap into a role (incl. cross-account) for short-lived creds
Trust policyOn the role — says who is allowed to assume it
Instance/Task roleEC2/ECS/Lambda auto-receive creds — no keys on disk
Permission boundaryA ceiling on the max perms an identity can ever have
IAM Identity CenterSSO (Single Sign-On) for humans → short-lived console/CLI sessions
OIDC (OpenID Connect) federationLet GitHub Actions assume a role with no stored secret
Policy evaluation: an explicit Deny always wins; otherwise you need an explicit Allow. Effective permission = intersection of identity policy, resource policy, permission boundary, and any SCP (Service Control Policy) (org guardrail).
🔑 GCP (Google Cloud Platform) IAM (Identity and Access Management) — Members, Roles & Hierarchy GCP ▶
How-To
Who (member) Can Do What (role) on Which Resource
GCP IAM binds a member (user, group, or service account) to a role (a bundle of permissions) on a resource. Because of the resource hierarchy, a binding at the project or folder level is inherited by everything beneath it — powerful and easy to over-grant.
Role typeDetail
BasicOwner/Editor/Viewer — broad, legacy, avoid in prod
PredefinedFine-grained, service-specific (e.g. roles/storage.objectViewer)
CustomYour own hand-picked permission set for true least-privilege
gcloud projects add-iam-policy-binding my-proj \
  --member="user:alice@example.com" \
  --role="roles/storage.objectViewer"
Prefer predefined/custom roles over basic ones, and bind as low in the hierarchy as possible (project > folder > org).
🤖 GCP (Google Cloud Platform) Service Accounts & Workload Identity GCP ▶
How-To
Machine Identity Without Leaking Keys
A service account (SA) is an identity for an app or VM (Virtual Machine) rather than a person. The trap is downloaded SA key files — long-lived JSON (JavaScript Object Notation) secrets that leak and rarely rotate. Workload Identity is the modern answer: it lets workloads (GKE pods, or external systems like GitHub Actions and even AWS) obtain short-lived SA credentials automatically, with no key file at all.
ApproachVerdict
Downloaded SA key (.json)Long-lived secret — avoid; the #1 GCP credential leak
Attached SA (on a VM/pod)Metadata server issues short-lived tokens automatically
Workload Identity FederationExternal identities (GitHub/AWS) assume an SA keylessly
Rule: if you're storing a .json key, ask whether Workload Identity can replace it. Usually it can.
⚠️ Cloud IAM (Identity and Access Management) Pitfalls & Privilege Escalation Security ▶
Security
How Over-Permissive IAM Becomes a Breach
Most cloud compromises aren't zero-days — they're IAM misconfigurations an attacker chains into full control. Knowing the traps is how you avoid (and, on a red team, find) them.
PitfallWhy It's Dangerous
Wildcards (*:*)"Just make it work" grants admin — the classic root cause
iam:PassRole / actAsLets a low-priv identity hand a powerful role to a service it controls → escalation
Overbroad AssumeRole trustA role anyone can assume is a role attackers assume
Long-lived access keysLeak in code/logs/laptops; rarely rotated
SSRF (Server-Side Request Forgery) → metadata serviceApp-layer SSRF steals the instance's role creds (IMDSv2 mitigates on AWS)
Public resource policiesA bucket/queue open to "Principal": "*"
Defenses: least privilege, no wildcards, IMDSv2, short-lived creds, and continuous scanning with CSPM (Cloud Security Posture Management) tools (Prowler, ScoutSuite, Steampipe) that flag these exact patterns.
🌐 AWS (Amazon Web Services) VPC (Virtual Private Cloud) — Subnets, Security Groups & NACLs (Network Access Control List) AWS ▶
How-To
Your Private Slice of the AWS Network
A VPC is an isolated virtual network you define with a CIDR (Classless Inter-Domain Routing) block (e.g. 10.0.0.0/16). Inside it you carve subnets, control routing, and layer two firewalls. Getting the public/private split right is the foundation of a secure architecture.
PieceRole
Public subnetRoute to an Internet Gateway (IGW) — for load balancers, bastions
Private subnetNo direct inbound; outbound via a NAT (Network Address Translation) Gateway — for app servers, DBs
Route tableDecides where a subnet's traffic goes (IGW, NAT, peering)
Security GroupStateful firewall on the instance — allow rules only; return traffic auto-allowed
NACLStateless firewall on the subnet — allow + deny; must allow both directions
Remember: Security Groups are stateful (the common case, instance-level); NACLs are stateless (subnet-level, coarse). Put databases in private subnets and never give them a public IP (Internet Protocol).
🔀 AWS (Amazon Web Services) Load Balancing & DNS (Domain Name System) — ELB (Elastic Load Balancing), Route 53, CloudFront AWS ▶
How-To
Getting Traffic to the Right Place, Fast
ServiceDoes
ALB (Application Load Balancer) (Application LB)Layer 7 — routes HTTP (HyperText Transfer Protocol)(S) by path/host, WebSockets, target groups
NLB (Network Load Balancer) (Network LB)Layer 4 — ultra-fast TCP/UDP, static IPs (Internet Protocol), extreme throughput

🌐 GCP (Google Cloud Platform) VPC (Virtual Private Cloud) — Global Networks & Firewall Rules GCP ▶
How-To
One Network That Spans the Planet
GCP's big networking difference: a VPC is global, not regional. One VPC can hold subnets in every region, and instances in different regions talk over Google's private backbone without extra peering. Subnets are regional; the VPC that contains them is global.
PieceRole
VPC (global)The whole network; subnets are regional within it
Firewall rulesStateful; applied by network tags or service accounts, not per-instance objects
Cloud NAT (Network Address Translation)Managed egress for private instances (no per-VM NAT gateway)
Cloud RouterDynamic (BGP) routing for hybrid/VPN links
Firewall rules being tag-based is the mental shift from AWS (Amazon Web Services): tag an instance web, write a rule "allow 443 to tag:web" — no security-group object to attach.

💾 AWS (Amazon Web Services) Storage — S3 (Simple Storage Service) Classes, EBS (Elastic Block Store) & EFS (Elastic File System) AWS ▶
How-To
Three Storage Types for Three Jobs
AWS storage splits into object (S3), block (EBS — a virtual disk for one EC2), and file (EFS — a shared NFS mount for many). Pick by access pattern; mixing them up is a classic mistake. (See the Object Storage topic for S3 fundamentals — here we focus on the AWS-specific pieces.)
ServiceTypeUse
S3ObjectFiles, backups, static sites, data lakes
EBSBlockBoot/data volume for one EC2 (Elastic Compute Cloud) (like a disk)
EFSFileShared filesystem mounted by many instances
FSxFileManaged Windows/Lustre file systems
▸ S3 STORAGE CLASSES (cost vs access)
ClassFor
StandardHot, frequent access
Standard-IA / One Zone-IAInfrequent access, cheaper storage
Intelligent-TieringAuto-moves objects by usage
Glacier / Deep ArchiveCold archive — pennies to store, slow/paid retrieval
Use lifecycle rules to age objects into colder classes automatically. EBS volumes are AZ-locked — snapshot to S3 for backup/restore across AZs (Availability Zone).

🏗️ Terraform on AWS (Amazon Web Services) & GCP (Google Cloud Platform) IaC ▶

Terraform's superpower in the cloud is being provider- agnostic — the same HCL workflow (init/plan/apply) provisions AWS, GCP, Azure, and 100+ others. You declare a provider, then resources. (See the Terraform topic for the core workflow — here's the cloud-specific shape.)

🏛️ Azure Hierarchy, RBAC (Role-Based Access Control) Scopes & Policy Azure ▶
Foundation
Four Levels, and Everything Inherits Downward
Almost every "why can't I do this?" in Azure is answered by knowing which scope a setting was applied at. Permissions, policy and cost all flow down the same four-level tree, and nothing flows back up.
ScopeWhat it isWhat you attach here
Management groupA container for subscriptions; nests up to six levels under the tenant rootOrg-wide policy, broad role assignments
SubscriptionThe billing and quota boundary — roughly an AWS (Amazon Web Services) accountBudgets, quotas, environment separation (prod / non-prod)
Resource groupA lifecycle container; resources in it are deployed and deleted togetherTeam-level RBAC, locks, tags
ResourceThe individual VM (Virtual Machine), storage account, key vault…Narrow, exception-level access
The gotcha: a resource group is not a security boundary by itself and it is not a network boundary at all — two VMs in different resource groups can sit in the same subnet and talk freely.
Access vs Shape
RBAC Answers "Who", Policy Answers "What"
These two get confused constantly. A role assignment decides whether you may act. A policy decides whether the resource is allowed to exist in that shape. A deployment can fail on either, and the error text tells you which.
Azure RBACAzure Policy
ControlsActions a principal may performProperties a resource may have
Made ofPrincipal + role definition + scopeCondition + effect, grouped into initiatives
EffectsAllow (deny assignments are rare and system-made)Audit, Deny, Modify, DeployIfNotExists, AuditIfNotExists
Failure looks likeAuthorizationFailed — 403RequestDisallowedByPolicy — names the policy
FixAssign the role at the right scope, then wait for propagationChange the request, or exempt the scope deliberately
 
# Who has access here, and inherited from where?
az role assignment list --scope "/subscriptions/<sub-id>/resourceGroups/rg-prod" --include-inherited -o table

# Why did that deployment get blocked? Ask the policy engine directly
az policy state list --resource "<resource-id>" --filter "complianceState eq 'NonCompliant'" -o table

# Built-in roles are usually enough — check before writing a custom one
az role definition list --custom-role-only false --query "[?contains(roleName,'Contributor')].roleName"
Least privilege in practice: Reader for everyone by default, Contributor scoped to a resource group, and Owner or User Access Administrator handed out only through PIM (Privileged Identity Management) with approval and a time limit. Resource locks (CanNotDelete / ReadOnly) are a separate, dumber safety net — they stop even an Owner, which is exactly why prod deployments sometimes fail mysteriously.

A virtual network is the private address space; everything else is a decision about what may cross it. Network security groups filter, route tables steer, and peering or a gateway connects it to somewhere else.

Choosing
Four Load Balancers, One Right Answer
ServiceLayerReachReach for it when
Load Balancer4 — TCP/UDPRegionalYou need raw throughput and any protocol

Storage
Redundancy, Tiers and Who Holds the Key
RedundancyCopiesSurvives

📈 Azure Monitor, Log Analytics & KQL (Kusto Query Language) Azure ▶
Observability
Metrics Are Free, Logs Are Opt-In
Platform metrics are collected automatically and kept for 93 days. Resource logs are not collected at all until you add a diagnostic setting pointing the resource at a Log Analytics workspace. The single most common monitoring complaint — "there's nothing in the logs" — is usually that nobody ever turned them on.
TableWhat lands in it
AzureActivityControl-plane operations — who created, changed or deleted a resource
AzureDiagnosticsResource logs from services that use the shared schema
HeartbeatAgent check-ins; the fastest way to spot a machine that stopped reporting
Perf / InsightsMetricsCPU (Central Processing Unit), memory, disk and network counters from monitored machines
SigninLogs / AuditLogsEntra ID sign-ins and directory changes
SecurityEvent / SyslogWindows security events and Linux syslog
AppRequests / AppExceptionsApplication Insights telemetry for your own code
 
// Who deleted things in the last day, and did it succeed?
AzureActivity
| where TimeGenerated > ago(1d)
| where OperationNameValue endswith "/DELETE"
| project TimeGenerated, Caller, OperationNameValue, ActivityStatusValue, ResourceGroup
| order by TimeGenerated desc

// Machines that have stopped sending a heartbeat in the last 15 minutes
Heartbeat
| summarize LastSeen = max(TimeGenerated) by Computer
| where LastSeen < ago(15m)

// Failed sign-ins by error code — the shape of an attack, or of a broken app
SigninLogs
| where TimeGenerated > ago(24h) and ResultType != 0
| summarize attempts = count() by ResultType, ResultDescription, AppDisplayName
| order by attempts desc

// Top CPU offenders, bucketed for a chart
Perf
| where ObjectName == "Processor" and CounterName == "% Processor Time"
| summarize avg(CounterValue) by Computer, bin(TimeGenerated, 5m)
| render timechart
The KQL that covers most days: where to filter, project to pick columns, extend to compute one, summarize … by to aggregate, bin() to bucket time, join to correlate two tables, and render to chart it. Filter on TimeGenerated first — it is the difference between a fast query and an expensive one. The same language drives Sentinel, Defender and Resource Graph.
🩺 Azure Troubleshooting Playbook Azure • Ops ▶
Method
Five Questions, In This Order
Azure failures nearly always fall into one of five buckets. Asking them in order saves you from packet-capturing a problem that was a missing role assignment.
#QuestionWhere to look
1Is Azure itself broken?Service Health for regional incidents, Resource Health for this specific resource
2Did the action even reach Azure — and who made it?Activity Log: the operation, the caller, the status and the correlation ID
3Am I allowed to do it?RBAC (Role-Based Access Control) at every scope, plus any policy assignment or resource lock
4Can the packets get there?Network Watcher — effective rules, effective routes, connection troubleshoot
5Is the thing inside the box healthy?Boot diagnostics, serial console, Run Command, app logs
Always capture the correlation ID. Every Azure Resource Manager operation carries one, it ties the portal error to the Activity Log entry to the deployment operation — and it is the first thing support asks for.
Toolkit
The Commands That Answer Each Question
# 2 — what actually happened, and under whose identity
az monitor activity-log list --resource-group rg-prod --offset 2h \
  --query "[?status.value=='Failed'].{op:operationName.value,by:caller,msg:properties.statusMessage}" -o table

# 2 — a failed template/Bicep deployment: the top-level error hides the real one
az deployment group show -g rg-prod -n my-deploy --query properties.error
az deployment operation group list -g rg-prod -n my-deploy \
  --query "[?properties.provisioningState=='Failed'].properties.statusMessage"

# 3 — effective permissions for a principal at a scope
az role assignment list --assignee user@contoso.com --all --include-inherited -o table

# 4 — will this packet be allowed? (evaluates every NSG in the path)
az network watcher test-ip-flow --vm web01 -g rg-prod --direction Inbound \
  --protocol TCP --local 10.0.1.4:443 --remote 203.0.113.10:51234

# 4 — what the NIC actually sees after all inheritance
az network nic list-effective-nsg --name web01-nic -g rg-prod -o table
az network nic show-effective-route-table --name web01-nic -g rg-prod -o table

# 4 — end-to-end reachability including DNS and the next hop
az network watcher test-connectivity --source-resource web01 -g rg-prod \
  --dest-address api.internal.contoso.com --dest-port 443

# 5 — the VM is unreachable: look at the screen and the boot log
az vm boot-diagnostics get-boot-log --name web01 -g rg-prod
az vm run-command invoke --name web01 -g rg-prod --command-id RunPowerShellScript \
  --scripts "Get-Service W3SVC | Select Status"
