🌐 APIs & HTTP (HyperText Transfer Protocol) — How Programs Talk to Each Other SCRIPT • Start Here ▶
WHAT IS AN API
Application Programming Interface
An API is a menu at a restaurant. You don't walk into the kitchen — you order from a menu (the API), the kitchen (server) makes it, and the waiter (HTTP) brings it back. You get what you need without knowing how it's made.
HTTP VERBS
GET · POST · PUT · DELETE
The four core actions match CRUD (Create, Read, Update, Delete):
GET — read/fetch data (no side effects)
POST — create/send new data
PUT — replace existing data entirely
DELETE — remove data
Think: GET a pizza menu, POST your order, PUT a replacement order, DELETE it.
STATUS CODES
What the Server Says Back
Every response has a 3-digit status code.
2xx = Success (200 OK, 201 Created)
3xx = Redirect (301 Moved, 304 Not Modified)
4xx = Your fault (400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found)
5xx = Server's fault (500 Internal Server Error, 503 Service Unavailable)
CodeNamePlain English
200OKEverything worked
201CreatedNew thing was made
400Bad RequestYou sent garbage data
401UnauthorizedWho are you? Log in first
403ForbiddenI know who you are — you still can't
404Not FoundThat URL (Uniform Resource Locator) doesn't exist
429Too Many RequestsSlow down, you're spamming
500Internal Server ErrorThe server broke (not your fault)
Handle the 4xx and 5xx split differently, because only one of them is worth retrying. A 4xx means your request was wrong and repeating it identically will fail identically; a 5xx means the far end had a problem and a retry with backoff is reasonable. Code that retries everything hammers a service that already told you no, and code that retries nothing gives up on a transient blip.
MAKING A REQUEST
Python fetch example
Using the requests library (install with pip install requests):
import requests

# Fetch a list of users from a free test API
response = requests.get("https://jsonplaceholder.typicode.com/users")

# Always check the status before trusting the data
if response.status_code == 200:
    users = response.json()        # parse JSON into a Python list
    for user in users[:3]:
        print(user["name"], "-", user["email"])
else:
    print(f"Error: {response.status_code}")
HEADERS & AUTH
Talking With a Credential
Most real APIs require an API key or token. Send it in the header, NOT the URL (URLs can appear in logs):
# Bearer token auth (most common for modern APIs)
headers = {
    "Authorization": "Bearer YOUR_API_KEY_HERE",
    "Content-Type": "application/json",
}
response = requests.get("https://api.example.com/data", headers=headers)
REST (Representational State Transfer) vs SOAP vs GRAPHQL
Three API Styles
REST — most common today; uses HTTP verbs + URLs; returns JSON (JavaScript Object Notation). Easy to learn, widely supported.
SOAP — older enterprise style; uses XML (eXtensible Markup Language); very structured and verbose. You'll encounter it in legacy systems.
GraphQL — you ask for exactly what you need in one request; returns only what you specified. Reduces over-fetching.

COMMON GOTCHAS
JSON Pitfalls for Beginners
Trailing commas — JSON does NOT allow them. {"a":1,} is invalid.
Single quotes — JSON requires double quotes. {'a':'b'} is invalid.
Comments — standard JSON has no comments. Use JSONC or strip them before parsing.
Large numbers — JSON numbers lose precision beyond 2^53. Use strings for large IDs.

🏗️ Object-Oriented Programming — Classes & Objects SCRIPT • Intermediate ▶
THE BIG IDEA
Bundle Data + Behavior Together
OOP groups related data (attributes) and actions (methods) into one unit called a class. A class is a blueprint; an object (or instance) is the real thing built from that blueprint. One blueprint → many objects.
CLASS ANATOMY
Your First Class
class Dog:
    # __init__ runs when you create a new Dog
    def __init__(self, name, breed):
        self.name  = name   # instance attribute
        self.breed = breed
        self.tricks = []    # every dog starts with no tricks

    def learn(self, trick):
        self.tricks.append(trick)

    def show_off(self):
        if self.tricks:
            print(f"{self.name} knows: {', '.join(self.tricks)}")
        else:
            print(f"{self.name} knows nothing yet.")

# Create two Dog objects from one blueprint
rex = Dog("Rex", "Lab")
buddy = Dog("Buddy", "Poodle")

rex.learn("sit")
rex.learn("shake")
rex.show_off()     # Rex knows: sit, shake
buddy.show_off()   # Buddy knows nothing yet.
FOUR PILLARS
Encapsulation · Inheritance · Polymorphism · Abstraction
Encapsulation — hide internal details; expose only what's needed (private _name convention in Python).
Inheritance — child class gets parent's methods; add or override as needed.
Polymorphism — same method name, different behavior per class (speak() on Dog vs Cat).
Abstraction — focus on WHAT, not HOW (you call .sort() without knowing the algorithm).
INHERITANCE EXAMPLE
Extend Without Duplicating
class Animal:
    def __init__(self, name):
        self.name = name

    def speak(self):
        raise NotImplementedError

class Dog(Animal):           # Dog inherits from Animal
    def speak(self):
        return f"{self.name} says Woof!"

class Cat(Animal):
    def speak(self):
        return f"{self.name} says Meow."

animals = [Dog("Rex"), Cat("Whiskers"), Dog("Buddy")]
for a in animals:
    print(a.speak())   # polymorphism — same call, different result
WHEN TO USE OOP
Not Everything Needs a Class
OOP shines when you have multiple instances of the same kind of thing (users, transactions, network packets). Overkill for a 30-line script that reads a file and prints output. Rule of thumb: if you're writing the same data structure twice, make it a class.
🗂️ Choosing the Right Data Structure SCRIPT • Intermediate ▶
THE LINEUP
List · Tuple · Dict · Set · Queue · Stack
Each structure is optimized for different operations. Picking the wrong one makes your code slow and confusing. Picking the right one makes it fast and readable.
StructureOrdered?Mutable?Duplicates?Best For
list []YesYesYesOrdered collections you'll iterate
tuple ()YesNoYesImmutable records (coordinates, RGB)
dict {}Yes (3.7+)YesKeys: NoKey→value lookup; configs, counters
set {}NoYesNoMembership tests; de-duplication
dequeYesYesYesFast append/pop from both ends
heapqPartialYesYesAlways get the smallest/largest item
Pick by mutability and lookup, in that order. If the collection must not change, a tuple says so to every future reader and to the interpreter; if the question is "is this in it", a set turns a linear scan into a constant one. Most performance surprises in beginner Python are a list being asked a membership question thousands of times.
DICT TRICKS
Patterns You'll Use Weekly
from collections import defaultdict, Counter

# Count word frequencies (classic interview problem)
words = ["apple", "banana", "apple", "cherry", "banana", "apple"]
counts = Counter(words)
print(counts.most_common(2))  # [('apple', 3), ('banana', 2)]

# Group items without KeyError
groups = defaultdict(list)
for word in words:
    groups[word[0]].append(word)  # group by first letter

# Dict comprehension — build in one line
squared = {x: x**2 for x in range(5)}  # {0:0, 1:1, 2:4, 3:9, 4:16}

# Merge two dicts (Python 3.9+)
a = {"x": 1}
b = {"y": 2}
merged = a | b   # {"x": 1, "y": 2}
SET USE CASES
Membership Test is O(1)
# De-duplicate a list instantly
names = ["Alice", "Bob", "Alice", "Carol"]
unique = list(set(names))

# Fast membership test (1M items, still instant)
allowed = {"admin", "editor", "viewer"}
if user_role in allowed:    # O(1) — use set, not list
    grant_access()

# Set operations
a = {1, 2, 3}
b = {2, 3, 4}
a & b   # {2, 3}   intersection
a | b   # {1,2,3,4} union
a - b   # {1}      difference
a ^ b   # {1, 4}  symmetric difference

Searching a list for a matching record is linear and shows up the moment the data grows; keying by the identifier makes the same question constant time and usually simplifies the code. ⚡ List Comprehensions & Generators — Pythonic Power SCRIPT • Intermediate ▶
LIST COMPREHENSION
Build a List in One Readable Line
A list comprehension is a concise way to create a list by applying an expression to each item in an iterable, with an optional filter. It replaces 4-6 lines of loop code with 1.
# Old way
squares = []
for x in range(10):
    squares.append(x ** 2)

# List comprehension — same result
squares = [x ** 2 for x in range(10)]

# With filter (only even squares)
even_sq = [x ** 2 for x in range(10) if x % 2 == 0]

# With transformation
names = ["alice", "bob", "carol"]
upper = [n.upper() for n in names]  # ['ALICE', 'BOB', 'CAROL']

# Flatten a 2D list
matrix = [[1,2],[3,4],[5,6]]
flat = [x for row in matrix for x in row]  # [1,2,3,4,5,6]
DICT & SET COMPREHENSIONS
Same Idea, Different Brackets
# Dict comprehension: name → length
names = ["Alice", "Bob", "Carol"]
lengths = {n: len(n) for n in names}
# {'Alice': 5, 'Bob': 3, 'Carol': 5}

# Set comprehension: unique first letters
firsts = {n[0].lower() for n in names}
# {'a', 'b', 'c'}

# Invert a dict
original = {"a": 1, "b": 2, "c": 3}
inverted = {v: k for k, v in original.items()}
# {1: 'a', 2: 'b', 3: 'c'}
GENERATORS
Lazy Evaluation — Process One at a Time
A list comprehension builds the entire list in memory at once. A generator expression (() instead of []) produces values one at a time on demand. Essential for large datasets (files with millions of lines, streaming data).
# List: builds 1M items in memory immediately
big_list = [x**2 for x in range(1_000_000)]

# Generator: computes each item only when asked
big_gen = (x**2 for x in range(1_000_000))
next(big_gen)  # 0 (computes only this one)
next(big_gen)  # 1

# Generator function with yield
def read_big_file(path):
    with open(path) as f:
        for line in f:
            yield line.strip()  # one line at a time

for line in read_big_file("huge.log"):
    if "ERROR" in line:
        print(line)   # never loads whole file
🎀 Context Managers & Decorators — Elegant Python Patterns SCRIPT • Intermediate ▶
CONTEXT MANAGERS
with — Guaranteed Cleanup
The with statement ensures cleanup code runs even if an error occurs. It calls __enter__ on open and __exit__ on close (or exception).
# Without context manager (bad)
f = open("data.txt")
data = f.read()
f.close()   # won't run if read() throws

# With context manager (correct)
with open("data.txt") as f:
    data = f.read()
# file is ALWAYS closed here, even on exception

# Multiple resources
with open("in.txt") as src, open("out.txt", "w") as dst:
    dst.write(src.read())

# Database connection pattern
with db.connect() as conn:
    conn.execute("INSERT INTO logs ...")
# connection closed + transaction committed/rolled back
DECORATORS
Functions That Wrap Functions
A decorator is a function that takes a function as input and returns a modified version. Used for: logging, timing, authentication checks, caching, retry logic — any cross-cutting concern you don't want to copy-paste.
import time
from functools import wraps

# Simple timer decorator
def timer(func):
    @wraps(func)   # preserves original function metadata
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        elapsed = time.perf_counter() - start
        print(f"{func.__name__} took {elapsed:.3f}s")
        return result
    return wrapper

# Apply with @ syntax
@timer
def slow_operation():
    time.sleep(1)
    return "done"

slow_operation()   # prints: slow_operation took 1.002s
FUNCTOOLS CACHE
Memoization in One Line
from functools import cache, lru_cache

# Cache all results forever
@cache
def fibonacci(n):
    if n < 2:
        return n
    return fibonacci(n-1) + fibonacci(n-2)

fibonacci(100)  # instant — cache prevents redundant calls

# LRU cache: keeps only the N most recent results
@lru_cache(maxsize=128)
def expensive_lookup(key):
    return database.fetch(key)

TYPE HINTS
Optional but Powerful Annotations
Python is dynamically typed but supports optional type annotations. Type hints don't change runtime behavior — they're documentation AND they enable static analysis tools (mypy, pyright) to catch type errors before running.
from typing import Optional, List, Dict, Tuple, Union

# Basic function with type hints
def greet(name: str, count: int = 1) -> str:
    return f"Hello, {name}! " * count

# Optional — can be None
def find_user(user_id: int) -> Optional[str]:
    return database.get(user_id)   # may be None

# Collections
def process(items: List[str]) -> Dict[str, int]:
    return {item: len(item) for item in items}

# Python 3.10+ — simpler union syntax
def maybe(val: str | None) -> int | str:
    return len(val) if val else "empty"

🗄️ SQL (Structured Query Language) & Databases — Where Data Actually Lives SCRIPT • Foundation ▶
WHAT IS A DATABASE
Structured, Persistent, Queryable Storage
A database stores data so it can be retrieved, filtered, sorted, and updated efficiently. A file full of JSON (JavaScript Object Notation) works for small things; a real database handles millions of rows, concurrent users, transactions, and relationships between tables without losing data.
RELATIONAL DATABASES
Tables, Rows, and Relationships
A relational database stores data in tables (like spreadsheets). Each table has rows (records) and columns (fields). Tables relate to each other through foreign keys. SQL (Structured Query Language) is the language for interacting with them. Popular: PostgreSQL, MySQL, SQLite, Microsoft SQL Server, Oracle.
BASIC SQL
CRUD in SQL — Create, Read, Update, Delete
-- Create a table
CREATE TABLE users (
    id      INTEGER PRIMARY KEY AUTOINCREMENT,
    name    TEXT NOT NULL,
    email   TEXT UNIQUE NOT NULL,
    age     INTEGER,
    created DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- Insert rows
INSERT INTO users (name, email, age)
VALUES ('Alice', 'alice@example.com', 30);

-- Read / query
SELECT * FROM users;
SELECT name, email FROM users WHERE age > 25;
SELECT * FROM users ORDER BY name ASC LIMIT 10;

-- Update
UPDATE users SET age = 31 WHERE email = 'alice@example.com';

-- Delete
DELETE FROM users WHERE id = 5;
JOINS
Combine Data From Multiple Tables
-- Users and their orders (one user, many orders)
CREATE TABLE orders (
    id      INTEGER PRIMARY KEY,
    user_id INTEGER REFERENCES users(id),
    amount  REAL,
    status  TEXT
);

-- INNER JOIN: only rows that match in BOTH tables
SELECT users.name, orders.amount, orders.status
FROM orders
INNER JOIN users ON orders.user_id = users.id;

-- LEFT JOIN: all users, even those with no orders
SELECT users.name, orders.amount
FROM users
LEFT JOIN orders ON users.id = orders.user_id;

-- Aggregate: total spent per user
SELECT users.name, SUM(orders.amount) AS total
FROM users
LEFT JOIN orders ON users.id = orders.user_id
GROUP BY users.id
ORDER BY total DESC;
PYTHON + SQLITE
Embedded Database, No Server Required
import sqlite3

# Connect (creates file if not exists)
conn = sqlite3.connect("mydb.sqlite")
conn.row_factory = sqlite3.Row   # access columns by name
cursor = conn.cursor()

# Create table
cursor.execute("""
    CREATE TABLE IF NOT EXISTS notes (
        id    INTEGER PRIMARY KEY AUTOINCREMENT,
        title TEXT NOT NULL,
        body  TEXT
    )
""")

# Parameterized insert (ALWAYS use ? placeholders, never f-strings in SQL!)
cursor.execute("INSERT INTO notes (title, body) VALUES (?, ?)",
               ("First note", "Content here"))
conn.commit()

# Query
rows = cursor.execute("SELECT * FROM notes ORDER BY id DESC").fetchall()
for row in rows:
    print(row["title"], row["body"])

conn.close()
The ? placeholder is critical. Never build SQL with string formatting — that's how SQL injection happens: f"WHERE name = '{user_input}'" lets attackers inject arbitrary SQL.
SQL vs NoSQL
Relational vs Document/Key-Value/Graph
SQL databases (PostgreSQL, MySQL, SQLite) — structured schema, ACID (Atomicity, Consistency, Isolation, Durability) transactions, complex queries, relationships. Best for: financial data, user records, anything needing data integrity.
NoSQL databases — flexible schemas, horizontal scaling, specialized access patterns:
• Document (MongoDB) — JSON-like docs; good for varying schemas
• Key-Value (Redis) — extremely fast lookups; caching, sessions
• Column-family (Cassandra) — time-series, logs, analytics
• Graph (Neo4j) — relationships between entities (social network, fraud detection)

⏳ Async Programming — Do More Without Waiting SCRIPT • Intermediate ▶
THE PROBLEM
I/O-Bound vs CPU-Bound Work
CPU-bound: computation is the bottleneck (image processing, cryptography, simulations). More CPU (Central Processing Unit) cores help. Use multiprocessing.
I/O-bound: waiting for external things (network responses, disk reads, database queries). CPU is mostly idle waiting. One thread can handle hundreds of concurrent I/O (Input/Output) operations by switching between them while each waits. Use asyncio.
ASYNC / AWAIT
Coroutines in Python
An async def function is a coroutine — it can pause itself at await points while other coroutines run. The event loop switches between them, never blocking the thread.
import asyncio
import aiohttp   # pip install aiohttp

async def fetch_url(session, url):
    async with session.get(url) as response:
        text = await response.text()
        print(f"{url}: {len(text)} chars")
        return text

async def main():
    urls = [
        "https://httpbin.org/delay/1",
        "https://httpbin.org/delay/1",
        "https://httpbin.org/delay/1",
    ]
    async with aiohttp.ClientSession() as session:
        # Fetch all three CONCURRENTLY — takes ~1s total, not 3s
        tasks = [fetch_url(session, url) for url in urls]
        results = await asyncio.gather(*tasks)

asyncio.run(main())
asyncio ESSENTIALS
The Key Building Blocks
# asyncio.gather — run coroutines concurrently

# asyncio.create_task — fire and forget
task = asyncio.create_task(some_coro())
# do other work, then...
result = await task

# asyncio.wait_for — timeout
try:
    result = await asyncio.wait_for(slow_coro(), timeout=5.0)
except asyncio.TimeoutError:

# asyncio.sleep — non-blocking wait

🛡️ Exception Handling — Writing Code That Doesn't Crash SCRIPT • Essential ▶
WHY EXCEPTIONS MATTER
The Real World Is Messy
Programs fail. Files don't exist. Networks time out. Users enter garbage. Exceptions are Python's way of signaling that something went wrong at runtime. Good code anticipates failures and handles them gracefully — instead of crashing with a wall of red text.
# Without exception handling — crashes if file missing
with open("config.txt") as f:
    data = f.read()   # FileNotFoundError kills the program

# With exception handling — graceful fallback
try:
    with open("config.txt") as f:
        data = f.read()
except FileNotFoundError:
    print("Config not found, using defaults")
    data = ""

CUSTOM EXCEPTIONS
Create Your Own Exception Types
Custom exceptions make your code's error vocabulary explicit. When a caller sees InsufficientFundsError, they know exactly what went wrong — no guessing from a generic ValueError.
# Define custom exceptions by inheriting from Exception
class AppError(Exception):
    """Base class for all app-specific errors."""

class InsufficientFundsError(AppError):
    def __init__(self, needed, available):
        self.needed = needed
        self.available = available
        super().__init__(
            f"Need ${needed:.2f} but only ${available:.2f} available"
        )

class UserNotFoundError(AppError):
    pass   # simple — message comes from caller

# Usage
def withdraw(account, amount):
    if account.balance < amount:
        raise InsufficientFundsError(amount, account.balance)
    account.balance -= amount

try:
    withdraw(my_account, 500)
except InsufficientFundsError as e:
    print(e)              # "Need $500.00 but only $23.50 available"
    print(e.needed)       # 500

🐛 Debugging — Finding Out Why Your Code Lies to You SCRIPT • Essential ▶
THE DEBUGGING MINDSET
The Bug Is Always in Your Assumptions
Debugging is the process of figuring out the gap between what you THINK the code does and what it ACTUALLY does. The number one rule: don't guess — observe. Beginners change random things hoping it works. Professionals form a hypothesis, test it, and narrow down the cause. The scientific method applied to code.
StepWhat to Do
1. ReproduceMake the bug happen reliably. A bug you can't reproduce is one you can't fix.
2. IsolateNarrow down WHERE it happens. Binary search the code — comment out halves.
3. HypothesizeForm a specific theory: "I think x is None here"
4. TestAdd a print/breakpoint to confirm or reject the theory
5. Fix & verifyFix it, confirm the bug is gone, confirm you didn't break anything else
Step 1 is the whole method; the rest is procedure. A bug you cannot reproduce cannot be confirmed fixed, so time spent making it reliable is never wasted — and it frequently reveals the cause on its own. The step people skip is 3: forming a specific, falsifiable theory before changing anything, rather than changing things until the symptom moves.

🔀 Concurrency — Doing More Than One Thing at Once SCRIPT • Advanced ▶
CONCURRENCY VS PARALLELISM
Two Words People Confuse
Concurrency is dealing with many things at once (structure) — like a chef juggling several dishes, switching between them. Parallelism is doing many things at literally the same instant (execution) — like several chefs each cooking one dish. Concurrency is about structure; parallelism is about simultaneous execution. You can have concurrency on a single core (task switching); you need multiple cores for true parallelism.
THE GIL
Why Python Threads Don't Speed Up CPU (Central Processing Unit) Work
CPython has a Global Interpreter Lock (GIL) — only one thread executes Python bytecode at a time. This means threads don't give you parallel CPU work in Python. But they're still great for I/O-bound work (waiting on network/disk), because the GIL is released during I/O (Input/Output) waits. The key question for choosing a tool: is your task I/O-bound or CPU-bound?
ToolBest ForTrue Parallelism?Why
threadingI/O-bound (network, disk, APIs)No (GIL)Threads wait on I/O concurrently; cheap
asyncioI/O-bound, many concurrent tasksNoSingle thread, cooperative; scales to thousands
multiprocessingCPU-bound (math, image processing)YesSeparate processes, each its own GIL/core
Match the tool to whether you are waiting or computing, and the whole confusion dissolves. Threads and async both help when the program is waiting on something outside itself; neither makes arithmetic faster, because only one thread executes Python at a time. If the profile shows the processor busy, the answer is separate processes — or a library that releases the lock and does the work in C.

The Classic Concurrency Bug
When multiple threads modify shared data without coordination, you get race conditions — results depend on unpredictable timing. The fix is a lock (mutex) that ensures only one thread touches the shared data at a time. Race conditions are notoriously hard to debug because they're intermittent.

counter = 0

    global counter

🛠️ Building a Real CLI (Command Line Interface) Tool — Putting It All Together SCRIPT • Capstone ▶
FROM SNIPPET TO TOOL
What Separates a Script from a Tool
A throwaway script has hardcoded values and prints with print(). A real tool that others can use has: command-line arguments, configuration, proper logging, error handling, and a clear exit code. Here's a complete example that ties together everything — argparse, logging, config, and exit codes — into a tool you'd actually deploy.
#!/usr/bin/env python3
"""logcheck — scan a log file for error patterns and report."""
import argparse, logging, sys, re
from pathlib import Path

# ── Logging setup ─────────────────────────────────────────
log = logging.getLogger("logcheck")

def setup_logging(verbose: bool):
    level = logging.DEBUG if verbose else logging.INFO
    logging.basicConfig(
        level=level,
        format="%(asctime)s %(levelname)s %(message)s",
    )

# ── Core logic ────────────────────────────────────────────
def scan(path: Path, pattern: str) -> int:
    regex = re.compile(pattern)
    matches = 0
    with path.open() as f:
        for num, line in enumerate(f, 1):
            if regex.search(line):
                matches += 1
                log.debug("match line %d: %s", num, line.strip())
    return matches

# ── Argument parsing ──────────────────────────────────────
def main(argv=None):
    p = argparse.ArgumentParser(description="Scan a log for a pattern.")
    p.add_argument("logfile", type=Path, help="log file to scan")
    p.add_argument("-p", "--pattern", default="ERROR", help="regex pattern")
    p.add_argument("-t", "--threshold", type=int, default=0,
                   help="exit non-zero if matches exceed this")
    p.add_argument("-v", "--verbose", action="store_true")
    args = p.parse_args(argv)

    setup_logging(args.verbose)

    if not args.logfile.exists():
        log.error("File not found: %s", args.logfile)
        return 2                       # exit code 2 = usage/file error

    count = scan(args.logfile, args.pattern)
    log.info("Found %d matches for %r", count, args.pattern)

    # Exit code drives monitoring/automation
    if count > args.threshold:
        log.warning("Threshold exceeded!")
        return 1
    return 0

if __name__ == "__main__":
    sys.exit(main())

def get_all_users(session):

One Encoding to Rule Them All
Unicode assigns every character a number ("code point") — covering every language, emoji, and symbol. UTF-8 is the dominant way to encode those code points as bytes: it's variable-width (1 byte for ASCII, up to 4 for others) and backward-compatible with ASCII (American Standard Code for Information Interchange). Rule of thumb: use UTF-8 everywhere. Legacy encodings (Latin-1, Windows-1252) cause the most "weird character" bugs.
ENCODING SCHEMES
Base64, Hex, URL (Uniform Resource Locator) — Different Jobs
These are not encryption — they're reversible representations, no secrecy. They exist to safely move binary data through text-only channels.
SchemePurposeExample
Base64Binary → ASCII text (email attachments, JWTs, data URIs)SGVsbG8= = "Hello"
HexBinary → readable hex (hashes, debugging, MAC addresses)48656c6c6f = "Hello"
URL encodingMake text safe in URLs (% escaping)%20 = space, %40 = @
None of these is encryption, and treating base64 as though it were is a recurring mistake. All three are transformations anybody can reverse without a key — they exist to make bytes survive a channel that expects text, and a password encoded rather than hashed is a password in plain sight. Use them for transport, never for secrecy. 
import base64, urllib.parse

# Base64
base64.b64encode(b"Hello")              # b'SGVsbG8='
base64.b64decode(b"SGVsbG8=")           # b'Hello'

# Hex
b"Hello".hex()                       # '48656c6c6f'
bytes.fromhex("48656c6c6f")            # b'Hello'

# URL encoding
urllib.parse.quote("a b@c")            # 'a%20b%40c'
urllib.parse.unquote("a%20b%40c")       # 'a b@c'

# Command-line equivalents (handy in pentest/CTF)
# echo -n "Hello" | base64

HASHING (NOT ENCODING)
One-Way by Design
Don't confuse hashing with encoding/encryption. Encoding is reversible (anyone can decode). Encryption is reversible with a key. Hashing is one-way — you cannot get the input back from the hash. Hashing is for integrity checks and password storage, never for "hiding" data you need to recover.

🧱 SOLID (Single responsibility, Open-closed, Liskov substitution, Interface segregation, Dependency inversion) Principles — Writing Code That Survives Change SCRIPT • Design ▶
WHY DESIGN PRINCIPLES
Code Is Read and Changed Far More Than Written
A program is rarely "done" — requirements change, bugs are fixed, features added. SOLID is five principles (coined by Robert C. Martin) for structuring code so it's easier to understand, extend, and change without breaking everything. You don't need to memorize them as dogma, but understanding the ideas dramatically improves your code as you move past beginner scripts.
THE FIVE PRINCIPLES
S - O - L - I - D
LetterPrinciplePlain English
SSingle ResponsibilityA class/function should do ONE thing. One reason to change.
OOpen/ClosedOpen to extension, closed to modification — add behavior without editing existing code.

✅ Data Validation — Never Trust Input SCRIPT • Essential ▶
THE GOLDEN RULE
All Input Is Guilty Until Proven Innocent
Data from users, APIs (Application Programming Interface), files, and networks is untrusted — it may be malformed, malicious, or just wrong. Validating it at the boundary (before it enters your logic) prevents both bugs and security holes (injection, crashes, corrupted data). The principle: parse, don't just check — convert raw input into trusted, typed objects at the edge, so the rest of your code can assume the data is clean.
PYDANTIC
Validation via Type Hints
Pydantic is the most popular Python validation library (and the engine behind FastAPI). You declare the shape of your data with types; Pydantic validates, coerces, and gives clear errors — turning messy input into trusted objects.
# pip install pydantic
from pydantic import BaseModel, EmailStr, Field, field_validator

class User(BaseModel):
    name: str = Field(min_length=1, max_length=100)
    age: int = Field(ge=0, le=150)      # 0 ≤ age ≤ 150
    email: EmailStr                          # validated email format
    role: str = "user"                      # default

    @field_validator("name")
    @classmethod
    def no_digits(cls, v):
        if any(c.isdigit() for c in v):
            raise ValueError("name cannot contain digits")
        return v

# Valid input → trusted object (note: "30" coerced to int 30)
u = User(name="Alice", age="30", email="a@example.com")
print(u.age)            # 30 (an int)

# Invalid input → clear, structured error
try:
    User(name="Bob3", age=-5, email="not-an-email")
except Exception as e:
    print(e)             # lists every validation failure

🪝 Webhooks & ChatOps — Event-Driven Automation SCRIPT • Practical ▶
WEBHOOKS
"Don't Call Us, We'll Call You"
Polling means repeatedly asking "anything new yet?" — wasteful and slow. A webhook flips it: you give a service a URL (Uniform Resource Locator), and it sends an HTTP (HyperText Transfer Protocol) POST to that URL when an event happens (a push, a payment, an alert). It's the backbone of modern integrations — GitHub→CI, Stripe→your app, monitoring→Slack. Your side just needs an endpoint that listens.
# A minimal webhook RECEIVER (Flask)
from flask import Flask, request, abort
import hmac, hashlib, os

app = Flask(__name__)
SECRET = os.environ["WEBHOOK_SECRET"].encode()

@app.post("/webhook")
def webhook():
    # 1. VERIFY the signature — never trust an unverified webhook!
    sig = request.headers.get("X-Signature", "")
    expected = hmac.new(SECRET, request.data, hashlib.sha256).hexdigest()
    if not hmac.compare_digest(sig, expected):
        abort(401)

    # 2. Process the event
    event = request.json
    if event["action"] == "opened":
        handle_new_issue(event)

    # 3. Respond FAST (2xx) — do slow work in the background
    return "", 204

WHAT IT IS
Turning Objects Into Bytes and Back
Serialization converts in-memory objects into a storable/transmittable format (text or bytes); deserialization reverses it. 🧪 Testing Strategy — Why and How to Test SCRIPT • Professional ▶
WHY TEST
Tests Are Your Safety Net for Change
Tests aren't about proving code works once — they're about being able to change code confidently later. Without tests, every change risks silently breaking something elsewhere, so people become afraid to touch the code (it "ossifies"). With a good test suite, you refactor fearlessly: if you break something, a test tells you instantly. Tests are also living documentation of how the code is meant to behave.
THE TEST PYRAMID
Many Fast Tests, Few Slow Ones
LevelTestsSpeedHow Many
Unit (base)One function/class in isolationMillisecondsMany (the bulk)
Integration (middle)Components working together (DB, API)SlowerSome
End-to-end (top)Whole system, like a real userSlow, flakyFew
The shape is a pyramid for a reason: lots of fast, reliable unit tests at the base; fewer slow, brittle E2E (End-to-End) tests at the top. The "ice cream cone" anti-pattern (mostly slow E2E tests) makes a suite slow and flaky — painful to run, so people stop running it.
TDD
Test-Driven Development — Red, Green, Refactor
TDD flips the usual order: write the test first, watch it fail, then write just enough code to pass. It forces you to clarify what the code should do before writing it, and guarantees test coverage. Not everyone does strict TDD, but the cycle is a valuable tool to know.
# 1. RED — write a failing test first
def test_celsius_to_fahrenheit():
    assert c_to_f(100) == 212
    assert c_to_f(0) == 32
# Run it → fails (c_to_f doesn't exist yet)

# 2. GREEN — write the minimum to pass
def c_to_f(c):
    return c * 9/5 + 32
# Run it → passes ✓

# 3. REFACTOR — clean up, tests keep you safe
# (add type hints, edge cases, docstring — re-run tests)

Qualities to Aim For

A test suite that takes ten minutes is run before merges; one that takes ten seconds is run constantly, which is where the value actually is — and tests that depend on order fail mysteriously and get deleted. 🛡️ subprocess Without Shell Injection SCRIPT • Security ▶
Reference
The Convenient Form Is the Dangerous One
shell=True exists because it lets you write the command the way you would type it, and that convenience is the vulnerability: a shell is a language interpreter, and you have just concatenated user input into a program. A list of arguments passes the values straight to the process with no interpreter in between, which removes the entire bug class rather than filtering it.
THE SAME COMMAND, TWO WAYS
import subprocess

# DANGEROUS — a shell parses this string, and the filename is part of it
filename = "report.pdf; rm -rf ~"       # it came from a form field
subprocess.run(f"pdfinfo {filename}", shell=True)
# the shell sees two commands. The second one runs.

# SAFE — a list of arguments. No shell, no parsing, no metacharacters
subprocess.run(["pdfinfo", filename], check=True)
# pdfinfo receives one argument, which is a very strange filename. Nothing else happens.

# Also safe, and better: capture output and fail loudly
r = subprocess.run(["pdfinfo", filename],
                   capture_output=True, text=True,
                   timeout=10, check=True)
print(r.stdout)
Notice what the safe version does not need: no escaping, no allowlist of characters, no regex to strip semicolons. The metacharacters stop being special because nothing is parsing them — and that is why this is a design fix rather than a mitigation. Every attempt to sanitise a shell string is a race against a language with many ways to say the same thing.
Reference
Everything Else on the Call, and Why
Once the argument list is right, four more parameters turn a working call into a reliable one. The defaults are chosen for interactive convenience and are wrong for anything running unattended.
ParameterDefaultWhat to use, and why
shellFalseLeave it. If you genuinely need a pipeline, build it with two Popen objects instead
checkFalsecheck=True — otherwise a failed command returns quietly and the script continues
timeoutNoneAlways set one. A hung child process hangs the parent forever
capture_outputFalseCapture it if you need it; note a large output can fill the pipe buffer if you read it wrongly
cwd / envInheritedSet them explicitly for anything scheduled — inherited state is how a script works by hand and fails in cron
Two cases people reach for shell=True to solve, and what to do instead: globbing is glob.glob() or pathlib, which is safer and clearer; pipelines are two processes connected with stdout=subprocess.PIPE. And the general principle: if you find yourself escaping, you are on the wrong path — the same lesson as parameterised SQL (Structured Query Language), one layer down.

Core Concept
Hints Nothing Checks Are Comments With Better Syntax

📁 pathlib & the End of String Paths SCRIPT • Essential ▶
Reference
One Object, and the End of Separator Bugs
Path manipulation with string concatenation is a portability bug waiting for a Windows user, and a correctness bug waiting for a trailing slash. pathlib replaces the whole category: a Path knows what it is, the / operator joins correctly on every platform, and the operations you actually want are methods on the object rather than functions in three different modules.
THE HABIT CHANGE, IN FULL
from pathlib import Path

# String paths: separator bugs, and every operation is a different function
import os
p = base + "/" + name + ".txt"            # breaks on Windows, breaks on a trailing slash
p = os.path.join(base, name + ".txt")      # better, still stringly typed

# pathlib: one object, operators that read like the thing they do
p = Path(base) / f"{name}.txt"

p.suffix                 # '.txt'
p.stem                   # the name without the suffix
p.parent                 # the directory, as a Path
p.with_suffix(".bak")     # same path, different extension
p.exists(), p.is_file()
p.read_text(encoding="utf-8")
p.write_text(data, encoding="utf-8")
p.parent.mkdir(parents=True, exist_ok=True)

for f in Path("logs").glob("**/*.log"):   # recursive, no os.walk
    print(f.resolve())
Three habits worth adopting wholesale. Always pass encoding="utf-8" to read_text and write_text — the default is platform-dependent, and that is a bug that only appears on somebody else's machine. Use resolve() before comparing paths, because ./a and a are equal as files and not as strings. And never build a path from user input without checking it stays inside the directory you intended — Path(base).resolve() in p.resolve().parents is the check, and its absence is directory traversal.
🧵 Threads, Processes & async — Choosing by Where the Time Goes SCRIPT • Intermediate ▶
Core Concept
One Question Picks Between All Three: Where Is the Time Going?
Concurrency in Python looks like three competing options and is really one diagnostic followed by an obvious answer. Is the program waiting, or is it computing? Waiting on the network, a disk or a database is I/O-bound and the answer is threads or async. Burning processor on arithmetic is CPU-bound and the answer is processes. “We added threads and it got slower” is almost always this question answered wrongly.
ModelRight forBecause
async / asyncioMany concurrent I/O (Input/Output) waits — thousands of socketsOne thread, no context-switch cost, and waiting is explicit at await
ThreadsI/O-bound work in libraries that are not asyncThe GIL (Global Interpreter Lock) is released during I/O, so threads genuinely overlap

Answer the question with a profiler rather than an intuition. The programs people most confidently describe as CPU-bound are usually waiting on a database, and the fix in that case is neither threads nor processes — it is one fewer query.
Practice
The GIL, Stated Accurately
The global interpreter lock is described badly more often than it is described well, and both directions cause bad decisions. It does not make threads useless, and it does prevent two threads executing Python bytecode simultaneously.
ClaimAccurate version
“Threads are pointless in Python”False. The GIL is released during I/O and inside many C extensions, so threads help exactly where waiting dominates
“The GIL makes Python thread-safe”False, and dangerous. Individual bytecodes are atomic; your read-modify-write is not. Use a Lock
“numpy is single-threaded because of the GIL”False. It releases the GIL for the heavy loops, which is why it scales
“Processes are just slower threads”They start slower and cannot share objects — arguments and results are pickled, so large payloads cost
“Free-threaded Python removes the question”It changes the trade rather than removing it. Treat the model choice as still yours to make
The row that costs real money is the second. The GIL is not a substitute for a lock: a counter incremented from two threads will lose updates, exactly as it would in any other language, and the belief that Python is implicitly thread-safe is how that bug reaches production.
Practice
Choosing, and the Failure Modes of Each
Once the diagnostic is done, each model has one characteristic way of going wrong that is worth knowing before you meet it.

ProcessesPickling costs, and the object that cannot be pickled. Also: the child that inherits state it should not
Two practical defaults. For I/O-bound work in ordinary application code, concurrent.futures.ThreadPoolExecutor is the smallest thing that works and requires no rewrite; reach for asyncio when the concurrency is in the thousands or the libraries are already async. For CPU-bound work, ProcessPoolExecutor with chunked inputs — and check whether the library you are using (numpy, polars, a compression codec) already parallelises internally, because wrapping it in processes then makes it slower.
📦 Packaging & Dependency Pinning — Making It Installable by Someone Else SCRIPT • Practical ▶
Core Concept
The Gap Between “Works on My Machine” and “Installs”
A script becomes software the moment somebody else has to run it, and the two artefacts that close that gap are a project file (what this needs, roughly) and a lockfile (exactly what was installed when it last worked). They answer different questions and having only the first is the most common reason a working project cannot be reproduced.

Practice
Pin for Applications, Range for Libraries
The rule that resolves most arguments is that the right answer differs by what you are building. An application is installed once into an environment you control, so pinning is free and reproducibility is everything. A library is installed alongside other people's dependencies, so pinning tightly makes it un-installable.
You are buildingDo this
An application or servicePin everything, with hashes, in a lockfile committed to the repo
A library for othersDeclare ranges — a lower bound you tested and an upper bound only where you know a break exists
A library, pinning exact versionsCauses dependency hell for every consumer. Two libraries pinning different patch versions cannot coexist
An internal toolTreat it as an application. Nobody depends on it as a library
Anything at allCommit the lockfile. It is not build output; it is a record of what worked
The middle row is worth stating as a rule for anyone publishing a package: pinning exact versions in a library is antisocial. It cannot coexist with any other library that made the same choice, and the person who discovers that is a stranger with no way to fix it.

Dependency management and supply-chain security are the same activity described by two departments. Every pin is a decision about what code you are choosing to run, and the mechanisms that make builds reproducible are the mechanisms that make them auditable.

🧹 Pre-Commit, Formatters & Linters — Ending the Style Argument SCRIPT • Toolchain ▶
The Inversion
A Formatter's Value Is Social, Not Technical
An autoformatter is usually justified on tidiness, and that undersells it. Its real payoff is that it removes an entire category of human argument — where the brace goes, how long a line is, whether to align the equals signs — by making the answer automatic and non-negotiable. The code style stops being a matter of taste anyone can debate in a review, which is worth far more than the formatting itself. The tool is valuable because it stops people discussing whitespace.
Tool classJobArgument it ends
Formatter (e.g. Black, Prettier)Rewrites layout to one canonical form“Your style vs my style” — there is now only one
Linter (e.g. Ruff, ESLint)Flags likely bugs & bad patterns“Is this a problem?” — the rule decides
Pre-commit hookRuns both before a commit is allowed“I forgot to run it” — you cannot commit unformatted
Keep the two straight: a formatter is not a linter. The formatter has no opinions worth arguing with and should run with zero configuration; the linter has opinions and every enabled rule is a small policy decision. Conflating them — trying to make the formatter enforce logic, or the linter enforce layout — is where teams reintroduce the argument they were trying to end.
The Decision
Enforce It at the Gate, Not by Asking People to Remember
A formatter nobody runs is a formatter that does nothing, and “please run it before you push” is a rule that fails on the busy day. The mechanism that makes it real is enforcement at a gate: a pre-commit hook locally for fast feedback, and the same check in CI so the hook cannot be skipped. The two together mean formatted code is the only code that can merge.
Adopt the formatter with no config and let it win every layout question; add a linter and treat each rule you enable as a deliberate choice; and enforce both in a pre-commit hook backed by a CI check, so the standard is automatic rather than remembered. When you introduce it to an existing codebase, reformat everything in one separate commit and record it in .git-blame-ignore-revs, or every future git blame points at the reformat instead of the author.
