⚙️ How a Database Actually Works Internals ▶
Concept
Pages, the Buffer Pool & the Write-Ahead Log
A database is not magic — it's a careful dance between disk and memory. Data lives on disk in fixed-size pages (commonly 8 KB); the engine caches hot pages in a memory buffer pool so most reads never touch disk. Durability comes from the write-ahead log (WAL).
ComponentJob
Storage engineReads/writes pages, manages indexes (InnoDB, Postgres heap)
Buffer poolIn-memory page cache — the #1 performance factor
WAL / redo logAppend every change before the data page — crash recovery
CheckpointFlush dirty pages to disk; trim the log
Why WAL: writing a tiny sequential log entry is fast and safe; the actual (random) page write can happen later. On crash, replay the log to recover committed work. This one idea gives you the "D" in ACID (Atomicity, Consistency, Isolation, Durability) and underpins replication and point-in-time recovery.
🧮 The Relational Model — Keys & Integrity Foundations ▶
Concept
Tables, Keys & the NULL Gotcha
The relational model organizes data into relations (tables) of rows and typed columns, with relationships expressed by keys rather than pointers. Constraints let the database enforce correctness so your application doesn't have to.
TermMeaning
Primary keyUniquely identifies a row; not null
Foreign keyReferences a PK elsewhere — enforces referential integrity
Unique / CheckColumn-level rules the DB guarantees
Candidate / composite keyOther unique columns; keys spanning multiple columns
The NULL trap: NULL means "unknown," not zero or empty. It uses three-valued logic — NULL = NULL is not true but NULL, and WHERE x = NULL matches nothing (use IS NULL). NULLs silently break naive comparisons, joins, and aggregates — the single most common SQL (Structured Query Language) bug.
📐 Normalization — 1NF Through BCNF Design ▶
Concept
Eliminate Redundancy, Then Know When to Stop
Normalization structures tables so each fact is stored once, preventing update anomalies (change an address in one row, forget the other five). You progress through normal forms, each removing a specific kind of redundancy.
FormRule
1NFAtomic values — no repeating groups or lists in a cell
2NFNo partial dependency on part of a composite key
3NFNo transitive dependency (non-key → non-key)
BCNFEvery determinant is a candidate key (stricter 3NF)
Rule of thumb: normalize to 3NF for transactional (OLTP) systems — it keeps writes clean. Then denormalize deliberately for read-heavy or analytics workloads, trading duplication for fewer joins. Star schemas (analytics) are intentionally denormalized.
🔒 ACID (Atomicity, Consistency, Isolation, Durability) & Transactions — Isolation Levels Foundations ▶
Concept
All-or-Nothing, and Who Sees What
A transaction groups statements so they succeed or fail as a unit. ACID is the guarantee: Atomic (all or nothing), Consistent (constraints hold), Isolated (concurrent txns don't corrupt each other), Durable (committed = survives a crash).
Isolation levelPrevents
Read Uncommittednothing — can read dirty (uncommitted) data
Read Committeddirty reads (Postgres default)
Repeatable Read+ non-repeatable reads (MySQL default)
Serializable+ phantom reads — as if txns ran one at a time
The trade-off: stricter isolation = more correct but more locking/aborts and less concurrency. Know the three anomalies (dirty, non-repeatable, phantom) and pick the weakest level that's still safe for your workload.
🕸️ ER Modeling — Designing the Schema Design ▶
Reference
Entities, Relationships & Cardinality
Before writing DDL (Data Definition Language), you model the domain: what things exist (entities), their attributes, and how they relate. An entity-relationship diagram (crow's-foot notation) is the shared language between engineers and stakeholders.
RelationshipImplemented as
One-to-manyFK on the "many" side (most common)
Many-to-manyA junction/join table with two FKs
One-to-oneShared/unique FK — often a sign to merge tables
Crow's-foot marks each end with cardinality (one/many) and optionality (zero/one). Get the relationships right here and the tables, keys, and joins fall out naturally — this is the bridge from requirements to a normalized schema.
🔗 SQL (Structured Query Language) Joins — Every Type, and the NULL Traps SQL ▶
Reference
Combining Rows Across Tables
Joins match rows from two tables on a condition. The type decides what happens to rows that don't match — and that's where most bugs live. 
SELECT u.name, o.total
FROM users u
LEFT JOIN orders o ON o.user_id = u.id;   -- keeps users with no orders
JoinReturns
INNEROnly rows that match in both tables
LEFT / RIGHTAll rows from one side; NULLs where no match
FULL OUTERAll rows from both; NULLs on either side
CROSSCartesian product (every combo) — usually a mistake
SELFA table joined to itself (hierarchies, pairs)
Traps: putting a filter on the outer table in WHERE silently turns a LEFT JOIN into an INNER JOIN (put it in the ON instead); and joining on a nullable column drops rows because NULL = NULL isn't true. Watch for fan-out: a one-to-many join multiplies rows and inflates SUM().
🪟 Window Functions — Analytics Without Collapsing Rows SQL ▶
Reference
Rankings, Running Totals & Row-to-Row Math
GROUP BY collapses rows; window functions compute across a set of rows while keeping every row. The OVER() clause defines the "window" (partition + order). 
SELECT name, dept, salary,
  RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS rnk,
  SUM(salary) OVER (PARTITION BY dept) AS dept_total
FROM employees;
FunctionUse
ROW_NUMBER / RANK / DENSE_RANKOrdering & top-N per group
LAG / LEADCompare to the previous/next row (deltas, growth)
SUM/AVG OVERRunning totals & moving averages
NTILEBuckets/percentiles
Killer use: "top 3 earners per department" or "each order vs the customer's previous order" — one query, no self-joins. Window functions are the single biggest jump from beginner to intermediate SQL (Structured Query Language).
🧱 CTEs (Common Table Expression) & Recursion — Readable, Composable Queries SQL ▶
Reference
Name Your Steps With WITH
A Common Table Expression (WITH) names a subquery so you can build a complex query as readable, stacked steps instead of nested parentheses. Recursive CTEs traverse hierarchies and graphs. 
WITH ranked AS (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY ts DESC) rn
  FROM events
)
SELECT * FROM ranked WHERE rn = 1;   -- latest event per user
Recursive form: an anchor query UNION ALL a step that references the CTE — perfect for org charts, category trees, or "all descendants of X." Readability tip: CTEs make a 60-line query reviewable; deeply nested subqueries don't. (Note: some engines materialize CTEs — check the plan if performance matters.)
Σ Aggregation — GROUP BY, HAVING & ROLLUP SQL ▶
Reference
Summarizing Rows Into Groups
Aggregate functions (COUNT, SUM, AVG, MIN/MAX) collapse many rows into one per group. GROUP BY defines the groups; HAVING filters after aggregation (unlike WHERE, which filters before). 
SELECT country, COUNT(*) AS n, SUM(total) AS rev
FROM orders
WHERE status = 'paid'          -- filter rows first
GROUP BY country
HAVING SUM(total) > 10000      -- filter groups after
ORDER BY rev DESC;
FeatureDoes
COUNT(*) vs COUNT(col)All rows vs non-NULL values only
COUNT(DISTINCT …)Unique values
ROLLUP / CUBE / GROUPING SETSSubtotals & grand totals in one pass
FILTER (WHERE …)Conditional aggregates (Postgres)
Classic error: selecting a non-aggregated column that isn't in GROUP BY — either group by it or wrap it in an aggregate.
🎯 Subqueries, EXISTS & Set Operations SQL ▶
Reference
Queries Inside Queries
A subquery is a SELECT nested in another statement. It can return a scalar, a list (for IN), or a table. Correlated subqueries reference the outer row and run per-row. 
-- customers who have placed at least one order
SELECT name FROM users u
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
ToolUse
IN / NOT INMembership — but NOT IN + NULLs = no rows (trap!)
EXISTS / NOT EXISTSExistence check — NULL-safe, often faster
UNION / UNION ALLStack result sets (ALL keeps duplicates & is faster)
INTERSECT / EXCEPTRows in both / in one but not the other
Prefer EXISTS over NOT IN whenever the inner column can be NULL — NOT IN (…NULL…) returns nothing, a famously silent bug. Many subqueries also rewrite cleanly as joins or CTEs (Common Table Expression); pick whichever reads clearest.
📇 Indexes Explained — B-tree, Hash & Covering Performance ▶
Concept
The Book's Index, for Your Data
An index is a sorted data structure that lets the database find rows without scanning the whole table — the difference between O(log n) and O(n). The cost: every write must also update the index, and indexes take space.
TypeBest for
B-treeThe default — equality & range (=, <, BETWEEN, ORDER BY)
HashEquality only, very fast
GIN / GiSTFull-text, JSONB, arrays, geospatial (Postgres)
CompositeMulti-column — order matters (leftmost-prefix rule)
CoveringIncludes all columns a query needs → index-only scan
Composite key order: an index on (a, b) helps WHERE a=… and WHERE a=… AND b=…, but not WHERE b=… alone. Index the columns you filter/sort on; don't over-index — each one slows writes.
🔍 Reading Query Plans — EXPLAIN ANALYZE Performance ▶
Reference
Ask the Database What It's Doing
The optimizer turns your SQL (Structured Query Language) into a physical plan. EXPLAIN shows that plan; EXPLAIN ANALYZE actually runs it and shows real timings and row counts. Reading plans is the core skill for fixing slow queries. 
EXPLAIN ANALYZE
SELECT * FROM orders WHERE user_id = 42;
SeeMeans
Seq ScanReading the whole table — often a missing index
Index Scan / Index-OnlyUsing an index (good)
Nested Loop / Hash / Merge JoinThe three join strategies
Rows estimated vs actualBig mismatch = stale statistics → bad plan
Workflow: find the node eating the most time, check if a Seq Scan should be an index, and compare estimated vs actual rows. A huge estimate error usually means ANALYZE (statistics) is out of date.
🚀 Query Optimization — Sargability & N+1 Performance ▶
Concept
Write Queries the Index Can Use
A query is sargable ("Search ARGument able") when it can use an index. Wrapping an indexed column in a function or leading a LIKE with a wildcard defeats the index and forces a scan. 
-- NOT sargable: function on the column
WHERE DATE(created_at) = '2026-01-01'
-- sargable: range on the raw column
WHERE created_at >= '2026-01-01' AND created_at < '2026-01-02'
Anti-patternFix
func(col) = xRewrite as a range, or index the expression
LIKE '%foo'Leading wildcard can't use B-tree — use full-text
The N+1 query1 query + N per-row queries → JOIN or batch (IN)
SELECT *Fetch only needed columns → enables covering indexes
The N+1 problem is the #1 app-layer DB killer (ORMs love to cause it): loading a list, then firing one query per item. Fix by eager-loading with a join or a single WHERE id IN (…).
🚦 Locking & MVCC — Concurrency Without Chaos Internals ▶
Concept
How Readers and Writers Coexist
MVCC (Multi-Version Concurrency Control) is how Postgres/InnoDB let many transactions run at once: writers create new versions of rows instead of overwriting, so readers never block writers and writers never block readers. Each transaction sees a consistent snapshot.
ConceptDetail
Row versionsOld versions kept until no txn needs them
VACUUM (Postgres)Cleans up dead tuples — neglect it and the table bloats
Row vs table locksFOR UPDATE locks specific rows for a write
DeadlockTwo txns wait on each other — DB kills one; retry it
Avoiding deadlocks: acquire locks in a consistent order and keep transactions short. Explicit locking (SELECT … FOR UPDATE) is how you safely implement "decrement inventory" under concurrency.
🍰 Partitioning & Sharding — Scaling One Big Table Scale ▶
Concept
Split the Data When It Won't Fit
Partitioning splits one table into pieces within a single database (by range/list/hash) so queries scan less and old data is easy to drop. Sharding spreads data across multiple databases/servers to scale beyond one machine.
TechniqueDetail
Range partitionBy date — drop last month in one command (time-series)
Hash partitionEven spread by a key's hash
Shard keyChooses which server a row lives on — pick carefully
Cross-shard queries/joinsThe hard part — slow, complex; avoid by design
Order of escalation: optimize queries & indexes → add a read replica → partition → (only then) shard. Sharding adds real operational complexity; a bad shard key causes hotspots and painful re-sharding.

🧰 Postgres Power Features — JSONB & Full-Text Postgres ▶
Reference
More Than Rows and Columns
Postgres blurs the line with NoSQL: store and index JSON (JavaScript Object Notation) documents, arrays, and run full-text search — often removing the need for a separate datastore. 
-- JSONB: query inside a document, indexed with GIN
SELECT data->>'email' FROM users
WHERE data @> '{"plan":"pro"}';

-- Full-text search
WHERE to_tsvector(body) @@ to_tsquery('postgres & index');
FeatureUse
JSONBSemi-structured data, indexed with GIN; @>, ->>

🐬 MySQL / MariaDB — The Other Giant MySQL ▶
Reference

MySQL (and its community fork MariaDB) is ubiquitous — WordPress, countless web apps, and managed offerings everywhere. Very capable; a few behaviors differ from Postgres and catch people out.
Thing to knowDetail

📦 SQLite — The Database That's Everywhere SQLite ▶
Reference
A Whole Database in One File
SQLite is an embedded, serverless database — the entire DB is a single file, no process to run. It's the most deployed database in the world: every phone, browser, and countless apps ship it.
Great forNot for
App/local storage, mobile, edgeHigh write concurrency (single-writer)
Tests & prototypesMultiple app servers sharing it
Analytics on a file (with extensions)Network access by many clients
Don't dismiss it: "SQLite is not a toy" — for read-heavy or single-node workloads it's blazing fast and zero-ops. Modern tools (Litestream, LiteFS, Turso) even give it replication. Know when not to reach for a server database.
🌊 Connection Pooling — Surviving Many Clients Ops ▶
Concept
Why Your DB Falls Over Under Load
Each database connection costs memory and a backend process. Open one per request and a traffic spike (or a serverless fleet) opens thousands, exhausting the server. A connection pool reuses a small, fixed set of connections.
LayerDetail
App-side poolHikariCP, pgx, SQLAlchemy — reuse connections per app
PgBouncerExternal pooler; transaction mode multiplexes many clients
ServerlessFunctions × requests = connection storm → use a pooler/proxy
Sizing: more connections isn't faster — past a point they just contend. A good pool is often just (cores × 2) + spindles, not hundreds. Connection exhaustion presents as timeouts under load; the fix is pooling, not a bigger max_connections.
🗂️ The NoSQL Landscape — Four Families NoSQL ▶
Concept
Not "No SQL (Structured Query Language)" — "Not Only SQL"
NoSQL databases relax the relational model to gain scale, flexibility, or a shape that fits a specific access pattern. They usually trade strong consistency and rich joins for horizontal scalability (the CAP trade-off).
FamilyModelExample
Key-ValueSimple map — fastest lookupsRedis, DynamoDB
DocumentJSON-like docs, flexible schemaMongoDB, Couchbase
Wide-ColumnRows with dynamic columns, huge scaleCassandra, Bigtable
GraphNodes & edges — relationships firstNeo4j
Choosing: pick NoSQL for a specific reason — massive scale, a document-shaped domain, or graph traversal — not to avoid SQL. Most apps are still best served by a relational database; "boring technology" wins more often than not.
🍃 MongoDB — Documents & the Aggregation Pipeline Document ▶
Reference
Store the Object, Not the Rows
MongoDB stores flexible JSON-like documents in collections. It shines when your data is naturally nested and your access pattern reads whole objects — no joins to reassemble them. 
// find + aggregate
db.orders.aggregate([
  { $match: { status: "paid" } },
  { $group: { _id: "$country", revenue: { $sum: "$total" } } },
  { $sort: { revenue: -1 } }
])
Schema design: model around access patterns — embed data you read together, reference data you read separately. Add indexes just like SQL (Structured Query Language). Modern Mongo has ACID (Atomicity, Consistency, Isolation, Durability) multi-document transactions, but they signal you may have wanted relational.
Watch out: unbounded array growth, and treating it as schemaless forever — inconsistent documents become a nightmare. Enforce a schema at the app (or with schema validation).
⚡ Redis — The In-Memory Multi-Tool Key-Value ▶
Reference
Data Structures at Memory Speed
Redis keeps data in RAM (Random Access Memory), making it microsecond-fast. It's not just a cache — it offers real data structures and is the go-to for caching, sessions, rate limiting, queues, and leaderboards.
StructureUse
String / counterCache values, rate limits (INCR)
HashStore objects (session, user)
Sorted SetLeaderboards, time-ordered queues
List / StreamQueues & event logs
Pub/SubLightweight messaging
Caching patterns: cache-aside (check Redis, miss → DB → populate) is most common; always set a TTL (Time To Live) and plan for cache invalidation. Persistence (RDB snapshots / AOF) means it can survive restarts, but treat it as a fast layer, not the source of truth.
🏛️ Cassandra & DynamoDB — Wide-Column at Scale Wide-Column ▶
Concept
Design for the Query, Not the Entity
Cassandra and DynamoDB scale to enormous write volumes across many nodes with no single point of failure. The catch: you must model around your queries up front — there are no ad-hoc joins.
ConceptDetail
Partition keyDecides which node stores the row — even distribution is critical
Sort/clustering keyOrders rows within a partition
Single-table designDynamoDB: model many entities in one table by key design
Hot partitionA bad key funnels traffic to one node — throttling
Tunable consistency (quorums) lets you dial latency vs freshness per operation. These shine for known, high-volume access patterns (feeds, IoT, sessions) — and hurt when requirements need flexible querying. Choose the key like your scalability depends on it, because it does.
🕸️ Graph Databases — When Relationships Are the Data Graph ▶
Reference
Traversals Instead of Joins
A graph database stores nodes and relationships as first-class citizens. Questions that need many-hop joins in SQL (Structured Query Language) ("friends of friends who like X") become natural, fast traversals. 
// Neo4j Cypher: mutual connections
MATCH (me:Person {name:"Ann"})-[:KNOWS]->(f)-[:KNOWS]->(fof)
WHERE fof <> me
RETURN fof.name, count(*) ORDER BY count(*) DESC
Great forExample
NetworksSocial graphs, org charts
Recommendations"People who bought… also…"
Fraud / securityAttack-path & ring detection (cf. BloodHound)
The relationship is stored directly, so a traversal is a pointer-hop, not a join — performance stays flat as hops increase. Use a graph DB when connections are the primary query; otherwise a relational DB is simpler.
↔️ OLTP (Online Transaction Processing) vs OLAP (Online Analytical Processing) — Rows vs Columns Analytics ▶
Concept
Two Opposite Jobs, Two Storage Layouts
OLTP (transactional) handles many small reads/writes of whole rows — your app database. OLAP (analytical) scans huge numbers of rows over a few columns — your reporting warehouse. Their opposite needs drive opposite storage.
OLTP (row store)OLAP (column store)
AccessFew rows, all columnsMany rows, few columns
LayoutRows togetherColumns together
Wins atPoint lookups & writesAggregations & scans
ExamplePostgres, MySQLBigQuery, Snowflake, ClickHouse
Why columnar is fast for analytics: reading only the 3 columns a query touches (not all 50), plus massive compression on similar values. Don't run heavy analytics on your OLTP database — it competes with live traffic. Move it to a warehouse.
🧊 Columnar Engines — Parquet, DuckDB & ClickHouse Analytics ▶

Columnar storage plus vectorized execution (processing batches of values at once) is what makes modern analytics fast. You'll meet it as a file format and as query engines.
ToolRole

🏞️ Warehouse vs Lake vs Lakehouse Analytics ▶
Concept
Where Analytical Data Lives
Three architectures for storing analytical data, each solving the previous one's limitation. The lakehouse is the current convergence.
ApproachWhat it is
Data WarehouseStructured, schema-on-write, SQL (Structured Query Language) — Snowflake, BigQuery, Redshift
Data LakeRaw files (Parquet) in object storage, schema-on-read — cheap, flexible, messy
LakehouseLake storage + warehouse features (ACID, tables) via Delta/Iceberg/Hudi
Table formats (Apache Iceberg, Delta Lake) are the key innovation — they add transactions, schema evolution, and time-travel on top of plain files, so one copy of data serves many engines. Warehouse = easy & governed; lake = cheap & open; lakehouse = both, at the cost of complexity.

💾 Backups & Point-in-Time Recovery DBA ▶
Concept
A Backup You Haven't Restored Isn't a Backup
The database holds the business's most irreplaceable asset. Backups protect against hardware failure, bad deploys, and DELETE-without-WHERE. The goal is a tested path back to any moment before disaster.
TypeDetail
Logical dumppg_dump/mysqldump — portable, slow to restore, per-DB
Physical backupFile-level (pgBackRest, Percona) — fast, whole cluster
PITRBase backup + WAL (Write-Ahead Log) archive → restore to an exact second
SnapshotsCloud volume snapshots — fast but check consistency
RPO/RPO drive design: continuous WAL archiving gives near-zero data loss (RPO). But the only backup that counts is a restore you've actually tested — schedule restore drills, or you have Schrödinger's backup.
👯 Replication & High Availability DBA ▶
Concept
Copies for Scale and Survival
Replication streams changes from a primary to one or more replicas. It buys you read scaling, failover, and geographic locality — but introduces lag and failover complexity.
ConceptDetail
Async replicationFast writes, but replicas lag → possible stale reads/data loss on failover
Sync replicationNo data loss, higher write latency
Read replicasOffload reporting/read traffic
Automatic failoverPatroni/orchestrator promote a replica on primary death
Split-brainTwo primaries accept writes — data divergence; fencing prevents it
Replication lag means "read your own write" can fail — route critical reads to the primary. HA needs a leader-election mechanism; rolling your own failover is how you get split-brain.
🔀 Schema Migrations — Zero-Downtime Change DBA ▶
Concept
Changing the Schema While Live
Schema changes are code changes and must be versioned, reviewed, and reversible. The hard part is altering a big table without locking it or breaking the currently-running app version.
Tool / IdeaDetail
Migration toolsFlyway, Liquibase, Alembic, Rails — versioned, ordered scripts
Expand/contractAdd new → backfill → switch → remove old (multi-deploy)
Locking DDL (Data Definition Language)Some ALTERs rewrite/lock the table — check first
Online toolsgh-ost, pt-online-schema-change for big MySQL tables
Golden rule: every migration must be backward-compatible with the currently-deployed code, because during a rollout both versions run at once. "Add a nullable column, deploy, backfill, then enforce" beats a single locking change. Always have a rollback.
🛡️ Database Security — Least Privilege & RLS Security ▶
Reference
Protecting the Crown Jewels
The database is the highest-value target. Defense is layered: control who connects, what they can touch, and protect the data at rest and in transit. Ties directly to the security domain.
ControlDetail
Least-privilege rolesApp user ≠ superuser; separate read/write/migration roles

And of course: parameterized queries to stop SQL (Structured Query Language) injection (the app's job), and network isolation so the DB is never internet-facing. Column-level encryption/masking protects PII (Personally Identifiable Information) even from DB admins.

🏗️ Designing a Schema From Requirements Craft ▶
Walkthrough
From "We Sell Stuff" to Tables
A repeatable process turns fuzzy requirements into a sound schema. Example: an e-commerce order system.
StepDo
1. Find nounsCustomer, Product, Order, OrderItem, Payment → entities
2. RelationshipsOrder has many OrderItems; OrderItem → one Product
3. Keys & typesPKs, FKs, pick types & constraints (money as decimal!)
4. Normalize to 3NFEach fact once; no update anomalies

Snapshot the price: an OrderItem stores the price at time of sale, not a live FK to Product.price — a classic modeling insight. Design OLTP (Online Transaction Processing) for correctness; derive OLAP from it.
⏱️ Time-Series & Event Data Craft ▶
Concept
When Time Is the Primary Axis
Metrics, logs, IoT (Internet of Things) readings, and financial ticks are append-heavy and queried by time window. Specialized handling keeps them fast and affordable as they grow without bound.
TechniqueDetail
Time partitioningChunk by day/week; drop old chunks instantly
Downsampling / rollupsKeep 1s data briefly, 1m/1h aggregates long-term
Retention policiesAuto-expire raw data past N days
ToolsTimescaleDB, InfluxDB, Prometheus, ClickHouse
The pattern that makes it sustainable: high-resolution recent + low-resolution history. You almost never need per-second data from last year, so roll it up and let raw data expire. Ties to the observability cards in ops.
🧭 Vector Databases — Embeddings & Similarity Search AI Bridge ▶
Concept
Searching by Meaning, Not Keywords
AI (Artificial Intelligence) models turn text/images into embeddings — vectors where similar meaning = nearby points. A vector database indexes these for fast nearest-neighbor search, the backbone of RAG (Retrieval-Augmented Generation) and semantic search.
ConceptDetail
EmbeddingA model maps content → a high-dimensional vector
ANN (Artificial Neural Network) indexHNSW/IVF — approximate nearest-neighbor for speed
SimilarityCosine / dot product ranks "closeness"
Optionspgvector, Pinecone, Weaviate, Qdrant, Milvus
Start simple: pgvector adds vector search to Postgres — often you don't need a separate vector DB at all. Hybrid search (vectors + keyword/filters) beats either alone. Direct bridge to the AI domain's RAG cards.
