⚙️ How a Database Actually Works Internals ▶
Concept
Pages, the Buffer Pool & the Write-Ahead Log
A database is not magic — it's a careful dance between disk and memory. Data lives on disk in fixed-size pages (commonly 8 KB); the engine caches hot pages in a memory buffer pool so most reads never touch disk. Durability comes from the write-ahead log (WAL).
ComponentJob
Storage engineReads/writes pages, manages indexes (InnoDB, Postgres heap)
Buffer poolIn-memory page cache — the #1 performance factor
WAL / redo logAppend every change before the data page — crash recovery
CheckpointFlush dirty pages to disk; trim the log
Why WAL: writing a tiny sequential log entry is fast and safe; the actual (random) page write can happen later. On crash, replay the log to recover committed work. This one idea gives you the "D" in ACID (Atomicity, Consistency, Isolation, Durability) and underpins replication and point-in-time recovery.
The Fingerprint
The Buffer Pool Is the Whole Performance Story — and the Working Set Must Fit in RAM (Random Access Memory)
Database performance collapses to one question: is the page you need already in the buffer pool? A read that hits the cache is memory-fast; one that misses is a random disk seek, orders of magnitude slower. Two consequences trip people up. First, benchmarks lie unless you control for cache warmth: the same query is slow on the first run (cold pages) and fast on the second, so an “it's fast now” taken after warming tells you nothing about the cold path a real user hits. Second and more important, performance falls off a cliff when the working set no longer fits: below that line most reads are memory, above it every read is disk, and throughput drops by orders of magnitude with no code change. And the WAL sets the write ceiling — a commit isn't durable until its log entry is fsync'd, so commit latency is disk-sync latency.
The realityWhat it means for you
Read hits the buffer poolMemory-fast — the common, cheap case
Read missesRandom disk seek — orders of magnitude slower
Working set > buffer poolPerformance cliff — every read hits disk
Commit = WAL fsyncCommit latency is disk-sync latency; batch to amortise
So the most useful capacity question is whether your hot data fits in RAM, and the most useful performance instinct is to distrust any benchmark that didn't control for a cold cache. Size the buffer pool to the working set, watch the cache-hit ratio as the number that predicts trouble, and remember a commit's speed is your disk's fsync speed — everything else is downstream of those two facts.
🧮 The Relational Model — Keys & Integrity Foundations ▶
Concept
Tables, Keys & the NULL Gotcha
The relational model organizes data into relations (tables) of rows and typed columns, with relationships expressed by keys rather than pointers. Constraints let the database enforce correctness so your application doesn't have to.
TermMeaning
Primary keyUniquely identifies a row; not null
Foreign keyReferences a PK elsewhere — enforces referential integrity
Unique / CheckColumn-level rules the DB (Database) guarantees
Candidate / composite keyOther unique columns; keys spanning multiple columns
The NULL trap: NULL means "unknown," not zero or empty. It uses three-valued logic — NULL = NULL is not true but NULL, and WHERE x = NULL matches nothing (use IS NULL). NULLs silently break naive comparisons, joins, and aggregates — the single most common SQL (Structured Query Language) bug.
The Decision
Put the Invariant in the Database — Every Writer Passes Through It, the App Layer Doesn't
The card says constraints let the database enforce correctness “so your application doesn't have to,” and that argument is worth making sharply: the constraint is the only rule every writer obeys. Teams that enforce invariants only in the service layer still corrupt their data, because there is always another writer — a migration script, a second service, an ORM (Object-Relational Mapping) path that skips validation, a one-off manual fix at 2am. Application validation is a rule some writers follow; a NOT NULL, a foreign key, a UNIQUE, a CHECK is a rule none can bypass. The common mistake is dropping constraints “for performance” or “for flexibility” — trading a small, known write cost for eventual silent corruption that is far more expensive to find than to prevent.
Enforced whereWho it actually constrains
Application / service codeOnly the writers that go through that code
ORM validationsSkipped by raw SQL, migrations, and other services
A database constraintEvery writer, no exceptions — including the 2am manual fix
“We'll just be careful”Nobody, eventually
So model invariants as constraints by default — NOT NULL, foreign keys, UNIQUE, CHECK — and relax one only with a named reason you have written down, not a vague appeal to performance. The database is the one place a rule is guaranteed; every layer above it holds only until the next writer forgets. Cheap up front, and the last line of defence when the application has a bug — which it will.
📐 Normalization — 1NF Through BCNF Design ▶
Concept
Eliminate Redundancy, Then Know When to Stop
Normalization structures tables so each fact is stored once, preventing update anomalies (change an address in one row, forget the other five). You progress through normal forms, each removing a specific kind of redundancy.
FormRule
1NFAtomic values — no repeating groups or lists in a cell
2NFNo partial dependency on part of a composite key
3NFNo transitive dependency (non-key → non-key)
BCNFEvery determinant is a candidate key (stricter 3NF)
Rule of thumb: normalize to 3NF for transactional (OLTP) systems — it keeps writes clean. Then denormalize deliberately for read-heavy or analytics workloads, trading duplication for fewer joins. Star schemas (analytics) are intentionally denormalized.
The Verdict
When to Stop, and When to Go Backwards on Purpose
Normal forms are a ladder with no instruction about where to get off, which is why the subject produces both under- and over-engineered schemas. The honest guidance is short and depends entirely on what the table is for.
WorkloadTargetWhy
Transactional — orders, accounts, anything written often3NF, and stopEach fact stored once means a write touches one place. BCNF beyond this rarely changes the tables you would have drawn anyway
Analytical — reporting, dashboards, a warehouseDenormalise deliberatelyStar schemas duplicate on purpose: joins are the cost at read time, and nothing is being updated in place
A read-heavy path inside a transactional systemA derived column or a materialised viewDuplication with an owner and a refresh rule, which is different from duplication by accident
Denormalisation is a decision, not a failure — provided it is written down. The distinction that matters is not normalised versus not; it is whether a duplicated value has a stated source of truth and something that keeps it honest. A copy nobody owns silently diverges, and the divergence surfaces as two dashboards disagreeing months later.
🔒 ACID (Atomicity, Consistency, Isolation, Durability) & Transactions — Isolation Levels Foundations ▶
Concept
All-or-Nothing, and Who Sees What
A transaction groups statements so they succeed or fail as a unit. ACID is the guarantee: Atomic (all or nothing), Consistent (constraints hold), Isolated (concurrent txns don't corrupt each other), Durable (committed = survives a crash).
Isolation levelPrevents
Read Uncommittednothing — can read dirty (uncommitted) data
Read Committeddirty reads (Postgres default)
Repeatable Read+ non-repeatable reads (MySQL default)
Serializable+ phantom reads — as if txns ran one at a time
The trade-off: stricter isolation = more correct but more locking/aborts and less concurrency. Know the three anomalies (dirty, non-repeatable, phantom) and pick the weakest level that's still safe for your workload.
Silently wrong
Read, Modify, Write — and Lose the Other Update
Wrapping two statements in a transaction does not make them atomic in the way people assume. At READ COMMITTED, the default in PostgreSQL, SQL (Structured Query Language) Server and Oracle, two sessions can both read a balance of 100, both subtract 10, and both write 90. One update is gone, both transactions committed, and no error was raised — the database did exactly what each session asked.
Isolation levelWhat it still permits
READ UNCOMMITTEDDirty reads — other sessions' uncommitted values
READ COMMITTED (common default)Non-repeatable reads, and lost updates on read-modify-write
REPEATABLE READ (MySQL default)Phantom rows in some engines; MySQL uses gap locks to reduce them
SERIALIZABLENothing — but expect serialisation failures you must retry
SELECT … FOR UPDATELocks the row now, at any level. The targeted fix for exactly this
How you would notice: you usually do not, which is why this is the entry worth remembering. It shows up as a balance, a stock count or a counter that drifts under concurrency and reconciles fine in testing, where nothing runs at the same time. Two reliable fixes: do the arithmetic in the database (UPDATE … SET n = n - 10, which is atomic), or take the row lock with SELECT … FOR UPDATE before reading.
🕸️ ER Modeling — Entities, Relationships & Cardinality Design ▶
Reference
Entities, Relationships & Cardinality
Before writing DDL (Data Definition Language), you model the domain: what things exist (entities), their attributes, and how they relate. An entity-relationship diagram (crow's-foot notation) is the shared language between engineers and stakeholders.
RelationshipImplemented as
One-to-manyFK on the "many" side (most common)
Many-to-manyA junction/join table with two FKs
One-to-oneShared/unique FK — often a sign to merge tables
Crow's-foot marks each end with cardinality (one/many) and optionality (zero/one). Get the relationships right here and the tables, keys, and joins fall out naturally — this is the bridge from requirements to a normalized schema.
The Trap
Model the Invariant, Not the Current Process
The most common schema mistake is not a missing normal form. It is modelling how the business works this year — the approval steps, the two regions, the one product line — instead of what is true about the domain regardless. Processes change every reorganisation; invariants do not, and the schema that encodes the second survives the first.
Process, which will changeInvariant, which will not
manager_approved, finance_approved as columnsAn approvals table: who approved what, when, in which role
email and email_2 on the customerContact methods as rows, with a type and a primary flag
A status column with eleven values the code branches onA state and a transition history, because somebody will ask when it changed
Price on the productPrice on the order line — the price at the time of sale is a fact about the sale, and a product's price changing must not rewrite history
That last row is the one that causes real damage. Storing a price only on the product means last year's revenue moves when somebody edits a price today — and nobody notices, because the report still runs. The general test: if this value changes, should history change with it? If no, it belongs on the transaction, not on the entity.
🔗 SQL (Structured Query Language) Joins — Every Type, and the NULL Traps SQL ▶
Reference
Combining Rows Across Tables
Joins match rows from two tables on a condition. The type decides what happens to rows that don't match — and that's where most bugs live. 
SELECT u.name, o.total
FROM users u
LEFT JOIN orders o ON o.user_id = u.id;   -- keeps users with no orders
JoinReturns
INNEROnly rows that match in both tables
LEFT / RIGHTAll rows from one side; NULLs where no match
FULL OUTERAll rows from both; NULLs on either side
CROSSCartesian product (every combo) — usually a mistake
SELFA table joined to itself (hierarchies, pairs)
Traps: putting a filter on the outer table in WHERE silently turns a LEFT JOIN into an INNER JOIN (put it in the ON instead); and joining on a nullable column drops rows because NULL = NULL isn't true. Watch for fan-out: a one-to-many join multiplies rows and inflates SUM().
Silently wrong
A WHERE on the Right-Hand Table Undoes Your LEFT JOIN
This is the most common wrong answer in SQL and it produces no error at all. A LEFT JOIN keeps unmatched left rows and fills the right side with NULLs. Then a WHERE clause tests one of those NULL columns, NULL is not true, and every unmatched row is filtered straight back out — leaving you with an inner join wearing a left join's syntax.
WrittenWhat you actually get
LEFT JOIN o ON …
WHERE o.status = 'paid'		Inner join. Customers with no order are gone
LEFT JOIN o ON … AND o.status = 'paid'Correct — the filter is part of the match, not applied after
WHERE o.id IS NULLDeliberate anti-join: rows on the left with nothing on the right. This one is on purpose
WHERE o.total > 100Same trap. Any comparison against NULL drops the row
COUNT(o.id) vs COUNT(*)After a LEFT JOIN these differ, and the difference is the unmatched count
How you would notice: run the join with no WHERE and compare row counts. If adding the filter drops your row count to exactly the inner-join count, the LEFT is decorative. The habit that avoids it entirely: filters on the right-hand table belong in ON; filters on the left-hand table belong in WHERE.
🪟 Window Functions — Analytics Without Collapsing Rows SQL ▶
Reference
Rankings, Running Totals & Row-to-Row Math
GROUP BY collapses rows; window functions compute across a set of rows while keeping every row. The OVER() clause defines the "window" (partition + order). 
SELECT name, dept, salary,
  RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS rnk,
  SUM(salary) OVER (PARTITION BY dept) AS dept_total
FROM employees;
FunctionUse
ROW_NUMBER / RANK / DENSE_RANKOrdering & top-N per group
LAG / LEADCompare to the previous/next row (deltas, growth)
SUM/AVG OVERRunning totals & moving averages
NTILEBuckets/percentiles
Killer use: "top 3 earners per department" or "each order vs the customer's previous order" — one query, no self-joins. Window functions are the single biggest jump from beginner to intermediate SQL (Structured Query Language).
Silently wrong
The Default Frame Is RANGE, and Ties Collapse Into One Bucket
SUM(x) OVER (ORDER BY d) looks like a running total and usually is one — until the ORDER BY column has duplicates. The default frame is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, and RANGE means “all rows with the same ordering value”, so every tied row gets the same total — the total after all of them. Two sales on the same date both show the day’s closing figure.
FrameMeaning
RANGE … CURRENT ROW (the default)All peer rows sharing the current ordering value are included
ROWS … CURRENT ROWExactly the rows up to this one. This is the running total people mean
No ORDER BY in the OVERThe frame is the whole partition — a group total, not a running one
ROW_NUMBER vs RANK vs DENSE_RANKTies: arbitrary distinct numbers, gaps after ties, no gaps
LAG(x) across a partition boundaryNULL, not the previous partition's last value — usually what you want, occasionally not
How you would notice: look for repeated values in a running-total column. Identical consecutive totals for rows with different amounts is the signature. Write ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW explicitly whenever you mean a running total — it costs eight words and removes the entire class of error.
🧱 CTEs (Common Table Expression) & Recursion — Readable, Composable Queries SQL ▶
Reference
Name Your Steps With WITH
A Common Table Expression (WITH) names a subquery so you can build a complex query as readable, stacked steps instead of nested parentheses. Recursive CTEs traverse hierarchies and graphs. 
WITH ranked AS (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY ts DESC) rn
  FROM events
)
SELECT * FROM ranked WHERE rn = 1;   -- latest event per user
Recursive form: an anchor query UNION ALL a step that references the CTE — perfect for org charts, category trees, or "all descendants of X." Readability tip: CTEs make a 60-line query reviewable; deeply nested subqueries don't. (Note: some engines materialize CTEs — check the plan if performance matters.)
The Fingerprint
The CTE Optimization Fence: Readable Steps the Planner Won't Optimize Across
CTEs read as clean, stacked steps — and on some engines that readability has a performance cost the syntax hides. Historically, and still in cases, a CTE is an optimization fence: it is materialised into a temporary result and the planner cannot push a predicate from the outer query into it. So a CTE that scans a million rows, filtered to ten by a WHERE outside it, computes the full million every time — the filter can't reach inside the fence. Older Postgres materialised every CTE; Postgres 12+ inlines simple ones by default, but MATERIALIZED forces the fence back and other engines vary, so the behaviour is not something to assume. The recursive form has its own trap: with no termination or cycle guard, a recursive CTE over a graph with a loop runs forever.
The assumptionThe realityThe check
“A CTE is just a named subquery”On some engines it's a materialised fenceEXPLAIN — is the outer WHERE pushed in?
The outer filter reaches the CTE cheaplyBehind a fence, the CTE computes fully firstFilter inside the CTE, or rely on inlining
A recursive CTE terminatesA cycle in the data loops foreverDepth cap or cycle detection; mind UNION vs UNION ALL
MATERIALIZED for clarityIt re-imposes the fence you may not wantUse it deliberately, not by habit
So use CTEs freely for readability — on a modern engine that inlines them it is usually free — but for a hot query treat the fence as real until EXPLAIN proves otherwise: check that the outer filter reaches inside, push predicates into the CTE when it doesn't, and give every recursive CTE a termination guard. The clean query and the fast query are usually the same on today's planners; the times they diverge are exactly the times a hot path can't afford the difference.
Σ Aggregation — GROUP BY, HAVING & ROLLUP SQL ▶
Reference
Summarizing Rows Into Groups
Aggregate functions (COUNT, SUM, AVG, MIN/MAX) collapse many rows into one per group. GROUP BY defines the groups; HAVING filters after aggregation (unlike WHERE, which filters before). 
SELECT country, COUNT(*) AS n, SUM(total) AS rev
FROM orders
WHERE status = 'paid'          -- filter rows first
GROUP BY country
HAVING SUM(total) > 10000      -- filter groups after
ORDER BY rev DESC;
FeatureDoes
COUNT(*) vs COUNT(col)All rows vs non-NULL values only
COUNT(DISTINCT …)Unique values
ROLLUP / CUBE / GROUPING SETSSubtotals & grand totals in one pass
FILTER (WHERE …)Conditional aggregates (Postgres)
Classic error: selecting a non-aggregated column that isn't in GROUP BY — either group by it or wrap it in an aggregate.
Silently wrong
Join First, Aggregate Second, and SUM Cannot Tell
If a query joins a one-to-many relationship and then aggregates, the “one” side is duplicated once per matching row before SUM ever sees it. The total comes back larger, in a way that looks entirely plausible, and no error is raised because nothing is wrong with the SQL (Structured Query Language). An order joined to three shipments has its value counted three times.
PatternWhat it does to the number
One join, one-to-many, then SUMMultiplies by the number of matches per row
Two such joinsMultiplies by the product — 3 shipments × 2 discounts = 6×
COUNT(col) vs COUNT(*)COUNT(col) skips NULLs. On an outer join that is often the point, and often the bug
AVG(col) with NULLsNULLs are excluded from both the total and the divisor — not treated as zero
SUM over an empty setNULL, not 0. COALESCE(SUM(x), 0) if a caller will do arithmetic on it
How you would notice: aggregate the fact table alone first and compare the total to the joined query’s. If they differ, the join is fanning out. The fix is to aggregate in a subquery or CTE (Common Table Expression) and join to the result, so each row arrives pre-summed — or use SUM(DISTINCT …) only when you can prove the duplicates are exact, which is rarely.
🎯 Subqueries, EXISTS & Set Operations SQL ▶
Reference
Queries Inside Queries
A subquery is a SELECT nested in another statement. It can return a scalar, a list (for IN), or a table. Correlated subqueries reference the outer row and run per-row. 
-- customers who have placed at least one order
SELECT name FROM users u
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
ToolUse
IN / NOT INMembership — but NOT IN + NULLs = no rows (trap!)
EXISTS / NOT EXISTSExistence check — NULL-safe, often faster
UNION / UNION ALLStack result sets (ALL keeps duplicates & is faster)
INTERSECT / EXCEPTRows in both / in one but not the other
Prefer EXISTS over NOT IN whenever the inner column can be NULL — NOT IN (…NULL…) returns nothing, a famously silent bug. Many subqueries also rewrite cleanly as joins or CTEs (Common Table Expression); pick whichever reads clearest.
Silently wrong
NOT IN Against One NULL Returns Zero Rows
WHERE id NOT IN (SELECT customer_id FROM orders) is the single most destructive NULL behaviour in SQL (Structured Query Language). If that subquery returns even one NULL, the comparison becomes unknown for every row, no row satisfies the predicate, and the query returns nothing at all. Not an error — an empty result, which reads as “there are none”.
WrittenWith a NULL in the subquery
x NOT IN (1, 2, NULL)Never true. x <> NULL is unknown, and unknown fails the WHERE
x IN (1, 2, NULL)True if x is 1 or 2 — the NULL is harmless here, which is why the asymmetry surprises people
NOT EXISTS (SELECT 1 …)Correct. Cares whether a row exists, not what is in it
LEFT JOIN … WHERE right.id IS NULLAlso correct, and often the faster plan on large tables
EXCEPT / MINUSCorrect, and treats NULLs as equal — different semantics again
How you would notice: an anti-join that returns exactly zero rows when you expected some is this bug until proven otherwise — check with SELECT COUNT(*) FROM orders WHERE customer_id IS NULL. The habit worth adopting outright: use NOT EXISTS and never NOT IN on a subquery. It is correct whether or not NULLs are present, so you never have to know.
📇 Indexes Explained — B-tree, Hash & Covering Performance ▶
Concept
The Book's Index, for Your Data
An index is a sorted data structure that lets the database find rows without scanning the whole table — the difference between O(log n) and O(n). The cost: every write must also update the index, and indexes take space.
TypeBest for
B-treeThe default — equality & range (=, <, BETWEEN, ORDER BY)
HashEquality only, very fast
GIN / GiSTFull-text, JSONB, arrays, geospatial (Postgres)
CompositeMulti-column — order matters (leftmost-prefix rule)
CoveringIncludes all columns a query needs → index-only scan
Composite key order: an index on (a, b) helps WHERE a=… and WHERE a=… AND b=…, but not WHERE b=… alone. Index the columns you filter/sort on; don't over-index — each one slows writes.
Silently wrong
A UNIQUE Index Does Not Stop Duplicate NULLs
UNIQUE is the constraint people trust most and it has a gap wide enough to drive a data-quality incident through: in standard SQL (Structured Query Language), and in PostgreSQL, MySQL and SQLite, NULL is not equal to NULL, so any number of NULL rows satisfy a unique index. A nullable email column with a unique index will happily hold ten thousand rows with no email.
SituationWhat actually happens
UNIQUE(email), email nullableUnlimited NULL rows. Duplicates only blocked between non-NULL values
SQL ServerThe exception — it permits only one NULL, which surprises people moving the other way
Composite UNIQUE(a, b) with b NULLSame gap, one column further in
The fixNOT NULL, or a partial index: UNIQUE … WHERE email IS NOT NULL plus a check
Related trapA function on the column (WHERE lower(email) = …) skips a plain index — slow, not wrong
How you would notice: one query, and it is worth running against any nullable column you believed was unique: SELECT COUNT(*) FROM t WHERE email IS NULL. If the answer is not zero and you thought the index guaranteed uniqueness, it never did. The general lesson is broader than indexes: every constraint in SQL has a NULL-shaped hole, and the constraint will not tell you.
🔍 Reading Query Plans — EXPLAIN ANALYZE Performance ▶
Reference
Ask the Database What It's Doing
The optimizer turns your SQL (Structured Query Language) into a physical plan. EXPLAIN shows that plan; EXPLAIN ANALYZE actually runs it and shows real timings and row counts. Reading plans is the core skill for fixing slow queries. 
EXPLAIN ANALYZE
SELECT * FROM orders WHERE user_id = 42;
SeeMeans
Seq ScanReading the whole table — often a missing index
Index Scan / Index-OnlyUsing an index (good)
Nested Loop / Hash / Merge JoinThe three join strategies
Rows estimated vs actualBig mismatch = stale statistics → bad plan
Workflow: find the node eating the most time, check if a Seq Scan should be an index, and compare estimated vs actual rows. A huge estimate error usually means ANALYZE (statistics) is out of date.
Silently wrong
EXPLAIN Without ANALYZE Prints the Estimate That Was Wrong
A plan is a prediction, and a slow query is usually slow because the prediction was wrong. Plain EXPLAIN shows you the planner's estimated row counts — the very numbers that produced the bad plan — and nothing about what really happened. Reading it and concluding the plan looks reasonable is agreeing with the mistake.
What to runWhat it tells you
EXPLAINThe plan and the estimates. No execution, no reality
EXPLAIN ANALYZERuns it, and prints estimated vs actual rows per node
EXPLAIN (ANALYZE, BUFFERS)Adds pages read from cache vs disk — where the time actually went
estimate 12, actual 1,240,000This is the finding. Stale statistics, or a correlation the planner cannot see
Nested Loop over a large actual row countThe classic consequence of that estimate, and the reason it is slow
How you would notice: read the plan bottom-up and look only for the largest ratio between estimated and actual rows. That node is the problem; everything above it is a consequence. Then fix the estimate rather than the query — ANALYZE the table, add extended statistics for correlated columns, or index the predicate the planner is guessing about. An EXPLAIN ANALYZE on production- sized data is worth more than any amount of reading the query.
🚀 Query Optimization — Sargability & N+1 Performance ▶
Concept
Write Queries the Index Can Use
A query is sargable ("Search ARGument able") when it can use an index. Wrapping an indexed column in a function or leading a LIKE with a wildcard defeats the index and forces a scan. 
-- NOT sargable: function on the column
WHERE DATE(created_at) = '2026-01-01'
-- sargable: range on the raw column
WHERE created_at >= '2026-01-01' AND created_at < '2026-01-02'
Anti-patternFix
func(col) = xRewrite as a range, or index the expression
LIKE '%foo'Leading wildcard can't use B-tree — use full-text
The N+1 query1 query + N per-row queries → JOIN or batch (IN)
SELECT *Fetch only needed columns → enables covering indexes
The N+1 problem is the #1 app-layer DB (Database) killer (ORMs love to cause it): loading a list, then firing one query per item. Fix by eager-loading with a join or a single WHERE id IN (…).
The Fingerprint
The Query That Was Fast and Went Slow: Stale Statistics and the Plan Flip
Sargability is how you let the planner use an index; the other half of query performance is that the planner's choices rest on statistics that go stale. The optimiser picks a plan from estimated row counts, and when the data grows or its distribution skews, yesterday's estimates send it down a bad plan — the query that ran in milliseconds for months suddenly takes seconds, with no code change, because the planner switched from an index seek to a full scan on numbers that no longer describe the table. Keep statistics fresh (ANALYZE/auto-analyze), and when a plan is wrong, read what the planner actually did rather than guess: EXPLAIN (and EXPLAIN ANALYZE, which runs it) is the only source of truth — it shows the real plan, where the row estimates blow up, and whether the index you added is used at all.
SymptomLikely causeThe move
A once-fast query slowly degradesStale stats; the plan flippedANALYZE; check EXPLAIN for a scan where a seek belongs
The index exists but isn't usedNon-sargable predicate, or stats say a scan is cheaperMake the predicate sargable; refresh stats
Fast in dev, slow in prodProd's data size/skew differsEXPLAIN on prod-like data, not a tiny dev table
“It should use the index”You are guessingRead EXPLAIN ANALYZE — it is not an opinion
So write sargable predicates, then treat EXPLAIN ANALYZE as the instrument you reach for before optimising anything — it replaces a guess about what the database is doing with the fact. And keep statistics current, because the most baffling regressions are not bad queries but good queries the planner stopped understanding once the data moved out from under its estimates.
🚦 Locking & MVCC — Concurrency Without Chaos Internals ▶
Concept
How Readers and Writers Coexist
MVCC (Multi-Version Concurrency Control) is how Postgres/InnoDB let many transactions run at once: writers create new versions of rows instead of overwriting, so readers never block writers and writers never block readers. Each transaction sees a consistent snapshot.
ConceptDetail
Row versionsOld versions kept until no txn needs them
VACUUM (Postgres)Cleans up dead tuples — neglect it and the table bloats
Row vs table locksFOR UPDATE locks specific rows for a write
DeadlockTwo txns wait on each other — DB (Database) kills one; retry it
Avoiding deadlocks: acquire locks in a consistent order and keep transactions short. Explicit locking (SELECT … FOR UPDATE) is how you safely implement "decrement inventory" under concurrency.
The Failure Mode
A Lock Wait Does Not Look Like an Error
This is what makes lock contention expensive to diagnose: the application does not receive a lock error. It receives nothing, for a while, and then a timeout — from the connection pool, the HTTP (HyperText Transfer Protocol) client, or the load balancer, depending on which gives up first. So the alert fires on a component several layers away from the cause, and the first three people to look at it are looking in the wrong place.
What you seeWhat is happening
Latency climbs on one endpoint, then everythingOne slow transaction holds a lock; every request needing that row queues behind it, then the pool is exhausted and unrelated requests queue too
The database looks idle — low processor, low diskWaiting is not work. A blocked system is quiet, which is why resource dashboards say nothing is wrong
It clears the moment you restart somethingThe blocking transaction was killed with its connection, so the evidence went with it
A deadlock error, occasionallyThe lucky case: the database detected a cycle and killed one side, so you get a message naming both statements
The query to know before you need it is the one that lists blocked sessions and their blockers — pg_locks joined to pg_stat_activity in Postgres, sys.innodb_lock_waits in MySQL. And the important half of the answer is the blocker, which is nearly always a transaction left open by application code that did work between BEGIN and COMMIT it did not need to — an HTTP call, a file write, a user waiting on a form.
🍰 Partitioning & Sharding — Scaling One Big Table Scale ▶
Concept
Split the Data When It Won't Fit
Partitioning splits one table into pieces within a single database (by range/list/hash) so queries scan less and old data is easy to drop. Sharding spreads data across multiple databases/servers to scale beyond one machine.

Shard keyChooses which server a row lives on — pick carefully
Cross-shard queries/joinsThe hard part — slow, complex; avoid by design
Order of escalation: optimize queries & indexes → add a read replica → partition → (only then) shard. Sharding adds real operational complexity; a bad shard key causes hotspots and painful re-sharding.
Where it stops
You Partition for Maintenance Long Before You Partition for Speed
The usual reason given for partitioning is query performance, and it is usually not the reason it actually becomes necessary. On a table of a few hundred gigabytes the queries are often fine and the maintenance is not: the vacuum takes all night, the index rebuild needs a window nobody will approve, the backup runs into the working day, and deleting last year's rows locks the table for hours.
OperationWhy partitioning changes it
Deleting old dataDROP PARTITION is instant; DELETE of 200M rows is an outage
Vacuum and index maintenanceRuns per partition, so it fits in a window and can be parallelised
Backups and restoresOlder partitions are immutable, so they need copying once, not nightly
Query performanceOnly improves with partition pruning — the predicate must include the partition key
Sharding across machinesA one-way door. Cross-shard joins, transactions and re-sharding are all now your problem
Partition on the column you will delete by, which is usually time, and which usually also serves pruning. And keep the two decisions apart in your head: partitioning is a local, reversible change to one table's storage; sharding is a distributed system with its own failure modes, and it should follow read replicas, caching, and every query fix — not precede them.

The Decision
JSONB Is a One-Way Convenience — Every Field in It Gives Up What the Engine Guarantees
The verdict warns against JSONB as an excuse to skip schema design; the sharper point is what a field concretely loses by living in a document. A key inside JSONB has no NOT NULL, no type, no foreign key, no default, no check — the database can enforce no invariant on it, which is exactly the guarantee the relational model exists to give. So the moment a field is filtered, joined, or aggregated regularly, it has earned a real column and should graduate to one. Performance sharpens the same line: GIN-indexed containment (@>) is fast, but pulling out a scalar and comparing (->>'x' = …) often can't use that index and scans, and updating a single key rewrites the whole document rather than patching it in place.
SignalWhat it tells you

The document has a fixed, known shapeIt was always a table; JSONB is hiding a schema
Genuinely variable / unknown fields per rowJSONB is the right tool — keep it
Frequent updates to one keyWhole-document rewrite cost — reconsider the shape
So decide per field, not per table: keep in JSONB only what is genuinely variable or write-once-read-rarely, and promote to a typed column anything you filter, join, or constrain — because a column gets you the index, the type, and the invariant, and a JSONB key gets you none of them. “Postgres can do NoSQL” is true; the trap is using it to avoid the schema decision rather than to handle data that genuinely has no schema.

The Fingerprint
“Looser SQL” Was a Data-Integrity Landmine — and MariaDB Is No Longer a Drop-In Twin
Two things behind the polite table rows deserve saying plainly. First, MySQL's historical permissiveness was not a quirk — it was the database breaking the one promise you use a database for: without strict mode an out-of-range number was silently clamped, an over-long string truncated, an invalid '0000-00-00' date accepted, a value coerced into the wrong type rather than rejected — so the store you trusted to enforce integrity quietly corrupted it. Modern versions default to strict mode, but a migrated database or an old config can still run permissive, and the failure is invisible until you find the truncated data months later. Second, MySQL and MariaDB have genuinely diverged: a drop-in fork once, they now differ in JSON (JavaScript Object Notation) handling, features and version numbering — the choice is real, and tooling that assumes one may not work on the other.
The trapWhat historically happenedThe fix

Where it stops
Concurrent Writers, Not Size — the Limit Is Not the One People Assume

🌊 Connection Pooling — Surviving Many Clients Ops ▶
Concept
Why Your DB Falls Over Under Load
Each database connection costs memory and a backend process. Open one per request and a traffic spike (or a serverless fleet) opens thousands, exhausting the server. A connection pool reuses a small, fixed set of connections.
LayerDetail
App-side poolHikariCP, pgx, SQLAlchemy — reuse connections per app
PgBouncerExternal pooler; transaction mode multiplexes many clients
ServerlessFunctions × requests = connection storm → use a pooler/proxy
Sizing: more connections isn't faster — past a point they just contend. A good pool is often just (cores × 2) + spindles, not hundreds. Connection exhaustion presents as timeouts under load; the fix is pooling, not a bigger max_connections.
The Decision
Sizing It — Why a Smaller Pool Is Usually Faster
The instinct under load is to raise the pool size, and it makes things worse past a point that arrives earlier than anyone expects. A database serves queries with a finite number of cores and disks; connections beyond that do not add capacity, they add contention — context switches, lock waits, and a scheduler dividing the same work into more, smaller pieces.
QuestionAnswer
How big should the pool be?Start near (cores × 2) + effective spindles and measure. Two-digit numbers, not three
Why does raising it help for ten minutes?Queueing moved from your application into the database, where it is less visible. Total throughput did not change
What if I have fifty application instances?Fifty small pools still sum to one large one. This is where an external pooler earns its place
Transaction mode or session mode?Transaction mode multiplexes far better and forbids session state — prepared statements, temp tables, SET. Choose it deliberately, because the failure is a confusing runtime error rather than a config warning
Serverless?Instances × concurrency, with no coordination between them. A pooler is not optional here, it is the architecture
The relationship between pool size and latency is the queueing one, not a linear one: utilisation past roughly 80% buys wait time rather than throughput, and the knee is steep. A pool sized to keep the database busy but not saturated finishes the same work sooner than one sized to keep every request from ever queuing.
🗂️ The NoSQL Landscape — Four Families NoSQL ▶
Concept
Not "No SQL (Structured Query Language)" — "Not Only SQL"
NoSQL databases relax the relational model to gain scale, flexibility, or a shape that fits a specific access pattern. They usually trade strong consistency and rich joins for horizontal scalability (the CAP trade-off).
FamilyModelExample
Key-ValueSimple map — fastest lookupsRedis, DynamoDB
DocumentJSON-like docs, flexible schemaMongoDB, Couchbase
Wide-ColumnRows with dynamic columns, huge scaleCassandra, Bigtable

Choosing: pick NoSQL for a specific reason — massive scale, a document-shaped domain, or graph traversal — not to avoid SQL. Most apps are still best served by a relational database; "boring technology" wins more often than not.
The Fingerprint
The Expensive Mistake Is Choosing the Store Before You Know the Queries
The four families sort neatly by data shape, which makes the choice look like a modelling decision. It is not — it is a query decision, and the costly error is picking the store for how the data looks and discovering, months in, the questions it cannot answer. Key-value is a hash map: blazing by key, useless for “find all X where Y”. Document stores tempt you to embed everything, then you need to join across documents and rebuild joins in application code — slowly, and without transactions. Wide-column scales without limit but forces the table to be modelled around one query, so a second access pattern means a second copy of the data. Each family is a bet on the questions you will ask, and the bet is hard to unwind.
FamilyThe query it punishes
Key-valueAnything but “get by exact key” — no scans, no secondary lookups unless you build the index yourself
DocumentCross-document joins — rebuilt in app code, without the database's help or its transactions
Wide-columnA second access pattern — the table is shaped for one query; another means denormalising a second copy
GraphAggregations and bulk scans — it is built to walk relationships, not to sum a column
So the honest sequence is queries first, store second: write down the questions the system must answer and how often, then pick the family that serves the hot ones cheaply — accepting the rare ones will be awkward. Relational stays the default precisely because it defers that commitment: you can ask it something you did not plan for. Choosing on data shape alone is how you end up running a second datastore to answer the question the first one made expensive.
🍃 MongoDB — Documents & the Aggregation Pipeline Document ▶
Reference
Store the Object, Not the Rows
MongoDB stores flexible JSON-like documents in collections. It shines when your data is naturally nested and your access pattern reads whole objects — no joins to reassemble them. 
// find + aggregate
db.orders.aggregate([
  { $match: { status: "paid" } },
  { $group: { _id: "$country", revenue: { $sum: "$total" } } },
  { $sort: { revenue: -1 } }
])
Schema design: model around access patterns — embed data you read together, reference data you read separately. Add indexes just like SQL (Structured Query Language). Modern Mongo has ACID (Atomicity, Consistency, Isolation, Durability) multi-document transactions, but they signal you may have wanted relational.
Watch out: unbounded array growth, and treating it as schemaless forever — inconsistent documents become a nightmare. Enforce a schema at the app (or with schema validation).
Where it stops
The Moment Your Access Pattern Needs a Join
Document databases are excellent when the document *is* the unit of access: fetch one, render it, write it back. The limit arrives when the same data has to be read a second way — by a field inside a nested array, or joined to another collection — because the embedding that made the first access pattern fast is what makes the second one hard.
SignalWhat it means
$lookup appearing in your pipelinesYou are doing joins in the application tier's database. Consider whether the model is relational
The same fact duplicated in many documentsDenormalisation is the design; the cost is updating every copy, correctly, forever
A document growing without boundArrays that append per event hit the 16 MB document limit. Model as a separate collection
Transactions across collectionsSupported since 4.0, and slower than the single-document case. Frequent use is a modelling signal
Aggregations that scan everythingIndexes must match the pipeline's first stages, or $match reads the collection
The honest test before choosing it: write down the three queries this data must answer. If they all start from the same identifier and return one document, a document store fits beautifully. If any of them start somewhere else, that query is either a second copy of the data or a join, and a relational model handles both without a decision. PostgreSQL's JSONB is also worth weighing here — document storage inside a database that can still join.

🕸️ Graph Databases — When Relationships Are the Data Graph ▶
Reference
Traversals Instead of Joins
A graph database stores nodes and relationships as first-class citizens. Questions that need many-hop joins in SQL (Structured Query Language) ("friends of friends who like X") become natural, fast traversals. 
// Neo4j Cypher: mutual connections
MATCH (me:Person {name:"Ann"})-[:KNOWS]->(f)-[:KNOWS]->(fof)

RETURN fof.name, count(*) ORDER BY count(*) DESC
Great forExample
NetworksSocial graphs, org charts
Recommendations"People who bought… also…"
Fraud / securityAttack-path & ring detection (cf. BloodHound)
The relationship is stored directly, so a traversal is a pointer-hop, not a join — performance stays flat as hops increase. Use a graph DB (Database) when connections are the primary query; otherwise a relational DB is simpler.
Where it stops
Two Hops Is a Join. Five Is a Graph.
The question is not whether the data has relationships — all relational data does — but how deep and how variable the traversals are. A relational join across two or three tables is fast and well understood. It is the queries where the depth is not known in advance, or is large, where the cost curves cross: each additional hop multiplies the work in SQL and is roughly constant in a graph engine.
Query shapeRight tool
One or two hops, known depthSQL. A join is the answer; a graph database is overhead
“Shortest path between A and B”Graph. Expressing this in SQL requires recursion and gets slow quickly
“Everything within N hops”, N variableGraph — this is the canonical case
Recursive CTE (Common Table Expression) in PostgresThe honest middle ground, and often enough. Try it before adopting a second database
Aggregations over the whole datasetNot a graph strength. Most graph engines are poor analytical databases
Two established uses justify the second database on their own: fraud rings and access-path analysis — and the second is exactly what BloodHound & SharpHound — Attack-Path Graphing does to Active Directory, which is a graph problem wearing a security hat. For everything else, start with a recursive CTE and adopt a graph engine when it stops finishing.
↔️ OLTP (Online Transaction Processing) vs OLAP (Online Analytical Processing) — Rows vs Columns Analytics ▶
Concept

OLTP (transactional) handles many small reads/writes of whole rows — your app database. OLAP (analytical) scans huge numbers of rows over a few columns — your reporting warehouse. Their opposite needs drive opposite storage.

Silently wrong
The Update Is the Problem, Not the Query — Why a Column Store Hates Your Write Pattern
The read story is well known; the write story is what surprises people migrating. Columnar engines store values of one column together, compressed, in large immutable blocks — so updating a single row means rewriting or shadowing an entire block, and doing that a thousand times a second is pathological. Most cloud warehouses respond by making single-row UPDATE and DELETE legal but expensive, and by charging for the scan they need to find the row. A team that migrates an application table into the warehouse "because analytics live there" discovers this as a bill rather than as an error.

Keep the application on a row store, stream changes into the warehouse, and let each do the job its storage layout was built for — the mechanics of that stream are in Change Data Capture — Reading the Database's Own Diary. And in a column store, stop writing SELECT *: it is the one habit that converts the fastest engine you have into the slowest.

🏞️ Warehouse vs Lake vs Lakehouse Analytics ▶
Concept
Where Analytical Data Lives
Three architectures for storing analytical data, each solving the previous one's limitation. The lakehouse is the current convergence.

The Decision
The Lakehouse Is Not the Default — Most Structured Data Still Belongs in a Warehouse
The lakehouse is pitched as the convergence everyone should adopt, and for a lake estate drowning in ungoverned Parquet it genuinely is the upgrade. But read the usual pitch — warehouse features on cheap open storage — and it hides two costs. First, the table format is a real commitment: Iceberg, Delta and Hudi are not interchangeable, and the engine and catalogue ecosystem around each differs, so “open” still means choosing a camp. Second, the flexibility is operational work you now own — compaction, the small-file problem, catalogue and metadata management — that a managed warehouse simply does for you. If your data arrives structured and your scale fits a managed warehouse's pricing, the warehouse is not the legacy option you are meant to grow out of; it is the lower-total-cost answer.

Concept

🔀 Schema Migrations — Zero-Downtime Change DBA ▶
Concept
Changing the Schema While Live
Schema changes are code changes and must be versioned, reviewed, and reversible. The hard part is altering a big table without locking it or breaking the currently-running app version.
Tool / IdeaDetail
Migration toolsFlyway, Liquibase, Alembic, Rails — versioned, ordered scripts
Expand/contractAdd new → backfill → switch → remove old (multi-deploy)
Locking DDL (Data Definition Language)Some ALTERs rewrite/lock the table — check first
Online toolsgh-ost, pt-online-schema-change for big MySQL tables
Golden rule: every migration must be backward-compatible with the currently-deployed code, because during a rollout both versions run at once. "Add a nullable column, deploy, backfill, then enforce" beats a single locking change. Always have a rollback.
The Decision
The Migration That Looks Instant Is the One That Takes the Site Down
Expand/contract is the known-safe shape; the step teams actually get wrong is judging which single statement is safe to run live — and the dangerous migration is the one that looks trivial. Adding a column with a non-null default on an older engine, or creating an index without the concurrent option, takes a full-table lock and stalls every query against that table for as long as the rewrite runs: seconds in staging on a small table, minutes of hard downtime in production on a large one. The incident's fingerprint is always the same — it passed review and passed staging, because staging's copy of the table was small. And the contract half is asymmetric: adding a nullable column is reversible, but dropping a column or table destroys data you cannot un-drop.
StepThe hazard staging's small table hides
Add column with a non-null defaultOn older engines it rewrites the whole table under a lock — add nullable, backfill, then enforce
Create an indexWithout the CONCURRENTLY/online variant it blocks writes for the build — always use the online form on a live table
Backfill a columnOne UPDATE over millions of rows holds a single long transaction — batch it in chunks
Drop a column or tableNot reversible — the data is gone; make it a separate, late, independently-revertible deploy
So the golden rule has a second half: backward-compatible with running code and separately reversible at every step — because the migration that fails is rarely the scary-looking one you tested carefully. It is the one-line ALTER that looked instant on a table a thousand times smaller than production.
🛡️ Database Security — Least Privilege & RLS Security ▶
Reference
Protecting the Crown Jewels
The database is the highest-value target. Defense is layered: control who connects, what they can touch, and protect the data at rest and in transit. Ties directly to the security domain.
ControlDetail
Least-privilege rolesApp user ≠ superuser; separate read/write/migration roles

And of course: parameterized queries to stop SQL (Structured Query Language) injection (the app's job), and network isolation so the DB (Database) is never internet-facing. Column-level encryption/masking protects PII (Personally Identifiable Information) even from DB admins.
The Fingerprint
RLS Is the Multi-Tenant Backstop Everyone Reaches For — and Its Bypass Footguns Are Where Tenants Leak
Row-Level Security is the right instinct for multi-tenant isolation — it pushes the “which rows can this request see” filter into the database, so no forgotten WHERE in the app leaks another tenant's data. But it has sharp edges that turn “isolation on” into “isolation off” silently. The table owner and superusers bypass RLS by default: an app that connects as the table's owner gets no filtering at all — the classic “RLS is enabled but not working” — and the fix is FORCE ROW LEVEL SECURITY plus a non-owner app role. The policy is only as trustworthy as the session state it keys on: RLS typically filters by a current-tenant value set with set_config, so any path that forgets to set it breaks isolation. And it is not free — RLS adds a predicate to every query, so a policy that can't use an index taxes every read.
The footgunWhat happensThe fix
App connects as the table ownerOwner bypasses RLS — all tenants visibleNon-owner role + FORCE ROW LEVEL SECURITY
Forgotten tenant set_configPolicy filters on an unset variable — leak or emptySet tenant context centrally, on every checkout
Policy predicate isn't sargableRLS on every query becomes a scanDesign the policy around an indexed tenant column
Treating RLS as the only controlOne bypass and isolation is goneKeep app-side scoping too — RLS is defence-in-depth
So use RLS as a genuine backstop — it catches the query that forgot to filter — but treat it as defence-in-depth, not the whole defence: a non-owner role with FORCE, the tenant context set centrally so no path can forget, an index on the filtered column, and app-side scoping kept in place. The failure mode is never “RLS rejected a valid query”; it is “RLS silently let everything through” — which you can't see until one tenant sees another's data.

🏗️ Designing a Schema From Requirements Craft ▶
Walkthrough
From "We Sell Stuff" to Tables
A repeatable process turns fuzzy requirements into a sound schema. Example: an e-commerce order system.
StepDo
1. Find nounsCustomer, Product, Order, OrderItem, Payment → entities
2. RelationshipsOrder has many OrderItems; OrderItem → one Product
3. Keys & typesPKs, FKs, pick types & constraints (money as decimal!)
4. Normalize to 3NFEach fact once; no update anomalies
5. Index for accessAdd indexes for the real queries

Snapshot the price: an OrderItem stores the price at time of sale, not a live FK to Product.price — a classic modeling insight. Design OLTP (Online Transaction Processing) for correctness; derive OLAP from it.
The Fingerprint
The Noun List Misses Two Things That Bite: Point-in-Time Facts and the Join Table
The noun-first walkthrough is right, and it reliably misses two things that surface only later, in production. The first the card hints at with the price snapshot, but it is a general principle: some facts are point-in-time and must be captured, not referenced. The price at sale, the address a package shipped to, the tax rate applied — model any as a live foreign key to a row that can change, and a later edit silently rewrites history. Ask of every value: must this be true as-of when it happened, or is the current value fine? — and copy the former into the record. The second miss is structural: “find the nouns” almost never surfaces the many-to-many relationships, because they are not nouns — a student enrols in many courses and a course has many students needs its own join table, and the tell that it was an entity all along is that the join carries attributes (the enrolment date, the grade).
The trapThe fingerprintThe fix
Reference a value that should be frozenOld orders “change price” when the product is editedSnapshot point-in-time facts into the record
Miss a many-to-manyYou bolt a comma-separated list into one columnA join table — many-to-many is never one column
Ignore a join table's own attributesNowhere to put “enrolment date” or “grade”The join was an entity; give it its own columns
Over-normalise the read pathA 3NF-perfect schema, slow reportingDerive a denormalised OLAP model; keep OLTP clean
So run the noun process, then run two passes it does not: mark every value that must survive a change to its source and snapshot it, and turn every “many of these relate to many of those” into a table you can later hang attributes on. The price snapshot is not a special case to memorise; it is the visible corner of the rule that OLTP models facts as-of the moment they were true.

TechniqueDetail

Silently wrong
Yesterday's Number Changes, and Nobody Reruns the Report
Two things make time-series totals quietly wrong, and both look like correct queries. The first is the time zone: grouping by day in UTC (Coordinated Universal Time) when the business means local time moves every event near midnight into the wrong day, and the daily total is off by hours of traffic. CauseEffect on the number

🌊 Streaming & Event Pipelines — Delivery Guarantees and the Lies About Time Analytics ▶
Concept
A Log You Read Rather Than a Queue You Drain
The mental model that makes streaming systems make sense is not a queue. It is an append-only log with a cursor per reader. Nothing is consumed — reading does not remove anything, and each consumer group tracks its own position independently. That single design choice explains almost every property people find surprising: several teams can read the same events for different purposes, a broken consumer can be rewound and replayed, and a slow reader falls behind rather than blocking anyone else. 
partition 0:  [e0][e1][e2][e3][e4][e5][e6][e7][e8] ← producers append here
                            ▲              ▲
                     analytics (3)   fraud check (7)   ← independent cursors

Ordering is guaranteed *within a partition*, and nowhere else.
Key choice decides partition, so key choice decides what stays ordered.
That last line is the design decision that matters most. Events for one account stay in order only if the account id is the partition key. Choose a random key for even distribution and you have traded away every ordering guarantee — usually without noticing until a "balance updated" arrives before the "account created".
Reference
Delivery Guarantees, and What "Exactly Once" Really Means
The three-way choice is usually presented as a dial you set. It is closer to a statement about where you put the work.
GuaranteeMechanismYou get
At most onceCommit the position before processingLoss on a crash. Acceptable for metrics, never for money
At least onceCommit the position after processingDuplicates on a crash. The default, and the right default
Exactly onceTransactional writes inside one system, or idempotent consumersReal within the boundary of a single system, and an aspiration across two
The practical answer is at-least-once plus an idempotent consumer, which is to say: make reprocessing the same event harmless. An upsert keyed on an event id, a natural key, or a deduplication window does this and survives every failure mode. Chasing end-to-end exactly-once across a broker, a job and an external API (Application Programming Interface) means building distributed transactions, and the idempotent version is smaller, cheaper and easier to reason about.
Concept
Two Clocks, and Why Windows Are Hard
Every streaming bug that takes a week to find is a confusion between when something happened and when it arrived. They are always different and occasionally different by hours.
ClockIsUse it for

Ingestion timeWhen the broker accepted itA compromise; deterministic on replay, which event time is not always
Windowing by processing time is trivial and wrong: a replay produces different numbers than the original run, which makes the pipeline unauditable. Windowing by event time is correct and forces a question with no clean answer — how long do you wait for stragglers? A phone that was offline for six hours will send you Tuesday's events on Wednesday.

🔁 Change Data Capture — Reading the Database's Own Diary Analytics ▶
Concept
Every Database Already Writes Down Every Change
Getting data out of a production database into a warehouse usually starts with a query on a schedule, and it is the wrong shape from the first day. Change data capture takes a different route: the database already maintains a durable, ordered record of every committed change, because replication and crash recovery depend on it. CDC (Change Data Capture) reads that log instead of the tables — the write-ahead log in PostgreSQL, the binary log in MySQL, the transaction log in SQL (Structured Query Language) Server — and turns it into a stream of inserts, updates and deletes.
ApproachHowWhat it misses
Query on a timestampWHERE updated_at > last_runDeletes, entirely. Rows that changed twice. Rows whose updated_at the application forgot to set

The deletes row is the one that quietly ruins warehouses. A timestamp-based load can never learn that a row is gone, so cancelled orders stay counted, closed accounts stay active, and the numbers drift upward forever in a way that looks like growth.
Concept
Snapshot, Then Stream — the Part That Is Actually Hard
The log only contains changes since the log started. To build a copy of a table you need its current contents plus every change from a precisely known point, and joining those two without a gap or an overlap is the whole engineering problem. 
1. note the current log position          ← the seam
2. snapshot the table (consistent read)
3. start streaming changes from (1)
4. apply — the snapshot may be stale, the stream will correct it

Which is why every CDC sink must be idempotent: step 4 will replay
changes that step 2 already contains, on purpose.

CDC is often sold as non-invasive, and operationally it is. Architecturally it is the opposite: it publishes the source system's internal schema to everyone downstream.

🧬 Data Lineage & Contracts — Where the Number Came From, and Who Promised It Analytics ▶
Concept
Two Questions That Consume Most of a Data Team's Week
Ask anyone who runs a data platform what they actually spend time on and the answer is two questions, asked constantly and answered by hand. "Where did this number come from?" — someone disputes a figure and the only way to answer is to read the query, then the query that fed it, then the job that loaded that. And "what breaks if I change this?" — a column is being renamed and nobody can say who depends on it, so either the change is blocked forever or it ships and something falls over.
Lineage answers both mechanically. It is the graph of what feeds what: source tables, transformations, models, dashboards, and the edges between them. And the reason it matters is not tidiness — it is that without it, both questions are answered by whoever has been there longest, which is a staffing dependency dressed up as a knowledge one.

Three Grades of Lineage, and What Each Is Good For
GradeGranularityAnswersCost
Table-levelThis table feeds that tableImpact analysis, and roughly where a failure came fromCheap — parse the SQL (Structured Query Language), or read the orchestrator's dependency graph
Column-levelThis column feeds that column, through these expressions"Which of the forty columns actually break if I drop this one?"Needs real SQL parsing per dialect; increasingly available in tooling
Row-level / provenanceThis specific value came from these specific inputsRegulated reporting and forensic disputesExpensive, rarely justified outside finance and pharma
Table-level lineage that is automatically derived beats column-level lineage that is maintained by hand, every time. Hand-drawn diagrams are accurate on the day they are drawn and misleading within a quarter — and a lineage graph nobody trusts is worse than none, because people check it, find it wrong once, and stop.
Concept
The Contract Is the Half Lineage Cannot Supply
Lineage tells you what is connected. It says nothing about what anyone promised — and the recurring failure in data platforms is not a missing graph, it is that a producing team never agreed to anything and had no way to know they had broken someone.
A data contract statesExample
Schema, with types and nullabilityorder_id: string, not null — and that adding a column is allowed while removing one is not
SemanticsWhat status = 'complete' means, in business terms. The field most often skipped and most often the cause of the argument
Freshness"Available within 30 minutes of the event, 99% of days"
Volume expectationsNormal daily range, so a silent collapse to zero is a violation rather than a Tuesday
OwnershipA named team, reachable, who answer for it
Change policyHow much notice, and by what channel. This is the clause the whole thing exists for
A contract only works if it is enforced where the data is produced. Checked in the warehouse, it is a report that the damage already happened. Checked in the producer's own pipeline — a schema test that fails their build — it stops the change before it ships, which is the only version anyone actually benefits from.
Concept
Why This Keeps Failing as a Documentation Project
Most organisations attempt this at least once as a catalogue exercise, and the shape of the failure is consistent enough to predict.
AttemptWhy it decays
A spreadsheet of every table and its ownerCorrect for a month. Nothing in anyone's workflow updates it, and nobody notices it has stopped being true
A wiki page of pipeline diagramsSame, plus the diagrams are prettier, so they are trusted longer after they stop being right
A catalogue tool bought and populated onceThe population was the project. Nothing repopulates it
Lineage derived from the code that runsCannot drift, because it is generated from the same definitions that execute. This is the only version that survives contact with a busy quarter
The general principle is the one this site keeps arriving at from different directions: documentation that is not derived from the thing it documents will diverge from it, and the divergence is invisible until somebody relies on it. Metric definitions have the same property, which is why The Semantic Layer & Metrics puts them in version-controlled code rather than in a glossary, and why Data Quality & Observability tests freshness rather than asserting it.
Concept
Starting Small, Where It Actually Pays
Neither of these is worth a platform programme. Both are worth doing narrowly, around the things that already hurt.
StepWhy start here
Derive table lineage for the pipelines you already haveUsually a day's work from the orchestrator's own graph, and it answers the impact question immediately

The measure of success is unglamorous and specific: how long it takes to answer "where did this number come from" for a figure you did not build. If that is still an afternoon of reading SQL, no amount of catalogue coverage has moved the thing that was costing you.
🗜️ LSM Trees — Turning Random Writes Into Sequential Ones DATA • Storage Engines ▶
The Inversion
Never Update in Place — Only Ever Append
A B-tree, the structure under most relational indexes, updates records where they live. That keeps reads fast and makes every write a random seek to the right page — cheap on a small dataset, punishing when writes arrive faster than a disk can seek. A log-structured merge tree refuses to update in place at all: every write is appended to memory and to a log, and the sorted files on disk are never modified, only replaced. It converts a storm of random writes into a stream of sequential ones — the single access pattern every storage medium is fastest at.
StepWhat happens
WriteAppended to an in-memory memtable and a write-ahead log — no seek, no disk read
FlushFull memtable is written out as an immutable, sorted file (an SSTable)
ReadCheck the memtable, then each level of sorted files, newest first — several places, not one
CompactionBackground merge of sorted files, dropping superseded and deleted keys
This is the engine under Cassandra, RocksDB, LevelDB and many time-series and event stores — exactly the write-heavy workloads that make a B-tree thrash. The append-only design is also why a delete is not a removal but a tombstone: a marker that says “this key is gone,” carried until compaction can finally drop it.
The Fingerprint
You Pay for Cheap Writes in Read and Space Amplification
Nothing is free; the LSM tree moves the cost, it does not remove it. Because a key can live in several sorted files at once, a read may have to look in all of them — read amplification — which is why LSM engines lean on Bloom filters to skip files that cannot contain the key. And compaction rewrites data repeatedly (write amplification) and keeps superseded copies until it runs (space amplification), which is why an LSM database's disk use and I/O (Input/Output) can spike when compaction kicks in.
B-treeLSM tree
WritesRandom, in placeSequential, append-only
ReadsOne place — fast, predictableSeveral levels — needs Bloom filters
Best workloadRead-heavy, point updatesWrite-heavy, ingest & time-series
The taxWrite amplification on random writesRead & space amplification; compaction spikes
You cannot minimise read, write and space amplification all at once — improving one worsens another, and the storage engine's tuning is a choice of which two to favour. That trade is the whole reason both structures exist and neither won: Indexes Explained — B-tree, Hash & Covering is the read-optimised default; this is its write-optimised opposite.
The Decision
Choose by the Write-to-Read Ratio, Not by Fashion
LSM is not “the modern, better” structure and B-tree the legacy one — they are two answers to opposite questions. A workload dominated by point lookups and in-place updates (a classic transactional database) is a B-tree's home ground; a workload dominated by high-volume ingest that is rarely updated (metrics, logs, event streams, a write-heavy wide-column store) is an LSM's.
Ask what the access pattern actually is — writes versus reads, appends versus updates, point lookups versus scans — and let that pick the engine, because the choice is baked deep into a database and expensive to reverse. It is the same divide Cassandra & DynamoDB — Wide-Column at Scale lands on from the distributed-database side: write-optimised storage is what makes their ingest rates possible.
🕸️ Data Mesh — Domain-Owned Data as a Product, and When It Is the Wrong Answer DATA • Architecture ▶
The Inversion
The Bottleneck Is Not Your Warehouse. It Is the Central Team That Owns It.
Warehouse, lake and lakehouse all answer where data lives. Data mesh answers a different question — who owns it — and the problem it names is organisational, not technical. A single central data team becomes the bottleneck for every domain's data, deeply understanding none of them, and the backlog grows without bound. Data mesh inverts the ownership: each business domain owns its data as a product — discoverable, addressable, documented, with an SLA (Service Level Agreement) — served through a self-serve platform under federated rather than central governance. It is a decentralisation of ownership, not a new storage engine.
PrincipleWhat it actually asks of you
Domain ownershipThe team that knows the data owns it end to end — pipeline included
Data as a productAn owner, an SLA, docs and quality — treated like a published API (Application Programming Interface), not a table
Self-serve data platformSo domains can publish without a platform engineer per pipeline
Federated computational governanceGlobal standards enforced by the platform, not by a central gatekeeper
The unit of change is org structure plus product thinking, and the “mesh” is the network of domain-owned data products that results — not a tool you install.
The Fingerprint
It Is an Org Restructure Sold as an Architecture — and That Is Where It Goes Wrong
The failure mode is adopting the word without the org change. A team that stands up “data products” but keeps central ownership, or decentralises ownership without a self-serve platform, gets the worst of both worlds — the coordination cost of decentralisation and the bottleneck of centralisation at once, now with more moving parts. Data mesh only pays off at a scale where the central team is genuinely the bottleneck and the domains genuinely have the maturity and headcount to own data products, which describes a small number of large organisations. Below that scale, the coordination overhead exceeds the bottleneck it removes.
Mesh pays off only if…and fails when…
Many domains, each with real data expertise and headcountOne or two domains, or domains with no one to own a product
The central team is a provable, measured bottleneckThe pain is actually scattered, low-quality data
A platform team can deliver genuine self-serve“Self-serve” is a wiki and good intentions
Leadership will carry the org changeOnly the data team wanted it
The honest test is which pain you have: if it is the central team's backlog, the mesh helps; if it is your data being scattered and untrustworthy, the mesh makes that worse before better — and most organisations have the second problem.
The Decision
Most Teams Need a Lakehouse and Clear Ownership, Not a Mesh
The reach-for-mesh mistake is treating it as the modern default. It is not — it is a specific answer to a specific scaling pain that most organisations do not have yet. For the majority, the right move is the storage architecture plus data-product discipline — documentation, SLAs, quality, a named owner — applied within a central or hub-and-spoke team. You get most of “data as a product” without the organisational upheaval.
So the decision is about scale and pain, not fashion. Adopt the mesh's principles — treat data as a product, give it an owner and an SLA — always; adopt its full decentralisation only when a central team is provably the bottleneck and the domains can genuinely carry ownership. Reach for a lakehouse for where the data lives — the choice Warehouse vs Lake vs Lakehouse lays out — and reach for a mesh only when who owns it is the thing that is broken.
