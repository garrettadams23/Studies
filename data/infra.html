🧾 Windows Server Editions & Licensing — What You Are Actually Buying Server • Licensing ▶
The decision
Standard vs Datacenter Is a Virtualisation Question, Not a Feature Question
People assume Datacenter is "the one with the good features". For almost every role that matters — AD DS (Active Directory Domain Services), DNS (Domain Name System), DHCP (Dynamic Host Configuration Protocol), file services — the two editions are identical. What you are buying is how many Windows virtual machines that hardware may run. Choose on VM density, then check the handful of features that genuinely differ.
StandardDatacenter
Virtual instances per licensed host 2 Unlimited
AD DS, DNS, DHCP, file, print Yes Yes
Storage Spaces Direct No Yes
Software-defined networking No Yes
Typical fit Physical box, or a host running one or two VMs A virtualisation host, or anything hyper-converged
The verdict: if a host will ever run more than about four Windows VMs, Datacenter usually costs less than stacking Standard licences — and you stop having to count. Below that, Standard. Get this wrong in the direction of Standard and you are not merely under-licensed, you are under-licensed retroactively, which is how licensing turns into an audit finding.
Core counting
Licensing Follows Cores, and There Is a Floor
Windows Server is licensed per physical core, with minimums that catch people out: you license every physical core in the host, at least 8 per processor and at least 16 per server, regardless of how few you use. A 2× 6-core host is still billed as 16 cores. Licences are sold in 2-core packs, so the arithmetic is always even.
The trap is hardware refresh. Moving a workload from an 8-core box to a 32-core box does not carry the licence with it — the new host needs double the core licences before the first VM boots. Price the licence alongside the tin, not after it.
The forgotten half
CALs (Client Access License) — Licensing the Connection, Not the Server
Core licences let the server run. CALs let something connect to it. They are bought separately, they are frequently forgotten, and they are the single most common finding in a Microsoft licensing review.
ModelBuy one perCheaper when
User CALNamed person, any number of devicesPeople have a laptop, a phone and a desktop
Device CALNamed device, any number of usersShift workers share a terminal or a shop-floor PC
External connectorServer, for unlimited external usersAnonymous or public-facing access
The verdict: count your CALs by whichever number is smaller — people or devices — and remember that Remote Desktop Services needs its own CAL on top of the Windows Server CAL. Two separate purchases for one session.
Failure mode
Evaluation Media That Quietly Expires
Evaluation installs run for 180 days and then begin shutting down hourly. It is a reliable source of a mystifying outage roughly six months after someone stood up a "temporary" server. Check what you are running before it tells you: 
# Which edition and how many days are left?
slmgr /dlv

# Evaluation to full: list targets, then convert (needs a reboot)
DISM /Online /Get-TargetEditions
DISM /Online /Set-Edition:ServerStandard /ProductKey:XXXXX-XXXXX-XXXXX-XXXXX-XXXXX /AcceptEula
A domain controller cannot be edition-converted in place. If the expiring server is a DC, you promote a replacement, transfer the roles, and demote the old one — which is a far longer evening than the one you were planning.
⬛ Server Core — Why You Would Remove the GUI (Graphical User Interface), and How You Manage It Anyway Server • Installation ▶
The trade
A Smaller Server Is a Smaller Target and a Shorter Patch Queue
Server Core is Windows Server without the desktop shell, Explorer, Edge, or most of the management consoles. The argument for it is not disk space. It is that code you did not install cannot be exploited and does not need patching — fewer components means fewer monthly reboots and a materially smaller attack surface.
Server CoreDesktop Experience
Local managementCommand line, sconfigFull GUI
Attack surfaceSmallerLarger
Patch/reboot frequencyLowerHigher
Vendor agent supportCheck first — some installers need a GUIAssumed
Good fitDC (Domain Controller), DNS (Domain Name System), DHCP (Dynamic Host Configuration Protocol), file, Hyper-V hostAnything with a vendor GUI console
The verdict: infrastructure roles that you administer remotely anyway are the easy yes. The blocker is almost never Windows — it is a third-party agent, backup client or line-of-business installer that assumes a desktop. Test the agents before committing the estate.
One-way door
You Cannot Switch Between Them After Installation
In Windows Server 2012 and 2012 R2 you could add and remove the GUI at will. That was removed in 2016 and has not returned. On any currently supported release, choosing Core or Desktop Experience at install time is permanent — changing your mind means a rebuild.
This is worth treating as a genuine one-way door: decide per role, write the decision into the build documentation, and default to Desktop Experience only where an agent actually requires it.
Local admin
sconfig, and the Handful of Commands Worth Memorising
A freshly built Core box needs enough local configuration to become remotely manageable — then you never sign in locally again. sconfig is a menu that covers most of it. 
# The menu that covers naming, domain join, networking, updates, remote management
sconfig

# Or do it directly in PowerShell
Rename-Computer -NewName DC03 -Restart
Add-Computer -DomainName corp.example.com -Restart
Enable-PSRemoting -Force

# Lost the command prompt entirely? This brings it back.
# (Task Manager -> File -> Run new task -> cmd)
The last one is not a joke. Closing the only console window on a Core box leaves you staring at a blank blue screen with no way in, and it is the first thing that happens to everyone exactly once.
Remote by default
Manage It From Somewhere Else — That Was Always the Point
Server Core is not "harder to manage". It is a server you manage the way you should have been managing the others: remotely, from an administrative workstation, over PowerShell remoting or with the graphical consoles pointed at it. 
# Interactive session on the remote server
Enter-PSSession -ComputerName DC03

# Fan out one command across many servers at once
Invoke-Command -ComputerName DC01,DC02,DC03 -ScriptBlock {
    Get-Service ADWS | Select-Object PSComputerName, Status
}
Once every server is administered this way, the presence or absence of a local GUI stops being a meaningful distinction — which is the actual argument for Core, and the reason it reads as difficult only to teams still signing in at the console.
🛠️ Server Manager, RSAT (Remote Server Administration Tools) & Windows Admin Center — Which Console Wins Server • Tooling ▶
Choosing
Three Overlapping Tools, Each Best at One Thing
These are not generations of the same product, and the newest does not replace the others. They overlap awkwardly, and knowing which to reach for saves more time than knowing any one of them deeply.
Server ManagerRSATWindows Admin Center
What it is Built-in role and server dashboard The classic MMC (Microsoft Management Console) snap-ins, installed on your workstation Browser-based gateway to many servers
Best at Adding roles; a quick health glance Deep object work — AD (Active Directory) users, DNS (Domain Name System) zones, GPOs (Group Policy Object) Day-to-day ops across a fleet; managing Core
Weak at Anything at scale Fleet views; needs a domain-joined workstation Niche AD tasks the classic snap-ins still own
Runs on The server, or your workstation Your workstation only A gateway server or your workstation
The verdict: install RSAT on your admin workstation and use it for AD, DNS and Group Policy work — the snap-ins remain the most complete tools for those objects. Use Windows Admin Center for everything fleet-shaped: patching status, certificates, event logs, remote PowerShell, and anything on Server Core. Use Server Manager to install a role and then close it.
Getting RSAT
RSAT Ships With Windows Now — Stop Downloading It
RSAT used to be a separate download matched to your exact Windows build. Since Windows 10 1809 it is a Feature on Demand built into the OS (Operating System), which means no download, no version mismatch, and one command. 
# See what is available and what is already installed
Get-WindowsCapability -Name RSAT* -Online | Select-Object Name, State

# The three most people actually want
Add-WindowsCapability -Online -Name Rsat.ActiveDirectory.DS-LDS.Tools~~~~0.0.1.0
Add-WindowsCapability -Online -Name Rsat.GroupPolicy.Management.Tools~~~~0.0.1.0
Add-WindowsCapability -Online -Name Rsat.Dns.Tools~~~~0.0.1.0
In a managed estate this is frequently blocked, because Features on Demand are pulled from Windows Update and the policy points at an internal update server that does not carry them. If the command fails with an 0x800f0954, that is the cause — the fix is a policy exception, not a download.
Failure mode
The Admin Workstation Is the Real Attack Surface
Every one of these tools concentrates domain-wide authority onto whatever machine you installed it on. A workstation that reads email, browses the web and holds Domain Admin tooling is the single most valuable target in the estate, and compromising it skips every other step of an intrusion.
The standard mitigation is a privileged access workstation: a separate, hardened machine with no mail client and no general browsing, used only for administration. Where that is not affordable, the minimum is a separate admin account that never signs in to a daily-driver machine. See Tiered Administration in the Security domain for the model this belongs to.
🧩 Roles & Features — What Installing a Role Actually Changes Server • Configuration ▶
The distinction
A Role Is a Job; a Feature Is a Capability
A role is what the server is for — domain controller, DNS (Domain Name System) server, file server. A feature supports a role or the administrator: failover clustering, .NET, the management tools. The practical difference is that roles usually open ports and start listening, and features usually do not.
Adding a role is therefore never only a software install. It typically creates service accounts, opens firewall rules, registers service principal names, writes new event log channels, and may add a scheduled task. That is why "just add the role to see" is a poor instinct on a production box — removing it afterwards does not reliably undo all of it.
Doing it
Install It in PowerShell So It Is Repeatable
# What is installed, and what could be?
Get-WindowsFeature | Where-Object Installed

# Install a role with its management tools (omit the switch on a server
# you manage remotely — the tools belong on your workstation, not here)
Install-WindowsFeature -Name AD-Domain-Services -IncludeManagementTools

# Capture a known-good server's feature set, then reproduce it elsewhere
Get-WindowsFeature | Where-Object Installed | Export-Clixml .\baseline.xml
Install-WindowsFeature -ConfigurationFilePath .\baseline.xml
The GUI (Graphical User Interface) and the cmdlet do the same work, but only one of them leaves a record you can diff, review and re-run. Build servers from a script even when you build them once — the second server always arrives eventually.
Failure mode
Role Creep, and the Server Nobody Dares Reboot
Servers accumulate roles because adding one to an existing box is faster than building a new one. The result is the machine that is somehow a domain controller, a file server, a print server and a licensing server — and therefore cannot be patched without scheduling four separate teams.
Keep domain controllers doing one job. A DC holds every password hash in the domain; every additional role on it is another way in, and every additional service is another reason someone objects to the reboot. If a server needs an explanation of what it does, it has too many roles.
🛡️ Server Hardening Baseline — The Short List That Removes Most Risk Server • Hardening ▶
Priorities
Six Things, Roughly in Order of Return
Hardening guides run to hundreds of settings and are mostly ignored because of it. This is the short list — the items that remove the most attacker options per hour spent. Do these before opening a benchmark document.
Do thisBecause
Deploy LAPS Randomises the local administrator password per machine. Kills lateral movement by reused local credentials, which is the most common way one compromised host becomes all of them
Never browse or read mail from a server Free, and removes the two most common initial-access paths in one decision
Install only the roles the server needs Every role is listening code and another patch dependency
Turn on an audit policy that logs something useful Default auditing will not tell you what happened. Logon events, account management, and process creation with command line are the minimum
Separate admin accounts from daily-driver accounts Stops a phished user session from being a domain-admin session
Patch on a schedule you actually keep A predictable monthly window beats an ambitious weekly one that slips
The verdict: LAPS first. It is the cheapest single control here and it breaks the technique that turns one workstation into the whole domain.
Baselines
Do Not Write Your Own — Start From a Published One
Microsoft's Security Compliance Toolkit and the CIS (Center for Internet Security) Benchmarks both publish server baselines as importable GPO (Group Policy Object) backups. Starting from one and documenting your exceptions is far better than assembling settings by hand, because the exceptions become the thing you review rather than the whole configuration.
Apply a baseline to a pilot OU first. Baselines routinely break older line-of-business applications by disabling legacy protocols and weak ciphers — which is the point of them, and also why they need a controlled rollout rather than a domain-wide link on a Friday.
Failure mode
Hardening That Was Never Verified
A baseline linked at the domain root is not evidence that it applied. Group Policy can be blocked, filtered out by a missing security group, or beaten by a more specific GPO — and none of that reports itself. Verify on a real machine: 
# What did this machine actually receive? Read the "Denied" reasons, not just Applied.
gpresult /h C:\rsop.html /f

# Is auditing on where you think it is?
auditpol /get /category:*

# Is LAPS actually storing a password for this computer object?
Get-LapsADPassword -Identity SRV01 -AsPlainText
This is the same lesson as any other control: the configuration you intended and the configuration in force are different claims, and only the second one protects anything.
🧱 AD DS (Active Directory Domain Services) Boundaries — When to Add an OU, a Domain, or a Forest AD DS • Design ▶
Orientation
The Objects Are Covered Elsewhere; This Is the Decision
What a forest, domain and OU are — and how they are attacked — is in Active Directory: Structure, Objects & Attacks in the Security domain. This card answers the question that actually lands on an administrator: something needs to be separated, so which boundary do you reach for? Almost always the answer is the cheapest one, and almost always people pick a more expensive one than they need.
BoundaryWhat it actually separatesCost to run
Organisational unit Policy targets and delegated administration Free — make as many as you need
Domain Replication scope, password policy scope, some legacy defaults Its own DCs (Domain Controller), its own trusts, its own backups
Forest Security. This is the only real security boundary A parallel directory in every respect
The verdict: a domain is not a security boundary — a Domain Admin in any domain of a forest can reach every other domain in that forest. If the requirement is "these administrators must never be able to touch that", the answer is a separate forest, and nothing cheaper will do. If the requirement is "different policy" or "different people administer it", the answer is an OU.
Design
Structure the Directory for Delegation and Policy, Not the Org Chart
The most common OU design mirrors the company's departments, and it is the wrong one, because reorganisations then force directory work that has no technical reason to happen. Structure instead by what you do to objects: the two things an OU exists for are attaching Group Policy and delegating rights.
A structure that survives reorganisation usually separates by object type first (workstations, servers, users, service accounts), then by whatever genuinely drives different policy — region, build standard, or regulatory scope. Keep it shallow. Deep nesting makes precedence hard to reason about and gains nothing that a well-named security group could not do.
Failure mode
The Default Containers Are Not OUs
CN=Users and CN=Computers are containers, not organisational units, and Group Policy cannot be linked to them. Anything created without a specified location lands there — which is where every new machine goes when someone joins it to the domain in a hurry.
The result is a machine that silently receives none of your workstation policy. Redirect the defaults once, at build time, and the problem stops existing: 
# Point the default containers at real OUs you control
redircmp "OU=Workstations,DC=corp,DC=example,DC=com"
redirusr "OU=Staff,DC=corp,DC=example,DC=com"

# Find the machines already stranded in the default container
Get-ADComputer -SearchBase "CN=Computers,DC=corp,DC=example,DC=com" -Filter * |
    Select-Object Name, Created
👑 FSMO (Flexible Single Master Operations) Roles — The Five Jobs That Cannot Be Done by Everyone AD DS • Operations ▶
Why they exist
Multi-Master Replication Has Five Exceptions
Active Directory is multi-master: change an object on any domain controller and the change replicates outward. That model breaks for operations where two simultaneous answers would corrupt the directory — handing out the same identifier twice, or two DCs disagreeing about the schema. Those five operations are pinned to a single holder.
RoleScopeDoes whatIf it is down
Schema masterForest Owns schema changes Nothing, until you extend the schema
Domain naming masterForest Adds and removes domains Nothing, until you add a domain
RID (Relative Identifier) masterDomain Issues pools of identifiers for new objects New object creation stops once DCs exhaust their pool
PDC (Primary Domain Controller) emulatorDomain Time authority, password-change target, lockout processing, GPO (Group Policy Object) edit target Noticed within the hour — this is the one that hurts
Infrastructure masterDomain Fixes cross-domain object references Stale names in cross-domain group memberships
The verdict: four of the five can be offline for days without anyone noticing. The PDC emulator cannot — it anchors domain time, and Kerberos rejects tickets once clocks drift past the tolerance. When someone reports "nobody can log in", check the PDC emulator and check time.
The one that matters
Transfer Is Routine; Seize Is a Decision You Cannot Undo
Transfer is a graceful handover between two running DCs — use it for maintenance and decommissioning, and it is entirely routine. Seizing is for a holder that is never coming back. It tells the forest a role has moved without the old holder's agreement.
The rule after a seizure is absolute: the old holder must never be brought back online. Two DCs believing they hold the same role produces divergence that is far worse than the outage you were fixing. Wipe it, do not boot it. 
# Who holds what, right now
netdom query fsmo
Get-ADDomain | Select-Object PDCEmulator, RIDMaster, InfrastructureMaster
Get-ADForest | Select-Object SchemaMaster, DomainNamingMaster

# Graceful transfer
Move-ADDirectoryServerOperationMasterRole -Identity DC02 -OperationMasterRole PDCEmulator

# Seizure — only when the old holder is gone for good
Move-ADDirectoryServerOperationMasterRole -Identity DC02 -OperationMasterRole PDCEmulator -Force
Note that the same cmdlet does both, and the only difference is -Force. Read the command twice before running it.
Placement
Where to Put Them, and the RID Pool Nobody Watches
For most organisations the defaults are fine: leave the roles where the first DC put them, keep the two forest roles together, and put the PDC emulator on a well-connected DC in the main site. Complexity here buys very little.
The one number worth monitoring is the RID pool. Each domain has a finite supply of relative identifiers, and while exhaustion is rare, it is unrecoverable in the sense that the fix is a domain migration. Scripted account creation that runs in a loop is the usual cause of a sudden jump. 
# How much of the RID space has been issued?
dcdiag /test:ridmanager /v | Select-String "Available RID Pool"
🔄 AD (Active Directory) Replication — How Changes Travel, and Triage When They Stop AD DS • Troubleshooting ▶
The model
Nothing Is Pushed Immediately, and That Is by Design
Each DC (Domain Controller) tracks a monotonic update sequence number per partition. A partner asks "what has changed since the number I last saw from you?", and receives only that delta. This makes replication cheap, and it means a change is never instantly everywhere.
WhereNormal delayPlanned by
Within a siteSeconds — change notification, no scheduleThe KCC (Knowledge Consistency Checker), automatically
Between sites15 minutes by default, and compressedSite links you configure
Urgent changesImmediate, regardless of scheduleAccount lockout, password changes to the PDC (Primary Domain Controller)
The verdict: "the change has not appeared yet" is usually correct behaviour rather than a fault. Before troubleshooting, confirm enough time has passed for the path involved — and remember a user's password change reaches the PDC emulator immediately even when everything else waits.
Triage
Three Commands, in This Order
Replication problems produce vague symptoms — a group membership that will not take, a password that works on one site and not another. Start broad and narrow: 
# 1. One-line summary of every partner link. Look at the failure columns first.
repadmin /replsummary

# 2. Which partition is failing, between which pair, and with what error?
repadmin /showrepl * /csv > repl.csv

# 3. Broad DC health — DNS, services, roles, the SYSVOL share
dcdiag /v /c /e

# Force a sync when you have fixed the cause and want to confirm
repadmin /syncall /AdeP
In practice the root cause is DNS (Domain Name System) far more often than replication itself. A DC that cannot resolve its partners' service records cannot replicate with them, and the error it reports describes the symptom rather than the cause.
Failure mode
The Tombstone Lifetime, and the DC You Left Switched Off
Deletions replicate as tombstones — markers that persist for a fixed lifetime, 180 days on any modern domain. A DC that is offline longer than that has missed the window in which it could learn about those deletions, and Active Directory will refuse to replicate with it rather than resurrect deleted objects.
There is no supported way to talk it round. A DC offline past the tombstone lifetime must be forcibly demoted, its metadata cleaned from the directory, and the server rebuilt and re-promoted. The practical rule: a domain controller is either in service or decommissioned. "Powered off for a while" is not a state AD supports, and the lab DC someone shut down in spring is the usual victim.
🤝 Trusts — Direction, Transitivity & Why They Are Backwards AD DS • Identity ▶
The confusing part
Trust Direction Is the Opposite of Access Direction
This trips up nearly everyone, including people who have configured trusts before. If domain A trusts B, then users in B can access resources in A. Access flows against the arrow. The trusting side is the one giving something up.
Read it as a sentence about credentials rather than a diagram: "A is willing to accept that B has authenticated someone." Whenever a trust seems to be working the wrong way round, it is almost always working correctly and being read backwards.
Types
Four You Will Meet, and What Each Is For
TypeBetweenTransitiveReach for it when
Parent–childDomains in one forestYes, automaticNever — it is created for you
ForestTwo forest rootsYesA merger, or a permanent partnership
ExternalTwo specific domainsNoOne domain needs access, and only that one
ShortcutTwo domains in one forestYesAuthentication is slow across a long referral path
The verdict: prefer external and one-way whenever the requirement allows it. A forest trust is transitive and two-way by default, which means it grants far more than most projects actually asked for — and trusts are rarely revisited once the project that needed them is closed.
Failure mode
SID Filtering Is the Control That Keeps a Trust Survivable
A Kerberos ticket carries the account's security identifiers, including a history field used during migrations. Without filtering, a compromised administrator in a trusted domain can inject an identifier belonging to a privileged group in your domain, and your DCs (Domain Controller) will honour it. That turns a trust into a full privilege path between organisations.
SID filtering discards identifiers that did not originate in the trusted domain, and it is enabled by default on external and forest trusts. It gets disabled during migrations, because SID history is exactly what migrations rely on — and then not re-enabled, which is the failure worth checking for. 
# List trusts and their properties
Get-ADTrust -Filter * | Select-Object Name, Direction, ForestTransitive, SIDFilteringQuarantined

# Inspect and re-enable filtering (quarantine) on a named trust
netdom trust corp.example.com /domain:partner.example.net /quarantine
netdom trust corp.example.com /domain:partner.example.net /quarantine:yes
Audit trusts on a schedule. They outlive the projects that created them, nobody owns them afterwards, and each one is a path into your directory that your own controls do not govern.
🗺️ Sites & Subnets — Why Clients Authenticate Against the Wrong DC (Domain Controller) AD DS • Topology ▶
The mechanism
A Site Is a Subnet List, and That Is How Clients Find a Nearby DC
Active Directory has no map of your network. It knows only what you told it: a site is a named object, and subnets are associated with sites. When a client starts up it looks up its own address, learns which site it is in, and asks for a domain controller in that site.
Sites drive three things: which DC a client authenticates against, how replication is scheduled between locations, and which distributed file system targets a client prefers. All three degrade the same way when the subnet list is wrong.
Failure mode
A Missing Subnet Sends Branch Offices Across the Country
If a client's address matches no defined subnet, AD (Active Directory) cannot place it in a site — so it hands back any domain controller. A new branch office whose subnet nobody added will authenticate against a DC on another continent, and the symptom is not an error but slow logons, slow group policy, and file shares that mysteriously prefer the wrong server.
This is self-diagnosing if you know where to look. Every unmatched client is logged on the domain controller that served it: 
# Clients whose subnet is not defined — NETLOGON logs every one
Get-Content C:\Windows\debug
etlogon.log | Select-String "NO_CLIENT_SITE"

# Which site does this machine think it is in?
nltest /dsgetsite
dcdiag /test:DCGetDcName

# Add the missing subnet
New-ADReplicationSubnet -Name "10.30.7.0/24" -Site "Branch-Leeds"
Make the NETLOGON check routine. It is the cheapest health check in Active Directory, it costs nothing to run, and it silently accumulates every network change nobody told the directory about.
Design
Site Links Describe Cost, Not Bandwidth
A site link says which sites replicate with each other, how often, and at what cost — an arbitrary number where lower means more preferred. It is not measured in anything; it exists so you can express "prefer this path" when more than one route exists. Consistency matters more than the values.
Keep the topology as simple as the network allows. The Knowledge Consistency Checker builds and repairs the replication topology automatically, and hand-crafted connection objects stop it doing that — so they survive as fossils long after the link they were working around was upgraded.
