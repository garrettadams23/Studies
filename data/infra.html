🧾 Windows Server Editions & Licensing — What You Are Actually Buying Server • Licensing ▶
The decision
Standard vs Datacenter Is a Virtualisation Question, Not a Feature Question
People assume Datacenter is "the one with the good features". For almost every role that matters — AD DS (Active Directory Domain Services), DNS (Domain Name System), DHCP (Dynamic Host Configuration Protocol), file services — the two editions are identical. What you are buying is how many Windows virtual machines that hardware may run. Choose on VM density, then check the handful of features that genuinely differ.
StandardDatacenter
Virtual instances per licensed host 2 Unlimited
AD DS, DNS, DHCP, file, print Yes Yes
Storage Spaces Direct No Yes
Software-defined networking No Yes
Typical fit Physical box, or a host running one or two VMs A virtualisation host, or anything hyper-converged
The verdict: if a host will ever run more than about four Windows VMs, Datacenter usually costs less than stacking Standard licences — and you stop having to count. Below that, Standard. Get this wrong in the direction of Standard and you are not merely under-licensed, you are under-licensed retroactively, which is how licensing turns into an audit finding.
Core counting
Licensing Follows Cores, and There Is a Floor
Windows Server is licensed per physical core, with minimums that catch people out: you license every physical core in the host, at least 8 per processor and at least 16 per server, regardless of how few you use. A 2× 6-core host is still billed as 16 cores. Licences are sold in 2-core packs, so the arithmetic is always even.
The trap is hardware refresh. Moving a workload from an 8-core box to a 32-core box does not carry the licence with it — the new host needs double the core licences before the first VM boots. Price the licence alongside the tin, not after it.
The forgotten half
CALs (Client Access License) — Licensing the Connection, Not the Server
Core licences let the server run. CALs let something connect to it. They are bought separately, they are frequently forgotten, and they are the single most common finding in a Microsoft licensing review.
ModelBuy one perCheaper when
User CALNamed person, any number of devicesPeople have a laptop, a phone and a desktop
Device CALNamed device, any number of usersShift workers share a terminal or a shop-floor PC
External connectorServer, for unlimited external usersAnonymous or public-facing access
The verdict: count your CALs by whichever number is smaller — people or devices — and remember that Remote Desktop Services needs its own CAL on top of the Windows Server CAL. Two separate purchases for one session.
Failure mode
Evaluation Media That Quietly Expires
Evaluation installs run for 180 days and then begin shutting down hourly. It is a reliable source of a mystifying outage roughly six months after someone stood up a "temporary" server. Check what you are running before it tells you: 
# Which edition and how many days are left?
slmgr /dlv

# Evaluation to full: list targets, then convert (needs a reboot)
DISM /Online /Get-TargetEditions
DISM /Online /Set-Edition:ServerStandard /ProductKey:XXXXX-XXXXX-XXXXX-XXXXX-XXXXX /AcceptEula
A domain controller cannot be edition-converted in place. If the expiring server is a DC, you promote a replacement, transfer the roles, and demote the old one — which is a far longer evening than the one you were planning.
⬛ Server Core — Why You Would Remove the GUI (Graphical User Interface), and How You Manage It Anyway Server • Installation ▶
The trade
A Smaller Server Is a Smaller Target and a Shorter Patch Queue
Server Core is Windows Server without the desktop shell, Explorer, Edge, or most of the management consoles. The argument for it is not disk space. It is that code you did not install cannot be exploited and does not need patching — fewer components means fewer monthly reboots and a materially smaller attack surface.
Server CoreDesktop Experience
Local managementCommand line, sconfigFull GUI
Attack surfaceSmallerLarger
Patch/reboot frequencyLowerHigher
Vendor agent supportCheck first — some installers need a GUIAssumed
Good fitDC (Domain Controller), DNS (Domain Name System), DHCP (Dynamic Host Configuration Protocol), file, Hyper-V hostAnything with a vendor GUI console
The verdict: infrastructure roles that you administer remotely anyway are the easy yes. The blocker is almost never Windows — it is a third-party agent, backup client or line-of-business installer that assumes a desktop. Test the agents before committing the estate.
One-way door
You Cannot Switch Between Them After Installation
In Windows Server 2012 and 2012 R2 you could add and remove the GUI at will. That was removed in 2016 and has not returned. On any currently supported release, choosing Core or Desktop Experience at install time is permanent — changing your mind means a rebuild.
This is worth treating as a genuine one-way door: decide per role, write the decision into the build documentation, and default to Desktop Experience only where an agent actually requires it.
Local admin
sconfig, and the Handful of Commands Worth Memorising
A freshly built Core box needs enough local configuration to become remotely manageable — then you never sign in locally again. sconfig is a menu that covers most of it. 
# The menu that covers naming, domain join, networking, updates, remote management
sconfig

# Or do it directly in PowerShell
Rename-Computer -NewName DC03 -Restart
Add-Computer -DomainName corp.example.com -Restart
Enable-PSRemoting -Force

# Lost the command prompt entirely? This brings it back.
# (Task Manager -> File -> Run new task -> cmd)
The last one is not a joke. Closing the only console window on a Core box leaves you staring at a blank blue screen with no way in, and it is the first thing that happens to everyone exactly once.
Remote by default
Manage It From Somewhere Else — That Was Always the Point
Server Core is not "harder to manage". It is a server you manage the way you should have been managing the others: remotely, from an administrative workstation, over PowerShell remoting or with the graphical consoles pointed at it. 
# Interactive session on the remote server
Enter-PSSession -ComputerName DC03

# Fan out one command across many servers at once
Invoke-Command -ComputerName DC01,DC02,DC03 -ScriptBlock {
    Get-Service ADWS | Select-Object PSComputerName, Status
}
Once every server is administered this way, the presence or absence of a local GUI stops being a meaningful distinction — which is the actual argument for Core, and the reason it reads as difficult only to teams still signing in at the console.
🛠️ Server Manager, RSAT (Remote Server Administration Tools) & Windows Admin Center — Which Console Wins Server • Tooling ▶
Choosing
Three Overlapping Tools, Each Best at One Thing
These are not generations of the same product, and the newest does not replace the others. They overlap awkwardly, and knowing which to reach for saves more time than knowing any one of them deeply.
Server ManagerRSATWindows Admin Center

Weak at Anything at scale Fleet views; needs a domain-joined workstation Niche AD tasks the classic snap-ins still own

The verdict: install RSAT on your admin workstation and use it for AD, DNS and Group Policy work — the snap-ins remain the most complete tools for those objects. Use Windows Admin Center for everything fleet-shaped: patching status, certificates, event logs, remote PowerShell, and anything on Server Core. Use Server Manager to install a role and then close it.
Getting RSAT
RSAT Ships With Windows Now — Stop Downloading It
RSAT used to be a separate download matched to your exact Windows build. Since Windows 10 1809 it is a Feature on Demand built into the OS (Operating System), which means no download, no version mismatch, and one command. 
# See what is available and what is already installed
Get-WindowsCapability -Name RSAT* -Online | Select-Object Name, State

# The three most people actually want
Add-WindowsCapability -Online -Name Rsat.ActiveDirectory.DS-LDS.Tools~~~~0.0.1.0
Add-WindowsCapability -Online -Name Rsat.GroupPolicy.Management.Tools~~~~0.0.1.0
Add-WindowsCapability -Online -Name Rsat.Dns.Tools~~~~0.0.1.0
In a managed estate this is frequently blocked, because Features on Demand are pulled from Windows Update and the policy points at an internal update server that does not carry them. If the command fails with an 0x800f0954, that is the cause — the fix is a policy exception, not a download.
Failure mode
The Admin Workstation Is the Real Attack Surface
Every one of these tools concentrates domain-wide authority onto whatever machine you installed it on. A workstation that reads email, browses the web and holds Domain Admin tooling is the single most valuable target in the estate, and compromising it skips every other step of an intrusion.
The standard mitigation is a privileged access workstation: a separate, hardened machine with no mail client and no general browsing, used only for administration. Where that is not affordable, the minimum is a separate admin account that never signs in to a daily-driver machine — the smallest useful version of the tiered-administration model.
🧩 Roles & Features — What Installing a Role Actually Changes Server • Configuration ▶
The distinction
A Role Is a Job; a Feature Is a Capability
A role is what the server is for — domain controller, DNS (Domain Name System) server, file server. A feature supports a role or the administrator: failover clustering, .NET, the management tools. The practical difference is that roles usually open ports and start listening, and features usually do not.
Adding a role is therefore never only a software install. It typically creates service accounts, opens firewall rules, registers service principal names, writes new event log channels, and may add a scheduled task. That is why "just add the role to see" is a poor instinct on a production box — removing it afterwards does not reliably undo all of it.
Doing it
Install It in PowerShell So It Is Repeatable
# What is installed, and what could be?
Get-WindowsFeature | Where-Object Installed

# Install a role with its management tools (omit the switch on a server
# you manage remotely — the tools belong on your workstation, not here)
Install-WindowsFeature -Name AD-Domain-Services -IncludeManagementTools

# Capture a known-good server's feature set, then reproduce it elsewhere
Get-WindowsFeature | Where-Object Installed | Export-Clixml .\baseline.xml
Install-WindowsFeature -ConfigurationFilePath .\baseline.xml
The GUI (Graphical User Interface) and the cmdlet do the same work, but only one of them leaves a record you can diff, review and re-run. Build servers from a script even when you build them once — the second server always arrives eventually.
Failure mode
Role Creep, and the Server Nobody Dares Reboot
Servers accumulate roles because adding one to an existing box is faster than building a new one. The result is the machine that is somehow a domain controller, a file server, a print server and a licensing server — and therefore cannot be patched without scheduling four separate teams.
Keep domain controllers doing one job. A DC holds every password hash in the domain; every additional role on it is another way in, and every additional service is another reason someone objects to the reboot. If a server needs an explanation of what it does, it has too many roles.
🛡️ Server Hardening Baseline — The Short List That Removes Most Risk Server • Hardening ▶
Priorities
Six Things, Roughly in Order of Return
Hardening guides run to hundreds of settings and are mostly ignored because of it. This is the short list — the items that remove the most attacker options per hour spent. Do these before opening a benchmark document.
Do thisBecause
Deploy LAPS Randomises the local administrator password per machine. Kills lateral movement by reused local credentials, which is the most common way one compromised host becomes all of them
Never browse or read mail from a server Free, and removes the two most common initial-access paths in one decision

The verdict: LAPS first. It is the cheapest single control here and it breaks the technique that turns one workstation into the whole domain.
Baselines
Do Not Write Your Own — Start From a Published One
Microsoft's Security Compliance Toolkit and the CIS (Center for Internet Security) Benchmarks both publish server baselines as importable GPO (Group Policy Object) backups. Starting from one and documenting your exceptions is far better than assembling settings by hand, because the exceptions become the thing you review rather than the whole configuration.
Apply a baseline to a pilot OU first. Baselines routinely break older line-of-business applications by disabling legacy protocols and weak ciphers — which is the point of them, and also why they need a controlled rollout rather than a domain-wide link on a Friday.
Failure mode
Hardening That Was Never Verified
A baseline linked at the domain root is not evidence that it applied. Group Policy can be blocked, filtered out by a missing security group, or beaten by a more specific GPO — and none of that reports itself. Verify on a real machine: 
# What did this machine actually receive? Read the "Denied" reasons, not just Applied.
gpresult /h C:\rsop.html /f

# Is auditing on where you think it is?
auditpol /get /category:*

# Is LAPS actually storing a password for this computer object?
Get-LapsADPassword -Identity SRV01 -AsPlainText
This is the same lesson as any other control: the configuration you intended and the configuration in force are different claims, and only the second one protects anything.
🧱 AD DS (Active Directory Domain Services) Boundaries — When to Add an OU, a Domain, or a Forest AD DS • Design ▶
Orientation
The Objects Are Covered Elsewhere; This Is the Decision
What a forest, domain and OU are — and how they are attacked — is in Active Directory — Structure, Objects & Attacks in the Security domain. This card answers the question that actually lands on an administrator: something needs to be separated, so which boundary do you reach for? Almost always the answer is the cheapest one, and almost always people pick a more expensive one than they need.
BoundaryWhat it actually separatesCost to run
Organisational unit Policy targets and delegated administration Free — make as many as you need
Domain Replication scope, password policy scope, some legacy defaults Its own DCs (Domain Controller), its own trusts, its own backups
Forest Security. This is the only real security boundary A parallel directory in every respect
The verdict: a domain is not a security boundary — a Domain Admin in any domain of a forest can reach every other domain in that forest. If the requirement is "these administrators must never be able to touch that", the answer is a separate forest, and nothing cheaper will do. If the requirement is "different policy" or "different people administer it", the answer is an OU.
Design
Structure the Directory for Delegation and Policy, Not the Org Chart
The most common OU design mirrors the company's departments, and it is the wrong one, because reorganisations then force directory work that has no technical reason to happen. Structure instead by what you do to objects: the two things an OU exists for are attaching Group Policy and delegating rights.
A structure that survives reorganisation usually separates by object type first (workstations, servers, users, service accounts), then by whatever genuinely drives different policy — region, build standard, or regulatory scope. Keep it shallow. Deep nesting makes precedence hard to reason about and gains nothing that a well-named security group could not do.
Failure mode
The Default Containers Are Not OUs
CN=Users and CN=Computers are containers, not organisational units, and Group Policy cannot be linked to them. Anything created without a specified location lands there — which is where every new machine goes when someone joins it to the domain in a hurry.
The result is a machine that silently receives none of your workstation policy. Redirect the defaults once, at build time, and the problem stops existing: 
# Point the default containers at real OUs you control
redircmp "OU=Workstations,DC=corp,DC=example,DC=com"
redirusr "OU=Staff,DC=corp,DC=example,DC=com"

# Find the machines already stranded in the default container
Get-ADComputer -SearchBase "CN=Computers,DC=corp,DC=example,DC=com" -Filter * |
    Select-Object Name, Created
👑 FSMO (Flexible Single Master Operations) Roles — The Five Jobs That Cannot Be Done by Everyone AD DS • Operations ▶
Why they exist
Multi-Master Replication Has Five Exceptions
Active Directory is multi-master: change an object on any domain controller and the change replicates outward. That model breaks for operations where two simultaneous answers would corrupt the directory — handing out the same identifier twice, or two DCs disagreeing about the schema. Those five operations are pinned to a single holder.
RoleScopeDoes whatIf it is down
Schema masterForest Owns schema changes Nothing, until you extend the schema
Domain naming masterForest Adds and removes domains Nothing, until you add a domain
RID (Relative Identifier) masterDomain Issues pools of identifiers for new objects New object creation stops once DCs exhaust their pool
PDC (Primary Domain Controller) emulatorDomain Time authority, password-change target, lockout processing, GPO (Group Policy Object) edit target Noticed within the hour — this is the one that hurts
Infrastructure masterDomain Fixes cross-domain object references Stale names in cross-domain group memberships
The verdict: four of the five can be offline for days without anyone noticing. The PDC emulator cannot — it anchors domain time, and Kerberos rejects tickets once clocks drift past the tolerance. When someone reports "nobody can log in", check the PDC emulator and check time.
The one that matters
Transfer Is Routine; Seize Is a Decision You Cannot Undo
Transfer is a graceful handover between two running DCs — use it for maintenance and decommissioning, and it is entirely routine. Seizing is for a holder that is never coming back. It tells the forest a role has moved without the old holder's agreement.
The rule after a seizure is absolute: the old holder must never be brought back online. Two DCs believing they hold the same role produces divergence that is far worse than the outage you were fixing. Wipe it, do not boot it. 
# Who holds what, right now
netdom query fsmo
Get-ADDomain | Select-Object PDCEmulator, RIDMaster, InfrastructureMaster
Get-ADForest | Select-Object SchemaMaster, DomainNamingMaster

# Graceful transfer
Move-ADDirectoryServerOperationMasterRole -Identity DC02 -OperationMasterRole PDCEmulator

# Seizure — only when the old holder is gone for good
Move-ADDirectoryServerOperationMasterRole -Identity DC02 -OperationMasterRole PDCEmulator -Force
Note that the same cmdlet does both, and the only difference is -Force. Read the command twice before running it.
Placement
Where to Put Them, and the RID Pool Nobody Watches
For most organisations the defaults are fine: leave the roles where the first DC put them, keep the two forest roles together, and put the PDC emulator on a well-connected DC in the main site. Complexity here buys very little.
The one number worth monitoring is the RID pool. Each domain has a finite supply of relative identifiers, and while exhaustion is rare, it is unrecoverable in the sense that the fix is a domain migration. Scripted account creation that runs in a loop is the usual cause of a sudden jump. 
# How much of the RID space has been issued?
dcdiag /test:ridmanager /v | Select-String "Available RID Pool"
🔄 AD (Active Directory) Replication — How Changes Travel, and Triage When They Stop AD DS • Troubleshooting ▶
The model
Nothing Is Pushed Immediately, and That Is by Design
Each DC (Domain Controller) tracks a monotonic update sequence number per partition. A partner asks "what has changed since the number I last saw from you?", and receives only that delta. This makes replication cheap, and it means a change is never instantly everywhere.
WhereNormal delayPlanned by
Within a siteSeconds — change notification, no scheduleThe KCC (Knowledge Consistency Checker), automatically
Between sites15 minutes by default, and compressedSite links you configure
Urgent changesImmediate, regardless of scheduleAccount lockout, password changes to the PDC (Primary Domain Controller)
The verdict: "the change has not appeared yet" is usually correct behaviour rather than a fault. Before troubleshooting, confirm enough time has passed for the path involved — and remember a user's password change reaches the PDC emulator immediately even when everything else waits.
Triage
Three Commands, in This Order
Replication problems produce vague symptoms — a group membership that will not take, a password that works on one site and not another. Start broad and narrow: 
# 1. One-line summary of every partner link. Look at the failure columns first.
repadmin /replsummary

# 2. Which partition is failing, between which pair, and with what error?
repadmin /showrepl * /csv > repl.csv

# 3. Broad DC health — DNS, services, roles, the SYSVOL share
dcdiag /v /c /e

# Force a sync when you have fixed the cause and want to confirm
repadmin /syncall /AdeP
In practice the root cause is DNS (Domain Name System) far more often than replication itself. A DC that cannot resolve its partners' service records cannot replicate with them, and the error it reports describes the symptom rather than the cause.
Failure mode
The Tombstone Lifetime, and the DC You Left Switched Off
Deletions replicate as tombstones — markers that persist for a fixed lifetime, 180 days on any modern domain. A DC that is offline longer than that has missed the window in which it could learn about those deletions, and Active Directory will refuse to replicate with it rather than resurrect deleted objects.
There is no supported way to talk it round. A DC offline past the tombstone lifetime must be forcibly demoted, its metadata cleaned from the directory, and the server rebuilt and re-promoted. The practical rule: a domain controller is either in service or decommissioned. "Powered off for a while" is not a state AD supports, and the lab DC someone shut down in spring is the usual victim.
🤝 Trusts — Direction, Transitivity & Why They Are Backwards AD DS • Identity ▶
The confusing part
Trust Direction Is the Opposite of Access Direction
This trips up nearly everyone, including people who have configured trusts before. If domain A trusts B, then users in B can access resources in A. Access flows against the arrow. The trusting side is the one giving something up.
Read it as a sentence about credentials rather than a diagram: "A is willing to accept that B has authenticated someone." Whenever a trust seems to be working the wrong way round, it is almost always working correctly and being read backwards.
Types
Four You Will Meet, and What Each Is For
TypeBetweenTransitiveReach for it when
Parent–childDomains in one forestYes, automaticNever — it is created for you
ForestTwo forest rootsYesA merger, or a permanent partnership
ExternalTwo specific domainsNoOne domain needs access, and only that one
ShortcutTwo domains in one forestYesAuthentication is slow across a long referral path
The verdict: prefer external and one-way whenever the requirement allows it. A forest trust is transitive and two-way by default, which means it grants far more than most projects actually asked for — and trusts are rarely revisited once the project that needed them is closed.
Failure mode
SID Filtering Is the Control That Keeps a Trust Survivable
A Kerberos ticket carries the account's security identifiers, including a history field used during migrations. Without filtering, a compromised administrator in a trusted domain can inject an identifier belonging to a privileged group in your domain, and your DCs (Domain Controller) will honour it. That turns a trust into a full privilege path between organisations.
SID filtering discards identifiers that did not originate in the trusted domain, and it is enabled by default on external and forest trusts. It gets disabled during migrations, because SID history is exactly what migrations rely on — and then not re-enabled, which is the failure worth checking for. 
# List trusts and their properties
Get-ADTrust -Filter * | Select-Object Name, Direction, ForestTransitive, SIDFilteringQuarantined

# Inspect and re-enable filtering (quarantine) on a named trust
netdom trust corp.example.com /domain:partner.example.net /quarantine
netdom trust corp.example.com /domain:partner.example.net /quarantine:yes
Audit trusts on a schedule. They outlive the projects that created them, nobody owns them afterwards, and each one is a path into your directory that your own controls do not govern.
🗺️ Sites & Subnets — Why Clients Authenticate Against the Wrong DC (Domain Controller) AD DS • Topology ▶
The mechanism
A Site Is a Subnet List, and That Is How Clients Find a Nearby DC
Active Directory has no map of your network. It knows only what you told it: a site is a named object, and subnets are associated with sites. When a client starts up it looks up its own address, learns which site it is in, and asks for a domain controller in that site.
Sites drive three things: which DC a client authenticates against, how replication is scheduled between locations, and which distributed file system targets a client prefers. All three degrade the same way when the subnet list is wrong.
Failure mode
A Missing Subnet Sends Branch Offices Across the Country
If a client's address matches no defined subnet, AD (Active Directory) cannot place it in a site — so it hands back any domain controller. A new branch office whose subnet nobody added will authenticate against a DC on another continent, and the symptom is not an error but slow logons, slow group policy, and file shares that mysteriously prefer the wrong server.
This is self-diagnosing if you know where to look. Every unmatched client is logged on the domain controller that served it: 
# Clients whose subnet is not defined — NETLOGON logs every one
Get-Content C:\Windows\debug
etlogon.log | Select-String "NO_CLIENT_SITE"

# Which site does this machine think it is in?
nltest /dsgetsite
dcdiag /test:DCGetDcName

# Add the missing subnet
New-ADReplicationSubnet -Name "10.30.7.0/24" -Site "Branch-Leeds"
Make the NETLOGON check routine. It is the cheapest health check in Active Directory, it costs nothing to run, and it silently accumulates every network change nobody told the directory about.
Design
Site Links Describe Cost, Not Bandwidth
A site link says which sites replicate with each other, how often, and at what cost — an arbitrary number where lower means more preferred. It is not measured in anything; it exists so you can express "prefer this path" when more than one route exists. Consistency matters more than the values.
Keep the topology as simple as the network allows. The Knowledge Consistency Checker builds and repairs the replication topology automatically, and hand-crafted connection objects stop it doing that — so they survive as fossils long after the link they were working around was upgraded.
📜 Group Policy Architecture — Where the Settings Actually Live Group Policy • Internals ▶
Two halves
A GPO Is a Directory Object Plus a Folder, and They Can Disagree
What looks like one object in the management console is stored in two places. The container lives in Active Directory and holds the metadata — version numbers, status, which client-side extensions are involved. The template is a folder in SYSVOL (System Volume) holding the actual settings files.
Group Policy containerGroup Policy template
Lives inThe AD (Active Directory) databaseThe SYSVOL share, named by GUID (Globally Unique Identifier)
HoldsVersion, status, extension listRegistry.pol, scripts, preferences XML (eXtensible Markup Language)
Replicated byAD replicationDFSR (Distributed File System Replication)
Fails asMissing GPO in the consoleGPO applies inconsistently by site
The verdict: these replicate over two independent mechanisms, so they can fall out of step. A policy that works in one office and not another, with no error anywhere, is the signature of SYSVOL replication being behind — not of a policy problem. Check DFSR before re-reading the GPO.
What it writes
Most of Group Policy Is Just Registry Keys With Rules About Them
Administrative template settings compile down to registry values in Registry.pol. What makes them policy rather than configuration is where they land: the four policy branches of the registry, which ordinary applications and users cannot write to, and which are re-applied on a schedule.
This is exactly why a true policy setting cannot be permanently changed by the user — the next refresh puts it back — and why a preference can. It is also why an .admx file is only a description of a setting: it tells the console what to show and which key to write, and installing one changes nothing on its own. 
# The central store — one copy of the templates for the whole domain,
# so every admin console shows the same settings
\\corp.example.com\SYSVOL\corp.example.com\Policies\PolicyDefinitions\

# Without it, each console uses its own local C:\Windows\PolicyDefinitions,
# and settings appear or vanish depending on who opened the editor
Create the central store early. Its absence produces one of the most confusing symptoms in Group Policy: a colleague cannot find the setting you just configured, because their console does not know it exists.
🔢 Processing Order & Precedence — LSDOU (Local, Site, Domain, Organisational Unit), Enforcement & Loopback Group Policy • Precedence ▶
The order
Last Writer Wins, and the Order Is LSDOU
Policies apply in a fixed sequence — Local, Site, Domain, OU — and each pass overwrites conflicting settings from the one before. The nearest OU therefore wins by default, which matches the instinct that specific beats general. Multiple GPOs (Group Policy Object) linked to the same container are applied by link order, lowest number last, so link order 1 wins.
ModifierEffectBeats
Enforced (on a link)Cannot be overridden by anything more specificEverything below it, and Block Inheritance

The verdict: Enforced and Block Inheritance are both escape hatches that make precedence hard to reason about, and they interact — Enforced wins over a block. Use them sparingly and document each one, because the person debugging the resulting behaviour in two years will not guess why they are there.
Two halves again
Computer Settings and User Settings Follow Different Objects
Every GPO has a computer half and a user half, and they are evaluated against different objects in different places. The computer half applies based on where the computer account sits; the user half based on where the user account sits. Linking a GPO with user settings to an OU full of computers does exactly nothing, and reports no error.
Timing differs too: computer policy applies at startup, user policy at sign-in, and both refresh in the background roughly every 90 minutes with a random offset so that an estate does not stampede a DC (Domain Controller). Some settings — drive maps, folder redirection, software installation — only take effect at the full startup or logon event, which is why a change sometimes needs a reboot rather than a refresh.
Loopback
The Setting for "This Machine, Whoever Signs In"
Sometimes user settings should depend on the machine rather than the person: a kiosk, a shared clinical workstation, a terminal server. Loopback processing tells the computer to apply the user half of the GPOs linked to the computer's OU.
ModeWhat the user getsUse when
MergeTheir own user policy, then the machine's user policy on topMostly normal machine, a few local overrides

Loopback is the correct tool for a real requirement and a common cause of "why did this user's settings vanish on that one machine". If a user behaves differently on a particular device and nowhere else, check the device's OU for loopback before anything else.

The verdict: reach for security filtering first — it is free, visible, and understood by everyone. Use item-level targeting when only one drive map or shortcut needs the condition. Treat WMI filtering as a last resort: it is the standard answer to "apply only to laptops", and it is also a per-client query on every refresh that slows logons across the estate.
Failure mode
The Security Filtering Change That Broke Everything in 2016
For a GPO to apply to a user or computer, that object needs both Read and Apply Group Policy. Removing Authenticated Users from security filtering and adding a specific group used to be the standard technique — until a security update made computers require Read access via the computer account itself.
The result: policies that had worked for years silently stopped applying. The fix is to leave Authenticated Users with Read on the delegation tab while restricting Apply to the target group. It looks redundant and it is load-bearing. 
# Check what a GPO is actually scoped to
Get-GPPermission -Name "Laptop Power Settings" -All |
    Select-Object @{n='Who';e={$_.Trustee.Name}}, Permission

# Restore the Read that the 2016 change made mandatory
Set-GPPermission -Name "Laptop Power Settings" -TargetName "Authenticated Users" `
    -TargetType Group -PermissionLevel GpoRead
🎛️ Group Policy Preferences — The Half People Forget Exists Group Policy • Preferences ▶
The distinction
Policies Are Enforced; Preferences Are Set and Let Go
A policy setting is re-applied on every refresh and the interface for it is greyed out. A preference writes an ordinary value that the user can then change — and, depending on the action you chose, it may never be written again.
ActionBehaviourUse for
CreateWrite only if absent; never touch againA default the user may override
ReplaceDelete and recreate every refreshSettings you need to stay correct
UpdateCreate if absent, amend if presentThe usual choice
DeleteRemove itCleaning up a previous mistake
The verdict: "the drive map is not updating" is nearly always Create where Update or Replace was meant. Create fires once and then stays silent forever, which looks exactly like a broken policy.
Security
Never Set Passwords Through Preferences — MS14-025
Preferences could once set local account passwords. The password was stored in the preferences XML (eXtensible Markup Language) in SYSVOL (System Volume), encrypted with a key Microsoft published in its own documentation — so any domain user who could read SYSVOL, which is every domain user, could decrypt it.
Microsoft removed the ability to create these in 2014, but did not remove existing ones. They persist in SYSVOL until someone deletes them, and finding them is a standard early step in an intrusion. Check now; it takes one command: 
# Any cpassword left in SYSVOL is a live credential leak to every domain user
Get-ChildItem -Path "\\corp.example.com\SYSVOL" -Recurse -Include *.xml -ErrorAction SilentlyContinue |
    Select-String -Pattern "cpassword" | Select-Object Path, LineNumber
If that returns anything: treat those credentials as compromised, rotate them, and delete the preference. Use LAPS for local administrator passwords — that is the control this anti-pattern was replaced by.

👥 Group Nesting Strategy — AGDLP, and Why Nested Groups Become a Mess AD DS • Identity ▶
The convention
AGDLP — Accounts, Global, Domain Local, Permissions
Put Accounts into Global groups by who people are ("Finance Staff"), put those global groups into Domain Local groups by what is being accessed ("Ledger Share — Modify"), and grant Permissions only to the domain local group.
The payoff is that the two things change independently. People move between roles constantly; resources change permissions rarely. One membership edit moves a person's entire access, and no access control list is ever touched.
The rule that makes it work: never grant a permission to a user, and never to a global group. The moment someone shortcuts it, the resource stops describing its own access and you can no longer answer "who can read this?" from the group model.
Failure mode
Token Bloat — When Group Membership Breaks Logon
Every group a user belongs to adds a security identifier to their Kerberos ticket. Past roughly 1,000 groups the ticket exceeds default buffer sizes and authentication fails — often as an HTTP (HyperText Transfer Protocol) 400 from a web application rather than anything mentioning Kerberos, which makes it a genuinely difficult diagnosis.
Deep nesting is the usual cause, because membership is transitive and nobody counts the indirect ones. Check the effective total, not the direct list: 
# Transitive group count — the number that matters
(Get-ADUser jdoe -Properties TokenGroups).TokenGroups.Count

# Users closest to the limit, worst first
Get-ADUser -Filter * -Properties TokenGroups |
    Select-Object Name, @{n='Groups';e={$_.TokenGroups.Count}} |
    Sort-Object Groups -Descending | Select-Object -First 20
Keep nesting to two levels — the depth AGDLP implies and no more. Every extra level makes membership harder to audit and pushes users toward a limit whose symptom does not name its cause.

The classic service account has a password set years ago, typed into several servers, recorded in a spreadsheet, and never rotated because nobody knows everything that uses it. 🎫 Kerberos in Operations — SPNs (Service Principal Name), Delegation & Clock Skew AD DS • Troubleshooting ▶
Orientation
The Flow Is Covered; These Are the Three Things That Break It
Kerberos Authentication Flow in the Security domain explains the ticket exchange, and Kerberos Attacks — Rubeus & Kerbrute in Red Team covers abuse. Operationally, almost every Kerberos incident is one of three causes: a service principal name that is missing or duplicated, delegation configured too broadly, or clocks that have drifted.
SPNs
A Duplicate SPN Breaks Authentication for Everyone
A service principal name maps a service on a host to the account running it. If it is missing, clients silently fall back to NTLM (NT LAN Manager) — which usually still works, so the symptom is "Kerberos is not being used" found during an audit rather than an outage. If it is duplicated across two accounts, the domain controller cannot decide which key to encrypt with and authentication fails outright. 
# Duplicates across the whole forest — run this before blaming the app
setspn -X

# What is registered for a given account, and adding one
setspn -L CORP\svc-webapp
setspn -S HTTP/app.corp.example.com CORP\svc-webapp
Use -S rather than -A: it refuses to create a duplicate. -A adds blindly and is how most duplicate-SPN outages are created, usually by someone fixing a different problem.
Failure mode
Five Minutes of Drift and Nobody Logs In
Kerberos timestamps tickets to prevent replay, and rejects anything outside a tolerance of five minutes by default. Beyond that, authentication fails across the estate at once, and the error text does not mention time.
The domain's time hierarchy is strict: every member syncs from a DC (Domain Controller), every DC from the PDC (Primary Domain Controller) emulator, and the PDC emulator from an external source. The classic incident is a virtualised PDC emulator syncing from its hypervisor host and an external source, and oscillating between them. 
w32tm /query /status              # what am I syncing from?
w32tm /monitor                    # offsets across all DCs
w32tm /stripchart /computer:dc01 /samples:5 /dataonly
Disable host time sync on a virtualised PDC emulator. One authority only. Two sources of truth for time is the same class of mistake as two sources of truth for data, and it fails more visibly.

🧹 Cleaning Up a Legacy Directory — Stale Objects & Over-Permissive ACLs (Access Control List) AD DS • Hygiene ▶
Method
Disable, Wait, Then Delete — Never Delete First
Every inherited directory contains accounts for people who left years ago and computers that were decommissioned. Each is a credential nobody is watching. The cleanup is easy; doing it safely is the part that needs a method, because deleting an account that turns out to run a nightly job is a worse outcome than leaving it.
Disable, move to a quarantine OU, and wait a full business cycle — a quarter, so that anything quarterly has had its chance to fail loudly. Then delete. The disable is instantly reversible; the delete is not. 
# Accounts unused for 90 days, still enabled
Search-ADAccount -AccountInactive -TimeSpan 90.00:00:00 -UsersOnly |
    Where-Object Enabled | Select-Object Name, LastLogonDate

# Computers the same, then disable and park them
Search-ADAccount -AccountInactive -TimeSpan 90.00:00:00 -ComputersOnly |
    Disable-ADAccount -PassThru |
    Move-ADObject -TargetPath "OU=Quarantine,DC=corp,DC=example,DC=com"

🧭 Windows DNS (Domain Name System) Administration — Zones, Scavenging & Forwarders Infra • Name Resolution ▶
Orientation
The Protocol Is Covered; This Is the Service AD (Active Directory) Cannot Live Without
DNS Deep Dive — Records, Resolution & Security in the Networking domain covers records, resolution and DNSSEC (Domain Name System Security Extensions). This card is about running Microsoft's DNS as the directory's locator service — because in an AD environment, DNS is not a supporting service. It is how every client finds a domain controller, and almost every "Active Directory is broken" incident is DNS.
Domain controllers register service records announcing which DCs serve which site and role. Clients query those records to find one. Break DNS and nothing authenticates, no policy applies, and replication stops — all reporting errors that describe symptoms rather than the cause.
Zone storage
AD-Integrated Zones Replicate Themselves
AD-integratedStandard primary/secondary
Stored inThe directoryA text file on one server
ReplicationAD multi-master — any DC accepts writesZone transfer from one master
Secure dynamic updatesAvailableNot available
Single point of failureNoneThe primary
Use AD-integrated zones with secure-only dynamic updates. Non-secure updates let any host on the network overwrite any record — including a domain controller's — which is a straightforward path to intercepting authentication.
Failure mode
Scavenging: Off Means Stale Records, On Wrongly Means Deleted Ones
Dynamic registration creates records; nothing removes them when a machine leaves. Over years the zone fills with stale entries and clients connect to addresses now belonging to something else. Scavenging deletes records that have not refreshed — and it is the single most dangerous switch in Windows DNS, because enabling it wrongly deletes live records.
Two intervals govern it. During no-refresh a record cannot update its timestamp; during refresh it can; after both elapse without a refresh it becomes eligible. Both default to seven days, so a record survives at least 14 days of silence. The trap is a static record with a timestamp — it will be scavenged. 
# Check before enabling anything
Get-DnsServerScavenging -ComputerName dc01

# Static records must have NO timestamp, or scavenging eats them
Get-DnsServerResourceRecord -ZoneName corp.example.com -RRType A |
    Where-Object { $_.Timestamp -ne $null -and $_.HostName -match '^(vpn|printer|nas)' }
Enable it on one zone, leave it a month, and read what it removed before enabling it everywhere. An aggressive interval on a site whose laptops are away for three weeks is an outage waiting for the holidays.
Resolution path
Conditional Forwarders Beat Stub Zones for Partner Domains
A forwarder sends everything unresolved to an upstream server. A conditional forwarder sends only queries for a named domain, which is the right tool for resolving a partner or acquisition domain across a trust. Root hints are the fallback when no forwarder answers.
Never point a domain controller's own client DNS settings at a public resolver. It must resolve the directory's records first — pointing it at 8.8.8.8 as a "backup" produces intermittent, extremely confusing replication failures, because sometimes the public server answers first and knows nothing about your domain.
📮 DHCP (Dynamic Host Configuration Protocol) Administration — Scopes, Reservations, Failover & Relay Infra • Addressing ▶
Design
Lease Length Is the Only Setting With Real Consequences
Most DHCP configuration is mechanical. Lease duration is the judgement call, and it trades address availability against churn: too long and a guest network exhausts its pool, too short and clients renew constantly and a server outage bites within hours.
NetworkTypical leaseReason
Wired office8 daysStable devices; renewal traffic is wasted work
Wireless corporate1 dayDevices come and go; addresses must return
Guest or conference2–4 hoursHigh churn, small pool
VoIP (Voice over Internet Protocol) handsetsLong, or reserveAddress changes disrupt call routing
Clients renew at half the lease, so an 8-day lease means a server can be down for four days before anyone notices. That is resilience, and also why nobody discovers DHCP has been broken until the following week.
Resilience
Failover Modes, and the Relay Everyone Forgets
Built-in failover replaces the old trick of splitting a scope 80/20 across two servers. Load balance shares requests between two servers in one site; hot standby keeps one passive for a remote site. Both replicate lease state, so a client keeps its address through a failure.
DHCP discovery is a broadcast and does not cross a router. Every subnet without a local server needs an IP (Internet Protocol) helper on its gateway pointing at the servers — and this is the thing forgotten when a new VLAN (Virtual Local Area Network) is created, producing "the new subnet does not work" with everything on the Windows side configured correctly. 
Add-DhcpServerv4Failover -ComputerName dhcp01 -PartnerServer dhcp02 `
    -Name "Site-A" -ScopeId 10.10.0.0 -LoadBalancePercent 50

Get-DhcpServerv4ScopeStatistics -ComputerName dhcp01   # pool exhaustion
Get-DhcpServerInDC                                       # authorised servers
Authorisation is a real control worth knowing. A Windows DHCP server refuses to serve leases until authorised in AD (Active Directory), which prevents a lab server from handing out addresses on production. It does nothing about a non-Windows rogue server — that needs DHCP snooping on the switches.
📁 File Services — Share vs NTFS (New Technology File System) Permissions, DFS (Distributed File System) & Quotas Infra • Storage ▶
The classic confusion
Two Permission Sets, and the Effective Right Is the Lesser
A file reached over the network passes two checks: the share permission and the NTFS permission. The effective access is the more restrictive of the two. Reached locally, only NTFS applies — which is why a permission problem can vanish when you test by signing in to the server.
The convention that removes the confusion entirely: set the share to Everyone — Full Control, and do all real work in NTFS. One place to look, one place to audit. Share permissions predate NTFS having any, and maintaining both is a way to create a puzzle for your successor.
DFS
Namespaces Buy You the Right to Move Data Later
A DFS namespace gives users a stable path — \\corp\shares\finance — that points at whichever server actually holds the data. Migrate the data, repoint the target, and no mapped drive, script or shortcut anywhere needs changing.
DFS replication is separate and keeps copies in sync. The pairing is powerful and has one sharp edge: DFSR (Distributed File System Replication) resolves a conflicting edit as last-writer-wins, moving the loser to a hidden ConflictAndDeleted folder. It is not a multi-master file system, and using it for a shared working folder across sites will lose someone's work.
Deploy the namespace even for a single file server. It costs almost nothing now and is the difference between a weekend migration and a transparent one.
Failure mode
The Share That Filled the System Drive
Without quotas, one user's export fills the volume, and if the share lives on the system drive the server stops — event logs cannot write, and the failure cascades well beyond the share. Two separate mechanisms exist and people configure the wrong one: NTFS quotas are per user per volume; File Server Resource Manager quotas are per folder and are the useful ones. 
# Soft quota — warn at 80%, do not block. Start here.
New-FsrmQuota -Path "E:\Shares\Finance" -Size 100GB -SoftLimit `
    -Threshold (New-FsrmQuotaThreshold -Percentage 80)

# And keep shares off the system volume in the first place
Start with soft quotas and reporting. A hard limit imposed without warning produces a support queue and a workaround culture — people start saving to their desktops, which is worse than the disk usage you were managing.
📜 AD CS (Active Directory Certificate Services) Design — Offline Roots, Issuing CAs (Certificate Authority) & Publishing Infra • PKI ▶
Orientation
The Theory Is Covered; This Is the Deployment You Have to Live With
PKI & Certificate Lifecycle in the Security domain covers chains of trust, certificates and revocation as concepts. This card is about the internal certificate authority you actually run — a system whose design decisions are effectively permanent, because rebuilding a root means re-issuing every certificate it ever signed.
Structure
Two Tiers, and the Root Stays Switched Off
The standard design is a standalone offline root that signs one thing — the issuing CA's certificate — and is then powered off and stored securely. An enterprise issuing CA, domain-joined, does all day-to-day work.
Offline rootIssuing CA
Domain-joinedNo — standalone, deliberatelyYes, for templates and auto-enrolment
Powered onOnly to sign or re-publish a CRL (Certificate Revocation List)Always
Compromise meansRebuild the entire PKI (Public Key Infrastructure)Revoke its certificate, stand up a new one
The verdict: the offline root exists so that the worst realistic incident is recoverable. A single online enterprise root is simpler to build and turns one compromised server into a full trust rebuild across every device — which is why the two-tier design is worth the extra afternoon.
Failure mode
The Offline Root's CRL Expires, and Everything Stops
A certificate revocation list has a validity period. When a client cannot fetch a current CRL for any CA in the chain, strict validation fails — so an offline root whose CRL quietly expired invalidates every certificate beneath it. The root is switched off, so nothing warns you, and the failure arrives all at once.
Set the offline root's CRL validity long — a year or more — publish it to a location that stays reachable, and put the renewal in a calendar owned by a team rather than a person. Check that the published locations resolve from a normal client, not from the CA: 
# Validate the whole chain and every revocation URL a client would use
certutil -verify -urlfetch cert.cer

# What the CA publishes, and when the current CRL expires
certutil -getreg CA\CRLPublicationURLs
certutil -CRL                       # force a fresh CRL now
The distribution points are baked into every certificate at issuance. Changing the URL (Uniform Resource Locator) later does not fix already-issued certificates — they carry the old address until they expire. Get the publishing addresses right before issuing anything.

🔄 Certificate Lifecycle — Auto-Enrolment and the Expiry Nobody Scheduled Infra • PKI ▶
Auto-enrolment
Getting Certificates Onto Devices Without Touching Them
Auto-enrolment issues and renews certificates automatically for accounts that have the rights. It needs three things aligned: Autoenroll permission on the template, the template published to an issuing CA (Certificate Authority), and a Group Policy setting enabling auto-enrolment for the computer or user.
All three, or nothing happens and nothing complains. That silence is the whole troubleshooting difficulty — check the three in order rather than re-reading the template, and confirm on a client with certutil -pulse followed by the CertificateServicesClient operational log.
Failure mode
Expiry Is the Outage That Is Fully Predictable and Still Happens
Every certificate carries the date it will break. Expiry outages are therefore unique: entirely foreseeable, scheduled by you, and still among the most common causes of self-inflicted downtime. They happen because nobody owns the inventory — the certificate was installed during a project, by someone who has moved on. 
# Everything the CA issued that expires in the next 60 days
certutil -view -restrict "NotAfter<=now+60:00:00,Disposition=20" `
    -out "CommonName,NotAfter,RequesterName"

# Local store on a server
Get-ChildItem Cert:\LocalMachine\My |
    Where-Object NotAfter -lt (Get-Date).AddDays(60) |
    Select-Object Subject, NotAfter, Thumbprint
Monitor expiry from outside, on the live endpoint. A CA report misses every certificate not issued by that CA — the public ones, the appliance ones, the one a vendor installed. The check that catches all of them connects to the port and reads what is actually being served.
🚑 Domain Controller Recovery — Authoritative vs Non-Authoritative Restore AD DS • Recovery ▶
The distinction
Two Restores That Look Identical and Do Opposite Things
Restoring a domain controller is not like restoring a file server, because the data is replicated and the other copies are still running. The question is whether the restored data should win.
Non-authoritativeAuthoritative
After restoreCatches up from its partnersOverwrites its partners
Use forA failed DC (Domain Controller) — almost always this oneRecovering objects deleted everywhere
RiskLowReintroduces everything else from that backup too
Reach for the Recycle Bin before either. If the AD (Active Directory) Recycle Bin is enabled, deleted objects are restorable in place with their group memberships intact — no backup, no downtime, no restore. Enable it now if it is not on; it is a one-way switch and costs nothing. 
# Is it on? If not, turn it on — irreversible, and you want it
Get-ADOptionalFeature -Filter 'name -like "Recycle Bin*"'

# Restore a deleted user, memberships intact
Get-ADObject -Filter 'Name -like "*jdoe*"' -IncludeDeletedObjects |
    Restore-ADObject
Failure mode
USN Rollback — Why You Never Snapshot a Domain Controller
Reverting a DC to a virtual machine snapshot rewinds its update sequence numbers. Partners have already seen higher numbers from it, so they ignore everything it sends — the DC believes it is replicating and is silently isolated, diverging from the domain until someone notices weeks later.
Modern Windows and hypervisors support VM-GenerationID, which detects the rollback and recovers safely. Do not rely on it: restore a DC with a supported system-state backup, or demote and rebuild. Rebuilding a DC is genuinely routine — promote a new one, let it replicate, remove the old.
Test the restore, not the backup. A backup job reporting success proves a file was written. The forest recovery procedure is long, involves seizing FSMO (Flexible Single Master Operations) roles and resetting the KRBTGT (Kerberos Ticket Granting Ticket account) account twice, and reading it for the first time during an incident is how a bad day becomes a bad month.
🗑️ Decommissioning a Server Properly — The Checklist That Prevents Next Year's Outage Infra • Lifecycle ▶
Method
Power Off Is Not Decommissioned
A server switched off and left in the rack is the origin of a specific recurring incident: eighteen months later someone reclaims the address or the name, and something nobody knew depended on it breaks. The fix is a sequence with a waiting period, not a single action.
StepWhy this order
Find what still talks to itFirewall logs and DNS (Domain Name System) query logs, not the documentation

Stopping the services while the host stays up is the step that earns the most. A dependency that fails against a running server produces a connection refused naming the host. The same dependency after a shutdown produces a timeout somewhere else entirely, and nobody connects it to the decommissioning.
Failure mode

A domain controller must be demoted, which removes its metadata, transfers any FSMO (Flexible Single Master Operations) roles it holds and cleans up its service records. Powering one off instead leaves records advertising a DC that no longer answers, and clients will keep trying it — producing slow logons that survive every other fix.
If the DC is already gone and cannot be demoted, clean the metadata explicitly. Do not leave it: replication partners keep attempting it, and the errors mask real faults.

One Physical Host Pretending to Be Many

📸 Snapshots Are Not Backups — What They Cost and How They Bite Infra • Virtualization ▶
Concept
A Snapshot Is a Fragile Dependency, Not a Copy
A VM (Virtual Machine) snapshot does not copy the disk. It freezes the current disk and writes all new changes to a growing delta file, so the running VM now depends on the original disk plus every delta in the chain. Lose or corrupt any link and the VM is gone. That is the opposite of a backup, which is an independent copy you can restore without the original. Treating one as the other is a classic career-ending mistake.

Snapshots have an expiry date even when nobody sets one — treat anything older than a day as an incident. The delta chain grows, the virtual machine slows, and the dependency on the original disk means a storage failure takes the snapshot with it. Take one before a patch, remove it after the change window, and alert on any that survive the week.

💾 Storage Fundamentals — Block, File & Object in the Datacenter Infra • Storage ▶
Concept
The Difference Is Who Owns the Filesystem
Block, file and object are usually introduced as three storage products. The distinction that actually predicts their behaviour is simpler: where the filesystem lives. Block storage hands a server raw addressable blocks and the server puts a filesystem on them. File storage keeps the filesystem on the storage system and lends you a path into it. Object storage has no filesystem at all — just a flat namespace of keys, retrieved whole over HTTP (HyperText Transfer Protocol).
Everything else follows from that. Only one server can own a block device at a time, because two filesystems writing the same blocks corrupt each other — which is why shared block storage needs a cluster filesystem or careful orchestration. File storage is shareable precisely because the storage system arbitrates. And object storage cannot modify part of a file, because there is no block layer to modify: you replace the whole object.

🧮 RAID (Redundant Array of Independent Disks) & Erasure Coding — What Redundancy Buys, and the Rebuild Window Infra • Storage ▶
Concept
Redundancy Protects Against Drive Failure and Nothing Else
RAID keeps a volume online when a disk dies. That is its entire promise, and it is worth stating flatly because the mistake it invites has cost more data than the failures it prevents: RAID does not protect against deletion, corruption, ransomware, a failed controller, a flood, or somebody typing the wrong command. Every one of those is faithfully replicated across all members, instantly. An array is an availability feature; a backup is a recovery feature, and they are not substitutes.
LevelSurvivesCapacity costNotes
RAID 0NothingNoneStriping only; failure risk multiplies with member count
RAID 1One of two50%Simple, fast reads, fast rebuild
RAID 5One driveOne drive's worthIncreasingly discouraged at large capacities — see below
RAID 6Two drivesTwo drives' worthThe realistic minimum for large spinning disks
RAID 10One per mirrored pair50%Best write performance and fastest rebuild; the database answer
Erasure codingConfigurable — n of m fragmentsTunable, far better than mirroring at scaleDistributed across nodes, not just disks
RAID 6 or 10 for anything spinning and large; RAID 5 has been out of its depth for years. The rebuild reads every remaining disk for hours, which is exactly when the second failure arrives — and the capacity saved is not worth the array. Erasure coding is the row to look at when the scale justifies it, because mirroring costs half of everything.
Concept
The Rebuild Window Is the Real Risk
When a drive fails, the array reconstructs its contents onto a replacement by reading every remaining drive end to end. On modern high-capacity disks that takes many hours, sometimes days — and throughout it the array is running degraded, under maximum read load, on drives that are the same age and model as the one that just failed. A second failure during that window is far more likely than the naive independent-failure arithmetic suggests, because the failures are correlated by age, batch and workload.
This is why single-parity RAID 5 fell out of favour for large disks rather than because of any change in the mathematics of parity: the array grew, the rebuild got longer, and the exposure window grew with it. The mitigations are practical rather than clever.
MitigationEffect
Double parity or better on large drivesA second failure during rebuild stops being fatal
Hot spares that rebuild automaticallyRemoves the hours between failure and someone noticing
Smaller failure domains — more, smaller groupsShorter rebuilds, less data at risk each time

Scrub or patrol-read on a scheduleFinds latent bad sectors before a rebuild depends on them

The last row is the one that turns a designed protection into an actual one. An array that has been running degraded for six weeks because nobody read the alert has the redundancy of a stripe, and this is far more common than a genuine double failure — the monitoring is what makes every other mitigation on the list mean anything. Hot spares are the next best pound spent: they remove the hours between the failure and a human noticing.
Troubleshooting
Erasure Coding — Why Scale-Out Systems Do Not Use RAID
Erasure coding generalises parity: split an object into k data fragments, compute m parity fragments, distribute all of them across nodes, and reconstruct from any k. It is what object stores and distributed filesystems use, and the reason is economic — three-way replication costs 200% overhead, while a 10+4 code survives four simultaneous failures for 40%.

The practical rule this leads to: mirror or RAID 10 for latency-sensitive random workloads, erasure coding for large capacity where throughput matters more than latency. And on any of them, remember the first card's point — none of this is a backup, because all of it replicates a deletion perfectly.

A storage area network carries SCSI (Small Computer System Interface) or NVMe (Non-Volatile Memory Express) commands between servers and arrays, so that a volume on the array appears to the server as a locally attached disk. Everything unfamiliar about SANs follows from that one fact: the vocabulary is networking vocabulary, the failure modes are networking failure modes, and the consequences are disk consequences — a dropped frame is not a retransmitted packet, it is an I/O (Input/Output) error that a filesystem has to handle.

📂 SMB (Server Message Block) & NFS (Network File System) at Scale — Protocol Behaviour, Versions & Why File Workloads Feel Slow Infra • Storage ▶
Concept
File Protocols Are Chatty, and Latency Multiplies
Opening a file over SMB or NFS is not one operation. It is a sequence: resolve the path component by component, check permissions, open, query attributes, read, close. Each step is a round trip. On a local network at half a millisecond, nobody notices. Over a link at forty milliseconds, the same operation that took ten milliseconds takes several seconds — and the throughput of the link is irrelevant, because nothing is waiting on bandwidth.
This single fact explains most file-server complaints. "The share is slow from the branch office" is almost never a bandwidth problem, and adding bandwidth reliably fails to fix it. It also explains why a workload of a million small files behaves completely differently from one large file of the same total size: the second is bandwidth-bound and the first is round-trip-bound.

⚡ Storage Performance — IOPS (Input/Output Operations Per Second), Throughput, Latency & Which One Is Your Limit Infra • Storage ▶
Concept
Three Numbers, and Only One of Them Is Your Problem
Storage performance discussions go wrong because three different measurements get treated as one quantity called "speed". IOPS counts operations per second and is what small random work needs. Throughput counts bytes per second and is what large sequential work needs. Latency is how long one operation takes, and it is what users actually experience. They are related but not interchangeable: an array can deliver enormous throughput while every individual operation is slow, and the users of a database will describe that as broken.
WorkloadBound byWatch

Vendor figures almost always quote the best case for one of these — usually large sequential reads or 100% random reads at an unrealistic queue depth. A figure without its block size, read/write mix and queue depth is not a measurement, and comparing two such figures is meaningless.
Concept
Queue Depth — The Number That Explains Confusing Results
Queue depth is how many operations are outstanding at once. It ties the other three together through a relationship worth internalising: IOPS ≈ queue depth ÷ latency. A single-threaded workload with one outstanding operation and a one-millisecond latency cannot exceed a thousand IOPS no matter how capable the array is — because it never asks for more than one thing at a time.
This explains the two most common confusions in storage benchmarking. A benchmark showing far lower IOPS than the array's rating is usually running at too shallow a queue depth to exercise it. And an array hitting its rated IOPS while everything feels slow is usually running at a very deep queue: the operations are being delivered, each one is just waiting in line, and latency has climbed accordingly.
ObservationReading

Read the three numbers together or you will optimise the wrong thing. Low throughput with low latency and a shallow queue is an application that is not asking — buying faster storage changes nothing, and that is the most common misdiagnosis in this table. The Thin-Provisioning Cliff
Thin provisioning is over-subscription: the array promises more capacity than it has, because most volumes never fill. This is sound and it is how essentially all modern storage is run. The failure mode is not gradual. Right up to the moment the pool is full, performance and behaviour are normal — and then writes fail across every volume in the pool simultaneously, including the ones nobody was growing.
ControlReason
Alert on pool utilisation at two thresholds, well before fullThe first is a warning; the second is an emergency
Alert on rate of growth, not only on level85% and stable is fine; 60% and climbing fast is not
Keep headroom that is genuinely reservedHeadroom you would consume in a pinch is not headroom
Know how long it takes to add capacityIf procurement takes six weeks, alert six weeks of growth early
Watch snapshot and clone consumption separatelyA pool commonly fills from snapshots, not from volumes
Reclaim deleted space — UNMAP or TRIM from the guestWithout it, thin volumes only ever grow, however much is deleted inside
Do not thin-provision at three layers at onceGuest, hypervisor and array each over-subscribing is unmodellable
The reclaim row is the one that quietly causes most pool-full incidents. Deleting a file inside a guest frees space in the guest filesystem and tells the array nothing; without UNMAP or TRIM propagating down, the array still considers those blocks written. Estates discover this when a pool is full while every volume inside reports plenty of free space.
Troubleshooting
Deduplication and Tiering — Reading the Claims Honestly
Both are sold with ratios, and both ratios are real for the workload they were measured on and meaningless for yours.
ClaimReality
"10:1 deduplication"Plausible on a VM estate from one template; near 1:1 on media or encrypted data
"Dedup makes backups cheap"True, and it is why backup appliances lead with it — full backups repeat enormously
"Efficiency features are free"They cost CPU, memory and metadata; inline dedup costs write latency
"Tiering means you need less fast media"Only if the working set is stable and smaller than the fast tier
"Tiering reacts automatically"On a schedule, often hours or a day — a Monday-morning shift is served from the cold tier
"Dedup protects nothing"Correct, and worth remembering: deduplicated data has one copy of each block by design
The last row matters for backup design specifically. A deduplicated backup repository is efficient and is a single fate-shared copy: corruption of a heavily-referenced block affects every backup that references it. That is not an argument against dedup — it is the argument for the second copy on different media that Backup Strategy — 3-2-1-1-0 and the Schemes That Make Restores Possible already insists on.
📆 Storage Capacity Planning — Forecasting Growth Before It Becomes an Incident Infra • Storage ▶
Concept
The Only Storage Emergency That Is Entirely Predictable
Almost every storage incident has a moment of surprise in it — a drive fails, a controller panics, a path drops. Running out of space does not. It approaches at a measurable rate, in plain view, for months, and it still causes outages routinely — because nobody was reporting the rate, only the level, and because the lead time to add capacity was longer than the warning anybody had configured.
The reframing that fixes it: capacity is a time problem, not a percentage problem. "The pool is 82% full" prompts nothing. "The pool has eleven weeks left at the current rate, and procurement takes eight" is a decision with a deadline, and everyone in the room understands it immediately.
Reference
What to Measure, and What Each Number Is For
A useful forecast needs a small set of numbers tracked over time. The trend matters far more than the precision.
MeasurePurpose
Used capacity per pool, weeklyThe raw series everything else is derived from
Growth rate, as a rolling averageSmooths one-off events into a usable trend
Weeks-to-full, derivedThe headline number; the one to alert on

Snapshot and clone consumption, separatelyGrows with change rate, not with new data; behaves differently
Performance headroom alongside capacityAn array frequently runs out of IOPS (Input/Output Operations Per Second) before it runs out of terabytes
Lead time to add capacity, measuredSets how far ahead your alerting has to reach
The performance-headroom row is the trap in an all-flash world. Capacity is cheap and plentiful; controller CPU (Central Processing Unit) and cache are not. An array at 50% capacity and 95% controller utilisation needs expansion just as urgently, and no capacity report will say so.
Troubleshooting

Linear extrapolation from the last few months is right often enough to be useful and wrong in specific, recognisable ways. Knowing the ways is what turns a forecast into a plan.

Seasonality — year-end, retail peaks, academic termsCompare year on year, not month on month
Retention policy changesExtending retention is a capacity decision; it is rarely reviewed as one
Efficiency ratio driftingEncrypted or pre-compressed data arriving deduplicates far less
Nobody ever deletes anythingThe most common cause of all; check whether lifecycle policies actually run
Growth that is really a bugA runaway log or a failing job can fill a pool in days
Two habits cover most of that list. Review capacity alongside the project pipeline rather than in isolation, so step changes arrive as plans instead of as surprises. And alert on acceleration as well as on level — a growth rate that doubles this week is usually a bug, and catching it as a bug rather than as a capacity request is both cheaper and faster. 🚚 Live Migration & Maintenance Mode — Patching Hosts Without an Outage INFRA • Virtualisation ▶
Concept
Copy the Memory While It Is Still Changing
Moving a running machine between hosts sounds impossible and is nearly mechanical: copy the memory across while the machine keeps running, then copy the pages that changed while you were copying, then the ones that changed during *that*, until the remaining set is small enough to transfer in a pause the guest does not notice. That pause is the whole game. It is typically well under a second, and everything that makes live migration fail is really something making that final set refuse to get small.
PhaseWhat happens
Pre-copyMemory streams to the target host while the guest runs
Iterative re-copyPages dirtied during the copy are sent again, and again
StunThe guest is paused for the final delta and the device state
SwitchoverThe target resumes; the network is told the MAC (Media Access Control) moved
CleanupThe source releases the machine
The requirement people forget: both hosts must be able to run the same instruction set. Mixed CPU (Central Processing Unit) generations in one cluster are why compatibility modes exist — they mask newer instructions so a guest never sees a feature that would vanish underneath it after a move. Turning that off to gain a few percent is a decision to stop migrating freely.
Reference

The capacity check is the one that gets skipped, and it is the one that hurts: a cluster running at 85% with no reserve cannot evacuate a host at all, so the maintenance window arrives, the evacuation stalls, and someone has to choose between shutting down guests and abandoning the patch. 📤 P2V & V2V — The Migrations That Still Happen INFRA • Virtualisation ▶
Concept
Converting a Machine You Are Not Allowed to Rebuild
Physical-to-virtual and virtual-to-virtual conversions were supposed to end a decade ago, and they keep happening — because somewhere there is a machine running software nobody can reinstall, whose vendor is gone, whose installation media is lost, and which the business depends on. The honest framing is that conversion is a *last* option, chosen when rebuilding is genuinely impossible, and that its output is a machine carrying every accumulated oddity of the original into a new home.
PreferWhen

Leave it physical, isolatedWhen conversion fails and the risk of touching it exceeds the risk of leaving it
The fourth row is a real answer, not a joke. An unconvertible machine running a critical process is a business risk that should be recorded, isolated on the network, backed up at the image level and given an end date — rather than quietly carried for another five years because nobody wants to write it down.
Reference

🩺 Virtualisation Troubleshooting — The Storage, Network, Host Triage Order INFRA • Virtualisation ▶
Concept
"The VM Is Slow" Is a Statement About Four Machines
Inside the guest, everything looks like the guest's problem: the disk is slow, the processor is busy, the network is dropping. It usually is not. The guest cannot see the other twenty machines on its host, the host cannot see the other hosts on the storage array, and none of them can see the switch. That is why virtualisation troubleshooting has an order — and why starting inside the guest, which is where the ticket points, is nearly always the slowest route to the answer.
OrderLook atBecause
1. StorageLatency at the datastore and the arrayThe single most common cause, and it presents as everything else
2. HostContention, memory pressure, swappingA stressed host makes every guest on it look individually ill
3. NetworkUplinks, drops, the physical switchShared by every guest on the host, so a single uplink explains a cluster of tickets
4. GuestIts own processes, its own configurationReal often enough to check, last often enough to check last
The tell for "not the guest" is several unrelated machines complaining at once. Two tickets from different applications on the same host, or on the same datastore, is a platform problem until proven otherwise, and the fastest first question is always: what else lives where this lives?
Reference

Vendor names differ; the concepts are the same everywhere, and each one answers a specific question the guest cannot answer about itself.

🏛️ Mainframe & Midrange — Why They Are Still There, and How You Integrate With One Infra • Legacy Platforms ▶
Concept
"Still Running" Is an Engineering Answer, Not an Embarrassment
The usual framing is that mainframes survive because nobody was brave enough to replace them. That is not the reason, and believing it is how integration projects get scoped badly. Two things keep these systems in place. First, the machine is built for a workload most modern infrastructure is not: enormous transaction volumes with per-transaction integrity, where the redundancy is in the hardware — a failing processor retries the instruction rather than failing the node. Second, and more decisively, the specification is the code. Forty years of rules about how interest accrues, how a claim is settled, how a shipment is rated, exist nowhere else in writing. Nobody is defending the platform; they are defending the only surviving copy of the business.
The asymmetry that decides these arguments: the current system's failure modes are known, bounded and already priced. A rewrite's are not, and they land on the day the rewrite goes live — which is also the day the people who understood the original are gone. That is not an argument against ever modernising. It is the reason modernising is done in slices, and it is why "we should just rewrite it" costs credibility in a room that has watched somebody try.
Reference

Modernising Without a Big Bang

It converts a maintainable legacy system into an unmaintainable modern one, which reads as progress on a slide.

A well-wrapped mainframe with a documented API, a monitored batch schedule and its access review inside the same governance as everything else is a perfectly defensible piece of infrastructure. 🗳️ Failover Clustering — Quorum Is the Whole Subject High Availability ▶
Core Concept
Clusters Do Not Fail Because a Node Dies. They Fail Because the Survivors Cannot Agree That It Did.
The failure everyone designs for — a node stops — is the easy one. The failure that actually takes clusters down is two halves that can each see themselves and not each other, both concluding they are the survivors, and both mounting the shared storage. Quorum exists entirely to make that impossible, by ensuring at most one partition can ever hold a majority.
SituationWhat the cluster must conclude
A node crashesEasy. The rest hold a majority and carry on
A network link between racks failsHard. Both sides are healthy and each sees half the cluster
A node is alive but unreachableIndistinguishable from dead, from the outside. This is why fencing exists
Both halves decide they are authoritativeSplit-brain. Two writers on one dataset — the worst outcome available
No majority anywhereCorrect behaviour is to stop. Unavailable beats corrupt
The line worth saying to anyone specifying a cluster: a two-node cluster with no witness is a coin toss. Each node holds exactly half the votes, neither can ever achieve a majority alone, and the design has no correct answer to a link failure. Two nodes is a common budget outcome and it is not a quorum.
Reference
Witnesses, Votes, and the Arithmetic
Quorum is arithmetic, and the arrangements exist to make the total odd or to break ties from somewhere that cannot be on either side of the partition.
ArrangementQuorum behaviour
3 nodesTolerates 1 failure. The smallest genuinely sane cluster
2 nodes + a witnessThe witness is the third vote. It must be somewhere neither node's failure takes with it
File-share witnessA share on a third site or an independent host. Cheap, and the usual answer
Cloud witnessA storage account or blob. Independent of both data centres by construction
4 nodesTolerates 1, not 2 — an even count buys nothing over 3. Add a witness or a fifth node
The witness placement is the part people get wrong: a witness in the same rack, on the same power feed, or behind the same link as one of the nodes is not a third opinion. It has to fail independently of both, which for a two-site cluster means a third site or a cloud service — and that is the whole reason cloud witnesses became the default answer.
Practice
Fencing, and Why the Cluster Sometimes Shoots a Node
Quorum decides who should be running. Fencing makes sure the loser actually stops. Without it, a node that was merely unreachable can come back holding stale locks and write to storage the survivors have already claimed.
MechanismWhat it does
STONITH / power fencingCuts power via IPMI or a switched PDU (Power Distribution Unit). Crude, and unambiguous
Storage fencing (SCSI reservations)Revokes the loser's access to the disk. It may still be running; it cannot write
Network fencingPorts disabled on the switch. Depends on the switch being reachable, which it may not be
No fencingThe cluster is trusting a node it cannot talk to. This is how corruption happens
Fencing that needs the failed node's cooperationNot fencing. If it were cooperating there would be no problem
Two operational habits. Test the failure you are afraid of, not the one that is easy to test — pulling a power cable proves little, while severing the inter-site link proves everything. And write down what the cluster should do when quorum is lost entirely, because the correct answer is usually “stop and page a human”, and a team that has not agreed that in advance will override it at 3am and cause the split-brain the design prevented.
🏗️ The Rack, the Power & the Cooling Data Centre ▶
Reference
Physical Constraints That Software People Meet Exactly Once
Most of this is invisible until it is violated, and then it is expensive. Racks, power and cooling are not background detail: they are hard limits that decide what can be installed, and every one of them has a failure mode where the equipment works fine until the day it does not.
ConstraintHow it bites
Rack units and depth42U is standard; depth is not. A 900mm server does not fit a 600mm rack, and nobody measures until delivery
Floor loadingA full rack is 700–1,200 kg. Older buildings and raised floors have real limits, expressed per square metre
Power per rackCircuits are rated in amps. Two 16A feeds is roughly 7kW total, not per feed — and modern kit is dense
Cooling capacityEvery watt in is a watt of heat out. A rack the power can supply may exceed what the room can cool
Weight distributionHeavy at the bottom. A top-heavy rack on castors is a genuine hazard while being moved
The order these are discovered in is almost always wrong: space is checked, then power, then cooling, then floor loading — which is the reverse of how hard they are to fix. Adding a rack is easy; adding a circuit is a project; adding cooling capacity is a building works programme. Ask about the last two first.
Reference
Dual Feeds Are Pointless if the Device Has One Supply
Redundant power is the most commonly claimed and most commonly broken piece of resilience in a rack, and the break is nearly always the same: redundancy has to be end to end. Two feeds, two PDUs (Power Distribution Unit), and then a switch with one power supply plugged into one of them.
What to checkWhy
Every device's supply countSingle-supply devices need a transfer switch, or they are a single point of failure
Which PDU each cable is inBoth cords of a dual-supply server in the same PDU is common and useless
Feed capacity when one failsEach feed must carry the whole load alone. Two feeds at 60% each means a failure trips the survivor
UPS (Uninterruptible Power Supply) runtime, measuredBatteries age. The runtime on the label is for new cells at 25°C
Generator start and transfer timeThe gap the UPS has to cover. Tested under load, or it is a hope
The A/B discipline is simple to state and needs enforcing at install time, because retrofitting it means unplugging live equipment: every dual-supply device takes one cord from feed A and one from feed B, and every single-supply device is documented as a known single point of failure. The second half matters as much as the first — an undocumented one is discovered during the outage.
Reference
Hot Air Comes Back Unless You Stop It
Cooling failures in a well-provisioned room are usually not about capacity. They are about air taking the shortest path, which is frequently a path straight back to the intake it just left.
ProblemFix
Recirculation through empty rack slotsBlanking panels. The cheapest cooling improvement that exists, and the most often skipped
Mixed intake directionsHot/cold aisle containment — all intakes facing the cold aisle, all exhausts the hot
Cable bundles blocking exhaustRoute to the sides. A dense bundle behind a server is a wall
Under-floor obstructionOld cabling under a raised floor stops the air that is supposed to arrive
Perforated tiles in the wrong aisleCold air delivered to the hot aisle cools nothing and costs the same
The measurement that settles arguments is intake temperature at the top of the rack, not room temperature. Rooms are cool at head height and hot at 2 metres; the equipment cares about what reaches its own intake, and a rack that is fine at the bottom and throttling at the top is the standard picture in a room nobody has contained. The efficiency version of this argument — what all that cooling costs, and what it emits — is Green IT — Power, Cooling, Hardware Lifespan & the Honest Carbon Maths.
🏷️ Labelling & Asset Tagging — The Boring Discipline That Pays Out at 3 a.m. Operations ▶
Core Concept
The Cost Is Paid Now and the Benefit Lands at 3 a.m.
Labelling is the clearest example of a discipline whose economics are misjudged because the two sides land at different times. Labelling a rack costs an afternoon while everything is calm; not labelling it costs twenty minutes of an outage, at the moment when twenty minutes is the most expensive commodity in the building — and it costs that repeatedly, for years.
MomentUnlabelledLabelled
Routine changeTrace the cable by hand, or unplug and see what breaksRead the label
Emergency, 3 a.m.Someone unplugs the wrong thing. This is the actual riskRead the label
New starter's first weekWeeks of tribal knowledge transferThe room documents itself
Auditor asks what this isAn afternoon of reconstructionA photograph
DecommissioningNobody dares remove anythingRemove what the label says
The argument that gets it funded is not tidiness, it is the second row. The most common cause of a second outage during a first one is somebody acting on a guess about what a cable does — and a label is the cheapest control against that which exists.
Reference
What to Label, and What to Put on the Label
Over-labelling fails as surely as under-labelling, because labels that carry information which changes are wrong within a year and then actively mislead.
LabelPut on itNot on it
Both ends of every cableSource device + port, destination device + portThe service it carries — that changes
The front and back of each deviceHostname and asset tagThe IP (Internet Protocol) address, unless it is genuinely static and documented
Rack frontRack ID matching the floor planA person's name
Power cordsWhich PDU (Power Distribution Unit) and outletAnything about the workload
Patch panel portsThe port on the far endWhatever was plugged in that day
The rule that keeps labels honest over time: label the physical fact, not the logical role. A cable's endpoints do not change while the cable is in place; the service it carries changes every migration. A label that says sw-core-01 Gi1/0/12 is true for the life of the cable, and one that says “payroll” is a lie waiting for the next project.
Practice
Asset Tags Are the Link Between the Room and the Database
The physical label only pays fully when it matches something. An asset tag is the join key between a device you can touch and the record in an inventory — which is what makes Asset Discovery — You Cannot Protect What Nobody Listed resolvable in a data centre rather than only on the network.
PracticeWhy
Tag at receipt, before installationThe one moment every device passes through, and the only one that catches everything
A tag that survivesPrinted labels fall off warm equipment. Use proper asset labels rated for the temperature
The tag is the primary keySerial numbers vary by vendor format; a tag you control does not
Photograph the rack after any changeTen seconds, and it settles most later questions without a site visit
Reconcile the room against the database quarterlyThe reconciliation is the control. A tag with no record, or a record with no tag, is a finding
The quarterly walk is the part that turns this from documentation into a control, and it is worth doing even badly: a rack-by-rack comparison of tags against the inventory finds decommissioned-but-still-powered hosts, undocumented equipment somebody installed, and records for devices that left the building — all three of which are invisible from a network scan.
📼 Tape, Archive & the Restore Nobody Has Tested Backup ▶
Core Concept
Tape Did Not Die. It Became the Offline Copy.
Tape's decline was widely announced and then reversed by ransomware, for a reason that has nothing to do with cost per terabyte: a tape on a shelf is not reachable from the network. Every online backup, however well replicated, is reachable by credentials an attacker may hold — and the whole point of the offline copy is that no credential reaches it.
PropertyTapeDisk / cloud
Offline by defaultYes, once ejected. This is the whole argumentNo — unless made immutable deliberately
Cost per TB at scaleLow, and lower still for cold archiveHigher, though the gap narrows with archive tiers
Restore latencyMinutes to hours — find, load, seekSeconds to minutes
Sequential throughputExcellent. A modern drive is faster than most networksDepends on the tier
Random accessEffectively none. It is a streamFine
The modern answer is not usually tape or cloud, it is whichever copy is genuinely out of reach of your production credentials. Object lock, an immutable archive tier, or a separate account with its own identity provider achieves the same property without a drive — and a tape that never leaves an autoloader connected to the backup server has lost the property it was bought for.
Reference
Three Questions, and the Last One Strands More Archives Than the First Two
Archive planning asks about capacity and media life, and the failure that actually loses data is usually neither.
QuestionThe honest answer
How long does the media last?LTO is rated 15–30 years in proper conditions. Rarely the binding constraint
How fast can we restore?Compute it: total size ÷ drive throughput, plus load and seek per tape. A 200 TB restore on one drive is days
Will there be a drive that can read it?The one that strands archives. LTO reads two generations back and writes one. An LTO-6 tape is unreadable in an LTO-9 drive
Will the software still exist?Proprietary backup formats need the software as well as the drive. Keep a documented restore path
Is the key still available?An encrypted archive with a lost key is a landfill item. Escrow it separately, and test that too
For anything with a retention period longer than a hardware generation, the plan needs a migration schedule, not just a retention schedule — a date by which the archive is re-written onto current media. Retention policies routinely specify seven years and never mention that the drive estate will turn over twice in that window.
Practice
The Restore Nobody Has Tested Is Not a Backup
Every organisation has backups. A much smaller number have restores, and the difference only becomes visible on the day it matters. A restore that has never been performed is a hypothesis, and it usually fails on something procedural rather than something technical.
What a test restore findsHow often it is the cause
The backup was not running on that hostExtremely common. Nobody watches a job that never alerts
It ran and captured the wrong pathCommon. The data moved and the job did not
The restore takes far longer than the RTO (Recovery Time Objective) assumedVery common, and it is arithmetic nobody did
No drive, no software, or no keyRare and terminal — see the previous card
Nobody present knows the procedureCommon at 3 a.m., and fixed only by rehearsal
Make it a scheduled, dated exercise with a written result: restore one real system to a scratch environment, time it, and record what broke. Quarterly is enough. The finding is almost never “the tape was bad” — it is that the RTO on the continuity plan was an aspiration, and the exercise is the only thing that converts it into a measured number.
🧹 Decommissioning at Estate Scale Lifecycle ▶
Core Concept
The Existing Card Covers One Server. This Is the Programme.
Decommissioning a known server is a checklist. Decommissioning at estate scale is a different problem, because the hard part is not the removal — it is finding the things nobody owns, and then discovering what still points at them after they are gone.
StageThe real difficulty
Finding candidatesNobody volunteers a system. Low utilisation, no logins, no patches, no owner in the CMDB (Configuration Management Database)
Establishing ownershipThe longest step. The named owner left in 2022 and their team was reorganised
Notice periodLong enough for a real objection, short enough to finish. Four to six weeks is typical
Powering off, not removingLeave it off and recoverable for a defined window. This is the step that makes the programme safe
Removal and disposalMedia sanitisation, asset record, licence reclaim — and the record that it happened
Run it as a standing programme with a monthly cohort rather than an annual project. A cohort of ten systems a month finishes; a project to clear four hundred stalls at ownership, which is the second row, and never restarts — and in the meantime the estate has grown again.
Practice
The Scream Test, Done Properly
The standard technique for an unowned system is to switch it off and wait for someone to complain. It works, and it is only responsible when it is bounded: a scream test without a rollback plan and a notice period is an outage you scheduled without telling anyone.
ElementWhy it is required
Notice, broadcast wider than you think necessaryThe user is frequently in a department you would not have asked
A firewall block first, then power offReversible in seconds, and it produces the same scream
Off, not deleted, for 30–90 daysThe objection often arrives at month-end, quarter-end or year-end
A named contact on the noticeA scream needs somewhere to go, or it goes to a ticket queue and is lost
Never during a change freeze or a peakThe one variable entirely within your control
The refinement that avoids most incidents is the second row. Block the traffic before removing the power: it exercises the same “does anyone need this” question, it is undone by deleting a rule, and it leaves the system available for forensic questions about what it was doing — which is precisely what a scream test destroys when it starts with the power button.
Reference
What Outlives the Host
The server is the easy part. The residue is what causes incidents months later, and almost all of it lives in systems owned by other teams.
ResidueConsequence if left
DNS (Domain Name System) recordsA dangling record pointing at a reclaimed IP (Internet Protocol) is a subdomain takeover — especially in cloud, where the address is reissued to a stranger
Firewall rules and NAT (Network Address Translation) entriesPermanent holes accumulating in the ruleset, each one now pointing nowhere or somewhere new
Monitoring checks and dashboardsAlerts nobody can resolve, which trains the team to ignore alerts
Backup jobsFailing nightly forever, or worse, succeeding on nothing
Credentials and service accountsThe account outlives its purpose and nobody rotates it. See Offboarding as a Security Control — The Checklist and Its Failure Modes
CertificatesIssued for a name that now resolves elsewhere
The first row deserves separating out because it is a security finding rather than untidiness. A CNAME (Canonical Name) left pointing at a decommissioned cloud resource can be claimed by whoever next allocates that name, and the result is an attacker serving content from your domain, with a valid certificate they obtained legitimately. Removing DNS should be the first step of a cloud decommission, not the last.
🩹 Patching a Server Estate — Windows, Rings & the Ones That Cannot Reboot INFRA • Operations ▶
The Inversion
A Server Is Not a Laptop That Happens to Be in a Rack
Laptop patching is a solved, largely automatic problem: rings, deferrals, a nudge to reboot. Servers break every one of those assumptions, because a server reboot is a negotiated event with a business, not a notification a user dismisses. Servers have dependencies on each other, maintenance windows that belong to someone else's revenue, and a minority that genuinely cannot take a scheduled reboot at all. The mechanism is the same; the constraints are entirely different.
Laptop patching assumesA server estate instead requires
Reboot whenever; the user re-opens their appsA window negotiated with the service owner
Devices are independentDependency order — the database before the app that needs it
One ring model fits allRings that follow criticality and tolerance for risk
Everything can eventually rebootA population that cannot — needing a different answer entirely
Rings still apply — canary servers first, then progressively more critical tiers — but the ring boundaries are drawn by blast radius and dependency, not by department. Patch the thing that everything else depends on last, in its own window, after its dependents have proven the patch is safe.
The Decision
The Server That Cannot Reboot Needs a Compensating Control, Not an Exception
Every estate has the machine that must not go down — the legacy application server, the OT gateway, the box running something nobody can rebuild. The wrong answer is a permanent patching exception, which is a quiet decision to leave a known vulnerability in place indefinitely. The right answer treats un-patchability as a risk to be compensated, not waived.
Instead of an exception…Compensate with
“It can never reboot”Network isolation — shrink what can reach it
“The vendor won't support the patch”Virtual patching / IPS (Intrusion Prevention System) in front; tighter monitoring
“We'll get to it”A named owner and a review date, so the risk is tracked, not forgotten
An unpatched server that is isolated, monitored, and on a register with an owner is a managed risk; the same server as a silent exception is an incident waiting for a date. The distinction is whether someone is accountable for it. For hypervisor hosts, the reboot problem has a different answer — Live Migration & Maintenance Mode — Patching Hosts Without an Outage — because the workloads can move off first.
