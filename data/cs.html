📉 Big-O in Practice — What the Notation Hides CS • Complexity ▶
Orientation
You Already Know What Big-O Measures; This Is Where It Misleads
Big O Notation — Measuring Algorithm Efficiency in the Scripting domain covers the notation itself. This card is the follow-up nobody gets taught: Big-O deliberately discards information, and the discarded information is what decides which code is faster on the machine you actually own.
The definition throws away constant factors and lower-order terms because it describes behaviour as n grows without bound. Real inputs are finite, often small, and run on hardware with a memory hierarchy that the model does not represent at all.
Where it breaks
Four Ways the Better Complexity Loses
SituationWhat actually happens
Small n Insertion sort beats quicksort below roughly 10–20 elements, which is why real sort implementations switch to it for small partitions rather than recursing further
Constant factors A linear scan of a contiguous array frequently beats a hash lookup for a few dozen items — no hashing, no pointer chasing, and the whole array is in cache
Memory layout A linked list and an array are both O(n) to traverse. The array can be an order of magnitude faster, because Big-O counts operations and cannot see cache misses
Worst vs typical Quicksort is O(n²) worst case and the usual default anyway, because that case is rare and its typical constant is excellent
The verdict: use Big-O to reject algorithms that will not survive growth, which is what it is genuinely good at. Do not use it to choose between two survivors — measure those, on representative data.
Failure mode
Optimising the Term That Was Never the Problem
The most common waste in performance work is improving an O(n²) loop over 200 items — microseconds — inside a request that spends 40 milliseconds waiting on a database. The complexity analysis was correct and the work was pointless.
Before optimising an algorithm, establish that computation is the cost. In most application code it is not: input/output dominates, and the useful numbers are the ones in Memory Layout & Cache Locality — Why Arrays Beat Linked Lists — roughly nanoseconds for memory, microseconds for local storage, milliseconds for a network round trip. Those three orders of magnitude decide more than an exponent usually does.
📊 Amortized Analysis — Why a Dynamic Array Is O(1) "On Average" CS • Complexity ▶
The idea
Averaging an Expensive Operation Across the Cheap Ones That Earned It
Appending to a dynamic array — a Python list, a Go slice, a C++ vector — is usually writing one value: O(1). Occasionally the backing store is full, and the whole thing is copied to a larger one: O(n). Calling append O(n) because of that would be true and useless.
Amortized analysis asks what a sequence of operations costs. Because the array grows by a constant factor — typically doubling — each resize is twice as expensive as the last but happens half as often. The copying work across n appends sums to less than 2n, so the average cost per append is constant.
The load-bearing detail is "by a factor". Growing by a fixed amount instead — 10 more slots each time — makes appending O(n) amortized, because resizes stop becoming rarer. This is a real bug people write when implementing their own buffer.
Distinction
Amortized Is Not Average-Case
MeansGuarantee
Average-caseExpected cost over a distribution of inputsProbabilistic — a bad input can defeat it
AmortizedWorst-case cost of a sequence, divided by its lengthGuaranteed — no input sequence beats it
Amortized is the stronger claim. Hash table lookup is average-case O(1), and an adversary who can choose keys can force collisions — see Hash Tables. Dynamic array append is amortized O(1), and no sequence of appends can make it worse.
Failure mode
Where the Average Is the Wrong Thing to Care About
Amortized guarantees say nothing about when the expensive operation lands. In a real-time or latency-sensitive path, the occasional O(n) resize is a latency spike, and "it averages out" is no comfort to the request that hit it. The same argument applies to garbage collection pauses.
The mitigations are the same in both cases: pre-size the structure if you know roughly how large it will get, or choose an implementation with worse average throughput and better worst-case bounds. Latency and throughput are different goals, and amortized analysis only speaks to the second. 
# Pre-sizing removes the resizes entirely when the size is known
buf = [None] * n_expected          # Python
buf := make([]int, 0, nExpected)     # Go: length 0, capacity reserved
⚖️ Time vs Space Trade-offs — What Caching Actually Costs CS • Complexity ▶
The pattern
Nearly Every Speed-Up Is Memory You Agreed to Spend
Precomputation, indexes, memoisation, lookup tables and caches are one idea in different clothes: store an answer so you do not compute it twice. The cost is memory, and — far more often the real problem — the obligation to keep the stored answer correct.
TechniqueBuysCosts
MemoisationRepeated calls become freeUnbounded growth unless evicted; wrong if the function is not pure
Database indexLookups go from scan to seekSlower writes, more disk, and a planner that may ignore it
Lookup tableArithmetic becomes an array readOnly wins if the table stays in cache
Denormalised copyNo join at read timeTwo sources of truth to reconcile
The verdict: the memory is the advertised cost and rarely the one that hurts. Invalidation is the real price — every cache is a claim that stored data still matches its source, and nothing enforces that claim for you.
Failure mode
A Lookup Table Bigger Than the Cache Is Slower Than the Maths
Replacing computation with a table assumes the read is cheap. Once the table exceeds the processor's cache, each read is a main-memory access of roughly a hundred nanoseconds — enough time to have executed hundreds of arithmetic instructions.
Modern processors are fast enough that recomputing a small value frequently beats looking it up. This is a genuine reversal from older guidance, and it is why measure is the whole answer here rather than a hedge.
🔁 Recursion & Induction — Trusting a Function That Calls Itself CS • Correctness ▶
The method
Do Not Trace It — Prove It
The reason recursion feels hard is that people try to simulate it mentally, unwinding each call. That does not scale past two levels. The working technique is induction, and it needs exactly three checks:
CheckAsk
Base caseIs there an input that returns without recursing, and is its answer right?
Inductive stepAssuming the call on a smaller input is correct, is my answer correct?
ProgressDoes every call move strictly toward the base case?
Assume the recursive call works. That is not a cheat — it is the inductive hypothesis, and it is the entire reason the technique exists. If all three checks hold, the function is correct, and you never traced a single call.
Failure mode
Progress Is the Check People Skip
Base case and inductive step are usually obvious. Progress is where real bugs live: recursing on n instead of n - 1 on one branch, or on a sub-list that is only sometimes smaller. The result is a stack overflow on a specific input rather than a wrong answer on all of them, which makes it a production bug rather than a test failure. 
# Progress fails when the pivot is the smallest element: the right
# partition never shrinks and the recursion never terminates.
def quicksort(a, lo, hi):
    if lo >= hi: return              # base case
    p = partition(a, lo, hi)
    quicksort(a, lo, p)              # BUG: should be p - 1
    quicksort(a, p + 1, hi)
Python defaults to a recursion limit near 1000 frames, which turns unbounded recursion into a clean exception. C and C++ have no such courtesy: the stack simply runs out, and a deep recursion on attacker-controlled input is a denial-of-service bug.
Practicalities
Tail Calls, and Why Python Will Not Help You
A tail call is a recursive call that is the last thing a function does. Some languages — Scheme, and most functional languages — are required to reuse the stack frame, making such recursion equivalent to a loop. Others, notably Python and CPython-adjacent runtimes, deliberately do not, because keeping the frames makes tracebacks readable.
The practical rule: recursion is the clearer expression for genuinely tree-shaped problems — parsing, directory walks, divide and conquer. For linear problems, write the loop. Where depth is bounded by data you do not control, convert to an explicit stack so the limit is memory you can measure rather than a frame count you cannot.
🧩 P, NP & Knowing When to Stop Looking for an Exact Answer CS • Tractability ▶
The distinction
Easy to Check Is Not the Same as Easy to Find
P is the set of problems solvable in polynomial time. NP is the set whose proposed answers can be verified in polynomial time. Every problem in P is in NP — checking is never harder than solving — and whether the reverse holds is the open question.
A useful example: given a schedule for 300 staff, confirming it satisfies every constraint takes seconds. Finding an optimal one may take longer than the age of the universe. Nothing about the checking speed implies anything about the finding speed, and that gap is the entire subject.
Why you care
Recognising One Saves You From Promising a Delivery Date
NP-complete problems are the hardest in NP: solve one efficiently and you have solved all of them. Nobody has, in over fifty years of trying. The practical consequence is that recognising your problem as one of them is a result, not a defeat — it tells you to stop searching for an exact efficient algorithm and change what you are promising.

The verdict: that last row is why package managers occasionally hang for a very long time. Dependency resolution is genuinely NP-complete, and the resolver is not badly written — it is running a solver on a hard instance.
What to do instead
Four Honest Exits

The failure mode is not choosing an exit: an exact algorithm ships, works on the test data, and hangs eighteen months later when a customer's input crosses a threshold nobody documented. Decide which guarantee you are dropping, and write it down where the next person will find it.
🧱 Memory Layout & Cache Locality — Why Arrays Beat Linked Lists CS • Data Structures ▶
Orientation
Which Structure to Pick Is Covered; This Is Why the Table Lies
Choosing the Right Data Structure in the Scripting domain has the operation-cost table. This card explains why that table mispredicts real performance so often: it counts operations, and the machine charges for memory access patterns.
Memory does not arrive one byte at a time. It arrives in cache lines, typically 64 bytes. Reading one integer from main memory fetches its fifteen neighbours whether you want them or not — so a structure whose elements sit next to each other gets the next fifteen reads nearly free.
The consequence
Same Big-O, Order-of-Magnitude Difference
ArrayLinked list
Traversal complexityO(n)O(n)
Elements per memory fetch~16 (64-byte line, 4-byte ints)1, plus a pointer to chase
Prefetcher can helpYes — the stride is predictableNo — the next address is unknown until arrival
Memory overheadNoneA pointer per element, often doubling the size
Genuinely better atEverything you iterateSplicing when you already hold the node
The verdict: linked lists are taught early and used rarely. Unless you need stable references to elements or O(1) splice with a node already in hand, an array or dynamic array wins — including for insert-in-the-middle at small sizes, because memmove of a contiguous block is extremely fast.
Applying it
Struct of Arrays, and Why Databases Went Columnar
If you process one field across many records, storing an array per field beats an array of records: the fetched cache lines contain only data you asked for. This is the same insight behind columnar storage — see Columnar Engines — Parquet, DuckDB & ClickHouse in the Data domain — and behind why a scan over a column store outruns a row store on analytics by so much. 
# Array of structs: summing one field drags every other field into cache
struct P { float x, y, z; char name[64]; };
P people[N];              # 76 bytes/record; ~0.8 useful bytes per line

# Struct of arrays: the summed field is contiguous
float xs[N], ys[N], zs[N];
char names[N][64];        # every fetched line is all x values
Do not reach for this by default — it makes code harder to read and only pays where a hot loop touches a subset of fields over many records. It is a profiling result, not a style.
#️⃣ Hash Tables — Collisions, Load Factor & the DoS (Denial of Service) That Exploits Them CS • Data Structures ▶
Mechanism
O(1) Is a Statement About Luck, Not a Guarantee
A hash function maps a key to a bucket index. Two keys landing in the same bucket is a collision, and it is not an edge case — by the birthday argument, collisions begin appearing once the table holds roughly the square root of its capacity in items. Every real implementation is mostly collision-handling machinery.
StrategyHowWeakness
ChainingEach bucket holds a listPointer chasing; degrades to a list under attack
Linear probingTry the next slot alongClustering, but excellent cache behaviour
Robin HoodProbe, stealing slots from luckier keysComplex deletion; very even probe lengths
Load factor — items divided by buckets — is the number that governs all of them. Beyond roughly 0.7 for open addressing, probe sequences lengthen sharply, so tables resize and rehash to stay under it. That resize is the same amortized cost described in Amortized Analysis, and the same latency spike.
Failure mode
Hash Flooding — Turning O(1) Into O(n) On Purpose
If the hash function is deterministic and public, an attacker can compute thousands of distinct keys that collide into one bucket. Every lookup then walks a long chain, and a single HTTP (HyperText Transfer Protocol) request with a crafted form body or JSON (JavaScript Object Notation) object consumes seconds of CPU (Central Processing Unit). One request, one core, no authentication needed.
This broke essentially every web framework simultaneously in 2011, because they all parsed request parameters straight into a hash table. The fix is hash randomisation: seed the hash function per process, so an attacker cannot precompute colliding keys. 
# Python randomises string hashing per process by default since 3.3.
# Same string, two processes, two hashes — that is the mitigation working.
$ python3 -c "print(hash('collide'))"
$ python3 -c "print(hash('collide'))"

# PYTHONHASHSEED=0 disables it. Only ever for reproducing a bug.
Never hard-code a hash seed in production, and never rely on iteration order. If you need a stable order, sort explicitly. Code that depends on dictionary ordering works until the day someone enables randomisation, and then fails somewhere unrelated.
Practicalities
Mutable Keys, and Equality That Disagrees With Hashing
A hash table's contract is that equal objects hash equally, and that a key's hash never changes while it is stored. Break either and entries become unreachable — present in memory, invisible to lookup, and undetectable by reading the calling code.
This is why Python refuses to hash a list, and why overriding equality without overriding hashing is a bug in Java, C# and Python alike. If you write one, write both, from the same fields, and make those fields immutable.
🌳 Trees — BST (Binary Search Tree), Balanced, Heap & Trie, and What Each Is Actually For CS • Data Structures ▶
Choosing
Four Trees, Four Different Jobs
"Tree" is not one structure. These four solve genuinely different problems, and confusing them is the usual reason someone reaches for the wrong one.
StructureAnswersReach for it when
BST / balanced treeOrdered lookup, range queries, predecessorYou need sorted order as well as lookup
HeapOnly "what is the minimum?"Priority queues, scheduling, top-k
TriePrefix matching, autocompleteKeys are strings sharing prefixes
B-treeOrdered lookup with few disk readsThe data is on disk — this is your database index
The verdict: if you only need "is this present?", a hash table beats all of them. Trees earn their place when order matters — range scans, nearest neighbours, or reading everything sorted without a sort.
Why balance
An Unbalanced BST Is a Linked List With Extra Steps
A plain BST built from already-sorted input degenerates completely: every insert goes right, and lookup becomes O(n). Since sorted input is extremely common — importing records by ID, replaying a log — this is the normal case rather than the pathological one.
Self-balancing variants (red-black, AVL) rotate on insert to keep depth logarithmic. You will rarely implement one; you should know that your language's ordered map is one, and that a hand-rolled BST in production code is a latent O(n).
Disk
B-trees Exist Because a Disk Read Is Enormous
A balanced binary tree over a million keys is about 20 levels deep. On disk that is 20 seeks, and a seek costs roughly a hundred thousand times a memory access. B-trees fix this by making each node hold hundreds of keys — one page — so the same million keys sit three levels deep and cost three reads.
This is the single most important structure in databases, and Indexes Explained — B-tree, Hash & Covering in the Data domain covers the query-planning side. The theory answer to "why not a binary tree on disk?" is: the memory hierarchy has a cliff in it, and B-trees are shaped around the cliff.
🕸️ Graphs — Representation, Traversal & the Four Algorithms Worth Knowing CS • Data Structures ▶
Recognising one
Most Hard Problems Are Graph Problems Wearing a Costume
Package dependencies, network topology, permission inheritance, build pipelines, service call chains, Active Directory attack paths — all graphs. Recognising the shape is most of the work, because the algorithms are standard once you have.

Failure mode
Traversal Without a Visited Set
Any graph with a cycle will loop forever if traversal does not record visited nodes. The same bug in a slightly different form — marking visited on dequeue rather than on enqueue — lets a node enter the queue many times, quietly turning a linear traversal into something far worse on dense graphs. 
from collections import deque

def bfs(adj, start):
    seen = {start}                     # mark on ENQUEUE, not on dequeue
    q = deque([start])
    while q:
        node = q.popleft()
        yield node
        for nxt in adj[node]:
            if nxt not in seen:
                seen.add(nxt)
                q.append(nxt)
Cycles also make "dependency resolution" fail in the field: a build system reporting a cycle is doing topological sort correctly, and the cycle is real. Fix the dependencies, not the tool.
🎲 Probabilistic Structures — Bloom Filters, HyperLogLog & Sketches CS • Data Structures ▶
The trade
Give Up Exactness, Get Constant Memory
These structures answer questions about enormous sets in kilobytes, by being wrong in a bounded and known direction. That last part is what makes them engineering tools rather than approximations: the error is one-sided, so you can build correct systems on top.
StructureAnswersWrong how
Bloom filterHave I seen this?False positives only — never a false negative
HyperLogLogHow many distinct?~2% error in ~12 KB, for billions of items
Count-min sketchHow often did this appear?Overestimates only — never under
The one-sidedness is the design. A Bloom filter saying "no" is definitive, so it is used as a cheap gate in front of an expensive check: databases consult one before reading a disk block, and a "no" skips the read entirely.
Bloom filters
A Bit Array, k Hashes, and No Deletion
Insert by hashing an item k ways and setting those k bits. Query by checking the same k bits: any zero means definitely absent; all ones means probably present. Nothing stores the item itself, which is why memory does not grow with item size.
You cannot delete. Clearing a bit would also delete every other item sharing it. The false-positive rate is fixed by bits-per-item and k, so the size must be chosen from the expected item count in advance — roughly 10 bits per item gives about 1%. Over-fill it and the rate climbs until every answer is "probably present".
Use one when a false positive costs only a wasted lookup, never where it costs correctness or safety. "Probably breached password" is a fine use; "probably authorised" is not.
🔤 Sorting & Searching — Why Your Language Picked the One It Did CS • Algorithms ▶
The real question
You Will Never Write a Sort; You Will Choose One By Accident
Implementing a sort is an interview exercise. The decision that matters in real code is which one your runtime already calls, because that choice determines whether your sort is stable, how it behaves on nearly-sorted data, and whether an adversary can push it into its worst case.
Used byAlgorithmStableChosen because
Python, Java objectsTimsortYesReal data arrives partly sorted; Timsort finds and merges existing runs
C++ std::sortIntrosortNoQuicksort speed, switching to heapsort to cap the worst case at O(n log n)
Rust sort_unstablePattern-defeating quicksortNoFastest in place; the stable version is offered separately and costs memory
DatabasesExternal merge sortUsuallyThe data does not fit in memory, which changes the problem entirely
Stability is the property that bites. A stable sort keeps equal elements in their original relative order, which is what makes "sort by date, then sort by name" produce what users expect. Do that with an unstable sort and the second pass silently scrambles the first — a bug that looks like a data problem.
Searching
Binary Search Is Easy to Describe and Famously Easy to Get Wrong
Binary search was published in 1946 and the first correct published implementation appeared in 1962. The standard Java version carried an overflow bug for nine years. The lesson is not that it is hard, but that off-by-one boundaries deserve real care — so call your standard library's version. 
# The classic bug: lo + hi overflows on large arrays in fixed-width ints.
mid = (lo + hi) // 2          # overflows in C/Java
mid = lo + (hi - lo) // 2     # does not

# Python: use the library. bisect returns an insertion point,
# which is more useful than a found/not-found boolean.
from bisect import bisect_left
i = bisect_left(sorted_items, target)
found = i < len(sorted_items) and sorted_items[i] == target
Sorting to enable one binary search is a losing trade: O(n log n) to save O(n). It pays only when you will search the same data many times — which is exactly the argument for a database index.
🗝️ Divide & Conquer, Greedy, Dynamic Programming — Recognising Which Applies CS • Algorithms ▶
Recognising
Three Strategies, and the Question That Separates Them
These are not interchangeable techniques to try in turn. Each requires a specific property of the problem, and applying one whose property does not hold produces an answer that is confidently wrong rather than slow.
StrategyRequiresFails how
Divide & conquerIndependent subproblems that recombineRecombination is harder than the split
GreedyA locally best choice is always globally safeSilently returns a suboptimal answer
Dynamic programmingOverlapping subproblems, optimal substructureState explosion — memory, not correctness
Greedy is the dangerous one. It is easy to write, usually plausible, and wrong in a way no test catches unless someone knew the optimum independently. Making change with coins of 1, 3 and 4: greedy takes 4+1+1 for six, while the optimum is 3+3. Before shipping a greedy algorithm, either prove the exchange argument or say plainly that the result is approximate.
DP in practice
Memoise the Recursion; Do Not Start With the Table
Dynamic programming is taught bottom-up, with a table and indices, which is why it has a reputation for being impenetrable. The practical route is the opposite: write the naive recursion, confirm it is correct, then add a cache. The result is the same complexity with none of the index arithmetic. 
from functools import lru_cache

# Naive recursion: correct, exponential, obviously right.
# One decorator makes it linear. That is the whole technique.
@lru_cache(maxsize=None)
def ways(n):
    if n < 0: return 0
    if n == 0: return 1
    return ways(n - 1) + ways(n - 2)
Convert to a bottom-up table only when you need it — to avoid recursion depth, or to drop memory from O(n) to O(1) by keeping just the rows still in use. Both are optimisations of a working solution, not the starting point.
🔡 String Algorithms — Matching, Edit Distance & Where Regex Fits CS • Algorithms ▶
Matching
Naive Search Is Usually Fine, Until the Data Is Adversarial
Checking a pattern at every position is O(n·m) worst case and close to O(n) on natural text, because mismatches happen early. Real substring search in a standard library is already better than naive, and the classic algorithms matter mainly for knowing why the worst case exists.
AlgorithmIdeaGood for
Knuth-Morris-PrattPrecompute how far to skip after a mismatchGuaranteed O(n + m), streaming input
Boyer-MooreMatch right to left, skip ahead on a bad characterLong patterns — often sublinear in practice
Rabin-KarpRolling hash, compare hashes not charactersSearching many patterns at once; plagiarism detection
Aho-CorasickA trie of all patterns, matched in one passThousands of patterns — intrusion detection, filters
Aho-Corasick is the one worth recognising operationally: it is how a signature engine scans traffic for ten thousand indicators in a single pass rather than ten thousand.
Failure mode
Catastrophic Backtracking — When a Regex Becomes a Denial of Service
A regular expression describing a regular language can be matched in linear time. Most production engines — Python, Java, JavaScript, PCRE — instead use backtracking, because it supports backreferences and lookaround. On a pattern with nested quantifiers, that backtracking can be exponential. 
# Nested quantifier over overlapping alternatives. Add one character
# to the input and the match time roughly doubles.
pattern = r"^(a+)+$"
subject = "a" * 30 + "!"        # no match, and it will take a while

# Mitigations, in order of preference:
#  1. Avoid nested quantifiers and overlapping alternations
#  2. Anchor, and make quantifiers possessive/atomic where supported
#  3. Use a linear-time engine (RE2, Rust regex) for untrusted patterns
#  4. Impose a timeout — the last resort, not the design
Never run a user-supplied regular expression on a backtracking engine. This is a real and regularly exploited class of outage, and it has taken down major services. If users must supply patterns, use an engine with linear-time guarantees.
Edit distance
Levenshtein Is Dynamic Programming You Will Actually Use
Edit distance counts the insertions, deletions and substitutions needed to turn one string into another. It powers spelling suggestions, "did you mean", fuzzy record matching and command-line typo correction, and it is the clearest small example of dynamic programming — a table where each cell depends on three neighbours.
It costs O(n·m) time and memory, so it does not scale to comparing one string against millions. The standard approach is to narrow candidates cheaply first — a prefix index, a trie, or blocking on a key — and compute edit distance only within the shortlist.
🎰 Randomised Algorithms — Sampling, Reservoirs & Monte Carlo CS • Algorithms ▶
Why randomise
Randomness Removes the Adversary's Advantage
A deterministic algorithm has a worst case, and anything that can choose your input can find it. Randomising a choice the algorithm makes means no fixed input is reliably bad — the same reasoning behind hash seed randomisation, and behind picking a random pivot in quicksort.
Two families worth telling apart: Las Vegas algorithms are always correct and take a random amount of time (randomised quicksort). Monte Carlo algorithms take bounded time and are occasionally wrong, with a probability you choose (primality testing).
Reservoir sampling
A Fair Sample From a Stream of Unknown Length
Take k items uniformly at random from a stream you cannot buffer and whose length you do not know in advance — log lines, telemetry, a large file. Keep the first k, then for item i replace a random one with probability k/i. Every item ends equally likely, in O(k) memory and one pass. 
import random

def reservoir(stream, k):
    keep = []
    for i, item in enumerate(stream):
        if i < k:
            keep.append(item)
        else:
            j = random.randint(0, i)     # inclusive
            if j < k:
                keep[j] = item
    return keep
This is how sampled logging and distributed tracing keep a representative slice without knowing the request volume ahead of time. The alternative people reach for — "keep every hundredth" — is not a uniform sample and correlates badly with periodic traffic.
Failure mode
The Wrong Random Number Generator
A default generator is built for speed and statistical quality, not unpredictability. Its output is reproducible from its seed, which is a feature for simulation and a vulnerability for anything security-relevant.
UsePythonNever use for
Simulation, sampling, shuffling display orderrandomTokens, passwords, keys, session IDs

Predictable password-reset tokens are a recurring real-world breach, and the code that produced them looked entirely reasonable. If the value protects something, use the cryptographic generator — it costs nothing here.

The verdict: the choice is about failure isolation more than performance. Threads share memory, which makes communication trivial and makes every shared variable a correctness problem. Processes make you say what you are sharing — which is why browsers and web servers put untrusted work in separate processes.
The cost
A Context Switch Is Cheap Directly and Expensive Indirectly
The direct cost — saving registers, swapping page tables — is on the order of a microsecond. The real cost is that the new task arrives to a cache full of the previous task's data, so it runs slowly until the cache refills. That indirect cost is invisible to every timer and can dominate.
This is why running far more runnable threads than cores makes throughput worse, and why thread-pool sizing is roughly core-count for CPU-bound work but much higher for I/O-bound work, where threads are blocked rather than competing.
Measure switches directly before theorising: vmstat 1 reports context switches per second in the cs column, and pidstat -w attributes them per process. A high voluntary switch count means blocking on I/O (Input/Output); a high involuntary count means CPU (Central Processing Unit) contention. Those two point at opposite fixes.
🗺️ Virtual Memory — Paging, the TLB (Translation Lookaside Buffer) & Swap's Bad Reputation CS • Operating Systems ▶
The mechanism
Every Address Your Program Uses Is a Lie the Kernel Maintains
Programs address virtual memory; hardware translates each access to a physical address through page tables. That indirection buys isolation between processes, memory that can be larger than RAM (Random Access Memory), and shared read-only pages — one copy of a library serving every process using it.
Translation itself would be ruinously slow if performed every access, so the processor caches recent translations in the TLB. A TLB miss costs a page-table walk; this is why large pages exist, and why a workload with a scattered access pattern can be slow for reasons no profiler attributes to memory.
Reputation
Swap Is Not the Problem — Thrashing Is
"Disable swap for performance" is common advice and mostly wrong. Swap lets the kernel evict pages that are genuinely never touched — initialisation code, an idle daemon — and use the reclaimed memory as cache. A system with swap and no swapping is healthier than one without swap.
The pathology is thrashing: the working set exceeds RAM, so pages are evicted and immediately faulted back. Throughput collapses because every access waits on storage. Disabling swap does not fix that — it converts a slow system into one where the out-of-memory killer terminates something instead.
Watch the paging rate, not the swap usage. Used swap is a historical fact and often harmless; si/so in vmstat staying non-zero is the live problem. The two get confused constantly, and only the second is an incident.
🔐 Concurrency Primitives — Mutexes, Semaphores, Conditions & Atomics CS • Operating Systems ▶

Failure mode
The Lock You Held for Too Long
The most common concurrency bug in production is not a race — it is a mutex held across something slow. A lock held during a network call or a disk write turns a concurrent service into a serial one, and the symptom is latency that climbs with load while CPU (Central Processing Unit) stays low. 
# Serialises every caller behind one network round trip
with lock:
    row = db.fetch(key)          # slow, and holding the lock
    cache[key] = transform(row)

# Do the slow work outside; hold the lock only for the shared state
row = db.fetch(key)
value = transform(row)
with lock:
    cache[key] = value           # may overwrite a concurrent write — usually fine
The second version can do duplicate work under contention. That is nearly always the right trade: duplicated computation is cheap, and a serialised service is not. Decide deliberately rather than by where the with happened to go.
🔒 Deadlock & Livelock — The Four Conditions, and Which One to Break CS • Operating Systems ▶
Diagnosis
Deadlock Needs All Four; Removing Any One Prevents It
ConditionBreak it by

Lock ordering is the practical fix. Define an order — by address, by identifier, by name — and require every code path to acquire in that order. The classic deadlock is two account transfers running in opposite directions; ordering by account number removes it entirely, and costs one comparison.
Livelock
Everything Is Running and Nothing Is Progressing
Livelock is deadlock's harder-to-spot relative: threads are not blocked, they are busy responding to each other and never advancing. Two people stepping aside in a corridor, repeatedly. It is worse than deadlock diagnostically, because CPU (Central Processing Unit) is busy and every thread looks alive.
The usual cause is a naive retry: detect a conflict, back off, retry immediately, collide again. Fix it the same way networks did — exponential backoff with jitter. Without jitter, retries stay synchronised and collide in lockstep forever.
Database deadlocks are normal and expected. The engine detects a cycle and aborts one transaction with a retryable error — so application code that talks to a database must handle deadlock as a retry case, not as a fatal exception. Code that does not is the source of the intermittent failures nobody can reproduce.
💾 Filesystems From the Inside — Inodes, Journaling & Crash Consistency CS • Operating Systems ▶
Structure
A Filename Is a Pointer, Not the File
The file is the inode: metadata plus the location of its data. A directory entry is just a name pointing at an inode number. Several names may point at the same inode — hard links — and the data survives until the last one is removed.
Two consequences that explain real behaviour. Deleting a file being held open by a process frees no space, because the descriptor is still a reference — which is why a disk can stay full after deleting a log, until the writer is restarted. And "disk full" with free space showing means inode exhaustion: millions of tiny files, checkable with df -i, which almost nobody runs first.
Crash consistency
Journaling Protects the Filesystem, Not Your Data
A write touches several structures — the data, the inode, the free-space map. Interrupted halfway, the filesystem is inconsistent. A journal records the intent first, so recovery replays or discards the whole operation and the structure is always valid.
The default mode journals metadata only, because journaling data as well halves write throughput. So after a crash the filesystem mounts cleanly and a file may still contain garbage or an old version: the guarantee is about the filesystem, not the file contents, and that distinction disappoints people at the worst moment. 
# The durability sequence applications must actually perform
# A write() is in the page cache, not on the device.
fd = os.open(path, os.O_WRONLY | os.O_CREAT)
os.write(fd, data)
os.fsync(fd)                     # the file's data is now durable
os.close(fd)
dir_fd = os.open(os.path.dirname(path), os.O_RDONLY)
os.fsync(dir_fd)                 # and now its NAME is durable too
The second fsync is the one everybody omits. Renaming a temporary file into place is atomic, but the directory entry itself is buffered — crash before that is flushed and the file is durable under a name that no longer exists. This is the bug behind a well-known class of "my config file was empty after a power cut".
🕰️ Time in Distributed Systems — Why Timestamps Cannot Order Events CS • Distributed ▶
The problem
Two Clocks Never Agree, and One of Them Runs Backwards
Ordering events across machines by wall-clock timestamp is the most common distributed systems mistake, because it looks like it works. Clocks drift, and NTP (Network Time Protocol) corrects them by stepping — which means a timestamp can go backwards, and two events can carry identical times.
The consequences are real: last-write-wins silently discards the wrong update, log correlation across services shows effects before causes, and a certificate can appear expired on one host and valid on another.
Use a monotonic clock for durations and a wall clock only for display. Measuring elapsed time by subtracting two wall-clock readings is a bug that surfaces rarely and confusingly — every mainstream language offers a monotonic source precisely for this.
The alternative
Logical Clocks Count Causality Instead of Seconds
A Lamport clock is a counter each node increments on every event and sends with every message; a receiver takes the maximum of its own and the sender's, plus one. This guarantees that if A caused B then A's number is lower — but not the reverse, so a lower number does not prove causality.
A vector clock carries one counter per node, which does capture the reverse: comparing two vectors tells you that one happened before the other, or that they are genuinely concurrent — neither caused the other.
Detecting concurrency is the point. Concurrent writes are a real conflict, and a system that knows this can surface both versions and ask, rather than silently picking the one with the larger timestamp. The cost is a vector that grows with the number of nodes, which is why production systems bound it or use hybrid logical clocks instead.

📡 Failure Detection & FLP — Why "Is It Down?" Has No Perfect Answer CS • Distributed ▶
The result
A Slow Node and a Dead Node Are Indistinguishable
If a node has not replied, it may be dead, or overloaded, or the network may have dropped the reply. From the outside these are identical, and no amount of waiting resolves the ambiguity — waiting longer only reduces how often you are wrong.
The FLP result proves this is fundamental: in an asynchronous system where even one node may fail, no algorithm can guarantee consensus in bounded time. Real systems get around it not by beating the proof but by adding timeouts — accepting that they will occasionally declare a live node dead.
Every timeout is a guess about the network. Too short and you evict healthy nodes during a traffic spike, causing the outage you were detecting. Too long and real failures go unnoticed. There is no correct value — only one tuned to your network's actual latency distribution.
Consequences
Fencing, Because the Old Leader May Not Know It Was Replaced
A node declared dead and replaced may still be running — paused by garbage collection, or on the far side of a partition. When it resumes it believes it is still the leader and may write. That is split-brain, and it corrupts data rather than causing downtime.
The standard defence is a fencing token: every leadership term carries a monotonically increasing number, and the storage layer rejects any write bearing a number lower than the highest it has seen. The stale leader's writes are refused by the resource itself rather than by agreement it cannot participate in.
This is why distributed locks are harder than they look. A lock with a lease and no fencing is not safe — the lease can expire while the holder is paused, and the holder has no way to notice before it writes. If you are implementing one, the token is not optional.

Consequence
Cache Lines Explain False Sharing
Memory moves in 64-byte lines, and cache coherency operates on whole lines. Diagnose it by suspicion rather than by profiler: the signature is negative scaling with thread count on a workload that should be embarrassingly parallel. 🔢 Number Representation — Two's Complement, IEEE-754 & the Bugs Each Causes CS • Architecture ▶
Integers
Overflow Is Silent, and the Minimum Has No Positive Twin
Two's complement represents negatives by inverting and adding one, which is why addition and subtraction need no special cases — and why the range is asymmetric. A 32-bit int spans −2,147,483,648 to 2,147,483,647: one more negative than positive.
So abs(INT_MIN) is negative. Negating the minimum overflows, and in C that is undefined behaviour the optimiser may assume cannot happen. The classic exploitable form is a length check passing because an attacker-supplied size overflowed to negative, and the subsequent allocation being far too small.
Floats
0.1 + 0.2 Is Not 0.3, and Money Is Not a Float
IEEE-754 stores a sign, an exponent and a fraction in base two. Tenths are not representable in base two any more than a third is in base ten, so the stored value is the nearest representable one and the error compounds across operations. 
# Not a language quirk — the hardware representation, everywhere
>>> 0.1 + 0.2 == 0.3
False
>>> from decimal import Decimal
>>> Decimal("0.1") + Decimal("0.2") == Decimal("0.3")
True
Store money as integer minor units, or as a decimal type. Never as a float. And never compare floats with == — compare against a tolerance appropriate to the magnitudes involved, because a fixed epsilon is wrong at both ends of the range.
Failure mode
The Special Values That Propagate Silently
IEEE-754 defines infinities, two zeros, and NaN (Not a Number). NaN is the dangerous one: it is not equal to itself, so a single NaN entering a pipeline propagates through every arithmetic operation and survives most validity checks written as comparisons.
A metric that reads NaN on a dashboard usually entered as a division by zero many steps upstream. Check with the language's dedicated predicate — math.isnan(), not x == float('nan'), which is always false. And note that x != x being true is the portable NaN test, which looks like a bug and is not.
👻 Speculative Execution & Its Security Cost — Spectre and Meltdown CS • Architecture ▶
Why processors guess
Waiting for a Branch Wastes a Hundred Cycles, So the CPU (Central Processing Unit) Does Not Wait
Instructions execute in a pipeline, several in flight at once. A conditional branch stalls it — the processor cannot know which way to go until the condition resolves, and if that depends on memory, resolving may take hundreds of cycles.
So it predicts, and executes ahead speculatively. If the guess was right, the work is already done. If wrong, the architectural results are discarded. Modern prediction accuracy is well above 95%, and this is a large part of why processors are fast.
The flaw
Discarded Work Leaves Traces in the Cache
Speculation discards architectural state — registers, memory. It does not undo microarchitectural state: data loaded during a mis-speculation stays in the cache. An attacker who can time cache access can therefore learn something about speculatively-read memory they were never permitted to read.
MeltdownSpectre
AbusesOut-of-order execution past a permission checkBranch prediction, trained by the attacker
ReadsKernel memory from user spaceMemory within the victim's own address space
Fixable in softwareYes — page table isolationNot generally; it is mitigated, not fixed
Spectre is the one that matters, because it is a property of speculation itself. Meltdown was an implementation bug and was fixed. Spectre is mitigated per-pattern — compiler barriers, index masking, isolating untrusted code in its own process — and new variants keep arriving, because the underlying optimisation is not going away.
What it means for you
Process Isolation Stopped Being Paranoia
Practical consequences most engineers actually meet: browsers reduced timer precision and put each site in its own process; cloud providers stopped co-locating untrusted tenants on one physical core; and mitigations cost real performance — single-digit to low-double-digit percentages on system-call-heavy workloads.
The transferable lesson is broader than these vulnerabilities: an abstraction that is correct architecturally can still leak through its implementation. Timing, cache state and power draw are all side channels, and none of them appear in the model the code was written against.
⚙️ Instruction Execution — Pipelining, Superscalar & Why Branches Are Expensive CS • Architecture ▶
The model
A Processor Is an Assembly Line, Not a Loop
The textbook cycle — fetch, decode, execute, write back — describes one instruction. Real processors overlap them, so while one instruction executes, the next is decoding and a third is being fetched. Throughput approaches one instruction per cycle even though each takes several.
Superscalar designs go further and issue several instructions per cycle across duplicated units, and out-of-order execution reorders them around stalls. The consequence worth internalising: instruction count is a poor predictor of speed. What matters is whether the pipeline stays full.
Stalls
Three Ways to Empty the Pipeline
HazardCauseMitigated by
DataAn instruction needs a result not yet producedForwarding; reordering
ControlA branch — which instruction comes next is unknownPrediction, and speculation
StructuralTwo instructions want the same unitDuplicating units
A mispredicted branch costs 15–20 cycles — the pipeline is flushed and refilled. Prediction is well above 95% accurate on typical code, which is exactly why unpredictable branches are so costly: a condition that is genuinely random defeats the predictor every other time.
Applying it
Sorting the Input Made the Loop Faster — and It Is Not a Trick
The famous demonstration: a loop summing values above a threshold runs several times faster over sorted data than unsorted, with identical instruction counts. Sorted input makes the branch predictable — long runs of taken, then long runs of not-taken — and the predictor gets it right almost every time.
The engineering lesson is not "sort your data". It is that branchless code can beat branching code where the condition is unpredictable: a conditional move, arithmetic on the comparison result, or a lookup table has no branch to mispredict. Worth reaching for only in a measured hot loop — it is harder to read, and the compiler often does it already.

♻️ Garbage Collection — Generational Collectors, Pauses & Tuning CS • Runtimes ▶
The core idea
Most Objects Die Young, and Collectors Are Built Around That
The generational hypothesis is an empirical observation: the overwhelming majority of allocations become garbage almost immediately. Collectors exploit it by splitting the heap — new objects in a small young generation collected frequently and cheaply, survivors promoted to an old generation collected rarely.
A young collection is fast because it costs time proportional to the objects that survived, not to the garbage. Allocating a million short-lived objects is nearly free to collect; keeping a million alive is what costs.

The Compiler Is Allowed to Assume It Never Happens
In C and C++, undefined behaviour does not mean "unpredictable result" — it means the standard imposes no requirement at all, so the optimiser may assume it cannot occur and reason from there. This is why a null check after a dereference can be deleted: the dereference already implied the pointer was non-null. 
// The dereference tells the optimiser p cannot be null,
// so the check below is dead code and may be removed.
int v = *p;
if (p == NULL) return ERROR;   // deleted at -O2
Undefined behaviour is not a runtime concept. It changes what the compiler emits, which is why a bug can appear only at higher optimisation levels, or only after a compiler upgrade, and why "it works in debug" proves nothing.
What to do
Sanitisers Now, Safer Languages at the Boundary
Rewriting a working C codebase is rarely justified. The standard advice — from the same organisations that published the 70% figure — is to write new code in a memory-safe language and prioritise the parts that parse untrusted input, which is where the exploitable bugs concentrate. 
# Catch it in CI rather than in a CVE. Both are cheap to enable.
clang -fsanitize=address,undefined -g -O1 prog.c
valgrind --leak-check=full ./prog
Sanitisers find these bugs only on code paths your tests actually execute — so their value is bounded by coverage, and pairing them with fuzzing is what makes the combination effective. Rust's guarantee is stronger precisely because it is a property of the type system rather than of the tests.
🌳 Merkle Trees — Verifying and Diffing Huge Data by Comparing Hashes CS • Data Structures ▶
The Inversion
Prove Two Copies of a Terabyte Are Identical by Comparing 32 Bytes
The obvious way to check whether two large datasets match is to read both and compare them — linear in the size of the data, and impossible when the two copies are on different continents. A Merkle tree turns that into comparing one hash. Hash every block, then hash each pair of hashes, and again, up to a single root hash. If two roots match, the datasets are identical, with the same confidence as the underlying hash function — and if they differ, the tree tells you not just that they differ but where, in a logarithmic walk rather than a full scan.

Which blocks differ?Read and compare everythingWalk down the mismatching branches — O(log n) exchanges

The recursive rule is the whole idea: if two subtree hashes are equal, everything under them is equal — skip it entirely. You only descend into the parts that changed, which is why a Merkle tree makes synchronising two nearly-identical copies cost a function of the difference, not of the total size.
Where It Shows Up
The Same Structure, Under Five Systems You Already Use
Merkle trees rarely appear by name, which is why they are worth learning once: you meet them repeatedly wearing different clothes. Every one of these is the same "hash the children up to a root" trick applied to a different verify-or-sync problem.
SystemWhat the tree buys it
GitA commit is a hash of a tree of hashes; identical subtrees are stored once, and history is tamper-evident
BlockchainsA block commits to all its transactions in one root; a light client verifies a payment without the whole chain
Certificate TransparencyAn append-only log proves a certificate was included, and proves the log never rewrote history
Backup & sync (rsync-style, ZFS, Dynamo)Anti-entropy: two replicas compare trees and ship only the blocks that differ

The unifying property is tamper-evidence plus cheap diffing: any change, anywhere, changes the root, and the tree localises the change without a linear scan. That is why the structure recurs anywhere data must be verified or reconciled across a slow or untrusted link.
The Scope Line
It Verifies and Diffs. It Does Not Search, and It Does Not Encrypt.
A Merkle tree is easy to over-credit. It is not a search structure — it will not find an item by key the way a Hash Tables — Collisions, Load Factor & the DoS That Exploits Them table or a B-tree does; it answers "are these the same?" and "what differs?", not "where is X?". It provides integrity, not confidentiality — the leaves can be plaintext, and the tree still detects tampering, but it hides nothing. And it is append-friendly, insert-hostile: adding to the end is cheap, but inserting at the front rewrites every hash above it.
Its entire security rests on the hash being collision-resistant — the day the hash function breaks, the tree's guarantee breaks with it, which is why systems built on Merkle trees care so much about which hash they chose. Reach for one whenever you must verify or reconcile large, mostly-unchanged data over an expensive or untrusted channel; reach for something else when the job is lookup. It is the same "let the hash do the work" instinct that Consistent Hashing — Adding a Server Without Moving Everything applies to placement rather than verification.
🔀 CRDTs — Merging Without Coordination, and What They Cannot Do CS • Distributed Systems ▶
The Inversion
Give Up Ordering. Design the Data So Every Merge Order Lands on the Same Answer.
Two replicas edit the same document offline — a phone in a tunnel, a laptop on a plane — and later reconnect. The usual answers are to pick a winner (last-write-wins, which Time in Distributed Systems — Why Timestamps Cannot Order Events shows silently discards the loser's work) or to force coordination (nobody edits without a lock). A conflict-free replicated data type takes a third path: it makes the merge operation commutative, associative and idempotent, so that applying the updates in any order, any number of times, converges to the same state — no central authority, no locks, no conflict dialog. The ordering problem is not solved; it is designed out.
Merge propertyWhat it guarantees
Commutative (a·b = b·a)The order updates arrive in does not matter
AssociativeHow you group and batch merges does not matter
Idempotent (a·a = a)Re-delivering the same update — which unreliable networks do — changes nothing
Those three properties are the whole trick: together they mean replicas that have seen the same set of updates are in the same state, regardless of the path each took to get there. That is strong eventual consistency — convergence with no coordination on the write path — and it is why an offline-first app can let everyone edit and still agree later.
The Fingerprint
The Families, and the Cost Each One Hides
“CRDT” is a family, not a single structure, and the interesting part is what each member gives up to guarantee convergence. The recurring cost is metadata: to merge correctly without a coordinator, a CRDT often has to remember more than the value itself — and that bookkeeping can outgrow the data.
TypeMerges byThe catch
Counter (G-Counter / PN-Counter)Per-replica tallies, summedGrows with the number of replicas, not the count
Set (G-Set, OR-Set)Union, with add/remove tagsRemoves need tombstones, or a re-add is lost
Register (LWW / multi-value)A rule for concurrent writesLWW drops data; multi-value hands you the conflict to resolve
Sequence (text / RGA)Stable positions between elementsTombstones for deletes; metadata can dwarf the text
The tombstone problem is the fingerprint: a naive set CRDT that deletes an element must remember it deleted it, forever, or a concurrent add resurrects it. That is why production CRDTs work hard at garbage-collecting metadata — and why “just use a CRDT” is a bigger commitment than it sounds.
The Scope Line
CRDTs Give Convergence, Not Consensus — They Cannot Enforce a Global Invariant
This is the boundary that matters and the one most often crossed. A CRDT guarantees the replicas agree eventually; it cannot guarantee the agreed-on state satisfies a rule that spans replicas. Two people can both book the last seat offline, and both merges succeed — the set happily contains both bookings. You cannot express “balance never goes negative” or “at most one winner” as a CRDT, because enforcing it requires seeing all the concurrent updates before deciding, which is coordination — exactly what a CRDT was designed to avoid.
So the decision is clean. Reach for a CRDT when concurrent, possibly-offline edits must merge without a central authority and eventual consistency is acceptable — collaborative editors, presence, shopping carts, multi-region caches. Reach for Consensus — Raft and Paxos, Without the Paper when a hard invariant must hold globally, and pay the coordination cost knowingly. Most real systems use both: consensus for the few operations that need an invariant, CRDTs for the many that only need to converge.
🕐 Modular Arithmetic — The Clock Maths Behind Hashing, Checksums & Crypto Applied Maths ▶
Concept
Counting on a Clock That Wraps
Modular arithmetic is ordinary arithmetic on a finite circle: everything is reduced to its remainder after division by some modulus. It is not a niche topic — it is what makes hash tables index, what makes checksums detect corruption, what makes sequence numbers wrap cleanly, and what public-key cryptography is built from. Anywhere a computer maps unbounded values into a bounded space, this is the operation doing it. 
# "a ≡ b (mod n)" means a and b leave the same remainder when divided by n
   17 ≡ 5 (mod 12)        # 17:00 is 5 o'clock
   -1 ≡ 11 (mod 12)       # going back an hour from midnight

# Arithmetic survives the reduction — you may reduce at any point
   (a + b) mod n = ((a mod n) + (b mod n)) mod n
   (a · b) mod n = ((a mod n) · (b mod n)) mod n

# which is why huge modular exponentiations stay computable:
   7^100 mod 13  # never needs 7^100 to be written down

🔲 Boolean Algebra — Truth Tables, De Morgan & Firewall Logic Applied Maths ▶
Reference
The Laws Worth Knowing by Heart
Boolean algebra is where firewall rules, search queries, access-control expressions and conditionals all live. Two laws do most of the practical work: De Morgan's, for negating a compound condition correctly, and distribution, for restructuring a rule without changing what it matches. 
# De Morgan — the one people get wrong under pressure
   NOT (A AND B)  =  (NOT A) OR  (NOT B)
   NOT (A OR  B)  =  (NOT A) AND (NOT B)

# Distribution
   A AND (B OR C) = (A AND B) OR (A AND C)
   A OR  (B AND C) = (A OR B) AND (A OR C)

# Absorption — spots redundant clauses in a grown-over rule set
   A OR  (A AND B) = A
   A AND (A OR  B) = A
"Block everything that is not HTTP (HyperText Transfer Protocol) and not from the office" is a De Morgan problem, and getting it backwards produces a rule that blocks nothing at all — while looking, in the console, exactly like the rule that was intended.

🎲 Probability Fundamentals — Independence, Conditional Probability & Expectation Applied Maths ▶
Reference
Four Rules That Cover Most Engineering Uses
Very little probability is needed to reason well about availability, retries, collisions and alert volumes — but the little that is needed has to be right, because the intuitions are actively misleading. 
# 1. Independent events multiply
   P(A and B) = P(A) · P(B)          # only if independent

# 2. "At least one" is easier through its complement
   P(at least one of n) = 1 - (1 - p)^n

# 3. Conditional probability
   P(A | B) = P(A and B) / P(B)

# 4. Expectation is a weighted average, and it adds — always
   E[X] = Σ (value · probability)
   E[X + Y] = E[X] + E[Y]            # even when X and Y are dependent
Concept
The Independence Assumption Is Where Availability Maths Goes Wrong
Redundancy calculations multiply failure probabilities, which is only valid when failures are independent. Real systems share racks, power feeds, network paths, certificates, control planes and deployment pipelines — so the correlated case is the normal case, and the calculated number is an upper bound on reality rather than an estimate of it. 
# Three servers, each 99% available, "so we get 99.9999%"
   P(all three down) = 0.01^3 = 0.000001

# True only if the three fail independently. They do not if they share:
   - the same power feed or rack
   - the same expiring TLS certificate
   - the same config push
   - the same upstream dependency
   - the same bug, deployed to all three at 14:00
The last line is the one that causes real outages. A simultaneous deployment makes three servers one server, statistically — and no amount of hardware redundancy addresses it.
Technique
Expectation, Applied to Retries and Alert Volume
Expectation answers "how much of this should we expect per day", which is the question behind capacity, on-call load and retry budgets. Its most useful property is that it adds even when events are dependent, so a total can be built from parts without worrying about correlation. 
# Alert volume from one rule
   E[alerts/day] = events/day · P(rule fires | event)

# Retries: expected attempts until success, p = success probability
   E[attempts] = 1 / p            # p = 0.5 -> 2 attempts on average

# Careful: the average is not the tail. With p = 0.5,
# about 1 request in 1,000 still needs 10 or more attempts.
That last comment is the whole reason retry budgets and circuit breakers exist: systems are sized for the average and taken down by the tail.
🧮 Bayes' Theorem & Base Rates — Why a 99%-Accurate Detector Floods the SOC (Security Operations Center) Applied Maths ▶
Concept
The Single Most Useful Piece of Maths in Security Operations
Detector accuracy is quoted as a property of the detector. It is not: the probability that an alert is real depends just as much on how rare the thing being detected is. When the base rate is low — and in security it is always low — even an excellent detector produces mostly false positives, and no amount of vendor benchmarking changes that arithmetic. 
   P(real | alert) = P(alert | real) · P(real)
                     ─────────────────────────────
                              P(alert)

# Worked: 1,000,000 events/day, 100 of them malicious (1 in 10,000)
# Detector: catches 99% of real ones, 1% false-positive rate

   true positives  = 100 × 0.99            =     99
   false positives = 999,900 × 0.01        =  9,999
   ────────────────────────────────────────────────
   P(real | alert) = 99 / (99 + 9,999)     ≈  0.98%

# 99% accurate. 1 alert in 100 is real. Both statements are true.
Technique

The arithmetic is not a counsel of despair; it tells you precisely which levers move the outcome, and which do not. Chasing a higher true-positive rate barely matters — the denominator is dominated by false positives.

Latency is the one that catches people. It is not normal, it has no meaningful "average case", and its tail is where the user experience actually lives — so summarising it with a mean and a standard deviation discards precisely the information that mattered.

Independent random events arrive in clusters — that is what randomness looks like, not what a problem looks like.    P(0) = 37%      P(1) = 37%      P(2) = 18%      P(3+) = 8%

# So ~1 month in 4 sees two or more failures, with nothing having changed.

p99 = 200ms means 99% of requests completed within 200ms. It says nothing about how bad the remaining 1% was — p99 and p99.9 can differ by two orders of magnitude, and frequently do. 🎂 The Birthday Paradox & Collisions — Hash Collisions, ID Reuse & Key Spaces Applied Maths ▶
Concept
Collisions Arrive at the Square Root, Not at the Size
Intuition says a space of N values needs roughly N items before two coincide. The truth is about √N, because collisions depend on the number of pairs, which grows quadratically. Twenty-three people give a better-than-even chance of a shared birthday out of 365 days — and the same arithmetic decides when a hash function, an ID scheme or a token space starts repeating. 
# Pairs among n items grow as n(n-1)/2 — that is the engine of it
   n = 23  ->  253 pairs  ->  P(shared birthday) ≈ 50%

# For a space of N possible values, a 50% chance of collision at roughly
   n ≈ 1.18 · √N

# Which for hash outputs means:
   32-bit  (4.3e9)     ->  collisions at ~77,000 items      # trivially reachable
   64-bit  (1.8e19)    ->  collisions at ~5 billion
   128-bit (3.4e38)    ->  collisions at ~2^64
   256-bit             ->  collisions at ~2^128             # not reachable
The 32-bit row is the practical warning. A 32-bit hash used as a unique key will collide in a table of a hundred thousand rows, and the resulting bug — two different things treated as one — is the kind that corrupts data quietly rather than crashing.
Reference
Where This Decides a Real Design Choice
Every identifier scheme is a bet that collisions will not happen at the scale you reach. The square-root rule is how to check the bet before making it.
ChoiceThe birthday consequence
Random 128-bit identifiersSafe at any realistic scale — the standard reason they are 128 bits
Truncating a hash to 8 hex characters32 bits; expect collisions in the tens of thousands
Short URL (Uniform Resource Locator) codes, 6 charactersCheck √N against your growth, or plan for retries on collision
Session tokensCollision is a security event, not just a bug — size for it

The last row is why hash sizes are what they are. Collision resistance is worth half the output length, so a 128-bit hash offers only 64 bits against a birthday attack — reachable, which is exactly why it was retired.
🔀 Entropy & Randomness — Measuring It, and Where Implementations Lose It Applied Maths ▶
Concept
Entropy Measures Uncertainty, Not Messiness
Shannon entropy is the average number of bits needed to describe an outcome drawn from a distribution. It is a property of the process that produced a value, not of the value itself — which is the point most password-strength meters get wrong. A password produced by flipping coins has its entropy no matter how tidy it looks; one produced by substituting characters in a dictionary word has very little, however messy it looks. 
   H = - Σ p(x) · log₂ p(x)          # bits

# Uniform choice from N equally likely options:
   H = log₂(N)

# A password of L characters chosen uniformly from an alphabet of size A:
   H = L · log₂(A)

   12 chars, lower+upper+digits (A=62)  ->  12 × 5.95  ≈  71 bits
   4 random words from a 7,776-word list ->  4 × 12.9  ≈  52 bits
   "P@ssw0rd!"                           ->  a few bits — it is on every list
The third line is the honest one. Entropy formulas assume uniform random choice; the moment a human chooses, the assumption fails and the number is fiction.
Troubleshooting
Where Real Systems Lose Their Randomness
Cryptographic failures caused by weak randomness are among the most damaging and least visible, because the output looks entirely normal. Every item here has caused real, documented compromises.
FailureConsequence
Using the language's default random()Predictable from a few outputs — never for keys, tokens or salts
Seeding from the clockThe seed space is tiny and guessable
Key generation at first bootEmbedded devices with no entropy source generate duplicate keys across a whole fleet
Virtual machines cloned from a snapshotEvery clone continues from the same state
Reusing a nonce or IVCatastrophic for stream ciphers and some modes — recovers plaintext or the key
The rule that avoids all five: take randomness from the operating system's cryptographic source — /dev/urandom, getrandom(), the platform CSPRNG (Cryptographically Secure Pseudorandom Number Generator) — and never from anything you seeded yourself.
Concept
Entropy Is Also Why Compression and Encryption Do Not Mix Well
Compression works by removing redundancy — that is, by raising the entropy per byte toward the maximum. Properly encrypted data already has maximum entropy, so it cannot be compressed at all, which is why archives must be compressed before encryption. And compressing before encrypting leaks information through the resulting length, which is the mechanism behind several web attacks: the size of the ciphertext reveals how well the plaintext compressed, and therefore something about what was in it.
🔑 Primes & Factoring — Why RSA (Rivest-Shamir-Adleman) Rests on a Hard Problem Applied Maths ▶
Concept
Easy One Way, Hard the Other
Public-key cryptography rests on operations that are cheap to perform and expensive to reverse. RSA's is multiplication: multiplying two large primes takes microseconds, and recovering those primes from the product is, as far as anyone knows publicly, infeasible at the sizes in use. Nothing proves it is hard — that is the uncomfortable part — but a great deal of effort has failed to make it easy. 
# Trivially easy
   p × q = n                       # two 1024-bit primes -> a 2048-bit modulus

# Believed infeasible for large n
   n -> (p, q)

# The security is not "big numbers" — it is the gap between the two costs.
# Trial division would need ~2^1024 steps. The best known methods are far
# faster than that and still nowhere near feasible at 2048 bits.
Reference
Why Key Sizes Are the Numbers They Are
RSA key sizes are large and grow awkwardly, because the best factoring algorithms are sub-exponential: adding bits raises the attacker's cost more slowly than it would for a symmetric cipher. That is the whole reason a symmetric key of 128 bits and an RSA key of 3072 bits are considered comparable.

📐 Discrete Logs & Elliptic Curves — The Other Hard Problem, and Why Keys Shrank Applied Maths ▶
Concept
Exponentiation Is Easy; Undoing It Is Not
The second hard problem underpinning public-key cryptography is the discrete logarithm: given g, p and g^x mod p, recover x. Computing the power is fast even for enormous exponents; recovering the exponent is not. Diffie–Hellman key agreement is this asymmetry used directly, and it is how two parties who have never met derive a shared secret over a channel that everyone can read. 
# Diffie-Hellman, in four lines
   public:   p (a large prime), g (a generator)
   Alice:    picks secret a, sends  A = g^a mod p
   Bob:      picks secret b, sends  B = g^b mod p
   both:     shared = B^a = A^b = g^(ab) mod p

# An eavesdropper sees p, g, A, B — and needs a discrete log to get further.
# Note what it does NOT provide: any idea who you agreed a key with.
That last line is the reason certificates exist. Key agreement without authentication agrees a perfectly good key with a machine-in-the-middle.
Concept
Elliptic Curves — Same Problem, Harder Playing Field
An elliptic curve provides a different set of objects to do the same exponentiation trick in, with one decisive property: the best known attacks against the curve version are far weaker than the best attacks against the integer version. Nobody has found a sub-exponential attack on well-chosen curves, so security grows with key size much faster — which is why 256 bits of elliptic curve stands in for 3072 bits of RSA (Rivest-Shamir-Adleman).
ConsequenceWhy it mattered
Smaller keys and signaturesCertificates, handshakes and packets all shrink
Less computation per operationMobile and embedded devices can afford real crypto
Faster handshakesA measurable share of TLS (Transport Layer Security) connection latency
Curve choice matters enormouslyA badly chosen or backdoored curve undoes all of it
The last row is why the curves in common use are few and heavily scrutinised, and why "we designed our own curve" is a statement that should end a procurement conversation.
Concept
Both Problems Fall to the Same Quantum Algorithm
Factoring and discrete logarithms look like different problems and are, mathematically, close relatives — which is why a single quantum algorithm would break both. That is the entire reason post-quantum cryptography moved to a different family of hard problems altogether, rather than simply increasing key sizes: there is no key size at which these two survive that algorithm. Symmetric cryptography and hashes are affected far less, needing roughly doubled key lengths rather than replacement.

🧭 Vectors & Embeddings — Similarity, Cosine Distance & What a Dimension Means Applied Maths ▶
Concept
An Embedding Is a Position, and Meaning Becomes Geometry
An embedding maps something — a word, a document, an image, a log line — to a list of numbers, a point in a high-dimensional space. The whole trick is that the mapping is trained so that similar things land near each other. Once that holds, questions about meaning become questions about distance, and distance is something a computer can answer at enormous scale. 
# Cosine similarity — the angle between two vectors, ignoring magnitude
   cos(a, b) = (a · b) / (|a| · |b|)

   a · b  = Σ aᵢbᵢ                  # dot product
   |a|    = √(Σ aᵢ²)                # length

#  1.0 = same direction     0.0 = unrelated     -1.0 = opposite

# Euclidean distance — straight-line separation, magnitude included
   d(a, b) = √(Σ (aᵢ - bᵢ)²)
Cosine is the usual choice for text because document length should not make two documents dissimilar. A long article and a short note about the same subject point the same way; only their magnitudes differ.
Concept
What a Dimension Is, and What It Is Not
Individual dimensions of a learned embedding rarely mean anything on their own. They are not "topic" or "sentiment" axes; they are whatever the training process found useful, and they are usually entangled. What carries meaning is the geometry of the whole space — directions and neighbourhoods — which is why inspecting a single coordinate tells you nothing and why interpretability is a research field rather than a lookup.
BelievingReality
"Dimension 42 encodes formality"Almost never; features are distributed across many dimensions
"More dimensions is better"Trade-off: capacity against storage, speed and the curse below
"Embeddings are comparable across models"They are not — a vector means nothing outside the model that made it
"Similar means relevant"Similarity is the model's notion of similar, which may not be the task's
The third row has operational teeth: re-embedding a corpus with a new model means re-embedding all of it. Mixing vectors from two model versions in one index produces results that are subtly and unfixably wrong.
⛰️ Derivatives & Gradient Descent — How a Model Actually Learns Applied Maths ▶
Concept
Walking Downhill on a Surface You Cannot See
Training is an optimisation: there is a loss function measuring how wrong the model currently is, and the parameters are adjusted to make it smaller. The gradient is the direction of steepest increase, so stepping against it goes downhill. The model never sees the whole landscape — it only ever knows the slope where it is standing, and takes a small step. 
# One parameter update, which is the entire idea
   θ  ←  θ - η · ∇L(θ)

   θ      the parameters
   L(θ)   the loss — how wrong the model is right now
   ∇L     the gradient — the slope, per parameter
   η      the learning rate — how big a step to take

# Repeat a few million times.
The derivative in the calculus domain is the same object: a rate of change. The only new idea here is doing it in millions of dimensions at once, one per parameter, which is why the operation is a matrix multiplication and why GPUs (Graphics Processing Unit) are involved.
Troubleshooting
The Learning Rate Is Where Training Goes Wrong
Most training failures reduce to the step size, and the symptoms are distinctive enough to diagnose from the loss curve alone.
SymptomCause
Loss oscillates or explodes to infinityLearning rate too high — the step overshoots the valley
Loss falls painfully slowlyLearning rate too low
Loss plateaus early and staysA flat region, a dead activation, or a vanishing gradient
Training loss falls, validation loss risesNot an optimisation problem — it is memorising the training set
The last row is the one that matters most in practice: the optimiser is succeeding perfectly at the task it was given, and the task was the wrong one. That is a statement about the loss function and the data, not about the descent.
Concept
Stochastic, and Why Noise Helps
Computing the gradient over the entire dataset for every step is unaffordable, so the gradient is estimated from a small batch. The estimate is noisy — and the noise turns out to be useful rather than merely tolerable, because it lets the process escape shallow dips it would otherwise settle in. Batch size therefore trades gradient quality against steps per second, and against the memory available.

Concept
In High Dimensions, Everything Is Far Away and Equally So
Geometric intuition is trained in two and three dimensions and stops working in hundreds. The specific failure that matters: as dimensions increase, the distances between random points concentrate — the nearest and the farthest neighbour become nearly the same distance away. Since "nearest" is what similarity search, clustering and anomaly detection all rest on, this undermines them from below.

The last effect is the one with a positive use: near-orthogonality is why a high-dimensional space can hold an enormous number of distinguishable directions, which is exactly what makes embeddings work at all. The curse and the capability are the same property seen from two sides.

🔵 Sets & Relations — The Formal Spine of SQL (Structured Query Language) Joins and Access Control Applied Maths ▶
Concept
A Table Is a Set, and a Join Is a Set Operation
The relational model is called relational because a table is a relation: a set of tuples. Once that lands, SQL stops being a list of clauses to memorise and becomes a small algebra — every query is a composition of set operations, and the operators behave the way set operators behave. 
# The operations, and their SQL spelling
   A ∪ B    union            ->  UNION
   A ∩ B    intersection     ->  INNER JOIN on the key, or INTERSECT
   A \ B    difference       ->  EXCEPT, or LEFT JOIN ... WHERE b.key IS NULL
   A × B    Cartesian product ->  CROSS JOIN — every row against every row

# A join is a filtered Cartesian product. That is not a metaphor:
   SELECT * FROM a JOIN b ON a.id = b.a_id
   ≡ SELECT * FROM a CROSS JOIN b WHERE a.id = b.a_id
This explains the accidental Cartesian product every analyst produces once: forget the ON clause and the database faithfully returns every pairing, because that is what the operation is before the filter. A thousand rows joined to a thousand rows is a million.
Reference
Relation Properties, and the Access-Control Bugs They Explain
A relation is any set of ordered pairs — "user X is a member of group Y", "role A inherits role B". Three properties decide how such a structure behaves, and each maps directly onto a familiar permissions problem.
PropertyMeansIn access control
ReflexiveEverything relates to itselfA role always includes its own permissions
SymmetricIf A→B then B→ARarely wanted — "can read" should not run backwards
TransitiveIf A→B and B→C then A→CNested groups; this is where surprises live
Antisymmetric + transitiveA partial orderA clean role hierarchy with no cycles
Transitivity is the one that produces incidents: nested group membership means effective permissions are the transitive closure of the membership relation, not the direct memberships anyone can see in a console. And a cycle in an inheritance graph — A inherits B inherits A — is the structure that makes a permissions resolver hang or overflow. Access Control Models in the Security domain covers the models; this is the shape underneath them.
Troubleshooting
Why NULL Breaks the Algebra
Set theory assumes every element either is or is not in a set. SQL's NULL introduces a third answer — unknown — and the algebra stops being two-valued. This is the source of the join and filter behaviour that reliably surprises people. 
   NULL = NULL       ->  UNKNOWN, not TRUE
   NULL <> 'x'      ->  UNKNOWN, not TRUE
   WHERE col <> 'x'  ->  drops NULL rows, which is usually not what was meant
   COUNT(col)        ->  ignores NULLs;  COUNT(*) does not
   NOT IN (subquery containing a NULL)  ->  returns nothing, ever
The last line is the classic silent bug: NOT IN against a column containing a single NULL returns an empty result set with no error and no warning. Use NOT EXISTS. The join-specific cases are in SQL Joins — Every Type, and the NULL Traps in the Data domain.

Three Tools, Used Constantly Without Being Named
Engineers reason formally more often than they think — arguing that a lock is held whenever a structure is modified, or that a retry loop terminates. Naming the technique makes the argument checkable by someone else, which is the entire practical value: an invariant written down can be reviewed, tested and asserted, while the same belief held loosely cannot.

Technique
Invariants Are the One With Immediate Cash Value
An invariant is a statement that must hold at every observable point. Writing them down turns vague correctness into something a test or an assertion can enforce — and the act of writing one frequently reveals that it is already violated. 
# Invariants worth asserting in real systems
   "The sum of all account balances is unchanged by a transfer."
   "Every item in the queue is either being processed or waiting — never both."
   "The lock is held whenever this structure is modified."
   "The free list and the allocated list are disjoint, and together are everything."
   "Total replicas acknowledging a write is always >= the write quorum."

# Then: assert them in tests, and in production where the cost allows.
Property-based testing is this idea automated: state the invariant, let the tool generate thousands of inputs and hunt for the case that breaks it. It finds the boundary conditions human-written examples systematically miss, because humans write the cases they already thought of.
Concept
The Counterexample Is the Politest Argument in Engineering
Design disagreements can circle for an hour on plausibility. One concrete case where the proposal produces a wrong answer ends it immediately, and ends it without anyone having to be persuaded of a general principle — which is why it is also the least adversarial way to disagree. "Here is a sequence of three events where this design loses a write" is a fact, and it can be checked.
🔬 Sampling & Confidence — What a Number From 200 Observations Actually Claims Applied Maths ▶
Concept
Every Measurement Is a Sample, Including the Ones That Look Complete
Monitoring samples. Surveys sample. A week of logs is a sample of all weeks. The number you computed is therefore an estimate with an uncertainty attached, and reporting it without that uncertainty invites decisions the data cannot support — most often, reacting to a change that is entirely within the noise. 
# Rough margin of error for a proportion, 95% confidence
   margin ≈ 1 / √n

   n =    100  ->  ±10%
   n =    400  ->  ±5%
   n =  1,000  ->  ±3%
   n = 10,000  ->  ±1%

# So "62% of users prefer X" from 100 people means somewhere in 52-72%.
# And quadrupling the sample only halves the error — precision is expensive.
Concept
What "95% Confidence" Does and Does Not Say
A 95% confidence interval means: if this procedure were repeated many times, about 95% of the intervals produced would contain the true value. It is a statement about the method, not a probability that this particular interval is right — a distinction that sounds pedantic until someone builds an argument on the misreading.
ClaimVerdict
"There is a 95% chance the true value is in this range"Common, and not what the interval says
"The intervals overlap, so there is no difference"Wrong — overlapping intervals can still be a real difference
"Bigger sample, so it is representative"Size does not fix bias; a biased sample is biased at any size
"We surveyed everyone who responded"Self-selection — the non-responders are usually the finding
The third row is the one worth internalising. A million rows from one region tells you about that region very precisely and about everywhere else not at all. Sampling bias and sampling error are different problems, and only one of them shrinks with more data.

📉 Anomaly Detection Maths — Z-Scores, MAD & Seasonality Applied Maths ▶
Reference
Two Ways to Say "Unusually Far From Normal"
The z-score is the standard measure and it has a specific weakness: it is computed from the mean and standard deviation, both of which are dragged around by the very outliers being looked for. The median-based alternative is robust — an extreme value barely moves it, so it keeps working on exactly the data where the z-score quietly fails. 
# Z-score — how many standard deviations from the mean
   z = (x - mean) / stdev

# Robust version — median absolute deviation
   MAD = median(|xᵢ - median(x)|)
   robust_z = 0.6745 · (x - median) / MAD

# Why it matters: one enormous spike inflates the stdev, so the
# NEXT spike scores as normal. The MAD version does not care.
The z-score also assumes a roughly normal distribution. Most operational data is not normal, so "three sigma" is not the rare event the textbook promises — on heavy-tailed latency data it fires constantly.
Concept
Seasonality — Compare Like With Like, or Alert Every Monday
Operational data has cycles: daily, weekly, monthly, and often a term or quarter rhythm. A threshold that ignores them fires every Monday morning and never fires during a quiet Sunday outage. The fix is to compare a point against the same phase of the cycle rather than against a global baseline.
ApproachGood forWeakness
Fixed thresholdHard limits — disk full, certificate expiryUseless for anything that varies
Rolling mean ± k·stdevSlowly varying seriesLearns the anomaly if it persists
Same hour, previous weeksStrongly weekly patternsNeeds history; holidays break it
Decompose into trend + season + residualThe general answerMore machinery, and needs enough history
Row two contains a real trap: a rolling baseline adapts, so a slow degradation is eventually absorbed into "normal" and stops alerting. A gradual memory leak can defeat an adaptive threshold entirely — which is why absolute limits and adaptive ones are both needed.
Concept
The False-Positive Cost Is Part of the Maths
An anomaly detector's threshold is not chosen to be statistically correct; it is chosen to balance two costs — the cost of a missed event against the cost of a false alarm, multiplied by how often each occurs. Because anomalies are rare, false-alarm cost dominates the total almost always, which is the same base-rate arithmetic as Bayes' Theorem & Base Rates — Why a 99%-Accurate Detector Floods the SOC arriving from a different direction.
🅰️ A/B Testing & Significance — Power, p-Values & Stopping Rules Applied Maths ▶
Concept
What a p-Value Says, Precisely
A p-value is the probability of seeing a result at least this extreme if there were no real difference. That is all. It is not the probability that the change works, not the probability the result is a fluke, and not a measure of how large the effect is. Every popular misreading inflates confidence, which is why a discipline built on p-values still ships changes that do nothing.
People hearIt actually means
"95% chance the change works"If there were no effect, we would see data this extreme 5% of the time
"p < 0.05, so it is real"One in twenty null results clears that bar by chance
"p = 0.06, so it does nothing"Nothing special happens at 0.05; it is a convention
"Significant, so it matters"Statistical significance says nothing about effect size
The last row is the commercially important one: with a large enough sample, a 0.01% improvement is statistically significant and practically worthless. Always report the effect size and its interval alongside.
Concept
Peeking — The Way Most Real Tests Are Ruined
Checking a running test repeatedly and stopping when it crosses significance is the single most common error in practical A/B testing, and it is fatal. Random fluctuation crosses the threshold eventually on almost any test, so a stop-when-significant rule finds "wins" in experiments where nothing is happening at all. 
# Fix the sample size BEFORE starting. Roughly, per variant:
   n ≈ 16 · σ² / Δ²          # continuous metric
   n ≈ 16 · p(1-p) / Δ²      # conversion rate

   Δ = the smallest difference worth detecting
   σ = the metric's standard deviation

# Note the Δ²: halving the effect you want to detect QUADRUPLES the
# sample needed. Small effects are extremely expensive to prove.
If continuous monitoring is genuinely needed, use a method designed for it — sequential testing or a Bayesian approach — rather than a fixed-sample test looked at repeatedly. Those methods pay for the peeking in their maths; the classical test does not.

A usage series is three things added together: a long-run trend, a repeating seasonal pattern, and noise. Fitting a line to the raw series mixes all three and produces a forecast that is confidently wrong in a direction determined by where in the cycle you happened to start. 
   observed  =  trend  +  seasonal  +  residual

# Practical procedure, no specialist tooling required:
   1. Plot it. Most forecasting errors are visible to the eye.
   2. Remove the seasonality — compare like periods (this Monday

   3. Fit the trend to the deseasonalised series.
   4. Project, then add the seasonal pattern back on.

🕸️ Lattices, Gently — The Hard Problem Post-Quantum Cryptography Moved To Applied Maths ▶
Concept
A Grid of Points, and the Difficulty of Finding the Nearest One
A lattice is a regular grid of points extending through space, described by a set of basis vectors. In two dimensions it is graph paper and everything about it is obvious. In several hundred dimensions, two questions become extraordinarily hard: find the shortest non-zero point, and find the lattice point nearest to some arbitrary location. Those are the problems post-quantum cryptography is built on — and unlike factoring, no efficient quantum algorithm for them is known. 
# A lattice is all integer combinations of its basis vectors
   L = { a₁v₁ + a₂v₂ + ... + aₙvₙ  :  aᵢ ∈ ℤ }

# The hard problems:
   SVP  shortest vector    — find the shortest non-zero lattice point
   CVP  closest vector     — find the lattice point nearest a given target

# Easy in 2-D with a "good" basis. In 500-D with a "bad" basis, not.
# That gap between good and bad bases is the trapdoor.
Concept
Learning With Errors — Hiding a Secret in Deliberate Noise
The construction most post-quantum schemes rest on is disarmingly simple to state. Take a secret vector, produce many linear equations involving it, and add a small random error to each. Without the errors, schoolroom linear algebra recovers the secret immediately. With them, the problem becomes lattice-hard — and the noise is what does all the work. 
# Given many samples of the form
   bᵢ  =  ⟨aᵢ, s⟩ + eᵢ   (mod q)

   aᵢ  public random vectors
   s   the secret
   eᵢ  small random errors        # without these, solve by Gaussian elimination

# Recovering s from many (aᵢ, bᵢ) pairs is Learning With Errors.
The practical costs of the switch follow from the structure: keys and ciphertexts are larger than their elliptic-curve equivalents, which matters for handshake sizes and for constrained devices. The engineering trade-offs and migration path are in Post-Quantum Cryptography — Harvest Now, Decrypt Later in the Security domain.
Concept
Why "No Known Attack" Is the Honest Claim
Lattice problems are not proven hard, any more than factoring is. What supports them is decades of study, a reduction showing that breaking the average case is as hard as the worst case for related problems, and no quantum algorithm giving the kind of advantage that demolished RSA (Rivest-Shamir-Adleman). That is a strong position and it is not a proof — which is precisely why deployments are hybrid, running a classical and a post-quantum algorithm together so that a break in either leaves the other standing.

⏳ Little's Law & Queueing — Why the Wait Explodes Before the Server Is Full CS • Systems ▶
Core Concept
One Equation, and the Reason Waiting Is Not Linear
Queueing feels like it should be proportional: twice the load, twice the wait. It is not, and the gap between intuition and arithmetic is where most capacity decisions go wrong. Little's Law is the whole of the first half: L = λW — the average number of items in a system equals the arrival rate multiplied by the average time each spends there. It holds for any stable system, with no assumption about the distribution of arrivals or service times, which is what makes it so widely applicable and so easy to overlook.
SymbolMeansIn a web service
LItems in the systemRequests in flight, including those queued
λ (lambda)Arrival rateRequests per second
WTime in the systemLatency, queueing plus service
RearrangedW = L / λ1,000 in flight at 200/s means a 5-second latency — whatever the code does
The rearrangement is the useful one, because L is the number you can usually measure and W is the one people argue about. A thread pool of 1,000 serving 200 requests a second is a five-second latency; no amount of profiling the handler changes that, because the wait is in the queue rather than in the work.
The Knee
Utilisation Does Not Trade Off Linearly Against Latency
The second half is why a system at 90% utilisation is not “10% away from trouble”. For a simple queue, the average wait scales roughly with 1 / (1 − ρ), where ρ is utilisation. The curve is flat and then it is a wall — and the wall arrives a long way before the server is full.

50%2×Comfortable. Spare capacity absorbs bursts

90%10×The knee. Small load increases now produce large latency increases

Three consequences worth carrying. Running at 90% is a decision about latency, not about efficiency — and it is a defensible one for batch work and a poor one for anything a human waits on. Variability makes it worse: bursty arrivals hit the wall earlier than the average suggests. And this is why adding one worker sometimes fixes everything — moving from 95% to 80% utilisation is not a 15% improvement, it is a four-fold reduction in queueing delay.

Retry stormsRetries raise λ at exactly the moment ρ is already high — the mechanism behind Resilience Patterns — Circuit Breaker, Retry & Timeout
Kanban work-in-progress limitsL is capped deliberately, so W becomes predictable. That is the whole argument for WIP limits
The practical habit is to measure L and λ before reasoning about W. Both are usually already in your metrics — in-flight requests and requests per second — and their ratio is the latency you actually have, independent of any story about why. When the ratio disagrees with the latency you believe you have, one of the two numbers is measuring something other than what its name says.
🗜️ Compression — Why It Works, and Why It Sometimes Cannot CS • Information ▶
Core Concept
Compression Exploits Redundancy, So Incompressible Data Is Data With None
Every compressor works by finding structure and describing it more briefly: repeated bytes, predictable patterns, skewed symbol frequencies. That single fact explains all the surprising behaviour. Data with no discoverable structure cannot be compressed — and a counting argument proves no algorithm can compress every input, because there are more possible files of length n than of length less than n.
DataCompresses?Why
English text, source code, logsVery wellSkewed symbol frequencies and enormous repetition
A CSV (Comma-Separated Values) of numbersWell, especially columnarSimilar values adjacent — the whole argument for Parquet
An already-compressed archiveNoThe redundancy has been removed. Re-compressing usually grows it slightly
JPEG (Joint Photographic Experts Group), MP3, MP4NoSame reason — lossy compression already removed the structure
Encrypted dataNo, and this is diagnosticGood ciphertext is indistinguishable from random. If it compresses, something is wrong
The last row is a genuinely useful test rather than a curiosity. Try to compress something you believe is encrypted — if the ratio is meaningful, either the encryption is not happening or it is badly broken, and that is a two-second check available to anyone.
Practice
Compress Then Encrypt Is the Only Order That Works
The ordering follows directly. Compression before encryption works, because the plaintext still has structure. Encryption before compression achieves nothing, because ciphertext has no structure left to find — and if it did, the cipher would be broken.
OrderResult
Compress, then encryptCorrect. Smaller and secret
Encrypt, then compressNo size reduction. A wasted pass
NeitherFine, and larger
Compress, encrypt, then compress againThe second pass does nothing, and the CPU (Central Processing Unit) is spent anyway
Compression ratio as a checkIf encrypted output compresses meaningfully, treat it as evidence of a broken or absent cipher
The correct order has a security cost that is not obvious and is worth stating plainly: compressing attacker-influenced data alongside a secret leaks the secret through the output length. If an attacker can inject text and observe the compressed size, matches with the secret compress better — and the size difference recovers it byte by byte. This is the mechanism behind the CRIME and BREACH attacks on compressed TLS (Transport Layer Security), and the reason compression of secret-bearing responses was disabled rather than fixed.
Reference
Choosing, and the One Number That Decides
Algorithms differ mostly along one axis — how much CPU you will spend per byte — and the right choice depends on whether the bottleneck is the network, the disk or the processor.
AlgorithmCharacterRight when
gzip / DEFLATEUniversal, modest ratio, modest speedCompatibility matters more than anything
zstdWide range of levels, fast at low onesThe current default answer for most new uses
lz4Very fast, weak ratioCompressing is cheaper than transmitting, but only just — memory, hot paths
brotliBest ratio for web text, slow to compressStatic assets compressed once and served many times
xz / LZMAStrong ratio, very slowDistribution archives where compression happens once
The decision rule that avoids most mistakes: if the data is served more often than it is created, spend CPU at creation time (brotli, xz); if it is created more often than it is read, use something fast (zstd at a low level, lz4). And measure the ratio on your own data before choosing — the published benchmarks are on corpora that may look nothing like yours.
⭕ Consistent Hashing — Adding a Server Without Moving Everything CS • Distributed ▶
Core Concept
Modulo Sharding Remaps Almost Everything When the Server Count Changes
The obvious way to spread keys across N servers is hash(key) % N. It is even, it is instant, and it has one catastrophic property: change N and nearly every key moves. Going from 4 servers to 5 relocates roughly 80% of the data — which for a cache means an 80% miss rate arriving at the database all at once, and for a database means a migration.
ServersKeys that move on adding one moreConsequence
% 4 → % 5~80%The cache is effectively cold
% 100 → % 101~99%It gets worse with scale, not better
Consistent hashing, 4 → 5~1/5 of keysOnly the share the new node takes over
Consistent hashing, node failsOnly that node's shareIts neighbour absorbs it; everyone else is untouched
Rendezvous hashingSame guarantee, different mechanismSimpler to implement, no ring to maintain
The second row is the important one and it is counter-intuitive: modulo sharding gets worse as the cluster grows. At four nodes you lose most of the cache; at a hundred you lose essentially all of it — so the technique fails hardest exactly where it was adopted to help.
Core Concept
The Ring, and Why Virtual Nodes Are Not Optional
Map both keys and servers onto the same circular space — the output range of the hash — and assign each key to the first server clockwise from it. Adding a server takes over only the arc between it and its predecessor, so the disruption is proportional to what changed, not to the size of the cluster.
RefinementThe problem it solves
Servers placed once eachArcs are uneven by luck. One node gets twice the load of another
Virtual nodes — each server at 100–200 pointsAverages the arcs out. Without this the balance is poor enough to matter
Weighted nodesA bigger machine gets more virtual points. Heterogeneous clusters work naturally
A node failsIts arcs pass to the next node clockwise — concentrated on neighbours, which is why virtual nodes spread the failure too
Rendezvous (HRW) hashingFor each key, pick the server maximising hash(key, server). No ring, no virtual nodes, same properties
If you are implementing this rather than using a library, the number of virtual nodes is the parameter that decides whether it works. One point per server gives a load imbalance large enough to negate the benefit; a hundred or two gives distribution close enough to even that nobody notices. It is not a tuning knob so much as a correctness requirement.
Where it shows up
One Idea That Made Horizontal Scaling Practical
This is worth learning once because it recurs everywhere, and in each place it is the answer to the same question: how do we add capacity without moving all the data?
SystemWhere it appears

The limitation worth stating alongside the idea: consistent hashing distributes keys evenly, not load. One extremely popular key — a celebrity account, a hot product — lands on one node regardless, which is the hot-partition problem that no amount of rebalancing fixes. That needs a different tool: replication of the hot key, or a composite key that spreads it deliberately.
🔢 Byte Order & Binary Layout — Endianness, Alignment & Struct Packing CS • Systems ▶
Core Concept
The Bug Class Where the Data Parses and Is Wrong
Endianness is not an exotic concern; it is the general form of a failure that shows up whenever bytes cross a boundary. The same four bytes mean two different numbers depending on who wrote them, and neither reader errors — one simply produces 16,777,216 where the other produced 256. Nothing crashes, nothing logs, and the number is wrong.
THE SAME FOUR BYTES, TWO NUMBERS
bytes on the wire: 0x00 0x00 0x01 0x00 big-endian (network order, most significant first) = 256 little-endian (x86, ARM by default, least significant) = 16,777,216 # Python: be explicit, always import struct struct.pack(">I", 256) # b'\x00\x00\x01\x00' big-endian struct.pack("<I", 256) # b'\x00\x01\x00\x00' little-endian struct.pack("I", 256) # native + PADDING. Almost never what you want on the wire. # Struct padding: this is 12 bytes in C, not 6 # struct { char a; int b; char c; } -> a, 3 pad, b(4), c, 3 pad struct.calcsize("cic") # 12 — native alignment struct.calcsize("<cic") # 6 — '<' also means "no padding"
Two rules remove almost all of it. Be explicit at every boundary: use > or < in a format string, never the native default, because native is whatever the machine that ran the code happened to be. And network byte order is big-endian — that is why htonl exists and why most protocol specifications say “most significant byte first”, even though nearly every machine running them today is little-endian.
Reference
Alignment and Padding, Which Surprise People Separately
The second half of “binary layout” is that a struct is not the sum of its fields. Compilers insert padding so each field starts at an address its type likes, and the padding is invisible in the source.
FactConsequence
Fields are aligned to their own sizeA 4-byte int starts at a multiple of 4. Bytes are inserted before it if needed
Field order changes the sizechar, int, char is 12 bytes; int, char, char is 8. Same fields
Padding bytes are uninitialisedWriting a struct to disk or a socket leaks whatever was in memory — a genuine information-disclosure bug
#pragma pack / __attribute__((packed))Removes padding, and can make access slower or fault on architectures that require alignment
Two compilers, two layoutsA struct is not a wire format. It never was
The third row is a security bug, not a formatting curiosity. Padding bytes are never initialised, so writing a struct straight to a socket or a file sends whatever was previously in that memory — which has leaked keys and pointers from real systems, and which no test will ever notice.
Practice
The Rule That Prevents All of It
Never send a struct. Serialise fields explicitly. Everything above is a symptom of treating an in-memory layout as if it were a defined format, and the layout belongs to the compiler, the architecture and the flags — none of which the reader on the other end shares.
ApproachVerdict
write(fd, &struct, sizeof(struct))Works until the other end differs. Then it is the bug in the first card

A schema format — Protobuf, Avro, MessagePack, CBORHandles endianness, alignment and versioning. The right default
Text formats — JSON (JavaScript Object Notation), CSV (Comma-Separated Values)Immune to all of this. Larger and slower, and usually fine
Reading a foreign binary formatThe specification will state the byte order. Believe it over your machine
Where the file format is not yours — a packet capture, a disk image, a mainframe extract — the same discipline applies in reverse: read the specification's stated byte order and unpack explicitly. This is the general version of a problem that the mainframe integration cards meet from the other end, where EBCDIC and packed decimal add two more encodings to the same question of “whose interpretation of these bytes is right?”
💣 Catastrophic Backtracking — When a Regular Expression Is a Denial of Service CS • Algorithms ▶
Core Concept
A Regular Expression That Is a Denial of Service
Most regex engines — those in Python, Java, JavaScript, .NET, PCRE — are backtracking engines. On a failed match they retry alternatives, and with a nested quantifier the number of alternatives grows exponentially with input length. Thirty characters can take longer than the rest of the request by orders of magnitude, on a single CPU (Central Processing Unit), from an input the user chose.
THE SHAPE, AND THE INPUT THAT KILLS IT
# Nested quantifier: (a+)+ — the engine can split "aaaa" many ways pattern = r"^(a+)+$" "aaaaaaaaaaaaaaaaaaaaaaaaaaaaa!" # 29 a's and one non-match # backtracking paths grow as 2^n. 29 chars ≈ half a billion attempts. # Same disease, common in the wild: r"^(\w+\s?)*$" # "trim and validate a sentence" r"^(\d+|\w+)*$" # alternation inside a quantifier — overlapping r"(.*),(.*),(.*)" # greedy .* that must be re-split on failure # Fixes, in order of preference r"^a+$" # 1. remove the nesting — usually possible r"^[^,]*,[^,]*,[^,]*$" # 2. make each part unambiguous, no backtracking needed # 3. use a linear-time engine: Go regexp, Rust regex, RE2 # 4. bound it: a timeout, and a maximum input length
It is the rare bug that is simultaneously a performance problem, a security vulnerability and invisible in code review — because the pattern looks correct, passes every test, and only misbehaves on inputs nobody wrote a test for. The tell is a quantifier applied to a group that itself contains a quantifier or an alternation: (a+)+, (\w+\s?)*, (x|xx)*.
Reference
Where It Reaches You, and Why the Input Is Usually Not Yours
The reason this class matters operationally is that the dangerous inputs arrive from outside and the patterns are frequently not written by the person who deployed them.
SourceWhy it is exposed
Input validation on a form fieldThe archetype — an email or URL (Uniform Resource Locator) pattern applied to attacker-chosen text
A log-parsing ruleLogs contain attacker-influenced content. A slow regex in the ingest path stalls the pipeline
A WAF (Web Application Firewall) or IDS (Intrusion Detection System) rule setRules written by a third party, run against traffic. See Suricata & Snort — Signature IDS/IPS
A dependency's internal regexYou did not write it and may not know it exists. ReDoS advisories against libraries are common
Markdown or template renderingUser content, complex patterns, and usually server-side
The fourth row is why this needs a dependency-scanning answer as well as a code-review one. Most exposure is in patterns you did not write, inside libraries and rule sets, so the practical controls are keeping dependencies current and putting a bound on input length at the edge.
Practice
Four Fixes, and Only One of Them Is Universal
Ordered by how well they work rather than by how easy they are.
FixStrength
Rewrite to remove the ambiguityBest. Usually possible — (a+)+ was never needed, and [^,]* beats .*
Use a linear-time engineUniversal. RE2, Go's regexp, Rust's regex cannot backtrack, by construction. They give up some features to guarantee it
Atomic groups / possessive quantifiersEffective where supported (PCRE, Java, .NET) — not available in Python's re or JavaScript
A timeout on the matchA backstop, not a fix. .NET and Java support it; Python and JavaScript do not, natively
Cap the input lengthCheap, blunt, and genuinely reduces the exponent. Do it anyway
The habit worth building is smaller than any of these: when you write a quantifier over a group, ask whether two different splits of the same input could both match. If they can, the pattern backtracks. And for anything running against untrusted input at volume, prefer a parser over a regular expression — the cases where a regex is genuinely the right tool for structured input are fewer than habit suggests.
