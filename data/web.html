🖼️ How the Browser Renders a Page Browser ▶
Concept
From Bytes to Pixels
Understanding the rendering pipeline is what separates people who "write CSS" from people who make fast sites. The browser turns your HTML/CSS into pixels through a fixed sequence of steps.
StepDoes
Parse → DOMHTML becomes the Document Object Model tree
Parse → CSSOMCSS becomes the style tree
Render treeDOM + CSSOM combined (visible nodes only)
Layout (reflow)Compute geometry — where & how big everything is
PaintFill in pixels (text, colors, borders)
CompositeAssemble layers on the GPU
Render-blocking: CSS blocks rendering (the browser won't paint unstyled content); a plain <script> blocks parsing. Use defer/async and keep critical CSS small so the page paints fast.
🌀 Reflow, Repaint & What Causes Jank Performance ▶
Concept
Why Animations Stutter
To hit 60fps the browser has ~16ms per frame. Reflow (recomputing layout) is expensive; repaint is cheaper; compositing a transform is cheapest. Triggering layout every frame causes jank.
ChangeCost
width/height/top/leftReflow (layout) — avoid animating these
color/backgroundRepaint only
transform / opacityComposite only — GPU, no layout (animate these!)
Layout thrashing: reading a layout property (like offsetHeight) right after writing one forces a synchronous reflow in a loop. Batch reads, then writes. Animate transform and opacity — they skip layout and paint entirely.
🌳 The DOM & Events — Bubbling & Delegation Browser ▶
Reference
How Clicks Travel Through the Page
The DOM is the live tree of the page that JavaScript manipulates. Events flow through it in phases — understanding this powers efficient event handling. 
// Event delegation: one listener for many children
list.addEventListener('click', (e) => {
  const item = e.target.closest('.item');
  if (item) select(item.dataset.id);
});
PhaseDetail
CaptureTop → target (rarely used)
TargetThe element clicked
BubbleTarget → top (default for listeners)
Delegation attaches one listener to a parent and uses bubbling to handle any child — essential for dynamic lists (no re-binding on add/remove). stopPropagation() halts bubbling; preventDefault() stops the browser's default action.
🗃️ Web Storage — Cookies, localStorage & IndexedDB Browser ▶
Reference
Where State Lives in the Browser
The browser offers several places to persist data, each with different size, lifetime, and security properties. Picking the wrong one causes bugs and vulnerabilities.
StoreUse / Note
CookiesSent with every request; use HttpOnly+Secure for auth tokens
localStorage~5MB, persists, sync API — readable by JS (XSS risk)
sessionStoragePer-tab, cleared on close
IndexedDBLarge, async, structured — offline apps
Cache APIStore responses for service workers/PWAs
Security: never store auth tokens in localStorage — any XSS reads them. Prefer HttpOnly cookies (JS can't touch them). Ties to the web-security cards.

📏 Flexbox — One-Dimensional Layout CSS ▶
Reference
Aligning Things in a Row or Column
Flexbox lays out items along a single axis and is the go-to for components: navbars, toolbars, centering, card rows. Set display:flex on the parent, then control alignment and distribution. 
.bar {
  display: flex;
  justify-content: space-between;  /* main axis */
  align-items: center;             /* cross axis */
  gap: 1rem;
}
PropertyControls
flex-directionrow (default) or column — sets the main axis
justify-contentSpacing along the main axis
align-itemsAlignment on the cross axis
flex: 1Grow to fill; flex-wrap to wrap
gapSpace between items (no more margin hacks)
Centering, solved: display:flex; justify-content:center; align-items:center — the answer to a decade of "how do I center a div."
🔲 CSS Grid — Two-Dimensional Layout CSS ▶
Reference
Rows and Columns at the Same Time
Grid handles two dimensions at once — perfect for page layouts and any grid of cards. Where Flexbox is content-driven, Grid is layout-driven: you define the structure, items flow in. 
.gallery {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(200px, 1fr));
  gap: 1rem;
}
FeatureDetail
grid-template-columns/rowsDefine tracks; fr = fraction of free space
repeat() + minmax()Responsive columns without media queries
auto-fit / auto-fillWrap columns to fit the container
grid-template-areasName regions; lay out visually in CSS
Rule of thumb: Grid for the overall page/section layout, Flexbox for the components inside it. The auto-fit + minmax one-liner gives a fully responsive card grid with zero media queries.
📱 Responsive Design — Fluid, Mobile-First CSS ▶
Concept
One Site, Every Screen
Responsive design adapts the layout to the viewport. The modern approach is mobile-first (style the small screen, then add complexity up) and increasingly intrinsic (let the content size itself).
ToolUse
Media queriesBreakpoints by viewport width
Container queriesRespond to the parent's size — true component responsiveness
clamp()Fluid type/spacing: clamp(min, preferred, max)
rem / % / fr / vwRelative units over fixed px
<meta viewport>Required tag or mobile scales wrong
Container queries are the big recent shift: a card can restyle based on the space it has, so the same component works in a sidebar or full-width — impossible with media queries alone.
✨ Modern CSS — Custom Properties, :has() & Layers CSS ▶

CSS Got Genuinely Powerful
Recent CSS added features that used to need preprocessors or JavaScript. Worth knowing because they simplify code you may still be writing the old way.

.btn { background: var(--brand); }

Custom properties + prefers-color-scheme is how modern dark mode works — swap variable values, not whole stylesheets (exactly how this site themes itself).

🔒 Closures, Scope & this JavaScript ▶
Concept
The Interview Trio, Explained
Three JS concepts that confuse beginners and get asked in every interview. Get them and most "weird JavaScript" stops being weird. 
function counter() {
  let n = 0;                 // captured by the closure
  return () => ++n;         // remembers n after counter() returns
}
const c = counter(); c(); c();  // 1, 2
ConceptDetail
ScopeWhere a variable is visible; let/const are block-scoped
ClosureA function that remembers variables from where it was defined
thisDepends on how a function is called (not where defined)
Arrow functionsNo own this — inherit from the enclosing scope
this gotcha: a method passed as a callback loses its this. Arrow functions or .bind() fix it. Closures power data privacy, memoization, and every event handler that "remembers" state.
⏳ Async Deep — Promises, await & the Event Loop JavaScript ▶
Concept
How Single-Threaded JS Does Many Things
JavaScript runs on one thread but stays responsive via the event loop: long operations (network, timers) run elsewhere and their callbacks are queued back. Promises and async/await make this readable. 
async function load() {
  try {
    const [a, b] = await Promise.all([getA(), getB()]); // parallel
    return merge(a, b);
  } catch (e) { handle(e); }
}
ConceptDetail
PromiseA value that arrives later (pending → fulfilled/rejected)
async/awaitWrite async code that reads like sync
Microtask vs macrotaskPromises (micro) run before timers (macro)
Promise.all / race / allSettledCoordinate multiple promises
Parallel vs serial: await a; await b; runs one after the other; Promise.all([a,b]) runs them together — a common performance win. Never await in a loop when the iterations are independent.
🧬 Prototypes & Modern Classes JavaScript ▶

JavaScript's Real Inheritance Model
Under the class syntax, JS uses prototypal inheritance: objects delegate to a prototype object. Knowing this explains how method lookup and class actually work.
ConceptDetail

🔷 TypeScript — Types for JavaScript JavaScript ▶
Reference
Catch Bugs Before They Ship
TypeScript adds static types to JavaScript, caught at compile time. It's now the default for serious projects — the editor autocomplete and refactoring safety alone are worth it. 
type User = { id: number; name: string; email?: string };
function greet(u: User): string {
  return `Hi ${u.name}`;
}
FeatureDetail
Interfaces / typesDescribe object shapes
GenericsReusable, type-safe code (Array<T>)
NarrowingTypes refine via checks (unions, guards)
strict modeNull-safety & more — turn it on
Mental model: types are erased at build time — they guide the compiler and editor, then disappear. The payoff is fewer runtime undefined errors and fearless refactoring in large codebases.
⚛️ React — Components, Hooks & the Mental Model Frameworks ▶
Reference
UI as a Function of State
React's core idea: your UI is a function of state — UI = f(state). You describe what the screen should look like for the current data; React efficiently updates the DOM when state changes. 
function Counter() {
  const [n, setN] = useState(0);
  return <button onClick={() => setN(n + 1)}>{n}</button>;
}
ConceptDetail
ComponentsReusable functions returning JSX
PropsRead-only inputs passed down
useState / useReducerLocal state
useEffectSide effects (fetch, subscriptions) — has gotchas
KeysStable list identity — never use array index if items change
The rules of hooks: call them at the top level, same order every render. State updates are asynchronous and batched. "Lift state up" to the nearest common parent when siblings need to share it.
🪝 React Patterns & Pitfalls Frameworks ▶
Reference
Avoiding the Common Traps
Most React bugs come from a handful of misunderstandings around effects, re-renders, and stale state. Knowing them saves days.
TopicDetail
ContextShare data without prop-drilling (theme, auth)
useMemo / useCallbackMemoize expensive work / stable function identity
useEffect overuseDon't sync state you can derive during render
Stale closuresEffect captures old state — fix deps array
Unnecessary re-rendersNew object/array props break memoization
Modern guidance: "You Might Not Need an Effect" — derive values during render, handle events in handlers, and reserve useEffect for genuine external synchronization. Don't reach for memoization until you've measured a problem.
🟢 Vue & Svelte — Other Reactivity Models Frameworks ▶
Reference
Not Everything Is React
React isn't the only game. Vue and Svelte reach the same goal — reactive UI — with different (often simpler) models worth understanding.
FrameworkApproach
ReactRe-render on state change; virtual DOM diff; explicit
VueFine-grained reactivity + template syntax; gentle learning curve

The trend: signals. Fine-grained reactivity (Solid, Vue, Svelte 5, Angular signals) updates exactly what changed without re-running whole components — the industry direction. Learn React for jobs; learn signals to understand where things are going.
▲ Meta-Frameworks — Next.js & Rendering Modes Frameworks ▶
Concept
SSR, SSG, ISR & CSR — When Each
Meta-frameworks (Next.js, Nuxt, SvelteKit) add routing, data fetching, and server rendering on top of the UI library. The key decision is where and when your HTML is generated.
ModeHTML built…Best for
CSRIn the browserApp-like dashboards (behind login)
SSRPer request on the serverPersonalized, fresh pages
SSGAt build timeBlogs, docs, marketing (fastest)
ISRStatic + periodic rebuildLarge mostly-static sites
SSR/SSG win on first-load speed and SEO (real HTML arrives immediately). React Server Components are the current frontier — render components on the server, ship less JS. Match the mode to the page: static where you can, dynamic where you must.
🗄️ State Management — When You Actually Need It Frameworks ▶
Concept
Don't Reach for Redux by Default
As apps grow, sharing state gets messy — but the answer usually isn't a big global store. Distinguish server state (data from an API) from client state (UI toggles); they need different tools.
NeedReach for
Server data (caching, refetch)React Query / SWR — not a global store
Simple shared UI stateContext, or lift state up
Complex global client stateZustand / Redux Toolkit / signals
URL as stateQuery params for filters/tabs (shareable)
Biggest insight: most "state management" pain is really server state (loading, caching, revalidation) — a data-fetching library like React Query solves it far better than Redux. Add global stores only for genuinely global client state.
🔌 Fetch, REST & CORS in Practice Backends ▶
Reference
How the Frontend Talks to APIs
The browser's fetch makes HTTP requests. You'll spend real time on status codes, headers, and the one that trips everyone up: CORS. 
const res = await fetch('/api/users', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify(user),
});
if (!res.ok) throw new Error(res.status);   // fetch doesn't throw on 4xx/5xx!
ThingDetail
Status codes2xx ok, 3xx redirect, 4xx client, 5xx server
CORSBrowser blocks cross-origin unless the server sends Access-Control-Allow-*
PreflightAn OPTIONS request before non-simple calls
fetch quirkOnly rejects on network error — check res.ok yourself
CORS is server-side: a CORS error means the API must allow your origin — you can't fix it from the browser. It's a browser security feature, not a bug in your code.
◈ GraphQL — Ask for Exactly What You Need Backends ▶
Reference
One Endpoint, Client-Shaped Responses
GraphQL exposes a typed schema through one endpoint; the client specifies exactly which fields it wants. It solves REST's over- and under-fetching, at the cost of new complexity. 
query {
  user(id: 42) { name, orders { total } }   # exactly these fields
}
ConceptDetail
Schema & typesStrongly typed contract
Query / Mutation / SubscriptionRead / write / realtime
ResolversServer functions that fetch each field
N+1 resolversClassic pitfall — fix with DataLoader batching
When to use: many clients with different data needs, or deeply nested data. For simple CRUD, REST is often simpler. Caching is harder than REST (one endpoint, POST) — weigh the trade-off.
🔴 Realtime — WebSockets, SSE & Polling Backends ▶
Reference
Pushing Data to the Browser
HTTP is request/response — the server can't just push. For live features (chat, notifications, dashboards) you need a different transport. Pick the lightest one that fits.
OptionUse
WebSocketsFull-duplex, persistent — chat, games, collaboration
Server-Sent EventsServer→client stream over HTTP — feeds, notifications (simpler)
Long pollingFallback where sockets aren't available
Short pollingJust refetch on a timer — fine for low-frequency updates
Don't over-engineer: if data changes every few minutes, polling is simplest. Reserve WebSockets for genuinely bidirectional, high-frequency needs. SSE is the underrated middle ground for one-way streams.
🔑 Frontend Auth — Tokens, Cookies & OAuth Backends ▶
Concept
Logging Users In, Safely
Auth on the frontend is mostly about where you store the credential and how you attach it. Get this wrong and you ship an XSS-exploitable token. Ties directly to the security domain's OAuth/session cards.
ApproachDetail
HttpOnly cookieJS can't read it → XSS-safe; pair with SameSite/CSRF protection
JWT in localStorageConvenient but XSS-readable — widely discouraged
OAuth / OIDC + PKCE"Sign in with…"; PKCE for public clients
Refresh flowShort-lived access token + refresh token rotation
Rule: prefer HttpOnly, Secure, SameSite cookies for session tokens. Never store long-lived secrets where JavaScript can read them. Auth is one place to use a battle-tested library, not roll your own.
🔄 Data Fetching Patterns — React Query & Caching Backends ▶
Reference
Server State Is Its Own Problem
Fetching data is easy; keeping it fresh, cached, and in sync across a UI is hard. Libraries like React Query (TanStack Query) and SWR handle the whole lifecycle so you don't reinvent it per component.
FeatureDoes
Caching & dedupSame query used twice → one request
Background refetchRevalidate stale data on focus/interval
Loading/error statesBuilt in — no manual flags
Optimistic updatesUpdate UI instantly, roll back on failure
Why it matters: hand-rolled useEffect + useState fetching leads to race conditions, duplicate requests, and stale UI. A query library turns all that into a hook — genuinely one of the biggest quality-of-life wins in modern frontend.
