🖼️ How the Browser Renders a Page Browser ▶
Concept
From Bytes to Pixels
Understanding the rendering pipeline is what separates people who "write CSS (Cascading Style Sheets)" from people who make fast sites. The browser turns your HTML/CSS into pixels through a fixed sequence of steps.
StepDoes
Parse → DOMHTML (HyperText Markup Language) becomes the Document Object Model tree
Parse → CSSOMCSS becomes the style tree
Render treeDOM + CSSOM combined (visible nodes only)
Layout (reflow)Compute geometry — where & how big everything is
PaintFill in pixels (text, colors, borders)
CompositeAssemble layers on the GPU (Graphics Processing Unit)
Render-blocking: CSS blocks rendering (the browser won't paint unstyled content); a plain <script> blocks parsing. Use defer/async and keep critical CSS small so the page paints fast.
The bug that sent you here
The Text Jumps When the Font Loads, and the Page Is Blank Until the CSS Arrives
Two of the three most-reported “the page feels broken” symptoms are direct consequences of the render pipeline, and both are fixable in the head of the document. CSS is render-blocking by design — nothing paints until it arrives, because painting first would mean painting wrong. Fonts then arrive later still, and swapping them reflows text that was already on screen.
SymptomCause, and the fix
Blank screen, then everything at onceRender-blocking CSS. Inline the critical rules; load the rest with media or asynchronously
Text appears, then jumps as the font loadsfont-display: swap without matched metrics. Add size-adjust / ascent-override on a fallback, or font-display: optional
Layout shifts as images arriveNo reserved space. width and height attributes, or aspect-ratio
A synchronous <script> stalls first paintParser-blocking. defer for order-dependent scripts, async for independent ones
The page paints and then freezesA long task on the main thread after paint — hydration, or a large JSON (JavaScript Object Notation) parse
The order is the thing to hold: HTML parses, CSS blocks the first paint, layout computes geometry, paint fills pixels, compositing puts layers on screen. Every symptom above is one stage being made to wait or repeat. And the reason transform and opacity are the animation-safe properties is exactly this: they touch only the last stage.
🌀 Reflow, Repaint & What Causes Jank Performance ▶
Concept
Why Animations Stutter
To hit 60fps the browser has ~16ms per frame. Reflow (recomputing layout) is expensive; repaint is cheaper; compositing a transform is cheapest. Triggering layout every frame causes jank.
ChangeCost
width/height/top/leftReflow (layout) — avoid animating these
color/backgroundRepaint only
transform / opacityComposite only — GPU (Graphics Processing Unit), no layout (animate these!)
Layout thrashing: reading a layout property (like offsetHeight) right after writing one forces a synchronous reflow in a loop. Batch reads, then writes. Animate transform and opacity — they skip layout and paint entirely.
Measure it
Your Laptop Is Not the Device That Will Jank
A layout thrash that costs 3 ms on a development machine can cost 25 ms on a mid-range Android phone, and 25 ms misses the frame. The animation you cannot make stutter locally is not a smooth animation — it is an animation measured on the fastest computer that will ever run it. The fix is not to guess; the browser will tell you.
StepWhat to do
Throttle the CPU (Central Processing Unit)DevTools → Performance → CPU: 4× or 6× slowdown. This is the whole trick
Record the interactionNot the page load — the scroll, the open, the drag that feels wrong
Read the frame budget60 fps is 16.7 ms per frame. Anything longer is a dropped frame, whatever it looks like
Find the purpleLayout and Recalculate Style blocks in the flame chart are the reflow you are looking for
Check the long tasksAny task over 50 ms blocks input — that is the tap that felt ignored
Two habits follow from the number. Animate only transform and opacity, because they skip layout and paint entirely; and batch reads before writes, because interleaving offsetHeight with a style change forces the browser to recompute layout on every iteration. Throttled DevTools is the cheapest device lab in existence, and it costs one dropdown.
🌳 The DOM (Document Object Model) & Events — Bubbling & Delegation Browser ▶
Reference
How Clicks Travel Through the Page
The DOM is the live tree of the page that JavaScript manipulates. Events flow through it in phases — understanding this powers efficient event handling. 
// Event delegation: one listener for many children
list.addEventListener('click', (e) => {
  const item = e.target.closest('.item');
  if (item) select(item.dataset.id);
});
PhaseDetail
CaptureTop → target (rarely used)
TargetThe element clicked
BubbleTarget → top (default for listeners)
Delegation attaches one listener to a parent and uses bubbling to handle any child — essential for dynamic lists (no re-binding on add/remove). stopPropagation() halts bubbling; preventDefault() stops the browser's default action.
The bug that sent you here
The Click Handler Works, Until the Row Was Added After Page Load
The most common DOM bug in existence: handlers attached in a loop at load time, and any element created afterwards — by a fetch, a framework render, a “load more” button — has none. The element looks identical and does nothing, which is why the first instinct is usually to blame the CSS (Cascading Style Sheets) or the framework rather than the listener that was never attached.
SymptomCause, and the fix
New rows are dead, original rows workListeners were attached to elements that existed then. Delegate to a parent that always exists and check e.target.closest('.row')
A handler fires twiceIt was attached twice — often a re-render that never removed the first. Same function reference or an AbortController signal to remove it
Someone else's handler stopped firingstopPropagation() upstream. It is not a local decision: it silences every ancestor, including analytics and framework roots
The form reloads the pageThe submit handler threw before preventDefault(), or never called it
A scroll or touch handler is jankyIt is blocking. { passive: true } tells the browser it will not call preventDefault
Delegation is the habit that removes the first two rows entirely: one listener on a container that outlives its children handles every present and future row, survives re-renders, and costs one listener instead of N. It is also why frameworks attach at the root rather than per element.
🗃️ Web Storage — Cookies, localStorage & IndexedDB Browser ▶
Reference
Where State Lives in the Browser
The browser offers several places to persist data, each with different size, lifetime, and security properties. Picking the wrong one causes bugs and vulnerabilities.
StoreUse / Note
CookiesSent with every request; use HttpOnly+Secure for auth tokens
localStorage~5MB, persists, sync API (Application Programming Interface) — readable by JS (JavaScript) (XSS risk)
sessionStoragePer-tab, cleared on close

Cache APIStore responses for service workers/PWAs
Security: never store auth tokens in localStorage — any XSS (Cross-Site Scripting) reads them. Prefer HttpOnly cookies (JS can't touch them). Ties to the web-security cards.
Measure it
The Browser Can Refuse, and It Can Take It Back Later
Storage is not memory you own — it is space the browser lends you under a policy that differs per browser and changes between versions. Two failure modes never appear in development: the write throws, and the data is silently gone next week.
SituationWhat actually happens
Private / incognito windowQuota can be tiny or zero; localStorage.setItem throws QuotaExceededError
Site data blocked by the userThe accessor itself throws — reading localStorage is enough to break the page
Safari, no visit for weeksScript-writable storage can be cleared under ITP; treat it as a cache, not a record
Storage pressure on the deviceNon-persistent origins are evicted first, and nobody asks you
Big writes on the main threadlocalStorage is synchronous — a large object blocks rendering to serialise it
Write every access inside try/catch, and make the page correct when the value is missing rather than treating that as an error state. The rule of thumb: if losing it would matter, it belongs on a server; browser storage is for conveniences a user would not notice losing — a remembered tab, a collapsed section, an unsent draft. For anything larger or structured, IndexedDB is asynchronous and does not block the main thread.

📏 Flexbox — One-Dimensional Layout CSS ▶
Reference
Aligning Things in a Row or Column
Flexbox lays out items along a single axis and is the go-to for components: navbars, toolbars, centering, card rows. Set display:flex on the parent, then control alignment and distribution. 
.bar {
  display: flex;
  justify-content: space-between;  /* main axis */
  align-items: center;             /* cross axis */
  gap: 1rem;
}
PropertyControls
flex-directionrow (default) or column — sets the main axis
justify-contentSpacing along the main axis
align-itemsAlignment on the cross axis
flex: 1Grow to fill; flex-wrap to wrap
gapSpace between items (no more margin hacks)
Centering, solved: display:flex; justify-content:center; align-items:center — the answer to a decade of "how do I center a div."
The bug that sent you here
The Flex Item Refuses to Shrink and Pushes the Page Wider Than the Screen
A long URL (Uniform Resource Locator), a wide table or a `pre` block inside a flex item makes the whole layout overflow horizontally, and no amount of width: 100% or overflow: hidden on the child fixes it. The cause is one line in the spec that nobody meets until it bites: a flex item's default min-width is auto, not 0 — it will not shrink below its content's intrinsic size.
SymptomCause, and the fix
Horizontal scrollbar caused by one long word or tablemin-width: 0 on the flex item (or min-height: 0 in a column)
overflow-x: auto on the child does nothingThe child is not too wide — the item refuses to shrink. Fix the item, then scroll inside the child
flex: 1 items are not equal widthsflex: 1 is 1 1 0%; flex-grow: 1 alone leaves flex-basis: auto, which is content-sized
gap makes items overflow their containerGaps are added after basis is computed. Let items shrink, or subtract the gap from the basis
Text truncation with text-overflow: ellipsis never triggersSame root cause. The ellipsis needs a constrained box, which min-width: auto prevents
min-width: 0 is the single most useful line of CSS (Cascading Style Sheets) in a flex layout, and it looks like it should do nothing. If a flex container is overflowing and you cannot see why, set it on the item before investigating anything else — it resolves this whole table's first, second and fifth rows at once.
🔲 CSS (Cascading Style Sheets) Grid — Two-Dimensional Layout CSS ▶
Reference
Rows and Columns at the Same Time
Grid handles two dimensions at once — perfect for page layouts and any grid of cards. Where Flexbox is content-driven, Grid is layout-driven: you define the structure, items flow in. 
.gallery {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(200px, 1fr));
  gap: 1rem;
}
FeatureDetail
grid-template-columns/rowsDefine tracks; fr = fraction of free space
repeat() + minmax()Responsive columns without media queries
auto-fit / auto-fillWrap columns to fit the container
grid-template-areasName regions; lay out visually in CSS
Rule of thumb: Grid for the overall page/section layout, Flexbox for the components inside it. The auto-fit + minmax one-liner gives a fully responsive card grid with zero media queries.
The bug that sent you here
One Long Word Blows the Column Out Past 1fr
Grid has the same intrinsic-minimum rule as flexbox, wearing different syntax. 1fr is shorthand for minmax(auto, 1fr), and that auto minimum is the content's intrinsic size — so a wide table, a long URL (Uniform Resource Locator) or a pre block makes a “flexible” column wider than its share, and the other columns shrink to compensate.
SymptomCause, and the fix
A 1fr column is far wider than the othersIts content will not fit. minmax(0, 1fr) lets it actually shrink
The grid overflows its container horizontallySame rule. Fix the track, then let the child scroll with overflow-x: auto
auto-fit collapses to one columnNo items, or a minmax() minimum larger than the container. auto-fill keeps empty tracks
Items land in the wrong cells after one is hiddenAuto-placement re-flows. Name the areas, or place explicitly, if position must be stable
grid-template-areas silently does nothingEvery row string must have the same number of columns, or the whole declaration is invalid
The pair to remember together: minmax(0, 1fr) in Grid is min-width: 0 in Flexbox. Both exist because both layout models default to “never smaller than the content”, which is the right default for text and the wrong one for anything that can be arbitrarily wide.

✨ Modern CSS (Cascading Style Sheets) — Custom Properties, :has() & Layers CSS ▶
Reference
CSS Got Genuinely Powerful
Recent CSS added features that used to need preprocessors or JavaScript. Worth knowing because they simplify code you may still be writing the old way. 
:root { --brand: #f97316; }
.btn { background: var(--brand); }
/* style a label only if it HAS an invalid input */

FeatureDoes
Custom propertiesReal variables — themeable, runtime-changeable
:has()The "parent selector" — style based on descendants
NestingNative nested rules (no Sass needed)
@layerCascade layers — tame specificity wars
clamp/min/maxMath in CSS for fluid design
Custom properties + prefers-color-scheme is how modern dark mode works — swap variable values, not whole stylesheets (exactly how this site themes itself).
The bug that sent you here
The var() Fallback Did Not Apply, and the Property Came Out Unset
Custom properties do not behave like the rest of CSS and the difference only shows up when something is wrong. They are substituted at computed-value time, which means a syntactically valid-looking value can be garbage by the time it is used — and when that happens the property becomes unset (inherited or initial), not the declaration you wrote before it. The usual cascade fallback does not save you.
SymptomCause
A property vanishes instead of using the earlier declarationInvalid at computed-value time. A bad var() makes the property unset, and an earlier valid declaration is not used
var(--x, red) ignored the fallbackThe fallback applies when --x is undefined, not when it holds an invalid value
A theme variable leaks into a componentCustom properties inherit. Set them on the element that owns the scope, not on :root by default
--gap: 10 then padding: var(--gap)px failsSubstitution is textual and happens too late. Use calc(var(--gap) * 1px)
:has() works in one browser and not the buildIt is widely supported now, but a build-time CSS parser that predates it can drop the whole rule
Two habits make the whole class of bug visible. Type your custom properties with @property where the browser supports it — it gives them a syntax, an initial value, and real invalid-value behaviour instead of silent unsetting. And register fallbacks at the point of use, because a var() that resolves to nothing is a very quiet way to lose a colour.

🔒 Closures, Scope & this JavaScript ▶
Concept
The Interview Trio, Explained
Three JS concepts that confuse beginners and get asked in every interview. Get them and most "weird JavaScript" stops being weird. 
function counter() {
  let n = 0;                 // captured by the closure
  return () => ++n;         // remembers n after counter() returns
}
const c = counter(); c(); c();  // 1, 2
ConceptDetail
ScopeWhere a variable is visible; let/const are block-scoped
ClosureA function that remembers variables from where it was defined
thisDepends on how a function is called (not where defined)
Arrow functionsNo own this — inherit from the enclosing scope
this gotcha: a method passed as a callback loses its this. Arrow functions or .bind() fix it. Closures power data privacy, memoization, and every event handler that "remembers" state.
The bug that sent you here
The Loop Printed 5 Five Times, and This Became Undefined
Two symptoms bring people to this card, and neither of them sounds like “closures”. One: a loop that schedules something prints the final value every time instead of 0, 1, 2, 3, 4. Two: a method that works as obj.save() throws “Cannot read properties of undefined” the moment you pass it somewhere as obj.save.
SymptomCause, and the fix
for (var i…) setTimeout(() => log(i)) prints 5, 5, 5, 5, 5var is function-scoped — one i, shared. let makes one binding per iteration
A callback reads a stale value from an earlier renderIt closed over that render's variable. In React, that is the dependency array's job
this is undefined inside a passed methodthis is decided by how the function is called, not where it was written
Fix for thatobj.save.bind(obj), an arrow wrapper () => obj.save(), or make it a class field
An arrow function inside a method sees the right thisArrows have no this of their own — they take the enclosing one. This is why they fixed the 2010s callback mess
The single sentence that resolves both symptoms: a closure captures the variable, not its value at the time, and this is not part of the closure at all. Once those are separated, the var/let loop and the detached-method error stop looking like the same mystery, which is how most people first meet them.
⏳ Async Deep — Promises, await & the Event Loop JavaScript ▶
Concept
How Single-Threaded JS Does Many Things
JavaScript runs on one thread but stays responsive via the event loop: long operations (network, timers) run elsewhere and their callbacks are queued back. Promises and async/await make this readable. 
async function load() {
  try {
    const [a, b] = await Promise.all([getA(), getB()]); // parallel
    return merge(a, b);
  } catch (e) { handle(e); }
}
ConceptDetail
PromiseA value that arrives later (pending → fulfilled/rejected)
async/awaitWrite async code that reads like sync
Microtask vs macrotaskPromises (micro) run before timers (macro)
Promise.all / race / allSettledCoordinate multiple promises
Parallel vs serial: await a; await b; runs one after the other; Promise.all([a,b]) runs them together — a common performance win. Never await in a loop when the iterations are independent.
The bug that sent you here
forEach Returned Immediately and Nothing Was Saved
Two opposite symptoms, both from the same misunderstanding of what await does. One: an async callback inside forEach — the loop finishes instantly, the function returns, and the writes land after the caller has already moved on, or not at all. Two: a for loop with await inside takes thirty seconds for thirty requests that could have taken one.
SymptomCause, and the fix
arr.forEach(async x => await save(x)) completes instantlyforEach ignores the returned promise. Use for…of with await, or Promise.all(arr.map(save))
Thirty sequential requests take thirty secondsawait inside a loop serialises. Promise.all when they are independent
“UnhandledPromiseRejection” with no stack you recogniseA promise nobody awaited threw. Promise.allSettled when partial failure is acceptable
One failure loses all the successesPromise.all rejects on the first failure. allSettled returns every outcome
A setTimeout(…, 0) runs after a resolved promiseMicrotasks (promises) drain before the next macrotask (timers). That ordering is the event loop
The sentence that covers all five: await pauses the function it is in, and nothing else. It does not pause a loop that never looked at the promise, does not make independent work parallel, and does not stop the rest of the program. Deciding whether calls are independent is the whole design question — Promise.all when they are, for…of with await when each depends on the last.
🧬 Prototypes & Modern Classes JavaScript ▶

The bug that sent you here
It Worked as obj.method() and Broke as setTimeout(obj.method)
class syntax hides prototypes well enough that people meet them only when something breaks. ⚛️ React — Components, Hooks & the Mental Model Frameworks ▶
Reference
UI (User Interface) as a Function of State
React's core idea: your UI is a function of state — UI = f(state). You describe what the screen should look like for the current data; React efficiently updates the DOM (Document Object Model) when state changes. 
function Counter() {
  const [n, setN] = useState(0);
  return <button onClick={() => setN(n + 1)}>{n}</button>;
}
ConceptDetail
ComponentsReusable functions returning JSX (JavaScript XML)
PropsRead-only inputs passed down
useState / useReducerLocal state
useEffectSide effects (fetch, subscriptions) — has gotchas
KeysStable list identity — never use array index if items change
The rules of hooks: call them at the top level, same order every render. State updates are asynchronous and batched. "Lift state up" to the nearest common parent when siblings need to share it.
The Fingerprint
Most React Bugs Are Fighting UI = f(state) — useEffect Is Not a Lifecycle Hook
Nearly every React bug is an attempt to work around UI = f(state) instead of with it, and the culprit is usually useEffect. Effects are for synchronising with external systems — a subscription, a non-React widget, the browser DOM — but they get used as a dumping ground for “run some code when things change,” which produces two classic failures. Derived state in an effect: storing a value that could be computed during render (a filtered list, a total) and wiring an effect to keep it in sync — extra renders and a copy that desyncs. And responding to an event in an effect instead of the handler that caused it: the effect fires on the state change, not the click, so the timing is wrong. The third trap is the stale closure — a callback captures the state from the render that created it, so a setInterval quietly reads an old value (the “why is my counter stuck” bug).
The instinctWhy it's wrongWhere it belongs
useEffect to derive stateExtra render; a copy that desyncsCompute it during render
useEffect to respond to a clickFires on state change, not the eventThe event handler
useEffect to reset state on a prop changeFights the model; flashes stale UIA key prop, or derive it
Reading state in setIntervalStale closure — captures the old render's valueA ref, or the functional updater
So before reaching for useEffect, ask whether the work synchronises with something outside React — if not, it almost certainly belongs in render (for derived values) or an event handler (for responses to actions). The rules of hooks keep the machinery working; this is the deeper discipline that keeps the app correct: describe the UI as a function of state and let React run it, rather than pushing changes around by hand with effects.

The Decision
Rendering Mode Is a Per-Route Decision — and the New Axis Is the Server/Client Boundary
The table sorts modes by page type; the sharpening is that it's a per-route (often per-component) choice, not one setting for the app: a marketing page wants SSG, its pricing table might want ISR, the dashboard behind login wants CSR or SSR — in the same codebase. The current frontier moves the decision inward to the server/client boundary. With server components, everything is server-rendered by default and ships no JavaScript; a "use client" directive marks where interactivity — and its JS — begins. So the skill is pushing that boundary down: keep data-fetching and static content on the server, isolate interactivity into small client leaves. The classic mistake is marking a large tree "use client" to make one button interactive, which drags the whole subtree's JS to the browser and undoes the benefit.

SSR and personalisation are powerful, but each is a server you operate and a cost per request, so reach for them where freshness or SEO demands it, not by default.
🗄️ State Management — When You Actually Need It Frameworks ▶
Concept
Don't Reach for Redux by Default
As apps grow, sharing state gets messy — but the answer usually isn't a big global store. Distinguish server state (data from an API) from client state (UI toggles); they need different tools.
NeedReach for
Server data (caching, refetch)React Query / SWR — not a global store
Simple shared UI (User Interface) stateContext, or lift state up
Complex global client stateZustand / Redux Toolkit / signals
URL (Uniform Resource Locator) as stateQuery params for filters/tabs (shareable)
Biggest insight: most "state management" pain is really server state (loading, caching, revalidation) — a data-fetching library like React Query solves it far better than Redux. Add global stores only for genuinely global client state.
The Fingerprint
Most State Bugs Aren't About the Library — They're State That Isn't State
The library debate hides the real source of state bugs: storing things that should not be stored at all. Three patterns cause most of it. Derived state — keeping fullName beside firstName and lastName, or isValid beside the field it validates — desyncs the moment one changes without the other, and no library prevents it. Copied server state — pulling API (Application Programming Interface) data into a client store “so components can read it” — creates a second source of truth that goes stale the instant the server changes. Over-globalised state — putting in a shared store what one subtree owns — means a value changes and something three screens away breaks for reasons nobody can trace. The through-line: a state-management problem is usually a state-modelling problem — the same fact living in two places.
Anti-patternThe bug it becomesThe fix
Store derived data (totals, isValid)Desync — the copy and its source disagreeCompute it on render; derive, don't store
Copy server data into a client storeTwo sources of truth; the copy goes staleLet a data-fetching cache own it
Globalise component-local stateSpooky action at a distance; untraceable changesColocate — keep state near its only user
Keep filters/tabs in memoryNot shareable, lost on refreshPut it in the URL — the URL is state
So before choosing a store, find the actual source of truth and keep exactly one copy: derive what can be derived, let the server's cache own server data, colocate what one subtree owns, and push shareable state into the URL. Do that and most apps need almost no “state management” at all — which is why the honest first answer to “which state library?” is usually “none yet”.

How the Frontend Talks to APIs (Application Programming Interface)

Measure it

◈ GraphQL on the Backend — Schema, Resolvers & Caching Backends ▶
Reference
One Endpoint, Client-Shaped Responses
GraphQL exposes a typed schema through one endpoint; the client specifies exactly which fields it wants. It solves REST (Representational State Transfer)'s over- and under-fetching, at the cost of new complexity.

  user(id: 42) { name, orders { total } }   # exactly these fields
}
ConceptDetail
Schema & typesStrongly typed contract
Query / Mutation / SubscriptionRead / write / realtime
ResolversServer functions that fetch each field

When to use: many clients with different data needs, or deeply nested data. For simple CRUD (Create, Read, Update, Delete), REST is often simpler. Caching is harder than REST (one endpoint, POST) — weigh the trade-off.
The Decision
GraphQL Doesn't Remove Complexity — It Moves It Server-Side and Hands the Client a Loaded Gun
The pitch is client-shaped responses; the reality is that the flexibility you give the client becomes a liability you own on the server. A client that specifies its own query can also specify a catastrophic one — a deeply nested user { friends { friends { friends } } } or a very wide selection that fans out into thousands of database hits — so GraphQL needs a defensive layer REST doesn't: query depth limits, complexity/cost analysis, and often persisted (allow-listed) queries in production. Caching regresses from free to your problem: REST's HTTP (HyperText Transfer Protocol) GETs cache in the browser and at the CDN (Content Delivery Network) for nothing, while GraphQL's single POST endpoint makes caching field-level or persisted-query work you build. And observability breaks on the URL (Uniform Resource Locator) — every operation is POST /graphql, so the path-based metrics, logs and rate-limits you relied on must be rebuilt per operation.
What GraphQL gives the clientThe responsibility it hands the server
Ask for exactly the fields it wantsN+1 fan-out per field — batch with DataLoader
Arbitrarily nested queriesDepth + complexity limits, or a query is a DoS (Denial of Service)
One flexible endpointCaching becomes field-level/persisted, not free HTTP+CDN
Any operation over POST /graphqlRebuild per-operation metrics, logs and rate-limits
So reach for GraphQL when many clients genuinely need different shapes of deeply-related data — the problem it is uniquely good at — but go in knowing you are relocating complexity, not removing it. Budget for the defensive layer, the caching you now own, and the observability you must rebuild. For simple CRUD with one client, REST keeps all of that for free, which is why “GraphQL by default” is usually the wrong call.
🔴 Realtime — WebSockets, SSE (Server-Sent Events) & Polling Backends ▶
Reference
Pushing Data to the Browser
HTTP (HyperText Transfer Protocol) is request/response — the server can't just push. For live features (chat, notifications, dashboards) you need a different transport. Pick the lightest one that fits.
OptionUse
WebSocketsFull-duplex, persistent — chat, games, collaboration
Server-Sent EventsServer→client stream over HTTP — feeds, notifications (simpler)
Long pollingFallback where sockets aren't available
Short pollingJust refetch on a timer — fine for low-frequency updates
Don't over-engineer: if data changes every few minutes, polling is simplest. Reserve WebSockets for genuinely bidirectional, high-frequency needs. SSE is the underrated middle ground for one-way streams.
The Fingerprint
The Cost of Realtime Is Operational, and It Arrives After Launch
Choosing the transport is the easy half; the half that bites is what a persistent connection does to the rest of the stack. A WebSocket is stateful and pinned to one server, which quietly breaks assumptions built for request/response. Proxies and load balancers buffer or time out idle connections unless told not to. Horizontal scaling stops being free: a message published on server A must reach a client connected to server B, so you need a pub/sub backplane (Redis, NATS) to fan out — the demo that worked on one box falls over across three. Auth cannot ride the usual per-request header, so you authenticate once at the handshake and handle token expiry mid-connection. And you own reconnection and state resync. SSE sidesteps most of it — plain HTTP, automatic reconnection with Last-Event-ID, rides cookies — at the price of being one-way and, on HTTP/1.1, capped by the browser's per-domain connection limit.
Hidden costWebSocketsSSE
Proxy / load-balancer behaviourNeeds explicit upgrade and idle-timeout configJust HTTP — usually works untouched
Scaling across serversNeeds a pub/sub backplane to fan outSame fan-out need, but connections are cheap HTTP
AuthOnce at the handshake; handle mid-connection expiryRides normal cookies / headers
ReconnectionYou write itBuilt in (Last-Event-ID)
So the honest decision adds the operational line to the transport line: if you do not need client→server streaming, SSE gives you most of realtime with almost none of the operational tax. Reach for WebSockets when interaction is genuinely bidirectional and high-frequency — and when you do, budget for the backplane and the reconnection logic up front, because they are not extras, they are the actual work.
🔑 Frontend Auth — Tokens, Cookies & OAuth (Open Authorization) Backends ▶
Concept
Logging Users In, Safely
Auth on the frontend is mostly about where you store the credential and how you attach it. Get this wrong and you ship an XSS-exploitable token. Ties directly to the security domain's OAuth/session cards.
ApproachDetail
HttpOnly cookieJS (JavaScript) can't read it → XSS-safe; pair with SameSite/CSRF protection
JWT (JSON Web Token) in localStorageConvenient but XSS-readable — widely discouraged
OAuth / OIDC (OpenID Connect) + PKCE (Proof Key for Code Exchange)"Sign in with…"; PKCE for public clients
Refresh flowShort-lived access token + refresh token rotation
Rule: prefer HttpOnly, Secure, SameSite cookies for session tokens. Never store long-lived secrets where JavaScript can read them. Auth is one place to use a battle-tested library, not roll your own.
The Fingerprint
There Is No XSS-Proof Place to Put a Token — Storage Narrows the Attack, It Doesn't Close It
The cookie-vs-localStorage debate is real but oversold, because neither survives XSS (Cross-Site Scripting) intact. An attacker who can run JavaScript in your page cannot read an HttpOnly cookie — but they don't need to: the cookie rides along on every request they trigger, so they act as the user without ever seeing the token. localStorage is worse (the token is stolen and reused anywhere), but the cookie is not safe, only safer. So storage choice changes the shape of the XSS win; it does not prevent it. The controls that actually bound the damage are elsewhere: short access-token lifetimes with refresh rotation (shrink the window), binding a token to a device or session (a stolen one is useless elsewhere), and — the root fix — not having XSS at all (CSP, output encoding).
BeliefThe gapThe control that matters
“HttpOnly cookie = XSS-safe”XSS still rides the cookie to act as the userShort lifetimes; the real fix is no XSS
“localStorage is fine with a CSP (Content Security Policy)”One CSP bypass and the token is exfiltratedPrefer HttpOnly; keep long-lived secrets out of JS reach
“Long-lived token for convenience”A stolen token works for its whole lifeShort access token + rotating refresh
“The token is the identity”A leaked token is portableBind to device/session; revoke server-side
So prefer HttpOnly, Secure, SameSite cookies as the default — they remove token theft, a real win — but stop treating where you store the token as the whole security decision. What decides your exposure is what an attacker can do in the window before the token expires and can be revoked, and that is answered by lifetime, rotation and binding — and, above all, by not shipping the XSS in the first place.

🌍 Internationalization (i18n) — Designing for Languages You Do Not Speak Quality ▶
Concept
i18n Is Not Translation — It Is Removing the Assumptions That Make Translation Impossible
The two words are used interchangeably and mean opposite halves of the job. Localization (l10n) is producing the French: translators, glossaries, a review cycle. Internationalization (i18n) is everything you do first so that producing the French is possible at all — and essentially all of it is removing English grammar and English typography from your code. It is engineering work, it happens before a single string is sent anywhere, and it is very cheap now and very expensive in two years. The costly version is not the translation budget; it is discovering that fixing the code is a rewrite of every screen.
The tell that a codebase was never internationalized is not the absence of a translation file. It is string concatenation in the view layer, and it is visible in one grep.
Concept
The Concatenation Bug, Which Is the Whole Subject in One Line
This looks harmless and cannot be translated by anyone, at any budget: 
// Untranslatable — three separate mistakes
"You have " + n + (n === 1 ? " message" : " messages")

// Translatable — one string, named placeholder, plural handled by the format
t("inbox.count", { count: n })
  en: "{count, plural, one {You have # message} other {You have # messages}}"
  pl: "{count, plural, one {...} few {...} many {...} other {...}}"
Assumption baked inWhere it fails
Word order is subject-verb-objectJapanese and Turkish put the verb last; a translator cannot reorder fragments your code will re-join
Plural means "one" versus "not one"Polish and Russian have few and many; Arabic uses six categories; Japanese uses one
Zero is just another plural"You have 0 messages" is grammatical; "No messages" is what a human writes, and only a message format lets a translator choose
Gender does not affect the sentenceIn Spanish and Hebrew the surrounding words change with the subject's gender — so the variable has to be inside the translated string
The rule that prevents all of it: a translator must receive whole sentences with named placeholders, never fragments. If a translator cannot move a placeholder to the other end of the sentence, the string is broken regardless of how correct the English reads.
Reference
Never Format These By Hand
Every runtime worth using ships a locale database. Hand-rolling any row of this table is how a product ends up telling a German user that something costs 1,234.50 € when it should say 1.234,50 €.
ThingUseWhat varies that you would not guess
NumbersIntl.NumberFormatDecimal comma; grouping by 2s in India (12,34,567); non-Western digits
CurrencyIntl.NumberFormat with a currency codeSymbol position, spacing, and the number of decimal places — JPY has none
DatesIntl.DateTimeFormatOrder, separators, 12- versus 24-hour, and which day the week starts on
Relative timeIntl.RelativeTimeFormat"3 days ago" declines differently and is not always a suffix

A locale is not a language: pt-BR and pt-PT differ in vocabulary and formatting, and en-GB and en-US disagree about the date order in a way that silently produces the wrong day for eleven days a month. Store and negotiate full locale tags, not two-letter languages.
Concept
Layout: Text Expands, and Some of It Runs the Other Way
Translated text is routinely much longer than the English — German and Finnish especially, and short strings expand proportionally most, so buttons and labels break before paragraphs do. Any container sized to fit the English is a defect waiting for a translation file.

The length assumption hides in one more place: a "character" is not a byte, a code point, or a visible glyph. A single family emoji is one thing on screen and several code units in JavaScript, so a database column sized in characters, a validator counting .length, and a user counting what they can see will all disagree. Concept
The Assumptions Hiding in Your Forms
Personal data models leak the developer's own country more reliably than anything else in the codebase, and each of these locks out real users rather than merely annoying them.
AssumptionReality
First name and last nameMany people have one name, several family names, or a family name written first. Store a full name and, only if you genuinely need it, a separate display name

Time deserves its own warning. Store instants in UTC (Coordinated Universal Time) and render in the viewer's zone — but "the day" is a local concept: a birthday, an opening time and a monthly billing date have no timezone at all, and converting them to UTC is what makes them arrive a day early for half the world. Concept

The reason i18n bugs ship is that they are invisible until a real translation arrives, which is usually after the design is frozen. Pseudo-localization removes that dependency: generate a fake locale from the English by accenting every character, padding the string, and bracketing it.

🧰 Accessibility Remediation — Working Through an Audit Backlog A11y ▶

🛡️ Frontend Security — XSS (Cross-Site Scripting), CSRF (Cross-Site Request Forgery) & CSP (Content Security Policy) Security ▶
Concept
The Browser-Side Attack Surface
The frontend has its own security risks distinct from the server. The big three every web dev must know — directly bridging to the security domain's web cards.
AttackDefense
XSSInjected script runs in your page → escape output, avoid innerHTML/dangerouslySetInnerHTML, use CSP

Frameworks help: React escapes by default (which is why dangerouslySetInnerHTML is named to scare you). Never build HTML (HyperText Markup Language) from untrusted strings; sanitize any rich content with a vetted library (DOMPurify).
The Fingerprint
XSS Is an Output-Encoding Bug, Not an Input One — Which Is Why Sanitising Input Fails
The instinct on XSS is to sanitise input at the door, and it keeps failing for a structural reason: the same string is safe in one place and dangerous in another. <b>hi</b> is inert as HTML text, live as an HTML attribute, a catastrophe inside a <script> block, and different again inside a URL (Uniform Resource Locator) or a CSS (Cascading Style Sheets) value. There is no single “clean” version of a string, so cleaning it on the way in is guessing which context it will land in. Encoding has to happen at output, escaped for the specific context it is rendered into — which is what a framework's default escaping does and what innerHTML / dangerouslySetInnerHTML bypass. The half people miss: the modern XSS is DOM-based — a client-side sink like innerHTML, location or eval fed attacker-controlled data — and it never reaches the server, so server-side sanitisation cannot see it.
BeliefWhy it failsWhat actually works
“Sanitise input at the door”The safe form depends on the output context, unknown at inputEncode at output, per context (framework default)
“The server sanitises, so we're safe”DOM (Document Object Model) XSS lives entirely client-sideAudit client sinks: innerHTML, location, eval
“We have a CSP, so XSS is handled”CSP limits blast radius, it doesn't remove the bugEncode first; treat CSP as defence-in-depth
“SameSite killed CSRF”Lax still allows top-level GETs; subdomains and non-cookie auth differKeep tokens on state-changing actions
So the durable rule is: never build markup from untrusted strings, let the framework encode at output, and where you must render rich content run it through a vetted sanitiser aimed at the right context. A nonce-based CSP is the seatbelt for the XSS you still missed — worth having, never the thing you rely on. Encode at the sink, not at the source.

Concept

The Fingerprint
A Service Worker Makes the Browser a Distributed-Systems Node — Versioning and Offline Writes Are the Hard Parts
“Test your update flow” undersells the shift: a service worker turns the browser into a node with its own cache and, with background sync, its own write buffer — and the two classic distributed-systems problems follow it home. Versioning first: the service worker is itself cached, and a newly deployed one installs but does not take control while old tabs stay open (the waiting state), so users keep running old code after you ship — and a cache-first strategy on your own HTML/JS can pin a user to a months-old version until the cache is explicitly busted. A bug fix is not fixed until clients actually pick it up. Offline writes second: let a user act offline and you now hold client-side pending mutations that sync later, which means ordering, conflicts, and “the server changed too” — eventual consistency you now own on the client.
The capabilityThe distributed-systems problem it brings
Service worker caches your HTML/JSUsers stuck on old code until the cache is busted
A new service worker “waiting”The deploy doesn't take effect while a tab stays open
Cache-first for the app shellFast, but a fix ships to nobody until you version the cache
Background sync / offline writesPending client mutations → ordering and conflict resolution
So decide the caching policy per resource with the update path in mind: cache-first for truly static, fingerprinted assets; network-first or stale-while-revalidate for anything that changes; and a deliberate way to activate a waiting service worker so a critical fix reaches users now. And treat offline writes as the distributed-systems feature they are — with a conflict story — not a free toggle. “Offline + installable” is a real win for content sites precisely because they mostly read; the moment users write offline, you have signed up to reconcile.
🌍 Rendering at the Edge — CDNs (Content Delivery Network) & Edge Functions Shipping ▶
Concept
Compute Close to the User
A CDN caches static assets in hundreds of locations worldwide so users download from nearby. Edge functions push compute there too — run code milliseconds from the user.
ConceptDetail
CDN cachingStatic assets served from the nearest POP
Edge functionsLightweight compute at the edge (auth, redirects, A/B)
Image optimizationResize/format on the fly (WebP/AVIF) at the edge
Cache headersCache-Control, ETags, immutable hashed assets
Trade-off: edge runtimes are limited (no full Node APIs, short execution) — great for fast, small logic, not heavy work. Combined with hashed filenames + long cache TTLs (Time To Live), the edge makes global sites feel local.
The Decision
The Edge Moves Compute Close to the User — Your Data Is Still Far, and That's the Real Limit
An edge function runs milliseconds from the user; the catch is that your database usually doesn't. Push dynamic rendering or personalisation to the edge and, the moment that code needs data, it makes a round-trip to an origin database in one region — so you have moved the compute across the planet and left the data behind, and the edge function sits waiting on the same cross-continent call it was supposed to avoid. Data locality, not compute, is the real limit on edge rendering: it wins only when the data the function needs is also near the user — an edge KV store, a globally-replicated read replica, or a value cached at the edge. Second trap: hundreds of ephemeral edge locations can't pool connections to a regional database the way a handful of long-lived servers do, so a naive edge-to-Postgres setup exhausts connections — which is why edge-native stores and connection proxies exist.
What you moved to the edgeWhether it actually helps
Static assets (CDN)Always — what the edge is best at
Small stateless logic (auth check, redirect, A/B)Yes — no data round-trip needed
Personalised render needing your DBOnly if the data is at the edge too; else the origin round-trip erases the win
Direct edge → regional PostgresTrap — connection exhaustion from ephemeral locations
So decide by where the data is, not where the compute is: put at the edge the things that need no data or whose data you can replicate/cache there, and keep data-heavy rendering near the data. The edge is a caching and light-compute layer that makes global sites feel local; treat it as a database tier and you rediscover that latency is dominated by the slowest hop — which, for an edge function calling a single-region DB, is the very hop you tried to remove.

🔠 Typography & Visual Hierarchy — Making It Look Deliberate Without a Designer CSS ▶
Concept
Amateur Design Is Usually Not Ugly — It Is Undecided
Look at an interface that feels unpolished and the problem is rarely a bad colour or a bad font. It is that nothing has a consistent reason for the size it is. Nine different font sizes, margins of 12, 14, 15 and 18 pixels chosen by eye, and four greys that are almost the same. 🌗 Theming & Dark Mode — Semantic Tokens, the Flash, and the Parts That Break CSS ▶
Concept
Name Colours by Role, Never by Appearance
Dark mode is not hard because of the colours. It is hard because of the names. A variable called --grey-100 or --light-border is a description of how it looks, so in a dark theme it is either wrong or a lie — and a codebase full of them cannot be themed without reading every usage to work out what each one meant. 
/* Appearance names — untenable in two themes */
--white  --grey-100  --dark-text  --light-border

/* Role names — one definition per theme, no usage changes */
--bg  --bg-raised  --text  --text-muted  --border  --accent  --danger

If colours are written inline, the work is proportional to the codebase and no framework shortens it — which is why "we will add dark mode later" is a much larger promise than it sounds.

📝 Forms — Validation Timing, Autofill & the Details That Decide Completion Quality ▶
Concept
The Form Is Where Users Leave
Almost every consequential thing a user does on the web happens in a form — signing up, paying, booking, reporting a fault. It is also the part of the interface most often built quickly and never revisited, which is why abandonment concentrates there. The failures are rarely aesthetic. They are a field that rejects a valid phone number, an error that appears while you are still typing, a page that discards forty answers because one was wrong, and a password box that fights the password manager.
Concept
Validation Timing Is the Whole Experience
Most validation complaints are not about the rules. They are about when the rules fired, and there is a well-established answer that almost nobody implements by default.
WhenEffect
While typing, before the first blurThe worst option. Tells someone their email is invalid after two characters. It is correct and it feels like being interrupted mid-sentence
On blur, after leaving the fieldThe right default. The user has finished their thought and is ready to hear about it
While typing, after an error is shownThe right complement — once a field is known bad, live feedback shows the fix landing and the error clears the moment it is right
On submit onlyAcceptable for short forms, punishing for long ones: the user learns about six problems at once, having thought they were finished
Server-side, alwaysNot a UX (User Experience) choice. Client validation is a convenience; the server is the only place a rule is actually enforced
Blur to show, input to clear. Two lines of policy that remove most validation complaints, and the combination is what makes a form feel like it is helping rather than marking your work.

Error Messages That Do Something
Instead ofWrite
"Invalid input""Enter a date in the past" — say what would be valid, not that this is not
"Password does not meet requirements"Show the requirements, live, with the ones already met marked. The rules should never have been a secret
"An error occurred"What failed, whether their data was kept, and what to do now
A red border aloneBorder, icon, and text — colour alone is invisible to a colour-blind user and to a screen reader
An error summary at the top onlySummary and per-field messages, with the summary linking to each field. Long forms need both
Two things make errors reach everyone: associate the message with its input (aria-describedby) so a screen reader announces it on focus, and put the error summary in a live region so it is announced when it appears. Both are small, and without them a blind user gets a form that silently refuses to submit — see Web Accessibility (a11y) — WCAG & ARIA.
Concept
Let the Browser Help — It Is Better at This Than You Are
A great deal of form quality is free, and is lost by re-implementing things the platform already does well. 
<label for="email">Email</label>
<input id="email" name="email" type="email"
       autocomplete="email" inputmode="email" required>

<input type="password" autocomplete="current-password">   <!-- sign in -->
<input type="password" autocomplete="new-password">       <!-- sign up -->
AttributeWhat it buys
<label for>A larger tap target, screen-reader association, and voice control. A placeholder is not a label — it disappears exactly when the user needs it
autocompleteThe single highest-value attribute on a form. It fills addresses and cards in one tap and is required by accessibility guidance
inputmodeThe right mobile keyboard without changing the field's semantics — numeric for a code, without the arrows and locale rules of a number input
typeFree validation, the right keyboard, and native pickers
A real <form> with a submit buttonEnter submits, browsers offer to save credentials, and it works before JavaScript loads
Blocking paste in a password field is the clearest example of a well-meant rule that reduces security: it defeats password managers, so users type something memorable instead. The same goes for splitting a one-time code into six separate boxes without handling a pasted string.
Reference
The Assumptions Worth Removing
Each of these rejects real people, and each is written by someone reasoning from their own data.
RuleWho it excludes
A clever email regular expressionValid addresses with apostrophes, plus-signs and new top-level domains. Check for an @ and send a confirmation — delivery is the only real test
Phone numbers must be ten digitsMost of the world. Accept spaces and +, and normalise server-side
Names must be alphabetic, two parts, no punctuationHyphenated names, apostrophes, accents, single names, and anyone whose family name comes first
A maximum password length of 16Password managers, passphrases, and any user with good habits. A hash is fixed-length whatever the input
A postcode patternEvery country but yours. Validate per country or not at all — see Internationalization (i18n) — Designing for Languages You Do Not Speak
Required fields you do not needEveryone, a little. Every mandatory field costs completions; ask why each one is required and delete the ones with no answer
Concept
Long Forms, Where the Losses Are Largest
TechniqueWhy
Save progress as they goSessions expire, tabs close, phones ring. Losing twenty minutes of answers is the most expensive thing a form can do to someone
Preserve everything on a failed submitClearing a form on validation failure is unforgivable and is still a default in some stacks
One question per screen, on mobileReduces cognitive load and makes each error unmissable; costs taps, which is the right trade on a phone
Show progress honestly"Step 2 of 4" sets an expectation. A progress bar that stalls at 90% destroys the trust it was there to build
Disable the submit button only after a clickPrevents double submission. Disabling it until the form is valid hides why it cannot be submitted, which is the more common failure
Ask the cheap questions firstSunk cost is real and works in your favour; the invasive question lands better on screen three than on screen one
The highest-value single change in most long forms is the second row. A user who loses their answers rarely tries again, and unlike almost everything else on this card it costs one decision rather than a redesign.
