🖼️ How the Browser Renders a Page Browser ▶
Concept
From Bytes to Pixels
Understanding the rendering pipeline is what separates people who "write CSS" from people who make fast sites. The browser turns your HTML/CSS into pixels through a fixed sequence of steps.
StepDoes
Parse → DOMHTML becomes the Document Object Model tree
Parse → CSSOMCSS becomes the style tree
Render treeDOM + CSSOM combined (visible nodes only)
Layout (reflow)Compute geometry — where & how big everything is
PaintFill in pixels (text, colors, borders)
CompositeAssemble layers on the GPU
Render-blocking: CSS blocks rendering (the browser won't paint unstyled content); a plain <script> blocks parsing. Use defer/async and keep critical CSS small so the page paints fast.
🌀 Reflow, Repaint & What Causes Jank Performance ▶
Concept
Why Animations Stutter
To hit 60fps the browser has ~16ms per frame. Reflow (recomputing layout) is expensive; repaint is cheaper; compositing a transform is cheapest. Triggering layout every frame causes jank.
ChangeCost
width/height/top/leftReflow (layout) — avoid animating these
color/backgroundRepaint only
transform / opacityComposite only — GPU, no layout (animate these!)
Layout thrashing: reading a layout property (like offsetHeight) right after writing one forces a synchronous reflow in a loop. Batch reads, then writes. Animate transform and opacity — they skip layout and paint entirely.
🌳 The DOM & Events — Bubbling & Delegation Browser ▶
Reference
How Clicks Travel Through the Page
The DOM is the live tree of the page that JavaScript manipulates. Events flow through it in phases — understanding this powers efficient event handling. 
// Event delegation: one listener for many children
list.addEventListener('click', (e) => {
  const item = e.target.closest('.item');
  if (item) select(item.dataset.id);
});
PhaseDetail
CaptureTop → target (rarely used)
TargetThe element clicked
BubbleTarget → top (default for listeners)
Delegation attaches one listener to a parent and uses bubbling to handle any child — essential for dynamic lists (no re-binding on add/remove). stopPropagation() halts bubbling; preventDefault() stops the browser's default action.
🗃️ Web Storage — Cookies, localStorage & IndexedDB Browser ▶
Reference
Where State Lives in the Browser
The browser offers several places to persist data, each with different size, lifetime, and security properties. Picking the wrong one causes bugs and vulnerabilities.
StoreUse / Note
CookiesSent with every request; use HttpOnly+Secure for auth tokens
localStorage~5MB, persists, sync API — readable by JS (XSS risk)
sessionStoragePer-tab, cleared on close
IndexedDBLarge, async, structured — offline apps
Cache APIStore responses for service workers/PWAs
Security: never store auth tokens in localStorage — any XSS reads them. Prefer HttpOnly cookies (JS can't touch them). Ties to the web-security cards.

📏 Flexbox — One-Dimensional Layout CSS ▶
Reference
Aligning Things in a Row or Column
Flexbox lays out items along a single axis and is the go-to for components: navbars, toolbars, centering, card rows. Set display:flex on the parent, then control alignment and distribution. 
.bar {
  display: flex;
  justify-content: space-between;  /* main axis */
  align-items: center;             /* cross axis */
  gap: 1rem;
}
PropertyControls
flex-directionrow (default) or column — sets the main axis
justify-contentSpacing along the main axis
align-itemsAlignment on the cross axis
flex: 1Grow to fill; flex-wrap to wrap
gapSpace between items (no more margin hacks)
Centering, solved: display:flex; justify-content:center; align-items:center — the answer to a decade of "how do I center a div."
🔲 CSS Grid — Two-Dimensional Layout CSS ▶
Reference
Rows and Columns at the Same Time
Grid handles two dimensions at once — perfect for page layouts and any grid of cards. Where Flexbox is content-driven, Grid is layout-driven: you define the structure, items flow in. 
.gallery {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(200px, 1fr));
  gap: 1rem;
}
FeatureDetail
grid-template-columns/rowsDefine tracks; fr = fraction of free space
repeat() + minmax()Responsive columns without media queries
auto-fit / auto-fillWrap columns to fit the container
grid-template-areasName regions; lay out visually in CSS
Rule of thumb: Grid for the overall page/section layout, Flexbox for the components inside it. The auto-fit + minmax one-liner gives a fully responsive card grid with zero media queries.
📱 Responsive Design — Fluid, Mobile-First CSS ▶
Concept
One Site, Every Screen
Responsive design adapts the layout to the viewport. The modern approach is mobile-first (style the small screen, then add complexity up) and increasingly intrinsic (let the content size itself).
ToolUse
Media queriesBreakpoints by viewport width
Container queriesRespond to the parent's size — true component responsiveness
clamp()Fluid type/spacing: clamp(min, preferred, max)
rem / % / fr / vwRelative units over fixed px
<meta viewport>Required tag or mobile scales wrong
Container queries are the big recent shift: a card can restyle based on the space it has, so the same component works in a sidebar or full-width — impossible with media queries alone.
✨ Modern CSS — Custom Properties, :has() & Layers CSS ▶
Reference
CSS Got Genuinely Powerful
Recent CSS added features that used to need preprocessors or JavaScript. Worth knowing because they simplify code you may still be writing the old way. 
:root { --brand: #f97316; }
.btn { background: var(--brand); }
/* style a label only if it HAS an invalid input */
.field:has(input:invalid) { color: red; }
FeatureDoes
Custom propertiesReal variables — themeable, runtime-changeable
:has()The "parent selector" — style based on descendants
NestingNative nested rules (no Sass needed)
@layerCascade layers — tame specificity wars
clamp/min/maxMath in CSS for fluid design
Custom properties + prefers-color-scheme is how modern dark mode works — swap variable values, not whole stylesheets (exactly how this site themes itself).

At scale, ad-hoc CSS becomes unmaintainable. Design systems encode consistent spacing, color, and type as reusable tokens and components, so a large app stays coherent.
ApproachDetail

🔒 Closures, Scope & this JavaScript ▶
Concept
The Interview Trio, Explained
Three JS concepts that confuse beginners and get asked in every interview. Get them and most "weird JavaScript" stops being weird. 
function counter() {
  let n = 0;                 // captured by the closure
  return () => ++n;         // remembers n after counter() returns
}
const c = counter(); c(); c();  // 1, 2
ConceptDetail
ScopeWhere a variable is visible; let/const are block-scoped
ClosureA function that remembers variables from where it was defined
thisDepends on how a function is called (not where defined)
Arrow functionsNo own this — inherit from the enclosing scope
this gotcha: a method passed as a callback loses its this. Arrow functions or .bind() fix it. Closures power data privacy, memoization, and every event handler that "remembers" state.
⏳ Async Deep — Promises, await & the Event Loop JavaScript ▶
Concept
How Single-Threaded JS Does Many Things
JavaScript runs on one thread but stays responsive via the event loop: long operations (network, timers) run elsewhere and their callbacks are queued back. Promises and async/await make this readable. 
async function load() {
  try {
    const [a, b] = await Promise.all([getA(), getB()]); // parallel
    return merge(a, b);
  } catch (e) { handle(e); }
}
ConceptDetail
PromiseA value that arrives later (pending → fulfilled/rejected)
async/awaitWrite async code that reads like sync
Microtask vs macrotaskPromises (micro) run before timers (macro)
Promise.all / race / allSettledCoordinate multiple promises
Parallel vs serial: await a; await b; runs one after the other; Promise.all([a,b]) runs them together — a common performance win. Never await in a loop when the iterations are independent.
🧬 Prototypes & Modern Classes JavaScript ▶
Concept
JavaScript's Real Inheritance Model
Under the class syntax, JS uses prototypal inheritance: objects delegate to a prototype object. Knowing this explains how method lookup and class actually work.
ConceptDetail
Prototype chainMiss a property → look up the chain until null
classSyntactic sugar over prototypes (constructor, methods)
extends / superInheritance & calling the parent
Static / #privateClass-level members; true private fields (#)
Modern advice: favor composition and plain objects /modules over deep class hierarchies. But you must understand prototypes to debug "why is this method undefined?" and to read library code.
📦 Modules & Bundlers — ESM, Vite & Tree-Shaking JavaScript ▶
Reference
From Many Files to Shipped Code
Modern JS is written as ES modules (import/export) across many files, then a bundler optimizes them into what ships to the browser.
ConceptDetail
ESMStandard import/export (vs old CommonJS require)
BundlingCombine modules, resolve deps
Tree-shakingDrop unused exports → smaller bundles
Code-splittingLoad chunks on demand (per route)
Vite / esbuild / RollupFast modern tooling (webpack's successors)
Vite is the current default: instant dev server (native ESM, no bundling in dev) + optimized production builds. Tree-shaking is why import { thing } beats importing a whole library.
🔷 TypeScript — Types for JavaScript JavaScript ▶
Reference
Catch Bugs Before They Ship
TypeScript adds static types to JavaScript, caught at compile time. It's now the default for serious projects — the editor autocomplete and refactoring safety alone are worth it. 
type User = { id: number; name: string; email?: string };
function greet(u: User): string {
  return `Hi ${u.name}`;
}
FeatureDetail
Interfaces / typesDescribe object shapes
GenericsReusable, type-safe code (Array<T>)
NarrowingTypes refine via checks (unions, guards)
strict modeNull-safety & more — turn it on
Mental model: types are erased at build time — they guide the compiler and editor, then disappear. The payoff is fewer runtime undefined errors and fearless refactoring in large codebases.
