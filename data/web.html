🖼️ How the Browser Renders a Page Browser ▶
Concept
From Bytes to Pixels
Understanding the rendering pipeline is what separates people who "write CSS (Cascading Style Sheets)" from people who make fast sites. The browser turns your HTML/CSS into pixels through a fixed sequence of steps.
StepDoes
Parse → DOMHTML (HyperText Markup Language) becomes the Document Object Model tree
Parse → CSSOMCSS becomes the style tree
Render treeDOM + CSSOM combined (visible nodes only)
Layout (reflow)Compute geometry — where & how big everything is
PaintFill in pixels (text, colors, borders)
CompositeAssemble layers on the GPU (Graphics Processing Unit)
Render-blocking: CSS blocks rendering (the browser won't paint unstyled content); a plain <script> blocks parsing. Use defer/async and keep critical CSS small so the page paints fast.
🌀 Reflow, Repaint & What Causes Jank Performance ▶
Concept
Why Animations Stutter
To hit 60fps the browser has ~16ms per frame. Reflow (recomputing layout) is expensive; repaint is cheaper; compositing a transform is cheapest. Triggering layout every frame causes jank.
ChangeCost
width/height/top/leftReflow (layout) — avoid animating these
color/backgroundRepaint only
transform / opacityComposite only — GPU (Graphics Processing Unit), no layout (animate these!)
Layout thrashing: reading a layout property (like offsetHeight) right after writing one forces a synchronous reflow in a loop. Batch reads, then writes. Animate transform and opacity — they skip layout and paint entirely.
🌳 The DOM (Document Object Model) & Events — Bubbling & Delegation Browser ▶
Reference
How Clicks Travel Through the Page
The DOM is the live tree of the page that JavaScript manipulates. Events flow through it in phases — understanding this powers efficient event handling. 
// Event delegation: one listener for many children
list.addEventListener('click', (e) => {
  const item = e.target.closest('.item');
  if (item) select(item.dataset.id);
});
PhaseDetail
CaptureTop → target (rarely used)
TargetThe element clicked
BubbleTarget → top (default for listeners)
Delegation attaches one listener to a parent and uses bubbling to handle any child — essential for dynamic lists (no re-binding on add/remove). stopPropagation() halts bubbling; preventDefault() stops the browser's default action.

📏 Flexbox — One-Dimensional Layout CSS ▶
Reference
Aligning Things in a Row or Column
Flexbox lays out items along a single axis and is the go-to for components: navbars, toolbars, centering, card rows. Set display:flex on the parent, then control alignment and distribution. 
.bar {
  display: flex;
  justify-content: space-between;  /* main axis */
  align-items: center;             /* cross axis */
  gap: 1rem;
}
PropertyControls
flex-directionrow (default) or column — sets the main axis
justify-contentSpacing along the main axis
align-itemsAlignment on the cross axis
flex: 1Grow to fill; flex-wrap to wrap
gapSpace between items (no more margin hacks)
Centering, solved: display:flex; justify-content:center; align-items:center — the answer to a decade of "how do I center a div."
🔲 CSS (Cascading Style Sheets) Grid — Two-Dimensional Layout CSS ▶
Reference
Rows and Columns at the Same Time
Grid handles two dimensions at once — perfect for page layouts and any grid of cards. Where Flexbox is content-driven, Grid is layout-driven: you define the structure, items flow in. 
.gallery {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(200px, 1fr));
  gap: 1rem;
}
FeatureDetail
grid-template-columns/rowsDefine tracks; fr = fraction of free space
repeat() + minmax()Responsive columns without media queries
auto-fit / auto-fillWrap columns to fit the container
grid-template-areasName regions; lay out visually in CSS
Rule of thumb: Grid for the overall page/section layout, Flexbox for the components inside it. The auto-fit + minmax one-liner gives a fully responsive card grid with zero media queries.

🔒 Closures, Scope & this JavaScript ▶
Concept
The Interview Trio, Explained
Three JS concepts that confuse beginners and get asked in every interview. Get them and most "weird JavaScript" stops being weird. 
function counter() {
  let n = 0;                 // captured by the closure
  return () => ++n;         // remembers n after counter() returns
}
const c = counter(); c(); c();  // 1, 2
ConceptDetail
ScopeWhere a variable is visible; let/const are block-scoped
ClosureA function that remembers variables from where it was defined
thisDepends on how a function is called (not where defined)
Arrow functionsNo own this — inherit from the enclosing scope
this gotcha: a method passed as a callback loses its this. Arrow functions or .bind() fix it. Closures power data privacy, memoization, and every event handler that "remembers" state.
⏳ Async Deep — Promises, await & the Event Loop JavaScript ▶
Concept
How Single-Threaded JS Does Many Things
JavaScript runs on one thread but stays responsive via the event loop: long operations (network, timers) run elsewhere and their callbacks are queued back. Promises and async/await make this readable. 
async function load() {
  try {
    const [a, b] = await Promise.all([getA(), getB()]); // parallel
    return merge(a, b);
  } catch (e) { handle(e); }
}
ConceptDetail
PromiseA value that arrives later (pending → fulfilled/rejected)
async/awaitWrite async code that reads like sync
Microtask vs macrotaskPromises (micro) run before timers (macro)
Promise.all / race / allSettledCoordinate multiple promises
Parallel vs serial: await a; await b; runs one after the other; Promise.all([a,b]) runs them together — a common performance win. Never await in a loop when the iterations are independent.

⚛️ React — Components, Hooks & the Mental Model Frameworks ▶
Reference
UI (User Interface) as a Function of State
React's core idea: your UI is a function of state — UI = f(state). You describe what the screen should look like for the current data; React efficiently updates the DOM (Document Object Model) when state changes. 
function Counter() {
  const [n, setN] = useState(0);
  return <button onClick={() => setN(n + 1)}>{n}</button>;
}
ConceptDetail
ComponentsReusable functions returning JSX (JavaScript XML)
PropsRead-only inputs passed down
useState / useReducerLocal state
useEffectSide effects (fetch, subscriptions) — has gotchas
KeysStable list identity — never use array index if items change
The rules of hooks: call them at the top level, same order every render. State updates are asynchronous and batched. "Lift state up" to the nearest common parent when siblings need to share it.
🪝 React Patterns & Pitfalls Frameworks ▶

Most React bugs come from a handful of misunderstandings around effects, re-renders, and stale state. Knowing them saves days.

🗄️ State Management — When You Actually Need It Frameworks ▶
Concept
Don't Reach for Redux by Default
As apps grow, sharing state gets messy — but the answer usually isn't a big global store. Distinguish server state (data from an API) from client state (UI toggles); they need different tools.
NeedReach for
Server data (caching, refetch)React Query / SWR — not a global store
Simple shared UI (User Interface) stateContext, or lift state up

🔌 Fetch, REST (Representational State Transfer) & CORS (Cross-Origin Resource Sharing) in Practice Backends ▶
Reference
How the Frontend Talks to APIs (Application Programming Interface)
The browser's fetch makes HTTP (HyperText Transfer Protocol) requests. You'll spend real time on status codes, headers, and the one that trips everyone up: CORS. 
const res = await fetch('/api/users', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify(user),
});
if (!res.ok) throw new Error(res.status);   // fetch doesn't throw on 4xx/5xx!
ThingDetail
Status codes2xx ok, 3xx redirect, 4xx client, 5xx server
CORSBrowser blocks cross-origin unless the server sends Access-Control-Allow-*
PreflightAn OPTIONS request before non-simple calls
fetch quirkOnly rejects on network error — check res.ok yourself
CORS is server-side: a CORS error means the API must allow your origin — you can't fix it from the browser. It's a browser security feature, not a bug in your code.
◈ GraphQL on the Backend — Schema, Resolvers & Caching Backends ▶
Reference
One Endpoint, Client-Shaped Responses
GraphQL exposes a typed schema through one endpoint; the client specifies exactly which fields it wants. It solves REST (Representational State Transfer)'s over- and under-fetching, at the cost of new complexity. 
query {
  user(id: 42) { name, orders { total } }   # exactly these fields

ConceptDetail
Schema & typesStrongly typed contract
Query / Mutation / SubscriptionRead / write / realtime
ResolversServer functions that fetch each field

🔴 Realtime — WebSockets, SSE (Server-Sent Events) & Polling Backends ▶
Reference
Pushing Data to the Browser
HTTP (HyperText Transfer Protocol) is request/response — the server can't just push. For live features (chat, notifications, dashboards) you need a different transport. Pick the lightest one that fits.
OptionUse
WebSocketsFull-duplex, persistent — chat, games, collaboration
Server-Sent EventsServer→client stream over HTTP — feeds, notifications (simpler)
Long pollingFallback where sockets aren't available
Short pollingJust refetch on a timer — fine for low-frequency updates
Don't over-engineer: if data changes every few minutes, polling is simplest. Reserve WebSockets for genuinely bidirectional, high-frequency needs. SSE is the underrated middle ground for one-way streams.
🔑 Frontend Auth — Tokens, Cookies & OAuth (Open Authorization) Backends ▶
Concept
Logging Users In, Safely
Auth on the frontend is mostly about where you store the credential and how you attach it. Get this wrong and you ship an XSS-exploitable token. Ties directly to the security domain's OAuth/session cards.
ApproachDetail
HttpOnly cookieJS (JavaScript) can't read it → XSS-safe; pair with SameSite/CSRF protection
JWT (JSON Web Token) in localStorageConvenient but XSS-readable — widely discouraged

🔄 Data Fetching Patterns — React Query & Caching Backends ▶
Reference
Server State Is Its Own Problem
Fetching data is easy; keeping it fresh, cached, and in sync across a UI (User Interface) is hard. Libraries like React Query (TanStack Query) and SWR handle the whole lifecycle so you don't reinvent it per component.
FeatureDoes
Caching & dedupSame query used twice → one request
Background refetchRevalidate stale data on focus/interval
Loading/error statesBuilt in — no manual flags
Optimistic updatesUpdate UI instantly, roll back on failure
Why it matters: hand-rolled useEffect + useState fetching leads to race conditions, duplicate requests, and stale UI. A query library turns all that into a hook — genuinely one of the biggest quality-of-life wins in modern frontend.
